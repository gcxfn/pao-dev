# 受控自进化实施路径：S8—S9

日期：2026-11-08。范围与阶段状态见[实施总计划](2026-11-08-内置记忆与受控自进化实施计划.md)。记忆、来源、预算和恢复基础见 [S0—S4](2026-11-08-内置记忆实施路径-S0-S4.md)、[S5—S7](2026-11-08-内置记忆实施路径-S5-S7.md)。本文的新增文件和接口均为待实现契约。

## 运行链路与边界

```text
真实失败/用户纠正/有依据的机会
  → collectEvolutionProblem
  → 判断未采用经验、调用方式、资源实现或核心问题
  → 明确可改资源与适用范围
  → 冻结原问题、正常用法、独立保留样例
  → 在候选副本生成局部改动
  → 用相同输入运行旧版与候选
  → 证据通过且仍在授权范围
  → 保存新资源版本
  → 事务更新 effectiveVersion
  → 新任务绑定新版本 / 运行任务在安全点切换
  → 观察实际使用
  → 具体退步证据触发回退及通知
```

普通模型错误不直接触发改文件。先查是否已有经验但没用到；如果改检索/提示策略即可解决，不改命令工具。需要改核心、存储、权限或预算规则的问题输出具体开发建议。

### 资源如何分开处理

| 资源 | 可自动改的内容 | 保持由核心控制的内容 | 加载路径 |
|---|---|---|---|
| PAO 自有技能、任务模板 | 允许目录中的正文、示例、局部工作步骤 | 正式需求、权限、预算和验收条件 | 现有 skills/resource loader 的附加资源路径 |
| 记忆策略 | 既有接口允许的检索参数、条件选择、提炼提示 | 表结构、来源可信分类规则、纠正优先和删除语义 | 内核读取受控策略资源，任务绑定版本 |
| 自定义命令、扩展工具 | 明确资源中的参数组织和工具实现 | 工具能力授予、可写边界和正常宿主权限检查 | 现有扩展加载入口；换版在会话安全点 |

核实的执行能力：`cards/process.ts::runCardProcess` 提供参数数组、工作目录、超时、取消和进程树停止；`cards/verifier.ts` 提供验收解析和影子目录；这些能力不等于操作系统沙箱。现有 `ExtensionToolContext.executeTool` 可使嵌套工具调用经过统一验证、钩子和权限检查，应优先使用。

按可信本机合作者的范围实现：冻结验收、限制候选可改文件、通过现有受控工具执行、验证实际结果、发布前核对差异。不得把候选代码直接载入正式会话来“试试看”；任意 Node 扩展可以直接访问文件/进程，若某类资源无法沿受控入口执行，应明确该类尚不具备自动验证/发布条件，列出缺口，不声称仅靠路径白名单已经隔离，也不因此扩建通用安全平台。

### 状态和接口

| 对象/接口 | 必要字段或参数 | 转移规则 |
|---|---|---|
| Problem | problemId、sourceIds、任务/资源版本、实际失败、原因判断、适用条件 | observed→classified→candidate 或 no_change/development_suggestion |
| Resource | resourceId、类别、允许目录、加载方式、能力范围、effectiveVersion | 只有用户能扩大资源与能力范围 |
| Candidate | candidateId、problemId、resourceId、baseVersion、差异、testPlanId | proposed→testing→passed/failed/cancelled；passed 不等于 active |
| Validation | 冻结输入、旧版结果、候选结果、正常样例、保留样例、费用引用 | 验收依据存核心管理位置，候选目录无写权限入口 |
| `activateCandidate` | candidateId、expectedEffectiveVersion、授权记录引用 | 全部前置仍有效才事务更新资源当前版本 |
| TaskBinding | taskId、resourceId/versionId 列表 | 开始时固定，安全点换版记录前后值 |
| `rollbackResource` | resourceId、badVersion、previousVersion、证据 sourceIds | 更新当前指向、停用失败版本；不删除已发生的业务结果 |

候选、验证、生效历史由同一个 SQLite 库管理；资源文件归 evolution 版本目录。文件先完整发布再将数据库状态标可用，生效指向只存数据库一处。没有再维护第二个 `current.json` 正本。

### 带证据的问题入口与界面施工

核实日期：2026-11-09。参考 LobeHub `builtin-tool-self-iteration` 的意图声明与后续处理分离，来源见总计划 §2.2。PAO 将其落入既有 Problem→Candidate→Validation 链路，登记建议不等于修改资源或启动付费验证。

#### 后端入口（S8-03/04/05）

在 `K/evolution/problems.ts` 增 `declareImprovementIntent`，与失败回执、用户纠正共用问题登记函数。建议输入包含 kind（记忆策略/技能/命令或扩展/系统缺口）、action（修改/创建/合并/删除/建议）、summary、reason、expectedBehavior、actualBehavior（有实际结果时）和 evidenceRefs；ref 指向已存在的来源、消息、工具调用、任务回执、记忆修订或资源版本。resourceId/baseVersion 有明确目标时提供，未定位目标允许待分类。

宿主从当前调用补入 projectId、taskId、sessionId、entryId/toolCallId，不信任模型自报当前身份。服务解析证据引用，保存原引用及可回读来源；无证据的泛化建议返回不受理理由，不伪造失败记录。有依据的机会可以登记，但 occurrenceCount 只能由独立事实来源计算，单次建议不能标“重复失败”。同一来源、目标与动作重复申报复用 problemId，不为查重计算摘要指纹。

返回 `{accepted, problemId?, disposition, reason?}`，disposition 表达待分类、合并到已有问题、无需改动或转开发建议。声明接口只写问题及来源关系，不具备资源写入和发布能力；普通记忆新增/纠正仍走 MemoryService。登记后按原 S8-04 分析是否未采用已有经验，再按已授权类别确定资源和验证，核心缺口进入 development_suggestion。模型自报 confidence 不作为入库事实、验证通过或发布门槛。

将 `K/friction/drafts.ts` 已有失败事实的产生调用点接到同一登记函数：保留原记录用途，以稳定来源引用关联，不定期解析 Markdown 生成另一份计数。模型主动申报经现有工具注册入口暴露；工具执行完成只返回登记结果，后台仍等待空闲、授权范围和预算允许后继续。

#### 详情查询与 UI（S8-12）

`K/desktop/memory.ts` 增 `readDesktopEvolutionProblems`、`readDesktopEvolutionDetail`、`readDesktopEvolutionValidation`，经 S4 bridge 返回问题、候选、差异、验证和范围。列表可按项目、资源类别、处理状态筛选；详情保留 problemId、candidateId、baseVersion、testPlanId、来源及费用引用，后续 S9 直接扩展同一 DTO。

记忆页增加“自进化”类型入口。`evolution-detail.tsx` 顶部显示具体问题、适用条件、当前阶段和目标资源；下面按“问题依据、改动、验证”分区：

- **问题依据：** 展示预期与实际行为、事实日期、发生次数及来源跳转；区分真实失败、用户纠正、有依据的机会。合并问题可展开各来源，保留未采用经验/调用方式/实现缺陷的分类理由。
- **改动：** 展示基础版本、候选版本、实际文件清单及差异；复用既有文本差异组件，窄屏使用逐行差异。删除、合并或保留现状按实际结果展示。候选尚未验证时标“待验证”，验证通过但未发布时标“验证通过，尚未生效”。
- **验证：** 原问题、正常用法和独立保留样例分组，逐项显示旧版结果、候选结果、通过/失败/未完成、回执及费用。任一关键失败保持可见；环境错误为未完成，不画成业务失败或通过。用户可回查保留样例，候选生成器仍不能读取其内容。

页头给出当前受阻原因，如范围外、等待额度、基础版本已变化或来源失效。S8 页面提供查看及回到原任务/开发建议入口；发布操作按 S9 的服务能力接入，界面不能把 passed 本地改成 active。

#### 验收与交付顺序

先打通一个真实回执→Problem，再接主动声明工具及重复归并，随后接详情 DTO 与界面。`KT/evolution-problems.test.ts` 覆盖稳定引用、重复声明、单次机会、无效来源、系统缺口及来源删除；断言登记后资源文件未改、模型验证调用为零。S8-12 的真实 Electron 用例核对差异对应 baseVersion、失败与未完成分别显示、每条依据可回读；这些机制验证与 S8-13 真实改进分列。

**具体顺序：** 03→04 形成真实问题及资源建议→按总计划 C4 已确认类别登记范围→01→02→05→06→07→08→09→10→11→12→13。范围内的具体资源不重复请求授权；扩大到用户资源、核心或其他未授权能力时再由用户决定。

### PAO 具体实现路线

下列接口为待实现契约，分别落实在原 S8-01—13 内；参考调研已完成，实施从真实问题及代码开始。

1. **问题输入（S8-03/04）。** `collectEvolutionProblem` 从失败回执或用户纠正取得 taskId、sourceIds、已用记忆修订、资源版本和失败条件。先读取 S3 使用事件，判断是未召回、已注入未采用、参数误用还是资源逻辑错误。未采用正确经验时先改受控提示/检索策略；核心缺陷输出开发建议。只有资源行为可改善才创建 Problem，重复同一来源复用已有 problemId。
2. **资源与存储（S8-01/02）。** `policy.ts` 从已授权类别映射到明确 resourceId、资源根和允许操作；`resources.ts` 读取当前文件和加载方式并保存 baseVersion。S8 在同一 SQLite 库按实际需要建 evolution_resources、evolution_problems、evolution_candidates、evolution_validations，来源关系用独立关联行保存 sourceId/memoryId/revision，便于沿删除入口查找；S9 再建版本、激活及任务绑定记录。正文文件放现有 evolution 路径，库内存身份、状态、定位和回执。
3. **单次改进契约（S8-01/07）。** `proposeCandidate` 输入为 problemId、sourceRefs、resourceId、baseVersion、允许修改文件、开发样例与具体失败、任务预算、AbortSignal。输出为 changed（candidateId、文件差异、理由、usageRefs）或 no_change；请求错误、取消和预算停止沿现有错误/状态入口返回。内核生成候选 ID 并绑定基础版本，模型只输出允许文件的编辑操作和依据。
4. **冻结验收（S8-06）。** `freezeValidationPlan` 保存三组：原问题复现、受影响正常用法、独立保留样例。每项固定输入、初始文件、允许工具、完成判据及模型配置；开发组可向生成器反馈，保留组只交验证器。先运行旧版，真实问题必须能出现对应失败；复现不了则回到问题分类，不继续制造改进。testPlanId 与 baseVersion 绑定，测试及期望不在候选可写目录。
5. **局部候选生成（S8-07）。** 将已登记基础版本复制到 candidates/<candidateId>，读取开发组失败回执；用 `modelRegistry.find/streamSimple` 和既有档位、认证、专用用量会话请求修改。返回内容按文件逐项应用并比较实际正文；未改动直接 no_change。先实现单次局部修改；开发组失败时最多自动生成 3 个不同候选，保持同一 problemId、基础版本、预算和输入范围。相同差异不再次付费验证；有合格候选即停止搜索。保留组失败结束本次改进，不能把保留答案回灌生成器后在同组重试。
6. **真实执行（S8-08/09）。** `runner.ts::runValidationCase` 为 baseline/candidate 各建独立 home、cwd 和 sessionDir，从同一初始文件复制。纯命令用 `runCardProcess`；技能效果用隔离验证进程内的 `createAgentSession`，显式传 agentDir、modelRuntime、sessionManager、resourceLoader 和 tools，工具只保留本用例必需能力。通过 additionalSkillPaths/additionalExtensionPaths 加载指定版本；默认自动发现不能带入正式 home 或另一候选。运行回执保存输出、退出码、相关文件变化、模型配置、requestId、费用及取消原因。子进程模型认证沿现有受控启动方式传入，不复制用户凭证文件。
7. **评估决策（S8-10）。** `evaluateCandidate` 用冻结判据逐项比较：原问题从失败到通过，关键正常用法及保留样例全部通过，范围检查通过，才能标 passed。启动失败、环境缺依赖或进程停止未确认标 incomplete，保留原因并停止发布；业务结果不符标 failed。若模型随机性使同一用例前后结论矛盾，才补做该用例的成对运行；证据仍不稳定则不宣称改善。总分仅用于报告，不能覆盖关键失败。
8. **用量与停止（S8-07/11）。** 每次生成/验证前写 attempt/requestId，预算沿 `reserveBudget/settleBudget/releaseBudget`，实际 usage 沿 `SessionManager.appendUsage`，聚合仅一次。首次真实验收无总额上限，但仍保留轮次、超时和取消。前台开始取消后台模型请求与验证进程，确认停止后写状态；重启只恢复已提交进度，未确认结束的尝试不当成可重新领取。
9. **来源与旧候选（S8-11）。** 发布前读取 sourceRefs 和 baseVersion；来源被删除时沿现有删除作业清除候选输入/回执里的目标正文，清理未完成就保持未完成状态；只保留排除所需定位。纠正、停用或基础版本变动导致依据失效时标待重评估，旧候选不得直接重新排发布。

**首个真实闭环（S8-13）：** 从已累计回执选一个文本技能错误，固定失败条件与正常样例；报告完整记录旧版实际失败、候选差异、开发组及独立保留组结果、总用量和适用范围。异常、取消及删除等机制用可控夹具验证，真实改进用实际模型运行；两类证据分列。

命令和可执行扩展逐类完成实际执行边界验证；文本技能的验证结果仅覆盖其已验证能力范围。S2 的提炼、来源和纠正契约由当前阶段继续实现，后续进化通过其公开接口读取。

### 版本控制与观察界面施工

**后端（S9-10—12）。** 沿 S8 的 evolution 详情增加 effectiveVersion、selectedVersion、activation/rollback 历史、taskBindings、观察回执及单资源 autoEvolutionEnabled。`mutateDesktopEvolution` 仅提供当前已实现的单资源停用自动进化与恢复版本动作，输入 resourceId、expectedEffectiveVersion 和目标 versionId（恢复时）。服务重新读取授权和验证状态；有冲突返回当前版本，不自动覆盖。恢复曾失败、未通过验证或依据已失效的版本只进入重新评估，不能经 UI 绕过发布判据。

停用自动进化沿 S9-10 停止新候选领取，保留当前有效版；响应明确是否还有正在收尾的任务。恢复版本调用既有版本/回退业务入口，返回操作 ID、实际当前版本和需要安全点切换的任务。页面用服务结果刷新状态，运行中旧绑定在真正重载完成前继续显示旧版。

**UI（S9-12）。** 在同一个 `evolution-detail.tsx` 增“生效与观察”区：

| 内容 | 显示与操作 |
|---|---|
| 当前生效 | 当前版本、适用项目/资源、启用时间、对应通过回执；与正在浏览的历史候选分别标注 |
| 任务绑定 | 任务名、实际 versionId、运行/等待安全点/已切换；可跳回原任务 |
| 实际观察 | 查看、实际使用、发布分别计数；仅实际使用关联成功/失败，无使用时显示“尚无使用结果” |

| 用户控制 | “停用此资源的自动进化”保留现行版；“恢复此版本”展示目标、当前版、受影响任务和实际验证状态，再提交服务 |
| 回退通知 | 简短说明资源、退步原因和当前有效版，链接到详情；已发生的业务结果单独列供核对 |

页面保持问题→候选→验证→生效→实际使用→回退的连续导航，切标签不丢选定版本。动作中、等待安全点、失败、已完成有各自状态；刷新或重开从服务恢复，不把关闭弹窗视为完成。布局沿 S4，同一详情组件按数据提供能力展示，不提前画空的“已生效”区域。

**验收（S9-12/13）。** 真实 Electron 验证停用一项后其他资源不变、选择历史版本后仍能识别当前有效版、后台切换时任务行显示实际绑定、版本冲突保留当前值、失败版无法直接恢复生效、回退通知可定位原因；读服务和实际任务绑定确认结果。重启后复查未完成操作与版本指向，复用 S9 原有中断测试，不再重复生成候选。

**具体顺序：** 固定版本→发布前置核对→更新有效指向→宿主加载与任务绑定→真实观察→判定退步→回退/运行中处理→用户控制→重启恢复→页面→发行验收。

### 发布、观察与恢复的实施路线

1. **形成版本（S9-01—03）。** `publishCandidate` 读取 passed 候选与 testPlanId，将已验证文件完整写入新 versionId 目录；短事务内重新核对当前 effectiveVersion 等于 baseVersion、来源仍有效、授权范围未变，插入 version/activation 后更新指向。文件失败不改指向，事务冲突保留旧版并标待重评估。生效事务不包含模型调用或进程执行。
2. **加载和任务绑定（S9-04/05）。** CLI 与桌面均在共享入口解析 resourceId→versionId，并写 taskBinding；资源加载器只接收该版本目录。运行中的任务继续使用固定版本；阻塞修复需先结束相关工具，在安全点记录新绑定并重载。新候选生成、后台取消和新版本写入均不能原地修改运行资源。
3. **使用与退步（S9-06—09）。** `observe.ts` 记录 viewed、used、patched 三种不同活动：查看详情是 viewed；任务明确选择该技能并引用 taskBinding 是 used；新版本发布是 patched。只有带实际执行回执的 used 才可关联成功/失败；仅资源已加载不能算实际采用。相关失败先核条件、模型配置与版本参与关系；可归因的正常用法破坏、原问题回归或用户明确指出退步形成 regression。`rollbackResource` 在当前指向仍是失败版时事务回到上一有效版，其他已生效修复不被旧回退覆盖。
4. **暂停和重启（S9-10/11）。** 关闭资源自动进化后停止新候选领取，保留当前有效版本；重启读取数据库的指向、绑定和未完成操作，完整版本直接加载，未发布目录不参与选择。仅暂停的后台运行按 checkpoint 续作；已失败或取消的候选不自动恢复为 passed。相关已发生业务文件/外部动作单独核对。

**定向验收：** 写版本中断、数据库生效冲突、旧任务与新任务并存、前台打断后台、用户停用、宿主重启、明确退步回退，以及回退期间另一修复已生效的场景。每个用例只检查其影响的状态/文件/加载行为；全部阶段正式启用仍沿总计划 C5。
