# 内置记忆实施路径：S5—S7

日期：2026-11-08。目标、依赖、状态和验收统一见[实施总计划](2026-11-08-内置记忆与受控自进化实施计划.md)。路径缩写和基础业务契约见[首期实施路径](2026-11-08-内置记忆实施路径-S0-S4.md)。本文的新增接口是实施约定；已有恢复、用量和执行入口以列出的源码为依据。

## 调用链与接口

### 项目接续

```text
进入项目 / 打开新会话
  → resolveMemoryScope
  → readProjectContext（目标、正式决定和文档引用）
  → readRecallSnapshot（计划、卡、意见、现场信号的只读现状）
  → renderProjectBrief（精简背景）
  → 等待用户任务，不派发

用户要求继续
  → readTaskContinuation(taskId)
  → 核对卡/实例/计划当前版本 + 成果定位 + 执行根
  → 得到“仍需做的具体下一步”
  → 沿现有任务受理/派发入口执行
```

### 成果复用

```text
执行完成及回执
  → registerArtifact（说明、条件、结果）
  → 已有稳定 Git 版本：引用 repo+commit+path
  → 无稳定版本：保存受管内容快照
  → 将 artifactId/versionId 关联原任务和回执

新任务
  → 检索用途与条件
  → resolveArtifactVersion（取准确版本）
  → 核对当前环境和输入输出
  → 在已有任务授权内复用
  → 保存本次结果及使用的历史版本
```

### 新增接口与状态归属

| 接口/对象 | 输入→输出 | 正本及修改边界 |
|---|---|---|
| `readProjectContext` | projectId→目标引用、约束、阶段来源、验收引用 | 数据库保存明确目标与引用；卡状态仍读卡 |
| `readTaskContinuation` | projectId/taskId→接续条目、来源、执行根、下一步 | 接续条目不改变任务卡状态；卡存在时以卡为准 |
| `recordProjectGoalChange` | 新用户决定+旧目标引用→新目标引用 | 新决定必须有用户来源，自动整理不能调整目标 |
| `registerArtifact` | 用途、条件、文件/版本定位、回执→artifactId/versionId | 已有版本只登记；没有稳定版本才保存内容 |
| `resolveArtifactVersion` | artifactId/versionId→可读内容位置、可用性、条件 | 缺失版本返回 unavailable，不返回最新文件代替 |
| `recordArtifactUse` | taskId、versionId、操作与回执→使用记录 | 复用行为仍走现有文件/执行入口 |
| `claimMaintenanceJob` | home、进程身份、允许任务类别→一项任务或空 | 扩展 S2 的队列表；不另建任务框架 |
| `runMaintenanceStep` | jobId、checkpoint、signal、剩余额度→进度/完成 | 每步提交后释放数据库事务；网络期间不锁库 |
| `recordMemoryUsage` | requestId、原任务/会话、用途、供应商用量→用量事件引用 | 原始用量归现有会话用量事件；记忆只引用 |

## S6

<a id="s6-backend-ui"></a>

### 成果关联与界面施工

核实日期：2026-11-09。参考 LobeHub `agent-runtime/transport/tool.ts` 的成果登记意图和执行器补齐来源、用量的方式；PAO 沿 `registerArtifact`、原任务回执和既有账本实现。源码入口见总计划 §2.2。

**后端（S6-01/05/08）。** `ArtifactVersion` 在已有 parentVersionId、originTaskId、sourceIds、receiptRef 上增加可选 sourceSessionId、sourceEntryId、sourceToolCallId、sourceToolName 和 usageRefs。字段只记录实际可取得的身份；人工登记没有工具调用时明确来源为人工，不生成虚构调用。usageRefs 引用现有 requestId/账本事件，不复制一份可独立修改的费用。

登记顺序为：执行结果与来源已落盘→确定交付文件清单及稳定版本→读取本次回执与可用用量引用→调用 `registerArtifact`→事务提交版本与关联。Git 版本和受管快照沿 S6-02—04；同一次来源登记重放时，通过已有任务/调用/成果身份找到原记录，比较确切版本与内容后复用。登记失败保留可重试结果，不能为了补登记重跑已执行的工具；后来到达的用量仅补引用。一个调用产生多个成果时共享同一 usageRef，不能重复计费。

桌面继续扩展 `K/desktop/memory.ts` 和 S4 窄桥，增加 `readDesktopArtifactDetail`、`readDesktopArtifactVersion`、`readDesktopArtifactUses`，参数为 artifactId、明确 versionId 及分页信息。详情返回元信息、版本列表、原任务/来源、验证状态与引用；版本读取返回所选版本文本或已有文件预览可用的受管引用，以及 unavailable 原因。大文本按现有文件读取方式分段；renderer 不用来源路径自行读历史文件。

**界面（S6-09）。** 在记忆页增加“成果”类型筛选，列表显示名称、用途、版本可用性和最近验证状态；进入 `artifact-detail.tsx` 后依次显示用途与适用条件、当前选定版本、内容预览、生成来源、验证结果、复用记录。

- 版本选择器展示版本时间、来源任务和验证状态；切换同时更新预览、来源与回执，标题标明历史版本。
- “查看生成过程”定位 sourceEntryId/toolCallId；“查看验证”打开对应回执；来源缺失时保留版本说明并显示缺失。
- “预览版本”读取确切内容；“打开当前文件”作为单独操作明确指向工作树，不能与历史预览混用。
- “在当前任务复用”先展示选定版本、目标和适用条件，经已有任务入口承接；页面浏览、切版本和预览均不执行代码。复用结果记录到本次任务，旧验证结果保持原样。
- 成果费用显示“关联请求费用”及共享归属；无法准确拆到单个文件时显示共享说明，不把累计任务费用标为该文件独占成本。

**验收（S6-11）。** 内核测试覆盖一次调用产生两份成果、登记重放、用量迟到、人工登记及原临时文件删除；确认版本数、调用次数和账本引用正确。真实 Electron 在同一成果两个不同版本间切换，断言预览、来源和验证一起切换；版本不可用时不能显示当前文件作为替代。完成这条链后再做跨任务复用。

**具体顺序：** 成果元信息→Git 定位/非 Git 保存→内容复用→版本链→检索→当前条件判断→实际复用→页面→解除引用。成果不因模型说“可能有用”就整目录归档，以实际产生的交付文件和回执为输入。

## S7

<a id="s7-backend-ui"></a>

### 费用与上下文界面施工

核实日期：2026-11-09。参考 LobeHub `context-engine/tokenAccounting` 的来源拆分，复用 PAO 请求装配和用量事件。S7-06/08/10 分别承担聚合、采集、展示，S7-12 验证完整链路。

#### 后端采集与查询

1. `K/memory/usage.ts`（新增，名称与已有账本职责分开）只聚合现有 usageRefs、memory_usage 和 job 归属，提供任务用途分组与请求明细。以账本 requestId/事件身份去重，失败、取消后的已发生费用仍计入；未知费用单列，并将可知部分标为已知费用小计。
2. 在共享内核最终请求装配处，基于实际发送的消息与工具定义记录 `ContextUsageSnapshot`：requestId、taskId/sessionId、采样时间、estimateMethod、各来源 estimatedTokens、estimatedTotal、可用时的模型上下文额度及省略原因。新增 `K/memory/context-usage.ts` 负责对已有请求投影分类和聚合，挂接点选 pi 公开的最终请求/上下文钩子；实现前核对钩子能看到的字段，覆盖不到的字段明确标未计入，不能声称是完整请求总量。
3. 来源分类为系统指令、对话正文、动态记忆、工具定义、工具调用与返回、附件内联内容、其他。单段内容只进入一类；记忆通过已有 custom message 身份识别，附件元数据与工具读取结果按实际所在消息计入。推理/供应商签名等能观察且确实发送的内容归其他，无法测量的多模态部分标未知。优先复用内核既有 token 估算入口，不引入第二套 tokenizer；估算占用与供应商真实 input/output/cache usage 分开保存和展示。
4. `readDesktopMemoryUsage` 沿 S4 契约补可选费用引用；新增 `readDesktopMemoryMaintenance`、`readDesktopTaskMemoryCost`、`readDesktopContextUsage`，均由同一公开桌面桥返回纯 DTO。任务成本返回用途分组、去重后的请求明细、未知项和共享引用说明；上下文查询按 requestId 返回快照，找不到时明确“尚无该请求记录”。
5. 正常请求不为生成统计额外调用模型。快照随已有请求归属保存，页面重开读取同一记录；来源内容删除时沿既有删除作业清理相关正文，统计只保留不含正文的数量和允许保留的身份信息。

#### 附件策略与触发条件

现有 `B/src/session-supervisor-utils.ts::injectFileAttachmentPreamble` 发送文件名、类型、路径和大小，全文由工具按需读取。S7 维持这一路径，统计元数据及实际工具返回占用；没有全文内联时不新建附件裁剪器。

若后续实际支持全文内联且出现附件使请求超预算，在该功能实现中复用上下文估算：先预算系统、工具、对话与记忆，再给附件分配剩余空间；装不下的正文改为短预览和可读取的来源标识，保留完整文件及分页读取入口。只有全部附件预览后仍超限才进入原有会话压缩流程。完整来源不可回读时明确失败，不悄悄发送残缺材料。该分支随内联附件功能验收，不作为当前 S7 无条件施工项。

#### UI 与用户操作

记忆页增加“运行与用量”视图，包含整理状态和任务用量；“本任务参考”提供进入同一任务用量的入口。`memory-activity.tsx` 显示等待、运行、让出前台、失败/无额度及最后处理时间，状态直接来自队列；可查看失败原因和关联任务，不提供绕过预算的强制运行按钮。

`memory-task-usage.tsx` 按提炼、嵌入、检索、验证等用途显示请求数、实际 token 和已知费用，展开后可定位请求与成果/候选。同一请求在多个关联项下可见，总计只算一次。注入显示 token 占用，不再作为独立模型调用重复收费；只有已记录的明确采用才显示采用次数。

`memory-context-usage.tsx` 使用按来源分组的横向条形图与数值表，标题显示所选请求时间及“估算”；有额度时显示占用与剩余，无额度时只显示数量。点选类别展开对应消息/工具名称及省略原因，不展示凭证或原始请求 JSON。旁列供应商实际输入、输出及缓存用量，缺字段显示未知；不把缓存数值缺失画成零。窄窗口改为纵向列表，全部详情通过键盘可达。

#### 定向验收与顺序

先完成 requestId 归因与聚合，再接上下文采集及 DTO，最后接 UI。`memory-usage.test.ts` 增加多成果共享请求、失败计费、迟到用量和未知价格；`memory-context-usage.test.ts` 验证同段不重复计入、工具定义计入、附件仅路径的真实输入、缺少可见字段时明确不完整。估算不得改变实际模型请求内容。

真实 Electron 从任务参考进入用量，选择两个 requestId，断言图表、请求时间和明细对应切换；退出重开记录仍一致；开始普通任务后整理显示让出，页面状态与队列一致。费用重算错误修聚合，分类错误修采集映射，迟到覆盖修请求归属；这些断言通过后进入 S7-12 发行验收。

**具体顺序：** 统一后台队列→宿主空闲调度→跨进程领取→增量规整→索引维护→用量归因与限额→观测→一致性恢复→页面→同任务比较。调度器只运行定义好的记忆作业，不扩成通用工作流平台。

### 经验整理与维护的实施路线

参考 Hindsight 的归纳来源关联与提交前来源复核、Hermes 的 view/use/patch 分离和空闲维护。源码依据见[调查文档 §7](2026-11-08-记忆与自进化方案调查.md#7-源码核实与采用结论)。具体代码仍使用 PAO 的来源、修订及队列机制。

1. **队列入口（S7-01—03）。** 现有 `extraction-jobs.ts` 已有 `createJob/claimJob/advanceCursor/completeJob/failJob/recoverJobs`；扩展实际表和类型支持 jobKind，旧提炼任务默认 extract。`maintenance.ts` 按固定类别调处理函数。job 的来源游标和运行状态只存在队列表；宿主只发送空闲、前台开始和关闭信号。
2. **限定处理范围（S7-04）。** `organize.ts::collectChangedMemories` 从 cursor 读取新增/修订项，按 projectId+department 和明确 task/branch 条件分组；只选同组有重叠主题或同来源的经验。没有变化直接结束。正式决定只整理关联和当前状态，不请求模型重新判断选择。读取输入同时保存 `(memoryId, revision)` 与 sourceIds 快照。
3. **结构化规整（S7-04）。** 先处理完全相同来源/正文及已存在的替代关系；剩余确需语义判断的组，经现有模型路由请求 keep、propose_merge 或 propose_experience，输出理由、适用条件及逐条来源引用。近似搜索仅发现候选，不能自动判定合并；语义候选和词法候选交替取前项并去重，避免同义第一名被融合排序挤出。具体合并仍经过既有 `mergeMemories` 的业务条件；被拒结果保留，不绕过服务直接写 SQL。
4. **归纳提交（S7-04/05）。** 将模型归纳标为 model_inference/tentative，sourceIds 指向实际原事件，额外在本次整理作业记录输入 memoryId/revision；同一归纳的来源数量不是确认条件。提交前在短事务内核对输入修订、usageState 及 source_exclusions；变化则丢弃该候选并按新游标重排，全部来源不可用则结束。复用 `extract-commit.ts` 的可用校验/去重逻辑，保持一个提交规则正本；新增经验才进入嵌入队列。
5. **使用反馈（S7-08/10）。** 读取 S3 的 search/inject/expand/used 事件，按 memoryId/revision 汇总；次数由事件聚合，不另维护手工计数正本。成功/失败必须关联任务回执，单纯 used 仍不表示成功。S7 对有证据的重复、矛盾和适用条件失效给出维护候选；技能文件的改动进入 S8，S7 不直接覆写技能或自动扩展授权。
6. **中断及费用（S7-02/06/07）。** 每组提交后推进 cursor；模型请求不占数据库事务；前台任务到来即取消尚未完成请求，已提交组不重跑。沿 `SessionManager.appendUsage` 和既有预算预留/结算记录一次用量，归属 jobId/sourceSessionId；未知用量明确未知。首次验收不限总额与日常后台额度按 C3 区分。

**定向验收：** 无变化零模型调用；不同项目或相互排斥条件不合并；整理期间纠正/停用/删除后旧归纳不提交；模型推断不能变 confirmed 决定；仅展示或注入不会记成 used；重复已提交批次不重复调用或计费；取消后按已提交 cursor 继续。来源原文清除与索引重建沿既定删除契约执行。
