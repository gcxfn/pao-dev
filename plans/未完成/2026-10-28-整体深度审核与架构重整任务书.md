### 1.2 反复修的症状

r2 到 r37 几乎每轮停在不同位置：环境（软件源、Docker 地址池耗尽、网络冲突、WSL 内存）、装配（kit 目录当文件传、子进程探针、两个配置目录环境变量不一致）、协议（回执缺字段、JSON 被说明文字包裹、命令引号转义）、状态一致性（地图过期、审核版本误判、状态文件发布）、生命周期（部长启动握手超时、会话上下文失效、关闭顺序）、人工门（无人值守时卡在人工确认和界面恢复门）、观察器（漏认评分容器、终态事实）。每次修复本身大多正确且局部，但下一轮又停在新位置。最新 r37：两张实施卡都已交付，卡在“须用户在界面显式确认”的恢复门，审核节点从未启动，官方评分没有运行。

### 1.3 初步判断（交给审核证实或推翻）

1. **链太长**：一次完整运行要经过十几次跨进程、跨角色的交接，每一跳有自己的契约；整链成功率是每一跳成功率的乘积。一小时一轮真实运行、一轮只暴露一处，收敛不了。
2. **“无人值守”不是一等概念**：产品默认的人工门、界面恢复门、裁定转人工会泄漏到基准运行里，只能靠逐个配方开关去补。
3. **交给模型的手续太多**：58 个工具，加上固定顺序的多步手续（逐项接受偏差→交卷→匹配裁定规则→推流），每一步都可能被真实模型做偏。
4. **同一事实多处保存**：卡文件、流程实例文件、回执、地图、判定包、账本、锁文件各存一部分，互相核对的代码越补越多。
5. **基准跑的不是产品本身**：基准宿主是桌面代码的打包副本，加上每轮复制冻结件和手写临时脚本，harness 自己成了故障源。
6. **离线检查没覆盖真实组合**：已有四部门固定回应测试，但没有用基准同一份配方、同一宿主路径、带真实模型常见偏差和故障注入跑通整链，所以问题只能在真实运行里暴露。
7. **过程成本高**：每轮冻结、摘要回执、主控签收、长篇留档，单次迭代的时间和上下文开销都很大。

## 3. 本轮原则

1. **先删后补**：每个问题先问“这一跳、这个状态、这个工具能不能不要”，再问怎么修。新增机制必须同时删掉旧机制，或写明为什么不能删。
2. **程序能确定的事不交给模型**：回执里的程序事实（改了哪些文件、跑了什么命令、退出码、版本）由程序采集；模型只给判断和说明。结构化结果走带类型的工具参数，不靠从自由文本里解析 JSON。
3. **每个停点都有主人和出口**：停住时必须说明谁能解除、无人值守时怎么解除、超时会怎样。
4. **一个事实一个家**：每种事实只由一个模块保存，其他视图从它派生。
5. **测的就是产品**：基准、桌面、终端走同一套宿主装配，不再为基准维护代码副本。
6. **离线先红后绿**：修历史故障前先写能复现它的离线用例；真实运行只做最终确认。
7. **兼容契约照旧**：卡片中文 frontmatter 键、公开工具名、配置键、用户数据目录属于兼容契约；要改必须给出迁移与回退，并在 P2 请用户确认。内部实现可以重写。

## 5. 离线整链彩排（本轮核心验证手段）

“彩排”指：不调用真实模型、不需要 Docker，在本机用基准同一份部门配方与流程（与 `kit.json` 等价）、同一套宿主装配（主控、部长、工人真实子进程）和真实 Git 工作目录，完整跑一遍受理→侦察→规划→实施（工人改文件、自测、回执）→交付→审核→流程结束。模型换成“脚本化模型”：按角色和当前可用工具返回预先写好的回应。

必须支持的偏差与故障注入（来源于历史运行，A1 补全）：回执缺字段、JSON 被说明文字包裹、工人自报未运行（not_run）、工具参数引号与转义、模型不按顺序调用工具、子进程启动慢或握手超时、子进程中途退出、地图过期、需要人工确认的门、宿主关闭后恢复。

同一套彩排还要能放进 Linux 容器运行（复用基准适配器），用来发现 Windows 与 Linux 的差异；这一层可以慢些，但不能需要真实模型。具体做法由 A4、A6 在审核中提出建议，I4、I5 实施。
