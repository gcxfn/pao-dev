# PAO v2 全阶段总计划

建稿：2026-10-02。状态：**全路线已编制；各阶段未据此开始实施**。

依据：需求 §1—§6、架构 §1—§9、项目与 plans 两级 AGENTS；本轮材料清单见 [来源](../附件/复用核验与来源.md)。当前代码进度未知，先核现场，不把“文档有了”当成“功能已完成”。

## 1. 总目标与保留边界

目标保持不变：以 pi 为内核（2026-10-02 起为 `PAO/` 源码 fork，原「自含扩展包」口径作废——R12），作为个人日常编码主力，终端先行，桌面端后做纯壳；四块必须能力为模型路由、skills/MCP、跨会话知识、子代理/工作流。

不恢复 SQLite Command Kernel、常驻服务、复杂恢复状态机、网状部门消息、hindsight 或第二套桌面内核。文件式卡片与知识正本不变。当前使用锁版 0.99.2；将来升级走适配，不因这次写计划自动追最新版本。

**本计划增加的是实施顺序、异常验收与可回退边界，不增加产品定位。** 新的解释或试运行参数标“建议”，先按 [契约修订](2026-10-02-实施前契约修订.md) 同步基线后使用。

## 2. 一次出齐的具体含义

M0—M3 均给出目标、复用、任务、依赖、交付、验收、不做与退出条件。后阶段不是空白提纲；也不是无视真实摩擦的逐日施工表。

每个阶段开工只做三件事：核对上一阶段证据及当前代码；冻结本阶段尚未选定的具体依赖/试跑上限；确认这份计划与现行规则无冲突。完成后修订差异即可，不重写整阶段方案。

保持横切路线：M1 把四块必须能力全部接起来；M2 在这些已能用的部件上加厚，而非长时间只造某一子系统。M2/M3 内部分“小批次”只是实施顺序，不改成新的长期里程碑。

## 3. 阶段总表

| 阶段 | 本阶段能得到什么 | 必须交付的能力 | 离场门槛 | 详细计划 |
|---|---|---|---|---|
| M0 | 能加载 PAO、能用 GLM 干真实活的 pi 环境 | 自含包、配置样例、冒烟、目录与摩擦日志 | 真实装载/工具调用有证据，必要兼容问题已明确 | [M0](2026-10-02-M0搭骨架.md) |
| M1 | 一个部门、一个执行 worker 的完整最小闭环 | 两档路由、卡/队列、直通蜂群、查库/入库、todo、skills、一个 MCP | 正常与失败/中断都走通；无误交付与未受控继续执行 | [M1](2026-10-02-M1各部分最小形态.md) |
| M2 | 有边界、可计量的日常多部门协作 | 星型协作、/派、保温、受限扇出、知识治理、大活流程 | 已启用能力异常可控，有真实任务与对照证据 | [M2](2026-10-02-M2各部分加厚.md) |
| M3 | 以同一个 pi/PAO 为内核的桌面入口 | 对话与取消、卡片看板、证据定位、项目切换、基础设置 | 桌面/终端状态一致；关闭/重连不双跑；不用桌面仍能干活 | [M3](2026-10-02-M3桌面壳.md) |
| 持续 | 长期可升级、可恢复、越来越少返工 | 锁版适配、备份恢复、知识淘汰、摩擦回归 | 每次维护有证据，未引入新常驻或第二真相 | [维护](../持续维护与升级.md) |

M3 不需要等所有可选 M2 升级项实现；需要 M2 的核心协作与终端契约稳定。worktree、高级重排、显式历史检索、专场对话等保留条件触发，不以“计划里列过”为由强行实现。

## 4. 依赖与开工顺序

`M0 → M1 → M2 核心稳定 → M3`。持续维护从 M0 的备份与日志开始，随版本增长，不叫 M4，也不做永远无法完成的一次性任务。

M1 内部顺序：**契约/最小计量 → 卡片与项目单写 → 单 worker → 路由与工具 → 知识闭环 → 一体化试用**。同阶段四块都交付，卡片先于蜂群，是依赖而非另开纵向阶段。

M2 内部顺序：**在线宿主与会话隔离 → 协作/依赖/预算 → 小并发与大活 → 知识加厚 → 对照与默认值校准**。没有 M1 的失败/取消/停机证据，不开扇出。

M3 内部顺序：**锁版 RPC 与最小壳验证 → 只读状态 → 写操作/取消 → 设置/项目切换 → 桌面真实试用**。先复用 pi 的实际事件与类型，不从 UI 倒推新控制协议。

## 5. 开工前要处理的剩余问题

R01—R05：worker 查库冲突、重试/依赖表述、直通卡验收与候选晋升、知识正本归属、后台与关闭契约。其余 R06—R11 涉及并行黑板、项目锁、计费、检索缓存、受限并行、插件叠加和无证据性能断言。

全部定位与建议已写入 [契约修订](2026-10-02-实施前契约修订.md)。这里不维护第二份规则正文。M0 无需等所有 M2 细节裁决，但不能跨过与当前实现直接相关的冲突。

## 6. 各阶段共同的交付方式

每个小批次只做一个可以独立检查的变化，产出对应代码/配置、必要测试、实际运行记录与摩擦。正式命令在首次实现后写入项目 AGENTS；计划中的接口意图不能冒充现成命令。

代码改动写回项目本体；测试记录、脱敏日志、截图与报告写当前目标项目的 `.pao/<任务名-YYYYMMDD>/产物/`。运行记录用 [模板](../附件/开工接口与记录模板.md)，证据正文只存一处，计划里链接引用。

每次开始先记录工作树基线；不得以回退为名删除用户已有修改。敏感资料、凭证、原始含密钥日志不进报告或公开仓库。本项目计划包不是授权修改其他项目、Vault、系统权限或全局工具链。

阶段结束按项目规则移计划到 `已完成/`、补完成日期，并维护 `plans/AGENTS.md` 的唯一当前焦点；没有完成证据不搬文件制造进度。

## 7. 同一把验收尺子

必须区分三种结论：**文件/代码已修改；静态检查或模拟测试已通过；目标 Windows 环境真实运行成功。** 不能以某一种代替另一种。

每阶段的专属测试列在各阶段计划中；共同口径在 [验收与度量](../附件/验收与度量口径.md)。严重问题包括：误标“已交付”、未知副作用下自动重做、未经允许外发、覆盖无关改动、未受控扩散调用、主会话关闭后受管任务继续执行、持久记忆错误地获得权限。

功能门槛与性能目标分开：正确性/控制性问题先修；token、时长和成本没有预定节省百分比，以实测决定。样本少时只报告样本结果，不把它写成普遍优势。

M2 评测沿原路线比较“无库单跑 / 有库单跑 / 有库受限蜂群”，固定任务、起点、模型菜单与验收，并把缓存冷热分开。每项合格交付成本计入所有角色、失败、审查、检索、沉淀维护，不只看主控。

## 8. 后期条件项：有计划但默认不开

| 条件项 | 启用证据 | 没触发时怎么处理 |
|---|---|---|
| 同项目并行写 worktree | 已多次因串行写形成瓶颈，接口已定，隔离/合并可验证 | 继续同项目一个写任务 |
| 超过最小规模的扇出/更多部门 | 独立任务的时间收益覆盖新增成本与整合开销 | 保持少部门、小并发，不固定复制角色 |
| 自动巡库卡 | ⚠️ 达原架构阈值，且在线宿主、预算、去重与部长复审已接通 | 只做机械标记和人工/部长处理 |
| 重排器、向量数据库 | 当前混合检索的实测问题不能通过适用范围、切分、钩子和淘汰解决 | 保持文件＋JSON 缓存 |
| 显式历史查询 | 真实任务反复需要追溯过去版本 | 默认不把归档混进当前依据 |
| 部门专场、实时 JSONL 流 | 桌面基本交互可用后确有反复摩擦 | 保留中继聊和卡片只读刷新 |
| 更强权限隔离 | 有绕过软纪律的证据，或任务风险要求强隔离 | 不伪称 M1 是沙箱；不承接越出当前保障的自动操作 |

上述条件不代表允许随意扩范围。每个条件项启用时，在已有 M2/M3 计划勾入当前批次并写原因；影响架构纪律时先修订正本，不偷偷上重平台。

## 9. 不确定项的处理

具体桌面框架、文件锁依赖、Windows 子进程约束手段、实际 provider 计费字段：已安排在首次需要它们的阶段核验，不用未知参数拼一份看似可执行的假配置。

API 能力存在但本机不通：先保留锁版与当前可用路径，定位扩展适配问题；只要原生能力可复用就不自建。确实涉及升级，走适配；确认扩展做不到才讨论原需求允许的最后手段，不在失败时直接 fork。
