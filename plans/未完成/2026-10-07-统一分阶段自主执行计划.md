## 2. 必须保持的架构与复用边界

内核业务位于 `PAO/packages/coding-agent/src/pao/`，桌面位于 `desktop/`。不合仓、不另起内核源码、不在 `PAO/` 同级创建仅大小写不同的目录。

| 责任 | 唯一归属及约束 |
|---|---|
| 工作流 | 配方、冻结图、节点轮次、依赖与审核分支；不能管理进程或读取 UI 状态作决定 |
| 卡与回执 | 执行、验收事实；状态经受保护接口修改，历史回执不可改写，旧尝试不能推进新轮次 |
| 派发 | 所有入口共用准入；启动前在锁内重核 owner、暂停、轮次、冻结版本和依赖 |
| worker/host | 会话、进程树、取消与停止确认；保留 StopProof，不能以父进程退出或布尔值代替整树停止证明 |
| 查询与页面 | 从权威数据投影；renderer 只走窄 IPC，不读内核文件、不建第二业务状态库 |
| 装配与宿主 | 注册、配置、启动和销毁；内核不得依赖 CLI/Electron；后台驱动随所属宿主生命周期停止 |
| 对话与 todo | 使用 pi 会话及其持久化/扩展能力；两端同一 todo 模型，不用 UI 清单推进卡状态 |

复用顺序：已有代码 → 标准库和原生平台 → 已安装依赖 → 核实后的公开成熟方案 → 最小必要实现。实施前查调用图和所有入口，不只修症状路径。

| 已定复用源 | 采用边界 |
|---|---|
| pi API、会话、现有 EmbeddedChat/消息组件、SDK driver、vendor 脚本 | 优先复用；不重写模型循环、聊天历史、进程体系或发行内核 |
| pi-studio、`@xyflow/react`、`react-resizable-panels` | 已有画布成果先核查，只借前端交互；按本地已安装类型适配，保留 MIT 声明 |

1. 主对话读取本阶段与上阶段放行记录，冻结本包需求编号、允许修改文件、明确禁止项、验收条件、接口与依赖。

3. **TDD（测试驱动开发）**：先把行为验收写为最小有意义的失败测试，运行证明“红”是目标行为缺失；再实现使其“绿”；最后整理实现并保持测试通过。修 bug 先留失败复现；保行为重构先补/确认特征测试，再证明改后行为不变。纯文档、文案或无需代码行为测试的改动做链接/渲染核验，由 TDD 审核解释适用范围，不为凑红绿写镜像测试，也不伪造已有代码的历史红灯。

### 4.3 四类独立审核

| 审核 | 必查内容 | 必须输出 |
|---|---|---|
| TDD 审核 | 红灯是否由目标缺陷引起、测试是否可执行、是否覆盖失败/取消/边界、是否真正测公开行为；是否削弱断言、跳过真验、把 mock 当集成 | 红→绿证据对应表；缺失测试及其触发行为；通过/不通过 |
| 对抗式审核 | 主动尝试错误 owner/轮次、并发/重复请求、断管、掉线、半写、退出、权限越界、输入注入、恢复竞态等当前功能可触发路径 | 路径/条件、实际或推导证据、影响、严重度；明确未能验证处 |
| 需求性审核 | 对原始需求逐条核实现、界面操作、语义、数据源、真实验收和非目标；检查漏做、擅改、假按钮、只有测试没有真实入口 | 每个验收编号→实现→证据；未满足项；通过/不通过 |
| 过度设计审核 | 挂载 ponytail review；查重复造轮子、无调用抽象/配置、无需求依赖、可以删的包装；不代替正确性审核 | 按技能给 file:line、删什么/用什么替代；没有可删项明确通过 |

审核必须完整阅读相关最终差异及调用面，不能只看实施总结。只报真实接口/数据能够触发的问题，不以偏好制造阻塞；争议记录依据，由独立审核确认“已解决”或“证据证明不成立”，不能由主对话单方面把有效缺陷改成不阻塞。**有效发现无未关闭项、四份结论均为通过**才叫审核完全通过——需求性与过度设计可合并一次派发（§4.2 第 5 条），但四份结论的放行口径不变。“待验”“环境受阻”“有条件通过”均不算通过。纯建议如被证实超出范围，记录理由，不借此新增需求。

四类审核统一分级：**P0**＝数据丢失、越权或失控执行等需立即停止相关执行的问题；**P1**＝核心流程不可用或关键验收不成立；**P2**＝受支持场景下的功能、需求或维护性缺陷；**P3**＝影响较小但有明确依据的缺陷。**P0—P3 的有效未关闭发现均阻断放行**，等级只决定处理次序，不是豁免条件；无缺陷依据的偏好或范围外优化单列“建议”，不占缺陷等级。审核子代理提出等级、影响与依据，主对话登记并组织处理；有争议先由原审核者复核，仍有分歧则由主对话另派未参与实施的独立审核者裁定并记录理由。裁定前保持未关闭；主对话不得自行降级、改称建议或删除发现来放行。
