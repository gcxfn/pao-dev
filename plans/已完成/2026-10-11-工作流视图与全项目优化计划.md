## 1. 现状结论

当前 23 节点工作流在桌面上主要有三个直接问题：

1. 运行实例使用 ReactFlow，配方只读图使用另一套固定 SVG；两处缩放、平移、适配和节点定位能力不一致。
2. 现有布局按依赖层排列，同层只按输入顺序排位。23 节点线性链约 5480px 宽，在 900px 左右窗口执行 fitView 后，节点文字会缩到难以阅读。
3. 画布没有工作流总览、状态统计、异常筛选、搜索定位和上下游高亮；节点切换、视口复用和键盘选择也存在同步问题。

审查还发现：

- 画布每个节点会重复扫描执行映射目录和卡文件，23 节点刷新时读盘量随节点数和映射数相乘增长。
- controlView() 与 v2 自动链会重复读取同一张卡，坏卡可能让整个实例视图失败。
- 运行图没有透出审核回边，视图无法解释“为什么回到前一步”。
- v1 工作流存在并发双跑、重复节点静默覆盖和缺少统一实例锁的风险；v2 卡标记写入顺序也有崩溃窗口。
- 高频桌面刷新、验收沙箱深扫、知识库入库巡检和 TUI 命令列表重建存在可测量的重复工作。
- 现有画布和性能测试主要覆盖 2～3 个节点，没有 23 节点、大量执行映射和异常卡的回归夹具。

## 3. 推荐的 23 节点视图方案

### 3.1 统一一套图视图

将配方图和运行实例图收敛到同一套画布模型与导航组件：

- 继续使用现有 ReactFlow 能力，给配方只读模式增加只读节点、缩放、平移、MiniMap、Controls 和适配全部。
- 共享节点尺寸、状态色、边类型、选中逻辑和详情栏契约；配方与实例只在“可编辑/只读”和“运行态字段”上有差异。
- 切换工作流或实例、节点数量变化、窗口大小变化时重新计算视口；保留用户主动缩放和位置，避免切换后空白或落在旧图区域。
- 视图状态只保存当前项目/工作流/实例的轻量偏好，不把临时布局写进业务控制正本。

### 3.2 三种查看方式

不要强行让 23 个节点全部以完整标题挤在同一屏，提供三个互相可切换的视图：

1. **总览**：适配全部节点，节点显示序号、短标题和状态；用于看依赖全貌、异常位置和整体进度。
2. **专注**：以选中节点为中心显示上下游路径，其他节点淡化或暂时隐藏；提供“上游/下游层数”选择和“一键定位下一个待处理节点”。
3. **列表**：按依赖顺序或状态列出节点，支持搜索、状态筛选和键盘选择；点击列表项同步定位画布和详情栏。

默认进入总览；用户点击节点、搜索结果或异常摘要后进入专注定位，但不强制改变用户已保存的缩放偏好。窄窗口提供“专注画布”按钮，暂时收起左右侧栏，切回后恢复选择、滚动位置和视口。

### 3.3 布局与连线

- 先保留 DAG 分层语义，再增加同层交叉最小化和稳定排序；排序依据使用依赖关系与原有输入顺序，保证同一配方不会每次跳动。
- 对长线性链支持纵向布局或分段换行，避免固定横向 5480px 长图；分支/汇聚保持依赖方向清晰。
- 普通依赖边默认不显示重复“依赖”标签；悬停、选中或异常时再显示必要标签。
- 审核回边使用独立边类型、颜色和图例，明确显示回到哪个节点以及原因摘要。
- 节点标题限制行数并提供完整名称提示；冻结配方外的实例节点单独标记“未映射”，不与真实起点混在第 0 层。
- 右键菜单按画布边界夹紧，详情栏按容器高度布局，不依赖固定视口高度。

### 3.4 状态、可访问性和中文界面

- 顶部增加节点总数、已完成、进行中、待确认、失败和未映射统计。
- 提供“只看失败/待确认/进行中”“搜索节点”“定位第一个异常”入口；控制区的节点选择改为可搜索、按状态分组，并提供“下一个待处理节点”。
- 选中节点时高亮上下游路径，其他节点降低视觉权重；状态不能只靠颜色，增加图标、文字和稳定的边框样式。
- 为节点、边、MiniMap、Controls 提供中文 aria-label；键盘 Tab→Enter/Space 选择节点时，同步右侧详情栏和外部选中状态。
- 为读屏用户提供节点的前置/后置节点文本摘要；SVG 连线继续可以视觉隐藏，但依赖关系必须有可读替代。
- Controls 与 MiniMap 的按钮提示统一为中文。

## 4. 分阶段实施

### 阶段 0：基线、代码图和夹具

**目标：** 在写代码前固定现状与边界。

- 核对当前三仓工作树，保留上一轮未提交修改。
- 用代码图检查画布、运行图、工作流读模型、v1/v2 控制和自动链调用链；代码图过期时记录并以当前源码复核。
- 建立隔离夹具：23 节点线性链、分支/汇聚图、审核回边图、一个坏卡、100/500 执行映射文件。
- 记录 700、900、1280px 窗口首次打开、切换实例、30 秒刷新、节点详情的耗时、读盘次数和截图。

**完成条件：** 有可重复夹具和改前数据；不修改正式项目数据，不调用真实模型。

### 阶段 1：画布基础和 23 节点可读性（P0）

**目标：** 先让用户能稳定看懂和操作大图。

- 统一配方/实例画布渲染和导航。
- 实现总览、专注、列表三种视图，以及窄窗口专注画布。
- 改进布局方向、稳定排序和交叉控制；增加视口生命周期管理和轻量偏好保存。
- 加入总览统计、异常定位、节点搜索、上下游高亮和长标题处理。
- 补齐中文键盘与读屏支持、边标签降噪、菜单边界处理和详情栏自适应。

**验收：**

- 在 700、900、1280px 宽度下可适配全部图；总览不要求完整标题全部可读，但节点序号和状态可辨识，专注/列表可读完整标题并能回到画布。
- 切换不同工作流、实例和节点数量后不出现旧视口空白；用户缩放、选中和滚动状态不无故丢失。
- 23 节点线性、分支、汇聚、审核回边均能找到节点、看懂方向并定位异常。
- 键盘和读屏路径能把节点选择同步到详情栏；不依赖真实模型。

### 阶段 2：运行态契约和读模型性能（P1）

**目标：** 让视图展示完整运行事实，并减少 23 节点刷新时的重复 IO。

- 在内核、SDK 和桌面契约中补充审核回边及必要的原因/目标节点字段；运行图与配方图使用同一边模型。
- controlView() 一次建立卡面、完成状态和依赖状态缓存；单个坏卡只标记对应节点为读取异常，其余节点继续展示。
- 画布一次刷新建立卡文件索引、执行映射索引和实例详情索引；节点详情复用索引，不逐节点重扫目录。
- 桌面执行流读取复用已发现的会话路径和 envelope revision；评估把全量刷新拆为按项目或按变更增量读取，但先以测量决定。
- v2 自动链在一次 tick 内复用卡状态索引；保留派发前的最终重读，避免用缓存掩盖并发变化。

**验收：**

- 审核退回在运行图中可见，目标和原因与内核记录一致。
- 坏卡夹具不会让其余 22 个节点消失；错误原因可定位。
- 100/500 映射夹具记录改前改后文件读取次数、耗时和内存；结果、重复记录、旧尝试、路径越界和坏文件处理保持一致。
- 30 秒刷新和节点详情不重复扫描同一目录；没有测量收益或引入失效风险的缓存不保留。

### 阶段 3：工作流正确性和并发边界（P1）

**目标：** 修复会让视图与实际执行不一致的状态问题，保持现有业务语义。

- v2 新卡先写入带 pao-workflow-v2 标记的卡面，再保存控制正本；失败时明确隔离孤儿卡或记录 fail-closed 状态，并补崩溃窗口测试。
- v1 清单解析拒绝重复节点名、重复卡号和跨节点重复归属，给出结构化损坏原因。
- v1 的 start/tick/confirm 统一使用实例锁；锁内重读清单并执行，避免并发请求覆盖映射或重复派发。
- v1 自动链在第一次异步读取前预留 in-flight；失败释放预留。明确同一批并发卡在停链时的语义，并按输入顺序归并报告。
- 视图层对“未映射、读取异常、并发冲突、暂停、审核回边”使用独立状态，不把错误显示成空闲或完成。

**验收：**

- 并发 accept/start/tick 压力测试不产生重复派发、孤儿清单映射或静默覆盖。
- 进程在 marker 写入、控制保存和清单保存的各崩溃窗口后，恢复结果可解释且不会绕过 v2 实例校验。
- v1/v2 合法、重复、损坏、暂停和审核回边夹具都能被 TUI 与桌面正确显示。
- 不改变现有停链、权限、租约、预算和回执规则；产品语义不明确的地方先记录决策再实现。

### 阶段 4：桌面、TUI 与全项目性能小包（P2）

按阶段 0～3 的测量结果选择进入，不把所有候选一次性塞进首轮：

1. **桌面刷新：** 按项目或 revision 增量读取，避免 turn_end/agent_end 高频事件重复读取所有项目。
2. **验收沙箱：** 按项目根和文件指纹缓存外链扫描，或按变更清单更新沙箱；安全扫描结果必须可追溯。
3. **知识库入库：** 当前条目只更新对应索引；全区巡检改为显式或节流后台任务。
4. **TUI 面板：** 按查询词和注册表版本缓存命令列表，避免每帧重建 SelectList；保留短终端滚动、搜索和中文提示。
5. **路径一致性：** 统一画布、看板和工作台的 Windows 大小写/斜杠/UNC 路径 key，补跨视图对齐测试。
6. **看板大数据：** 数百或上千卡时评估分段或窗口化渲染，保留拖放占位和键盘操作。
7. **启动速度：** 测量 worker 冷启动和内存后，再决定是否把 PAO 重模块改为按角色动态加载；先保证必要扩展注册不变。

**验收：** 每个小包都有改前/改后三次以上中位数、波动、重复工作次数和真实入口证据；收益不明确或增加复杂度就保留原实现并记录原因。

## 8. 审查补充纳入项

全项目审查在计划初稿后又确认三项，纳入阶段 4 的候选，优先级如下：

- **Worker 输出内存上限（P1/P2，先测量）：** worker runner 同时把完整 stdout/stderr 保存在内存，并把相同内容持续写入 live 文件。长任务会造成无界内存和重复写入。优先让 live 文件作为临时证据正本，内存只保留有限尾部和解析状态，结算时追加 trailer 后原子整理；补大输出回归并保留写失败回退。
- **验收扫描错误不能静默当作“无外链”（P1）：** 外链扫描的权限、I/O 和 readlink 异常目前可能被跳过，自动验收会继续。区分“确实没有外链”和“扫描不完整/无法判断”；无法判断时阻止自动通过或显式标为需人工处理。
- **开发文档入口一致性（P2）：** 根 README 的 Node 版本和桌面测试命令与当前 package.json、真实 Electron e2e 入口不一致。修正文档并让新手能按文档完成正确的环境检查和界面验证。

这些项仍遵循先建立夹具、再决定是否修改的原则；若阶段 0 证明某项没有实际收益，就只留下测量记录，不强行增加抽象。



## 9. 视图数据完整性补充

阶段 2 同时处理以下两个会直接影响 23 节点工作流理解的问题：

- **多卡节点：** 运行图当前可能只给节点绑定第一张卡。契约应至少返回卡数、状态汇总和可展开的卡列表；节点详情能跳到每张卡的轮次和回执，不要求用户先去看板猜剩余卡。

## 10. 树状主干、并行子流程与大图压缩方案

### 10.1 不把真实工作流改成纯树

PAO 的执行真相仍应是 DAG（有向无环图；节点可以有多个前置和后置）。纯树只能表达“一进一出”的层级：

- 分支后汇聚时，树会重复节点或丢失第二条依赖；
- 审核退回、循环和多入口时，树会把回边隐藏成错误的顺序；
- 只靠视觉位置推断并行，容易出现“看起来并行，实际仍串行”的误解。

因此建议增加一个“树状视图”作为 DAG 的压缩投影，保留一个“详细 DAG 视图”查看全部真实边。树状视图只改变展示，不改变卡片协议、调度和状态机。

### 10.2 推荐的树状结构

23 节点默认显示为少量可读的流程块：

- 开始
- 前置准备
- 并行组 A（例如 3 条分支，共 7 个节点）
- 汇聚/结果整理
- 人工审核
- 交付

并行组是一个可展开的复合节点。收起时只显示组名、分支数、已完成/进行中/失败统计和总耗时；展开后显示组内各分支。条件分支也使用同样的复合节点，但标注“条件分支”而不是“并行”。

底层模型保留每个真实节点和边，并给复合节点增加稳定的 groupId、parentId、branchId、joinId。审核回边在总览中显示为“退回到 X”的短标记，进入详细 DAG 后再显示完整回边。

### 10.3 并行不能只靠自动猜测

调度上使用明确的 Fork → Branch → Join 语义：

- Fork 创建并行组和分支；
- Branch 内节点按依赖执行；
- Join 是屏障，按配置等待全部必需分支，或在明确的“任一成功/允许部分失败”策略下继续；
- 每个并行组设置最大并发数、失败策略和取消策略；
- 运行记录保存 parallelGroupId、branchId、joinId、分支序号、开始/结束时间和失败原因，视图才能稳定还原并行关系。

可以用依赖关系初步提示“这些节点可能并行”，但默认不自动改变现有串行语义。只有用户确认或工作流版本明确声明为并行组，才改变调度。

### 10.4 减少画布面积的五层策略

1. **复合节点折叠：** 默认只渲染顶层节点，组内节点使用隐藏/展开机制；23 个节点可先压成 6～10 个流程块。
2. **分层布局：** 以 Fork、Join、条件和人工节点为主层，用纵向树状布局；组内再用局部 DAG 布局。
3. **分阶段分页：** 总览只显示当前阶段、异常组和关键路径；点击“展开全部”才显示完整图。任何被隐藏的节点仍在列表和搜索中可到达。
4. **语义缩放：** 远处显示图标、序号和状态计数，近处显示标题、卡数和回执；不把 23 个完整标题缩到同一屏。
5. **边界路由：** 组外只画进入组和离开组的边，组内边在展开后显示；普通依赖边不重复写文字，减少线和标签噪声。

### 10.5 适合 PAO 的布局实现顺序

先做不改变依赖语义的低风险版本：

1. 由现有节点/边生成 compound group 和树状投影；
2. 用 ReactFlow 的 parentId/sub-flow 和 hidden 能力实现折叠、展开；
3. 复用现有 ReactFlow 的缩放、平移、MiniMap 和 fitView；
4. 对顶层和组内分别做稳定的分层布局与交叉减少；
5. 只有现有布局仍无法处理复杂分支时，再评估引入 ELK layered；先做夹具、许可证和包体积评估，不直接把新布局库写进核心契约。

### 10.6 成熟项目的可借鉴做法

- Dify 的工作流以无限画布保存节点和边，支持条件分支、并行分支、迭代和合并路径；官方文档还提供并行模式的最大并发数设置。[Dify 工作流快速入门](https://docs.dify.ai/en/guides/application-orchestrate/creating-an-application) 、[Dify 并行分支介绍](https://dify.ai/zh/blog/accelerating-workflow-processing-with-parallel-branch)
- Dify 当前前端依赖中包含 elkjs，说明成熟编辑器会用可配置的分层布局处理复杂边和分支，而不是只按输入顺序排位。[Dify web/package.json](https://github.com/langgenius/dify/blob/main/web/package.json)
- React Flow 官方建议树形布局优先考虑 Dagre，复杂图和多连接点可评估 ELK；官方也提供复合节点、子流程、展开/折叠和通过隐藏节点减少大图渲染的做法。[React Flow 布局指南](https://reactflow.dev/learn/layouting/layouting) 、[React Flow 子流程](https://reactflow.dev/learn/layouting/sub-flows) 、[React Flow 展开/折叠示例](https://reactflow.dev/examples/layout/expand-collapse) 、[React Flow 大图性能指南](https://reactflow.dev/learn/advanced-use/performance)
- Dify 的公开问题也暴露了一个需要吸取的教训：并行执行即使真的发生，如果运行记录没有 parallel_id 等分组元数据，前端仍会退化成平铺列表，用户无法判断哪些节点属于同一并行组。[Dify 并行日志分组问题](https://github.com/langgenius/dify/issues/29320)

本项目不照搬 Dify 的业务节点或运行时，只借鉴“显式并行组、可折叠复合节点、分层布局、运行元数据完整”这四个机制。

### 10.7 新增验收样例

- 23 节点中选出 3 条可并行分支：总览收起后不超过 10 个顶层块；展开后能看到每个分支的状态和耗时。
- 同一组分支汇聚到一个节点时，Join 等待语义在执行和视图中一致；任一分支失败时，用户能看到“组失败/分支失败/是否继续”。
- 审核回边、条件分支、未映射节点和多卡节点不会被树状投影吞掉；详细 DAG 可回看完整依赖。
- 总览、专注、列表三种视图之间选中节点、搜索结果和详情栏保持同步。



## 11. 本轮方案的实施顺序调整

将树状/并行需求拆成三个可独立验收的边界，避免一次同时改变界面、协议和调度：

1. **先做展示压缩（P0）：** 树状投影、复合节点、收起/展开、语义缩放和详细 DAG 切换；执行仍按现有规则运行。
2. **再做并行契约（P1）：** 在工作流定义和运行记录中增加并行组、分支、汇聚、最大并发和失败策略；桌面、TUI 和日志先能完整展示。
3. **最后启用并行调度（P1）：** 只对明确声明且通过资源冲突检查的并行组并发执行；加入 Join 屏障、取消/失败策略和压力测试。没有明确声明的现有流程保持原顺序。

这样即使某个 23 节点工作流暂时不能安全并行，也能先获得树状视图和更小的画布。
