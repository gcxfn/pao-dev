# 实施前契约修订

建稿：2026-10-02。完成日期：2026-10-03（文档状态与目录闭环）。状态：**R01—R11 已于 2026-10-02 批入正本，本清单关闭并归档；不代表实现及真实验收全部完成**。依据为[K3 审查包](../附件/K3外部审查包-2026-10-02.md)开头的既有批准记录。原审阅内容保留，不改写成另一份现行架构；当前实现缺口与补验见[修复计划](存档-收编-2026-10-04/2026-10-03-审查修复与验收补齐.md)。

依据：[S1—S5](../附件/复用核验与来源.md)。性质分为“旧句订正”和“本轮新增建议”；下文不会把后者冒充已对齐决策。

## 结论

总体形状不用推翻。新版已经采纳精确指针、同项目单写、按类型处理失败、混合检索、受限补查、机械中转、项目隔离保温、知识适用范围和全角色成本口径。下一步应修正剩余矛盾、补运行边界，然后用阶段验收约束实现，不再追加新平台。

下文为 2026-10-02 审阅时的定位、建议与验收约定；其中当时的「待写回／可开工」不是当前状态。现行契约只维护在需求、架构与 AGENTS，后续 R26—R42 不追加在本已关闭清单中。

## R01｜查库权限与作用域：旧句订正＋执行约定

**原文定位**：架构 §6.3 仍说“worker 没有工具、不检索”；§6.4 已批准一次受限补查。§6.3 的标题与 §6.8 里程碑仍称“语义主路、词法兜底”，正文已改成双路混合。

**建议改文**：§6.3 保留部长完整查库、主控无查库；worker 仅有 §6.4 的受限入口。标题及里程碑表同步改成“词法＋语义双路；云端失败时词法独跑”。

**新增执行约定**：项目、部门、来源版本、外发许可从可信任务上下文绑定，不靠模型自行填写来授权。受限入口不能通过 `部门=全部` 或工具别名绕过限制。建议“一次”按同一授权轮次的卡累计，重试不自动恢复额度；需要加查先明确追加授权。

**验收**：第二次补查、跨部参数、其他项目同名条目不会被当作正式依据；禁外发同时覆盖条目、查询词和重建任务。对应 M1-05、G1-08/09。

## R02｜失败、依赖、终态：旧句订正

**原文定位**：架构 §2.1 已按原因路由，§3 第六机制与 §8.5 仍说失败自动重派一次。§2 写“后继卡只认终态”，但终态还包括失败、取消；§2.1 又写依赖等待“父卡”，与 `parent`/`depends_on` 新含义不一致。

**建议替换要义**：

> 重派遵从 §2.1 的失败类型、现场核对与同轮总尝试上限。仅当 `depends_on` 的所有前置卡均为“已交付”时放行后继；前置失败或取消不算满足。`parent` 只表示协作归属与预算，不能替代依赖。无法推进时派生显示原因，不新增等待状态。

卡片格式也统一为 §2.1 已选定的 YAML frontmatter Markdown，删去 §2 开头“JSON 或 MD”的可选歧义。原已否决决策按修订规则留日期说明，不静默抹去历史。

**验收**：前置失败/取消不误放行，缺输入不空跑；旧尝试回执不能结新尝试。对应 M1-02、G1-02/04/05。

## R03｜直通卡验收与知识晋升：本轮新增澄清

**原文定位**：§2 要部长核毕才“已交付”；§6.5 微任务不起部长，主控把候选写入待验证；§6.6 又把入库三选一绑定部长审回执。

**建议定清**：直通卡 owner 为主控会话，扩展收回执和运行证据；低风险可判的验收由确定性检查完成，主控依据结构化结果落状态。判断性或高风险验收，另派审查或交人，不让主控读大篇执行日志。

主控写 `待验证/` 是**候选投递特例**，不是写正式知识。候选写入由扩展执行、去重、留来源。正式晋升仍需部长审核；M1 可按需启动一次知识审核会话，不需要 M2 的长期保温。没有可沉淀内容，明确记录“无增量”即可结卡，不为跑通链路捏造知识。

直通卡初始指针来自已批准模板或用户输入；需要重新作知识准备时不勉强直通，可转常规卡。微任务不能因为没部长而永久卡在待审。

**验收**：分别跑“无知识候选直通完成”和“候选落池后经部长晋升”。对应 M1-03/05/07、G1-03/10。

## R04｜知识正本与上级公约：本轮新增归属澄清

**原文定位**：架构 §6.2 已定 PAO 专属教训住部门库；项目 AGENTS 上级嵌入区仍规定记忆不散落工作区、经验教训统一进 Vault。项目局部规则未明确例外如何获得上级授权。

**建议处理**：通过原有 agents-md-authoring 流程确认并同步“PAO 产品内部专属知识”与“跨项目通用经验”的归属。建议前者在 `部门/`、后者在 Vault，互相只放指针；跨项目通用知识不由 PAO 擅自迁移或复制。

在上级嵌入区未更新前，不能用本项目一句话假定已覆盖上级纪律。本轮不改嵌入区，也不移动任何 Vault 内容。M1 可先用隔离测试库验证工具，正式长期入库前完成归属确认。

**验收**：同一经验无两份活正本，代码运行产物不误归入 Vault。对应 M0-01、M1-05。

## R05｜关闭、取消、异常退出：本轮新增运行契约

**原文定位**：§1 主会话关闭全停；§6.7 又有后台巡库直接拉起；§8.6 主控唯一唤醒源。未写清后台任务宿主、强退后的进程树、取消后的锁释放时机。

**建议定清**：后台只指“主会话在线期间不阻塞前台”；所有部长、worker、巡库和 PAO 启动的本地子进程归属于在线宿主。主会话关闭后不再派发，停止本轮拥有的进程树。程序路由/唤醒属于主控扩展，不必每次调用主控模型，但不得绕宿主另启常驻服务。

取消先阻止新调用并停止执行，确认停止后释放项目写入锁；已产生的改动和证据保留。异常重启先只读盘点，核对启动前已有改动与本轮差异，再由人决定；不自动清锁重跑，不替用户重置工作树。

正常退出、Ctrl+C、主控被强制终止、终端关闭要分别在 Windows 验证。无法证明某种强退能停子树，必须报告限制并关闭相应自动执行方式，不能宣称“全停已通过”。官方 subagent 示例仅是复用起点，不是此保证。[E3]

**验收**：G1-06/07，M2 巡库与保温再次复跑。停止能力失败属于发布阻断，不推迟到做漂亮看板时再补。

## R06｜黑板单写与项目锁交接：M2 前冻结的新增约定

**原文定位**：§6.1 允许本任务 worker 自由写黑板；§2.1 已承认单文件原子替换不能防并发覆盖。同项目单写在合作卡中还可能与等待相互阻塞。

**建议**：并行 worker 写各自便签/产物文件；`黑板.md` 作为索引只由 owner 更新，不多人整页覆盖。无需新数据库或消息系统。

项目写入锁只管理受 PAO 调度的修改，不宣称能阻止用户编辑器或其他程序。等待需要同项目写入的协作方前，先记录现场、停止当前写操作并交还锁；回来重新核对变更。不让父卡握住锁再等子卡申请同一把锁。锁涉及 canonical 项目路径，需处理 Windows 大小写/路径别名。

**验收**：两个并发便签不互相丢失；协作不因锁自锁；手动改动能被发现而非被覆盖。对应 M2-02/03、G2-02/03。

## R07｜预算与 token：M1 起统一口径的新增约定

**原文定位**：§2、§8.5 定总尝试和父预算，但尚未规定父子重复计费、请求内部重试、嵌入成本与未知用量。

**建议**：每次真实模型/嵌入调用只计一次，卡片回执保存来源；父卡总额是子项汇总，不把已含子卡的总额再相加。调度尝试、API 请求和 API 重试分别记，统一限制，不能假装一种计数覆盖所有失败。

价格未知、失败未回 usage 的费用记“未知/估算”，不得填零。缓存字段是否包含在 input 中取决于上游口径；先保存原始 usage，再规范化，不能再把缓存命中 token 重复加到总输入。按 [度量口径](../附件/验收与度量口径.md) 对账。

预算门禁阻止新的派发与请求，预留在途请求可能产生的费用；不能承诺中断后供应商账单绝不多一分钱。价格无法界定时不启动声称受硬金额上限保护的自动扇出，先用明确的轮次上限及用户同意的试跑额度。

**验收**：合计可逐项复算、无重复计费、未知不冒充零；超限不继续扩散。对应 G1-11、G2-04。

## R08｜检索状态、缓存与外发撤销：M1 检索前冻结的新增约定

**原文定位**：§6.3 返回状态/适用范围，但入口仍只有 query/部门/top_k；规定模型与切分变化重建，未写全权限撤销、删除、归档的失效路径。

**建议**：有效依据与风险提示分开返回，待验证/待复核不挤占正式 top_k。版本或适用范围缺失时标未知，不自动认作有效。条目修改、归档、删除、项目授权撤销均更新检索候选与缓存；不只处理新增。

禁外发检查位于查询嵌入、条目嵌入、批量重建的共同入口。配置变化后先阻断新外发，缓存清理不等于已撤回上游以前收到的数据。向量缓存仍是可删除、可重建的派生文件，不作为正本。

**验收**：已归档/已删除条目不再作为当前依据；禁止项目无查询词或正文外发；同名跨项目与版本冲突测试通过。对应 M1-05、G1-08/09。

## R09｜线性依赖到受限并行：M2 前冻结的新增约定

**原文定位**：§2 标注 v1 只允许线性链；§8.7 及 M2 又要求侦察并行研究、再进入规划。

**建议**：M1 只接受单前置；M2 才明确开放有限分叉与汇合，仍用 `depends_on` 和五状态，先拒绝自依赖/环/未知卡；汇合节点必须等所有前置“已交付”。不引入通用可编程工作流语言。

某个并行分支失败时，保留其他已完成产物，不悄悄当全部成功；由 owner 改范围或补卡。协作 parent 不参加依赖满足判断，也不能拿来制造隐含环。

**验收**：G2-01/02，失败分支不被规划或集成忽略。

## R10｜worker 配置与插件叠加：M1 前冻结的新增约定

**原文定位**：§1 禁 worker 再派发，§6 限制写库；需求同时装 todo/skills/MCP 并考虑 goal 审计。尚未规定子进程加载哪些全局扩展。

**建议**：主控、部长、worker 使用明确角色装载清单，记录最终工具清单；不让 worker 继承带派发/全库管理/自动推进的全局扩展。检查间接工具入口，不只删提示词里的名字。[E4]

rpiv-todo 只管理会话内执行步骤；卡片仍是项目跨会话任务唯一真相。pi-goal-x 优先只借独立审查能力；整包若带第二套进度或自动恢复，则不用其运行时。[E6/E7]

M1 对通用 shell/文件权限仍按原架构明确为“纪律＋审计”，不是强沙箱。受 PAO 自有工具管理的路径与权限检查要落实；外部工具无法强约束的边界如实标注。

**验收**：worker 不能通过已加载 PAO 调度接口递归派发；todo/goal 完成不改卡片终态；隐式扩展加载可诊断。对应 G1-12/13。

## R11｜文档措辞与性能断言：轻量同批清理

架构中的“全文只被读一次”“首次理解成本只付一次”“打回率随时间单调下降”“小样成本是整稿二十分之一”“毫秒级”“90% 认领体验”没有本项目运行证据，应改成目标或示例，不列为既成性能结论。对比只用本项目实测。[S1 §3/§5/§6.7/§7]

§8.4 的“主控直答零拉取”限定为跨部门意图/裁决答复，不覆盖 §8.9 已允许的小文件用户问答。门面“三次读取”是定位路径约束，不等于固定三次工具调用就一定完成事实核验。用户已贴进主对话的长文本，事后落盘也不能退还已经进入上下文的 token；隔离收益应从后续避免重复读取衡量。

需求抬头保留原定案日期，另加末次修订日期；M0 验收把“需求 §8 前三项”订正为“需求 §8 第一项的三个子项”，避免误把 skills/MCP 也划到 M0。
