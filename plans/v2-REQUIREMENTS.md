# PAO v2 需求定案

> 定案日期：2026-10-01。末次修订：2026-10-02（复用清单 §4.1、横切路线 §6、外部评审落地）。来源：三轮需求访谈。
> 本文是 v2 重启的需求基线；架构决策见 `v2-ARCHITECTURE.md`，实施计划另立。
> 现状断言均截至上述日期，来源退役或版本变化时同批订正。

## 1. 一句话定位

以 pi 为内核的个人编码 agent：**终端先行、桌面端二期做纯壳，最终完全替代 ZCode 成为日常编码主力**。
一切定制优先走 pi 扩展 API，不动 pi 源码；跟 pi 上游更新的成本必须保持低。

## 2. 需求定案（访谈结论）

| 问题 | 定案 |
|---|---|
| 为什么推倒重来 | 基座受限（有的功能可能要 fork 源码，但想跟上更新）＋方向不对（旧 PAO 做成了重型编排平台）＋没真用起来 |
| 真实场景 | 日常编码主力（对标 ZCode / Claude Code），自己掌控提示词、工具、上下文策略 |
| 交互形态 | 先终端；桌面端最终要，但必须是「壳不带内核」——内核跟 pi 上游同步 |
| 上游同步策略 | **锁版本使用，升级时适配**（2026-10-01 定案）：不追单个 release、不维护 fork；锁定一个 pi 版本日常用，按批次升级，升级时执行一次适配（见 §5.4） |
| 验收标准 | 日常杂活全部切过去，能顶住就算成 |
| 投入节奏 | 慢推：每天 1–2 小时，重可持续不重速度 |
| 必须能力 | ①模型路由 ②扩展生态（skills+MCP） ③跨会话记忆 ④子代理与工作流（四块全选） |
| 记忆系统 | **不采用 hindsight**（注入噪音大、成本高、系统重，2026-10-01 否决）；记忆 = 文件式部门知识库，细则见 `v2-ARCHITECTURE.md` §6 |
| 旧代码处置 | 需求定了再定取舍（本文第 7 节给出建议） |

## 3. 明确不要的（旧 PAO 教训）

- SQLite Command Kernel、Director→Agent→Worker 重编排、控制协议、预算/审批机器、Desktop 大仓——与「日常编码主力」目标不匹配。
- GUI 先行、为平台而平台的功能。旧 PAO 四天推到 500+ 后端/1000+ 桌面测试后从未真实使用，v2 以真实使用为唯一进度表。

## 4. pi 现状与能力映射（截至 2026-10-01，pi 0.99.2）

版本事实：旧 PAO 锁定 0.84.2（2026-08-14）→ 当前 0.99.2（2026-09-30），6 周约 20 个版本；
0.86.0 / 0.87.0 均含 breaking changes → 升级必须小步 + 冒烟。

| v2 需求 | pi 0.99 已有能力 | 需要 fork？ |
|---|---|---|
| 模型路由 | `models.json` 自定义 provider（OpenAI 兼容端点）；0.99 起扩展可 `registerVirtualModel()` 按请求路由物理模型与思考档位 | 否 |
| 扩展生态 | 内置 MCP（`mcp.json` / `pi mcp add` / `pi.registerMcpServer()`，stdio+HTTP+OAuth）；`skills/` 原生；工具 `exposure`/`namespace`/`prepareLoadload` 注：`prepareLoadout()` | 否 |
| 跨会话记忆 | 自写文件式知识库即可（**hindsight 已否决**，2026-10-01：噪音/成本/重；pi 生态该能力存在但不用） | 否 |
| 子代理与工作流 | SDK `createAgentSession` / `pi --print` 子进程；RPC `steer`/`follow_up` | 否（自建薄调度层） |
| 上下文工程 | `context` / `context_with_system` / `before_agent_start`(systemPrompt) / `ContextEditEntry` / per-model compaction | 否 |
| 桌面壳（二期） | `pi --mode rpc` / `RpcClient` / rpc-extension-ui 文档 | 否（壳经 RPC 对接，不内置内核） |

**结论：访谈中担心的「基座受限」在 0.99 已大幅缓解，四块必须能力大概率零 fork 可达成；先用 M0/M1 实测验证，再谈任何 fork。**

### 4.1 复用清单（2026-10-01/02 生态盘点定案）

自写只留任务卡系统与知识库薄工具（查库/建部/入库）；其余按下表取用（真引入时把许可证与维护状态记 `.agents/notes/implemented/`）：

| 能力 | 取用 | 方式 |
|---|---|---|
| 模型路由（档位） | pi 官方 `registerVirtualModel`（抄 `examples/extensions/jev-router.ts`） | 直接用 |
| 上下文工程（提示词/注册表渲染） | pi 官方 `before_agent_start` | 直接用 |
| MCP | pi 官方内置（mcp.json / registerMcpServer / exposure） | 直接用 |
| 会话内 todolist | `@juicesharp/rpiv-todo`（MIT、活跃） | 直接装 |
| goal/验收审计 | `pi-goal-x`（MIT，含独立完成审计员） | M1 末评估直用或借设计 |
| 子代理/蜂群 | 官方 `examples/extensions/subagent/` 骨架；扇出/记账/worktree 参考 `@quintinshaw/pi-dynamic-workflows`（2026-10-02 销账：扇出已落地；记账随工作流引擎 v1；引擎不抄——工作流以卡为唯一真相，见架构 §11） | 抄改 |
| 语义搜索（查库） | 按架构 §6.3 自建；`pi-memory`（qmd，MIT）备选评估 | 自建为主 |
| 任务卡/看板/队列 | pi 生态与 OMP 均无现成品 | 纯自写 |

OMP（oh-my-pi）是 pi 的整个 fork 而非插件——只借鉴设计，不引入；`context-mode`（Elastic-2.0）不引入。OMP 借鉴点备忘：模型角色表与 context 溢出自动升级、重试链（摩擦日志候选）；task 批量派发 schema；Agent Hub（M3 壳设计参考）。

## 5. 架构原则

> 2026-10-02 订正：原「插件优先 / fork 是最后手段」**已否决**（否决笔记见 `.agents/notes/rejected/`）——定案直接 fork pi 0.99.2 源码为 PAO 本体（`PAO/`，独立 git 仓库保留上游 remote，主分支 `pao-main`），在 fork 上实施全部定制（OMP 同路线）。§5.4 升级四步照旧，第③步从「修扩展包」变为「rebase fork 改动」，成本变高由慢推与锁版缓冲；改动保持集中模块化，减小 rebase 面。§4.1 复用清单参考对象不变，「直接用官方 API」理解为「在 fork 内直接实现/改造」。

1. **fork 路线（2026-10-02 定）**：pao 本体 = pi 0.99.2 源码 fork（`PAO/`，独立 git 仓库，主分支 `pao-main`，保留 upstream remote），直接改源码；端点、密钥、模型菜单等运行配置仍走配置文件与 .env，不硬编码。
2. **改动纪律**：改动集中、模块化、可定位（便于 rebase 上游）；不动与 pao 无关的上游代码；能配置解决的不写死。
3. **摩擦日志驱动**：日常使用每次「这不行」记一条；只有反复出现的摩擦才立项。
4. **升级纪律（已定案）**：锁版本使用，不逐版追逐；**按批次升级**——默认每月一次，或摩擦日志出现「新版才修复/才有」的项时提前。每次升级执行适配四步：
   ① 比对锁定版 → 目标版之间的 CHANGELOG，重点扫 breaking changes 与自己依赖面相关的条目；
   ② 跑冒烟测试集（覆盖扩展包实际用到的 pi API）；
   ③ 修复扩展包/配置中受影响处；
   ④ 更新锁版记录（版本号 + 日期），同步订正文档中的现状断言。
   当前锁定：**0.99.2（2026-10-01）**。
5. **桌面壳不做第二真相源**：会话与状态真相在 pi，壳只渲染与操控（旧 PAO 控制协议教训的简化版）。
6. **工具返回纪律**（2026-10-02）：自有工具默认回简略版——成败、关键错误、完整输出的落盘路径；信息不够可展开，不为省 token 截掉错误原因逼着重跑；高频串联的小读取合并成批。写 PAO 工具时照此设计。

## 6. 路线（横切分层：每阶段所有部分齐头并进；慢推，每步以真实使用验收）

> 2026-10-02 订正：①原「M0 裸奔周（零代码）」**已否决**——直接开做，其验证价值（GLM 实测、摩擦日志）并入 M0/M1 验收项；②原「M1 新仓库（命名待定）」作废——扩展包住本仓库 `PAO/` 文件夹（本体自含包）；③原按子系统纵向分期改为横切分层：每个里程碑把所有部分都推一格，不搞「长期只有某一块能跑」；④铁律：每个里程碑开工前先落一次性计划（`plans/未完成/`）再动手。

- **M0 搭骨架**：本体包立起（`PAO/`：manifest、扩展可被 pi 加载、配置布局、git 与测试框架就位）；GLM 经 `models.json` 接入并立即投入日常真实使用（摩擦日志从这里开张；2026-10-02 补：同时开启 pi 自带 cache-warmer 的 idle 保温，models.json 给 GLM 条目配 promptCache 寿命字段，否则保温逻辑无依据）；`部门/` 注册表与 `.pao/` 目录约定落地。验收：pi 带 PAO 扩展正常跑、GLM 顶日常活、骨架文件齐。
- **M1 各部分最小形态**（每部分都动一格）：两档虚拟模型路由；卡片最小闭环（建卡、五状态、`/队列` 最小渲染）；直通卡蜂群（官方 subagent 示例接入：主控派卡给 headless worker、收回执）；一个部门成型（建部工具＋库骨架＋查库最小版＋入库最小版）；rpiv-todo 装上；移植高频 skills；MCP 实挂一个；注册表渲染进主控提示（内部顺序：先卡片后蜂群——蜂群调度依赖卡片协议）。运行形态限死：一个部门、单 worker、同项目串行写（架构 §2.1）、线性依赖；两档模型与一个 MCP 验证可用，不做自动选择。验收（2026-10-02 补，正常＋异常都走通）：正常——一条龙真干一件日常活（拆卡→派→回执→入库）；缺输入的卡不空转（退回补卡）；失败重试不把旧尝试回执当新结果；主会话中断后能列出未完卡，并核对已发生的项目改动再由人决定。
- **M2 各部分加厚**（摩擦日志驱动，各部分按 top 项推进）：协作卡与星型中转、`/派` 命令、入库与机械巡检加厚、后台卡与扇出、值班保温、巡库卡、机械验收员（结构化验收条目三种句式＋临时影子沙箱＋`pao_验收`，纯机械全过自动落已交付；架构 §12，工作流全自动的前置件）、交卷自动化（`pao_交卷`：机械生成提交信息、验收通过自动＋手动双入口、只 commit 不 push；架构 §13）、越界写检测（git 真值比对实际改动 vs 回执声明，虚报/越界亮出、工作流模式自动插人工门；架构 §14）、用量显示（每轮 `turn_end`→footer 状态行＋`/队列` 部门累计行；全建在 pi 原生 usage 上，成本自带；架构 §15）、定时与值守（首跑清单＋借系统任务计划起一次性 headless 会话＋定时任务内建管理命令＋留档登记；架构 §16）、备份与分享（外层仓库私有远端补配·先记录后建＋分享 v1 文档化；架构 §17）、主控记忆（事实层 MEMORY.md＋主控部经验层＋门禁；门面＝查库自动路由；架构 §18）、交付唤醒（在场三通道；架构 §19）、后台扇出与 waiting（后台模式＋三态可见＋完成通知；载体待拍板；架构 §20）、工作流引擎 v1（配方文件＋机械驱动＋`/流` 一键启动；节点＝部门＋干法、可按节点留人工门，架构 §11；「大活流程（侦察∥研究→规划）」以工作流文件固化）。加不加厚看四指标（摩擦日志按此记录）：任务完成否、总完成时长、全角色合计用量成本、用户介入次数——合计口径，不看主控单点上下文轻了多少；成本看**每项合格交付总成本**（含规划、检索、审查、重试、知识维护），单次调用便宜不算赢；缓存命中的 token 与实际消耗分开记。效果存疑时用同批任务做对照：无库单跑／有库单跑／有库受限蜂群，冷热启动分开记。
- **M3 桌面壳（二期）**：纯壳渲染 `.pao/`；动手前先读 `docs/rpc.md` 与 `docs/rpc-extension-ui.md`。
- **持续**：升级纪律运转；摩擦日志滚动。
