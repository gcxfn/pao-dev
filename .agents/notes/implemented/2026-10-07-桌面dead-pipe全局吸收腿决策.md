# 桌面 dead-pipe 全局吸收腿决策（2026-10-07）

## 决策

desktop 主进程断管边界（`desktop/apps/desktop/electron/platform/dead-pipe.ts`，W-bug7）的
uncaughtException 腿保留**全局吸收**：凡 `isDeadPipeError` 为真（EPIPE/EIO/ENOTCONN，
口径同内核 interactive-mode `DEAD_TERMINAL_ERROR_CODES`）的未捕获错误，不论来源一律吸收
（尽力一行记录后继续运行）；非断管错误仍全部走 onUnexpected（console.error＋错误框）呈现。

这是对内核口径的**有意放宽**（内核 interactive-mode 流级吸收＋uncaughtException 一律 crash）：
内核 TUI 依赖终端存活，未捕获断管即死终端，crash 是正解；桌面 GUI 不依赖控制台，
Electron 内部 console 转发路径（W-bug7 实录：console.log internals 遇死管道抛 EPIPE）
没有可挂流级处理器的自家 stream 对象，只能在顶层吸收。

## 代价

非控制台管道的同类错误（如子进程 stdio、IPC socket 的 EPIPE/ENOTCONN）只要没挂自己的
error 处理器，也会在此被吸收，失去崩溃信号且不落持久化日志（仅尽力 console 一行，
console 写失败会回流被流边界吸收）。这类来源现无已知实例；一旦出现，表现为「该子进程
功能异常而壳不崩」，可在其拥有管道的边界补流级处理，不必回退本决策。

## 对策与依据

- 吸收处记录已增强为单行「code＋message＋来源栈帧」（stack 只作诊断线索，不用于归因
  判定——stack 匹配不可靠，对抗式审核 R1 与 V2 实施一致认定不采用）。
- 模块头注释如实分工（流级腿＝本边界管道；uncaughtException 腿＝全局），不再宣称
  「只在拥有该管道的边界吸收」。
- 流级接线仅 main.ts 一处、stdout/stderr 两条流；desktop 其余子进程管道错误处理
  （checkpoint-store.ts 等）保持本边界建立前的既有状态。
