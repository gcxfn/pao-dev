## 内核能力评审结论（已写入计划 §4 绑定段）

- **分发落点**：inject 走 `controlWorkflow → runDesktopFlowCommand` 链独立 action，三目标在 `runDesktopFlowCommand`（desktop/index.ts L76-117）内、`flow.run("control "+…)` 之前分发，不进 `pao_control_node`/`flow-control-payload`。
- **owner**：复用 `sendDesktopChat`（非空 ≤100_000、拒 `/`、要求 `ctx.isIdle()`，接受条件原生满足）；发起者属于 owner＝`flow.控制.owner===sessionId`。
- **minister**：复用 `host.inject(…,"followUp")`（host.ts L1454-1496，`MinisterInjectResult{ok,原因,模式,处置}`，处置=RPC disposition started/queued/handled 真实排队语义）；新增内核导出 `runDesktopMinisterInject` 验 `部长会话`+轮次（host-bridge `#injectMinister` hotSession 匹配范式）。
- **worker**：侦察确认无现成运行中注入入口；**深查实证可行，面=激活 stdio[3] Node IPC 通道**——一次性夹具四组全通（父 proc.send→子 on("message")→子 process.send ack；spawn 未等 ready 的早期投递也经缓冲送达；`channel.unref()` 不影响 message 投递，不把一次性 worker 变常驻）。stdin 管道对非 rpc 模式阻塞等 EOF 会死锁启动；`--mode rpc` 需重建生命周期；文件轮询靠模型主动读不保证接受——stdio[3] 是 L162 唯一可行面。
  - 真实入口：子端 worker-only 扩展（仿 budget.ts）`session_start` 捕 ctx、`process.on("message")` 收 `{type:"pao_worker_inject",id,text}`→`pi.sendUserMessage(text,{deliverAs})`；父端 `WorkerRunner.injectWorkerMessage` 按 `#active` entry send+收 ack 设超时。
  - 可投递时机：`ctx.isIdle()` true→`followUp`（开新一轮）；false→`steer`（runLoop steering drain 中途消费）。两者落会话文件为真实 user 消息，满足「对应会话看到正文」。
  - 队列行为：不自建持久队列；ack 如实标 `started`/`queued`（isIdle=false 且消息在 steering/followUp 队列）/`rejected`；`pi.sendUserMessage` 返回 void，处置由 isIdle 推断。残留边界如实标注：runLoop 末次 drain 后、session.close 前入队的尾声注入可能滞留——ack 标 `queued`+原因点明，不谎称 started。
- **审计**：`flow.记录.push({时间,事件:"inject",...})`+`saveControl`；worker 记卡+attempt 在理由内格式化；owner 不伪造节点/轮次。
- **投影核对源**：minister 绑定＝`部长会话`+热会话比对；worker 卡+attempt＝`readDesktopWorkerActivity`/`CanvasNodeExecutionRef`；节点/轮次未变＝`轮次`；脚本节点＝`executionMode==="脚本"` 不提供注入。
- **画布注入区**：`node-runtime-details.tsx` `injection` 分区占位（L16-19/L493，supervision 后第 9 分区）；目标锚点复用 canvas-page `canvasWorkerAnchor`/`needsPick`/minister kind。

## 审核发现 → 修补（3 审核；2 真 major + 4 minor 全修）

- [major] **owner 注入必败**：sendInjection 对 owner 也传 nodeName/round，IPC 解码器 `inject+target=owner` 拒收→必被 TypeError 拦+误报「结果未知」。修：`canvasInjectionCommand` 纯函数按 target 组命令，owner 不带 nodeName/round，minister/worker 缺 round 返回 block 不发 0，worker 缺 executionId/cardRef/attempt 分别 block。新增 3 测试用例。
- [major] **RuntimeControls 下拉绕过注入草稿守卫**：`onSelectNode→updateSelectedElement` 直写 selectedElementId 不走 guardLeave→草稿静默丢失。修：走与画布 selectNode 同口径守卫链（requestAction 确认）。
- [minor] detail 未读默认目标投错 → detailLoading 期间 blockReason「正在读取执行锚点…」禁发。
- [minor] `onOpenSessionThread` 不查 injectionDirty → 两处守卫链改 `dirty||injectionDirty`。
- [minor] worker busy 态 ack queued 不验证真入队（closing 假排队）→ busy 态要求 hasPendingMessages 才报 queued。
- [minor] minister/worker 缺 runtime 控制权 check → `controlOwner`（持锁 check+上下文 recheck）替代裸 owner()。
- [主对话修] `pi-sdk-driver` typecheck 挂：`flow-backend.ts` mutate `Promise<void>`→`Promise<unknown>`（inject 返回值丢弃，Flow.control 面只发 confirm/pause/resume）。
- [登记 nit] 协议常量双处字面值（加同源注释）、IPC text 不限长、injection 展开对脚本节点多拉 detail、workerNeedsPick 未消费、「实例入口默认 owner」判读（注入区挂节点详情，未选节点无 owner 入口——规格句意按节点面板回退满足）。
- [判读] error vs rejected 形态差异非缺陷：UI 对 `state:"error"` 与 `disposition:"rejected"` 都走 refused 保正文，符合 L168/L160。

## §5 批 3a 验收逐项

1. **三目标各一次真实接受并在对应会话看到正文**——链路代码级真实：owner→sendDesktopChat→pi.sendUserMessage（持久化 user 消息）；minister→host.inject followUp→写 stdin prompt→等 RPC response+disposition；worker→stdio[3] proc.send→子端 sendUserMessage→ack。三端都不是「发出即报成功」。**运行证据**：端到端真实投递未跑 core/live spec——见存疑。
2. **多 worker 只投所选执行** ✅——executionId=runId 唯一锚点；`#active` 精确 find+内核再核卡路径/attempt，不代投。
3. **六类分别拒绝** ✅——无在途/未绑定/owner忙/轮次attempt过期/非owner/超长空文本各有判据落点；error 与 rejected 都如实带原因呈现。
4. **排队只按底层真实结果** ✅——minister queued 只在 RPC disposition=queued；worker queued 只在 hasPendingMessages 为真（修补后）。
5. **传输结果未知不重发** ✅——超时/断连→rejected+「结果未知请查看目标会话，不自动重发」，无重试路径。
6. **审计准确** ✅——`flow.记录` inject 事件含目标/会话或执行标识/结果/≤200字摘要；worker 记卡+attempt；owner 不伪造节点/轮次；已投递审计写失败→如实返回两项事实。
7. **注入不碰状态机/回执/推进** ✅——三分支在 `flow.run("control "+…)` 前 return，不进 pao_control_node；不写卡回执/不确认门/不推进；接收会话后续正常动作照旧。
8. **脚本节点不提供 worker/minister 注入** ✅——canvasInjectionPlan 剔除脚本节点的 worker/minister 选项，只留 owner；内核侧 `执行方式==="脚本"` 拒。

## 存疑/如实标注

- **真实投递端到端未跑**：批3a 改动的三目标真实注入（owner→会话正文、minister→stdin、worker→IPC ack）经代码链路+一次性 IPC 夹具实证（双向通、unref 不影响 message、不把 worker 变常驻），但**未跑真实 Electron 执行环境的端到端 spec**——canvas.spec 是 renderToString 级，不覆盖 sendInjection 真实 IPC 投递。批3a 属「界面」批，规格 L231「批2/2p/3a/3b-U 各执行对应界面 spec」的对应界面 spec 即注入区渲染（canvas-node-detail 注入用例覆盖分区渲染/锚点/守卫）；真实三目标投递的端到端接受证据如实登记为**代码链路+夹具级**，真机投递建议联调抽查。
- **worker IPC 早期投递缓冲**：spawn 未等 ready 的 send 经 ipc 缓冲送达（夹具实证）；ack 15s 超时窗口覆盖装配期。
- **尾声注入滞留**：runLoop 末次 drain 后/session.close 前入队的注入可能不消费——busy 态修补后要求 hasPendingMessages 才报 queued，closing 假排队落 rejected+原因，不谎称已入队。
- **「实例入口默认 owner」判读**：注入分区挂节点详情内，未选节点时无 owner 入口；规格此句若指节点面板内无 worker/部长时的回退则已满足，若指实例级独立入口则有缺口——登记让后续定。

## 结论

批 3a 满足必需验收的代码级判定：三目标注入链路真实可达（worker IPC 通道实证可行）、六类拒绝分明、排队如实、不重发、审计准确、不碰状态机、脚本节点剔除。2 个真 major + 4 个 minor 审核发现全部修补并有定向测试兜底。真实三目标投递的端到端接受证据属代码链路+夹具级（见存疑），建议真机联调抽查确认。可在 §7 标完成。
