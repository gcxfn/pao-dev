## 二、公开 API 签名

### 纯库(worker/index.ts 全量 re-export)

```ts
// 运行器(推荐每个调度轮次 new 一个;defaultWorkerRunner 供工具与钩子共用)
class WorkerRunner {
	constructor(options?: { registry?: ProcessRegistry; 证据目录?: string });
	run(options: WorkerRunOptions): Promise<WorkerReceipt>;
	cancel(卡号: string): Promise<StopProof>;
	stopAll(): Promise<StopProof>;
	尝试数(卡号: string): number;          // 计数器,供调用方读
	尝试表(): Record<string, number>;
	已在运行(卡号: string): boolean;
	readonly registry: ProcessRegistry;
}

interface WorkerRunOptions {
	卡号: string;
	提示词: string;                        // 作为最后一个命令行参数
	cwd?: string;
	命令?: string;                         // 覆盖可执行文件(测试/假进程用)
	参数?: string[];                       // 覆盖基础参数;缺省 = ["--mode","json","-p","--no-session"]
	模型?: string; 思考档?: string;
	工具白名单?: string[];                 // 以 --tools a,b,c 传给子进程
	产物路径?: string[]; 证据目录?: string; 环境变量?: Record<string,string>;
	超时毫秒?: number; 信号?: AbortSignal;
}

// 模块级便捷绑定(defaultWorkerRunner)
runWorker(options: WorkerRunOptions): Promise<WorkerReceipt>
cancel(卡号: string): Promise<StopProof>
stopAll(): Promise<StopProof>

// 项目写锁(锁目标 = <项目根>/.pao/项目锁;项目根先 realpath,Windows 大小写/别名归一)
acquireProjectLock(options: { 项目根: string; 持有者: string; 重试?: number }): Promise<ProjectWriteLock>
releaseProjectLock(lock: ProjectWriteLock, proof: StopProof): Promise<void>   // 必须出示停止确认
isProjectLocked(项目根: string): Promise<boolean>

// 重启只读盘点(绝不写文件、不清锁、不重跑)
盘点(options: { 工作区: string; 项目根?: string /* 缺省 = 工作区/../.. */ }): Promise<InventoryReport>

// 退出钩子(幂等,同一 runner 只挂一次)
installExitHooks(runner: WorkerRunner, options?: { 信号?: boolean }): void
//   挂 beforeExit;信号:true 时接管 SIGINT/SIGTERM(先 stopAll 再恢复默认终止)

// 树杀原语(按 pid,不按名字)
killTree(pid: number, 宽限毫秒?: number): Promise<string>
```

## 三、验收对照(8/8)

1. **拉起与回执收集** ✓ — 缺省入口与上游 subagent 示例同款自举(`process.execPath` + 当前运行脚本,即本仓库 pi 入口;退化到 PATH 上的 pi),依据:保证跑的是 fork 内核而非全局安装;`--mode json -p --no-session`。stdout 按 JSON 行解析 `message_end`,usage 五项分开累加;测试验证「模型正文自称用了 999999 tokens」不进账目(用法只取事件流)。测试用 `node` 跑临时假脚本,不依赖模型端点。
2. **回执结构** ✓ — 必填字段逐项删除判无效、摘要 4 行判问题、状态五值外判问题,均有测试。
3. **取消顺序** ✓ — 结构上:`releaseProjectLock` 第二参必须是 `StopProof` 实例(instanceof 运行期校验 + 签发符号不导出),StopProof 只有 `cancel/stopAll` 能拿,而二者都先树杀并等进程 close(reap)才签发。测试:取消调用后、凭据拿到前 `isProjectLocked === true`;停妥(进程 pid 探活失败)后放锁成功;伪造凭据放锁报「无效凭据」;取消后同卡 run 被拒。
4. **进程登记表** ✓ — spawn 即登记(pid/命令/卡号),退出标 `运行中:false`;`stopAll()` 只处理登记的运行中进程;registerWorkerTools 挂 session_shutdown → stopAll(测试:钩子触发后 stopAll 被调用);beforeExit 兜底;SIGINT/SIGTERM 钩子先停子树再恢复默认终止(信号接管在实测中验证,见下)。测试另有「未登记的同名 node 控制进程在 stopAll 后仍存活」,证明不按名字全局杀。
5. **Windows 停树** ✓ — `taskkill /PID <pid> /T /F`,依据:/T 杀整棵树含 worker 私自再派的孙进程(Worker 的 proc.kill 只能杀直接子进程),/F 强制(pi 子进程未必响应窗口消息),按 pid 定位满足「只杀登记在案」。测试:worker(父)→孙进程两级,stopAll 后两级都探活失败;单独的 killTree 对已退出 pid 静默成功。实测见第四节。
6. **重启只读盘点** ✓ — 扫 `工作区/卡/`(含部门子队列,深度≤3)列未完卡(待认领/进行中:状态+尝试数+最后回执摘要,取最后一段回执);git 对项目根 `status --porcelain`(-c core.quotepath=off 防中文路径转义)+ 分支/HEAD。测试:盘点前后整个工作区文件快照逐字节相等、先获锁后盘点锁仍在(不清锁)、非 git 目录如实报不可用。
7. **worker 无再派发入口** ✓ — `工具白名单` 以 `--tools a,b,c` 拼进子进程命令行;测试让假子进程把 `process.argv` 写盘,断言 `--tools` 与白名单值、提示词均在子进程实收 argv 里。白名单内容主控接线时定,本卡不硬编码。
8. **尝试计数统一** ✓ — 同一 WorkerRunner(同一调度轮次)内同卡每 run 一次 +1,`尝试数/尝试表` 可读;run 内部无任何重试路径(测试:子进程写启动标记,失败一次标记只有一条,计数器=1)。重派 = 主控新开调度轮次(新 runner 实例)。

## 四、Windows 停树实测(R05 四场景,Node v24.18.0 / Windows 10.0.26200)

用临时驱动脚本驱动本卡真实代码(host 拉起假 worker,worker 再派孙进程并落盘孙 pid):

| 场景 | 做法 | 结果 |
|---|---|---|
| 正常退出 | stopAll 后 process.exit(0) | 宿主/worker/孙全部死,退出码 0 ✓ |
| Ctrl+C | SIGINT 自raise 触发钩子(先停子树再恢复默认终止) | 宿主退出,worker/孙全部死 ✓ |
| 强杀主进程 | `taskkill /PID <宿主> /F`(不带 /T,不给清理机会) | worker/孙**也全部死了** |
| 关终端 | 同上方式近似模拟(不可拦截终止) | worker/孙全部死 |

「强杀也全停」的成因是 **libuv 的运行时行为,不是本卡代码的保证**:Node 在 Windows 上把子进程放进带 kill-on-close 的 Job Object,父进程句柄关闭时子进程被级联杀掉(逐级传递到孙进程)。据此如实标注:

- **可靠保证**(本卡代码契约):正常退出(session_shutdown)、Ctrl+C/SIGTERM(钩子)、显式 cancel/stopAll 三条路径停整棵登记树,有自动化测试钉住。
- **依赖运行时的部分**:宿主被不可拦截强杀时子树是否随之死,取决于宿主是 Node 且子进程未 detached/breakaway;worker 若再派非 Node 子进程或 detach 子进程,可能留尾巴。R05 要求「哪种停不干净就关闭该自动执行方式」——按实测本机四场景全停,未见留尾巴;但此结论绑定 Node v24 + Windows,换宿主/换子进程形态需复测,不宜写进对外承诺。

## 五、取舍与已知限制

- **StopProof 防伪造**:类与签发逻辑收在 runner.ts 模块内,签发符号为模块私有常量(不导出),`签发停止确认` 函数不导出、index.ts 不经 `export *` 泄漏(验收打回修订,2026-10-02)——模块公开面只剩 StopProof 类(构造被符号校验锁死)与 cancel/stopAll 签发的实例;lock.ts 的 instanceof 运行期校验兜底。
- **取消后同卡封锁至新调度轮次**:cancel 把卡号加入本 runner 的黑名单,同卡再 run 直接抛「已取消」;重派由主控新开 runner(=新调度轮次),与「同轮授权总尝试上限」的语义一致。
- **stopAll 后运行器整体封锁**:主会话退出后不再派发(R05),`run` 抛「已取消」。
- **POSIX 无树杀原语**:killTree 走 SIGTERM→SIGKILL,孙进程可能残留(测试环境是 Windows,POSIX 分支有覆盖但未在真机实测)。
- **锁崩溃残留**:proper-lockfile 锁目录按 stale(24h)过期,不提供自动清锁(R05 定案「不自动清锁重跑」);持锁进程崩溃后 24h 内需人工清理。
- **尝试计数不落盘**:计数器在 runner 内存,主控接 A 卡时若要跨轮次累计尝试,需按卡 frontmatter 的「尝试」字段为准(本卡 run 返回的「尝试」是本轮次内序号)。
- **未知状态**:runner 实际不会产出「未知」(close 总给 exitCode);该值保留给「强杀且无任何事件」的兜底分支,回执校验接受它。
- **产物路径来源**:runner 无法知道 worker 产了什么,`产物路径` 由调用方从 run options 传入(接线时由回执落盘方填),回执校验只保证字段存在且是字符串数组。
- **信号接管的边界**:SIGINT/SIGTERM 钩子是进程级单例语义,多 runner 时每个 runner 各挂一对(去重按 runner 实例);主控若还有别的 SIGINT 用途需评估冲突。
- **biome**:只对本卡 15 个文件精确路径执行 `--write`,未动 test/pao 其他卡文件。
- **未验证**:未接真实模型端点(黑板约定);registerWorkerTools 未在真实 pi 会话里跑过(ExtensionAPI 面以类型对齐 + 假 registrar 测试);session_shutdown 真实触发链路依赖主控接线后验收。
