# PAO 全域补充审查

审查日期：2026-10-22  
范围：`PAO/packages/coding-agent/src/pao/` 中此前未深入的业务模块，以及 CLI/core/modes 接入。  
方式：只读审查。未修改产品源码、测试、配置或 `AGENTS.md`，未运行产品测试、类型检查、构建或性能基准。

## 结论

指定范围未发现需要立即并入本批的第四项重复；先确认两项可直接实施的高价值补丁，再评估一项资源问题：

1. **值得直接实施：临时计划全列查询只扫描、解析、读取启动记录一次。** 当前工作台提示和 `pao_plan_query` 全列都会进入 `queryTemporaryPlan()`；它先调 `listTemporaryPlans()` 扫一遍，再为坏定义扫第二遍，并为每份计划的启动摘要与最终返回值各读一遍启动记录。
2. **值得直接实施：自动召回成功路径只构建一次会话投影。** `before_agent_start` 召回成功后，当前连续两次调用 `ctx.sessionManager.buildSessionProjection()`；可复用同一消息快照。
3. **资源问题明确，但不建议塞入本轮小补丁：地图逐文件启动最多四次 Git 子进程。** `captureDispatchMap()` 对有 N 个文件的覆盖范围，同步 Git 子进程数随 N 线性增长，完成文件读取后又执行一次完整索引读取。这有固定的源码与调用证据，但没有计时或采样数据，不能据此宣称桌面发生卡顿或给出耗时比例。
4. `bindMinister()` 连续两次调用 `cardStates()` 属真实微型重复，收益小，建议随后续 workflow 补丁顺手处理，不单独派单。
5. 知识检索的同步扫库不能被异步取消信号中途打断，这是真实生命周期缺口；直接在每个文件循环里加检查并不能解决事件循环被占用的问题，本轮不建议做表面补丁。

CLI、扩展装配、后台工作端口和 `print` 模式等待路径的职责边界清楚，未发现 PAO 业务规则复制进 core 的证据。`memory/memory-vendor.ts` 只读调查，本轮候选均不需要修改它，因此没有越过其他代理的写范围。

## 资源问题：地图 Git 子进程随文件数增长

**证据**

- `dispatch-brief/workspace.ts:130-145` 的 `fileState()` 对每个路径执行 `git show HEAD:path`、`git show :path`，再分别用 `cat-file -e` 判断 HEAD 与索引中是否存在，单文件最多四个 `spawnSync`。
- `workspace.ts:170-180` 先列举受跟踪与未跟踪文件；`:203-215` 再逐文件采集。地图允许目录覆盖，因此文件数由声明范围决定，不只是少量固定文件。
- `workspace.ts:227` 读完每份文件后又执行一次 `git ls-files --stage -z` 计算根索引摘要，没有复用前面的索引信息。
- 当前真实调用面：`dispatch-brief/tool.ts:86`、`precheck.ts:72`、`snapshot.ts:641`、`workflow/minister.ts:445`。代码图旧索引还显示 `worker/dispatch-core.ts` 的 `executeDispatch()` 位于同一传递调用面。
- 现有 `dispatch-brief-artifacts.test.ts` 已保护 HEAD、暂存区、工作区、未跟踪文件及三者摘要不同的行为。以上是固定子进程次数与数据路径证据；没有记录实际耗时，不能评价用户感知性能下降的幅度。

**建议方案与风险**

由主控另派时，用批量 Git 读取替代逐文件读取：一次读索引条目与 HEAD tree，再用 `git cat-file --batch` 取所需 blob；工作区内容继续从文件系统读取。根目录的完整索引数据在同一条索引读取链路中生成原 `mapDigest`，避免完成后完整重读。采用一个明确的批取适配层即可，不加入缓存系统或通用 Git 框架。

需要保留每文件 `headDigest`、`indexDigest`、`workingDigest`、`contentDigest`、`size`，路径排序、排除范围、缺失文件、未跟踪文件和地图摘要。冲突索引、删除文件、HEAD 有而工作区缺失、工作区新增未跟踪、暂存与工作区不同等状态必须先有测试矩阵。风险高于前两项，而且当前 `spawnSync` 调用堆叠确实会占用 Node 主线程直到子进程返回；不能只用并发包装而不核对 Git 输出和错误语义。

本轮不建议把这一项塞进计划查询或记忆补丁中。

## 生命周期缺口：知识扫描取消粒度不足

`knowledge/search.ts:84-113` 的 `scanLibrary()` 使用同步 `readdirSync`、`statSync`、`readFileSync`；`search.ts:119` 在扫描前检查取消，`:153` 执行整次同步扫描，`:163` 之后才再次检查。真实入口 `knowledge/tools.ts:234-243`、`knowledge/auto-route.ts:171-184`、`knowledge/gate.ts:150-156` 都把取消信号传入。

由于扫描期间事件循环不能切回异步取消处理，只在文件循环中加入取消检查仍要等扫描完成才可能观察取消；这不能直接解决“用户取消后同步读库继续”的生命周期问题。也没有测量表明这是当前用户可感知的卡顿来源。

`knowledge/inspect.ts:118-143` 还在文件锁内同步读取、核验并写回子索引。中途取消若只留下部分区已更新、部分区未更新，会改变目前可解释的锁内原子边界。因此本轮不建议直接加取消检查。

如果后续有实际延迟样本，建议按完整边界设计异步或让出事件循环的扫描，并把缓存、外发许可收敛、子索引原子写和取消落点一起验证。当前仅记录为生命周期缺口，没有据此宣称性能退化。
