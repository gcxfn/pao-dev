# 四项改进与第三题故障：主控审核验收

日期：2026-10-23。结论：**不通过，不能将当前批次标为完成或据此恢复真实模型对比**。

本轮由主控独立阅读和运行验证，不采用两位中断子代理的未完成结论。审核对象为 PAO 内核基于 `f296e4c63a3ecd2ade47bae078d88cfb0fdbdeaa` 的当前未提交差异及其调用者。审查范围是本批增量和受影响入口，不是重新逐行审核整个上游仓库。

## 阻塞问题

### 1. P1：手动验收入口漏接尝试基线，验收声明变更保护可被绕过

位置：`PAO/packages/coding-agent/src/pao/cards/verifier.ts:1174`、`:1430`。

`executeVerify` 调用 `verifyCard` 时不传 executionKey。随后 `selfReportDeliveryGate` 用缺省 attempt 读取旧式基线路径，而新的认领链只保存按尝试隔离的 JSON 基线。读取不到旧式基线时，按历史兼容路径跳过验收哈希和改动核查；存在有效的新基线也没有消费。

实际复现：第二次认领建立基线后，把卡验收由原声明改成 `存在: 已跟踪.txt`，通过无 executionKey 的正式 `verifyCard` 入口验收，结果为 `全过自动交付`。预期应因验收声明哈希变化而停止。模拟的是操作者对文件的修改；基线、Git 和验收函数均真实运行，没有模型调用。

最小修复方向：在验收公共边界解析当前尝试的真实 execution-context/基线。已有新式执行证据时不得退回缺基线的旧兼容逻辑；旧式手工卡按真实旧契约处理。不要仅修改工作流自动链，因为手动工具仍是支持的入口。

### 2. P1：旧独立验证卡可以给未验证的新代码重新盖章

位置：`PAO/packages/coding-agent/src/pao/workflow/control.ts:686`、`:715`、`:727`。

版本变化会使旧 pass 失效，但再次提交 pass 时仅要求旧卡已交付、有机械验收段或证据，并将当前工作树重新写成新判定的 contentTree。没有验证卡证据中的检查后 tree 与当前成果树相等的要求，也没有强制新的独立验证轮次。

实际复现：真实 Git 受管副本和 Node 工人完成一次独立验证，部长 pass 后修改原项目 `source.txt`；不运行新的工人或验收，再次提交同一判定得到成功。预期拒绝，但函数正常返回。模型回执由确定性脚本模拟。

最小修复方向：复用已有机械验收的检查后 tree、执行绑定和尝试身份，校验它们确实覆盖当前最终成果。过期时进入新的独立验证，不能仅重新提交部长意见。检查时应覆盖初次判定前的变化，不仅覆盖已有 pass 后的变化。

### 3. P1：重试交卷仅看最后一次尝试，遗漏前次尚未提交的成果

位置：`PAO/packages/coding-agent/src/pao/cards/delivery.ts:493`、`:551`。

每次尝试单独核对改动是正确的；但最终交卷也使用最后一次尝试的基线，会将第一次失败尝试留下的成果当作认领前改动排除。自动链又允许无新改动时幂等结束，不能保证最终 Git 提交包含整卡成果。

实际复现：第一次尝试创建 `旧成果.txt` 后失败，第二次认领只复验，由模拟 owner 批准交付；`deliverCard` 返回 `交卷:false`、`无基线外改动`，没有创建包含旧成果的提交。卡状态和最终 Git 交付由真实代码处理；owner 批准是夹具模拟，不冒充真实质量验证。该复现不证明模型本身是否能完成题目。

最小修复方向：区分本次回执归因与整卡累计交付。基于保留的尝试基线和真实执行根收集尚未交付的本卡改动，并保留原有用户改动、并发卡和越界保护；不能直接从最早 tree 做全仓 `git add -A`，也不能重写历史基线。

### 4. P2：桌面与状态读取未接入版本核对，刚完成的流程也显示运行中

位置：`PAO/packages/coding-agent/src/pao/desktop/workflow.ts:50`，以及 `desktop/plans.ts:256`、`desktop/canvas.ts:473`、`status/workflow-instances.ts:118`、`status/results.ts:498`。

`controlView`/`controlReport` 的新规则要求当前 contentTree 才将 pass 算为完成，但这些同步读取入口没有提供它。异步控制核心和界面因而给出不同状态。

实际复现：同一份刚完成的流程，`readControlReport` 返回 `completed`，`readDesktopFlows` 返回 `运行中`，没有 intervening 源码修改。运行的是实际内核读模型，没有启动 Electron，因此结论限定为桌面后端数据错误，不冒充真实页面交互验证。

最小修复方向：在真实读取边界接入共用的异步核对，一次请求内复用成果树。保持对外载荷一致；不能将未经核对的历史 pass 默认算作当前有效，也不应在渲染线程增加反复同步 Git 扫描。

## 额外静态发现

- `fanout/execute.ts:305` 仍只用 `receipt.artifact_path` 做边界核查，自动链和手动核查已改为 changes 优先。合法的 `artifact_path:[]`、`changes:[源码路径]` 会在扇出摘要被标成漏报。该结论来自直接调用链，尚未完整运行扇出入口复现。应共用声明选择规则，保留 changes 明确为空与缺省的区别。
- “修完这轮放行”配置需要补端到端验收：回边重置清空判定，仅保留 `放行修复`；新的完成条件又要求 change 判定，宿主对 `放行修复` 节点跳过 judging。旧测试只断言标记，没有跑到最后一轮结束。这里存在状态条件相互不兼容的直接证据，未在本轮新增完整复现，不能声称该配置已验收。

## 简洁性和性能结论

认可并保留的方向：复用 Git 内容树、原状态机、原工作流回边、地图摘要算法和宿主装配；地图重采辅助函数消除了重复实现；每次独立沙箱切断跨次残留。没有证据要求推翻这些边界重写。

未通过的核心是规则没有贯穿所有入口：尝试基线在派发侧落地，手动验收仍走旧路径；单次改动归因被用于累计交付；控制核心引入版本核对，展示调用者没有接线；部长 pass 写入了新版本，但没有核实验证证据的版本。这些应在已有公共边界收拢，不宜给每个入口再加局部开关或补丁。

性能方面：先前单独诊断人工门三卡测试实际通过但耗时约 33.4 秒，超出原默认 30 秒。本轮没有据此扩大超时或删除检查。内容树捕获会启动多个 Git 子进程，部分控制操作前后重复捕获；这里只确认存在成本，未通过对照采样证明其退化幅度或优化收益。真实题目总耗时、内存和完整桌面发行性能仍未验收。

接下来修复优先级为：公共验收基线 → 验证证据版本 → 累计交卷 → 读取接线，并复核扇出声明与回边超限配置。上述阻塞修复并重新运行对应诊断前，本批保持未完成。
