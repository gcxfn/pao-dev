## 根因与修复结果

原累计交卷只看最后一次 attempt 的基线，因此第一次失败 attempt 已留下、第二次认领后才进入基线的内容会被当成认领前既有改动而排除。第二次只读复验可能返回“无基线外改动”的普通幂等结果，整卡成果没有进入提交。

随后又确认两个入口问题：

1. `deliverCards` 调用 `deliverCardOnce` 时不传 `executionKey`，原逻辑只对受管副本自动解析 context，现代 primary 卡没有可靠 context，验收后的源码或验收声明变化可能漏检。
2. 如果受管副本中的成果由累计证据发现，而交卷仍按宿主的 legacy `git add` / `git commit --only` 路由，宿主可能看不到受管副本成果。

当前实现已经处理这两个问题：

- 当前 attempt 有可靠 `execution-context` 时，即使调用者没传 `executionKey`，也自动解析并用于实时验收与内容 tree 核对。
- 当前 attempt 已有基线但 binding 缺失时明确拒绝“执行上下文缺失”；binding 存在但损坏或无法解析时让异常暴露，不退回 legacy。没有本 attempt 基线时才保留旧卡兼容。
- 验证 context 与提交路由分开。context 负责 `assertDeliveryContentMatchesVerification`、实际执行根和内容 tree；路由按真实 `worktree.kind`、执行根是否与任务根不同以及显式 key 决定。
- 同根 primary 的普通现代重试没有显式 key 时仍推进原 `HEAD`，使用逐路径 `git add` 和 `git commit --only`，认领前用户暂存保持不变。
- 明确 key、`managed` worktree 或执行根不同于任务根时使用受控 `commit-tree`，在临时 index 中只重建经证明路径，不执行全仓 `git add -A`，也不改写宿主 index。
- 自动识别复用现有 `readExecutionBinding`，没有新增持久化格式、模式开关或公共 API。

累计归属仍逐 attempt 核对：保留 JSON 基线、绑定摘要、tree 对象、相邻基线 tree 差和历史回执必须一致；当前 attempt 不因历史证据充分而跳过独立验收。认领前用户同路径脏文件、其他卡声明、共享仓库中的其他卡、删除、重命名、受管副本和受管副本已清理等边界都保留拒绝或受控处理。证据不足统一拒绝为“累计成果归属不足”，不会猜归属，也不会报告幂等成功。

原外部复现 fixture 在第一次 claim 后直接写文件、没有历史回执，当前行为仍是安全拒绝，不把无法归因的中间改动算作本卡成果。

- 交卷归属只使用可校验的基线、binding、Git tree 和回执事实；证据无法逐项对应时拒绝。
