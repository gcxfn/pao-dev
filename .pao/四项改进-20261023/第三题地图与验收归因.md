# 第三题地图与影子验收只读归因

调查日期：2026-10-23。对象为仓库基线 `f296e4c63a3ecd2ade47bae078d88cfb0fdbdeaa` 及冻结前已复制到本目录的证据。第三题容器保持暂停；本轮未 unpause、未 exec 容器、未改冻结现场、未运行模型或测试。

## 结论

A 项同时存在真实地图过期与 harness 归因错误。规划地图保存后，实施阶段同一个工作区继续发生写入，freeze 重采地图声明的 coverage 后发现内容已不一致；但 `prepareDispatchBrief` 当时没有采集当前 coverage，直到 `freezeDispatchBrief` 才比较，于是把“地图早已过期”报成“准备与冻结之间已变化”。卡面 `inputs` 也不是唯一地图来源，工作流依赖节点的地图会由 `dispatch-core.ts` 另行注入，因此删除卡面指针不能单独关闭核查。

B 项有两个已证实但不同的失败机制：`npx tsc --noEmit` 把 `tsc` 当成可临时下载的包名，找不到本地 TypeScript 时联网装入了错误的 `tsc@2.0.4`；`npm run build` 则是进程启动阶段 `ENOENT`，所以显示 `exit 127 / 命令不存在：npm`。基线源码的固定影子目录、增量复制和失败现场原位保留确有造成连续复跑不稳定的风险，但现有日志不足以证明这次两个错误就是由残留目录唯一造成。主控当前工作区已经加入每次唯一影子目录和禁止无 `--no-install` 的 `npx` 两项候选修复，尚未完成整合验证。

### 真实根因

- 真实过期：地图在 `13:54:39Z` 保存，实施阶段在同一 `/app` 工作区继续发生写入；freeze 按保存的 coverage 重采后得到不同摘要，这是核查在拒绝一份与当前内容不一致的代码地图。具体涉及业务源码、构建生成文件还是两者的组合，现有快照无法判定。
- 阶段归因错误：prepare 没有采集当前 coverage。地图若在“保存后、prepare 前”已经过期，只有 freeze 比较时才暴露，错误仍描述成“prepare 到 freeze 之间变化”。这会把旧状态带进新尝试，导致一张依赖地图反复阻断。
- 来源控制缺口：工作流地图注入与卡面 `inputs` 是两条来源。删除卡面指针后仍会因节点交接地图被核查，单一入口无法解释或关闭地图依赖。
- 不能由模型重写基线来绕过：coverage 绑定的是保存地图时的代码摘要，而认领基线用于计算本次尝试改动。两者用途不同。重建认领基线 tree/ref 若改变了“当前工作区减认领基线”的比较起点，只能影响越界核查，不能合法说明旧地图仍然新鲜；应在地图层保留明确来源、保存时间和过期结果。

### 最小修复接口

1. 在 `DispatchBriefDraft` 中为每张上游地图保存一个小型的 `preparationMapProof`：地图 ref、保存 `mapDigest`、比较所用 `executionRoot`、当前回收得到的 coverage 摘要或逐文件 identity。直接复用 `captureDispatchMap`，不要另建一套哈希算法。
2. 在 `prepareDispatchBrief` 中，对已经解析到的每个上游地图采集当前 coverage，并立即与保存地图比较。不一致时返回独立错误码，例如 `stale_map_before_prepare`，诊断中列出地图 ref、`capturedAt`、采集根和发生变化或缺失的文件。保持 `stale_map` 作为现有关闭核查的错误大类，具体阶段放进 `code` 或结构化细节。
3. 在 `freezeDispatchBrief` 中再次采集，只比较 prepare 证明与 freeze 当前 coverage；变化时返回另一错误码，例如 `map_changed_during_prepare_freeze`。这样能准确区分旧地图与真正的竞态。
4. 若产品决定“地图只作规划背景，不继续约束实施”，应由派发装配层明确停止注入，而不是让模型逐个删除卡面字段。卡面、工作流和手工派发仍须采用同一地图有效性规则；不能只修 `worker/dispatch-core.ts` 一条路径。
5. `sameDispatchMapCoverage` 仍可保留布尔比较。可增加一个只服务于诊断的 `diffDispatchMapCoverage(saved, current)`，返回路径与变化种类；只有真实错误需要列出文件时才调用，避免把比较细节复制到 worker、workflow 和 cards。

### 行为测试建议

1. **保存后、prepare 前过期**：建一张有效地图，修改 coverage 内真实文件，再调用 prepare。断言返回 `stale_map_before_prepare`，诊断列出该文件；确认不是等到 freeze 才报。
2. **prepare 后、freeze 前变化**：prepare 成功后修改同一 coverage 文件再 freeze。断言返回 `map_changed_during_prepare_freeze`，证明第二个窗口仍受保护。
3. **工作流来源独立核查**：卡面 `inputs` 不含地图，但传入工作流 `upstreamMapRefs`。修改地图 coverage 后仍必须拒绝，并在诊断标明“workflow/map source”，防止靠删卡面指针绕过。
4. **未过期与范围外变化**：coverage 不变时 prepare/freeze 通过；只改 scope 外文件时仍通过。这可验证 `sameDispatchMapCoverage` 的范围语义并防止用整仓 dirty 状态过宽拒绝。
5. **原样保留 verify 复核**：freeze 成功、写入 map 后等派发前改动文件，`verifyDispatchSnapshot` 仍拒绝。测试真实内容变化，不匹配提示文字。

### 真实根因

- `npx tsc --noEmit` 的包名解析是已证实的首因链：`npx` 将 `tsc` 视为 package/executable；影子内本地 `node_modules/.bin/tsc` 不可用时，它走联网自动安装，结果装入了与 TypeScript 包同名但内容不同的废弃包 `tsc@2.0.4`。`--no-install` 的后续结果 `exit 0` 支持“本地 TypeScript 存在但未优先解析或被自动安装路径抢占”的故障方向。
- `npm run build` 的 `127` 是 `execFile` 启动命令头 `npm` 时得到 `ENOENT`。它与 `npx` 自动安装不是同一个错误，也不是 build 脚本返回 127。现有日志未保存最终环境快照，无法从证物中确定为什么同次运行能启动 `npx` 而不能启动 `npm`。
- 连续复跑不一致具有真实结构条件：固定目录复用、增量复制不删除残留、失败副本可能原位保留、依赖入口的重建只处理 junction。复跑可能看见上一次留下的普通目录、旧 `.bin`、旧文件或缺失依赖。但这次日志没有逐项重建第一次执行前后的目录内容，因此不能宣称这是两个首次错误的唯一原因。

### 最小修复接口

1. 每次验收都创建新的唯一影子副本，失败排障副本移到独立、带卡号/参与标识的保留目录。这样下一次执行绝不进入上一次失败后的目录；保留保护仍在。
2. 如果产品坚持固定目录复用，刷新前必须原子清空/替换副本，至少严格处理普通目录形式的 `node_modules`，而不只处理 junction。默认方案仍是每次唯一目录，因为实现简单、不会让残留状态成为验收输入。
3. 验收命令层面禁止可联网的 `npx` 自动安装。当本地工具不可用时返回结构化“依赖不可用/命令未解析”，保持失败，不下载其他包，也不返回成功。
4. 保留现有进程管理器，在启动前把命令头解析结果记录为诊断：请求命令头、解析到的可执行文件绝对路径、`cwd`、生效 `PATH`、本地 `.bin` 检查结果和失败阶段。可复用 `execFile`，无需引入 shell 或新框架。
5. 修复测试契约时按真实隔离语义更新：取消测试观察新目录中的活动副本，而不是预热一个固定目录；“读取验收起始副本”的测试应断言命令所在唯一副本在创建时的内容，而不是期望后来的验收复用早先的旧副本。不要为了旧测试保留残留目录。

### 行为测试建议

1. **真实连续两次**：同一沙箱根连续执行两次失败验收，第一次写入哨兵文件和目录，第二次检查新副本不含哨兵，且两份失败现场都可定位。断言两个 `workDir` 的绝对路径不同。
2. **普通依赖残留**：构造 `node_modules` 普通目录与伪 `.bin/tsc`，不应被下一次验收静默继承；唯一副本方案下第二次没有它，固定目录方案下刷新应删除或重建。
3. **本地 `tsc` 可用**：准备一份真实可执行的本地工具桩，记录调用次数；验收只调用它，不发生下载或替代包执行。这里验证实际调用结果，不能只匹配安全文本。
4. **本地工具缺失**：移除本地工具，断言得到“依赖不可用”，不出现网络安装，也不自动通过。
5. **命令解析失败**：构造不含 `npm` 的执行环境，实际启动 `npm run build`，断言退出 127、诊断给出“进程启动/ENOENT”，并记录 cwd 与 PATH；再构造含 npm 的对照环境，命令完整运行。无需假设固定值。
6. **取消时的活动副本**：真实启动父孙进程，通过观测活动 `workDir` 的 ready/pids 文件确认命令正在使用哪个唯一目录，再取消并核对进程和后续命令。

### 能保证与不能保证

- 能保证：原错误中 `npx` 的联网安装现象和 `npm` 的进程启动失败类型均有日志与源码链双重证据；后续 `--no-install` 的通过是真实行为对照。
- 能保证的机制：固定目录残留能让验收读取与上一次不同的依赖/文件状态；唯一目录能切断这种跨次继承，但必须同步调整测试的路径发现与快照时点口径。
- 不能保证：这次连续错误的精确历史目录状态、最终 `PATH` 差异，以及“残留目录是本次首错的唯一原因”。需要有完整环境、每次目录清单与命令解析记录的复现实验才能补齐这些结论。
