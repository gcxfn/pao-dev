# 报告阻塞 2、回边超限放行与损坏证据边界修复

日期：2026-10-23。结论：阻塞 2 的源码修复已完成并冻结，回边超限“修完这轮放行”的宿主跳过第三次判定行为、统一异步读取入口、新式损坏证据不得降级为静态审核均已有定向回归。本文只报告本代理边界内的结果；全仓检查、Electron 交互和跨模块最终验收由主控统一完成。

## 根因

1. 旧独立验证卡可以给后来变化的新成果重新盖章。原因是 pass 校验只确认卡已交付和存在验收材料，没有把机械验收的尝试、检查后 tree、执行根及 execution-context/尝试基线绑定到当前成果；首次判定前、等锁期间和已有 pass 后的变化都可形成过期证明。
2. “修完这轮放行”超过回边上限后，回边重置会清掉审核判定并留下 `放行修复`，而宿主仍把“拆解结束但无判定”当作可进入下一次判定；同时完成条件又要求 change 判定，形成状态冲突。
3. 新式执行证据已存在，却缺机械验收结论或同时缺执行根、关联摘要时，审核证据函数曾返回 `unverified`，使部长写“未验证运行”就能把损坏的新式证据按旧卡契约放行。
4. 桌面与状态读取需要版本核对，但同步 `controlView()` 无法自行读取 Git 内容树；若各入口分别扫描，会形成状态不一致和重复实现。

主要实现：

- pass 判定记录并复核 `projectRoot` 与 `contentTree`，当前成果变化后旧 pass 失效；重新 pass 必须由当前尝试的验收证据覆盖。
- `reviewEvidence()` 统一复核当前尝试、前后 tree、执行根、仓库根、工作树摘要、输入快照、关联摘要、execution-context 与尝试基线。
- 当前尝试已有 execution-context 或基线时，缺验收结论、缺 tree、或同时缺执行根和关联摘要均明确 `blocked`；真正没有新式证据的旧卡和静态零卡保留原契约。
- 公共边界复用同一个 `hasCurrentExecutionEvidence()`，避免三套分支各写一种判断，也没有增加配置开关、缓存或第二份状态。
- 已重构出 `applyReviewBackEdge()`，让普通打回与受控质量返工共享回边计数、超限处理、轮次重置和历史保留。
- 超限“修完这轮放行”保持 `放行修复` 与历史，宿主以 `!node.放行修复` 防止第三次判定，当前轮满足交付及配置后可完成。
- 导出 `readControlView(flow: FlowControl, options: DriverOptions, deadMinisters?: ReadonlySet<string>): Promise<ReturnType<typeof controlView>>`；内部复用 `currentContentTree()` 和 `controlView()`。`readControlReport()` 再复用它，没有另立缓存或状态真相。

## 正确性复核

- 三项新回归使用临时真实 Git 仓库、真实受管工作树、真实 Node 工人进程和真实 `runAutoChain()` 机械验收链；模型回执由确定性 Node 脚本模拟，只代表协议输入，不证明模型质量。
- 前两项测试在验收完成后先断言当前尝试的 execution-context 确实存在，再篡改卡正文。即使 pass 理由明确包含“未验证运行”，`decideNode()` 仍以“不能降级为静态审核”拒绝，且控制正本没有 pass 判定。
- 第三项移除当前尝试的 execution-context、尝试基线及两项执行绑定字段，重新调用同一公开 `decideNode()` 路径，确认没有新式证据的旧卡仍能按明确标注“未验证运行”的契约放行，没有因修复扩大拒止范围。
- 回边超限无人工门的现有行为测试已实际通过：第三次审核只完成拆解而不进入判定，`decideNode()` 仅调用两次，最终 `readControlReport()` 为 `completed`。
- `readControlView()` 的返回类型直接引用 `controlView()`；`readControlReport()` 只投影该结果，统一读入口行为已有定向测试。没有访问正式 PAO_HOME，没有调用付费模型或新增 benchmark，没有启动 Docker，也没有提交 Git。

- 复用 `currentContentTree()` 计算一次真实成果树，复用 `controlView()` 展示，复用 `reportFromView()` 保持载荷；没有新增缓存、额外状态文件或第二套投影。
