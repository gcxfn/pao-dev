# 已知边界（pao 自有代码）

2026-10-03 K3 审码修复批遗留的观察项：都是「知道、拍板暂不修」的边界。动相关代码前先读这页；修掉一条就把它从这页删掉。

1. **散场审计与树杀顺序耦合**：`host/host.ts` `#散场Entry` 先树杀、后落监督审计行——若 killTree 本身抛错，该次散场不会留下审计记录（交接页若已落盘则仍有痕）。修法（审计包进 try/finally）极小，按 2026-10-03 拍板暂不修。
2. **「留 owner」停因靠文案匹配**：`workflow/tools.ts` 的结构化挂起字段是主判据，`chain.停因.includes("留 owner")` 只是兜底。改停因文案会静默击穿兜底——改文案前先改判据。
3. **派发超时的分钟粒度**：保温.json「派发超时分钟」只收 ≥1 的整数，小数或 0 会被拒收并回落默认值。派卡非阻塞化（静默提醒）重构落地时会重写此段，届时一并处理。
4. **工作流节点名的空格不对称**：流名三入口已禁空格；配方节点名带空格时写入与读取的规范化路径不一致（同病、流名已治节点名未治）。新配方节点名避免空格；收口时补同款禁令。
5. **卡状态机读-合并-写后的小竞态窗**：`cards/statemachine.ts` `changeCardStatus` 会重读最新卡再校验写入，但两个写者同毫秒读到同一版本时仍可能互相覆盖。单写者协议（只有 owner 改状态）下窗口几乎不可达；真要堵需文件锁，代价大于收益，故只记。

## 受理入口（`pao_accept_task` / `intake/`）

6. **「全链路身份」给不全时说给不全**：受理返回卡号/卡路径/尝试号（内核真实可查）；实例/节点/轮次只有工作流派发在准备期真实解出实例上下文时才填，普通卡一律 `undefined`。所以「一次调用返回完整身份」在普通卡上实际是「返回卡号，尝试号要等认领」——工具文本会写「尝试号未产生（未启动就没有尝试）」，不要把它读成失败，也不要让上层把 undefined 当 0。
7. **幂等判据落盘在项目侧，不在 PAO_HOME**：位置 `<项目根>/.pao/intake/受理账.json`（项目根由卡目录推导）。失效条件三条，都会导致「同一请求被当新任务重新建卡」：① 账文件被删或换项目根；② 卡目录整体搬迁/复制到另一个项目根；③ 自动判据（`auto:<sha256前16位>`）依赖的四个字段（目标/部门/验收/依赖）里任一被改写——改了措辞就是新判据，这是设计取舍（宁可重复建卡也不把两条不同任务误合并），不是 bug。
8. **自动判据不做语义去重**：自动判据只是「目标+部门+验收+依赖」的稳定摘要，不消除同义改写（「修好登录」与「登录修好」是两个判据）。要真幂等必须由调用方给 `request_key`。
9. **受理账坏 = 如实失败，不自动修**：`受理账.json` 是坏 JSON、版本不认识、条目形状不对时 `readIntakeLedger` 抛 `IntakeLedgerError`，受理如实拒绝。**不重置、不覆盖、不跳过**——修账是人工动作，自动"修复"会把重复提交重新变成重复建卡。
10. **停止后旧受理结果失效，但工具只提示不拦截**：`isIntakeOutcomeStale` 判的是「卡已终结/尝试号已变/卡不见了」，`pao_accept_task` 的重复提交分支与 `pao_inventory` 的说明文字会带上这条纪律，但**不阻止**调用方继续拿旧 outcome 干别的（上游是模型，拦不住它的推理）。真正的兜底是查询面：`pao_inventory` 列的是当前真相。
11. **建卡成功但落账失败 = 报未受理**：卡已建、但受理账写不进去时，受理如实返回 `rejected` 并在原因里给出卡号与路径。此时卡是真的在那里的（用户可能看到一张"多余"的卡），但拒绝是对的——不然幂等失效，下次重试会再建一张。这条是故意的取舍，不是缺陷。

## 盘点面（`pao_inventory`）

12. **终态卡分区只报卡面事实，判不出「这条受理是被 dup 还是被停」**：`inventory.ts` 的「已终结卡」分区读的是卡文件本身（`status`、`completed`、最后一段 `## owner记录`），**不读受理账**。所以它能回答「这张卡现在是什么终态、谁在什么时候用什么理由终结的」，但**不能**回答「这次受理是幂等判重（duplicate）还是真的被停止/作废」——那要跨目录 join 受理账，属于 F 批的账本场景。要看受理身份，用 `pao_accept_task` 当次的返回文本，或后续 F 批的查询面。另两条同源边界：① 平铺卡目录不在本工具扫描范围（只扫 `<工作区>/卡/`），终态卡因此看不到；② 分区默认只报最近 5 张（`SETTLED_CARD_LIMIT`），超出会写「另有 N 张未列出」并给下一步，**不是全量**。

## 部门目录与详情投影（`dept/catalog.ts` / `desktop/dept.ts`）

13. **思考强度在投影里恒为「[不展示]」**：`context/index.ts` 的遮蔽正则按**键名**命中 `thinking`（`/…|thinking|reasoning|…/i`），`thinkingLevel` 被同名前缀连坐，整个值替换成 `[不展示]`。规则本意是遮蔽思维链**正文**，`thinkingLevel` 却是 `low/medium/high` 枚举参数。投影如实透传遮蔽结果，桌面不猜不补。已知可安全展示的真值：`生效`、`来源`、`provider`、`model`、`未配置原因`。修法在内核：判定改为「按值形态」而非「按键名前缀」，改时须连带复核所有以 `thinking` 开头的配置键。
14. **注册表「读不了」与「不存在」是两件事**：`validateDeptCatalog` 只认「文件不存在」并给出「还没有登记过任何部门」；注册表路径是目录、权限拒绝等「路径在但读不了」的情形由 `readDeptCatalog` 的 catch 单独成条（`部门: "（注册表）"`）。两条都必须并进最终的 `问题` 数组——曾因校验结果整体覆盖 `catalog.问题` 而把读失败降级成「没有登记部门」，界面于是谎报空列表。改动此函数时不得退回「直接赋值」。
15. **非部门名条目不会摊进部门行**：`（注册表）`、`（档位）` 这类占位的 `问题.部门` 不是真实部门名，因此它既不属于任何部门的详情页，也不会出现在部门行的 `问题数` 里。界面若只在部门行渲染问题，就必然漏掉「整份注册表/档位读不出来」。须由目录总表单独渲染。
16. **两类部门内容不混为一谈**：技能（`pao配置/skills/<名>/SKILL.md`）走技能装载，工具（`read`/`write` 等内置名）走工具白名单。旧配方把技能名混写在「工具」行时，校验点名要求拆分，投影把混写项标为「表外」并说明不会被装载——**不静默丢弃**，因为静默丢会让部门看起来"正常"而实际少了能力。
17. **「未信任技能」没有事实源**：内核没有技能信任清单/白名单，因此投影只报「缺失」，不报「不可信」、不造中间状态。将来接入信任清单时，在 `catalog.ts` 的 `DeptSkillRef` 上扩展，不要在界面侧补假状态。

## 上下文恢复与总预算（`status/context-recovery.ts` / `usage/`）

18. **恢复读路径没有用户入口**：`context-recovery.ts` 只读、零落盘、零派发，但全仓对它只有自身与自己的 spec 引用；`/pao` 子命令、`plan-tools`、桌面读模型都没接。现成的 `pao_plan_query` 覆盖「计划/要求/约束/确认版本/历史版本/运行关联」，**不覆盖**「绑定实例/步骤/轮次/版本、且旧轮次提醒不推进新轮次」的待办视图。接入口时新建干净中转桶，不要往 `status/index.ts`（`/pao status` 仪表盘专有模块）加行；一屏全给用 `mergeRecallTodos([snapshot.待办, cardRecallTodos(项目根)])`——卡面失败待办默认不在快照里。

19. **缺轮次记为 `undefined`，不记为 0**：召回待办的身份键把缺失的轮次/定义版本编码成**空串**而不是 `"0"`。写 `"0"` 会让「不知道第几轮」与「第 0 轮」撞成同一条待办。同理过期判据只在**两侧都有且不等**时判过期，缺一侧不判——宁可多提醒一次，不可误杀真实待办。

20. **无数据不显 `$0`、未授权不显「额度 0」**：`formatMeteredCost` 是全仓唯一费用渲染入口，`unknown` 永远洗不成已知（`sumMeteredCosts` 遇到任一 unknown 即整项 unknown）。未配置总预算时状态是**「未启用」**，不是「额度 0」。绕过这个入口直接 `toFixed(2)` 就会把「不知道」印成「花了 0」。

21. **总预算门禁不能承诺「绝不超支」**：预留是事前的数，真实费用可能超；`settleBudget` 如实记超额但不回滚不阻止。门禁保证的是「不会因并发各领一份完整额度」（读账→判断→写预留三步在同一个 `withFileLock` 临界区内）与「结果不明时不再授额」。真正硬拦在轮次边界，属 `worker/budget.ts` 的 `before_provider_request`——跨任务总额与轮次边界硬拦是两件事，别把前者说成后者。

22. **门禁只在用户显式给总预算时注入钩子**：`ExecuteDispatchOptions.预算门禁?` 未注入时全是空操作，所以「没给预算 → 行为零变化」是设计保证而非巧合。接线点在**取锁重核之后、认领之前**——卡状态机没有 `in_progress → unclaimed` 回退路，认领后被拒会留下停在 `in_progress` 的僵尸卡，即「已派发假象」。

23. **进程被 SIGKILL 时账停在 `reserved`**，与「正在跑」看起来一样，需「账本对登记表」巡检才能转回。**H0 已补人工入口**：`/pao budget`（只报，列出每笔停着的预留的卡号/尝试号/金额/时刻/判据键）与 `/pao budget 归还 <卡号>:<尝试号>`（人显式下命令才写，按判据精确匹配）。三条口径要记清：① **没有任何自动归还**——「预留时间很旧」不构成归还理由，进程可能还在跑、钱可能已经花了只是没回执，错放回去的额度会让后来者一起超支；② 归还只做 `reserved → released`，已结算的报「不能归还——取消不抹费用」，结果不明的报「须先查清」，都沿用 `budget-ledger.ts` 既有护栏；③ 这条命令**只挂命令面、不挂 worker 工具面**（`role.ts` 的 `WORKER_SKIPPED_MODULES` 含 `budget-command`），agent 自己改不了钱账。

    **「账本对登记表自动比对」是刻意不做，不是欠着的活**（2026-10-17 定案），三条理由：① 巡检输出已经答全「谁/卡几/尝试几/多少钱/何时/什么状态/下一步」，人拿着 pid 去 `pao_inventory` 对一眼就能比，内置一层是替人做判断；② 进程登记表是**纯内存、不持久**的（e2a 查出的设计缺口），跨重开读不到别人的 pid，能比的只有同进程的，价值远小于看上去；③ 比对结果一旦出现「账上有、进程没在」，就会有人想让它自动归还——**红线不靠近处开小口**。要判断就由人判断。

24. **三条派发路径已统一受门禁管**（H0 收口）：`pao_dispatch_card`/受理链（`worker/index.ts` 的 `dispatchInBackground`）、扇出（`fanout/execute.ts` 的补位车道）、工作流自动链（`workflow/auto.ts` 的单卡派发）都注入同一个 `buildDispatchBudgetGate`，判据与拒绝文案不会分叉。门禁工厂住在 `usage/dispatch-gate.ts` 而不是 `worker/index.ts`，原因是**循环依赖**：`fanout/execute.ts:41`、`workflow/auto.ts:33` 都从 `worker/index.ts` import，反向再 import 就会成环。装配处有一条不可改的次序：`预算门禁` 必须排在 `...dispatchOptions` **之后**，否则调用方一个同名键就能把门禁静默关掉（`usage-gate-coverage.test.ts` 用源码字符位置钉住了）。仍未变的边界：扇出直调链路上没有 worker 完成回调，所以预留会停在 `reserved` 不自动结算——那是分层事实（结算发生在进程退出、回执落卡那一刻），不是漏接线，**不要看到 `reserved` 就去「修」它**。

## 卡状态与交付证据（`cards/statemachine.ts` / `cards/delivery.ts`）

25. **底层 `changeCardStatus` 本身不证明验收通过**：它是状态字段的写入口，校验迁移合法性（`checkTransition`）、写者权限（`checkWriterAuthority`）与「转失败必须带失败类型」，**不自行核对产物或要求回执**；该函数经 `cards/index.ts` 导出，SDK 调用者仍须先履行验收职责。

    **2026-10-18 更新**：公开工具 `pao_change_status` 转 `delivered` 已接入 `cards/verifier.ts` 的 `reviewCardForDelivery`，复用机械验收、自报和越界检查，并重查当前回执产物是否存在；机械未过不能用 `basis` 绕开，人工验收必须给依据。该修复收紧模型直接使用的公开工具，未把底层同步状态函数改成另一套异步验收器，也未迁移历史卡。下面的 F 批说明保留当时的判断背景；不能再把公开工具描述为仍可无条件跳过机械检查。

    口径分三层，别混：① **分层是有意的**（状态机管迁移合法、交付管证据完整），所以这不是「设计失控」；② **洞在于第二层不是门**（`deliverCard` 是约定不是强制路径），所以这**是**缺陷；③ **本轮不修**（F 批是验证批；收紧它要重新定义「`delivered` 迁移是否强制要求回执」，会波及既有 ~180 个 spec 与历史卡，属 H 批的兼容契约决策）。

    这也解释了 F 批 T11 为什么能把伪造的 `delivered` 造出来：**T11 验的不是「产品有 bug」，而是「产品不会把伪造的 `delivered` 当成已验证的成果来展示」**——伪造态可造（本条第 ② 层）与界面如实展示（T11 断言）是两件事，互不抵消。判据：桌面只列仓库里真有的文件、不出现「已验证」字样（`desktop/apps/desktop/tests/core/f-desktop-t11-forged.spec.ts`）。修本条时同步改该 spec 的口径注记。

26. **子进程树杀在 POSIX 上名不副实**：`src/utils/kill-tree.ts:122-159` 按平台分叉——Windows 走 `taskkill /PID <pid> /T /F`（有回执、有重试、能列成员，名实相符）；POSIX 只有 `process.kill(pid,"SIGTERM")` → `waitPidGone` → `process.kill(pid,"SIGKILL")`，**无组杀、无后代枚举**，文件头 `:12` 自认「孙进程可能残留」。上层 `worker/runner.ts` 的收尾判据也只看退出码/退出事件（`:202`、`:218`、`:559-565`），没有一处检查「进程树成员是否真的没了」。所以：**`run()` 返回不等于树里没人了**；要断言树清空必须自己枚举进程（Windows 侧可看 `taskkill` 回执的成员清单）。这是**已核实的平台差异，不是待验项**，别在 POSIX 上宣称「已树杀」。**推论的推论**：既然 POSIX 侧是「没有这个能力」而不是「这个能力写错了」，将来谁在 POSIX 上补它，**那不是修 bug，是加能力**——要按新能力走变更评估（杀到谁、失败怎么办、要不要回执留痕、与 `StopProof` 怎么对齐），不能当成补一个漏掉的 `return`。

27. **场景测试里的替身必须严格照卡的声明写文件**（F 批 T01–T05 踩出来的四条）：① 配方**不提供 `{轮次}` 之类的隐式变量**——`workflow/recipe.ts:119` 的 `PLACEHOLDER_PATTERN` 只替换已声明的参数，所以 `验收` 里写死 `sN/1/` 时，第 2 轮路径还是同一个字符串，别指望产品按轮次改；② 真要按轮次分目录，只能走**已声明的配方参数**；③ 替身写的路径必须与卡上 `验收` **逐字一致**——不一致会先被验收判「未过」，再被 `checkBoundaryWrite` 判「虚报：声明未写」，两条错叠在一起最难查；④ **重做轮的区分靠内容变化（如正文追加 `<!-- 重做轮：<理由> -->`），不靠改路径**；旧稿退到 git 历史仍可 `git log --oneline --all -- <路径>` 查回，正好满足「旧稿/意见/新稿都可查」。详情与三次踩坑记录见 `.pao/harness完善-20261017/F批-全链离线验证/F3-全链离线场景-交付记录.md` 第六节。
