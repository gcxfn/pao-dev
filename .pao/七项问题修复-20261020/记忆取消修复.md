# 第 4 项：自动查库取消修复

日期：2026-10-20。

## 结论

第 4 项已修复：自动查库现在接收并贯通取消信号。在管理器启动等待中取消时，本次调用立即退出，共享管理器仍继续完成启动并保留同一实例；在召回阶段取消时，当前 gbrain 适配器把信号交给 `pi-mcp` 的 `McpClient.callTool`，MCP 客户端结束等待并发送 `notifications/cancelled`，共享 HTTP 客户端保持可继续使用。自动路由在所有文件检索都已结束、只剩供应商未返回时也会及时退出；取消不会被包装成“供应商降级”或“语义库召回失败”。

隔离测试使用本机随机端口的假 MCP HTTP 服务器，没有连接共享 gbrain、正式 PAO_HOME、外部模型或网络服务。下文的 gbrain 取消结论是“真实 `GbrainVendor` 与真实 `McpClient` 代码路径 + 隔离服务器”，不是对当前运行中的共享 gbrain 服务所做在线验证。

## 经过

初始反例得到确认：`autoPatrol` 已把 `signal` 传给 `vendorRecall`，但 `createVendorRecall` 的返回类型没有第三个参数，生产接线因此丢失信号；它直接等待 `manager.acquire()` 和 `vendor.recall()`，取消只能在两者完成后才检查。仅剩供应商一路未完成时，整次自动查询会继续等待。

代码图确认 `createVendorRecall` 的生产调用方是 `paoExtension`，测试和状态、接线冒烟等调用方依赖原有前两个参数。因此给第三个参数设为可选，保留无信号调用兼容。

首次语义路径测试直接等待一个不响应信号的假供应商，测试超时，说明只透传信号仍不足。随后在自动路由外层复用仓库已有的 `raceWithAbortSignal`：它会在取消时结束本次等待，同时注册迟到 Promise 的成功和失败处理器，避免未处理拒绝。

`pi-mcp` 的公开接口已核实：`McpClient.callTool(name, args, options)` 的 `options.signal` 是原有能力，取消后会结束当前请求并发送 MCP 取消通知。故 gbrain 路径直接传递原信号，不需要关闭或重建共享客户端。

## 做了什么

- `memory-vendor.ts`：`MemoryVendor.recall` 增加可选 `signal` 参数。已有只实现两个参数的供应商如 mnemosyne 仍兼容；其下层暂不能中止的部分由桥接层保证外层及时返回。
- `gbrain.ts`：`GbrainVendor.recall` 将信号贯通到 `McpClient.callTool`，由现有 MCP 请求取消能力处理。
- `memory/index.ts`：`createVendorRecall` 增加可选信号；在发请求前检查取消；管理器启动和供应商召回都用 `raceWithAbortSignal` 保护；共享 `MemoryVendorManager` 不因一个调用取消而关闭、复位或降级。
- `knowledge/auto-route.ts`：语义路外层也使用同一取消竞速，防止旧供应商或第三方实现不响应信号时阻塞整次自动查询；取消错误重新抛出，不进入“失败库”或“语义库召回失败”结果。
- 测试增加了启动等待取消、召回中迟到成功、迟到失败、自动查询只剩供应商未完成，以及真实 gbrain 适配器的隔离 MCP HTTP 取消与取消后继续召回。

没有修改根 `plans/`、`已知边界.md`、其他代理文件或正式运行数据。

## 风险与主代理整合事项

- mnemosyne 及其他现有第三方的 `recall` 下层未必支持取消。外层会及时返回，并为迟到成功/失败注册消费处理；但底层请求仍可能运行到结束。不能宣称所有供应商都能在底层立即中止。
- gbrain 通过 MCP 请求取消；隔离测试证明取消通知到达测试服务器且共享客户端可继续用。真实共享 gbrain 在取消通知后的资源回收、日志和数据库负载没有在线验证。
- `MemoryVendor.recall` 的第三个参数为可选；已有两参数实现无需同步修改。整合时请保留生产 `createVendorRecall` 的三参数签名和 `auto-route.ts` 的外层竞速，二者分别保护信号贯通与不响应信号的旧实现。
