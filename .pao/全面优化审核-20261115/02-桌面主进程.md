## D02 两处 git 调用补超时与隔离环境

**问题。** 两个 git 调用函数没有超时。仓库被别的 git 进程锁住或网络盘卡住时，调用永不返回，相关界面一直转圈。其中一处还吞掉了全部错误、没有用隔离环境变量。

**参照写法。** 同仓已有正确写法，照它做，不发明新写法：`electron/platform/files/git-review.ts` 约 109—134 行（15 秒超时），以及 `electron/platform/files/git-environment.ts` 导出的 `isolatedGitEnvironment()`。

**允许修改：**
- `electron/orchestration/app-store-orchestration.ts`（仅 `gitOutputLines` 函数）
- `electron/platform/files/app-store-diff.ts`（仅 `executeGitCommand` 函数）

**实施步骤：**

1. `app-store-orchestration.ts` 的 `gitOutputLines`（约 1986 行）。改前：
   ```ts
   try {
     const { stdout } = await execFileAsync("git", args, { cwd: workspacePath });
     ...
   } catch {
     return [];
   }
   ```
   改后要求：
   - 选项改为 `{ cwd: workspacePath, timeout: 15_000, env: isolatedGitEnvironment() }`，在文件顶部按相对路径导入 `isolatedGitEnvironment`。
   - `catch` 保留“返回空数组”的行为（调用方依赖它），但要记录原因：`catch (error) { console.warn("[orchestration] git 读取失败", args.join(" "), error); return []; }`。
2. `app-store-diff.ts` 的 `executeGitCommand`（约 144 行）。改前选项是 `{ ...options, env: isolatedGitEnvironment() }`。改后为 `{ timeout: 15_000, ...options, env: isolatedGitEnvironment() }`（`timeout` 放在 `...options` 前面，调用方显式传入的值优先）。其余不动。

**禁止：** 不改这两个函数的签名和返回形状；不改其他 git 调用点。

**验收：**
- 通用桌面检查四条通过。
- `pnpm exec playwright test -c apps/desktop/playwright.config.ts apps/desktop/tests/unit/changed-files.spec.ts` 通过。
- 界面测试 `tests/core/changed-files.spec.ts` 通过（命令格式见总览第 4 节）。
- 反面场景（写成一条新的单元测试，放 `tests/unit/` 下同主题 spec 里；若 `gitOutputLines` 未导出无法直接测，则只测 `executeGitCommand` 所在模块的公开入口）：在一个临时目录里放一个名为 `git` 的假脚本不可行时，改用“对不存在的目录调用”验证：函数在 15 秒内返回错误结果而不是挂起，且不抛出未捕获异常。测试文件属于“允许修改”的延伸，新增即可。

## D03 终端输出合并后再发送

**问题。** 内置终端每收到一小块输出就发一次进程间消息（`electron/platform/terminal-service.ts` 约 325 行），界面每收到一块就更新一次状态（`src/features/workbench/terminal-panel.tsx` 约 175 行）。大量输出（如安装依赖、跑测试）时每秒上千次，界面卡顿。

**目标。** 主进程把同一终端的输出按约 16 毫秒合并后一次发送。界面代码不改。

**允许修改：**
- `electron/platform/terminal-service.ts`
- `tests/unit/` 下新增一个 `terminal-output-batching.spec.ts`

**实施步骤：**
1. 在 `terminal-service.ts` 找到终端会话对象的类型定义（含 `dataSubscription`、`exitSubscription` 字段的那个）。增加两个字段：`pendingData: string`（初始 `""`）和 `flushTimer: ReturnType<typeof setTimeout> | undefined`。创建会话对象的地方同步补初始值。
2. 在类里新增私有方法 `flushPendingData(webContents, session)`：若 `session.pendingData` 为空直接返回；否则取出内容、把 `pendingData` 清空、清掉并置空 `flushTimer`，然后调用现有的 `this.sendToOwner(webContents, session, desktopIpc.terminalData, { terminalId: session.id, data })`。
3. 改 `session.pty.onData` 回调。改前：
   ```ts
   this.appendReplay(session, data);
   this.sendToOwner(webContents, session, desktopIpc.terminalData, { terminalId: session.id, data });
   ```
   改后：
   - `this.appendReplay(session, data);` 保留、仍然每块立即执行。
   - `session.pendingData += data;`
   - 若 `session.pendingData.length >= 65536`，立即调用 `flushPendingData`。
   - 否则若 `session.flushTimer` 为空，设置 `setTimeout(() => this.flushPendingData(webContents, session), 16)`。
4. 在 `session.pty.onExit` 回调的**第一行**调用 `this.flushPendingData(webContents, session)`，保证退出事件之前输出已发完。
5. 在该类销毁/关闭会话的每个路径（搜索 `dataSubscription?.dispose` 或 `dataSubscription.dispose`）里，先清掉 `flushTimer` 并把 `pendingData` 置空。

**禁止：** 不改 IPC 通道名和消息形状；不改 `appendReplay`；不改 `terminal-panel.tsx`。

**验收：**
- 通用桌面检查四条通过。
- 新增单元测试覆盖三件事（用假的 pty 对象和假的发送函数；若该类无法在单元测试里构造，则把合并逻辑抽成同文件内导出的小函数 `createTerminalDataBatcher(send, delayMs, maxChars)` 再测它，类里调用它）：
  1. 连续写入 100 小块后等 30 毫秒，只发送 1 次，内容等于 100 块按顺序拼接。
  2. 单次累计超过 65536 字符时不等定时器立即发送。
  3. 调用“退出前刷新”后，待发内容已全部发出且顺序在退出通知之前。
- 搜索 `tests/` 下文件名含 `terminal` 的 spec，全部运行并通过（至少包含 `tests/production/packaged-terminal.spec.ts` 以外的 core/unit 用例；production 用例需要打包，不要求运行）。
- 反面场景：终端关闭后 50 毫秒内不再有任何 `terminalData` 发送（测试里断言发送次数不再增加）。
