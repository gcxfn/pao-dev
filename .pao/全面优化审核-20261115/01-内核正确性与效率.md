## K02 注入留痕改为锁内重读后写入


1. 把 `auditInject` 改为异步函数，函数体改为：

   ```ts
     const latest = readControl(recipe, options);
   ```

## K03 清理没动现场时释放执行根守卫

**背景。** 执行根守卫是放在任务目录 `.pao/执行根守卫/` 下的一把锁，派发工人和清理工作副本都要先拿到它，保证不会一边干活一边删目录。`worktrees/local-host/host.ts` 的清理流程拿到守卫后，只要清理没成功就一直握着：

```ts
finally { if (!guardReleased) retainCleanupGuard(guard); }
...
function retainCleanupGuard(guard) { void guard; }
```

结果是：因为“目录还在用”“有未提交改动”这类原因拒绝清理之后，这个任务目录直到应用重启都无法再派发，也无法再次清理。

**用户认可的方案。** 按“清理有没有动过现场”分两种：

| 情况 | 处理 |
|---|---|
| 还没开始归档或删除就退出（占用中、有活动执行、有未提交或未跟踪文件） | 释放守卫，提示“已保留现场，未做任何修改” |
| 已开始归档或已执行删除后失败；或守卫状态为 `unknown` | 继续握住守卫，提示“现场可能不完整，需重启应用后处理” |

**允许修改：** `worktrees/local-host/host.ts`（清理函数与 `retainCleanupGuard`）；`local-worktree-host-cleanup.test.ts`（新增用例）。

**实施步骤：**
1. 在清理函数里（搜索 `retainCleanupGuard(guard)` 所在的 `try/finally`）新增局部变量 `let mutated = false;`。
2. 在调用 `prepareExecutionRootForRemoval` 的**前一行**置 `mutated = true;`。该调用之前的所有退出路径都属于“没动现场”。
3. `finally` 改为：
   ```ts
   if (!guardReleased) {
     if (!mutated && guard.occupancy !== "unknown") await guard.release();
     else retainCleanupGuard(guard);
   }
   ```
   `guard.release` 的真实名字以 `worker/lock.ts` 的 `acquireExecutionRootGuard` 返回值为准。释放本身抛错时记录日志并按“继续握住”处理，不向外抛出盖住原始结果。
4. “没动现场”的拒绝结果，说明文字里加上“已保留现场”；“继续握住”的结果加上“需重启应用后处理”。只改说明文字，不改结果的状态字段和错误码。

**禁止：** 不改 `worker/lock.ts`；不改派发侧拿守卫的逻辑；不改变清理成功路径。

**验收：**
- 内核基础检查通过；`local-worktree-host-cleanup.test.ts`、`worker-execution-root-guard.test.ts`、`local-pao-worktree-host.test.ts` 通过。
- 新增用例，每条都要真的再拿一次守卫来证明：
  1. 工作副本有未提交改动 → 清理被拒 → **立刻再次获取守卫成功**。
  2. 提交改动后再次清理 → 成功（证明被拒后可重试）。
  3. 让归档或删除步骤失败（用现有测试里的故障注入方式）→ 清理失败 → 再次获取守卫**失败**。
  4. 守卫状态 `unknown` → 清理被拒 → 再次获取守卫失败。
- 第 1 条在未改代码时应失败，写进回报。

## K04 散场完成后不再重复散场

**问题。** `host/host.ts` 的 `#散场Entry`：

```ts
if (entry.停止) return entry.停止;
entry.停止 = this.#执行散场(entry, reason);
try { return await entry.停止; } finally { entry.停止 = undefined; }
```

散场（结束一个保温会话并写审计记录）完成后把标记清空，于是晚到的第二次调用（等待超时、空闲熔断、全部停止三条路径都会调）会把整套散场再执行一遍：重复写审计、对已退出的进程再发终止。同文件多处用 `entry.停止` 判断“这个会话正在或已经散场”，清空后这些判断也失效。

**允许修改：** `host/host.ts`（仅 `#散场Entry`）；`host-lifecycle.test.ts`（新增用例）。

**实施步骤：** 改为成功后保留、失败才清空：

```ts
if (entry.停止) return entry.停止;
const pending = this.#执行散场(entry, reason);
entry.停止 = pending;
try {
  return await pending;
} catch (error) {
  if (entry.停止 === pending) entry.停止 = undefined;
  throw error;
}
```

**验收：**
- 内核基础检查通过；`host-lifecycle`、`host-fuse`、`host-supervision`、`host-handoff`、`host-rpc-background-real` 测试通过。
- 新增用例：同一会话先后（不是同时）调用两次散场入口，审计记录只有一条，两次返回同一份记录。
- 反面场景：第一次散场抛错后，第二次调用会重新执行散场。

## K06 系统通知子进程启动失败要有人接

**问题。** `notify/toast.ts` 的 `defaultSpawner` 启动 `powershell.exe` 发系统通知，只转发 `close` 事件。启动失败（找不到程序、被安全软件拦截）时子进程发出 `error` 事件，没有监听的 `error` 会让整个进程崩溃。

**允许修改：** `notify/toast.ts`；`notify-toast.test.ts`。

**实施步骤：**
1. 在 `defaultSpawner` 里 `spawn` 之后立即加 `child.on("error", (error) => { ... })`：记录警告（用该文件或同目录已有的日志方式），不抛出。
2. `on` 转发里补一条：调用方登记 `close` 时，`error` 也触发同一个处理函数（只触发一次，用一个布尔标记防止 `error` 与 `close` 各触发一次）。这样等待通知结束的代码不会永远等下去。

**验收：** 内核基础检查与 `notify-toast.test.ts`、`worker-notify*.test.ts` 通过。新增用例：注入一个只发 `error` 不发 `close` 的假子进程，发通知的函数正常结束、返回失败结果，处理函数只被调一次。

## K10 判定包对新增未跟踪文件设大小与二进制限制

**问题。** `workflow/control.ts` 的 `buildDecisionPackage` 把节点执行期间新增的未跟踪文件全文读进判定材料：

```ts
parts.push(`新增未跟踪文件:${path}\n${readFileSync(join(source.基线.项目根, path), "utf8")}`);
```

没有大小限制，也不区分二进制。工人产出一个大数据文件或图片，就会把整份内容塞进给模型的判定请求，浪费用量甚至超出上限导致判定失败。

**允许修改：** `workflow/control.ts`（仅这段循环，可在同文件加一个私有小函数）；`workflow-decision-facts.test.ts` 或 `workflow-control.test.ts`。

**实施步骤：**
1. 新增私有函数 `untrackedFileExcerpt(absolutePath: string): string`：
   - 用 `statSync` 取大小。超过 `UNTRACKED_FILE_MAX_BYTES = 65_536` 时返回 `（文件 N 字节，超过 65536 字节，未纳入正文，须独立核查）`。
   - 否则读成 Buffer，前 8000 字节里含 `0` 字节则返回 `（二进制文件 N 字节，未纳入正文）`。
   - 否则返回 UTF-8 正文。
2. 循环里改用它。再加一个总量上限 `UNTRACKED_TOTAL_MAX_BYTES = 262_144`：累计纳入的正文超过后，后续文件只列路径和大小，并在末尾加一行“其余 N 个新增文件未纳入正文，须独立核查”。
3. 常量写在函数旁，不做成配置项。

**禁止：** 不改已跟踪文件的 diff 逻辑；不改判定包的其他字段。

**验收：** 内核基础检查通过；`workflow-control.test.ts`、`workflow-decision-facts.test.ts`、`workflow-independent-review*.test.ts` 通过。新增用例三条：小文本文件仍全文出现；70KB 文本文件只出现说明行，文件路径仍在；含 `0` 字节的小文件只出现“二进制文件”说明行。

## K12 按卡号找卡先读单张卡

**问题。** `worker/dispatch-core.ts` 的 `locateDispatchCard` 每次都 `scanCards(cardsDir)` 读取并解析目录里所有卡，再挑出一张。一次派发调用它 7 次，卡越多越慢。

**不要做的事。** 不合并、不缓存这 7 次调用：它们分布在不同的锁内外，每次重读是为了拿到最新状态，属于正确性设计。本任务只降低单次调用的成本。

**允许修改：** `worker/dispatch-core.ts`（仅 `locateDispatchCard`）；`worker-dispatch.test.ts`。

**实施步骤：**
1. 先走快路径：`findCardFile(cardsDir, 卡号数字)` 找到文件名后 `readCard(join(cardsDir, 文件名))`，成功且 `card.card_no === target` 就直接返回。`findCardFile` 需要的参数类型以 `cards/cardfile.ts` 为准。
2. 快路径任一步失败（目录不存在、没找到文件、读取或解析抛错、卡号对不上），**不抛出**，落回现有的 `scanCards` 全量逻辑，原有报错文字和 `读取问题` 字段保持不变。

**验收：** 内核基础检查通过；`worker-dispatch.test.ts`、`worker-dispatch-guards`、`dispatch-fault-injection`、`s5-06-project-dispatch` 测试通过。新增用例：目录里有一张坏卡和一张好卡，找好卡成功；找坏卡时报错文字与改动前逐字相同（含“另有 1 张卡读不出来”）；文件名卡号与文件内 `card_no` 不一致时结果与改动前相同。
