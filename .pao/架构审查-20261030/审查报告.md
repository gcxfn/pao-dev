# PAO 架构与简洁性审查

日期：2026-10-30。对象：开发根、PAO 内核、desktop 当前工作区（包含未提交和未跟踪源码）。本轮只审查，不实施重构，不更改正式 PAO_HOME。

## 1. 结论

部门业务分工已经明确。反复修补的主要原因，是这些分工还没有完全落实为唯一的状态归属、统一的交接操作和覆盖各种执行方式的验证。现在的实现已经有不少共享入口，但新机制与旧机制仍同时参与运行；一种情况修好后，另一种角色、执行方式或中断时点可能走到另一条路径。

建议继续收敛现有内核，而不是再增加一套协作平台，也不按目录进行全库重写。优先处理：统一待决与恢复、统一结果完成路径、减少模型必须完成的手续、明确模块依赖、验证角色与故障的组合。每批必须替换对应旧分支，不能只增加新的入口。

当前不能再说“组织流程从未跑通”。最新[第五轮报告](../深度审核重整-20261028/真实运行/first-20261030-05/report.md)显示官方评分已执行、reward=0；[实施记录](../深度审核重整-20261028/实施与验收记录.md)记录组织 completed、审核 pass。这证明曾完成一次组织链，不证明答案正确，也不证明所有异常路径可靠。0 分的具体业务原因不在本次已核实范围，不能直接归因于部门架构或审核作弊。

## 3. 优先问题

### R1：同一种“需要上级判断”仍有不同出口

优先级：高。性质：当前源码确认的结构缺口；未在本轮做端到端复现。

- `PAO/packages/coding-agent/src/pao/worker/post-dispatch.ts:261`：自报 fail/not_run 经 onUnmetReports 登记结构化待决。
- 同文件 `:368`：部长 hold 仅记录停审并返回“链停，留 owner”，没有走上述待决登记。
- `workflow/host-bridge.ts:434`：直接执行节点需要语义判断时立即返回 hold。
- `workflow/auto.ts:438`：停因保存为审计记录，不等于创建有处理人、截止和可执行出口的待决。
- `workflow/control.ts:1850`：即使类型允许“部长hold”，也要求至少一项 fail/not_run；部长对整体方案或证据的疑虑未必对应某条工人自报未达项。

触发：机械检查通过、但仍有自然语言验收需要判断；部长认为证据不足；直接执行节点没有部长可作判断。已有类型名不代表生产路径已接通。

建议：由协作控制统一接收“需要判断”的结果，记录对象身份、问题、裁决者、允许的动作和截止。区分任务缺陷、证据不足、范围变更、授权问题，但不要按“来自工人/部长/审核”各造一套停链规则。不得把 hold 自动变成 pass；具体缺陷可返修，超出授权仍交用户。

验证：同一未达条件分别通过直接执行、部长拆解和独立审核进入；每种路径都产生可办理待决或明确失败，且超时不能被当成已停写。

### R2：结构化状态与展示文案仍共同决定流程

优先级：高。性质：源码确认；不据此声称每个实例都会发生不一致。

- `workflow/control.ts:1858` 的 applyPending 同时写 `待决`、`暂停`，部分种类还写 `裁定`。
- `workflow/control.ts:1950` 的 requestRuling 又重写裁定及暂停文案。
- `workflow/control.ts:1209` 的 releaseRulingPause 以 `flow.暂停 === 等待…裁定:…` 的字符串精确匹配作为放行条件之一。
- 多个清理/恢复分支需要同时清除三项；`workflow/transition.ts` 当前主要处理待决创建、合并、决策匹配和过期，并不是整个工作流唯一的状态迁移实现。

触发：恢复、审核裁定、返修中断或修改停因文案。对用户显示的文字参与控制判断，会让改提示语也可能影响流程。

建议：结构化停因成为决策来源；暂停文案和旧裁定字段由它派生。旧文件在读取边界转换，旧接口仅做适配，内部不继续多处维护同一停因。卡状态、执行是否停止、审核是否通过代表不同事实，不能粗暴合成一个“完成”。

验证：改变展示文案不影响行为；旧实例可读；每个持久化中断点重开后能明确继续或拒绝，不能重复交付/提交。

### R3：模型工具允许大量实际无效的参数组合

优先级：高。性质：源码与历史运行记录共同支持。

`workflow/tools.ts:711` 的 pao_control_node 用一个对象承载 confirm/pause/resume/reopen/rework/rule/resolve_pending 七种动作，许多参数全为可选。`tools.ts:776` 才在执行阶段拒绝 pending_key/decisions 与错误 action 的混用；`driver.ts:791` 再用长提示说明不能混用哪些字段。

最新实施记录中第四轮真实模型两次把逐项裁决参数发给 confirm，并混淆待决编号与待决项编号。当前补丁已改善错误指引，不能把这个已修的提示缺口再次报成原样未修；但宽泛参数定义仍存在。

建议：沿用公开工具与授权边界，把每个 action 的合法字段组合定义清楚，让工具说明、参数校验和调用实现共用这一份定义；对模型只提供当前角色需要的操作。能由宿主绑定的身份不让模型重新填写。先核对实际模型供应商支持的参数格式，不假设所有供应商都支持同一种联合结构。

验证：混用动作、漏项、旧编号、重复办理和迟到决定，均在副作用前拒绝；模型纠正后可重试，且不会突破人工授权。

### R4：执行监督反向理解工作流内部格式

优先级：中高。性质：源码确认的职责耦合。

`worker/supervision.ts:18` 导入 workflow/control，`:19` 导入 workflow/minister；hasV2WaitingPosition（约 `:113`）解析卡正文 HTML 标记、读冻结配方和控制文件，自行判断暂停、裁定、节点轮次与回执。这超出了执行层只报告进程活动的职责。

后果：工作流身份格式、暂停语义或节点归属变化时，监督模块也必须跟着修。监督、推进和界面可能逐渐拥有不同的“当前是否还在做事”解释。

建议：工作流提供一个窄查询，返回当前执行归属和监督所需状态；执行层只保存执行身份、活动、结果和停止证据。现有装配入口注入这个查询即可，无需事件总线或通用依赖注入框架。

验证：普通任务仍可监督；换轮次、暂停、迟到回执和控制损坏时表现明确；静态边界检查增加执行实现不得导入工作流内部文件的约束。

### R5：关键模块注册失败仍可留下部分可用会话

优先级：中高。性质：源码确认的故障处理风险，未注入复现。

`pao/index.ts:374` 的 register 对任何注册异常都只写 warning 后继续。cards、worker、workflow、verifier、delivery 等关键能力也使用该包装。函数可能已注册部分工具/事件后抛错，警告不能撤销这些副作用，也不能证明本次任务所需能力齐全。

建议：装配前明确当前角色的必需能力。关键能力失败应使该次装配明确失败，并清理已申请资源；仅确属可选的能力才允许明确降级。优先用现有角色清单和预检，不新增插件健康管理框架。

验证：让关键模块注册失败，确认任务不能继续派发；可选记忆不可用时仍可运行，但状态明确说明无记忆。

### R6：地图核验仍逐文件启动多次同步 Git

优先级：中。性质：静态性能问题，未实测本轮耗时。

`dispatch-brief/workspace.ts:150` 的 fileState 对每个文件执行两个 git show、两个 git cat-file；底层 `:20` 使用 spawnSync。captureDispatchMap（`:220`）循环调用它。precheck、brief、snapshot 又会调用采集/重采集。

一次完整采集覆盖 N 个文件，单是这一步约有 4N 次同步 Git 启动，外加仓库和列表查询。广覆盖和反复重验会放大成本；不能据此把全部模型超时都归因于它。

建议：优先复用现有 Git 帮助函数与 Git 批量读取能力，在一次操作内复用同一采集结果。保留版本变化、删除、未跟踪文件及执行中止检查；不先加跨请求长寿命缓存。

验证：不同覆盖规模记录 Git 进程数和耗时，同时断言地图摘要与旧语义一致。任务真正开始前仍需核对现场，不能为了减少调用去掉必要重验。

### R7：验证有正常整链，但异常组合和结构收敛还未证明完成

优先级：高。性质：当前场景与留档确认的验收限制。

- `bench/rehearsal/scenarios/normal.json` 已有真实进程、Git 和固定脚本模型的正常链；这是进步，不应再说完全没有整链测试。
- `bench/rehearsal/fault-matrix.json:3` 仍标 draft-unverified；条目存在不代表每个停点实际触发过。必须结合对应测试和实际日志判断，不能只凭这个标签宣布所有故障都未测试。
- 历史离线复核已有部分旧代码失败、新代码通过的证据，不能抹去这些成果。
- G2 文件分类报告明确：16 类可变状态只是分类结果，旧新同口径收益尚未证明。
- 第五轮内部审核 pass、外部 reward=0，说明组织完成与产品正确性必须分开验收；本轮未调查具体答题失败原因。

建议：在既有彩排中覆盖几组关键组合：执行方式×审核要求×有人/无人值守×结果类型，以及交接各阶段中断。使用同一业务要求，而不是为每个补丁写一个只验证新分支的样例。原始证据、审核结论和外部验收分别报告。

结构验收只看有实际意义的结果：相同规则是否仅有一个实现归属、模型需操作的固定步骤是否减少、旧路径是否退出内部运行、同一故障是否通过所有入口。行数、文件数和测试数量不能替代这些结果。

## 4. 为什么规则很明确，仍修了这么多次

1. 业务规则回答“谁负责什么”，还需要技术协议回答“交接中途断电、结果迟到、重复提交、版本改变怎么办”。这些问题需要处理，但应在公共交接边界处理一次。
2. 之前经常修复某次运行中最先暴露的一条路径。下一轮走到另一个角色或恢复时点，又遇到不同出口。R1 是当前仍可见的实例。
3. 新机制落地时没有彻底替换旧内部路径，形成额外同步责任。R2 比“文件太多”更能说明问题。
4. 部分确定操作仍依赖模型理解工具说明、抄编号和选择手续，失败被当成提示词问题继续补说明。R3 表明输入设计本身也需改变。
5. 过去环境、基准装配、观察器和生命周期也造成停链，不能全部归咎于部门衔接。10-28 的失败考古可作历史依据，不能作为10-30当前未修问题清单。
6. 正常链成功只验证一种组合。它没有自动证明人工判断、直接执行、部长hold、返修、关闭和恢复能任意合法组合。

因此不需要用户再写更多部门细则。需要开发把已确定规则落实成可检查的职责和状态边界，并以组合行为验证收敛。

## 5. 建议保留的基础

- 共享派发核心 `worker/dispatch-core.ts` 和已有完成入口 `worker/post-dispatch.ts`。继续向它们收拢，不再新增派发器。
- 内核与桌面平级宿主边界。`desktop/.../pao-worktree-host.ts:91` 起将 create/inspect/resolve/cleanup 委托共享 PaoLocalWorktreeHost，桌面保留存储与平台适配，方向正确。
- 结构化工人结果、当前 attempt 身份、成果版本绑定、停止确认、独立审核副本、原子写与跨进程互斥。这些保护有真实用途，不应以简洁为由删除。
- runtime/background 的公开计数适配、context 的有界采集、memory 的并发启动与关闭管理、knowledge 的可重建缓存，已有明确职责。抽样未形成足以主张重写的证据。
- 部门专业配置与模型判断。统一通用交接，不代表所有部门使用同一专业方法，也不应强制所有小任务都经过侦察、规划、部长、工人、审核的完整层级。

## 6. 目标职责与实施顺序

| 板块 | 独占职责 | 不应负责 |
|---|---|---|
| 主控/部长/执行者/审核者 | 范围、分工、专业实现、证据判断和必要取舍 | 手工同步状态、复制身份、机械续跑 |
| 协作控制（现有 workflow 收拢） | 依赖、任务与尝试的关联、待决、返修和推进 | 直接管理系统进程、猜模型文字来判终态 |
| 执行（现有 worker/host/worktrees） | 会话/进程、隔离目录、活动、取消、停止证明 | 判断部门业务是否验收通过、解析工作流控制文件 |
| 任务记录与证据（现有 cards 等） | 任务定义、尝试结果、证据与版本、可靠读写 | 自行决定下一个部门、另造全局流程真相 |
| CLI/桌面 | 用户操作、展示、宿主生命周期适配 | 复制业务状态迁移与删除保护规则 |
| bench | 调用产品、故障注入、独立验收与报告 | 维护产品宿主副本、替产品补业务成功 |

以上是职责归属，不要求新建六个目录或六层包装。部门名是配置；需要统一的是交接协议及错误语义。

推荐顺序：

1. **待决与恢复**：先统一 R1/R2。完整定义处理人、允许动作、截止及重放行为；迁移旧内部分支，保留公开兼容读取。
2. **模型交互与完成入口**：处理 R3，核对单卡、批量、工作流调用同一完成规则。旧工具变薄适配，保留确实不同的公开行为。
3. **执行边界与装配**：处理 R4/R5，执行层不再读取工作流内部；必需能力缺失不能进入半装配运行。
4. **组合验收与性能**：每批用 R7 的共同场景验收；再按 R6 进行批量 Git 读取和测量。无需等所有代码重写完才验证。

完成一批的条件是：新路径验证通过、被替代旧路径退出内部运行、兼容边界明确、没有把未知结果写成成功。不要用“又新增若干测试”作为该批结构收敛的唯一证明。

## 7. 本轮实际检查与限制

实际执行：在 PAO/packages/coding-agent 运行 `node scripts/gate-boundary.mjs`，退出0，B1—B6检查通过，覆盖CLI、内核公开入口、桌面宿主与driver的静态依赖边界。该检查主要防止内核依赖桌面、宿主依赖CLI；它不会发现R4这种内核模块之间的反向业务依赖。已有bundle检查也不证明发行包与当前源码完全一致。

未运行：全量测试、构建、真实Electron、付费模型、容器、官方评分、故障注入与性能基准。引用的彩排/真实运行结果是已有报告，不是本轮重新执行。没有修改产品源码、测试、规则、计划或历史报告。

本报告完成了以部门交接与职责边界为中心的跨仓架构审查；不是全仓逐行正确性审计。其他模块的深层缺陷、完整供应商兼容性和第五轮业务0分原因仍未核实。
