# 设计包：桌面「对话/派发/取消/确认同一控制入口（五态）」— 2026-10-04

需求出处：总册 P3（`plans/未完成/2026-10-04-后续执行总册.md:125-126`）。原则：桌面纯壳、文件即真相、不造第二真相（v2-ARCHITECTURE.md:70、:491）；一会话一控制方、同会话不能双驱动（v2-ARCHITECTURE.md:502、:564）；「已交付＝验收通过」（v2-ARCHITECTURE.md:49）。

## 1. 现状：控制/状态数据从哪来、断在哪

**控制通道分散（对话/取消/确认各有独立入口）**
- 渲染层经 preload 直调 5+ 独立通道：`pi-gui:submit-composer`（contracts/ipc.ts:215）、`pi-gui:cancel-current-run`（:155）、`pi-gui:respond-to-host-ui-request`（:182）、`pi-gui:start-thread`（:147）、`pi-gui:send-child-thread-follow-up`（:149）；各自 handler（electron/ipc/register-desktop-ipc.ts:687-760）。取消走 `immediate` 绕过串行动作队列（register-desktop-ipc.ts:755-760）。
- 发送与停止是两个按钮两条链：composer-panel.tsx:160（`primaryActionIsStop` 由 `status==="running"` 推导）→ use-session-composer.tsx:76-91 → app-store-composer.ts:452/476（发送，running 时转排队 followUp/steer :506-559）、:701-721（取消）。
- 「确认」（验收）桌面端无任何入口（src 全文 grep 无「验收」语义代码）。

**状态只有三态，无停止中/验收通过**
- `SessionStatus = "idle"|"running"|"failed"`（session-driver/src/types.ts:24；桌面侧 contracts/desktop-state.ts:14）。子线程另有 queued/running/waiting/complete/failed（desktop-state.ts:131-132），与控制面脱节。
- 取消链断点：`cancelCurrentRun`（pi-sdk-driver/src/session-supervisor.ts:1322-1355）置内部标志 `cancellationRequested`（:210，不对外）→ `session.abort()` 失败仅 warn（:1334-1338）→ **立即** `record.status="idle"` 并 emit（:1350-1353）。abort 是否真停无确认，「停止中」被跳过，「已停止」是假设非证据；abort 挂死时 UI 永远显示 idle。
- fork 侧反而已有停止证据链：pao_终止卡→runner 树杀→等真退出→StopProof→先停后放锁（worker/index.ts:424-540；worker/kill.ts:6-13；dispatch-core.ts:637-649 含 24h 兜底同收敛路径），但桌面会话（pi 直驱）不走这条链。

**响应丢失无查证路径**
- 控制请求无 requestId/幂等键；invoke 回的是全量 DesktopAppState 而非回执。失败/超时后渲染层唯一手段是重拉 `pi-gui:state-request`（register-desktop-ipc.ts:318-320）猜结果；重复点击＝重复写请求（重复发消息/重复 abort）。会话文件级有单写者租约可防跨进程双写（pi-sdk-driver/src/session-lease.ts:8-27），但进程内无请求级幂等。

**PAO 侧状态面（可复用的真相源）**
- 卡五态 待认领/进行中/已交付/失败/取消＋迁移表＋终态（PAO/packages/coding-agent/src/pao/cards/types.ts:6；cards/statemachine.ts:16-22、:76-78）；单写者校验＋盘上重读防覆盖（statemachine.ts:86、:185-227）。
- 执行映射 `.pao/执行映射/<执行标识>.jsonl`：每次执行独占文件、`flag:"wx"` 首行「启动」（worker/session-bridge.ts:27，崩溃残留不会被误读成成功），尾行 成功/失败/取消/未知/停止未确认（worker/runner.ts:547-597）。
- 桌面只读投影每次重读卡＋映射末行，半行只标等待不推断（pao/desktop/read-model.ts:1、:94-146）；看板经 `pi-gui:get-workboard` 一次拉三段只读聚合（pi-sdk-driver/src/pao-workboard.ts:48-53）。

**断点小结**：①三态 vs 五态缺「停止中/验收通过」；②控制动作多入口无统一回执；③无请求幂等与查询接口；④「确认」动作不通（桌面不写卡，owner 链未接）。

## 2. 方案：最小形态

**2.1 同一控制入口（砍机制优先）**
- 新增单一 IPC 通道 `pi-gui:session-control` 承载 send/cancel/dispatch/confirm/query 五动作，主进程一个控制协调器串行受理、统一回执；现有 `submitComposer`/`cancelCurrentRun`/`respondToHostUiRequest` 通道保留为内部实现，不删除（渲染层逐步切换，旧通道本期不拆）。
- 取消仍走 immediate 捷径（绕串行队列，register-desktop-ipc.ts:757-759 语义保留）；send/dispatch/confirm 走既有动作队列。
- **派发/确认不直接写 PAO 文件**：桌面把「派卡/确认」转成对 owner 会话（主控/部长）的控制消息（send 语义），由 owner 走既有 pao_派卡/pao_交卷/卡状态机（单写者纪律，statemachine.ts:86）。桌面侧五态仍只读推导，不新增写路径。

**2.2 五态状态源与判定（纯函数，表驱动）**
`ThreadControlState = 接收|执行|停止中|已停止|验收通过`，输入三元组，全部来自现有真相：
- 接收：控制回执 accepted 但 run 未启动（driver 排队消息存在，session-driver/types.ts:47 queuedMessages / supervisor `promptStarting`）。
- 执行：`SessionStatus==="running"` 且无未决取消。
- 停止中：cancel 回执 accepted 且未收到停止确认——落地改一处：session-supervisor.ts:1351 不再立即置 idle，先置新增枚举值 `"stopping"` 并 emit，`session.abort()` settle 且确认非 streaming 后再落 idle（失败落 failed）；`cancellationRequested` 随 snapshot 对外暴露。types.ts:24 与 desktop-state.ts:14 同步加 `"stopping"`。
- 已停止：idle/failed 且最近一次 cancel requestId 匹配完成（abort 拒绝/挂死超时也归此，附「未确认」标记）；进程死亡（sessionClosed reason）独立区分（总册 :126）。
- 验收通过：仅 PAO 卡路径存在——映射末行＋卡面 `状态==="已交付"`（read-model.ts:146 待审判定复用：回执在而状态未终=待审）；普通 pi 会话无此态，UI 留空不显示。

**2.3 「响应丢失先查状态」**
- 每个控制请求带渲染层生成的 `requestId`（uuid）；主进程按 `(target, requestId)` 记账（内存 Map，存 accepted/rejected/done + 结果摘要），重复投递直接返回首账，不重发写请求。
- invoke 超时/异常后，渲染层先发 `action:{kind:"query", requestId}`（只读、不走写路径）查该请求账与 target 五态；账丢失（重启）＝「未知」，按 query 返回的文件/驱动真相重建视图，不盲重发。

## 3. IPC 契约草案＋白名单/持久化影响面

```
通道 pi-gui:session-control（ipc.ts 新增一条，request-validation.ts 新增 expectSessionControlRequest）
req  = { target:{workspaceId,sessionId}, requestId:string(≤128), action:
  | {kind:"send",     text:string, attachments?:ComposerAttachment[], deliverAs?:"steer"|"followUp"}
  | {kind:"cancel"}
  | {kind:"dispatch", 卡目标:string, 派单理由?:string}     // 转 owner 会话文本，P3 最小
  | {kind:"confirm",  卡引用:string, 依据?:string}         // 转 owner 会话文本
  | {kind:"query",    requestId?:string} }                 // 只读
resp = { requestId, accepted:boolean, reason?:string,
         controlState:"接收"|"执行"|"停止中"|"已停止"|"验收通过"|"未知",
         state:DesktopAppState }
```
- 白名单：复用 expectSessionTarget/expectString/expectComposerAttachments/expectOptionalDeliverOptions（request-validation.ts:129、:71、:472、:508）；requestId 必须非空字符串；action 按联合类型逐支校验，未知字段拒绝（同 :54 风格）。dispatch/confirm 文本参数只进 owner 消息体，不经任何文件写。
- 持久化影响：控制账为内存 Map，不新建盘上文件；如需随 UI state 持久化走既有 `schedulePersistUiState` 通道（app-store-composer.ts:716 已用），不新增 JSONL。卡/执行映射仍由 fork 独占写，桌面零写入。

## 4. 测试与验收（hermetic 可测）

1. 五态映射纯函数表驱动：输入 (SessionStatus, pendingCancel, cancelRequestId, 卡状态/映射末行) → ThreadControlState 全组合用例。
2. 停止中链：mock `session.abort()` 挂起，cancelCurrentRun 后快照 status==="stopping"；abort settle 后落 idle/failed，事件序列（stopping→sessionUpdated）断言；abort 抛错仍收敛非卡死（对齐 supervisor.ts:1334 语义）。
3. 幂等：同 requestId 两次 send，driver.sendUserMessage 恰调一次，第二次返回首账。
4. 查证恢复：模拟 invoke reject → query(requestId) 返回已受理/已完成；重启后 query 返回「未知」＋全量真相。
5. 校验：expectSessionControlRequest 拒坏形状（未知 action、缺 requestId、多余字段）。
6. 真机沿总册 P3 验收口径（总册 :131）：慢流、取消、强退、断线、重复点击、取消确认、多会话多项目、中文空格路径；渲染不平白多发模型请求。
