## §0 一句话架构

wemux = 控制面（server，Postgres）+ worker 常驻 daemon（WebSocket 双向 JSON 消息）+ 每任务隔离 git worktree + 四种可插拔 agent runtime（OpenCode=本地 HTTP server+SSE；ClaudeCode=CLI stdin/stdout stream-json；Codex=子进程 JSON-RPC（app-server/proto）；Pi=**进程内 SDK** `@mariozechner/pi-coding-agent`）。任务态与结果以 `DistributedTask`/`TaskExecutionResult` 契约贯穿，`task.ack`/`task.event`/`task.result` 三段回报 + `idempotencyKey` 幂等 + worker 侧可靠外发队列。

## §2 逐问题答案（带锚点）

### 1. 任务如何下发到 worker（协议/消息形状、配对机制）

- **配对**：worker 先拿一次性 pairingCode，`POST {cloud}/api/control-plane/executors/pair` 换 `executorId + executorToken`（`apps/worker/src/control-plane/pair-client.ts:10-20`；请求形状 `ExecutorPairRequest`：pairingCode/machineId/machineName/workspaceRoot/maxConcurrency/labels/capabilities，`packages/shared/src/types/executor.ts:550-560`）。daemon 无 token 时进入 `unpaired` 态等待（`daemon.ts:961-971`）。
- **通道**：单条 WebSocket，URL `?token=` 携带凭证，消息即一行 JSON（`apps/worker/src/control-plane/ws-client.ts:29-30、63-77`）。消息契约全集：`ExecutorToControlPlaneMessage` / `ControlPlaneToExecutorMessage` 判别联合（`packages/shared/src/types/executor-messages.ts:101-554、556-1079`）。
- **下发**：`task.assign { task: DistributedTask, runtimeEnvironment?, featureFlags? }`（executor-messages.ts:578-583）。`DistributedTask` 38+ 字段（`packages/shared/src/types/task-domain.ts:565-613`），关键字段：`id / originTaskId / originTaskRunId / workspaceSessionId / idempotencyKey / retryCount / leaseExpiresAt / workerEventSequence / returnMode('summary'|'branch'|'commit') / syncBackStrategy / timeoutSec / baseCommit / workingDirectoryMode / autoCommitEnabled / publishPolicy / gitIdentity`。
- **配对幂等**：worker 收到重复 `task.assign`（同 id 已在 assignedTasks/running/queued）→ 只刷新缓存不重复入队（`message-handler/task.ts:19-26`）；首收即回 `task.ack { taskId, idempotencyKey, accepted:true }`（task.ts:35-41）。`idempotencyKey` 由 CP 生成并随任务走，所有 `task.ack/event/result` 都回带它，CP 据此防重放。
- **并发闸门**：worker 本地还有一层 `maxConcurrency` 队列，超出就排队并在心跳里上报 `queuedTaskIds`，CP 用它展示排队位次（`daemon.ts:612-647`；调度端 `executor-scheduling.ts:74-121`）。

### 2. 隔离 git worktree 如何准备与清理

- **分支命名**：`task/${taskId 规范化小写}`（`packages/shared/src/task-git-branch.ts:6-14`）；工作区会话可覆盖为 `task.workspaceBranchName`（`task-executor/index.ts:138`）。任务卡片（Task）另有一套 `buildTaskBranchName(worktreeId,title)`（`packages/shared/src/task-workspace.ts:350`）。
- **目录布局**：`<workspaceRoot>/worktrees/<workspaceId?|users/<userId>>/<taskId>`（`apps/worker/src/core/workspace.ts:29-41` + `packages/shared/src/workspace-paths.ts` 的 `getWorkspaceWorktreeBaseDir`）；repo 缓存目录 = `<base>/<name>-<sha1(repoUrl)前12位>`（`git-workspace.ts:18-26`），同 repo 多任务共享一份 clone。
- **准备**（`ensureRepoReady` + `ensureFreshWorktree` + add，`git-workspace.ts:177-210、131-175`；`task-executor/index.ts:223-241`）：
  1. 无 repo 缓存 → `clone --no-checkout --single-branch --branch <startPoint>` 只拉目标分支；
  2. `fetch origin <branch>:refs/remotes/origin/<branch>`（git-workspace.ts:37-40）；
  3. `ensureFreshWorktree`：先 `worktree prune` → 若目标分支被别的 worktree 占用则 `worktree remove --force` 抢占 → 再删目标路径（fs 级 `rmSync recursive, maxRetries:5`）→ 删同名本地分支 → 再 prune（git-workspace.ts:131-175）；
  4. `worktree add --force -B <branch> <path> <startPoint>`，startPoint 取 `origin/<taskBranch>`（重试续跑）否则 `baseCommit || defaultBranch || main`（task-executor/index.ts:237-240）。
  并发隔离即「一个 taskId 一个目录一个分支」；同任务重发是**销毁重建**（先清后建，保证干净起点）。
- **脏处理**：不做 stash/合并——直接强删重建（只影响该任务自己的 worktree）；真正成果在 commit/push 阶段已上分支。`worktree list --porcelain` 手写解析器用于找同分支占用者（git-workspace.ts:91-115）。
- **两种模式**：`workingDirectoryMode: 'worktree' | 'original-dir'`（`types/core.ts:70`）；original-dir 模式在用户原目录 `checkout -B`（git-workspace.ts:212-223），清理时明确跳过不动用户目录（`local-worktree.ts:853-864`）。
- **清理**：CP 发 `executor.worktree.cleanup.request{worktreePath, branchName, deleteLocalBranch, deleteRemoteBranch}` → `cleanupLocalTaskWorktree`：`worktree remove --force` → `worktree prune` → `removePathSafely` → 按需删本地/远端分支，全程 `executor.workspace.operation.event` 流式汇报阶段（`executor-ops.ts:785-818`；`local-worktree.ts:820-948`）。注意：**任务主链路（task-executor）结束时不自动清 worktree**，保留现场供 CP 钻取 diff/验收，清理是独立控制面操作（未发现任务完成即清理的代码路径——未确认存在自动清理）。
- 工作区会话型 worktree（非一次性任务）走同一文件的 `ensureLocalTaskWorktree`，支持复用已存在 worktree（`tryReuseExistingWorktree`，local-worktree.ts:747-763）。

### 3. agent runtime 如何被 spawn 与驱动

统一入口 `runWorkerAgentTask` → OpenCode 专用通道，其余走 `runWorkerAgentPrompt` 的 runner 表（`apps/worker/src/execution/agent-runner.ts:78-123、207-274`）。四种 runtime 三种驱动方式：

| Runtime | 驱动方式 | 流式回收 | session id 来源 |
|---|---|---|---|
| OpenCode | spawn `opencode serve --hostname=127.0.0.1 --port=<分配>`（本地 HTTP server；按 config+env hash 的**端口缓存池**复用，跨 prompt 共享） | SDK `session.promptAsync` + `event.subscribe` SSE（message.part.updated/delta）；另有 500ms `session.messages` 快照轮询双保险，会话 busy 结束且有 settled assistant 输出才算完成；120s 无活动超时 | `session.create` 返回 id；`ensureOpencodeSession` 支持传入 resume id 复用（client.ts:303-334） |
| ClaudeCode | spawn `claude -p --output-format=stream-json --input-format=stream-json --verbose --include-partial-messages --replay-user-messages --permission-mode <m> [--resume <id>]` | stdout 逐行 JSON（`readJsonLine`，agent-runner-shared.ts:57-60）；控制请求用 stdin `control_response` 回写（批准/提问） | 初始化消息返回 session_id；`--resume` 续 |
| Codex | spawn `codex app-server`（旧版 `proto`），`codex --help` 探测子命令（codex-runner.ts:22-47） | stdin/stdout JSON-RPC：`thread/started`→sessionId，`item/*` 事件流，turn/completed 带 token 用量（codex-runner.ts:1723-1726、1494） | thread id 即 sessionId，可 thread/resume |
| Pi | **进程内 SDK**：`createAgentSession({cwd, agentDir, authStorage, modelRegistry, tools, customTools(MCP), sessionManager, ...})`（pi-runner.ts:639-650） | `session.subscribe(handlePiSessionEvent)`：agent_start/turn_start/message_update(text_delta/thinking_delta)/tool_execution_*/agent_end → 统一转成 OpenCode 风格事件（message.updated / message.part.updated{part,delta}）（pi-runner.ts:444-551） | `session.sessionId`（pi-runner.ts:723） |

- 所有 runner 对外收敛成同一事件词汇表 `ExecutorAgentPromptEvent`：`session.status | message.updated | message.part.updated | message.part.delta | interaction.pending | permission.updated | session.error | session.idle`（`types/executor.ts:536-548`）——**wemux 把四种 runtime 归一成一个事件协议**，这是最值得抄的一层。
- abort：AbortSignal → OpenCode `session.abort` HTTP 调用（prompt-session.ts:288-295）；Pi `session.abort()`（pi-runner.ts:687-690）；Claude/Codex 随子进程 kill。
- Pi 的会话目录被 wemux 托管：`<agentDir>/sessions-wemux/<sha1(agentDir::cwd::model)前16位>`，续聊默认 `SessionManager.continueRecent`（`apps/worker/src/execution/pi-session-config.ts:158-160、398-424`）。

### 4. 取消/超时/失败的状态机

- **状态机**（`types/core.ts:44-56`）：`draft → queued → assigned → preparing → executing → syncing_back → completed | cancelled | failed | timed_out | lost`（11 态；终态集见 server 端 `executor-ws-message-handler.ts:89-95`）。worker→CP 每步 `task.event{status,message,sequence}`，`sequence` 单调递增防乱序（`task-event-sequence.ts:6-9`，初值取 `task.workerEventSequence`）。
- **用户点停止**：CP 发 `task.cancel {taskId, reason}` → worker：abort 当前执行 + 删定时器 + 从三张表（assigned/queued/running）移除 + 回 `task.result{status:'cancelled', result.summary=reason}`（`message-handler/task.ts:46-64`；`buildCancelledTask` task-lifecycle.ts:26-50）。**取消也算一次完整 result 回执**，不是只改状态。若任务还在排队未启动，直接出队不再执行。信号本身带 `reason`（'user_stop'|'server_abort'|'server_timeout'|...，`types/executor.ts:527-534`）。
- **杀进程树**：worker 侧全部走 `AbortController`；OpenCode server 进程有专项处理——非 Windows 用 `process.kill(-pid)`（进程组）、Windows 直接 `proc.kill`，`process.once('exit')` 兜底清池（`opencode/client.ts:27-51`）。daemon shutdown 时 abort 全部 activeExecutions + 关终端会话 + `shutdownOpencodeServers`（daemon.ts:437-501）。
- **超时**：真正生效的超时是三个：① OpenCode 120s 无输出超时（prompt-session.ts:43-46）；② CP 心跳超时 `TASK_WORKSPACE_RUNTIME_HEARTBEAT_TIMEOUT_MS` → 会话标 lost + abort 挂起 prompt，理由「执行器心跳已超时」（executor-ws-message-handler.ts:469-491）；③ worker 断线后 CP 把「曾 active 但不再被上报」的会话**立即**标 lost（不等假死超时，executor-ws-message-handler.ts:371-388 有中文注释说明动机）。注意：`DistributedTask.timeoutSec`（默认 1800，上限 7200，`routes/shared.ts:843`）存在于契约与 DB（schema-core.ts:946），但**未找到 worker 或 server 侧按它起的强制计时器**（未确认：可能在 web 层展示用，或由 leaseExpiresAt 机制接管）。
- **半成品 worktree**：失败/取消不自动清。失败 result 带 errorMessage 照常回传（task-executor/index.ts:318-346）；worktree 保留，由人/CP 稍后显式 cleanup 或下次同任务执行时被 `ensureFreshWorktree` 销毁重建。重试用 `retryCount` + 同 taskId 同分支 → `origin/<branch>` 自动续。
- **lost 恢复**：worker 重连后 register/heartbeat 上报真实 running/queued，CP 对账把 lost → executing/assigned（「执行器已重新连回控制面，任务仍在运行」，executor-ws-message-handler.ts:303-337）。

### 5. 结果与 diff 如何回传与存储

- `task.result { task: DistributedTask(整对象回传，含 result), executorId, sequence }`（executor-messages.ts:186-191）——不是只回结果，是**整个任务对象**带新状态回传，CP 直接落库。
- `TaskExecutionResult`（`types/task-domain.ts:212-232`）：`taskId / status('completed'|'failed'|'cancelled'|'timed_out') / returnMode / summary / output / filesChanged[] / changeSummary? / remoteBranchName? / commitShas[] / startedAt / completedAt / durationSec / executorNodeId / agentSessionId / opencodeSessionId / usage(ModelTokenUsage) / delivery(TaskResultDelivery)`。
- **diff 不走 result**：result 只带 `filesChanged`（git status 文件名列表）与 commitSha；完整 diff 由 CP 按需另发 `executor.git.baseline-diff.request{worktreePath, baselineTreeSha, targetCommitSha}` / `working-tree-diff` / `commit-diff` 等 RPC，worker 端 `git-ops.ts`（1653 行）实现 13 种 git 查询/操作（`executor-ops.ts:476-747`；`runtime/git-ops.ts`）。基线在开工前用 `baseline-snapshot` 存 treeSha。
- **交付元数据** `delivery`（`distributed-task-result.ts:53-135`）：按 returnMode 生成 branch 交付（branchName/repoUrl/baseBranch/pushed/suggestedNextStep/reason）与 PR 准备包（自动拼好的 title/description），并显式给出 `syncFailureReason`（如「缺少 task 级临时凭证，已创建本地提交但未推送远端」git-workspace.ts:294）——**失败也结构化，不是抛字符串**。
- 落库：CP `task-sync.ts:280-398` 把 result 展开到三处：DistributedTask.result、TaskRun.result+usage、workspaceSession 摘要；`upsertTaskLog` 把 output 写进任务对话流（task-sync.ts:327）。

### 6. worker↔控制面的心跳/断线重连

- 心跳：**5s 固定间隔** `executor.heartbeat`，携带 runningTaskIds/queuedTaskIds/telemetry/mesh/terminalSessions/localServerPort 等全量状态快照（daemon.ts:1000-1023；形状 executor-messages.ts:126-145）。CP 对纯心跳落库做 10s 节流（executor-ws-message-handler.ts:103、392-400，注释明确「心跳 5s 一次，10s 落库」）。
- 附加 RTT 探测：CP 可发 `executor.latency.ping`（sentAt），worker 回 pong 带 sentAt/receivedAt/respondAt 三时间戳（executor-ops.ts:108-123）。
- 断线：ws error/close → `abortActivePrompts`（交互 prompt 是易碎品，直接放弃）→ 关预览隧道 → 清 handler → `scheduleReconnect` **固定 5s** 重连（daemon.ts:780-801、887-919）。带 `connectAttemptSeq` 防旧连接回调串台（daemon.ts:809、835）。
- **可靠外发队列**：`task.ack / task.event / task.result / executor.agent.prompt.event|response` 五类为可靠消息，断线时入队（上限 1000，满了优先淘汰非终态消息），重连成功 register 后 flush（daemon.ts:657-700、876）。`send()` 返回 false 即入队（daemon.ts:694-700）。
- CP 侧对账：register/heartbeat 的 running/queued 与 DB 比对，多退少补（303-337）；执行器离线 → 其名下 running/waiting 会话全部标 lost（424-458）。
- 租约：`leaseExpiresAt` 在 CP 分派时写入（`control-plane/task-dispatch.ts:64` `nextLeaseExpiry()`），路由/共享层使用（routes/shared.ts:1208 用 30s）；worker 侧不消费它（未发现 worker 读 lease 的代码）。

### 7. 任务→执行会话的关联键（PAO 重点）

wemux 用 **四层双向键 + 结果回写**，没有单点魔法：

1. **派发时预埋**：`DistributedTask.workspaceSessionId`（可选）+ `originTaskId` + `originTaskRunId`（task-domain.ts:567-570）——卡在出生时就带着「我属于哪个任务/会话/运行」。
2. **运行期绑定对象**：`TaskExecutionRun { id, distributedTaskId, workspaceId, workspaceSessionId, executorNodeId, agentSessionId?, opencodeSessionId?, status, result? }`（task-domain.ts:234-252）——run 是「一次执行」的一等实体，task↔run↔session 三方各持对方 id。
3. **结果回写**（核心！）：worker 在 result 里永远回填 `agentSessionId` 与 `opencodeSessionId`（两字段同值兼容旧名，task-executor/index.ts:194-195、299-300；Pi 的 sessionId 从 `session.sessionId` 而来 pi-runner.ts:723）。CP 收到 `task.result` 后写回：workspaceSession 的 `agentSessionId/opencodeSessionId/runtimeSessionId`（`server/src/cluster/task-sync.ts:350-355`）和 TaskRun 的同名字段（task-sync.ts:371-372），取值链 `result.agentSessionId ?? result.opencodeSessionId ?? session.agentSessionId ?? ...`（旧值兜底）。governance/审计同款（governance-service.ts:240、304-305）。
4. **第二级钻取协议**：CP 可反向「按 sessionId 读原始会话」——`executor.agent-sessions.read.request { source: 'claude'|'opencode'|'codex'|'pi', sessionId }`，worker 本地扫盘找到对应 JSONL/JSON 文件逐条解析返回（`worker/src/local-api/agent-sessions.ts:818-839`；Pi：扫 `~/.pi/agent/sessions*/**.jsonl` 按 basename 匹配 sessionId，698、798-816；Claude：`~/.claude/projects/**/*.jsonl`；Codex：`~/.codex/sessions/**/*.jsonl`；OpenCode：message 目录）。也就是说 **sessionId 本身就是足够稳定的钻取键**，worker 能从磁盘裸文件把会话内容重建出来（含 boilerplate 过滤，`shared/executor-agent-session.ts:8-30`）。
5. **失败也能关联**：即使任务失败，result 仍回传（status='failed'），此时 sessionId 可能缺失——CP 靠 `taskId` 前缀（worktree/分支命名 `task/<taskId>`、commit message `wemux: <taskId>` git-workspace.ts:269）做兜底归因。

PAO 直接答案：**关联键 = 在派卡时把 paoCardId 写进会话（Pi 的 SessionManager 目录/首条消息 metadata），并在 worker 会话结束时把 `sessionId` 写回卡的 JSONL 回执**；卡→会话不需要实时猜测，靠「派发预埋 + 结果回填」两端各写一次。

## §3 PAO 可抄清单

> 图例：[直抄] 机制可直接搬；[翻译] 需按 PAO 假设改造（括号内为翻译点）；wemux 文件为 Apache-2.0，逐文件抄代码须保留原许可声明（见 §5）。

### A. 卡→会话可靠关联键（最高优先，直答 PAO 缺口）
- **抄**：「派发预埋 + 结果回填」双写模式（§2.7）：卡协议加 `sessionIds` 字段；worker 会话创建后立即（不等结束）回一条 `session.started{cardId, sessionId, pid}` 事件；结束时 result 回填最终 sessionId/usage/durationSec。参考 `task-executor/index.ts:194-195`、`task-sync.ts:350-372`。
- **抄**：`TaskExecutionResult` 字段集作 PAO「diff 回执」模板：`status/summary/output/filesChanged/commitShas/durationSec/sessionId/usage`（`types/task-domain.ts:212-232`）。
- **抄**：`ExecutorAgentSessionSummary/Detail` + 本地扫盘读回（`types/executor.ts:436-470`、`local-api/agent-sessions.ts`）作 PAO Electron「两级钻取第二级」——PAO 是 pi fork，**直接扫 `.pao/worker会话/*.jsonl` 即可**，甚至比 wemux 简单（不用跨四种 home 目录）。
- [直抄程度：高] 关联键是纯文件协议，无 server 依赖。

### B. 五态控制入口的状态机骨架
- **抄**：11 态判别 + 终态集合常量 + 「取消也回完整 result」原则（`types/core.ts:44-56`；`task-lifecycle.ts:26-50`）。PAO 五态可映射：接收=assigned、执行中=preparing/executing、停止中=独立过渡态（wemux 没有显式「stopping」态——它用 abort 即终态，PAO 的「停止中」要自己加，参考 abortReason 枚举 `types/executor.ts:527-534` 表达停止原因）。
- **抄**：AbortController-per-task + 事件单调 sequence（`task-lifecycle.ts:54-122`、`task-event-sequence.ts:6-9`）：PAO 的 worker 子进程会话同样应该每卡一个 AbortController，JSONL 事件带 sequence 防乱序。
- **抄**：心跳快照模式：worker 状态文件每 5s 写一次全量（running/queued 卡 id 列表），主控/Electron 读文件即可判活，不用进程间 RPC（`daemon.ts:756-778` → PAO 版写 `.pao/worker状态.json`）。
- **抄**：CP 侧「任务消失检测」：卡显示执行中但 worker 状态文件里没有它 → 立即标异常而非等超时（`executor-ws-message-handler.ts:371-388` 的中文注释直接可抄进 PAO 设计文档）。

### C. worktree 隔离（PAO 若做代码类卡）
- **抄**：`ensureFreshWorktree` 的「prune→抢占同分支旧 worktree→fs 强删→删分支→重建」五步 + `removePathSafely` 的 maxRetries 重试删（`git-workspace.ts:122-175`）——Windows 上删目录失败是常态，这个重试参数（5 次×100ms）是实战值。
- **抄**：repo 缓存共享布局 `<root>/repos/<name>-<hash(url)>` + `clone --no-checkout --single-branch`（`git-workspace.ts:18-26、197-199`）：多卡同仓库只 clone 一次。
- **抄**：分支命名函数 `getTaskGitBranchName(taskId) => task/<slug(taskId)>`（`task-git-branch.ts`，14 行小函数可整文件抄，带许可头）。
- **抄**：清理是**显式独立操作**且 original-dir 模式绝不清理（`local-worktree.ts:853-864`）——PAO「验收通过→清理」态可对应 `executor.worktree.cleanup.request` 的参数形状（删不删本地/远端分支由卡决定，`executor-messages.ts:827-841`）。
- [翻译] wemux worktree 命名含 workspaceId/userId 维度，PAO 单机可简化为 `.pao/worktrees/<cardId>`。

### D. runtime 归一事件协议（对 PAO pi 内核是「抄自己」）
- **抄**：统一事件词汇表 `ExecutorAgentPromptEvent` 8 种 + `message.part.updated{part, delta}` 增量形状（`types/executor.ts:536-548`；pi-runner.ts:350-438 演示 pi 原生事件→统一事件的映射）。PAO 的 pi 会话 JSONL 落盘如果采用同一形状，Electron 聚合端、主控回放、未来接入其他 runtime 三方共用一套渲染。
- **抄**：`waitForPiSessionSettled`：`session.prompt()` resolve 后还要排空内部事件队列才算真完成（pi-runner.ts:587-598）——**pi 内核实战坑**，PAO 直接抄。
- **抄**：`installPiToolCallStreamRepair`：修 pi 流式 toolCall 块缺 id/参数分片的问题（pi-runner.ts:123-240）。这是对 pi 的 upstream bug 修复，PAO fork 可考虑上移到内核。
- **抄**：usage 提取：pi AssistantMessage.usage → ModelTokenUsage 归一（pi-runner.ts:308-336）。
- [翻译] wemux 把 pi 当四个 runtime 之一跑在 worker 里；PAO 的 worker 本来就是 fork 内核 spawn 的，这层映射天然存在，只需保留事件形状。

### E. 可靠性模式（文件真相源版翻译）
- **抄（思想）**：可靠外发队列（§2.6）：PAO worker 与主控之间无 WS，但「终态消息永不丢」原则翻译为——worker 写 JSONL 是追加+fsync，主控错过事件时按 sequence 补读；队列淘汰策略（满 1000 先丢非终态）可翻译为状态文件的环形缓冲。
- **抄**：连接代数防串台（`connectAttemptSeq`，daemon.ts:809）：PAO 的 Electron 聚合端 watch 文件时同理，用文件代数/mtime 防旧 watcher 事件。
- **抄**：结构化失败回执：`delivery.syncFailureReason` 的写法——每种不 push/不 commit 的情况都给一句人话 reason（git-workspace.ts:283-295）。

### F. 小而美的纯函数（可直接带许可抄）

## §4 明确不值得抄的

1. **client-server 全套传输层**：WS 双向消息 + executor.register/心跳握手 + route-selection 多线路探测（`control-plane/route-selection.ts`）+ mesh（EasyTier）。PAO 无 server、文件即真相源，这套传输/路由/注册发现全部多余。
2. **CP 侧调度评分器**（`executor-scheduling.ts:62-199`）：为多 worker 集群设计（preferred/binding/failureRate/busyScore）。PAO 单机蜂群用不上；若未来多 worker，再回来抄排序因子。
3. **OpenCode server 端口缓存池**（`opencode/client.ts:23-49`）：为复用外部 CLI 的 HTTP server。PAO 的 pi 是进程内内核，无此成本。
4. **`timeoutSec` 契约字段**：wemux 自己都没有可靠的强制执行（§2.4 未确认项），抄进来只会得到一个没人兑现的承诺。PAO 应直接设计「无输出超时 + 主控强杀」两个真实存在的超时。
5. **Codex/ClaudeCode 两个 runner 的协议细节**（共 2700+ 行）：PAO 只需 pi；等真要接外部 CLI runtime 时再回来抄（届时 claude-runner.ts 的 stream-json 双向协议与 codex-runner.ts 的 app-server JSON-RPC 是现成参考）。
6. **zellij/persistent-terminal/mesh-runtime/preview-tunnel/desktop-sandbox 等周边子系统**：与 PAO 执行链核心无关（占 worker 目录约一半代码量）。
7. **任务执行时不自动清 worktree**：wemux 保留现场是配合它的 CP diff 钻取；PAO 磁盘敏感，验收通过即清（但要在回执里先落 diff/hash，学它「清理前先物化证据」的思想——`materializeRuntimeEnvironment` 与 baseline-snapshot 的顺序）。
8. **Postgres/Drizzle 存储层**：PAO 用 JSONL，无迁移可比。
