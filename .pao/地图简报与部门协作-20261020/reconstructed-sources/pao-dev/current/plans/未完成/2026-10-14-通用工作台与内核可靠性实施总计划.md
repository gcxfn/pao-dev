## 1. 目标、文档归属与完成标准

### 1.1 要交付的产品

把 PAO 现有工作流页面变成由主控对话安排工作的通用工作台。第一版以小说创作为完整使用场景：讨论计划 → 主控创建临时工作流 → 已有部门分工 → 查看步骤卡 → 确认执行 → 阅读文件 → 提修改意见 → 审稿与修订 → 人工确认 → 按需保存模板。

临时工作流像可执行的待办清单，但保留前置依赖、部门、约束和验收要求。它由主控使用工具创建，不增加“创建临时工作流”按钮，不要求用户将已讨论的内容重填表单。步骤卡取代画布成为默认工作入口。

## 3. 范围、权限及明确边界

| 文档与验收 | `plans/`、必要决策笔记、`.pao/` 隔离证据 | 原报告保留，任务与状态只在本计划维护 |

### 3.2 本计划不包含

- 视频剪辑器、视频编码/时间线、素材管理平台；后续有真实需求再扩展工具和格式。
- 新工作流引擎、第二套调度状态、插件市场、通用数据库或全局缓存框架。
- 运行中直接改冻结图、任意跳步、部分成功放行汇聚、写任务并行、跨会话接管规则放宽。
- 自动升级或批量迁移 v1 实例、全库改名、顺手清理无关代码和历史成果。
- 正式 PAO_HOME 写入、正式会话试跑、真实供应商调用、外部发送、推送和发布。它们不由“计划整合”自动获得授权。
- 修改 pi 上游本体。审查问题优先在 PAO 业务层修复；确有公开接口缺口时，先给出最小缺口与替代方案，再单独决定。

### 3.3 小说工作区与当前交付机制

第一版复用现有以 Git（本地文件版本记录）基线支持的项目执行、越界检查及交付机制。小说集成样例必须在隔离 Git 项目中运行，且先形成初始提交，具备有效 `HEAD`；只有 `git init` 仍不满足 v2 基线要求。应用对尚未准备版本记录的目录给出启动前说明和处理指引，不假装任意空目录都可直接自动交付，不自动初始化正式目录，不静默跳过基线。

计划定义、控制和运行证据放 `.pao/`；小说设定、大纲、正文及审稿文件放项目普通目录，例如 `创作成果/<planId>/<步骤ID>/<轮次>/`，确保未被 `.gitignore` 排除。现有基线把 `.pao/` 整区排除在差异检测面之外，不能把小说正文也放进临时计划目录，再宣称越界核查和自动交付已覆盖正文。

不为小说任务运行代码编译或强制代码测试。文件存在、可读取等机械检查只证明成果形成；人物一致性、情节与文风由审稿及用户确认负责。非 Git 目录的全新交付模式不纳入本批；如实施调查证明首批场景必须改变这项边界，先修订本计划，再改执行层。

开发仓不自动提交、推送或发布。隔离样例中的 Git 基线和产品自动交付产生的本地提交属于测试数据，要和开发仓提交明确区分。

### 4.2 三个对象，分别承担什么

| 对象 | 保存内容 | 不保存的内容 |
|---|---|---|
| 临时计划定义 | 稳定计划 ID、显示名称、来源项目/主控会话、定义版本、步骤要求与依赖、创建请求身份、执行关联 | 不复制正在执行的节点状态、卡片状态或费用总额 |
| 执行实例 | 现有 v2 冻结配方、实例 ID、owner、节点轮次、任务卡、回执和控制记录 | 不从页面内存恢复业务状态，不跟随模板编辑悄悄变化 |
| 已保存模板 | 可复用的步骤、部门、依赖、参数、约束、技能、预算、验收、人工门及已有审核/并行定义 | 不含当前会话、卡号、实例状态、当前意见处理状态、本次成果路径与回执历史 |

推荐临时定义落在所属项目 `.pao/临时工作流/<planId>/计划.md`。同目录保留最小必要的未执行编辑版本供撤销；首次执行后冻结，不能靠修改这份定义更改已运行实例。实际执行目录布局沿用既有启动器约定，稳定分配及重试回读按下一段执行；计划只关联它，不再建立第二个控制文件。

现有 `desktop/index.ts` 的 `startDesktopWorkflow` 会读取 PAO_HOME 模板文件、随机分配执行目录并返回 `void`，不能直接满足临时定义的要求。本次在共享工作流边界补“项目内定义启动”分支，复用预检、owner、冻结和 v2 执行核心；不得把临时定义偷偷安装进全局模板库。执行目录沿用现有布局约定，但必须在首次启动受理时持久确定，同一启动请求的重试复用原目录，并返回实际实例 ID、目录及受理状态；既有模板启动入口保持兼容。

主控工具在原会话内部串行执行，不能照搬外部桌面启动入口的“会话必须空闲”判断，导致主控正在调用启动工具时永远被拒。外部请求的忙碌守卫仍保留；新通道通过原 owner 内的串行工具入口和同一业务检查启动，不能整体删除空闲检查或并发向会话发普通 prompt。

`planId` 使用内核生成的稳定 ID；显示名可重名或含普通空格，不能拿显示名拼任意磁盘路径。内部配方名由稳定 ID 派生为符合既有校验的名称。现有配方协议字段不全局改名；显示名称、预期成果等界面字段由独立计划定义承载。

每个步骤具有计划内稳定 ID，显示顺序只供阅读。适配器负责步骤 ID 到合法配方节点名的映射；未执行改标题不能丢失意见对象，依赖与审核回边必须同步校验。v1 既有实例保持原身份和行为，不自动转换。

成果和意见沿已有执行记录、对话记录扩展最小关联；没有可复用归属时才加计划内的专用记录，不增加通用事件平台。

### 4.3 必须提供的业务动作

下列为动作语义，正式导出名在阶段 3 固定；主控工具和桌面桥调用同一实现。

| 动作 | 输入关键项 | 受理前检查 | 成功结果与失败行为 |
|---|---|---|---|
| 创建临时计划 | 逻辑请求 ID、显示名、步骤及约束 | 项目和来源会话由宿主核实；结构、依赖、部门均校验 | 落盘后返回 planId、版本和摘要；失败不展示已创建 |
| 修改/撤销 | planId、预期定义版本、具体字段或目标旧版本 | 同项目、原主控归属、未启动、无版本漂移 | 原子保存新版本；撤销也是一次有版本检查的修改，不能覆盖别处新修改 |
| 查询/恢复查看 | 已发现的 planId/实例身份 | 路径属于项目、文件可读、版本可识别 | 返回定义及现有运行投影；损坏显式报错，不重建假状态 |
| 确认并启动 | planId、精确版本、独立启动请求 ID、用户确认事实 | 预检通过、定义未变化、原 owner、当前未启动 | 复用 v2 启动；受理后返回真实实例关联，不把“已受理”说成完成 |
| 人工确认/暂停推进/恢复 | 现有实例、节点、轮次、动作与理由 | 复用现有控制桥和内核守卫 | 内核成功后刷新；过期轮次、错误会话和不满足条件一律拒绝 |
| 保存模板 | planId、定义/冻结版本、模板名、目标模板版本 | 白名单提取、文件名校验、同名及运行中模板保护 | 写入现有模板目录；失败保留计划，原运行继续关联原实例 |
| 对步骤/文件提意见 | 计划/实例、步骤 ID、轮次、可选文件版本身份、意见 | 确认目标仍可定位、会话归属正确 | 保存对话关联并报告实际投递状态，不把发送当作应用 |

主控只有在结构化工具成功后才能宣布创建。普通回复中的编号清单、Todo 或原型关键字不触发真实创建。主控系统说明和工具说明需要告诉模型：何时把讨论转为计划、缺什么时询问、如何使用已有部门及保存模板动作。

### 4.4 重复请求、崩溃和确认边界

1. 创建、启动、保存模板分别使用可持久识别的逻辑请求 ID。同一逻辑操作的网络重试沿用原 ID；参数变化却复用 ID 时拒绝，不猜用户意图。
2. 在项目/计划锁内重读并检查版本。并发重复创建只落一个定义；启动只受理一次；模板保存只产生一个目标版本。
3. 启动器先有稳定执行身份，再建立关联。若控制文件已经形成但返回丢失，重试必须找回原实例；若只留下不完整启动，显示待恢复原因，禁止直接再启动第二份。
4. 不用“内容相似”来合并两个不同的任务。同名计划可以并存，始终靠项目、来源会话和稳定 ID 区分。
5. 对话中的执行确认必须关联当时展示的计划版本；确认后计划被改，旧确认失效。复用现有显式确认能力，不通过伪造 `ui.confirm=true` 绕过。若确认无法被现有桥可靠承载，仍在当前主控展示一次确认卡，不要求重填计划。
   确认事实只能由宿主确认回调或可信的用户交互事件提供，并绑定 planId、定义版本和启动请求 ID；模型传入的 `confirmed: true`、自行转述“用户已同意”或普通助手文本均无效。等待确认期间不持有长期文件锁；返回后重新核对 owner、版本和预检结果，再在锁内受理。无桌面集成使用明确模拟的宿主确认回调，不能将其标作真实用户确认。
6. 创建不启动，启动不保存模板，保存模板不改变当前执行。用户没有请求保存时不自动加入模板库。
7. 重开应用只恢复查看和连接现有状态，不静默重派任务。机器重启后遗留在途状态按现有租约/恢复规则显示，用户明确恢复后才继续。

### 4.5 成果、版本和意见的关联

- 预期成果是要求；实际成果必须来自真实执行回执、节点产物或既有明确文件来源，并经过宿主路径核实。只读零卡节点可有审查记录而没有文件，不伪造“审稿文件”。
- 一个文件条目至少关联项目、计划/实例、步骤、轮次、已确认路径和可用于识别版本的依据。同名不同目录分别显示；历史轮次不得因为路径相同而覆盖旧稿。
- 第一版小说输出采用第 3.3 节受 Git 检测的普通成果目录，按计划/步骤/轮次保留原稿，并关联真实执行实例。没有保存历史正文时，不承诺能预览那个历史版本；显示真实可用记录。
- 文件意见绑定提交时正在阅读的版本。阅读旧稿时收到新版本，只提示“有新版本”；不抢光标、滚动位置或悄悄把意见改绑新稿。
- 意见至少区分“已记录”“已送达/待送达”“已应用/未应用”。“已应用”须有真实业务处理结果和对应改动依据；不新增靠前端勾选就生效的状态。
- Markdown 预览沿用现有内容安全处理；符号链接、相对路径、Windows 大小写与 UNC 路径继续走既有宿主边界。路径核验失败不能退回让页面直接读盘。

## 5. 工作台交互规范

### 5.1 页面与状态

| 区域 | 必须显示/支持 | 交互边界 |
|---|---|---|
| 现有应用导航和工作流标签 | 本次任务、历史运行、已保存模板；未保存模板标记 | 不把临时任务和模板混成一个名单，不新增临时创建按钮 |
| 顶部摘要 | 工作名、全局总数与已完成/进行中/待处理/失败/读取异常、来源会话 | 统计包含筛选外步骤；明确显示过滤后数量，避免用户误读 |
| 中间步骤卡 | 序号、名称、部门、状态、具体等待原因、已生成文件 | 按真实依赖稳定排序；搜索、筛选、下个待处理、多卡展开、审核退回均可到达 |
| 右侧详情/文件栏 | 步骤完整任务、输入、约束、验收；或文件正文与来源 | 打开文件不改变步骤选择和发言对象；“定位所属步骤”才切步骤 |
| 底部主控对话 | 当前会话、当前讨论对象、输入草稿、真实送达反馈 | 查看步骤不自动改变发言对象；“讨论这一步/就此文件提意见”显式改变 |

步骤卡不是只按 1→2→3 的假串行列表。多个前置显示“等待第 2、3 步”；显式并行组可并排或分组，窄屏纵排。审核退回显示目标、原因及轮次，旧成果保留。多卡节点展示全部卡及汇总状态；不以第一张卡代表全部完成。

状态不能只靠颜色。读取异常、等待前序、等待部长、待审、待人工确认、预算不足、暂停推进、执行失败、已取消、已完成分别解释。未知值显示未知并可查看技术原值，不随意翻译成成功。

“暂停推进”只阻止后续节点启动，不能写成“停止所有任务”。停止在途执行继续使用已有停止/终止入口和原会话守卫；首批没有整个实例的一键强杀语义。重试必须说明目标步骤、轮次及影响的下游，不能误重跑全流程。

### 5.2 部门、编辑和阅读

- 部门用原生下拉，从当前 PAO_HOME 的真实目录读取；加载、空目录、失败、旧部门失效分别展示。不允许自由输入不存在的部门，不自动新建，不悄悄替换成第一项。
- 未启动计划支持字段编辑、依赖校验、保存反馈和撤销。运行中冻结任务要求只读；可经主控提出变更并展示“尚未应用”。首批不实现运行中改图，也不把改模板说成改本次任务。
- 模板覆盖/另存必须明确；同名和版本漂移不覆盖。运行中同名模板继续遵守已有保护，可另存，不削弱冻结规则。
- 成果名可点击，附必要相对路径；右栏默认只读，编辑走现有编辑器和未保存提示。支持专注阅读、返回步骤详情、复制完整路径。
- 文件缺失、移动、权限不足、过大和格式不支持分别说明；非文件说明保留文字。Markdown/文本优先，图片复用已有预览，视频提供真实可用打开方式，不做剪辑功能。
- 进度刷新不得抢当前选择、焦点、草稿或阅读位置。切任务/会话按各自身份保存草稿；提供“回到当前步骤”。
- 在 700、900、1280px 窗口和 125% 系统缩放检查。窄窗口右栏可移到下方或进入专注阅读，主要操作不被遮挡。
- Tab、Enter/Space、退出预览及焦点返回可用，控件有中文名称；读屏可听到步骤、状态、前置关系和文件来源。

## 6. 分阶段执行细则

每阶段按“核对入口与影响面 → 小范围修改 → 定向检查 → 真实入口补验 → 记录证据”执行。任务 ID 只用于定位和验收，不表示新的技术模块。阶段失败只回到对应边界修复，不顺手扩大重构。

### 阶段 0：固定基线与实施契约

**输入：** 本计划、三仓当前工作树、旧验收及 fork 审查证据。

**执行：**

1. 记录开发根、PAO、desktop 的当前分支/提交和已有改动；只标记本轮文件，不重置原改动。
2. 用代码图确认预算、写卡、协作、临时计划接入、工作流动作、文件预览与对话调用链，核对图是否过期；当前源码优先。
3. 在约定证据目录准备隔离 PAO_HOME、项目、会话及 Git 仓；确定自动化不会读取真实凭证或连接真实端点。
4. 复用审查脚本确认问题仍在；已被其他修改修复的条目先按第 7 节验证，不重复修改，登记“既有修复，经补验通过”。
5. 固定计划 ID、步骤身份、存储归属、启动关联和显式确认方式，核对现有 v2 启动是否可接内存/项目内定义。差异写入本计划第 4 节，不能留给页面各自猜测。
6. 固定性能夹具和采样方法，先留改前数据；记录真实 Electron 和 TUI 的启动方式与环境。

**边界：** 不开始画布重构，不建新框架，不触碰正式数据。若新契约与现有 owner/冻结规则冲突，先缩小方案，不能绕过守卫。

**完成条件：** 有基线文件、可重跑隔离夹具、任务—代码—验证入口清单；第 4 节不存在会影响实现的未决存储/身份问题。

### 阶段 1：停止、回执与文件写入可靠性

**范围：** 审查第 1、2、3、4、12 项；主要为 memory、worker budget/runner、cards、knowledge ingest。

**执行：**

1. 把审查反例转为对应模块的回归用例；先确认失败点与真实入口一致。
2. 统一记忆工具取消检查；合并并发启动等待，处理启动期间关闭及迟到实例。
3. 对齐父子预算与最终回执例外，保持工具调用/费用兜底，避免用无限加轮修掉表象。
4. 改正卡片字符串序列化，补字段类型校验；历史畸形卡报清楚，不批量自动改用户文件。
5. 入库所有文件名/目标归属检查前移到移动前；合法重复入库和已有锁内幂等行为保留。

**完成条件：** 第 7 节对应五项验收全部通过；取消前未发出的模拟写入为 0、最终回执可完成且预算仍能拦住失控、字符串来回一致、非法入库不改文件、供应商无遗留实例。

### 阶段 2：任务受理、并发和反馈正确性

**范围：** 审查其余 12 项：5–11、13–17。

**执行：**

1. 为卡片扫描提供“可读结果＋问题”，逐个迁移相关消费者；空目录与读取失败分开，保留正常任务可用性。
2. 修正模型选择的完整 ID；部长插话明确即时干预或排队，并等待对应请求的确认。当前任务/确认门的紧急补充采用即时干预；普通新增任务排队，界面说明实际模式。
3. 协作和巡检把查重、限额和创建保护在同一跨会话/进程临界区，避免嵌套卡号锁导致死锁。
4. 自动链逐卡核额度；受理前保留并发预留，确定拒派时归还。已受理后失败不能当未运行退账；重开后计数也必须一致。
5. 供应商模型 ID、部门大小写、验证出处、审计部分成功和桌面用量分别小范围处理。
6. v1 人工确认复用目录归属守卫，保留现有实例锁及 v1/v2 行为。

**完成条件：** 第 7 节全部 17 项已验收，或阶段 0 已确认原有修复并提供相同验收证据。没有用伪成功、吞错或取消限额来让检查通过。

### 阶段 3：临时计划的共享内核能力

**前置：** 阶段 0、1；阶段 2 中的受理幂等、目录身份与额度问题在启流接入前通过。

**执行：**

1. 在 workflow 边界内实现计划定义读写、版本与编辑撤销，不将它们塞进页面或上游模型循环。
2. 接入既有配方校验，适配任务、部门、依赖、人工门、预算和预期成果；拒绝未知部门、环形依赖与失效版本。
3. 提供第 4.3 节动作，来源会话/项目由宿主解析。创建工具成功只表示计划落盘。
4. 补项目内定义启动分支，复用 v2 启动、冻结与控制；先持久分配请求对应的执行目录，再受理执行，返回真实实例身份。实现重复启动恢复、关联回读和部分启动错误。新增查询能够发现临时定义及关联实例，不要求先加入模板库，也不按名称重走全局模板加载。
5. 保存模板使用字段白名单并参数化本次特有路径；无法安全泛化的值展示给用户确认或作为待填参数，不能保存一个误指向上次文件的模板。
6. 补正常、非法、并发、写失败、响应丢失和进程中断用例，检查 v1 读取及既有 v2 流程没有退化。

**完成条件：** 无桌面 UI 时，以明确标注的模拟宿主确认回调，通过正式内核入口完成创建→修改→撤销→确认启动→查询→保存模板；模型布尔值不能自行授予确认。重试不重复执行或重分配执行目录，启动后定义冻结，保存模板不带运行数据。

### 阶段 4：主控对话与桌面桥接入

**前置：** 阶段 3 的契约固定。

**执行：**

1. 扩展既有 SDK/IPC/contracts 的最小动作和查询接口；页面只传已发现身份与用户意图。
2. 在主控上下文/工具说明中接入讨论转计划规则，读取已有部门，缺关键信息时定向提问；不靠扫描自然语言自动执行。
3. 对话显示计划摘要、“查看计划”及与具体版本关联的执行确认；工具受理失败展示真实原因，消息重放不重建计划。
4. 接入步骤/文件讨论对象，保存草稿与意见关联；已记录、待送达、已送达、已应用的事实分开。
5. 多会话/多项目、同名计划和来源主控被关闭时给出明确归属提示；不静默改由另一个主控执行，也不新增自动接管。

**完成条件：** 在真实 Electron 的当前主控内讨论并通过正式工具创建；无临时新建按钮，无重复填表，无跨会话操作或伪造路径。结构化离线工具事件只作为可重复测试输入，须标记模拟，不能证明模型会自主选对工具。

### 阶段 5：步骤卡、部门与成果右栏

**前置：** 阶段 3–4 可查询真实计划/实例。

**执行：**

1. 在现有工作流标签/页面接入卡片主视图，继承搜索、筛选、全局统计、下个待处理、审核回边、多卡和当前选择能力；取消默认画布入口。
2. 用共享投影显示状态；前端只保存选择、展开、草稿、阅读位置等界面偏好。
3. 右栏接任务要求编辑与部门目录下拉；加载错误、失效部门、版本冲突均可见。
4. 将明确的文件成果接到右栏预览，支持专注阅读、返回详情、同名区分、历史轮次和新版本提示；显式编辑沿用已有编辑器。
5. 接入人工确认、暂停推进、恢复及既有单卡停止讨论入口，展示正确影响；未支持的运行中改图不给假按钮。
6. 完成三种窗口宽度、系统缩放、键盘与读屏检查。进度刷新不抢焦点，切任务不丢草稿。

**完成条件：** 第 5 节全部行为及第 9 节对应场景通过真实 Electron 验证，产物点击来自真实隔离文件，不使用静态原型代替集成。

### 阶段 6：其他页面交互、中文与 TUI 补齐

**前置：** 核心卡片流程能运行；可按独立页面小包实施。

**执行：**

1. 按第 8 节九类确认项逐项改默认展示，统一预算、用量、耗时、文件和错误文案。
2. PAO 常用工具的对话结果提供计划、步骤、文件、受理结果与错误的专用展示；模型结构化事实和原始记录保留。
3. 复盘按步骤/轮次列完成、打回、成果和人工确认；原始恢复记录另查。
4. 在普通导航可达页面扫查残留技术字段与英文状态；每个命中先确认实际可见，再改文案，不全局替换 JSON。
5. 真实 Windows ConPTY 验证同名实例精确选择、损坏实例钻取、坏卡问题和交接页；卡片页面与 TUI 对同一隔离状态结论一致。

**完成条件：** 第 8 节九类确认项已处理，四类疑点已验证并有结论；普通流程无需 JSON，技术详情仍可查；同名/损坏 TUI 有实机证据。

### 阶段 7：完整小说闭环、恢复、性能决策与离线发行验收

**前置：** 阶段 1–6 通过各自验收。

**执行：**

1. 完成第 9 节全部必验场景，运行至少一次“审稿打回→重做→再审→人工确认”的完整离线流程。
2. 重开应用、强制结束测试应用及重启测试机器后，检查计划、实例、文件和意见关联；在途任务不得静默重派。机器重启由用户安排或在另行获准的测试环境完成，不擅自重启当前工作机器；未能执行则保持该项未验。
3. 按第 10 节测量性能候选，逐项作实施或保留结论；实施项重新跑受影响的行为与性能验收。
4. 执行受影响模块的定向测试、内核类型/边界检查和桌面类型/架构检查；为真实 Electron 和最终离线发行检查执行必要构建。
5. 本地生成 Windows 解包发行物，使用隔离 PAO_HOME 启动，断开对源码绝对路径与全局 CLI 的依赖后再走关键流程；不发布、不安装覆盖正式版。
6. 更新长期需求/架构的实际新契约及文档导航；整理结果、失败记录、复现命令和限制。最后核对三仓改动范围，保留原有成果。

**完成条件：** 第 1.3 节整体完成条件全部满足；无未解释的新回归。真实供应商或创作质量未验必须明确，不能用模拟输出冒充真实创作成果。

### 8.2 四类必须先核实的疑点

1. 错误出口：用隔离数据触发不存在、损坏、权限和连接故障，检查有无操作上下文和下一步；不是所有底层错误都等于 JSON 问题。
2. 时间与实例摘要：核对实际值域、本地时区和不同来源；原本已中文的状态不重复改造，原始时间可查看。
3. 设置中的配置路径：按实际宿主返回的路径核实说明；保持凭证存储提示，不把未经验证的文案疑点当成落盘错误。
4. 内核传给部门的预算 JSON：先确认是否真的进入普通用户视图。纯机器输入保持结构，不为界面美化破坏模型事实。

用户主动打开的 JSON 文件、源码、终端、差异和原始导出保留原文。通信、持久化、比较及缓存里的 `JSON.stringify` 不属于 UI 改造范围。

## 9. 完整使用与故障验收

### 9.1 固定小说样例

使用隔离 PAO_HOME 和已有初始提交的 Git 创作项目，部门名单由夹具注册，不写死到产品。成果落第 3.3 节的普通目录，不能落入 `.pao/` 或被忽略的路径。首个样例包括：

| 步骤 | 工作与成果 | 验收责任 |
|---|---|---|
| 1 创作设定 | 设定、人物及边界文件 | 机械检查文件可读，审查内容满足本次约定 |
| 2 故事大纲 | 大纲文件，依赖步骤1 | 对应设定与结构要求，文件来自本步骤真实回执 |
| 3 首章初稿 | 初稿文件，依赖步骤2 | 有实际正文，按当前轮次保留，不能用预期路径冒充完成 |
| 4 审稿 | 审稿意见文件或实际审查记录，依赖步骤3 | 需要输出文件时它属于写任务，不能标只读；给出通过/修改及证据，必要时按已有审核回边退回步骤3 |
| 5 修订与交付确认 | 修订稿，依赖步骤4；设置人工确认门 | 机械通过后仍等待用户阅读并确认；意见未处理不冒充已修改 |

至少跑一次审稿要求修改的分支。旧稿、意见和修订稿均能回查，审核回边的次数上限沿现有规则；不扩展无限循环或自动认可小说质量。

验收必须看到实际正文/大纲变更进入真实 Git diff，并出现在隔离项目的本地交付提交中；只有文件能在侧栏打开不能证明执行、越界核查和交付闭环。没有有效 HEAD、成果被忽略或声明路径不符时，启动/交付应给出明确原因，不降级成假成功。

### 9.2 验收场景矩阵

| 场景 | 操作 | 必须观察到的结果 |
|---|---|---|
| 创建与确认分离 | 当前主控讨论出五步并调用创建工具 | 出现真实步骤卡，无新建临时按钮；未确认不派发，不自动入模板库 |
| 创建重放 | 丢失工具返回、重复通知、同请求重试 | 同一计划、同一版本，不生成第二份；不同请求的同名计划可并存 |
| 编辑/撤销 | 未启动修改部门、验收与依赖后撤销 | 卡片与详情一致；撤销保留依赖正确；发生外部修改则拒绝覆盖 |
| 失效确认 | 展示版本1后修改到版本2，再提交旧确认 | 拒绝启动，说明计划已变；版本2需要对应确认 |
| 确认可信性 | 模型自行传已确认；宿主确认等待期间切换会话/编辑计划 | 自报确认无效；回调后重核归属与版本，不能按旧确认启动；已受理后响应丢失只找回原实例 |
| 重复启动 | 两窗口/会话重复确认，受理后中断响应 | 只有一个关联实例和一次执行；重试找回原实例 |
| 部门异常 | 加载慢、空、损坏、已删除部门、大小写重复 | 分别提示；不偷偷换部门、不自动建部；无效项阻止启动 |
| 真实文件 | 从步骤卡和成果页打开同名不同目录文件 | 右栏显示正确正文和来源；选中步骤及发言对象不被打开动作改变 |
| 文件异常 | 删除/移动、无权限、过大、不支持格式、越界路径 | 有具体原因和可用操作；无页面直接读盘后门；非文件文字不出现打开按钮 |
| 新旧稿与意见 | 阅读旧稿时产生新稿，再提交旧稿意见 | 旧正文不被抢换；意见绑定旧版本；新稿可显式切换 |
| 零卡审核 | 只读节点只形成审查记录 | 不报“没有第一张卡”导致整步失败；有真实记录，无虚构文件 |
| 人工门 | 修订已交付但用户未确认；再确认两次 | 下游不擅自通过；首次真实成功后更新，重复请求不推进两次；过期轮次拒绝 |
| 审核退回 | 步骤4要求步骤3重做 | 展示目标/原因/新轮次，保留旧成果；真实受影响后续按内核规则处理，不全流程假归零 |
| 运行中修改 | 用户要求换部门或重排步骤 | 显示变更提议及未应用状态，不改冻结图；可走已有暂停/裁定或后续新计划，不假装本次已改 |
| 暂停与停止 | 暂停推进；另从原主控停止某张在途卡 | 暂停不冒充杀进程；停止有真实结果；卡片与记录口径一致 |
| 插话送达 | 忙碌部长接收补充意见，另触发拒收/超时 | 已受理模式与结果可见；失败不显示已送达，不让意见悄悄丢失 |
| 文件编辑 | 进入已有编辑器，改动未保存时切换 | 未保存保护与既有行为一致；预览模式不会写回 |
| 草稿和刷新 | 输入意见后切任务、选步骤、30秒进度更新 | 草稿按对象保留，选择/焦点/阅读位置不跳；有显式回到当前步骤入口 |
| 保存模板 | 未运行与已运行计划各保存一次；同名/失败重试 | 均只保存定义；冲突不覆盖，另存明确；失败内容保留，不把历史路径当通用输入 |
| 从模板再运行 | 选择已保存模板，换项目/输入后启动 | 新实例、新成果归属；不引用上次卡号、会话、绝对成果路径或完成状态 |
| 应用重开 | 关闭并重开测试应用 | 临时计划、来源会话与实例可找到，模板保存状态正确；不自动重新派发 |
| 崩溃与重启 | 在定义写入、启动关联、确认返回等窗口中断；重启测试机器 | 原件不被半写覆盖；状态可解释，重复请求可恢复；在途残留需明确恢复，不从卡猜完成 |
| 同名与越权 | 两项目/两主控创建同名任务，操作另一个身份 | 精确定位；错误会话/项目/轮次拒绝，不能按显示名猜 |
| 多卡与异常 | 23节点样例含多卡、长标题、未映射、坏卡 | 所有可读步骤可找到，错误不冒充空闲；汇总不漏卡，详情可达每张卡/轮次 |
| 并行边界 | 显式同组不同部门只读；再加入同部门/写任务 | 仅原定安全组合并行；全部前置和人工门仍有效；不靠视觉并排推断实际并发 |
| 全局统计/耗时 | 使用筛选与并行样例查看摘要 | 总量包含筛选外节点；缺时间明确未知；并行总耗时不能把重叠区间直接相加冒充实际历时 |
| 普通文案 | 打开预算、用量、工具详情、复盘、设置及错误 | 第8节项目达标；原始数据仍能主动查看；原本正确内容不破坏 |
| TUI一致性 | ConPTY钻取同名实例、损坏清单和交接页 | 与内核/桌面事实一致，问题可定位，正常任务不消失 |

## 10. 性能候选与进入条件

统一使用改前/改后至少三次测量，记录中位数、波动、文件读取/目录扫描次数与内存；同机同数据、区分冷启动和热读。夹具为模拟规模，不冒充生产测量。

| 候选 | 夹具和要测什么 | 何时改、改到什么边界 |
|---|---|---|
| 每节点完整预检 | 5/23/100节点，测相同环境和档位的重复读取 | 确认存在重复工作后只在一次预览内复用静态检查；各节点预算分别核，启动前权威预检不省略 |
| 执行日志增量前全项目扫描 | 23节点、100/500映射、跨多个1MiB日志段，测扫描次数与耗时 | 优先复用本次请求已核实的映射，或收窄单执行核验；不跳过项目、会话和路径身份检查 |
| 长期用量账本 | 固定小/大账本对比摘要耗时与解析量 | 达到明显影响交互的规模再做增量摘要；不得维护第二个费用真相 |
| 项目/revision刷新 | 多项目和密集结束事件，观察30秒重复读盘 | 合并重复刷新或按真实变化读取；不加无明确失效来源的常驻缓存 |
| 外链扫描/沙箱 | 多文件、符号链接及权限错误，测扫描与建立开销 | 只有能保证变更/链接失效条件完整才做缓存或增量；任何不确定仍阻止自动验收 |
| 大看板 | 100/500/1000卡测首次呈现、滚动、选择和拖放 | 真有瓶颈才做分段/窗口化，保留键盘、拖放占位、搜索和统计完整性 |
| Worker按角色加载 | 同样环境多次冷启动，测耗时和内存 | 真有收益再缩小加载；必须扩展、工具和隔离检查不能丢 |

性能改动的最低进入条件：确有可重复的重复工作或用户可见延迟，且已有实现不能直接避免。保留改动须证明目标重复工作减少、行为一致；纯耗时收益若小于测量波动，不作为保留复杂实现的理由。无收益的候选登记“已测，保留原实现”即完成该项决策。
