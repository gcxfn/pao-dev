# 地图、简报与部门并行协作修复任务书

编制日期：2026-10-20（Asia/Shanghai）。依据：用户关于主控、部门、地图、任务简报、主控自主使用 worktree 的明确要求，以及本轮“把这些修复工作做一个任务书”的指令。

本轮交付范围为编制任务书，不启动产品实现、真实模型调用或对比实验。后续实施范围、批次状态和验收入口统一维护在[执行总册 §10.11](2026-10-17-Harness完善与工作台迭代执行计划.md#1011-2026-10-20-地图简报与部门并行协作)，本文维护需求、分工和验收标准。

## 1. 目标与成功条件

补齐从用户需求到侦察地图、规划、任务简报、部门执行、成果整合和独立审核的协作链路，解决以下问题：

1. 主控与各执行会话上下文膨胀。
2. 多个部门重复调查同一批材料。
3. 并行任务依赖、修改范围与责任不清。
4. 地图过期却仍被用于派发。
5. 简报遗漏开工所需的信息。
6. 部门对接口及其变化理解不一致。
7. 并行成果缺少整合、冲突处理和集成验证。
8. 回执与实际变更、验证证据对不上。

成功标准：中大任务中，主控能依靠用户对话、必要摘要、状态和异常完成协调；执行者拿到简报后无需重新寻找任务背景；各部门按明确边界工作；整合后的成果通过对应验证。随后用真实任务比较交付质量、总费用、耗时、人工介入和返工，不能用主控上下文变小代替整体收益。

## 2. 范围、职责与原有定案

### 2.1 按任务需要启用流程

| 情况 | 默认方式 | 需要避免的问题 |
|---|---|---|
| 明确、独立的小任务 | 单卡直接派执行者，完成修改和必要验证 | 不强制增加侦察、规划和部长调用 |
| 需要了解现状的中任务 | 侦察给地图和结论，按需要规划后派执行 | 接收方不从头重复调查 |
| 跨模块、可独立并行的大任务 | 侦察／必要研究、规划、并行实施、整合与审核 | 先确定契约和依赖，再同时写代码 |
| 风险较高的变更 | 在对应流程增加独立审核 | 执行者自报通过不能替代审核 |

保留主控、部长、worker 的已有职责；不要求每个部门每次都启动部长，不新增一层管理角色。侦察、规划、实施、前端、审核是能力与责任的示例，不自动创建这些部门或覆盖现有人设。部门内部可按自己的规则分工，但 worker 不递归派发。

### 2.2 主控与部门的分工

- 主控：理解用户目标和约束，选择流程与部门，审定计划，处理优先级、权限、预算和需求变更等裁决，接收结果。中大任务的技术调查、详细方案、技术整合与深度审查交给对应任务。
- 侦察：调查项目现状，提供地图、事实依据、限制、风险和未知项。外部研究按实际需要单独安排。
- 规划：综合已有调查，确定方案、接口、任务切片、依赖、整合负责人及验收要求。
- 执行部门：按任务简报开展局部阅读、修改和验证；必要内部并行由部长负责。
- 整合负责人：由已有部门或任务承担，逐项接纳成果、解决冲突、运行集成验证；不设常驻新角色。
- 审核：核对实际变更和真实证据，给出结论与问题，不只阅读执行者总结。

主控可以自主判断、创建和管理本任务需要的 worktree（Git 的独立工作目录），再派部门并行；授权任务范围内的普通创建和派发不逐次向用户确认。发布、外发、扩大权限、难以撤销的操作仍按项目已有授权边界处理。

### 2.3 信息交接的解释

[架构 §5](../v2-ARCHITECTURE.md#5-双重理解成本的解法)已有地图、局部切片与调查摊销；[§8.7](../v2-ARCHITECTURE.md#87-接口契约制度打底流程分层)已有分级流程与规划整合职责。本任务补齐它们的可执行交接和验证。

“传指针，不搬内容”具体按以下方式执行：必要结论、任务要求和本任务相关契约随简报交接；完整原文、日志和大型成果留在原处，附精确证据入口。简报不是文件路径清单，也不是上游全部内容的副本。下游默认无需遍历上游材料，必要时定点核对。

worker 需要读取将修改的真实代码和相关规则；审核需要读取变更与证据。限制的是重复寻找背景、全景扫描和无关材料读取，不承诺所有文件只读一次。已有禁止越界读取的提示需同时允许任务范围内必要的依赖核查；发现范围外的实质缺口时退回补充。

部门之间结果可由系统路由；主控保留全局依赖和裁决视角，不人工复述上游全文，不为规则已覆盖的每次交接增加一次模型审批。不另建绕过现有归属、配额和状态管理的部门通信系统。

### 2.4 不包含的工作

- 部门设置页、增加部门数量、部门改名／删除，以及通用组织管理平台。
- 通用删除／回收站、编码转换保护、保存点恢复及保存点空间预算；这些仍见[已有讨论稿](2026-10-20-部门设置与执行保护讨论稿.md)。worktree 本身的占用、活动引用及清理属于本任务生命周期范围。
- 重写模型运行循环、会话、知识库、预算账本、工作流状态机、Git 快照引擎或通用消息框架。
- 正式 PAO_HOME 迁移、历史批量改写、安装替换、远端推送或发布。
- 以强制降低模型、跳过必要审核、删除失败证据或只统计主控用量来制造节省。

## 4. 修复要求

### 4.1 按角色装配上下文

1. 主控默认接收需求、计划摘要、状态、异常和验收结论，不自动注入源码全文、部门完整会话或长日志。
2. 规划者收到必要的调查结论；worker 收到自己的执行简报；审核者收到验收要求、变更摘要和证据入口。禁止把整段主对话复制给所有接收方。
3. 正常派发由程序从已保存的任务定义和上游有效交接成果装配最小输入，不要求主控先读全文再转述。简报正文直接进入接收方本次输入，任务卡和证据路径用于追溯／定点补查；不能仍只发送“先读卡和若干报告”。执行期间任务定义不可被后来编辑静默替换；变更沿现有版本／轮次机制处理，旧尝试仍绑定原输入。
4. 工具结果按任务返回必要片段、失败原因和完整证据位置。截断必须明确，不能截掉失败后返回成功；长内容按段读取。
5. 角色工具与技能按现有装载机制收窄；记录实际发送的工具说明规模，不以静态工具总数推断每次 token 消耗。
6. 自动召回按内容身份、当前上下文是否仍含该内容去重，并有正文总量边界；压缩、切换、恢复或事实被纠正后重新判断，不能用永久“已见”标记导致必要事实消失。只处理本链路相关的真实重复，不新建记忆系统。
7. 使用现有压缩与交接机制保留目标、决定、未完成项、版本和证据入口；通过事件唤醒接收结果，不忙等或轮询模型。

### 4.2 地图复用与失效处理

地图至少包括：适用项目／仓库、代码基线及相关未提交状态、调查范围、关键文件／调用关系、限制和风险、已确认事实、未知项、证据定位和更新时间。

- 版本核对同时考虑提交后的变化、未提交修改、相关未跟踪文件，以及会影响结论的配置／接口；不能只比较 HEAD 或文件时间。具体比较方式优先复用已有文件版本与 Git 差异能力。
- 地图声明覆盖边界，不能只用“记录过的几个文件未变化”推断整个结论有效；新增调用方、依赖及公共接口变化也需判断。无法确定影响面时标为需复核，交给有范围的侦察。
- 派前判断：无关变更继续复用；影响局部结论时更新相关部分；核心依赖或范围改变时先补调查。实际启动前再次核对；运行中发现失效须报告并按影响暂停相关任务。
- 更新留存来源和替代关系，通知受影响的待执行／在执行任务，保留旧尝试的地图版本。无关任务可继续，避免一个模块变化导致全项目重新侦察。
- 地图是任务产物，不承担任务状态；不默认全库扫描、不为每个文件永久建立一套新索引。

### 4.3 足够开工的简报与补充通道

| 必需信息 | 要求 |
|---|---|
| 任务身份与目标 | 关联真实卡、尝试／轮次、owner、项目和成果；目标可判断完成 |
| 范围与限制 | 允许修改的模块／文件、明确不做的内容、环境及适用规则 |
| 已确认结论 | 侦察／规划给出的必要事实和决定；未知项单列，不能变成默认事实 |
| 接口和依赖 | 本任务使用的接口版本、输入／输出、前置成果与并行关系 |
| 验收 | 每项成果对应可检查条件；注明需要真实集成验证的部分 |
| 证据与定位 | 必要片段、路径与函数／章节、读取目的；材料可访问 |
| 执行及整合位置 | 实际工作目录／工作树、基线、交付去向及整合责任 |

程序核对缺字段、坏引用、身份不符、失效版本及前置未就绪；不能机械保证语义没有遗漏。接收方在已有接任务／规划轮次中检查是否足以开工，不强制增加一轮模型“同意”。

缺口分开处理：可由任务范围内局部核查解决的直接核查；影响目标、接口或范围的，明确返回缺什么、影响什么、希望谁补充。沿现有 `missing_input`、`blocked`、`checkpoint`、协作和回流机制处理，不新增卡状态、不伪装为瞬时故障无限重试。已有明确事实直接复用，不让用户重复回答。

验收“足够开工”时，先为场景列出上游已知、完成本任务必需的事实与决定，逐项检查简报是否携带。接收方能据此开始目标代码的定位／修改／验证，不需先打开上游整份报告、全目录搜索任务背景或追问已知答案。针对目标代码、必要调用方和证据的局部核查不算重复调查；执行中首次发现的新问题可以正常回流，不能以“全过程零追问”作为通过条件。

### 4.4 接口唯一来源与变更传播

1. 复用项目已有类型、协议、接口文档和测试作为契约正本，指定维护责任；没有现成契约时只补本次协作必需部分。
2. 简报携带本任务相关的参数、字段、错误语义等必要摘要，并指向精确版本。各部门不能各存一份互不关联的接口“正本”。
3. 并行前按风险采用类型检查、契约测试或实际调用核对；不把自然语言“理解一致”当作兼容证明，也不要求所有接口另造 schema。
4. 修改契约必须记录原因、影响任务和新版本；派前拒绝已知冲突的旧简报。运行中通知相关任务重新确认，不能默默适配或改写旧执行输入。
5. 审核按交付时实际契约核对。若方案错漏涉及重拆，由规划修订，主控只处理需要用户意图／优先级裁决的部分。

### 4.5 主控自主 worktree 与并行调度

1. 主控工具面能发现创建、查询、绑定派发及结束处理能力，说明适用情况和限制；普通小改不默认创建工作树。
2. 保留同一任务／工作流状态归属，单独关联实际执行目录。当前从 `cardsDir` 推导 `cwd` 的行为需调整相关边界，不能靠复制卡目录让每个工作树各有一份任务状态。
3. 复用宿主工作树管理，校验同仓库、应用登记、任务归属、真实路径和工作树身份；模型不能通过任意路径参数让执行落到不相关目录。共享内核使用窄宿主接口；CLI 与桌面共用业务契约，缺宿主能力时明确说明，不能静默在主目录并行写。
4. 明确创建基线。主目录未提交内容不自动出现在新 worktree；任务依赖这些内容时先用不破坏原件的方式建立已知基线，无法确认则报告缺口。基线采用可恢复的实际内容快照，关联源仓库、HEAD、纳入／排除文件清单和内容摘要；内容摘要用于核对工作树及测试是否对应同一输入，不能代替可恢复内容。优先复用已有 Git 对象／文件版本能力，二进制及相关未跟踪文件按实际内容保存，捕获前后发现变化则重核；未保护范围明确列出。不得暗中 stash、reset 或混入用户无关修改。
5. 共享任务状态、认领、预算与限额用现有共同短锁／原子更新保护；代码写互斥按实际执行目录区分。取得锁和实际启动前核对同一输入版本；不同 worktree 不应被整项目长锁无意串行化，同一目录仍需互斥。
6. 沿用现有部门并发、共享名额、父子预算、依赖和取消机制，不另建并发配置系统；前置未满足时不得启动，重复请求不重复建树或重复派发。
7. 运行进程、卡、回执和工作树关联可追溯。取消时确认执行停止后才释放写保护；停止未确认的工作树保持占用，崩溃／重开只读盘点，不自动清锁、重跑或删除。
8. 清理只处理本任务管理的工作树，先确认无活动执行且成果已提交保留、合入或明确放弃；不强删、不自动删分支、不删除用户工作树。失败和冲突目录保留。盘点包括工作目录、依赖和构建产物占用，不能把共享 Git 对象等同于零额外空间。

生命周期只覆盖三条主路径：正常结束后按条件清理；异常时保留成果并只读盘点；由有权操作者决定后续保留或清理。A 批逐项列出现有登记／请求身份能直接提供什么、实际缺什么；只补关联和拒绝不安全操作所需部分，不新增自动恢复执行、后台清扫服务或空间调度系统。重复请求沿现有稳定请求身份查回，不能以“已有幂等框架”为未经核实的实现假设。

### 4.6 整合、冲突与证据审核

- 并行开工前指定整合任务、顺序和目标基线。复用现有 owner／受控交付能力管理任务分支，不授予 worker 任意 Git 写权限，不自动提交开发仓既有改动或推送远端。
- 优先在受管理的整合工作树逐项接纳成果；整合目标若被外部修改，先复核，不能覆盖用户当前工作区。既有交卷逐路径提交和基线差异核对需适配实际执行根，避免在主目录提交 worker 工作树之外的文件。
- 文本冲突和语义冲突分别处理：Git 无冲突只说明文本能合并；仍需类型／契约／集成检查。冲突列明文件和原因，交对应任务处理，不自动选 ours/theirs 掩盖问题。
- 每次整合保留输入成果、源版本、结果版本和检查结果。重复提交整合请求应能查回结果，不重复应用同一成果；中断后保留已完成结果与待办，不假报整体完成。
- 证据对应任务、尝试／轮次、实际代码版本／未提交状态、工作目录、命令、退出结果和完整日志位置。测试后又改代码，原测试不能证明新版本通过。
- 审核核对实际差异、声明修改范围、成果存在性与对应证据；worker 自报 `pass` 不直接放行。缺文件、缺退出结果、版本不符、失败及未运行明确区分，禁止填零、推断通过或伪造证据。
- 单项通过、整合通过、独立审核通过和用户要求的确认沿现有语义分开；下游只由满足前置的真实结果解锁。主控收到短结论和必要异常，详细证据留可核对入口。

## 5. 实施批次与协作分工

产品实现和对应测试优先由子代理承担，主对话负责理解需求、拆分、整合及独立验收。分工以边界为准，不能同时修改共享派发核心或卡协议；同一组文件的定位、修改和验证由同一执行者连续完成。

| 批次 | 工作 | 前置及交付 |
|---|---|---|
| A 现状与基线 | 查调用图／现有能力与差异；固定身份和最小交接契约；保留当前可复现版本与运行方式 | 实现前完成；给问题—入口—修复—验收覆盖表。不能只留 HEAD 而遗漏当前未提交改动 |
| B 地图与简报 | 角色输入装配、有效性核对、补充回流、压缩／召回相关重复 | A；用已有卡及工作流验证，不只测字符串模板 |
| C 接口与依赖 | 关联契约版本、变更影响、受影响任务处理和派前复核 | A，交接约定与 B 对齐；不同文件可并行，公共入口单人整合 |
| D 工作树执行 | 主控能力、任务根／执行根、锁、配额、取消和生命周期 | B/C 契约明确后；独立工作树真实并行、同目录互斥，单卡／扇出／工作流共用入口 |
| E 整合与审核 | 受控交付适配、冲突回流、集成验证、证据版本关联 | D；覆盖重复请求、中断及旧证据误用 |
| F 全链与对比 | 真实工具／进程集成，必要宿主验收，随后真实任务对照 | B–E 关键保护通过；工程结果与真实模型效果分别报告 |

A 固定的是基线与证据，不为保留基线自动提交、reset、创建额外产品分支或运行付费实验。实现时按用户给出的实施授权执行必要操作；外部付费调用与发布遵守既有授权边界。

## 6. 验收矩阵

| 编号 | 场景 | 必须观察到的结果 |
|---|---|---|
| V01 | 上游包含长原文／日志，连续多次派发 | 主控及无关 worker 请求不自动包含全文；各接收方有足够开工信息，原件仍可定位 |
| V02 | 同一范围被多个任务使用 | 复用同一有效地图；读取切片有明确目的，不重复全景扫描；用实际读取轨迹判断 |
| V03 | 相关文件、未提交内容、未跟踪文件或公共接口变化 | 识别受影响地图／简报并补核；新旧地图来源与替代关系可追溯，相关任务使用更新版；无关变更不触发全图重建；无法判定时明确需复核 |
| V04 | 校验后、启动前修改输入或代码 | 启动前重核能拦截不一致；已启动尝试的原输入不被后续编辑替换，并可按该尝试取回当时的简报、地图和契约引用 |
| V05 | 缺接口字段、目标歧义、坏路径／越权引用 | 已知缺字段或身份错误被程序拒绝；语义缺口可退回补充，不无限重试、不让用户重复已答内容 |
| V06 | 简报自足，证据需要定点核验 | 对照预先列出的上游已知必需事实检查无遗漏；启动输入直接含简报正文，无需先读卡／多份报告拼任务；局部代码／证据核验允许，新发现问题能回流 |
| V07 | 两部门用到不同接口版本，运行中升版 | 不按已知冲突版本继续派发；相关任务收到影响与补充，旧尝试、旧证据保留 |
| V08 | 主控实际调用工作树能力并派发两个独立写任务 | 真正落在不同执行目录；共享卡／预算无重复丢失；两进程执行时间有重叠证据 |
| V09 | 同目录双写、依赖未就绪、超并发／预算 | 正确互斥或拒绝；不能为得到并行结果移除共享状态保护 |
| V10 | 主目录已有未提交／未跟踪修改，任务引用其中内容 | 创建基线和实际输入一致；用户原改动不被 stash、覆盖或误提交 |
| V11 | 取消、停止未确认、崩溃和重开 | 先停后放锁；不自动清理活动树／清锁重跑，已有成果和证据可盘点 |
| V12 | 重复建树／派发／整合请求，途中丢返回 | 可查回原受理和已完成结果，不重复创建、执行或合入 |
| V13 | 两项局部检查通过，但整合后不兼容 | 集成检查检出；不得把局部通过升级为整体通过 |
| V14 | 文本冲突及无文本冲突的语义冲突 | 指定负责人处理，记录原因和新结果；不静默覆盖，修后重验受影响范围 |
| V15 | 回执漏报改动、日志缺失、退出失败、代码晚于测试 | 实际差异和证据核对阻止误放行；未运行／未知／失败如实显示 |
| V16 | 自动召回重复，随后压缩、纠正、切换或恢复 | 不重复膨胀，也不丢仍需要的事实；纠正后不复活旧事实，跨任务不串入记忆 |
| V17 | 旧卡、v1/v2 工作流、单卡、扇出、CLI／桌面 | 保持支持行为，不能借新格式绕过 owner／轮次／人工门；缺能力明确报告 |
| V18 | 清理工作树时有运行任务／未保留改动／外部目录 | 拒绝不安全清理，保留成果；正常结束路径能释放本任务资源 |

先做有意义的定向测试和类型／边界检查，再做真实文件、Git、工作树和子进程集成。工具替身或模拟模型事件只能证明工程链路；不能证明地图理解、简报语义充分、真实协作质量或 token 收益。

涉及桌面宿主能力时必须有真实 Electron 关键链路验证；若改变内嵌契约或发行内容，按影响验证实际解包发行物。复用各仓当前脚本，不照抄旧文档中的包管理命令。缺环境、真实模型、系统操作或发行验证必须明确列为未验，不替换成模拟结论。

## 7. 对比实验与继续投入的判断

### 7.1 三种配置与公平边界

- 单代理：同一基座和模型档位的单代理连续完成任务，保留正常项目规则／技能及验收，不人为削弱。
- 修复前 PAO：A 批保存的可复现版本及运行配置；记录当前实际流程和缺口，不假设地图／简报已生效。
- 修复后 PAO：按任务需要使用有效地图、任务简报和部门协作；不是每项都走完整流程。

先保存修复前基线，修复后在同一结果表分别列三种配置，区分修复收益与相对单代理的收益。修复前不可运行的场景记失败／不可运行和原因，不伪造结果，也不把后续修复倒填进基线。

共同环境及底层能力一致：模型／档位、项目规则、代码读取与编辑、shell、测试工具和可用依赖。单代理可使用原生 Git／worktree，不人为禁止合理工作方式。PAO 特有的地图／简报装配、部门调度和工作树管理属于被测变量，不能要求基础组使用同一编排，也不能因此额外给予 PAO 更强模型或不同验收标准。

首轮选择至少三项 PAO 以外的代表任务：明确小修改、需要调查的中等任务、可并行的跨模块任务。每组从一致的独立代码／输入快照开始，使用同一验收标准；不能重复在上一组已改好的目录开工。首次调查和同类后续任务分别记录，以判断地图复用收益。

模型、思考档位、工具、依赖环境、人工介入规则及缓存情况保持可比；若同时比较降档策略，单独列出，不把路由降价混称交接机制节省。小样本用于发现问题和决定下一步，不宣称统计上证明所有任务有效。

### 7.2 统计口径

| 指标 | 口径 |
|---|---|
| 质量与完成率 | 同一验收标准，包含集成结果和已知偏差 |
| 总费用／用量 | 主控、侦察、规划、所有部门／worker、审核、重试、压缩及相关辅助调用；真实请求只计一次 |
| 完成时间 | 从任务开始到合格交付；等待、返工及整合耗时均计入 |
| 人工介入 | 补充信息、纠正、冲突裁决和恢复次数及原因 |
| 重复调查 | 结合实际工具读取／搜索轨迹，区分重复全景扫描与必要局部核验 |
| 上下文与维护 | 各角色输入规模、压缩／重复注入、失败和恢复；本轮工程投入另列，不混成运行费用 |

缓存读写单列，原生费用未知就标未知；不将缓存 token 当免费，也不把父项汇总与子项再次相加。读取字节数不能直接冒充精确 token，日志压缩率不能作为 token 节省率。以已有会话、用量和证据产物汇总，不为首轮实验新建监控平台。

质量／授权边界退化的结果不能因便宜判为成功。其余指标存在取舍时如实呈现：若只对复杂任务有收益，则限制适用范围；若主要增加交接、返工或费用，则简化对应阶段。首轮无明确优势时停止扩建并给出原因，不预设节省百分比或把未证实结论写成成果。
