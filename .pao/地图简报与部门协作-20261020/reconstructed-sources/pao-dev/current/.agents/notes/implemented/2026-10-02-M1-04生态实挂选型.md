# M1-04 生态实挂选型：rpiv-todo、codebase-memory MCP、skills 目录（2026-10-02）

## 定案

- **todo 包**：装 `@juicesharp/rpiv-todo@2.12.0`（MIT，作者 juicesharp，仓库 rpiv-mono，npm 名不变），走 pi 官方包路径 `pao install npm:...`，落用户级 `~/.pi/agent/settings.json`。只装这一个包。边界：todo 只管单会话执行步骤，跨会话任务唯一真相＝卡片；回归测试 `test/pao/todo-boundary.test.ts` 固化（注册面盘点＋包内不落盘＋卡目录无旁路）。
- **真实 MCP**：codebase-memory-mcp（本机 0.11.0，`C:/Users/ASUS/.local/bin/codebase-memory-mcp.exe`）以 stdio 挂**用户级** `~/.pi/agent/mcp.json`，env `CBM_CACHE_DIR=D:\cbm-cache`，无鉴权。另一候选 mnemosyne 留"未验证"（属 M2 记忆供应商接入，不与 M1-04 混做）。
- **skills**：pi 原生 skills 机制，pao 的 skills 正本住 `pao配置/skills/`，经用户级 settings 的 `skills` 字段（绝对路径）挂入；只移植两件高频（commit、codebase-memory），不整包灌。
- **worker 角色隔离**：`PAO_ROLE=worker` 环境变量门控，扩展注册层跳过派发/全库管理/自动推进/后台管理/主控诊断类模块（`src/pao/role.ts` WORKER_SKIPPED_MODULES）；WorkerRunner 拉起子进程时强制注入该变量（`src/pao/worker/runner.ts`），主控忘设也不会漏。清单与代码锚点成文于 `pao配置/装载清单.md`（R10 正本）。

## 为什么

- rpiv-todo 是 pi 官方包生态里的成熟 todo 件（overlay 活面板、/reload 与 compaction 后由对话重放重建），**状态不落盘、天然单会话**，与"卡片是跨会话唯一真相"边界零摩擦；自写一套 todo 违背复用优先。
- MCP 选 codebase-memory 而非先挂 mnemosyne：M1-04 要的是"一个真实 MCP 连接并调用，首选已存在且日常需要的能力"——代码图是本项目工作规则第 9 条的日常依赖且本机已装、无密钥、零成本；mnemosyne 属 M1-05/M2 记忆供应商接口的事。
- 用户级挂 MCP：代码图跨项目使用、缓存按项目分库在全局盘；项目级 `.pi/mcp.json` 只在受信项目生效，覆盖不了 pao 会话开在任意目标项目的形态；该配置无密钥，用户级无泄露面。
- skills 走 settings `skills` 字段而非搬进 `~/.pi/agent/skills/`：pao 配置的正本按公约住 `pao配置/`，用户级目录只放指针，不散落副本。
- worker 隔离用环境变量而非官方 per-role 机制：pi 无内建角色概念；G1-12 要求"扩展注册面直接+间接入口都查"，注册层跳过是唯一能同时掐掉工具与事件钩子的位置，`--tools` 白名单只遮蔽模型可见性、遮不住钩子。

## 被否方案

- **项目级 `.pi/mcp.json` 放 PAO 仓库**：只在 PAO 仓库内受信生效，日常目标项目用不上；且会把运行配置混进源码仓库。
- **worker 隔离只靠 `--tools` 白名单**：遮得住工具声明，遮不住事件钩子（如巡检落卡）与命令注册；不满足"检查间接入口"。
- **把 `~/.agents/skills/` 下 ZCode/Orca 件（computer-use、orca-cli 等）整包搬进 pao**：工具名/权限前提不成立（强绑 ZCode 工具与桌面环境），违背"依赖前提真实存在才移植"。
- **todo 状态做跨会话持久化或接卡片**：制造第二任务真相，直接违反 G1-12；rpiv-todo 的对话重放模型恰好不需要。
