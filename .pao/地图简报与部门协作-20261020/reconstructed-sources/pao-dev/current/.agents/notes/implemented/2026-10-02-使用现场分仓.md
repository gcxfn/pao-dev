## 为什么

PAO_HOME 的定位长期没对齐：外层 `workspace/pao` 混装「开发项目的产物」（plans 定案、fork、摩擦日志）与「pao 使用现场的运行时数据」（部门库、pao配置、体检）。旧结构下靠会话 cwd 碰巧落在 pao 根才工作，分仓后立刻暴露两处真实缺陷（见下）。用户定案：**外面的 pao 是开发它的项目，使用现场必须独立**。

## 定案结构

| 使用现场（PAO_HOME） | `D:\AI\workspace\pao\` | 部门/、pao配置/、.pao/体检/——独立 git 仓库，首提交 `f4cbab3` |

- 两仓并列不嵌套；`pao配置/skills` 在 `~/.pi/agent/settings.json` 的注册路径因使用现场沿用 pao 路径而继续有效。

## 分仓暴露并同日修掉的两处缺陷

1. **知识库工具让模型拼绝对路径**：`pao_查库/入库/巡检` 的「知识库路径」是必填参数，模型只能从 cwd 猜——旧结构猜对、新结构必猜错，且错了静默报「无命中」。修复：新增可选 `部门` 参数（工具从 PAO_HOME 解析 `$PAO_HOME/部门/<部门>/知识库`），路径不存在时 isError 明说并带 PAO_HOME 当前值；`知识库路径` 降级为显式覆盖用。真跑验证：部门=平台评测、查询=GLM 命中 4 条。
2. **测试用「向上五级＝工作区根」定位配置**：loadout-tiers-config / skills-loadout 两测试假设测试文件向上五级是含 pao配置 的根。改为向上六级到 workspace 再进 pao（使用现场）。

## 教训（NTFS 大小写不敏感）

同父目录下 `pao` 与 `PAO` 是**同一个目录**——分仓搬迁第一步因此把使用现场目录建进了 fork 工作树内，返工。规则：本仓内禁建小写 `pao/` 子目录；搬迁用「移子目录」而非「改名父目录」（会话 cwd 锁父目录会 Device or resource busy）。另：npm workspace 链接是绝对路径符号链接，整目录搬家后全断，进 fork 跑一次 `npm install` 重建即可。

## 被否方案

- **使用现场并入开发仓（单仓）**：混合两种变更节奏（代码迭代 vs 运行时数据积累），diff 噪声大、备份策略难分；否。
- **改名 fork 目录避开大小写碰撞（`workspace/pao/本体`）**：治标不治本，垫片/文档全要跟着改一遍且语义更绕；用户改为改开发仓名（pao-dev）——治本。
