## 二、件一：agent-session 单飞旗前检查

### 修法与落点

`PAO/packages/coding-agent/src/core/agent-session.ts` `_runAgentPrompt`（现 :1776 起）入口、`_agentRunAbortRequested = false`（现 :1785）之前新增：

```ts
// Single-flight pre-check, thrown before the try block: a concurrent prompt that
// slipped past prompt()'s isStreaming check during the pre-flight window must fail
// cleanly instead of reaching agent.prompt() and settling early from this method's
// finally while the real run is still active.
if (this._isAgentRunActive) {
    throw new Error(
        "Agent is already processing. Specify streamingBehavior ('steer' or 'followUp') to queue the message.",
    );
}
```

- 抛点在 try 块（现 :1794）之前：输家不经过 finally（:1806-1813），不再提前 `_emitAgentSettled`（:1060，清旗 :1062）、不再双发 `agent_settled`、不再把 `_isAgentRunActive` 清零造成 idle↔running 摆动。
- 错误文案与 `prompt()` 既有 isStreaming 闸（:1976-1980）逐字一致，宿主侧无需区分。
- 置位检查到置位（:1781→:1793）之间全同步无 await，JS 单线程下检查即闸，无 TOCTOU。
- 调用面核实：`_runAgentPrompt` 仅 3 个调用点（:2073 `prompt()`、:2279/:2283 appendCustomMessage 直发道），后者的直发道本就以 `isStreaming` 为前置判据，旗前检查只在其竞态滑窗时触发，不改变正常路径。
- 低层 `agent.prompt()` 的 `activeRun` 单飞闸（`packages/agent/src/agent.ts:374-378`）保留为兜底，未动。
- 影响面：CLI/RPC 等一切直用 `AgentSession.prompt()` 的宿主同时受益（报告 §三·伴随项原意）；桌面主修（driver 排队道）仍是独立道次，本包不涉及。

### TDD 红测（报告 §四·缺口 2 的内核级确定性测试）

新增 `PAO/packages/coding-agent/test/agent-session-single-flight.test.ts`（1 例）：

- 窗口构造：扩展 `before_agent_start` 处理器对 `prompt === "First"` 睡 50ms。该钩子在 `prompt()` 的 isStreaming 检查（:1976）之后、`_runAgentPrompt` 置位之前——第二条 prompt 在此窗内通过 isStreaming 检查并先入 `_runAgentPrompt` 占住低层 activeRun，第一条随后带旗闯入。此构造为全微任务级确定性，无拍速依赖。
- 断言四连：输家以会话层文案拒绝；输家拒绝时 `agent_settled` 计数为 0；`isStreaming` 仍为 true；赢家放行落定后全程恰 1 次 `agent_settled`。
- 说明：报告原文写「慢 input 处理器」，实测推演 input 慢钩（isStreaming 检查之前）只能造出「后来者被既有 ：1976 闸拒绝」的绿路径，造不出双入 `_runAgentPrompt`；重叠窗的唯一确定性入口是检查后钩子，故用 `before_agent_start`。红测实测红（见下），证实窗构造正确。

## 三、件二：migration-migrate.test.ts 类型错

### 修法与依据（二选一之「改测试」）

`MigrationPlan` 是判别联合（`src/pao/migration/migrate.ts:122-124`）：`{ status: "ok"; content; changes } | { status: "conflict"; reason }`。`reason` 只在 conflict 变体上存在——这是联合类型的本意，实现侧（含 `runCardMigration` :355 收窄后取 `plan.reason`）形状正确，**不应为了测试断言方便给 ok 变体补 reason 字段**。故选「优先改测试断言取值路径」：三处两行断言合并为一行整对象断言，`toEqual` + `expect.stringContaining` 非对称匹配器同时钉住 status 与 reason 取值路径，类型与断言语义双收：

- `test/pao/migration-migrate.test.ts:241`：`expect(plan).toEqual({ status: "conflict", reason: expect.stringContaining("随便键") })`
- `:250`：同式，`重复终结留档`
- `:264`：同式，`吨位`
