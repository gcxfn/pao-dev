## ③ 停止链边界 L2（S1 放行遗留，二选一决策输入）

### 问题原文定位与机制

位置：`PAO/packages/coding-agent/src/core/tools/bash.ts:126-181`（createLocalShellOperations.exec 内）＋ `worker/kill.ts:123-145`。

```
bash.ts:128  let stopError: unknown;
bash.ts:134-145 onAbort = () => { ... stopping = killTree(child.pid, 2000, createdBefore).then(
               () => {}, (error) => { stopError = error; rejectStop(error); }) ... }
bash.ts:165  const exitCode = await Promise.race([waitForChildProcess(child), stopFailed]);
bash.ts:166  await stopping;
bash.ts:167  if (stopError) throw stopError;        ← 先判停止错误
bash.ts:168  if (signal?.aborted) { throw new Error("aborted"); }  ← 后判取消
bash.ts:393-395  if (err instanceof Error && err.message === "aborted") → 渲染 "Command aborted"
```

机制：用户取消（abort）时 Windows 走 `killTree`（bash.ts:137），该函数是两跳 PowerShell 严格树杀，**预算封顶「首跳 60s＋间隔 0.5s＋二跳 30s ≈ 90.5s」（kill.ts:132 注释原文；跳超时硬编码 kill.ts:137 `60000 : 30000`）**。bash 工具的返回必须先 `await stopping` 等树杀链走完，所以：

1. **abort 时延**：即便目标 shell 已退出（race 由 waitForChildProcess 赢），仍要等 killTree 的收尾确认；WMI/进程表枚举慢的机器上首跳即可耗 60s，最坏 90.5s 后用户才拿到取消返回。
2. **先判顺序**：若树杀失败（killTree reject→stopFailed reject，或 race 后 `await stopping` 完成但 stopError 有值），抛出的是 killTree 的错误文本而非 `"aborted"`；调用方 :393 用 `err.message === "aborted"` **精确匹配**，于是「用户取消」被归类为普通命令错误——错误分类、UI 语义（Command aborted）、上层取消逻辑全部丢失。反过来，若简单对调两行先抛 `"aborted"`，则会吞掉「树未杀干净」的停止失败事实，与 S1 确立的「停止证明后才算停」冲突。POSIX 分支不受影响（onAbort 走同步 killProcessTree，bash.ts:144）。

### 两个选项的具体改法与代价

**选项一：先判顺序调整（语义修复）**
改法：:165-170 重排为 `signal?.aborted` 先判；stopError 不吞——abort 时抛出的消息保留停止失败详情（如 `aborted (stop confirmation failed: <stopError>)`），并同步把 :393 的精确匹配改为 `startsWith("aborted")`（或单独判取消标记），stopError 细节另 console.warn。改动面＝bash.ts 本地约 5 行＋一处判定。
代价：不缩短 90.5s 最坏时延（只是语义变对）；需要小心保住「停止确认失败可见」不违反先停后放锁纪律；`message === "aborted"` 是 pi 上游调用面通用约定（本文件 :393 与其他消费者），改匹配方式要核全部消费点。

**选项二：abort 时延收窄（预算收窄）**
改法：给 killTree 增加可配置两跳预算（现签名 `(pid, graceMs=2000, createdBefore)`，Windows 跳超时硬编码），bash 工具的 abort 路径传短预算（如首跳 15s＋二跳 10s），worker 停止链/StopProof 保持 60/30 不变；或 bash 在「进程已退出且 signal.aborted」时不等收尾确认直接返回 aborted，收尾检查转后台 warn。
代价：改 kill.ts 公共函数（被 worker 停止链、StopProof、多测试共用，回归面大）；Windows 高负载下短预算更易触发「停止失败」报错（宁报错不假报，用户取消时见错误比等 90.5s 优，但 P0 语义上树残余风险升高）；仍需叠加选项一的顺序调整才能修复语义——单独做选项二不完备。

### 本调查倾向

**选项一（先判顺序调整）为主**。理由：(a) stopError 顺序是错误分类正确性问题，会导致上层把用户取消当命令失败处理（可触发错误恢复路径），危害确定且常触发；90.5s 最坏时延仅在高负载 WMI 慢时出现，正常取消在进程退出后数百 ms～数秒即返回。(b) 改动面小、不触碰 kill.ts 公共契约，符合最小改动与「减少 fork 面」。(c) S6 的主题是非阻塞化，bash abort 时延对主控阻塞的边际影响小；若后续实测确有高频慢取消，再单独立包做选项二（短预算）叠加。实现红线：stopError 不得静默（并入消息＋warn 日志），:393 匹配方式变更需核全消费点。
