## 一、结论：暂缓——默认不采纳，试点方案留档按摩擦触发

**不建议现在把 worker 执行链改架 durable**。核心理由四条，逐条有代码证据：

1. **恢复语义与进程模型对不上**。durable 的断点续跑是「同一存储被后继进程 reopen → `resume()` 重派 pending 任务」（`packages/durable/src/harness/scheduler.ts:231-258`，open 时把幸存 `running` 任务改回 `pending`），且自述「**一个存储同一时刻只归一个进程，没有跨进程锁**」（`packages/durable/README.md:529`）。PAO 的 worker 链是「owner 主会话 + 一次性 worker 子进程 + 项目文件锁」三方协作：worker 崩溃后 owner 还活着，续跑意味着 owner 再 spawn 一个后继 worker 进程去 reopen 同一存储——可行，但「尝试 N」从此横跨多个进程与一个 SQLite 库，身份故事翻倍（详见撞车清单 A）。
2. **abort 语义是协作式，顶替不了强制树杀**。durable abort 是「提交 abort 标记 → 等它拥有的活先停 → 各任务自跑善后」（`scheduler.ts:274-322`、README「Abort and Subagents」），**不杀任何 OS 进程**。PAO 的停止链价值恰在「进程真死才放锁」：`taskkill /T /F` 强杀 + 等退出确认 + StopProof 凭据放锁（`kill.ts:123-162`、`runner.ts:348-366`、`lock.ts:83-93`）。worker 挂死时 durable 的「等 owned work 完成」语义恰好是反效果（挂死＝永远等不完）。两套 abort 必须同时存在且排好序，这是新增复杂度，不是替换。
3. **可退役清单经核实接近空集**。加列预估「statemachine/process/wakeup 一部分」可退役——逐一核对不成立：`cards/statemachine.ts` 是卡五态单写者状态机＝编排契约本体（加列明文不动）；`cards/process.ts` 是验收命令执行器（与 durable 无重叠域）；`cards/wakeup.ts` 是 50 行纯函数依赖扫描（无状态可接管）。现行 worker 链的其余机制（登记表/租约/代数/live 证据/通知面）要么是编排契约，要么 durable 没有对应物。**采纳 durable 换不来删除现有手写件**，买到的是「worker 会话崩溃不丢上下文」这一件事。
4. ** Experimental API 税是永久的**。上游自标「**Experimental. The API changes without notice**」（`README.md:3`），1.0.0→1.0.2 四天三版（CHANGELOG，2026-10-01 首发）。worker 执行链是生产关键路径，接线上游就要永久维护隔离层＋升级门（fork 内 `src/experimental/durable/` 先例就是这么做的，而该目录正被 S10 第 2 条整目录移除——同批计划里一边删一边再接，须有强理由）。

**且现行方案已有廉价替代**：worker 会话本就持久化在 `<项目根>/.pao/worker会话/`（`session-bridge.ts:21-22`），pi 支持 `--session-id` 复开既有会话（`coding-agent/src/main.ts:437-440`）。「后续 worker 用同一会话标识复开旧 transcript＋继续提示词」是一个零新依赖的 checkpoint-lite，能吃到 durable 断点续跑收益的大头（不丢对话上下文）。durable 的独占增益只剩「工具调用中断语义/任务态/自底向上 abort」这些 PAO 用不上的部分。

**收档方式**：本报告登记为「暂缓，摩擦触发」。若「长活 worker 崩溃重开重跑」在摩擦日志里成为真实高频损失（对照口径见 §四试点方案），按 §四方案跑一次性试点拿数据再议；不满足触发条件即维持现状。采纳与否均不动 §17「文件即真相源」定案。

### 2.2 核心模型

- **Harness**：一个打开的存储＋在其上跑 agent 的机器。一切变更走单线原子提交，**提交落盘前不显示任何东西**。
- **Conversation/Entry/Commit/Document**：会话＝不可变条目流；`commit(tx)` 可同时追加条目/改文档/建任务，要么全存要么全不存；文档＝与会话同存的类型化 JSON 状态（`pi.agent`/`pi.live`/`pi.inbox`/`pi.usage`/`pi.provider`）。
- **Task**：持久状态机，每步存 checkpoint；有 owner（其会话或另一任务）。状态 `pending/running/waiting/completing`；**重启后 running→pending 保留 checkpoint**（`scheduler.ts:231-258`）。
- **Submission**：交给会话的输入/写入，可 `wait()`；**同 `requestId` 重投返回既有提交，不重复执行**（`src/harness/submissions.ts:155-159`；按会话内去重）。

### 2.3 恢复语义（本评估的主题）

- `Harness.open()` 载入活任务、把幸存 `running` 改回 `pending`；`resume()` 启调度器重派。工具调用的 intent（最终参数＋replay 策略）**先于 execute 提交**；进程死于调用中时，`replay:"safe"` 的工具重跑，否则模型收到 `interrupted` 错误结果（已提交的输出保留）（`src/harness/tool.ts:88-110`）。
- 流式部分/工具输出**至多每 100ms 提交一次**，崩溃最多丢这个窗口（README Watching 节）。
- abort：标记制、**自底向上**——abort 一个任务先 abort 它拥有的活，善后 handler 等活停完才跑（README Child Tasks 节；`scheduler.ts:274-322`）。
- 存储：SQLite（WAL＋`synchronous=NORMAL`：**进程崩溃提交存活，断电可能丢最新一条**）/ JSONL（追加式，可选 fsync）/ 内存。**一进程一存储，无跨进程锁**（README Storage 节）。
- 无注册定义可接手的任务落 `orphaned`；缺定义只阻塞不报错（`inspect()` 可查）。

### 2.4 对 PAO 有意义的公开面清单

`Harness.open/root/createConversation/submit（requestId 去重）/resume/close`、`conversation.abort/configure/viewState/watch`、`waitForTask/taskGraph/inspect/usage`、`defineTask/defineDoc/defineExtension/defineTool`、存储后端 `storage/sqlite/node` 等。类型面宽（index.ts 导出 180 行），全部 Experimental。

## 三、现行执行链对照与撞车清单

### 3.1 现行链回顾（哪个环节是「断点续跑」的候选接线点）

现行链（S5/S6 后形态）：

```
pao_派单（受理即返,B 档非阻塞,worker/index.ts:588-666 fire-and-forget）
  → executeDispatch（dispatch-core.ts:730-856,单一受保护事务链:
     项目队列→预算队列→并发名额→项目写锁→workflowCheck 锁后重核→认领）
  → 认领=卡状态机 待认领→进行中（尝试+1）＋认领基线快照＋租约三字段
  → runner.run（runner.ts:372-686）:spawn 一次性 worker 子进程
     （pi --mode json -p,PAO_ROLE=worker,live 证据逐 chunk 落盘）
  → worker 崩溃=退出码<0 → 回执「未知/失败」→ appendDispatchReceipt 落卡
  → owner 侧机械验收（verifier）→ 已交付 → wakeup 解锁下游
```

**崩溃恢复现状＝「孤儿接管重开重跑」**：worker 死后 owner 存活，走接管三查（dispatch-core.ts:139-166：同号回执去重→登记表活进程→状态机落失败），卡落失败（结果未知），点名重派=新尝试从头跑。项目写锁在 owner 手里，worker 崩溃不触及锁（lock.ts:17-18：持锁进程崩溃才留残锁，stale 24h，不自动清锁——R05）。

**接线点判定**：若试点，唯一说得通的改架点是 **runner.run 的 worker 进程内部**——worker 子进程从「无状态一次性 pi 会话」换成「打开本尝试专属 durable 存储＋同一套工具扩展的 Harness 会话」。owner 侧派发/认领/租约/锁/回执落卡/验收**全部不动**（编排契约不动）。owner 在「接管三查」的第三查后新增一个分支：查到本尝试有 durable 存储且卡未落终态 → spawn 后继 worker 复开该存储 resume()，而不是重开新尝试。**不建议**的另一条路（owner 进程内自持 Harness、worker 变成 durable 子会话/ToolTask）：摧毁进程隔离与角色模型（PAO_ROLE_ENV worker 角色、shell 护栏、预算按进程强停、树杀），属全链重构，与「最小试点」背道而驰。

### 3.2 撞车清单（逐条 file:line）

#### A. 同号重试去重 vs durable requestId 去重

**PAO 侧（身份=卡路径＋尝试号，真相在卡文件）**：

| 位置 | 机制 |
|---|---|
| `pao/worker/dispatch-core.ts:103-113` | `claimRefusalDetail`：进行中卡拒派时，当前尝试已有回执→返回既有结果（同号不重派）；无回执→「结果未知：先查现场，重启后不盲重放」 |
| `pao/worker/dispatch-core.ts:145-149` | `takeoverOrphanForDispatch` 第一查：当前尝试已有回执→接管被拒（同号不重派） |
| `pao/worker/dispatch-core.ts:220-226` | `claimRefusalReason`：进行中不双跑；终态不重跑 |
| `pao/worker/registry.ts:54-56` | `#cardKey`（Windows 小写归一）——去重/租约/代数的统一身份键 |
| `pao/worker/registry.ts:59-74` | `claimGeneration/bumpClaimGeneration`：认领代数，接管推进代际、旧条目打「被接管」拒旧 worker 状态覆盖 |
| `pao/worker/runner.ts:220-223` + `377-378` | `executionKey` 同口径；`#active.has(key)` 双跑拒绝 |
| `pao/worker/index.ts:203-208` | 工具同步面提前拒派（同文案） |
| `pao/cards/statemachine.ts:159-161` | 尝试号只在「待认领→进行中」实际启动时 +1——尝试号即派发事务号 |

**durable 侧（身份=requestId，真相在存储，作用域=单会话）**：`packages/durable/src/harness/submissions.ts:155-159`（`submissionByRequest(conversationId, requestId)`，同号返回既有 submission）。

**撞车点**：
1. **两套答案源**。「尝试 N 是否已在跑/已完事」将同时有两个权威答案——卡文件（现行，契约指定为真相源）与 durable 存储（running→pending 的内部状态）。两者会分歧：存储说 pending（崩溃后未 resume），卡说已落终态（owner 已裁决取消）——谁赢？契约要求文件赢，则 durable 的任务态永远只是参考，其 requestId 去重对本问题变成冗余机件；若存储赢，直接违反加列边界。
2. **作用域错位**。durable requestId 去重按会话内生效；PAO 去重按卡路径跨进程跨会话生效。若把 requestId 设为 `卡路径#尝试号`，跨「同一卡不同 worker 代进程」的去重仍要落回卡文件判定——durable 去重接不上这个键。
3. **尝试号语义冲突**。断点续跑=同一尝试横跨多个 worker 进程（多个执行标识、多份 durable 存储 reopen）。而 `claimRefusalDetail` 把「当前尝试存在任何回执」当作终局信号（去重优先于续跑）。若后继进程在续跑中先落了任何中间回执，同号去重会把后续接管全部拒死。**裁决建议**：中间 checkpoint 只住 durable 存储，绝不进卡回执区；卡回执区仍只收终局回执——此约束必须写进试点协议，否则两机制互锁。

#### B. abort 树杀（kill.ts StopProof 链） vs durable 自底向上 abort

**PAO 侧（强制 OS 级，凭据链保证「真死才放锁」）**：

| 位置 | 机制 |
|---|---|
| `pao/worker/kill.ts:54-120` | Windows 树杀：PowerShell 进程表快照＋成员身份（pid:创建时刻）双配对＋深优先杀序＋二跳续杀种子，防 pid 复用误杀、防假报树灭 |
| `pao/worker/kill.ts:123-162` | `killTree`：Windows `taskkill /T /F`（两跳预算约 90.5s）；POSIX SIGTERM 宽限→SIGKILL 兜底 |
| `pao/worker/runner.ts:60-76` | `StopProof` 类＋模块私有签发符号（外部无法伪造） |
| `pao/worker/runner.ts:348-366` | `#stopEntry`（树杀＋等真退出）＋`confirmStopped`（活动进程仍在→拒签凭据） |
| `pao/worker/runner.ts:693-714` | `terminate`（上级终止标记）→`cancel`（①阻新派②树杀③签发 StopProof） |
| `pao/worker/runner.ts:720-732` | `stopAll`（主会话退出全停，R05） |
| `pao/worker/lock.ts:83-93` | `releaseProjectLock` 必须出示 StopProof——「先停后放锁」类型级强制 |
| `pao/worker/lifecycle.ts:23-82` | session_shutdown/SIGINT/SIGTERM/beforeExit 退出钩子全停 |
| `pao/cards/process.ts:18-27` | 验收命令执行同用 killTree（超时 124/树杀失败兜底 SIGKILL） |

**durable 侧（协作式，存储内标记）**：`packages/durable/src/harness/scheduler.ts:274-322`（abort 提交标记/无定义者落 orphaned/join 运行中的调用）；README Abort and Subagents／Child Tasks 节（abort 自底向上，等 owned work 停完才跑善后）。

**撞车点**：
1. **语义方向相反**。PAO 杀Worker 的主场景是「挂死/超时/上级裁决」——目标进程不配合，必须强杀；durable abort 语义是「等它自己做完手里的活再善后」。对挂死进程，durable abort 语义等于永远不返回。**killTree/StopProof 不可退役**，durable 不提供任何替代物。
2. **双向漏信号的-new 风险**。接线后停止一个 durable worker 必须**两件事都做且有序**：先向其存储投递 abort 标记（否则后继进程 resume() 会复活被裁决取消的工作——「abort 树撞车」的实体形态），再树杀 OS 进程（否则挂死进程占着项目写锁与并发名额）。但标记投递本身要 worker 进程/owner 能写同一存储——owner 不持有 worker 的存储句柄时，只能靠「owner 在卡文件落终态＝后继永不 spawn」这条间接裁决线兜底。任何一条绕过卡文件的 resume 路径都是复活事故。
3. **「父先于子 idle」等待语义多余**。durable 保证 owner idle 前其 owned work 全停；PAO 的对应保证由 StopProof 链在 OS 层给出且更硬（树杀＋退出确认＋凭据）。两套并存时 durable 的等待树只会增加续跑 worker 的收敛复杂度。

#### C. 加列预估的「statemachine/process/wakeup」——核实为不可退役

| 文件 | 实质 | durable 有对应物吗 |
|---|---|---|
| `pao/cards/statemachine.ts:16-22,86-110,187-241` | 卡五态迁移表＋单写者校验＋读-合并-写落盘＝**编排契约本体**（加列明文不动） | 无——durable 任务状态机管的是执行内部态，不懂 owner/尝试/回执/审计段 |
| `pao/cards/process.ts:4-84` | 验收命令执行器（execFile＋树杀超时） | 无——verifier 域，不属 worker 执行链 |
| `pao/cards/wakeup.ts:38-50` | 依赖解锁纯函数扫描（§19 交付唤醒） | 无——文件扫描，无状态 |

#### D. 其他重叠点（如实列出不构成撞车但需裁决）

| 现行件 | durable 对应 | 关系 |

## 四、三件产出

### 产出①：试点证据方案（最小试点怎么跑、度量什么）——留档按摩擦触发

**触发条件（先决）**：摩擦日志出现「长活 worker 崩溃/中断后重开重跑」造成可量化损失（重复 token 成本或延误）≥2 次记录；不满足即不跑。

**试点形态（选项 a：worker 进程内部改架，owner 侧零契约改动）**：

1. 隔离 PAO_HOME＋一次性测试项目；保温配置开一个实验开关（如 `保温.json「断点续跑」`，缺省关＝现状零行为）。
2. worker 启动体换成 thin wrapper：打开 `<项目根>/.pao/worker会话/<执行标识前缀>/durable.sqlite`（openNodeSqliteStorage），装 PAO worker 提示词与工具为 extension，submit 同一 buildWorkerPrompt 提示词，wait 到终局，最后一条助手消息仍按现行 JSON 回执协议交 stdout（回执契约不变）。
3. 长活场景：一张多轮工具密集卡（脚本化工具或 faux provider 驱动，跑 30 分钟量级）。
4. 崩溃演练：跑至中途对 worker 进程 `taskkill /F`（模拟崩溃，owner 不死）→ owner 收「未知」回执 → 走接管三查 → 新分支：发现本尝试 durable 存储且卡未终态 → spawn 后继 worker 复开同一存储 `resume()` 续跑到终局。
5. 对照三臂：A=现状重开重跑（基线）；B=durable 断点续跑；C=**廉价替代**（后继 worker 以同一 `--session-id` 复开既有 pi 会话＋继续提示词，零新依赖，`main.ts:437-440` 机制）。
6. 终止演练：续跑中调 `pao_终止卡`——验证树杀＋StopProof 放锁照常、后继不再 spawn、durable 存储残留随 R19 归档清理。
7. 锁/租约回归：worker 崩溃全程不触项目写锁（锁在 owner 手）；owner 崩溃场景维持 R05 残锁 24h 人工裁决，不因 durable 改变。

**度量（对账口径，同卡同输入）**：
- 三臂总成本（token/费用）与总墙钟：B、C 相对 A 省多少；B 相对 C 的边际增益是否值得 Experimental 税；
- 正确性：中断工具的 `interrupted` 结果与文件副作用——`replay:"unsafe` 默认下 edit/write/bash 类工具绝不自动重跑（`tool.ts:98-110`），核对续跑后 git 真值比对与认领基线快照结论无漂移；
- 契约不破：卡回执区只收终局回执（中间 checkpoint 只住存储）；同号去重、接管三查、租约代数行为与现状逐条一致；
- 清理负担：每尝试一个 SQLite 文件的产生量与 R19 归档清理成本；§17 使用现场仓将新含二进制库文件的备份影响（须评估是否 ignore）。

**通过门槛**：B 相对 A 有可观的成本/时延节省，且 B 相对 C 的增益足以覆盖隔离层维护与升级门成本；任一契约回归失败即判不采纳。

### 产出②：可退役清单（若采纳 durable 且试点通过）

诚实结论：**无条件可退役项＝0**。现行 worker 链把状态全放在 owner 进程与卡文件，worker 本体刻意无状态（一次性），durable 没有可整体顶掉的手写件。有条件候选（均待试点证据）：

| 候选 | 条件 | 性质 |
|---|---|---|
| `session-bridge.ts` 的 worker会话 transcript 部分（21-22 行会话目录） | 选项 a 采纳后 durable 存储即完整会话 | 部分替代；执行映射日志仍留 |
| live 证据的「中途查看」用途（B 档静默读取面） | 若试点证明 viewState/committed 输出可作读取口 | 部分替代；live 的证据契约与活性打点用途保留 |
| 若未来写 worker 侧自研 checkpoint（现无此件） | —— | 预防性：durable 在位则永不自研 |

**不可退役（明确登记）**：`kill.ts`/`StopProof`/`confirmStopped`（durable abort 不杀 OS 进程，语义方向相反）；`registry.ts` 全部（部门/派单理由/租约/代数是编排字段）；`lock.ts`（跨进程互斥不外包，加列明文）；`cards/statemachine.ts`/`wakeup.ts`/`process.ts`（§3.2-C）；`dispatch-core.ts` 同号去重与接管三查（文件真相源）；K1/K2 后台链与实例级累计（owner 会话机制，与 worker 内部执行正交）。

### 产出③：experimental API 隔离接口建议（若未来采纳）

原则：durable 类型一个都不漏进 `src/pao/**` 业务模块；单点包裹，升级门挂在持续维护流程。

1. **单一适配模块**：新建 `src/pao/worker/durable-worker.ts`（唯一允许 import `@earendil-works/pi-durable*` 的文件，含深导入 `storage/sqlite/node`）。加一条 biome/lint 边界规则（或 check:gates 检查）：pao 业务模块 import pi-durable 即红。
2. **PAO 自有小接口面**（全部用 PAO 类型，签名不出现 TaskId/ConversationId/Context 等 durable 类型）：
   ```ts
   /** 断点续跑 worker 会话（experimental 包裹层，API 不承诺稳定） */
   export interface ResumableWorker {
     run(options: WorkerRunOptions): Promise<WorkerReceipt>;        // 同一回执契约
     static openAttempt(input: { 卡路径: string; 尝试: number; 项目根: string }): ResumableWorker | undefined;
                                                                      // 存在即复开（resume），不存在 undefined
     storagePathOf(input: { 卡路径: string; 尝试: number; 项目根: string }): string | undefined;
                                                                      // 供接管三查第四分支探测 checkpoint
     dispose(): Promise<void>;
   }
   ```
   requestId 映射规则固化在层内：`requestId = ${cardKey}#${尝试}`；abort 标记投递也封装在层内（`abortAttempt()`），卡文件终态裁决永远优先于存储态。
3. **版本门**：适配层带契约测试套（open/submit/requestId 去重/resume/abort 标记/replay unsafe 中断行为六断言，仿 durable 自带 conformance 思路）；持续维护升级流程里 pi rebase 后先跑该套再跑全量。上游 README:3 自标无通知变更——把「升级必红可能性」当作常态而非事故。
4. **默认关**：保温配置显式开关，缺省关＝完全现状路径（零 import 执行、零行为变化）；试点证据未过门槛不翻缺省。
5. **生命周期**：每尝试存储路径规范化到 `<项目根>/.pao/worker会话/` 下随执行标识管理，归档随 R19 清理；存储文件进 `.pao` 归档边界（是否入使用现场仓备份随 §17 评估定，试点时量出体积再定）。
