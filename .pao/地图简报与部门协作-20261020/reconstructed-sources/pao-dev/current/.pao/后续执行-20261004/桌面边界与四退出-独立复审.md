## 四退出技术证据

审查对象：[四退出技术验收.mjs](四退出技术验收.mjs) 与 `四退出技术验收-2026-10-04T02-26-53-102Z/总结果.json` 及关联身份、心跳、原始终端输出。四项记录均在清理前完成断言：父进程、真实宿主部长进程、孙进程 PID 不再存活；孙进程心跳文件至少 600 ms 不再变化；独立对照进程仍存活且心跳继续。身份还核对父子 PID、IPC 已连接及 managed 标记。失败不因 finally 清理变为通过。

据此可支持“这四种技术退出操作后，所测受管进程树停止，所设独立对照进程未被误杀”。`kill-parent-only` 的 taskkill 参数不含 `/T`，其父死后的后代停止有较强独立证据。其他用户进程未逐个观测，不能扩大成对所有系统进程的无误杀保证。

这是正式 CLI/MinisterHost 加无模型心跳夹具的技术集成验证。没有在途模型请求，`modelRequests: 0` 为场景设计值，不是供应商网络计数；不能单独证明正在生成的远端请求已取消。也未验证图形 Windows Terminal 关窗体验，该项已按用户授权跳过。

本机 node-pty 的 `WindowsPtyAgent.kill` 会关闭 ConPTY，并异步枚举 console PID 后主动 `process.kill`。所以 `close-conpty` 证明该终端关闭机制后的停止结果，不能单独把效果全部归因 PAO 父死守护。

`AttachConsole failed` 对应 node-pty 独立 console 枚举辅助进程；其失败后存在 5 秒回退路径。它不推翻已经在清理前完成的 PID 和心跳断言，也不能被解释成正常无错退出。该报错未出现在本次四项各自保存的终端原始输出/对照 stderr 中；本次只能确认代码来源和上述影响边界，无法仅凭这些文件独立重建主脚本 stderr 报错的精确时序。建议保留主进程整体 stdout/stderr 原件链接，报告继续列明这个限制。
