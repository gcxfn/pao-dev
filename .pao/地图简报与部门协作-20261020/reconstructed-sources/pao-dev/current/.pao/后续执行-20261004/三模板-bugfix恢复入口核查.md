# bugfix 旧实例正式恢复入口核查（2026-10-04）

结论：现有正式 UI 可以确认恢复并把实例交给新主控，原源码、卡和回执都保留；但本次卡累计 12 轮额度已全部用完，恢复或授权第二次尝试不会获得新的 12 轮。按预算不变的要求，当前能力不能继续完成业务。此次只读调查未改任何运行数据、源码或预算，也未发模型请求。

## 正式 UI 恢复

在原业务工作树打开新的交互主控，PAO_HOME 仍指使用现场。在输入框提交以下正式命令，核实对话框中的实例与理由后，由执行验收的主代理实际点击确认（本调查没有代为确认）：

```text
/pao flow control {"动作":"恢复","名字":"业务修复-real-20261004","卡目录":"D:/AI/workspace/临时文件夹/PAO-对照验收-20261004/业务-bugfix-real-20261004/.pao/业务验收/卡","实例":"ffc97a6c-4350-45aa-bb83-43d98f37ba06","原owner":"d236a6ff-0ee2-46ce-9f23-457e884b53aa","理由":"已核原主控及工人退出；保留第一次失败回执与已有源码修改，测试和审查尚未完成。本次仅确认接管恢复，不提高卡预算，不将恢复等同业务成功。"}
```

该路由复用 pao_节点控制，必须有交互界面且 ui.confirm 返回真实确认；恢复校验实例、旧 owner、当前真实会话身份和无进行中卡。确认后由当前会话接管 owner，清除暂停/裁定、追加人工恢复记录。失败卡仍失败，因此实例可继续显示挂起。这是合理状态，不能标成业务通过。

证据：workflow/tools.ts 节点控制 execute 与 control 路由；workflow/control.ts resumeControl。不要用注入 confirmed:true 或编辑控制文件替代确认。

## 卡重派入口及当前阻塞

正式工具 pao_改状态 支持以下参数（这里只列可用接口，不建议明知额度耗尽仍执行）：

```json
{"卡目录":"D:/AI/workspace/临时文件夹/PAO-对照验收-20261004/业务-bugfix-real-20261004/.pao/业务验收/卡","卡号":1,"操作者":"主控","新状态":"待认领","依据":"显式授权原卡第二次尝试，保留第一次回执及源码，预算不变"}
```

卡的 owner 是字符串“主控”，与控制正本的会话 UUID 是两个字段。失败→待认领受默认尝试上限 2 约束，当前尝试 1 符合；领取时才递增尝试。随后正式 pao_推流 参数为名字与上述卡目录，由自动链派发。

但 worker/dispatch-core.ts 的 remainingDispatchBudget 会先累计原卡所有尝试回执，再从原卡预算扣除，不能把“尝试上限”当作费用或轮次追加授权。实际卡预算 turns=12/toolCalls=80，第一次回执 turns=12/toolCalls=15；所以剩余 turns=0，派发会报“卡卡0001 预算耗尽：turns”，不会开始新 worker。恢复函数不改预算；pao_改状态没有预算修改参数。

同实例开发节点已经拆解结束，control.ts addNodeCards 也会拒绝再次交新卡（“拆解已结束或本批没有卡”）。因此不能用主控另建一个未绑定卡冒充原流程续跑，也不能无审计地改卡预算或擦回执。
