## 三、③test:core:* 内嵌全量构建消重＋陈旧产物拒绝

### 现状核实

`apps/desktop/package.json` 恰 26 个 `test:core:*`，全部以 `pnpm build && ` 开头；`pnpm build`＝build:deps（4 共享包 build）＋notification-helper（win32 早退 no-op）＋electron-vite build。L8 r1 实测全量 build ≈5 分钟 → 单 spec 调试一次付 5 分钟构建。范围外同款：test:e2e:core / test:e2e:native / test:e2e:live / demo:* / test:e2e:runner 也内嵌 build，本批不动（登记，后续可同法推广）；test:e2e:core 是 CI 整车道门，保持保证新鲜的朴素 build。

### 方案（先写后动手——mtime 新鲜度门，宁误重建不赴陈旧）

新增 `apps/desktop/scripts/build-if-stale.mjs`（约 60 行，零依赖）＋apps/desktop script `"build:if-stale"`；26 个 test:core:* 的 `pnpm build && ` → `pnpm build:if-stale && `（replace_all 一处改齐）。

- 输入面（max mtime 递归收集）：apps/desktop 的 `electron/`（main/preload 源）、`src/`（renderer 源，index.html→/src/main.tsx）、`contracts/`、index.html、electron.vite.config.mjs、四个 tsconfig、package.json、notification-helper 脚本；四共享包目录（session-driver/catalogs/extension-ui/pi-sdk-driver，剔除 dist/node_modules/test——test 改动不影响构建产物）；根 pnpm-lock.yaml。
- 判定：stamp（`node_modules/.cache/desktop-build-stamp.json`，记录上次成功构建后的 maxInputMtime）缺失、或 out/main/main.js 缺失、或当前 maxInputMtime > stamp → 陈旧 → 跑完整 `pnpm build`，成功后重写 stamp；否则跳过。git checkout/rebase 会刷新被换文件 mtime → 必然触发重建，陈旧产物到不了测试。
- `--check` 干跑：只报「fresh（跳过）/ stale（需构建）」并以 0/1 退出，不动手——供逻辑自检与门脚本探测。
- ponytail 天花板注明：mtime 比对是 make 同级语义，「内容改了但 mtime 被拨旧」的极端场景检测不到；需要强保证时升级为内容指纹。
- **不采纳**：project references / tsc -b——应用构建瓶颈在 electron-vite/renderer（全 build ≈5min 中 build:shared 仅 9.5s），tsc 增量图帮不上；PAO 侧 tsc 全仓 4.4s（TS7）同样无收益。

### 验证

1. 无 stamp 首跑 `build:if-stale` → 触发完整构建（同时复核「≈5min」数据）→ stamp 落盘。
2. `--check` 复跑 → fresh（退出 0）。
3. touch 一个源文件 → `--check` → stale（退出 1，证明 mtime 判定生效）→ 恢复该文件原 mtime → `--check` 复归 fresh（零额外构建完成逻辑自检）。
4. 抽 3 个 test:core:* 单跑（navigation / changed-files / persistence——均不在 L8/S11 已知红清单）：起跑日志应显示跳过构建，测试等价绿。隔离口径沿用脚本既有 PI_APP_TEST_LANE=core PI_APP_REAL_AUTH=0 PI_APP_TEST_MODE=background＋harness 自管隔离。
