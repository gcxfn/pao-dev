## 一、双配对再攻击

### 1. 同一毫秒内 pid 复用骗过配对（1a）——闭合，且强于 V3 记录的自评

配对判据是「 transported created ＝＝ 二跳快照行创建时刻（毫秒）」。攻击需复用进程的创建毫秒与原成员相同，而真实链路的时序约束是单向的：

- 原成员 M 创建于 C0，首跳快照时刻 T1≥C0（必须活着才被枚举），被 taskkill 杀死于 T2≥T1；
- pid 只能在 M 的进程对象销毁后被复用，复用者 N 创建于 T3≥T2（taskkill 是外部进程派生＋强制终止销毁，仅此一步就是几十毫秒级）；
- 骗过配对要求 T3==C0，即「创建→快照→taskkill→销毁→pid 再发行→新进程创建」全部落在同一毫秒——物理不可行；
- WMI CreationDate 由内核填充，用户态不可伪造；首跳预写清单由 $rows 真快照生成，无捏造注入面。

结论：V3 记录把 C1 说成「毫秒精度口径」的窄窗防护，实际该窗口在真实杀链里是**空集**。无发现。

### 2. stderr 丢弃记录的混入（1b）——主链无害；新 P4-1

- **parseSurvivors 误读：不可能**。记录走 `[Console]::Error.WriteLine`（stderr），parseSurvivors 只吃 execFile 回调的 stdout 参数；探针 B 实测纯配对场景 stdout 恰为一行清单、stderr 为空，两流干净分离。
- **错误语义污染：不发生**。探针 C 实测（脚本头部两条丢弃记录＋尾部 throw）：stderr 次序＝丢弃记录在头、真实原因（`Tree member still alive: 3333`）在尾——种子展开段在脚本最前、throw 在最后，次序由静态位置保证；`slice(-160)`（verifier.ts:679 注释处）取尾留的正是真实原因。taskkill 自身失败文本也先于 throw 落 stderr，同理不挤尾。全仓 grep 确认 error.message 无任何结构化解析消费面（只有 process.ts 挂 cause＋console.warn、verifier.ts 截尾展示），丢弃记录文本混入只是排障信息增量。
- **P4-1（新发现，登记级）**：丢弃记录只在**同跳也失败**时才可见（stderr→error.message→process.ts console.warn）；若种子被丢弃后本跳杀干净（exit 0 成功路径），execFile 回调走 resolve 分支、stderr 被丢弃——「近失丢弃」审计线索永久不可见。无功能实害（丢弃动作本身正确），属可观测性缺口。建议挂账：成功分支可采 stderr 一行 console.warn。

### 3. 预写清单 stdout 格式 vs parseSurvivors（1c）——一致，无漂移

- 生产端（kill.ts:101 `'{0}:{1}' -f $_.ProcessId, ToUnixTimeMilliseconds` 逗号 join）与解析端（kill.ts:37-47 `split(/[\s,]+/)`＋`split(":")`＋双方正整数）**同文件单点维护**，一处改两边可见；
- PS `-f` 对整数输出与重定向编码（OEM/ANSI）对「数字:数字」形态无影响——探针 B 真 PS 实测 stdout＝`"22112:1791329672843\r\n"`，喂给同逻辑解析逐 token 命中（`\s` 吸收 CRLF，parseInt 容忍 BOM）；
- 测试双向钉住：C1/C2 用例以字面元组 `@(4244,1339778498123)` 断言二跳脚本、以字面 `"4244:1339778498123"` 喂首跳 stdout——任何一侧格式漂移即红；
- 空清单形态（$selected 空→Write-Output 空行→token ''→NaN 丢弃）与重复 pid 形态（见 §二.2）均有落点。

## 二、C2 预写语义攻击

1. **时机确认**：静态顺序（kill.ts:100-104）＝杀循环→Write-Output 预写→$remaining 全表收尾→throw。收尾是两次全表枚举的秒级大头，被超时杀时预写已落 stdout——「Write-Output 后被杀 stdout 仍完整带回」由 R2 探针 2 实证、V3 §六.2 拼合维持。**确认，这正是 C2 目的**。剩余窗口只有杀循环尾与预写语句之间的亚毫秒（V3 §六.3 已如实记录，维持原判可忽略）。
2. **预写与 throw 的读者自洽：成立**。预写是「已尝试成员全集」（机器通道，二跳种子），throw 是「其中仍活着者」（人读通道）——throw 列出的 pid 必然 ⊆ 预写清单，超集关系明确；成功路径预写行被 resolve 分支静默消费，不产生用户可见残留。双重失败终态报错是二跳自己的 lastError，语义仍是「此刻还活着什么」，与首跳预写不冲突。
3. **附带确认（记录性，非缺陷）**：二跳种子若含根自身（首跳根活且报回），根行会因 `if ($root)` 与种子展开段**重复入选 $selected**（List 非集合）——三个落点全部无害化：杀循环重复项经杀前重查（已死→null→continue）跳过；预写清单重复 pid 被 parseSurvivors 的 Map 按 pid 去重（注释即为此留）；根若真活则 throw 消息重复同一 pid（纯观感）。既有防御覆盖，登记 P4-2 备查即可。
