## evals 框架现状（核实结论）

- 框架：`PAO/packages/evals`，基于 vitest-evals 0.15.0；用例平铺在 `evals/` 下。
  - `*.docs.eval.ts`＝文档对照评估（Docker 双镜像），`eval:docs` 入口；
  - 其余 `*.eval.ts`＝host 评估，本机 vitest 跑，入口 `npm run eval:host -w packages/evals`（即 `vitest run --config vitest.evals.config.ts --project host`），单文件可 `-- evals/xxx.eval.ts` 定向。
  - 用例格式：`describeEval(name, { harness, judgeThreshold, skipIf }, it => it("...", async ({run}) => ...))`；harness 来自 `src/harness.ts` 的 `createPiCodingAgentHarness`（模型在运行时才解析，PI_PROVIDER/PI_MODEL 缺失才报错）。host 项目内用普通 vitest `describe/it` 亦可（不需要 harness），可控序列类即此形态。
  - `skipIf` 是 describeEval 套件级原生选项——模型类的 S12 门控用它，不需要改任何框架文件（无受阻项）。
- 框架无需改注册表/既有文件即可挂新用例：host 项目 include 为 `evals/**/*.eval.ts` glob，新文件即自动纳入。biome 与根 tsc 的 include 均不含 `packages/evals/evals/**`（既有 evals 文件同口径，非本包特殊化）。

断言 S8 §6 契约，观测口径与实现措辞解耦（清单状态按 details 整表快照的内容子串判定；提醒按「该次工具结果 content 相对原文被追加」判定，不依赖文案）：

2. 新建清单：整表快照入 details，activeForm 可携带。
3. 整表替换＋四态流转：新表完整生效、旧条目不残留、四态均可落。
4. 上限 20：21 条拒绝，工具仍可用。
5. 非法输入拒绝不覆写：未知状态/空内容/重复内容——旧清单存活由陈旧提醒「非空」口径证明（拒绝若覆写/清空，第 5 次实质调用不会触发提醒）。
6. 空数组清空：合法操作，清单归零。
7. 陈旧提醒（阈值 5 可控模拟 tool_result 事件）：清单空不计数；满 5 追加提醒；同陈旧期只提醒一次；失败/读取类（read/grep）/todo_write 自身不误计；新 todo_write 重置（再满 5 再提醒）；清空后不再提醒。

### 模型评估类（2 用例，`todo-write-timeliness.model.eval.ts`，S12 授权后运行）

- 场景与预期行为：
  - 基线三步（a/b/c 三文件，任务书在 workspace 文件）：先列清单→每步完成立即更新（不攒批）→交付前对账→`submit_checklist` 结构化提交最终清单。
  - 计划变化重构（x1/x2 后第二指令作废 x3、新增 y/z）：立即重构清单（作废取消/移除＋新步骤纳入）→按新清单执行→对账提交。
- 评分口径（确定性计算，无 LLM 评委，各 0..1 随 run 产物记录，judgeThreshold: null——低分是数据不是基建失败）：
  - 更新及时性：每个步骤完成动作与其后下一步实质动作之间，todo_write 快照 completed 计数必须增长（攒批扣分；多阶段按阶段平均）；
  - 列表准确性：合规 todo_write 占比（≤20 条、内容非空去重、≤1 个 in_progress），且全程覆盖全部在册步骤；
  - 重构正确性：计划变化后的首个 todo_write 即取消/移除作废步骤并纳入新步骤；
  - 交付对账完整：submit_checklist 恰一次，finalTodos 与地面真值一致，无 pending/in_progress 残留。
- todo_write 用契约替身（整表替换/四态/上限 20/空数组清空/非法拒绝不覆写，与内核已落地实现同契约；promptGuidelines 即 S8 纪律段同源口径）：评分口径稳定、不随内核重构漂移；S12 需端到端口径时把 customTools 换真实 todo_write 再跑即可（替身契约即验收契约）。
