# 原始报告：模块边界与依赖方向（子代理产出，2026-10-07）

## 维度小结

**总体判断：边界基本干净，方向纪律明显被有意识维护。**

核过的证据面：
- **内核 → 桌面/CLI**：`PAO/packages/` 全量 grep 无任何 `electron`、`apps/desktop` import。唯一反向耦合是 `pao/app.ts` 用**路径拼接**内嵌了桌面仓布局知识（见问题 1）。
- **桌面 → 内核**：三层通道全部走契约面——renderer（`desktop/apps/desktop/src/`）只 import `@pi-gui/session-driver` 类型，零内核、零 electron import；electron main 走 `@pi-gui/pi-sdk-driver` + `@earendil-works/pi-coding-agent`（含 `/pao`、`/pao/desktop` 两个**已声明的 package exports**）；`electron/platform/pao/` 桥接层只消费 driver 的 reader 类型与本地 `contracts/`，electron 侧**没有**任何直接 `readFileSync` 伸进 `.pao` 卡目录或内核源文件。`vendor-pao-kernel.mjs` 的 `../../../PAO` 相对路径是构建期脚本，产物已拷入 `vendor/`，不构成运行时依赖。
- **core/ 形态**：整体接近上游，仅 5 个文件被 pao 渗透（6 处 import + 1 处路径映射），但每处都是上游文件 diff（见问题 2）。
- **worker→workflow** 经 `dispatch-context` 注入回调收口（T02 重构注释明示「worker 通用派发不再导入 workflow/{control,driver,minister,recipe}」），是方向正确的设计，不是问题。

**主要风险区**：① `pao/` 内部 cards 为中心的网状互边（cards↔dept、cards↔worker、cards↔friction、knowledge↔memory），多为通用件错放层级造成；② `pao/app.ts` 内核反向依赖桌面仓布局；③ core→pao 的 6 处硬 import 扩 fork rebase 面。

## 问题清单

**P1**

1. `PAO/packages/coding-agent/src/pao/app.ts:19`（另 23-24、36-51 行）— 内核模块 `inspectLocalDesktop/runDesktopApp` 硬编码 `resolve(getPackageDir(), "../../../desktop")`，内嵌桌面仓布局知识（`apps/desktop/out/main/main.js`、`node_modules/electron/path.txt`、pi-sdk-driver 链接核对），是「共享内核依赖桌面」的唯一实锤，且默认路径只在 pao-dev 开发仓成立。建议：整块迁到 CLI 宿主层（`cli.ts` 侧实现 `pao app` 命令）或由 desktop 仓提供启动入口，内核只暴露版本/身份常量。

**P2**

2. `PAO/packages/coding-agent/src/core/sdk.ts:6-8`、`core/agent-session.ts:59`、`core/model-runtime.ts:68`、`core/tools/bash.ts:7`、`core/extensions/loader.ts:102` — core 反向值导入 pao 业务模块（`pao/context/precompaction`、`pao/runtime/request-fetch`、`pao/worker/budget`、`pao/worker/kill`），每处都是上游文件的永久 diff，扩大 fork rebase 面，与 §22「最小 diff 压 rebase 面」纪律相逆。建议：core 侧开 hook/注册点由装配层注入，或把 `killTree` 这类无业务通用件下沉 core/utils。
3. `PAO/packages/coding-agent/src/pao/cards/statemachine.ts:3` — 卡协议状态机直接 import `../friction/drafts`（recordFrictionDraft）做副作用写摩擦草稿，协议层混入诊断关注点；而 `friction/drafts.ts:24-25` 又反向 import `cards/atomic`＋`cards/lock`，形成 cards↔friction 互边。建议：状态机经事件/回调外发摩擦信号，或把 recordFrictionDraft 连同 atomic/lock 迁 shared。
4. `pao/dept/scaffold.ts:3`、`pao/dept/registry.ts:3`、`pao/dept/projects.ts:5` ↔ `pao/cards/render.ts:3`、`pao/cards/tools.ts:6` — cards↔dept 互依：dept 三个文件从 cards 只取 `writeFileAtomic`（通用原子写却住在 cards/ 包里），cards 又依赖 dept/projects 的 listProjects。建议：`writeFileAtomic`/`withFileLock` 迁 `shared/`，卡协议与部门注册互不 import。
5. `pao/cards/metrics.ts:26-27`、`pao/cards/process.ts:2` — 卡层借执行层内部件：从 `worker/usage` 取 usageLineFromEventState/totalsUsage、从 `worker/kill` 取 killTree，与 worker→cards（receipt/runner/budget）构成 cards↔worker 互边；按 §27.1 卡与执行是两条边界。建议：用量聚合与进程树杀作为通用件迁 shared，或只允许派发/执行边界消费。
6. `pao/status/workflow-instances.ts:77` — 注释声明与 `pao/desktop/workflow.ts`「同口径」读冻结配方＋控制清单，实为两处手工同步的平行实现，无共享代码，口径漂移只靠注释纪律。建议：抽公共的控制正本读取函数，status 与 desktop 两个查询面共用。

**P3**

7. `pao/worker/runner.ts:168,395`、`pao/host/host.ts:250` — 内核运行时判断 `process.versions.electron` 并设 `ELECTRON_RUN_AS_NODE`，内核感知桌面宿主运行时。内嵌场景（§27.3）下可接受，但散在两处；建议收敛到单一 host-env 适配点并标注宿主关系出处。
8. `pao/workflow/driver.ts:18`、`pao/workflow/auto.ts:24` — 工作流层 import `../ui/glyphs`（bar/glyphFor/treePrefix）渲染常量，与 §27.1「工作流禁止直接写 UI 状态」字面冲突；glyphs 是零依赖纯函数、风险极低。建议：glyphs 迁 `shared/` 即归位。
9. `pao/knowledge/tools.ts:12`、`pao/knowledge/auto-route.ts:19` ↔ `pao/memory/session.ts:7`、`memory/resident.ts:18` — knowledge↔memory 互边：knowledge 借 `MemoryHit` 类型（type-only，运行时无环），memory 借 knowledge/outbound 的外发许可校验。建议：`MemoryHit` 类型迁 shared，外发检查归 memory 侧适配器。
10. `desktop/apps/desktop/electron/main.ts:16,23`、`electron/orchestration/orchestration-runtime.ts:7` — 桌面 main 同时走 `@pi-gui/pi-sdk-driver` 与 `@earendil-works/pi-coding-agent` 根包两条通道拿内核能力。均系公开 exports、方向合法，但双通道并存会稀释「桥接层是唯一通道」的约束力。建议：约定 main 进程对内核的业务调用统一收口 pi-sdk-driver，根包 SDK 仅限类型与扩展定义。

**正面确认**（无问题，值得保持）：worker→workflow 的注入式收口（`worker/dispatch-core.ts:37` 仅 type import，`worker/index.ts:20` 是装配层接线）；桌面 renderer 零越权；`contracts/` 契约目录自洽不外借；`pao/desktop/owners.ts` 的 owner 注册表限定「同进程只读活性信号」，未造跨宿主全局单例。
