# 定时改惰性＋用户态常驻（桌面壳即调度器）

- 日期：2026-10-02（深夜）
- 状态：已实施（架构 §16 改版、§19 加正交注记、M3 计划加桌面调度节）

## 为什么改

原 §16.2 定案「借 Windows 任务计划程序注册定时任务、到点起一次性 headless 会话」。三个问题在桌面路线讨论中暴露：

1. **系统注册项＝垃圾**（用户原话顾虑）：schtasks 注册项进系统、卸载残留、用户不可见——与项目「无常驻、关闭全停」的洁癖相悖。
2. **与运行时锁误伤**：桌面/终端单实例互斥定案后，桌面常开持有锁，凌晨定时 headless 会话启动即被拒——定时机制被互斥毁掉（首跑清单本来就是惰性的 session_start 扫描，不冲突；冲突只在独立定时会话）。
3. **真无人值守需求其实由桌面覆盖**：用户会常开桌面——桌面端开着时本来就是活进程，天然可当调度器。

## 新定案（用户拍板「用户态常驻就是我要的」）

- **v1（终端期）＝纯惰性**：session_start 顺带跑机械维护带（巡检阈值扫描/留档修剪/积压检查，几百 ms 内，超限分片轮转）。零定时注册、零后台进程。
- **v2（桌面期）＝桌面壳即调度器（用户态常驻）**：桌面开着时进程内跑轻调度——定时机械活（spawn headless 机械子会话，值守最小工具集＋登记红线）、文件监听实时通知（toast）、缓存预热。桌面关闭即全停，回落惰性。
- **三条铁律**：调度器只触发、状态真相在文件（不造第二真相）；机械子会话生命周期绑定桌面壳（R05 兼容）；桌面不是必需品。
- **锁语义精确化**：运行时锁＝交互运行时单实例（终端 TUI／桌面壳互斥）；worker 子进程与桌面 spawn 的机械子会话豁免。

## 被否方案

- **系统态常驻（daemon/服务）**：常驻的好处（无人值守/实时/热缓存）真实，但代价是生命周期工程（拉起/watchdog/热替换）、第二真相风险（内存活状态 vs 文件真相分家）、必须碰系统注册、权限窗口＝永远、静默失败——Hermes gateway 是实证。否。
- **借系统任务计划**：见上「为什么改」。任务模型资产（任务 json 字段/留档格式/登记红线/值守装载清单）保留，桌面调度器复用。
- **应用内调度库（node-cron/bree）**：依赖进程存活，违反 §1，维持否决。

## 业界对照

git `gc --auto`/brew cleanup 的惰性模式（v1 同款）；Claude/Codex 定时跑云端（pao 无云端不适用）；Claude Code/Codex 本地定时用 OS 调度器＝正是我们要避的系统注册路线。
