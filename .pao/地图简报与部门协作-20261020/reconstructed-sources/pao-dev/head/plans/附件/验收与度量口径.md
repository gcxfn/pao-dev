# 验收与度量口径

编制：2026-10-02。末次补记：2026-10-03。适用：M0—M3 与持续维护。

来源：需求 §6 的四指标与三组对照、架构 §2/§7 的回执和验收纪律。以下计算细节与样本建议是本轮实施补充，不是附件已有实测结果。

## 1. 哪些问题必须先修

发现以下情况，不以“其他测试多数通过”抵消：未验收就已交付；失败/取消前置误放行；旧尝试结果推进当前卡；不清楚副作用却自动重复写；覆盖用户原有改动；未经授权外发；重试/递归/并发失控；已取消或主会话关闭后受管任务继续执行；桌面与终端形成两个写 owner；过期/错误项目知识被当有效依据；知识内容改变工具权限。

以上只约束实际受影响、准备启用的功能。例如，自动巡库的问题阻止启用自动巡库；桌面双窗口的问题留到桌面实现时验证。普通修复不需要等待全部 M2/M3 功能、真实记忆写入或四种终端退出都验完。

检查围绕项目支持的入口、现有数据和能实际发生的情况。没有调用路径或使用需求的假设，不据此增加兼容层、权限框架或永久检查。已有关闭、取消机制被修改时，才补受影响的停止验证。

纯性能未改善不是安全失败；可保留功能但关闭成本过高的默认路径。未完成实测要写“未验证”，不能用跳过冒充通过。

## 2. 四项主指标

| 指标 | 定义 | 必须同时报告 |
|---|---|---|
| 完成情况 | 按冻结的任务验收逐项判定，交付后发现问题追加记录 | 总任务数、合格数、失败数、取消与环境阻塞；失败不可从分母消失 |
| 总完成时长 | 用户有效提交到最终验收的真实墙钟时间 | 排队、模型/工具、人工等待；内部耗时可另列但不能替代端到端 |
| 全角色用量/成本 | 主控、部长、worker、审查、补查、嵌入、重试、压缩/中继及维护的合计 | 原始 usage、规范化 token、已知实付/估算/未知、配置快照与价格日期 |
| 用户介入 | 任务启动后需要用户补输入、纠方向、选方案、授权、修复环境或救场的次数 | 类型与原因；必需授权不混同失败救场，起始任务描述不算介入 |

同时记录首次验收是否通过、打回原因、交付后缺陷、错误知识采用和未受控后台调用。这些诊断项解释主指标，不另外做综合“万能评分”。

四指标账 v1 的机械介入计数只含人工门、打回和分支裁决，不含用户自由插话。它是可自动获取的代理指标，不能替代上表「实际用户介入」。M2-07 对照需补记补输入、纠方向、环境救场等，分别注明机械／人工记录来源，不把缺失项填零。M1-07 原成本缺主控、币种不明，保留未知，不能直接作为完整对照基线。

## 3. token 与费用，避免算错

先保存供应商原始 usage，再做统一字段映射。不同接口的 input 可能包含缓存命中，也可能把 cache read/write 单列；必须按接口定义核对。

规范化总输入＝实际送入模型的全部输入，缓存命中是其中的分类；**不能不看上游定义就把 input＋cached 相加**。输出含不含推理 token 同理，不能重复加。

每个模型请求、重试请求、嵌入批次记录唯一来源标识，避免回执重复投递重复收费。模型回复里的自述 token 不作计量证据。

费用按实际端点和账号套餐核算。标注币种、价格版本、时间；不同币种不直接相加，没有汇率依据时分别报告。免费额度或订阅不意味着资源成本为零；现金支出与额度使用可以分列。

没有费用或 usage 就记未知；可以给带方法的估算，但不能把估算伪装成账单。失败、取消和中途断线也可能产生费用，未返回字段仍需在未知项列出。

## 4. 每项合格交付成本

同一批任务的总投入，包括合格和失败尝试，以及该批新增知识的整理/嵌入/复核费用，除以合格交付数。若合格数为零，结果写“不适用：无合格交付”，不写零成本。

父卡总额＝本卡直接费用＋各子项费用，子项只纳入一次。某份父回执已经带汇总值，就不能再把它与子回执全量相加。

既有库的历史建设投入单列；做冷启动比较时报告本批建库投入，做复用比较时报告增量维护投入。不要既把所有历史成本压到一个新任务，也不要永远不计知识维护。

“卡片 attempts”“模型 turns”“实际 API requests”分别统计。一次 worker 尝试可能包含多个模型轮次，每轮又可能发生接口重试；共同受在线宿主的上限控制。

## 5. 安全试跑额度与在途成本

每次调用前检查剩余额度和最大输出设置；并行前对可预计的在途上界做保守预留，收到结果后结算并释放。暂不为此做独立预算分配平台。

端点价格/输出上限不足以计算时，试跑需明确总请求、轮次和并发上限，并注明金额上限无法精确保证；没有用户认可的试跑额度，不自动开启付费扇出或大规模嵌入重建。

取消或超限意味着“不再发起新工作并尽力停止在途”，不宣称能撤销已经在上游产生的账单。

## 6. M2 三组对照

A：单 worker，不使用部门历史库；B：单 worker，使用同一冻结知识库；C：受限蜂群，使用与 B 完全相同的知识库。

三组都保留用户要求、项目 AGENTS、必要代码和任务规则，不能通过删掉 A 的必需资料人为抬高知识库收益。相同任务、相同起始代码快照、相同验收；模型档位和工具菜单先固定，另记真实物理路由。

建议先选 6 类代表任务：小 bug、明确小功能、已知模块维护、跨模块改动、资料/文档核验、知识不足或版本冲突。每类一项，三组共 18 次，作为**小规模初测建议而非统计充分性保证**。可在授权预算内缩小试验，但要说明少了哪些覆盖，不能据此得出普遍最优结论。

B/C 用同一版本知识库，不在跑一组后偷偷把其答案写入另一组。若知识库本身是这批任务过程中建立的，应单列学习实验，不能与冻结对照混为一谈。

分开记录冷启动和热会话/缓存；试验顺序交错。新建会话不自动等于上游缓存冷启动；无法控制或核实缓存时标“缓存状态未知”，按返回用量说明，不虚构清空缓存。模型输出波动或结果接近时，优先复跑争议任务，别为追求漂亮平均数无限追加实验。

## 7. 如何作启用决定

先满足正确性与控制门槛，再比较完成率、端到端时长、总成本和人工介入。不存在所有指标必须同时下降的先验承诺：并行可能用更高成本换更短时间，独立审查可能用更慢完成换更少缺陷，须把取舍明示。

对一种任务，若蜂群只是增加交接而无可观察收益，保留单 worker 常用路径。知识检索若主要返回错版本或无关条目，先修作用域/钩子/过期处理，不立刻加更多模型或向量数据库。

试运行期能记录平均数及中位数，但必须同时给样本数和单任务差异；只有几个样本时不做夸张的百分比保证。负面结果同样进入部门“评测”区。

## 8. 日常替代与退出旧工具

M1 的一条龙成功只证明最小链路，不等于已经完全替代 ZCode。M2 要按用户实际常做的任务种类逐类迁移，记录回退到旧工具的次数和原因；仍需保留旧工具处理的类别明确列出。

建议以连续一批真实日常任务进行观察，批量规模在开工时由用户确认；可以先用 10 项作为初始观察批次，不把这个建议当可靠性统计证明。关键不是凑数量，而是常用任务都真实使用、严重问题闭环且用户愿意继续用。

## 9. 证据保存

每个验收记录：任务/卡/尝试标识、代码或输入快照、环境与时间、实际命令/工具、退出码、期望与实际、原始输出路径、费用来源和结论。截图可辅助，不代替日志与可复跑步骤。

测试夹具、模拟错误和真实端点分别标记。测试库不混进正式部门库。脱敏后才纳入备份或版本控制；不用运行日志存明文密钥。阶段计划只引用证据，不抄整份日志。

执行证据须携带规范项目／卡路径、启动尝试与本次运行标识，跨项目同号、重启重新计数不得覆盖旧记录。回执使用启动身份，迟到结果仍归旧尝试。没有原始日志或费用来源时明确说明保存边界，不补造输出。

测试运行成功、失败集合比对成功、真实集成通过分开报告。基线检查覆盖文件加载失败、未处理错误、测试未跑完和全绿输出，原上游失败集合不扩大的门槛不降低。真实集成只按本次改动与实际启用范围补验，不用未开发功能扩大当前修复的出口。
