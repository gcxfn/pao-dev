# 通知与等待审查

> 2026-10-21 方向订正：以下源码与时间线证据保留。用户随后明确“主控派发后结束当前轮次，结果投递再唤醒”，因此本文增加模型等待工具的建议已撤回；没有模型等待工具本身不构成缺陷。现行处理方向以[主审查报告](../../../流程问题分级审查-20261021.md)第二节和架构§20为准：宿主保活、结果投递与唤醒、可查询停因及既有监督接线。以下“必须修”的分类是订正前审查意见，不作为实施指令。

## 结论

1. **卡 2 结束后并不存在 worker 卡住或锁等待。** worker 于 `13:52:01.245Z` 以 `exitCode: 0` 退出，共享锁在 `13:52:01.507Z` 释放，执行锁在 `13:52:01.508Z` 释放。主控直到 `14:06:17Z` 才手动交付卡 2，间隔为 14 分 16 秒左右。不能把 30 次 `sleep 300` 的请求时长相加后算成新增耗时；关键是这段时间里主控持续用睡眠轮询，没有及时取得或处置后台终局。

2. **当前契约没有“每张自动链卡完成就通知主控”。** 自动链只在整条链完成、停下或失败时发一条通知，见 `PAO/packages/coding-agent/src/pao/workflow/tools.ts:420-423`。本次卡 2 成功后，自动链因容器缺少 Git 基线而在越界核查处停下，见 `PAO/packages/coding-agent/src/pao/workflow/auto.ts:420-445`；按源码本应产生一条 `[自动链停下]` 通知。把“没有逐卡通知”当成本次故障根因是不成立的。

3. **可以确认“端到端没有及时生效”，但还不能确定通知具体漏在发送、动态注入、唤醒还是模型读取中的哪一步。** 主控 JSONL 从 13:52 到 14:06 没有 `pao-dispatch-notify` 动态消息，也没有 `有新的后台结果` 唤醒正文；主控直到 `14:06:05Z` 的睡眠返回后才从派发锁日志推断 worker 已退出。动态 `context_with_system` 内容不一定会写入 JSONL，因此现有证据不能证明通知正文没有进入某次请求，也不能据此断言模型明确看见后故意忽略。

4. **长睡眠是已观察到的重要等待问题。** 当前唤醒使用 `followUp`，不会打断正在执行的 bash；它要等 agent 不再发起工具调用时才被消费。主控在 13:50 到 14:01 连续发起 `sleep 300`，13:52 到达的通知可能因此至少等到下一次边界，而 14:01:05 到 14:06:05 的最后一次睡眠直接覆盖了发现终局前的主要时间。这个机制足以解释“通知已排队但未及时改变行为”，但本次没有事件级审计，不能证明通知一定已经排队。

5. **可以证明的代码缺口是：没有模型可调用的后台等待入口，也没有可跨轮查询的自动链停因。** `waitForAutoChain()` 已经存在，但只作为内部返回面供测试和收尾使用，见 `PAO/packages/coding-agent/src/pao/workflow/tools.ts:485-486`；主控模型只能固定睡眠并反复查看部分状态。因此，即使不能定位本次通知在哪一步失效，通知与等待流程仍有必须修复的可达缺陷。

## 必须修

### 1. 给主控提供可调用的后台等待，不再依赖固定睡眠

复用现有 `waitForAutoChain()`、`waitForBackground()`，提供一个有明确超时和返回状态的主控工具，例如“等待后台派发或自动链到下一个终局”。等待结果至少包含：

- 当前是否仍在途；
- 已完成、停下、失败或超时；
- 工作流、卡号、停因；
- 下一次进行人工处置的最小依据。

提示词同时明确：不能把 `in_progress` 当作 worker 仍活着，不能用 `sleep 300` 代替后台终局查询。

最小验收：使用 faux provider 和延迟假 runner，调用等待工具后，在自动链停下时工具及时返回；返回文本包含准确的停因和卡号。该测试不调用模型 API，也不冒充真实集成验证。

### 2. 持久化自动链终局与停因，并使查询能够恢复

当前停下原因只存在于 `AutoChainReport.stopReason` 和一次性内存通知中；链结束并从 `chainInFlight` 删除后，主控查询仍只能看到卡 `in_progress`。重启或通知漏投后，只能从锁和回执推断。

最小建议是把最近一次自动链的 `running / stopped / failed / completed`、时间、工作流实例、卡号、停因写入已有流程实例或独立运行态文件，并让 `pao_query_flow` 或盘点接口明确显示“后台链已停，等 owner 裁决”。

最小验收：构造“越界核查无法核对”的确定性测试，停链后查询立即显示具体停因；销毁并重新创建会话对象后再次查询，信息仍存在。文件只追加或原子替换，不能因通知消费而删除真相。

### 3. 为通知生命周期增加可核对的事件与失败处理

当前无法区分“没有调用通知”“主动唤醒发送失败”“正文注入后模型忽略”和“会话关闭前被清空”。现有 `unreadCount()` 也不足以定位阶段。

最小建议是给每条通知分配稳定 ID，并记录产生、唤醒请求、注入、消费和关闭丢弃结果。异步发送失败要能够在后台状态或日志里看到，不能只依赖一次性的控制台警告。该记录只需要覆盖通知生命周期，不需要建立通用事件框架。

最小验收：分别模拟发送正常、发送失败、正文已注入、会话关闭四种情况；每一步产生唯一且可追踪的记录，失败不会被显示成成功。测试须使用 faux provider 或纯函数替身，不调用模型 API。

### 4. 补齐长工具和 settle 边界回归测试

现有 `PAO/packages/coding-agent/test/pao/worker-notify-sdk.test.ts:20-89` 只覆盖 provider 响应回调期间产生通知，没有覆盖通知在长时间 bash 工具执行期间到达。`PAO/packages/coding-agent/test/pao/workflow-auto-chain.test.ts:720-735` 只检查通知缓冲文本，没有验证真实 `AgentSession` 是否被唤醒；`:1380-1400` 也只检查通知合并。`PAO/packages/coding-agent/test/print-mode.test.ts:94-140` 没有覆盖在途后台任务与 dispose 的关系。

至少补三类确定性测试：

1. 假 bash 工具运行期间通知到达，工具结束后下一次 provider 请求恰好看到一次正文。
2. 通知在 agent 准备 settle 时到达，产生一次 continuation，不能被 shutdown 清掉。
3. `--print` 存在已受理后台任务时，要么等待其收敛，要么明确返回稳定的“后台仍在运行”状态，不能静默 dispose。

## 优化

- **逐卡完成通知**：只有在产品明确要求“卡完成即可由主控处置”时才增加。当前自动链契约是整链终局通知；本次卡 2 后紧接着停链，所以优先修停链通知即可。
- **更清楚的状态表达**：自动链停下后，查询面可把 `in_progress` 旁边标出“链已停，等 owner”，避免模型将卡状态误当成进程状态。
- **压缩重复进度**：可把连续轮询整理成一条后台状态摘要，但不能替代终局通知或可调用等待。
- **Linux toast**：该容器中的 toast 无条件无效只能是旁路体验问题。没有任何证据表明它导致本次通知丢失。

## 实验配置与模型行为

- 容器没有可用的 Git 基线，导致自动链在每张成功卡后停在越界核查。下一次实验前应预检 Git 基线能力；这是实验准备问题，不属于通知代码故障。
- 卡 2 包含 6 条自然语言验收句，机械验收全过后按规则停给主控人工审核。这解释了为什么自动链本来也需要 owner 处理；但主控的处置时间仍应通过后台等待通知触发，而不是靠睡眠猜测。
- 主控当时只查看卡状态、日志尾部和锁记录，未使用可恢复的流程查询，也没有主动验证后台链是否在途。这属于模型/提示词造成的等待方式问题，但根因中仍有代码缺少等待入口和持久停因的缺口。
- 本次不能把 14 分 16 秒全部归因于 worker、锁或通知机制。13:52:01 后 worker 和锁已经结束；可确认的是后台终局没有及时转化为主控行动。

## 不确定性

- **未证实：通知函数没有执行。** 源码显示自动链停下后会调用 `notify()`，但真实运行没有通知生命周期审计。
- **未证实：通知正文完全丢失。** 动态 system section 不持久化；JSONL 只能证明没有 `pao-dispatch-notify` custom 消息，不能证明每次 provider 请求的系统上下文都不含正文。
- **未证实：模型收到正文后故意忽略。** 主控行为符合“没有看见或被延后”的情形，但不足以证明它已经看到。
- **未证实：某个单一代码分支就是本次唯一故障点。** 可证的是当前设计允许通知排队很长时间，并且缺少可调用等待、持久停因和阶段审计。
- 本次没有真实集成复测，也没有调用模型 API。后续验收应分别标注确定性的模拟测试和真实运行观察，不能用模拟测试替代端到端结论。
