# 自动工作流、验收与部门交接状态审查

审查日期：2026-10-21。范围限于自动工作流、机械验收、部门交接、单卡重派、审核启动与停止状态。未审题解，未调用模型，未读取隐藏测试，未修改产品、实验或运行逻辑。

## 结论

在已有证据能够确认的范围内，没有足够证据把当前源码中的工作流守卫列为“必须修”。

无 Git 时停链留 owner、工作卡无机械条目时停主控审、最后消息格式不合格时判 `unknown_outcome`，都是明确的 fail-closed（校验条件不足时停止，不把未知当成功）行为。卡3 的单卡重派走了受保护入口；依赖、实例、轮次、owner、暂停和写锁检查仍存在。卡3 attempt2 未结束时审核节点没有启动，属于正常等待。

本轮真正需要整改的是组织与准备配置：自动执行没有配出可自动推进的执行条件。产品侧另有一个尚未选定的能力缺口：执行已经产生真实结果，但最后一条消息漏交合法回执时，是否需要一个保留同一 attempt 成果的恢复入口。现有严格拒绝和不自动推进本身正常；恢复入口必须先核对同一 attempt 的幂等、重复终结和迟到回执边界，不能直接规定“运行器从代码围栏提取后自动追加”。

落盘流程状态为“挂起”而卡3 在运行，不能据此判暂停失效。`flow.状态` 是持久快照，查询视图会从卡状态重算；当前材料缺少重派后的 `pao_query_flow` 回包，因此只能确认“持久快照可能陈旧或与实时视图不同”，不能断言正确查询结果，也不能断言守卫被绕过。停止已另行确认：22:48:40 发起，22:52:42 确认，两个容器均已退出，`auto_resume=false`。

## 单卡重派、依赖与审核没有发现绕过

[日志检查结论.md](日志检查结论.md) 第13行记录卡3 从失败重置为待认领，再用 `max_attempts=2` 派发 attempt2；[nested-log-summary.json](nested-log-summary.json) 快照中卡1、卡2 已交付，卡3 为 attempt2、`in_progress`。

状态机允许 `failed → unclaimed`，实际重新认领为 `in_progress` 时递增 attempt（[statemachine.ts](../../../../../PAO/packages/coding-agent/src/pao/cards/statemachine.ts#L17)）；默认尝试上限为 2（[statemachine.ts](../../../../../PAO/packages/coding-agent/src/pao/cards/statemachine.ts#L25)）。失败卡不能直接用工具迁到 delivered，必须先重试或取消。

单卡派发最终进入受保护派发链。[dispatch-core.ts](../../../../../PAO/packages/coding-agent/src/pao/worker/dispatch-core.ts#L1195) 在取得写锁后、认领前重新核对工作流；[dispatch-context.ts](../../../../../PAO/packages/coding-agent/src/pao/workflow/dispatch-context.ts#L73) 核对实例、轮次、owner 和真暂停字段。认领时通过依赖门（[dispatch-core.ts](../../../../../PAO/packages/coding-agent/src/pao/worker/dispatch-core.ts#L391)），而依赖只有 `delivered` 才放行（[deps.ts](../../../../../PAO/packages/coding-agent/src/pao/cards/deps.ts#L64)）。现有证据没有显示“手动重派即自动视为依赖满足”。

审核节点要求实施节点的本轮拆解结束、所有卡 delivered，并在审核节点有 `pass` 或显式放行修复时才完成（[control.ts](../../../../../PAO/packages/coding-agent/src/pao/workflow/control.ts#L193)）。审核部长只在实施节点交付完成、审核拆解结束且尚未判定时才收到判定任务（[host-bridge.ts](../../../../../PAO/packages/coding-agent/src/pao/workflow/host-bridge.ts#L239)）。卡3 attempt2 运行中，审核保持未启动是正常等待。

## 只读守卫

工作流部长的工具门只放行 `read/grep/find/ls`、交工人卡、结束拆解、提交判定、读取判定包和请求裁定（[index.ts](../../../../../PAO/packages/coding-agent/src/pao/index.ts#L261)）；`bash`、`write`、`edit` 等被阻断。部门配方中的“工具”行主要约束工人派发，不决定部长会话自身的工具面（[catalog.ts](../../../../../PAO/packages/coding-agent/src/pao/dept/catalog.ts#L64)）。

这个限制确实较严。侦察与规划无法执行 `python3`、`ls` 之外的 shell 探测，因此包是否可导入、路径是否可写等会留给实施。但当前行为是 fail-closed，且没有发现只读部长因此修改产品。不能为了这次诊断直接放行通用 `bash`，否则会重新打开写文件、重定向和嵌套执行路径。若未来有反复出现的真实需求，应先设计专用只读入口，而不是放宽整个工具门。

## 最小验收点

1. 组织配置：运行时显示“自动交付”或“需 owner 核对”；无 Git 可以降级，但不能显示自动完整核对已通过。
2. 机械验收：机械验收写为 `跑:`、`存在:`、`包含:` 时可得到可定位命令、退出码或文件证据；只有人话条目时明确转人工。
3. 回执：格式无效可保持 `unknown_outcome`；若增加恢复入口，必须通过同 attempt 幂等、错卡或错 attempt 拒绝、重复终结留档、迟到回执留档和产物真实性检查。
4. 单卡重派：依赖未 delivered、owner 或实例不符、真暂停、轮次不符、写锁冲突都在认领前拒派。
5. 审核：实施未全部交付时审核不能启动；缺少验证证据时审核不能自动 pass。
6. 状态：实时查询和持久快照分别呈现；重派后查询与实际卡状态一致；旧快照不能被当实时闸门。
7. 只读：写工具、通用 shell、重定向、删除和网络写继续被阻断；若要新增入口，只能执行明确白名单中的只读检查。
8. 停止：`auto_resume=false`，两个容器已退出；停止后不得从旧现场自动续跑。
