### 4.1 P0：功能回归与状态机死路

#### D1. 工作流部长的监督确认闭环断裂，S3-5“删除无影响”不成立

这是本次审核最高严重度的发现。

事实链：

1. `WORKFLOW_MINISTER_TOOLS`（`role.ts:20-33`）的 12 项白名单里没有 `pao_ack_supervision`。
2. 但 `index.ts:574-577` 对所有 `role === "部长"` 调用 `registerSupervisionTools`；工作流部长也是“部长”，所以工具**实际被注册**。S3 记录 `:66` 写“该工具只由 host 模块注册……原白名单中的名字实际从未装配”，与代码相反。
3. 工作流部长启动时 `setActiveTools` 只启用 12 项白名单（`index.ts:464-471`）；`tool_call` 钩子对非白名单工具直接 `block`（`:477-481`，理由“工作流部长只读规划”）。所以 ack **已注册但不可调用**。
4. 监督提醒正文明确要求“逐个使用 `pao_ack_supervision(key="...")` 确认”（`host.ts:740-743`）；提醒投递成功后写入 `pendingNoticeKey`（`host.ts:764-765`、`state.ts:176-179`），`due()` 随后跳过带 `pendingNoticeKey` 的对象（`state.ts:191`），只有 `markHandled` 会清除（`state.ts:167-172`）。
5. 结论链：工作流部长收到首次提醒 → 按提示调用 ack → 被白名单钩子拒绝 → `markHandled` 永不执行 → 该对象在重新调度前不再提醒，计时也不重置。**提示语与权限自相矛盾。**

影响：工作流部长的周期监督确认闭环断裂；这不是“删掉一个未装配的工具”，而是把现有能力锁死。触发条件是“工作流部长收到周期监督提醒”，不是每个会话都会发生，但一旦发生就是静默失效。

建议（按成本从低到高）：

- 把 `pao_ack_supervision` 加回 `WORKFLOW_MINISTER_TOOLS`；`tool_call` 钩子会随之放行。这是最小修复。
- 或为工作流部长另设“远程回执”通路，不依赖本会话工具调用；但要同时改提醒文案与测试。
- 补一个**真实装配测试**：同时断言“工具已注册且已激活”，并断言 ack 后 `pendingNoticeKey` 被清除、对象重新计时。
- 订正 S3 记录 `:66`、测试注释 `workflow-minister-tool-policy.test.ts:82`、`docs/pao-supervision.md:28`。

#### D2. 关闭或异常暂停后，卡绑定待决无法继续办理

事实链（`control.ts`）：

1. `pauseControlIfUnpaused` → `setPause(..., preserveExisting=true)`：已有 `decision` 停因时，把它改成 `recovery_required`，同时保留 `pending` 和 `route`（`:1897-1904`）。
2. `assertPendingBinding` 对任何非 `decision` 停因直接报“实例已暂停或待恢复，不能办理待决”（`:2009-2010`）。所以 `resolvePendingOnce` 无法办理。
3. v3 `resumeControl` 遇到任一 `in_progress` 卡就拒绝恢复（`:2991-2992`）；若卡都已交付，则 `changeControlStop(flow, undefined)` 直接丢弃 pending（`:3010`），没有恢复 `decision`。

结果：关闭/异常本应“保留现场”，但保留的 pending 既不能被 `resolvePendingOnce` 办理，也不能经 `resume` 恢复；用户只能手工改卡或手工改控制文件。若产品定案是“关闭即放弃待决”，当前也应显式丢弃并记录，而不是留下一个不可办理的 pending。

**这不是纯源码推导，S7 的 F3-R-U 真实运行已经复现了前半段。** `F3-R-U/run.json` 的运行快照是 `control.status=挂起`、`stop.category=decision`，并带 `普通裁定:…:实施:1:卡0001:1` 待决；同一槽位的最终控制副本 `control/工作流实例-文稿修订流水线.md:179` 已变成 `recovery_required`、`:186` 理由是“主会话关闭，须显式人工恢复”、`:188` 仍保留该 pending。也就是说：跑完时是 decision+pending，关闭会话后变成 recovery_required+pending——正好落进上面第 2、3 步；“不能办理”由 `assertPendingBinding` 的源码判断证明，未在本轮补跑中实际调用办理器。F3-R-A 的最终控制副本同样在 `:170` 变成 `recovery_required`。

**这条是 S1/S2 验收记录没有披露的。** 建议：`resumeControl` 对 v3 pending 增加显式分支，二选一：

- 重新校验实例、节点、轮次、卡、attempt、截止和执行占位后，恢复 `decision` 停因并保留 pending；
- 明确标记 pending 已放弃，写入结果记录后清除。

无论哪种，都要有可审计入口，不能靠手工改文件；补“关闭 → 恢复 → 裁决/办理”的真实产品测试。

### 4.3 P1：代码与行为

#### D3. 交付/提交完成后重核失败，会留下“卡已交付、提交已存在、pending 仍在”的现场

`resolvePendingOnce` 在 review、卡状态改为 `delivered`、`deliverCard`/独立审核提交之后，phase 5 才在 `:2820-2862` 重新 `assertPendingBinding` 并用当前时钟执行 `assertStopAction`。

如果办理期间超过 deadline，`projectControlStop` 会把 expired 视为不可执行、actions 变成 `resume`；如果期间发生暂停或关闭，类别也不再是 `decision`。两者都会在**不可逆工作完成后**失败。此时 pending 仍在，卡已交付，Git 提交已存在；再次调用仍会因到点或暂停被拒，产品没有 reconciliation 步骤。

影响：数据一致性缺陷，可能产生孤立交付记录和重复提交风险；正常路径不受影响。S1/S2 记录未披露。

建议：在开始 review/交付前做一次完整的截止与停因预检；最终清场阶段对“已经提交但重核失败”定义可恢复结果（例如写 `submission_failed` 或进入人工核对阶段），不要要求重跑全部办理。补“办理过程中到点/关闭”的竞争测试。

#### D4. `pao_control_node action=rule` 的卡绑定分支缺少推进幂等门

对比 `tools.ts:778-803`（`resolve_pending` 分支）与 `:850-884`（`rule` 分支）：

- `resolve_pending` 在 `resolvePendingOnce` 后先检查 `待决办理.advance.status === "accepted"`，已受理只查询（`:778-785`）。
- `rule` 分支在 `resolvePendingOnce` 后**无条件** `tickWorkflowCore` 并 `markPendingResolutionAdvanceAccepted`（`:864-873`）。

同一 `rule` 请求重放时，`resolvePendingOnce` 会返回 `idempotent:true`，但工具仍可能重复推进工作流或唤醒下游。S2 关于“同 key 不重复唤醒”的结论不适用于这个分支。

建议：把 `advanceAccepted` 检查抽成两个分支共用的后置逻辑；重放且已受理时只读查询。补真实工具路径的 `rule` 重放测试。

#### D5. `requestRuling` 对已有 pending 只改 route，不重核 kind/卡/attempt/items

`control.ts:2185-2198`：已有 pending 时只检查 instance、node、round、phase、channel，然后合并理由并 `changeControlStop(decisionStop(next, "rule"))`；不调用 `assertPendingBinding`，不检查 `kind`、`card_ref`、`attempt`、`items`。

影响：一个“普通偏差”或“部长 hold”可以被改写成 route `rule`，登记阶段的结构化依据和卡绑定没有重新校验，停因语义被改写。`decideNode` 后续虽要求卡已 delivered，未必能直接放行 in-progress 偏差，但控制正本已进入不一致状态。

建议：已有 pending 分支复用 `assertPendingBinding`，要求 key、kind、card_ref、attempt、items 完全一致；不同 kind 或不同绑定直接拒绝。

#### D6. 桌面 `runReload` 重新加载扩展后没有过 PAO 守卫

`desktop/packages/pi-sdk-driver/src/session-supervisor.ts:1942-1956` 的 `runReload` 只调用 `session.reload()` 和 `syncRecordAfterSessionMutation`；guard 调用点在 `:980`（createSession）、`:1119`（forkSession）、`:2154`（createOrReopenRecord）。

内核 reload 会 `resourceLoader.reload()`，扩展错误只收进 `getExtensions().errors`，不抛出；reload 后没有再次调用 `ensurePaoBuiltinLoaded`。因此运行期重载（设置/命令触发）失败时会话继续存在，但没有 PAO，正是 S5 桌面守卫要避免的状态。

建议：reload 完成后调用同一守卫并升级为 `PaoExtensionLoadError`；补一条 reload 失败用例。

#### D7. 契约类型校验用 `String(value)`，数组可冒充合法字符串

`policy.ts:717-726`：

```ts
if (field === "result") return ["pass","change","reject"].includes(String(value)) ? undefined : "...";
if (field === "failure_axis") return ["card","dept_standard","both"].includes(String(value)) ? undefined : "...";
```

`["pass"]`、`["card"]` 等数组会通过契约校验。`rule` 动作下 `result: ["pass"]` 会先通过校验，人工通道还可能先弹出确认，随后才在 `decideNode` 被拒；`failure_axis: ["card"]` 配合 `result: "pass"` 可通过全部校验，并被原样展开写入 `node.判定`，与 `失败轴?: "card"|"dept_standard"|"both"` 的持久化类型不符。

影响：不会误推进流程，但契约不封闭、会留下脏数据或误导性确认。另：`status/results.ts:454` 用 `round: gate.round ?? 0` 生成确认建议，而契约要求轮次为 ≥1 的整数；缺轮次时用户按建议操作会得到参数错误。

建议：改为显式 `typeof value === "string"` + 白名单；补数组/对象用例；`results.ts` 缺轮次时省略 `round` 或从停因身份读取。

#### D8. worker 模块内注册中途抛错会漏收自己的资源

`worker/index.ts` 的顺序是：先订阅登记表（`:784`）、自建通知面（`:803-805`），再逐个 `registerTool`（`:1118-1136`），最后才定义 `dispose`（`:1167-1176`）并返回给调用方；调用方的 `teardown.add("worker-tools", ...)` 也在返回之后（`index.ts:596-610`）。

任一 `registerTool` 抛错时，`registerWorkerTools` 直接退出，`dispose` 不会被创建或登记，留下的包括：一个仍在运行的 unref 20 秒静默定时器、一条登记表订阅；单独使用且未传共享通知面时还会漏收自建通知缓冲。S5 的装配测试 ③ 只断言了 `index.ts` 侧 host 观察器的解绑，没有检查 worker 自己的这些资源。

影响：每次失败泄漏一组资源；长驻桌面进程反复失败会累积。这使 S5“半装配资源全部回收”的声明只对 `index.ts` 侧成立。

建议：在注册工具前先构造 `dispose` 并用 `try/catch` 或 `finally` 调用；或把资源清理登记提前到调用方 teardown；补真实断言。

#### D9. 预算拒绝的“下一步”提示会张冠李戴

`usage/dispatch-gate.ts:117-122`：

```ts
if (!reserved.ok) {
    const 未授权 = reserved.reason.includes("未显式给总预算");
    return { ok: false, kind: 未授权 ? "未授权" : "额度不足", reason: reserved.reason };

```

`reserveBudget` 的失败不止“额度不足”：`budget-ledger.ts:272-287` 还包括“同一判据指纹不符”（276-281）和“预留金额非法”（285-287），这些都落到 `kind: "额度不足"`，随后 `BUDGET_REFUSAL_NEXT`（`dispatch-gate.ts:200-203`）给出“等额度或让用户显式加额度”的错误建议。并发名额也用 `message.includes("并发名额已满")` 分类（`:104`）。

影响：真实触发条件较窄，但一旦触发，用户会按错误方向排查；更重要的是“分类事实”寄居在另一个模块的文案里，改文案就静默改行为。

建议：`reserveBudget` 返回 `code: "NO_GRANT" | "FINGERPRINT_MISMATCH" | "INVALID_AMOUNT" | "INSUFFICIENT"`；`shared-budget` 抛带 `code` 的错误；`dispatch-gate` 按 code 映射 kind，不再读文案。

#### D10. S6 批量读取把全部内容驻留内存，32MiB 预算不约束总峰值

`dispatch-brief/workspace.ts:303-310` 的 `batchContents` 把每个 chunk 的对象内容放进 `Map`；`readFileStates` 读完所有文件后才逐个计算 sha256（`:365-374`）。旧实现是逐文件 `fileState`，处理完即可释放。

32MiB 只限制单次 `cat-file --batch` 的输出，不限制最终驻留总量。覆盖范围大或仓库文件大时，峰值内存约为所有 head/index/worktree 内容之和，可能 OOM；现有性能与边界用例只测进程数和时间，未测内存。

建议：按 chunk 取回后立即算 head/index 摘要，只留 size/digest；或设总字节上限，超出走逐文件回退。
