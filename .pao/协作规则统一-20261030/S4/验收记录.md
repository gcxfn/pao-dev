## 经过与协议选择

**为什么查询放工作流模块。** 控制正本、冻结配方、v2 标记的解释权本来就属于工作流模块；执行侧只需要“这个对象现在是哪种状态、位置在哪、active 时投给谁”。新增的 `WorkflowSupervisionQuery` 接口只有两个方法（`resolveRoute`、`position`），返回 `WorkerSupervisionState = "active" | "waiting" | "stale" | "unknown"`、`reason`、`location` 和 active 时的 `route`，不暴露 `ControlStop`、裁定通道或动作权限。没有把这套结构再复制到执行侧当类型用，也没有让执行侧读一半控制结构。

**类型归属先修正。** `WorkflowDispatchContext` 原先定义在 `workflow/dispatch-context.ts`，执行侧 `worker/dispatch-core.ts` 以 type-only 引入——这正是“以 type-only 为由继续泄漏整个控制结构”的入口。本轮把最小字段定义移到 `worker/dispatch-types.ts`，`workflow/dispatch-context.ts` 反向再导出保持既有导入面，执行侧从自己的归属处引用。B7 门禁连 type-only 一起查，避免以后又走回去。

**为什么 unknown 不是 waiting 也不是 active。** 等待裁决（暂停、待裁定、已交回执待审核）有明确等待位，才允许 `waiting`；控制正本损坏、身份标记损坏、缺卡路径、缺部长会话这类“无法确认”必须是 `unknown`。`unknown` 不产生 active 路由，不做回执投递目标，但保留 `running: true`、`supervisionState: "unknown"` 和带位置的 blocker 文案，宿主因此仍把它纳入 20 秒扫描与 15/30 分钟提醒，而不是悄悄从快照里消失、更不会被当成完成。`waiting` 和 `stale` 则退出当前“运行中”监督：暂停或待裁定的工人不被报成持续执行。unknown 首次出现时快照键会加 `unknown:` 前缀（`supervision.ts:247`），该对象的提醒计时从降级时刻重新开始，属于“状态变坏要重新提醒”的有意行为，不写回任何控制文件。

**装配层只做一次判断。** `pao/index.ts` 的 `resolveSupervisionRoute` 先问工作流查询，返回 undefined（普通卡或 v1 卡）再回退本地部长规则。这个回退留在装配层，执行侧不知道工作流存在，工作流模块也不知道工人登记表。扇出回执直接用同一查询的 `resolveRoute`，不再各自拼路由。边界范围要说准：B7 检查的是 `worker/supervision.ts` 的执行闭包（`supervision`、`registry`、`runner` 及其下游），不覆盖 `worker/index.ts`——后者是工人工具的装配面，保留着既有的 `resolveWorkflowDispatch` 引用（`worker/index.ts:61,920-925`，T02 装配注入），与 `pao/index.ts` 同属“可以同时引用两侧”的层，不是 S4 新增反向依赖。

**桌面为什么只加投影。** 内核 `controlView` 早已输出统一 `停止`；桌面缺的是“把它送到渲染层”。driver 只声明只读的 `PaoFlowStopProjection`，主进程 `normalizeStop` 对类别、权限、动作、身份做逐字段校验，缺字段或未知值显式 throw（失败可见，不猜）；契约给 `WorkflowControlStop` 和唯一的 `workflowControlCanResume(control)`；运行控制与卡片视图都改用它，卡片模型的业务状态先读 `stop.category`，只有旧 v1 清单没有 `stop` 时才回退原来的 `hold`/`pauseReason` 文本判断。驱动和渲染层都没有新建可独立写入的流程状态缓存，只读透传。

**门禁为什么要反例。** 只加“当前代码没有违规导入”的检查，无法证明检查本身有效。`assertB7SelfTest` 在系统临时目录写一个 `worker/supervision.ts` 故意 import type 的 `../workflow/control.ts`，走同一套 `walkClosure` 与同一过滤条件；抓不到就判自检失败。反例证明的是检查器的有效性，不是产品的行为。

## S4-1 窄查询的判定规则

`resolveWorkflowSupervisionPosition`（`supervision-query.ts:163-217`）按顺序判定：

1. 卡面不含 `pao-workflow` → undefined（普通卡沿旧规则）；含标记但非 v2 → undefined（v1 旧卡保持原有监督规则）。
2. v2 标记或身份解析失败 → `unknown`，原因“工作流 v2 身份标记损坏”，保留卡号/卡路径。
3. 缺 `entry.card_path` → `unknown`，保留实例/节点/轮次。
4. 控制正本读不到/冻结配方损坏 → `unknown`，原因取错误文本，位置仍保留。
5. 实例、节点轮次、卡号任一不符 → `stale`（“当前卡已不属于控制正本的实例/节点/轮次”）；登记的 `supervision_owner` 与控制正本 owner 不符 → `stale`。
6. 有停止原因（`flow.停止.reason`）、暂停或待裁定 → `waiting`，原因取统一投影文本。
7. 本卡当前 attempt 已有回执 → `waiting`（“已交回执，等待部长审核”）；同节点其他卡的回执不影响仍在运行的兄弟卡。
8. 非直接执行且节点尚未绑定部长会话 → `unknown`。
9. 其余 → `active`，附 `routeFrom` 生成的真实部门/脉络/owner/节点部长/轮次路由。

`resolveWorkflowSupervisionRoute`（`supervision-query.ts:145-157`）用于派发与回执：非 v2 返回 undefined；身份损坏、实例/节点/轮次不符、已暂停/已登记裁定、非直接节点且未绑定部长会话都 fail-closed 抛出；成功才返回带 `binding.source = "workflow"` 的路由。v1 卡不读不存在的控制正本。

边界内的残留：装配层漏注入查询时，`supervision.ts:290-303` 仍用字面量 `card.body.includes("pao-workflow-v2:")` 判断“这可能是 v2 卡”并转 unknown。它不做标记解析、不提取身份、不读控制正本，只是无查询时的 fail-closed 安全网；生产装配始终注入查询，真正的标记解释仍在 workflow 模块。保留这条字面量是为了让“查不到”不落入“按普通卡默认运行”。

## S4-3 桌面同源细节

- 内核：`controlView` 在存在 `flow.停止` 时输出 `停止: projectControlStop(...)`（`workflow/control.ts`），类别有五类：`decision`、`manual_pause`、`recovery_required`、`terminal_block`、`legacy_unknown`；动作为 `rule`/`resolve_pending`/`resume`；权限为 `owner`/`human`。
