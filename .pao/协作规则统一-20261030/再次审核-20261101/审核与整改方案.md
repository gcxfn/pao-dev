## 2. 主要问题

### R1：关闭或暂停后，保留的待决没有完整恢复通路（高；旧 D2）

**触发与影响：** 卡绑定待决登记后，关闭宿主或暂停会保留 pending，却把停止类别改成 `recovery_required` 或 `manual_pause`。办理入口只接受 `decision`。v3 的 `resumeControl` 遇到仍为 `in_progress` 的卡直接拒绝；卡若已交付，则普通恢复又会清除整个停因，连带清掉 pending。用户无法用现有恢复动作可靠地接续原办理过程。

**证据：** `PAO/packages/coding-agent/src/pao/workflow/control.ts:1886`（setPause）、`:2009`（assertPendingBinding）、`:2947`（resumeControl，尤其 2991、3010）。v2 迁移已有保留待决分支，v3 没有等价处理。身份探针也实际观察到 shutdown 后办理被恢复守卫拒绝，但本轮未完整实跑“关闭→人工恢复→办理”。

**最小整改：** 为 v3 带 pending 的恢复加入明确分支：核对 owner、卡 attempt、执行占用与已持久化办理阶段，再恢复对应待决或进入明确的人工核对结果。保留 pending 的身份、原决定和已发生提交事实。卡状态 `in_progress` 不足以证明进程仍在写；恢复也不能仅凭用户说明跳过真实占用检查。

**验收：** 分别覆盖办理前关闭、已 delivered 后关闭、已 submitted 后关闭；未停止写者时拒绝，确认停止后可以接续，原决定不丢失且不重复交卷。

### R2：办理已生效后，到期或暂停可能阻断最终收尾（高；旧 D3）

**触发与影响：** `resolvePendingOnce` 分段执行验收、卡交付、Git 交卷，最后才再次检查当前停因与时间。若中途到期或暂停，最后检查可能拒绝，留下“卡已 delivered、交卷已存在、pending 仍在”。后续普通办理也可能被过期或恢复守卫挡住。

**证据：** `workflow/control.ts:2519` 起的办理过程；约 2703 改卡状态、2750 交卷、2820 最终锁内核对、2858 当前动作检查。源码路径成立，本轮未注入提交完成后恰好到期的竞争。

**最小整改：** 区分“尚未执行副作用”和“副作用已持久化”的恢复规则。前者可因截止拒绝；后者应核对已有交付对象、回执与办理记录后收尾或进入可操作的人工核对，不能只留下通用错误。收尾不等于允许继续派工，暂停仍应阻止新的执行。只增加一次办理前截止检查不能解决此问题。

**验收：** 在 delivered、submitted、pending_cleared 各边界注入到期、暂停和重启；最终要么完整完成，要么明确等待核对且可恢复；提交对象只产生一次。

### R3：卡绑定 `rule` 忽略显式 node/round（高；本轮补充）

**触发与影响：** 模型工具或 `/pao flow control` 调用 `action=rule`，传入错误节点或过期轮次，只要当前存在卡绑定普通裁定，入口就取当前 pending key 办理，忽略请求中的 node/round。陈旧请求可能被应用到当前待决。

**证据：** `workflow/policy.ts:630` 明确“提供时必须一致”；`workflow/tools.ts:819` 只比较 instance，`:823` 构造 identity，但 `:850–861` 的卡绑定分支不使用它。`resolvePendingOnce` 只收到 pending_key、decisions、basis，无法补查被丢掉的请求身份。桌面三动作入口另有节点/轮次核对，但没有覆盖这一 rule 工具路径。

**验证限制：** 子代理运行正确身份、node=不存在、round=999 三组探针，三者都进入相同的恢复守卫。由于夹具提前 `bridge.shutdown()`，正确输入也失败，未直接验证错误身份完成交卷。源码缺口已确认，动态终点未验证。

**最小整改：** 在卡绑定分支把显式 instance/node/round 与选中的 pending 一致性核对；将核对与选中待决的办理入口绑定，避免校验后重新读取了另一个 pending。不要简单禁止原契约允许省略的字段。

**验收：** 经真实工具入口测试正确值成功，错 node、错 round、错 instance 在副作用前拒绝；控制文件、卡状态和 Git 引用不变；补一个旧请求遇到新待决的用例。

### R4：`rule` 清除待决后，推进失败会失去原重试入口（高；订正旧 D4）

**触发与影响：** 卡绑定 rule 先完成办理并清除 pending，再调用 `tickWorkflowCore`。如果此时推进失败或取消，同一 rule 重试已经找不到 cardPending，会转入普通节点裁定路径；直接任务没有部长会话，因而报“裁定须指定当前节点与三态结果”。已有交付无法通过原请求继续完成推进受理。

**证据：** `workflow/tools.ts:850–887`；`resolve_pending` 路径约 768–817 会利用办理记录及 advance 状态。源码确认，本轮未做 rule 的推进失败注入。

**订正：** 上一份报告把重点写成“缺幂等门导致重复推进”。本轮更明确的结论是清 pending 后原 rule 路径不可重入。不能声称已复现重复唤醒。

**最小整改：** 让卡绑定 rule 能通过稳定身份找回原办理记录，复用 `resolve_pending` 的推进受理后置逻辑。仅抽一个 `advanceAccepted` 函数不够，还必须解决清 pending 后如何定位原记录。避免以“当前最新记录”代替精确身份，否则可能误接新一轮任务。

**验收：** 清 pending 后注入推进失败；相同请求可恢复到 accepted，交付和 Git 提交不重复；相同身份不同依据拒绝，陈旧请求不影响新轮次。

### R5：到期处理入口不全，查询与执行对可用动作判断不一致（高；旧 E10 应转为整改）

**触发与影响：** 部长 `requestRuling` 登记的待决没有接入同样的截止调度；宿主重新接管已有停止实例时也不重建 timer。查询投影没有传当前时间，因此尚未被调度写成终止事实的过期待决仍显示可 rule；实际执行使用当前时间而拒绝。

**证据：** `workflow/control.ts:2152` requestRuling；`workflow/host-bridge.ts:222` 调度、`:618/:657` 两个卡回执登记入口、`:831` drive 在已有停止事实时返回。`control.ts:908`、`status/workflow-instances.ts:370`、`host-bridge.ts:307` 的投影调用未传 now。计划 S2 明确要求判断请求接到期调度，故不只是可选优化。

**隔离实跑：** 主代理调用真实 `projectControlStop`，同一个已过 deadline、phase 仍为待处理的普通裁定，在 now=undefined 时返回 owner/`rule`；传入 2026-11-01 当前核查时间后返回 human/`resume`。这是纯策略实跑和调用链核对，不是完整桌面实机验证。

**最小整改：** 所有待决登记入口使用现有调度机制；宿主接管时从持久状态重建，按稳定 key 去重，按总预算与待决截止取更早时间。读面显式传入同一轮查询时间，只做投影不写盘。恢复动作的可执行性与 R1 同批解决。到期业务结果不能冒充写者停止证明。

**验收：** 部长判断、卡偏差、直接任务裁定分别测试运行中到期和重启后到期；查询动作与执行策略一致；停止写者尚未确认时仍禁止新写者接手。

### R6：工作流部长注册了监督确认工具，却无法调用（中；旧 D1）

**触发与影响：** 工作流部长收到要求使用 `pao_ack_supervision` 的监督提醒，但该工具不在专用工具白名单，既未进入活动工具集合，也会被 tool_call 守卫阻止，确认提醒的闭环断裂。

**证据：** `PAO/packages/coding-agent/src/pao/role.ts:20` 的 `WORKFLOW_MINISTER_TOOLS`；`index.ts:478` 守卫与 `:574` 注册；`host/tools.ts:62` 注册实现及 remoteReceipt、`:129` 父宿主回执处理。源码确认。

**最小整改：** 加回工作流部长白名单，复用已有 remoteReceipt 及父宿主确认逻辑；无需再设计专用确认协议。同步订正文档中“删除无影响”的结论。

**验收：** 真实扩展装配下工具已注册、已激活且调用可通过；父宿主收到对应会话及 key 的确认后清除原提醒，旧 key 不能清除新提醒。

### R7：桌面重新加载未执行同样的 PAO 装配守卫（中；旧 D6）

**触发与影响：** 会话创建、fork、恢复有 PAO 必需扩展检查；已有会话 reload 后若资源加载器收集了 PAO 装配错误，`runReload` 仍继续同步会话，可能把缺少 PAO 能力的会话当作已重新加载成功。

**证据：** `desktop/packages/pi-sdk-driver/src/session-supervisor.ts:1942–1956`，reload 后直接 sync；相同文件 `:2270` 提供已有守卫。源码确认，未重跑 Electron 故障注入。

**最小整改：** reload 后、更新成功状态前复用装配检查，按当前会话生命周期中止或标记失败，保留可诊断原因。另核对 `pao-extension-guard.ts:50`：读取加载错误时异常被转换为空数组，不应把真实读取失败等同于无错误；需区分已声明支持的运行时与测试替身。

**验收：** 创建和 reload 对同一 PAO 加载失败给出一致拒绝结果；正常 reload 成功，非 PAO 可选扩展的既有处理不改变。

### R8：worker 注册中途失败可能漏释放本模块资源（中；旧 D8）

**触发与影响：** worker 模块在工具注册前后已持有宿主订阅等资源，但 dispose 直到注册流程后段才构造并返回。中途 registerTool 抛错时，上层拿不到本模块释放函数，外层逆序清理无法覆盖这些资源。

**证据：** `PAO/packages/coding-agent/src/pao/worker/index.ts:1090–1193`，1118 起注册，1168 才构造 dispose，1192 返回。源码确认，未作本轮资源泄漏计数测试。

**最小整改：** 在资源建立时立即登记清理责任，失败路径释放已建立资源；成功时把同一释放函数交给宿主。不要在成功返回前无条件 finally 清掉仍需使用的资源。

**验收：** 逐个注册点注入失败，断言此前创建的订阅、通知面、定时器和退出钩子均已释放；重复释放安全，原始装配错误不被掩盖。

### R9：相同待决并发办理，第二个调用返回阶段冲突（低；本轮实跑）

**触发与影响：** 同进程同时调用两次相同 `resolvePendingOnce`，一次 completed，另一次报“当前阶段为 delivered，不能写入预期阶段”。最终卡 delivered、pending 清空、办理 completed，但重复调用者看到失败。

**隔离实跑：** 子代理使用真实控制文件与 Git、模拟完成回执执行 `Promise.allSettled`。Git 全引用提交数 1→3；新增为 input boundary 和一份交付提交。单次对照同样增加 2，未发现重复交卷。主代理读取了结果文件。该探针不证明跨进程并发安全。

**最小整改：** 同 key、同输入的调用协调为共享结果，或竞争后重读办理阶段并按已生效事实返回；不同输入仍拒绝。优先利用现有锁及记录，不引入通用任务框架，也不要把整个含外部执行的流程塞进长期文件锁。

**验收：** 同输入并发均得到可理解的一致结果、只有一份交付；不同输入并发明确拒绝。此项优先级低于恢复死路，不能据此声称已有数据损坏。

## 5. 后续优化

1. **地图读取按批摘要。** `dispatch-brief/workspace.ts:318` 的 readFileStates 在全部批次内容返回后才逐路径处理，32MiB 只限制单批输出。先测代表性仓库的峰值内存、耗时和 Git 进程数，再把消费者只需摘要的内容按块处理、按 oid 复用摘要。需保留 Git 固定树与工作区内容核对、换行路径、非 blob 和大对象路径。不能只优化内存而破坏一致性。
2. **提取实际重复的完成步骤。** 待决办理与 post-dispatch 的权限和恢复时序不同，不强制合成一个大函数。优先共用已验证的验收、交付、交卷结果核对与推进受理步骤，各入口保留自身策略。
3. **逐步统一字段元数据和理由码。** 七动作 policy 已集中，但 schema、字段清单仍有重复；在本轮触及字段时收口真实重复。会影响权限或分类的分支使用结构化理由码，展示文字只负责说明。无需建立通用协议生成框架。

以上优化应在高优先级恢复问题关闭后进行；没有性能测量结论，不把地图优化列为发布阻断项。
