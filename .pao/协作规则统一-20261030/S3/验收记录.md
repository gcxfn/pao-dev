## 经过与协议选择

原 `pao_control_node` 的 schema 把所有字段都设为可选，执行器在 `loadRecipeFor` 之后才检查少数字段组合；工具描述是一段手写自然语言，与执行校验没有共同来源。这样既无法在读取业务资源前拒绝错误参数，也会让工具描述、状态提示和宿主提示各自维护一份手续说明。

本轮选择在 `policy.ts` 新增动作契约表作为唯一来源：`NODE_CONTROL_ACTION_CONTRACT` 记录每个动作的必填、可选、禁用字段、身份来源、权限和合法调用例；`validateNodeControlInput` 用它校验，`nodeControlDescription` 用它生成工具描述，`formatNodeControlInvocation` 用它生成固定手续提示。没有另建第二份校验器，也没有把校验逻辑复制到状态或宿主模块。

供应商适配没有为 `oneOf` 新增模型供应商分支。工具根 schema 仍为扁平 `Type.Object`，`action` 是七种字面量的联合；`prepareArguments` 只修正模型常见形状（动作空白、`round` 数字字符串、`decisions` JSON 字符串），不改变字段契约。当前适配器直接接受对象参数，因此始终保持扁平对象，不输出联合结构。

身份抄写方面，`resolve_pending` 仍要求完整 `pending_key` 和逐项 `decisions`，不要求 `instance/node/round/attempt`；其他动作的 `instance/node/round` 可省略，由当前控制正本和停因身份补足，显式提供时仍需一致。这样保留旧待决编号的陈旧保护，也没有放宽拒绝旧轮次、旧实例决定所需的身份检查。

## 动作契约

代码正本是 `PAO/packages/coding-agent/src/pao/workflow/policy.ts` 的 `NODE_CONTROL_ACTION_CONTRACT`；下表只解释，不替代源码。

| 动作 | 必填 | 可选 | 禁用 |
|---|---|---|---|
| confirm | name | cards_dir、instance、node、round、reason | result、failure_axis、references、target、prev_owner、pending_key、decisions |
| pause | name、reason | cards_dir、instance | node、round、result、failure_axis、references、target、prev_owner、pending_key、decisions |
| resume | name、prev_owner、reason | cards_dir、instance | node、round、result、failure_axis、references、target、pending_key、decisions |
| reopen | name、node、prev_owner、reason | cards_dir、instance、round | result、failure_axis、references、target、pending_key、decisions |
| rework | name、node、target、reason | cards_dir、instance、round | result、failure_axis、references、prev_owner、pending_key、decisions |
| rule | name、reason、references、result | cards_dir、instance、node、round、failure_axis、target | prev_owner、pending_key、decisions |
| resolve_pending | name、pending_key、decisions | cards_dir | node、instance、round、reason、result、failure_axis、references、target、prev_owner |

身份与权限：confirm 只确认不推进，须界面人工确认；pause 由主控 owner 执行；resume 须 `prev_owner` 和界面人工确认；reopen 须节点/轮次/原处理人与现场一致并界面确认；rework 的 node 必须是当前审核节点且受回边限额约束；rule 须人工确认且 `result=pass` 才能通过，非 pass 必须给 `failure_axis`；resolve_pending 的身份全部从控制正本读取，只按完整待决编号逐项办理。

## S3-2 校验前移与字段错误

`PAO/packages/coding-agent/src/pao/workflow/tools.ts:764` 在 `loadRecipeFor`（同文件 765 行）、`buildDriverOptions` 和任何写入前调用 `validateNodeControlInput(params)`。该函数是纯函数：不读配方、不读控制文件、不读卡目录，不产生副作用。错误按字段逐项报告，包含未知 action、未知字段、禁用字段、缺少必填、字段类型、`decisions` 项结构/重复 `item_ref`，以及 `rule` 非 pass 缺 `failure_axis`；非法调用不会进入配方版本检查或文件读写。

`resolve_pending` 的额外白名单在字段契约层先拒绝 `instance`、`node`、`round` 等身份字段；其他动作带 `pending_key` 或 `decisions` 时统一提示只能配合 `resolve_pending`，并提示重查 `pao_query_flow`、原样使用完整待决编号。原有 `attempt` 等历史混用字段按未知字段拒绝，不再默认落到最近的动作。

## S3-3 供应商适配与格式转换

`PAO/packages/coding-agent/src/pao/workflow/tools.ts:753` 的 `prepareArguments` 调用 `prepareNodeControlArguments`（`policy.ts:811-823`）：只修剪 `action` 首尾空白、把纯数字字符串 `round` 转为整数、把 JSON 字符串 `decisions` 解析为数组；对象参数始终原样返回。`policy.ts` 导出的 `NODE_CONTROL_ACTIONS` 同时用于 `Type.Union` 的七种 `Type.Literal`；根 schema 是对象，不生成 `oneOf`，也没有为任意供应商增加分支。`workflow-control-action-contract.test.ts` 第 4 个用例覆盖形状修正与字段契约不放宽。

## S3-4 身份与减少抄写

`PAO/packages/coding-agent/src/pao/workflow/tools.ts` 在非 `resolve_pending` 路径读取当前控制正本后组装身份：`实例 = params.instance ?? control.实例`，`节点 = params.node ?? control.停止?.identity?.node`，`轮次 = params.round ?? control.停止?.identity?.round`；显式 `instance` 与正本不一致时仍报「节点控制实例不匹配」。`resolve_pending` 的 `PendingResolutionInput` 仍只有 `pending_key` 和 `decisions`，真实工具会在控制锁内核对完整待决编号和逐项项号；旧 `pending_key` 仍由 `planPendingResolution` 拒绝，不能被新动作绕过。

`rule` 的 `reason`/`references` 继续走原 `decisionFieldProblems`；`resume`/`reopen` 仍要求 `prev_owner` 和现场核查说明；`rework` 仍要求当前审核节点和目标回边，回边次数不被重置。减少的是调用方抄写，不是执行侧身份和证据校验。
