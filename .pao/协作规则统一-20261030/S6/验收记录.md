## 经过与协议选择

1. **方案 A 而非 B**：两种候选——A 用 `cat-file --batch-check` 取身份、`cat-file --batch` 取内容；B 用 `ls-tree`/`ls-files --stage` 先取 oid 再批量取内容。选 A：一次 `--batch-check` 同时得到存在性、类型、oid 与 size，而 B 需要再跑一轮才能拿到类型和大小，且对工作区/索引差异的处理更绕。裁判标准是 artifact 逐字节等价，A 在 36/36 用例上满足。
2. **只保留三种回退**：回退必须「准确触发条件 + 有用例」，否则违反 §12.3-2 的「不能所有情况都回退旧实现」。三个条件都写进 `batchReadFallbackReason`/`batchObjectTooLargeForRead` 并有专门用例（gitlink 对象存在时真实触发逐文件老命令；64MiB 整条触发回退并断言老命令出现）。
3. **S6-3 只做 prepare 内部一处**：侦察发现唯一可合并项是 `brief.ts:532` 与 `:572` 的同参数身份读取（同栈、中间无副作用）。另一候选「prepare→freeze 跨阶段传递复用」被驳回，理由：§12.2 原文限定「一次 prepare 内部」；freeze 的「准备与冻结之间已变化」检测点会永久失活；§12.2 交付要求明写「不能把派发前重验省掉」；S6-2 之后单次采集已是常数进程，收益远小于在安全关键路径引入跨阶段状态的风险。
4. **批量失败一律 fail-closed**：任何「数量/格式/长度」不符都抛 `missing_input`，并让 `readFileStates` 在缺状态时抛错。宁可本次采集失败，也不允许用一半新一半旧的数据生成可用地图（§12.2 S6-4 原文）。
5. **MF-1 用回退修复而不是提高上限**：审计发现单对象 64MiB 临界时旧实现仍能成功、新实现因 `--batch` 头部超出 `maxBuffer` 报 ENOBUFS。修复方式是「超阈值的单个对象回退逐路径老命令」，而不是提高 `maxBuffer`——保持与旧实现相同的上限语义，也满足 §12.3-6「不提高任务预算与测试超时」的精神。阈值取 `64MiB − 8192`，给每对象头部留足余量。
6. **SF-1（对象损坏仓库）记录不修**：head blob 损坏时旧实现会产出「空内容」的摘要，新实现按缺失处理。改为旧行为需要逐文件 `cat-file -e`，会把批量化收益抵消掉；新行为是 fail-closed、更诚实，故作为已知差异登记。
7. **格式化与等价证明**：最终验证批首跑只有 biome 格式门禁失败。用 `biome format --write` 只做格式，随后用 TypeScript 编译器 API 把两版解析成「节点种类 + 字面量语义值」比较，7322 节点 / 129097 规范化字符完全相等，证明格式化无逻辑变化；bench 侧另有去空白归一后逐字节相同。
8. **复测口径**：先跑「旧基线 5 次」，再跑一次受控复测（对照组），再因源码被 biome 格式化而重跑最终轮。三轮原始数据全部保留，判定只用「最终源码 + 安静窗口」那一轮；测量期间源码被编辑的一轮明确标记作废。
