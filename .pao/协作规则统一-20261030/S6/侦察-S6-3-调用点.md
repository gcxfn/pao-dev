## 3. 裁决与实施（2026-10-31）

### 3.1 已实施（批准项）：prepare 内同参数 Git 身份读取合并

**改动位置**：`PAO/packages/coding-agent/src/pao/dispatch-brief/brief.ts:572-578`（唯一改动文件；仅 1 个 hunk，+6/-1 行）。

```ts
// 任务根与执行根指向同一真实目录时（普通主工作树派发），第二次 Git 身份读取与第一次同参同值；
// 两次读取之间只有纯校验、没有写盘/派发/等待，因此直接复用本次操作内已采集的同一份结果。
const projectGitIdentity = gitIdentity.ok
	? sameRepositoryPath(projectRoot, executionRoot)
		? gitIdentity
		: tryReadGitIdentity(projectRoot)
	: undefined;
```

**为什么等价**：
- `projectRoot`/`executionRoot` 在 `brief.ts:530-531` 已各自 `realpathSync`；`sameRepositoryPath`（`workspace.ts:552-557`）做 `\`→`/`、去尾斜杠 + `pathKey` 归一比较，为真即同一真实目录 → 第二次 `repo()` 与第一次同参、同值。
- 两处之间（`:533-571`）只有 managed 证明校验与 commonGitDir 比较，全部是纯内存判断，**无写盘/派发/等待**，Git 状态不可能变化。
- 失败语义不变：第一次 `!ok` 时 `projectGitIdentity` 仍为 `undefined`（与改动前 `gitIdentity.ok ? ... : undefined` 完全一致）；第一次 `ok` 时复用对象同样是 `{ok:true, repositoryRoot, commonGitDir, head, treeId}` 结构，后续 `:579-591` 的比较与 `execution_binding_invalid` 文案不变。
- 不同根（managed worktree）时 `sameRepositoryPath` 为假，**原两次读取路径原样保留**。
- 复用生命周期：仅是本函数局部变量在同一次调用栈内传递，无模块级/跨请求状态、无新字段、不改签名。
- **入参规范性（符号链接）**：`sameRepositoryPath(projectRoot, executionRoot)` 的两个入参就是 `brief.ts:530-531` 的 `realpathSync(input.projectRoot)` / `realpathSync(input.executionRoot)`，**都是解析过符号链接的绝对路径**；`sameRepositoryPath`（`workspace.ts:552-557`）只再做 `\`→`/`、去尾斜杠与 `pathKey` 大小写归一，不引入路径解析。因此：①符号链接指向同一真实目录时 realpath 后必然相等，不会误判为"不同路径"；②反过来 realpath 后相等即确系同一真实目录，不存在"两个不同目录被当成同一个"的失真。

**无副作用前提的证据（auditor 复核用；`brief.ts:530-578` 逐段）**：

| 行区间 | 内容 | 副作用性质 |
|---|---|---|
| 530-531 | 两次 `realpathSync(input.projectRoot)` / `realpathSync(input.executionRoot)` | 只解析路径（文件系统元数据读取），不写盘 |
| 532 | 第一次身份读取 `tryReadGitIdentity(executionRoot)`（内部 4 次只读 `rev-parse`） | 只读 Git，无写操作 |
| 533-539 | managed 且身份不可读 → 抛 `execution_binding_invalid` | 纯值校验 + 抛错 |
| 540-551 | managed 宿主证明字段（worktreeId/commonGitDir/bindingDigest）trim 非空检查 → 抛错 | 纯值校验 + 抛错 |
| 552-553 | `repositoryRoot` / `commonGitDir` 局部变量赋值 | 纯内存 |
| 554-564 | 宿主 commonGitDir 与执行根 Git 共同目录比较（`sameRepositoryPath` 纯字符串比较）→ 抛错 | 纯值校验 + 抛错 |
| 565-571 | 声明了 commonGitDir 但身份不可读 → 抛错 | 纯值校验 + 抛错 |
| 572-578 | 复用判断（574-578 表达式）：`sameRepositoryPath` 纯字符串比较 + 局部变量赋值（条件不满足时才走 :577 的 4 次只读 `rev-parse`） | 纯内存；或只读 Git |

这一段内**没有**任何文件写入（`writeFileSync`/`appendFile`/`mkdir`/`rename`/`rm` 等全无）、没有任何 Git 写命令（`add`/`commit`/`checkout`/`restore` 等）、没有 `await`/`setTimeout`/网络调用、没有派发或返回模型；全程唯一的外部进程调用就是只读的 `rev-parse`（:532 一次、:577 条件分支一次），且前者在复用成立时与后者同参同值。故"两次采集之间无副作用边界"成立，复用不减少任何跨边界重验。

**收益**：普通主工作树派发（projectRoot === executionRoot）每次 `prepareDispatchBrief` 省 **4 个 `rev-parse` 进程**；`dispatch-core.ts:1322` 单次 prepare 即省 4 个（`verifyDispatchSnapshot`、`workflowCheck`、`freeze` 的重采全部不动）。

### 3.2 未采纳（Lead 裁决）：prepare→freeze 跨阶段复用上游地图重采（原方案 B）

计划原文（`plans/未完成/2026-10-30-...实施计划.md:368`）：

> | S6-3 操作内复用 | 合并一次prepare内部等价重复采集；跨有副作用边界仍重新核验 | 明确复用生命周期，不能把派发前重验省掉 |

未采纳理由（Lead 裁决原话要点，逐条记录）：
1. §12.2 原文是"合并一次 **prepare 内部** 等价重复采集"；prepare→freeze 属**跨函数、跨阶段**，不属"prepare 内部"。
2. "冻结阶段复核"是 `freezeDispatchBrief` 自己的阶段语义（错误文案就是"上游地图覆盖内容在准备与冻结之间已变化"）；删掉后该检测点**永久失活**。虽然 `verifyDispatchSnapshot:538` 仍在派发前复核，但验收要求"不能把派发前重验省掉"，不接受在安全关键路径上用跨阶段状态换一次 O(1) 采集。
3. S6-2 批量化后单次采集已是常数个 Git 进程（实测 8 个），每上游地图每次派发省 1 次采集的收益，远小于引入 `types.ts` 跨阶段 hint 的复杂度与回归面。
4. 不加 `mapRechecks` 字段，`types.ts` 不动。

评估记录（未实施，供后续审计）：原方案是在 `DispatchBriefDraft` 增加可选 `mapRechecks?: {ref, mapDigest}[]`，`freeze` 在 ref+摘要完全一致时 `continue` 跳过重采、否则回退原路径。等价性与风险分析见本报告 23:5x 前的历史版本（结论：技术可行，但按裁决不做）。
