# S5 装配失败与资源生命周期验收记录

日期：2026-10-31（当日完成）。依据：[实施计划§11](../../../plans/未完成/2026-10-30-协作规则统一与模块边界优化实施计划.md#11-s5装配失败与资源生命周期)。阶段状态唯一维护于执行总册§10.23。

## 结论与边界

**结论：S5 工程优化完成；真实供应商效果未验证（V1 未执行）。**

- 装配失败现在只有一个出口：`paoExtension` 的失败信号是**返回的 Promise**，装载器 `await factory(api)` 等它完成收尾后才 `discard()` 半装配实例并抛错；CLI 退出码非 0、桌面拒绝启用会话。旧的「关键模块 catch 成一条 warning 后继续装配」路径已删除。
- 必需/可选分流以 `pao/role.ts` 的能力清单为唯一事实来源：未登记模块＝编程错误（装配即失败）、必需模块失败＝`PaoAssemblyFailure`（带模块名＋能力＋原始原因）、可选模块失败＝登记降级清单＋一条 warning 并继续。
- 装配期前校验（`pao/preflight/assembly.ts`）只做确定可检查项，在**第一次注册前**完成：受管父进程无控制通道、工作树状态目录为空、预算环境变量类型错、配置前置（`PAO_HOME`／档位配置）不合格。缺配置与编程错误在错误来源与文案上可区分。
- 半装配清理不假称「工具注册可原子回滚」：已注册的 tool/command/handler 由装载器 `discard()`（整个 Extension 对象不入集合）整体废弃，pao 自己创建的资源由自建 teardown **逆序 await 释放**，清理错误与装配错误一起暴露；宿主注入的 `runner`/`host`/`worktreeHost` 不释放。迟到的 API 调用会得到 loader 的 `failed to load and its API is no longer active`。
- 可选记忆：未配置＝显式降级且普通任务可用；已启用但清理失败＝`PaoAssemblyCleanupFailure` 暴露资源错误、现场保留可重试，不因「可选」吞掉。

边界：

- 本轮验证的是**当前源码**（开发根 HEAD `a4689ecc`；内核仓工作区＝HEAD `d29d7a838`＋未提交改动；桌面仓工作区＝HEAD `8dd923cb`＋未提交改动）在隔离 `PAO_HOME`、离线供应商（`PI_OFFLINE=1`／`PI_NO_LOCAL_LLM=1`）下的装配边界，**不是真实供应商运行**。
- 只证明「装配失败被宿主看见、半装配实例不可用、资源被释放或明确未确认」；装配成功后的业务行为由 S1—S4 覆盖。
- 真实基准跑批（bench map）与 Electron 端到端用例本轮未执行，见末节「遗留与未验证」。

## 经过与协议选择

**1. 装配失败用「返回值 Promise」传播，不新增异常通道。** `ExtensionFactory` 本来就允许 `void | Promise<void>`，loader 的 `initializeExtension` 是 `await factory(api); commit()`，catch 里 `discard()`。让失败路径返回收尾 Promise，装载器就天然等到资源释放完才 discard——「已启动资源等待关闭」与「整体丢弃半装配实例」两件事都有了确定顺序，无需改上游 loader。成功路径仍是同步返回 `undefined`，既有同步调用测试不受影响。

**2. 半装配清理用自建登记袋，不用 `session_shutdown` 兜底。** `core/extensions/runner.ts` 的 session_shutdown 语义是：任一 handler 抛错，所有 `onConfirmedShutdown` 清理全部跳过；而且装配失败时扩展根本没进集合，session_shutdown 永远不会到达它。所以用「每建一个资源就 push 一个释放动作，失败时逆序 await，单错不阻断并聚合」的自建 teardown；loader 的 `discard()` 已具备另外半边（state 机＋退 eventBus 订阅）。

**3. 清单放 `role.ts`，装配层不再自己维护跳过表。** 角色门控与「哪些能力必需」本来就是同一件事的两面：分开维护必然在新增模块时漂移。现在 `paoAssemblyRequirements(loadout)` 是唯一事实，`index.ts` 只做查表；未登记模块直接失败，新模块不会悄悄回到旧 warning 语义（这正是 S5-3「移除关键模块仅 warning 后继续的路径」的机制保障）。

**4. `tiers` 从必需降为可选，`workflow` 保持必需并带 `PAO_HOME` 前置。** 「模型入口」由 `model-command` 独立承担（它零配置依赖，读不到档位时按原生 `/model` 回落），档位路由是增强而不是可用性前提；把它列必需会让「裸起/无档位配置」直接不可用——这正是 2026-10-03 真机教训（tiers 抛错把 model 命令连坐跳过）要避免的。反之 `workflow` 是派发自动链的必需件，缺它是不可见的能力降级（工具消失、队列仍显示空），所以必需。

**5. `PAO_HOME` 完全未配置＝裸起显式降级；配了但读不出来＝装配失败。** 裸起是既有产品模式，`test/pao/wiring-smoke.test.ts` 在 2026-10-29 就把它钉成契约；S5 不擅自改变产品流程。区分口径是「配置前置」：没有配置＝用户没启用这条路（登记降级，普通任务照常）；配置在但坏＝用户明确要求了这条路却不可用（必需能力缺失，装配前失败）。实现上由 `routing/config.ts` 的 `PAO_HOME_MISSING_MESSAGE` 常量区分「缺失」与「解析失败」，前置状态带 `absent` 标记。

**6. 不做「工具注册原子回滚」的假承诺。** ExtensionAPI 的 `registerTool`/`registerCommand`/`on` 注册后没有撤销 API（只有 provider/mcp/virtualModel 三组有 unregister），唯一站得住的语义是：失败实例整体废弃＋pao 自有资源释放＋迟调用由 loader 的 `assertActive` 拒绝。记录与代码注释都按这个口径写。

**7. 桌面失败判定放「会话创建之后」，不放 `extensionsOverride`。** switch/new/fork 都是先 teardown 再 `createRuntime`，在装载结果改写钩子里抛错会留一个半死的 runtime；在 `createSession` 返回后判定、失败则 dispose 再抛，错误能落到既有 `withErrorHandling→lastError` 通道，用户看得见，且复用路径已有的 catch 会释放租约。

**8. 失败信号是返回值，包装工厂必须 `return` 它。** 这是本轮实跑撞到的真实集成陷阱：`(pi) => { paoExtension(pi); }` 会让装载器当作同步成功 commit，失败 Promise 变成 unhandled rejection。生产内置入口直接传 `factory: paoExtension` 所以安全；已在 `paoExtension` 的 JSDoc 写明该约定。

## 遗留与未验证

1. **真实供应商效果未验证**：V1 未执行，本轮所有结论只限于装配边界。
2. **bench 真实跑批未执行**：只核对了 `bench/map_bench_pao/pao_agent.py`、`bench/scripts/single-entry.mjs` 的判失败通道（CLI 子进程退出码／`errors.length`），未跑 map 批量；同一失败通道由 `cli-assembly-failure-real` 的真实子进程用例覆盖。
