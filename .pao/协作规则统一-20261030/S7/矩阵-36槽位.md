## 八、X 槽四条实证与 C 槽说明

X（结果未知）槽按 Lead 裁定记录产品事实、不判缺陷：§3.3 把「执行停止/任务完成/验收通过/流程完成」当四种不同事实，禁止的是停止未确认就释放写占位与宣布成功。X 槽断言逐条带四条实证：

1. 进程已消失：派发瞬间 worker 快照 pid 集合与结束时进程表对照，`unknown.dispatch-snapshot-pids-gone`；
2. 回执非 success 且 `failure_type` 与 stderr 同源：`unknown.receipt-not-success` + `unknown.receipt-failure-type-sourced-from-stderr`；
3. 尝试数未涨、无二次派发：`unknown.attempt-not-bumped` + `unknown.no-auto-redispatch`；
4. 控制正本未完成、无交付提交：`unknown.control-not-completed` + `unknown.no-impl-commit` + `unknown.no-delivery`。

两种链路的表达并行记录，均属产品既有设计：F1 单卡直派＝卡 `in_progress` + 失败回执；F2/F3 工作流自动链＝卡 `failed` + 失败回执 + 流程挂起。

C 槽：自建 kit 副本把 owner active 工具加上 `pao_stop_background`、`pao_terminate_card`（夹具层放宽，未改产品源码；`bench/organized-post/` 正式夹具未动，见上节 sha256 与 git 状态）。原失败 unmatched 原文保留：`未知工具：pao_stop_background 不在本请求可用工具 pao_start_flow, pao_query_flow, pao_push_flow, pao_control_node, pao_decision_pack, pao_ack_supervision, pao_inventory 中`。业务取消（控制正本 `停止.category=manual_pause`）与停止状态（产品返回「已停 N 个进程」及 pid 对照）分两条事实记录。
## 九、未覆盖项与说明

- 脚本模型只验证编排与契约，不证明专业质量（计划 §13.2 原话）。
