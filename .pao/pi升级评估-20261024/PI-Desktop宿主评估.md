# PI-Desktop 作为 PAO 宿主的初步评估

截至 2026-10-25。用户提出考虑改用 `vastsa/PI-Desktop` 并将 PAO 以插件实现。本次仅调查，不代表已决定迁移或已验证兼容。当前修复继续按原任务审核及提交；直接合并 pi 1.4.0 暂不启动，以便先讨论宿主路线。

## 结论

### 本次子代理评估后的主控复核

2026-10-25，用户要求“完全通过插件，不修改任何宿主源码”，并补充桌面机制和UI复用。两位子代理均为group/deepseek high，报告分别见[插件公开能力](子代理评估-插件公开能力.md)与[PAO行为映射](子代理评估-PAO行为映射.md)。主控实际复核了两份结论之间的分歧及底层调用链。远端HEAD仍与下述固定提交一致。

**结论：存在不修改PI-Desktop/pi源码、且复用宿主模型与会话执行的完整接入设计路线；静态评估为条件可行，尚未经过真实插件闭环验证。无需先假定修改宿主，也不必把整套旧执行宿主塞进插件。** PAO本体仍需重构接入，不能原样加载现有扩展。

推荐一个插件：内部保留PAO部门、任务卡、验收和返修规则；一个常驻服务通过公开pi.desktop.invoke调用session/create、agent/prompt、agent/getStatus、session/get、agent/abort；监听session:turnEnded并核对真实回合与业务回执，再机械推进下一步。PAO继续负责现有的任务身份、attempt和验收证据，宿主负责模型执行和会话历史。业务状态归PAO并不是第二个模型执行宿主。

这修正了先前只看专用collaboration接口时的过窄判断：它的spawn/send确实要求活动工具身份，但普通公开会话接口没有同样限制。完成消息也确实可以启动来源会话的一轮，而不只是静静落入队列；不能据此宣称所有模型后续行为都确定执行。确定性的流程判断仍应由PAO代码执行。

主控复核证据：apps/desktop/electron/main/plugin-runtime.ts:5611起提供受权限保护的公开desktop.invoke，对普通操作不要求存在工具调用；mcp-control.ts:189起注册普通会话/Agent操作，createMcpControlController转交已有IPC；ipc/session-ipc.ts:228起转交session.create；services/plugin-services.ts:585起广播回合结束事件；runtime/plans.ts:272发布该事件。文档对应03-plugin-api.md:1135起的desktop control及:1352起的回合结束契约。子代理个别文档行号有偏移，以本段复核位置和实际符号为准。

仍需验证四项，不能把静态可达当成运行成功：

1. **事件与恢复**：回合结束事件无确认/重放，且文档明确可能仍有迟到工具结果。事件只用于唤醒，必须核对持久状态、回执和写入停止；重开后对账，不能直接当作可安全验收。文档关于“0.14.8尚未发布事件”的字样陈旧，不能据此断言本次0.21源码没有事件；具体安装发行物另行核对。
2. **工作树**：不能只凭MCP便捷工具的字段表断言无隔离能力。通用desktop.invoke没有按该便捷工具schema删字段；sessionCreate IPC透传参数，Rust rpc/mod.rs:2636起实际读取isolated:true并创建隔离工作树。这是可达源码路线，但插件说明未完整承诺参数和后续合并/清理操作，需验证并确认公开契约稳定性。也可以由PAO使用现有Git工作树实现，将目录作为projectPath交给宿主；这保留工作树管理，不等于保留第二模型执行宿主。该替代同样尚未运行。
3. **取消与退出**：agentAbort支持sessionId加turnId校验，插件应按实际回合取消，避免中止后来任务；不能只看便捷工具schema推断没有turnId。宿主退出限时仍成立，需在工作中持续保存状态，退出时取消并标中断，重开显式恢复；本次不承诺退出后后台继续作业或等待所有任务成功完成。
4. **UI与权限**：插件内PAO页面及聊天扩展有真实公开接口，整套宿主布局和交互没有任意替换契约；权限审批、配置和实际Windows运行均未集成验证。详情见下方UI表。

能复用：项目与持久会话、模型配置与凭证执行、回合历史与用量记录、Agent侧执行、常驻服务生命周期、事件通道、插件安装/启停/设置、命令入口、工作面板、主题及聊天插槽。仍由PAO维护：部门职责、任务书、卡和attempt、机械验收、返修历史、流程控制、业务去重与恢复映射。宿主Token记录可以复用，不代表自动得到了完整费用统计或P5降负担结论。

推荐后续最小验证采用“常驻服务＋普通会话接口＋PAO自有工作台”，验证派发、机械验收、原卡返修、迟到事件、精确取消与关闭重开。此次没有开始实现、安装、付费试跑、合并或迁移。下文保留较早评估的背景和调查记录，涉及后台调度与工作树的保留判断以本段复核为准。

值得先做最小接入验证。长期把 PAO 的部门、卡、配方、验收和经验维护为独立业务包，由成熟桌面宿主提供会话、模型、界面、后台与安装更新，方向合理。当前证据不足以认定现有 PAO 可以直接作为插件装入 PI-Desktop，或不再需要任何宿主改动。

推荐结构为一个 PAO 业务包、一个 PI-Desktop 插件及其薄宿主适配；业务包内部按现有模块组织，不为每个部门另建插件。是否继续提供 CLI 由既有产品需求决定；桌面插件本身不能证明现有无界面基准运行入口仍可用。

## 可以复用什么

- Electron 桌面界面、项目与持久会话、模型配置、插件设置及安装。
- 插件工具、侧栏/面板、常驻服务、消息总线等扩展面。
- `session/collaboration/spawn/send/list/status/result/cancel` 的宿主会话协作能力，包括真实持久会话标识、取消而不删历史，以及实际回合结束后的宿主完成回调。
- pi 仍是模型执行引擎。固定源码的 agent-runtime 将 pi-ai、pi-agent-core、pi-coding-agent 精确固定于 1.3.0。因此这主要是宿主与集成路线迁移，同时仍需跟随 pi 内核版本。

这些能力可能替代 PAO 的部分通用宿主维护，但是否能替代每个 PAO 入口须逐项验证。

## 已确认的接口差异

1. **不是完整 pi 扩展 API。** 桌面普通 Agent 会话使用自己的 TrustedExtensionRunner，只支持声明的子集。规范明确区分普通桌面会话和原生 Pi 会话续接；不能据“支持 pi 扩展”推导出 PAO 全部能力可用。
2. **自定义消息与会话读写缺口。** `sendMessage`、`appendEntry`、`sessionManager` 读取列为待后续支持；实际 runner 将前两者登记为 inert API，会诊断但不执行，sessionManager 的部分读取返回空。PAO 当前依赖这些能力，直接导入可能出现“能加载、业务无效”。
3. **提示注入方式不同。** 可信扩展的 before_agent_start 采用返回 `systemPrompt` 字符串的折叠机制；实际构造的 systemPromptOptions 是空对象。PAO 使用 `systemPromptOptions.sections`、`context_with_system` 等接口，需改为宿主支持的装配方式，不能直接复用原钩子。
4. **后台派发约束不同。** 协作 API 的 spawn/send 只能在当前插件 Agent 工具调用期间执行；面板与常驻服务不能据此自由派发。PAO 自动链在模型工具调用结束后继续驱动部门的行为，须验证能否由宿主完成回调及后续工具调用正确承接，或是否需要一个小型公开宿主接口。
5. **持久身份与执行环境需映射。** PAO 的实例、节点轮次、部长/工人身份、当前 attempt、执行绑定、工作树隔离、机械验收及取消，不能直接等同于一个 Worker Session。需明确哪些事实归宿主、哪些归 PAO，保留一个事实一个归属。

## 能力归属与适配规模

当前修复已先提交内核 `0236147ed`。下表是提交后的接入评估，不代表开始迁移。

| 能力 | 推荐归属 | 接入判断与待验证点 |
|---|---|---|
| 部门目录、简介与任务书装配 | PAO业务包 | 保留现有规则；插件把宿主会话身份和任务输入交给同一业务入口 |
| 卡、轮次、attempt、回执与验收 | PAO业务包 | 保留数据契约与返修历史，不另建一套宿主业务状态 |
| 会话、模型调用与持久消息 | PI-Desktop | 优先替代自有通用执行部分；会话身份要明确映射到PAO角色，不能只记显示名 |
| 工作树和执行目录 | 宿主负责真实执行，PAO保存绑定 | 须验证每个子会话能绑定正确目录，取消后不遗留写入；尚未证实满足现有保证 |
| 后台自动链 | PAO负责业务推进，插件适配宿主调度 | 最大不确定项：工具调用结束后如何继续派发，不能用持续空转模型轮次维持调度 |
| 结果通知与唤醒 | 宿主投递，PAO决定业务接收者及去重 | 现有sendMessage不可直接用；需要完成回调到正确会话、关闭后恢复及重复事件的实际证据 |
| 侧栏、设置和过程展示 | 插件界面 | 复用宿主面板，按业务读模型渲染；旧桌面界面不能直接视为可复用 |
| 安装、应用更新、通用模型设置 | PI-Desktop | 尽量不再自建，但预览版本稳定性及Windows安装仍需真实检查 |
| CLI与无界面基准 | 既有CLI宿主调用同一业务包 | 桌面插件不能自动替代；本次不删除现有入口 |

这里的“业务包”是可独立测试、由不同宿主调用的一份普通模块，不需要先做插件市场或自建通用插件框架。部门是该模块读取的配置和知识，不是一个部门对应一个插件。可把现有流程、卡片和验收逐步移出pi fork，通用能力在验证后再交给宿主，避免同时保留两套会话和执行实现。

## 决策门槛与实施顺序

推荐先决定是否允许一个隔离的最小验证，暂不批准完整迁移。当前仅评估，未安装、未写接入代码、未启动验证。后续若获授权，按以下次序推进：

1. 锁定宿主提交与插件契约，列出实际需要的公开调用；先确认后台派发、定向投递、持久会话及目录绑定四个关键缺口。
2. 用一个PAO插件完成下述真实闭环，模型只处理小任务；分别记录业务回执、宿主消息、取消和重开证据，不以工具返回值代替结果。
3. 公开接口足够才提取独立业务包；不足则列出最小宿主接口补充，先评估能否向上游维护，不把绕行补丁散进业务代码。
4. 闭环通过后再评估现有桌面界面、历史数据和CLI适配，分阶段替换。迁移前保留可用旧入口及数据备份，不让新旧宿主同时写同一现场。

继续迁移的门槛：上述关键能力均有真实证据，业务规则只有一份，宿主改动集中且可维护。若需要广泛修改Rust/Electron/扩展运行器，或长期把完整旧执行宿主藏进插件，则暂不换基座，继续现有PAO并独立减少pi fork改动。后者仍可复用此次业务分离工作。

这不是“官方有同名功能就删除本地代码”：须对照真实语义，尤其接受后排空、主动取消、关闭顺序、持久身份和验收边界。官方功能满足同一行为时才替换；缺少的PAO业务保证保留在小范围适配中。迁移工作量目前只能判为多阶段工程，不能据插件示例推算成几天；关键接口验证后才给可靠估计。

## 最小验证内容

先在隔离开发目录和隔离数据中实现一个可安装 PAO 插件，仅覆盖以下闭环，不迁移正式数据、不删除现有实现：

1. 主会话按动态部门简介，将一个目标交给一个部长会话。
2. 部长派一个执行者，产生实际文件与原卡回执；通过现有机械验收规则。
3. 执行者结束后，结果自动进入正确部长，再交正确主会话；相同结果不重复唤醒。
4. 制造一个任务范围内的缺陷，原卡合法返修，attempt 递增而旧证据保留。
5. 验证取消、会话关闭/重开、工作树绑定及真实人工门；不能只看工具返回成功。

优先使用宿主公开协作 API 和插件扩展口。发现缺口先列明真实触发路径，再判断小型宿主补充是否可接受。若为完成最小闭环必须广泛修改 Rust、Electron、扩展运行器或嵌入整套旧 PAO 执行运行时，须重新评估是否实际减少维护负担。

初步判断：迁移总成本明显高于单纯升级 pi 1.4.0，主要成本在执行接线、持久身份、恢复及界面迁移，业务模块有复用潜力。尚不具备可靠工期和节省费用估算；最小验证结果出来后再估计。

## 2026-10-25补充：UI能否只靠插件实现

以下为主控对同一固定提交的实现复核，未安装或运行。插件可以新增完整PAO工作界面、在聊天中增加入口，并改变整体外观；公开契约不等于允许任意替换宿主所有界面和交互。

| 需求 | 可采用的插件机制 | 边界 |
|---|---|---|
| 部门、任务卡、流程、验收记录的专属工作台 | contributes.views，插件自带HTML/JS/CSS，在宿主工作面板打开 | 可自行设计内部布局；不是替换主窗口或宿主导航。宿主缓存视图上限4，不要将每个部门做成独立常驻视图 |
| 独立设置页、复杂编辑表单、弹出窗口 | ui.panel或自己的view；简单设置用contributes.settings | 简单设置由宿主表单生成；复杂部门配置放自己的页面，不能据此改写宿主所有设置页 |
| 聊天里的“交给部门”按钮、快捷选择部门 | composerControl、composerTrigger及composerTransforms | 在现有输入区域增加入口；不替换整个编辑器或其提交语义 |
| 每条回复下显示任务状态、回执链接、人工操作 | entryExtra、userAction、assistantAction | 是附加内容，不改写宿主既有消息正文或原按钮行为；实际操作仍须走业务权限和回执规则 |
| PAO派发和验收工具显示成专属卡片 | toolCard | 只能注册本插件自己的agentTools，不据此替换其他插件或宿主工具卡 |
| 在回复里渲染PAO流程图或结构化内容 | blockRenderer | 使用本插件命名空间的代码块标签；不是接管全部Markdown渲染 |
| 自己的确认框、详情弹层 | pi.ui.openLayer | 宿主权限/审批等需要用户决定时会隐藏插件层，不可覆盖宿主决策界面 |
| 色彩、字体、背景、间距等外观 | contributes.themes、运行时themes接口及windowAppearance | 主题CSS会作用于宿主样式，可做比换颜色更广的外观调整；依赖内部class的布局覆盖较脆弱，不等于稳定的布局/交互替换接口 |

与此不同，renderer的pi.ui.injectStyle会把普通样式规则限制在本插件挂载区域；不能把它误认为任意全局改样式接口。可信renderer确实与宿主处于同一网页环境，但直接操作宿主DOM、调用内部store或抓内部IPC不计入本次公开接口方案，也不作为长期兼容保证。

建议保留宿主项目列表、会话列表、聊天主体、模型设置和通用文件/工具展示，在一个PAO工作面板内集中部门、任务卡和验收；聊天输入区加派发按钮，回复旁显示状态与跳转。这样可以只交付一个插件，且不要求复刻现有PAO桌面的每一处布局。现有React纯展示组件可能迁移，但当前组件对自有IPC和状态的依赖需逐一拆开，不能直接宣称整套界面可搬入。

源码证据（均为上文固定提交）：packages/plugin-sdk/src/renderer.ts:50列出7种插槽，:282定义样式与弹层，:454限制自有工具卡；apps/desktop/src/plugins/renderer-slots/registry.ts负责附加注册和重复键；style-injection.ts:46实现作用域；apps/desktop/src/components/workpanel/PluginViewTab.tsx:19实现工作面板视图；apps/desktop/electron/main/plugin-view-host.ts:52为视图缓存上限、:432为隔离页面配置；packages/plugin-sdk/src/index.ts:1240起为主题、设置、面板和revealView；packages/plugin-sdk/src/theme-css.ts:321及apps/desktop/src/features/app/useAppShellRuntime.tsx:574共同实现主题校验和全局样式注入。examples/plugins/ui-slots-lab/renderer/index.mjs:31起有真实各插槽示例；不只依据路线图判断。

主控同时确认实际plugin-runtime.ts:660、:662在应用退出时分别限制插件关闭钩子1.5秒和总体收尾3秒。不能把存在onUnload回调等同于宿主允许等待所有PAO在途工作完成。纯插件接入必须明确持久取消/恢复的语义，并验证退出后确实无遗留写入；若要求退出前无限等待模型工作完成，则与此宿主退出契约冲突。本轮没有实际启动验证。
