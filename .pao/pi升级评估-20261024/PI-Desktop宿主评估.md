# PI-Desktop 作为 PAO 宿主的初步评估

截至 2026-10-25。用户提出考虑改用 `vastsa/PI-Desktop` 并将 PAO 以插件实现。本次仅调查，不代表已决定迁移或已验证兼容。当前修复继续按原任务审核及提交；直接合并 pi 1.4.0 暂不启动，以便先讨论宿主路线。

## 结论

值得先做最小接入验证。长期把 PAO 的部门、卡、配方、验收和经验维护为独立业务包，由成熟桌面宿主提供会话、模型、界面、后台与安装更新，方向合理。当前证据不足以认定现有 PAO 可以直接作为插件装入 PI-Desktop，或不再需要任何宿主改动。

推荐结构为一个 PAO 业务包、一个 PI-Desktop 插件及其薄宿主适配；业务包内部按现有模块组织，不为每个部门另建插件。是否继续提供 CLI 由既有产品需求决定；桌面插件本身不能证明现有无界面基准运行入口仍可用。

## 调查范围

只读克隆位于本目录 `pi-desktop-source/`，未安装依赖、未启动程序、未执行该仓库脚本。调查固定提交 `d2c9fc44087f24260521c66530c4f92c04790105`，根 package.json 为 0.21.0，2026-10-24 发布提交。README 称该系列为 Early Preview。主分支会继续变化，后续验证须另锁定实际版本。

阅读：README、架构规范、插件开发指南、插件 API、可信扩展规范、插件路线及实际 `packages/agent-runtime/src/extensions/runner.ts`、事件能力清单和依赖声明。没有进行完整源码审计、真实 Windows 启动或插件闭环验证。

## 可以复用什么

- Electron 桌面界面、项目与持久会话、模型配置、插件设置及安装。
- 插件工具、侧栏/面板、常驻服务、消息总线等扩展面。
- `session/collaboration/spawn/send/list/status/result/cancel` 的宿主会话协作能力，包括真实持久会话标识、取消而不删历史，以及实际回合结束后的宿主完成回调。
- pi 仍是模型执行引擎。固定源码的 agent-runtime 将 pi-ai、pi-agent-core、pi-coding-agent 精确固定于 1.3.0。因此这主要是宿主与集成路线迁移，同时仍需跟随 pi 内核版本。

这些能力可能替代 PAO 的部分通用宿主维护，但是否能替代每个 PAO 入口须逐项验证。

## 已确认的接口差异

1. **不是完整 pi 扩展 API。** 桌面普通 Agent 会话使用自己的 TrustedExtensionRunner，只支持声明的子集。规范明确区分普通桌面会话和原生 Pi 会话续接；不能据“支持 pi 扩展”推导出 PAO 全部能力可用。
2. **自定义消息与会话读写缺口。** `sendMessage`、`appendEntry`、`sessionManager` 读取列为待后续支持；实际 runner 将前两者登记为 inert API，会诊断但不执行，sessionManager 的部分读取返回空。PAO 当前依赖这些能力，直接导入可能出现“能加载、业务无效”。
3. **提示注入方式不同。** 可信扩展的 before_agent_start 采用返回 `systemPrompt` 字符串的折叠机制；实际构造的 systemPromptOptions 是空对象。PAO 使用 `systemPromptOptions.sections`、`context_with_system` 等接口，需改为宿主支持的装配方式，不能直接复用原钩子。
4. **后台派发约束不同。** 协作 API 的 spawn/send 只能在当前插件 Agent 工具调用期间执行；面板与常驻服务不能据此自由派发。PAO 自动链在模型工具调用结束后继续驱动部门的行为，须验证能否由宿主完成回调及后续工具调用正确承接，或是否需要一个小型公开宿主接口。
5. **持久身份与执行环境需映射。** PAO 的实例、节点轮次、部长/工人身份、当前 attempt、执行绑定、工作树隔离、机械验收及取消，不能直接等同于一个 Worker Session。需明确哪些事实归宿主、哪些归 PAO，保留一个事实一个归属。

## 能力归属与适配规模

当前修复已先提交内核 `0236147ed`。下表是提交后的接入评估，不代表开始迁移。

| 能力 | 推荐归属 | 接入判断与待验证点 |
|---|---|---|
| 部门目录、简介与任务书装配 | PAO业务包 | 保留现有规则；插件把宿主会话身份和任务输入交给同一业务入口 |
| 卡、轮次、attempt、回执与验收 | PAO业务包 | 保留数据契约与返修历史，不另建一套宿主业务状态 |
| 会话、模型调用与持久消息 | PI-Desktop | 优先替代自有通用执行部分；会话身份要明确映射到PAO角色，不能只记显示名 |
| 工作树和执行目录 | 宿主负责真实执行，PAO保存绑定 | 须验证每个子会话能绑定正确目录，取消后不遗留写入；尚未证实满足现有保证 |
| 后台自动链 | PAO负责业务推进，插件适配宿主调度 | 最大不确定项：工具调用结束后如何继续派发，不能用持续空转模型轮次维持调度 |
| 结果通知与唤醒 | 宿主投递，PAO决定业务接收者及去重 | 现有sendMessage不可直接用；需要完成回调到正确会话、关闭后恢复及重复事件的实际证据 |
| 侧栏、设置和过程展示 | 插件界面 | 复用宿主面板，按业务读模型渲染；旧桌面界面不能直接视为可复用 |
| 安装、应用更新、通用模型设置 | PI-Desktop | 尽量不再自建，但预览版本稳定性及Windows安装仍需真实检查 |
| CLI与无界面基准 | 既有CLI宿主调用同一业务包 | 桌面插件不能自动替代；本次不删除现有入口 |

这里的“业务包”是可独立测试、由不同宿主调用的一份普通模块，不需要先做插件市场或自建通用插件框架。部门是该模块读取的配置和知识，不是一个部门对应一个插件。可把现有流程、卡片和验收逐步移出pi fork，通用能力在验证后再交给宿主，避免同时保留两套会话和执行实现。

## 决策门槛与实施顺序

推荐先决定是否允许一个隔离的最小验证，暂不批准完整迁移。当前仅评估，未安装、未写接入代码、未启动验证。后续若获授权，按以下次序推进：

1. 锁定宿主提交与插件契约，列出实际需要的公开调用；先确认后台派发、定向投递、持久会话及目录绑定四个关键缺口。
2. 用一个PAO插件完成下述真实闭环，模型只处理小任务；分别记录业务回执、宿主消息、取消和重开证据，不以工具返回值代替结果。
3. 公开接口足够才提取独立业务包；不足则列出最小宿主接口补充，先评估能否向上游维护，不把绕行补丁散进业务代码。
4. 闭环通过后再评估现有桌面界面、历史数据和CLI适配，分阶段替换。迁移前保留可用旧入口及数据备份，不让新旧宿主同时写同一现场。

继续迁移的门槛：上述关键能力均有真实证据，业务规则只有一份，宿主改动集中且可维护。若需要广泛修改Rust/Electron/扩展运行器，或长期把完整旧执行宿主藏进插件，则暂不换基座，继续现有PAO并独立减少pi fork改动。后者仍可复用此次业务分离工作。

这不是“官方有同名功能就删除本地代码”：须对照真实语义，尤其接受后排空、主动取消、关闭顺序、持久身份和验收边界。官方功能满足同一行为时才替换；缺少的PAO业务保证保留在小范围适配中。迁移工作量目前只能判为多阶段工程，不能据插件示例推算成几天；关键接口验证后才给可靠估计。

## 最小验证内容

先在隔离开发目录和隔离数据中实现一个可安装 PAO 插件，仅覆盖以下闭环，不迁移正式数据、不删除现有实现：

1. 主会话按动态部门简介，将一个目标交给一个部长会话。
2. 部长派一个执行者，产生实际文件与原卡回执；通过现有机械验收规则。
3. 执行者结束后，结果自动进入正确部长，再交正确主会话；相同结果不重复唤醒。
4. 制造一个任务范围内的缺陷，原卡合法返修，attempt 递增而旧证据保留。
5. 验证取消、会话关闭/重开、工作树绑定及真实人工门；不能只看工具返回成功。

优先使用宿主公开协作 API 和插件扩展口。发现缺口先列明真实触发路径，再判断小型宿主补充是否可接受。若为完成最小闭环必须广泛修改 Rust、Electron、扩展运行器或嵌入整套旧 PAO 执行运行时，须重新评估是否实际减少维护负担。

初步判断：迁移总成本明显高于单纯升级 pi 1.4.0，主要成本在执行接线、持久身份、恢复及界面迁移，业务模块有复用潜力。尚不具备可靠工期和节省费用估算；最小验证结果出来后再估计。
