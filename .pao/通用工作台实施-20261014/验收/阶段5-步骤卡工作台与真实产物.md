# 阶段 5 验收：步骤卡工作台与真实产物

计划：`plans/已完成/2026-10-14-通用工作台与内核可靠性实施总计划.md`（阶段 5 执行项见 `:273-284`，完成条件见 `:286`，交互规格见 `§5.1 :167` / `§5.2 :183`，验收场景矩阵见 `§9.2 :388`）

## 结论

阶段 5 的界面已由步骤卡工作台承担，画布不再是默认入口。工作台的状态、挂起原因、轮次与**真实产物**都来自内核只读投影（控制正本＋卡回执），页面没有任何写通道：编辑、停卡、确认都只是把指令交给当前主控会话。真实 Electron 用例 4 项全部通过，其中「点产物 → 右栏显示盘上真实正文」用的是夹具真正写到磁盘的文件。

过程中查出并修掉两个真实缺陷（都不是测试写法问题）：**产物按错基准解析**（真实布局下所有真实产物都被判「越界」）与**实例扫描漏掉嵌套临时计划实例**（界面读不到节点状态）。两个缺陷都补了回归用例并做了反向验证。

## 数据是否模拟

- 界面状态与产物：**不模拟**。夹具用内核构建产物真实建计划、启动实例、建卡、写回执、写产物文件，界面读的是同一份磁盘数据。
- 主控会话：夹具用桌面既有 IPC 真实建一个会话（`createSessionViaIpc`）并切到它，不启动真实模型；因此**人工确认/暂停这类要落到主控的动作在验收里走的是真实失败路径**（没有活着的 owner 部长会话），这正好验证了「失败如实报、正本不动」。
- 未调用任何真实供应商（全程离线）。

## 过程中查出并修掉的缺陷

### 缺陷 A：真实产物按错基准解析，真实布局下全部被判「越界」

- 现象：真实启动布局里 `工作区 = <项目根>/.pao/临时工作流/<计划ID>/执行/<启动请求ID>`、`卡目录 = <工作区>/卡`，而回执里的产物路径按**项目根**记录（派卡提示口径，也是 `projectRootForCards(卡目录)` 的基准）。`desktop/plans.ts` 拿工作区当基准 → 每个真实产物都落「路径越出工作区，不作为产物展示」，界面永远显示不出真实产物。
- 修法：`artifactOf` 参数改名 `项目根`；相对路径统一正斜杠 `(relative(项目根, 绝对) || ".").split(sep).join("/")`；调用点改 `stepProgress(flow, projectRootForCards(record.卡目录))`。
- 回归：`PAO/packages/coding-agent/test/pao/desktop-plans.test.ts` 新增「真实启动布局下产物按项目根解析」用例（真实建计划→启动→建卡→回执→交付，产物写在 `<项目根>/创作成果/初稿.md`），断言 `相对路径 === "创作成果/初稿.md"`、`存在 === true`、无越界说明。该文件 11 passed。
- 反向验证：修前该用例的断言在旧基准下必然失败（越界说明出现），修后通过。

### 缺陷 B：实例扫描漏掉嵌套的临时计划实例

- 现象：`readDesktopFlows(project)` 原来只扫 `.pao` 与一层子目录，而临时计划的控制正本埋在 `.pao/临时工作流/<计划ID>/执行/<请求ID>/` 下 → `getWorkflowControl`/`controlWorkflow` 找不到实例，界面所有步骤卡停在「未开始」，确认/暂停按钮也拿不到节点。
- 修法：`PAO/packages/coding-agent/src/pao/desktop/workflow.ts` 改为按层数递归收集目录（新增 `collectDirectories`，跳过 `node_modules`，深度 4）。
- 回归：`desktop-plans.test.ts` 新增「临时计划的控制正本埋在 .pao 深处也要被实例扫描发现」，断言实例号与节点名 `["s1","s2"]`。该文件 13 passed。
- 反向验证：把深度改回 1 重跑 → 该用例失败（工作流列表为空）；恢复深度 4 → 13 passed。

### 缺陷 C：顶部多出一行（坏计划披露）时，工具条压住步骤卡列表

- 现象：阶段 6 回归时给 core 夹具加了「一张读不出来的计划定义」，页面顶部因此多出一行 `plans-issues`。Playwright 报 `locator.click: Timeout 30000ms exceeded … <button class="workflow-cards__step-main"> from <div class="workflow-cards__body"> subtree intercepts pointer events`——搜索/筛选/工具栏与步骤列表重叠，按钮点不到。
- 根因：`.workflow-cards__main` 是固定行数的 grid（`grid-template-rows: auto auto auto auto minmax(0,1fr) auto`，6 行轨道），页面多出一个子元素后轨道与子元素错位。
- 修法：`desktop/apps/desktop/src/styles/workflow-cards.css` 的 `.workflow-cards__main` 改成 `display:flex; flex-direction:column`（`overflow:hidden`），`.workflow-cards__body` 加 `flex: 1 1 auto`，`.workflow-cards__chat` 加 `flex: 0 0 auto`，不再依赖固定行数。
- 回归：重建桌面产物后 `tests/core/workflow-cards.spec.ts` 4 passed（59.7s），其中就包含「坏计划定义要点名披露」那一条。

### 缺陷 D：按草案补齐顶部后，底部对话把中栏压成 0 高

- 背景：用户 2026-10-15 指出真实界面与草案 `pao-workflow-cards.html` 不一致，选定「按草案补齐，保留计划要求的额外行」。补齐项＝顶栏面包屑（当前项目 / 当前主控）、计划标签页（多计划时）、修改反馈行＋撤销、等待人工确认区（查看成果文件 / 提出修改意见 / 确认放行）、保存工作流面板（名称必填、空名报错）、底部主控对话的标题与底栏。
- 现象（补齐后首次回归）：`tests/core/workflow-cards.spec.ts` 2 failed——① 点 `workflow-cards-stop-s2` 报 `TimeoutError … <div class="workflow-cards__main"> intercepts pointer events`；② 三种宽度用例里 `workflow-cards-inspector` 不可见。
- 根因：顶部多出确认区/面包屑后，`.workflow-cards__body`（`flex: 1 1 auto; min-height: 0`）在 flex 收缩里被压到 0 高；`@media (max-width: 1080px)` 又把 `.workflow-cards__chat` 设成 `max-height: none`，复用的真实对话组件高度不受限，进一步吃掉中栏。
- 修法（`desktop/apps/desktop/src/styles/workflow-cards.css`）：`.workflow-cards__main` 改 `overflow-x: hidden; overflow-y: auto`（内容超一屏时主列自己滚动，而不是压中栏）；`.workflow-cards__body` 加 `min-height: 260px`；`.workflow-cards__chat` 上限收到 `max-height: 34vh`，`@media (max-width: 1080px)` 下为 `30vh`。
- 回归：`pnpm build` 后 `tests/core/workflow-cards.spec.ts` **4 passed（57.7s）**；`plan-recovery.spec.ts`＋`settings-general.spec.ts` 7 passed（1.0m）；`theme.spec.ts`＋`workflow-cards-model.spec.ts` 26 passed；typecheck/eslint/prettier 全过。
- 截图：`临时文件夹/阶段7-发行与性能-20261015/界面-1280.png`（草案对齐后的 1280 宽实机截图）。

### 缺陷 E：布局不是「草案那种一页」——中栏内部滚动＋对话被限高

- 背景：用户 2026-10-15 看过实机截图后表示「展示效果还是不一样」，并要求「就按那个设计图来，文字描述不清楚」——即不再逐条确认，直接照 `C:\Users\ASUS\.codex\visualizations\2026\10\14\01a13a3c-8558-7510-a9dd-a0fc60cd4a77\pao-workflow-cards.html` 的排版还原。
- 与草案的实际差异（读草案 CSS 1–126 行后逐条比对）：① 草案 `.pc-body` 是自然高度的两栏网格（`minmax(0,1fr) 256px`、`align-items:start`），中栏与右栏不各自滚动，整块随页面一起滚；本实现把中栏与右栏都设成 `overflow-y:auto`，形成两个内部滚动区。② 草案 `.pc-chat` 是自然高度、`padding:12px 18px 15px`、`border-top:5px solid`；本实现给对话区设了 `max-height:34vh`，并且它靠 flex 抢高度。③ 草案左栏 152px，本实现 232px。④ 草案步骤卡的状态在标题行右上角（`.pc-step-state`），本实现的卡片在缺陷 D 之后仍偏「表单行」。
- 修法（`desktop/apps/desktop/src/styles/workflow-cards.css`、`workflow-cards-view.tsx`）：`.workflow-cards__body` 改回 `display:grid; grid-template-columns:minmax(0,1fr) 256px; gap:16px; align-items:start`（去掉 `flex/min-height/overflow`）；`.workflow-cards__center` 改 `display:flex; flex-direction:column; gap:9px`（去掉 `overflow-y:auto`）；`.workflow-cards__inspector` 去掉 `overflow-y:auto`，`padding-left:14px`；`.workflow-cards__chat` 去掉 `max-height`，改 `padding:12px 18px 15px`，对话正文包进新的 `.workflow-cards__chat-body`（`max-height:320px; overflow-y:auto`，对应草案 `.pc-messages{max-height:132px}` 的口径）；左栏基准宽度 232px → 184px（`@media (max-width:1080px)` 160px）；步骤卡重排为「序号方块＋标题＋右上状态＋缩进副行＋预期成果链接」（`.workflow-cards__step-state[data-state]` 按 done/running/review 着色）。
- 回归：`pnpm build` 后 `tests/core/workflow-cards.spec.ts` **4 passed（56.2s）**；`plan-recovery.spec.ts`＋`settings-general.spec.ts` **7 passed（59.1s）**；typecheck / eslint / prettier 全过。
- 截图：`临时文件夹/阶段7-发行与性能-20261015/界面-1280-对齐后.png`（顶部）与 `界面-1280-底部.png`（滚到底部，可见草案式的粗顶线对话面板）。
- 仍未与草案一致的地方（有意保留）：应用自身的左侧主导航（新建会话/工作流/工作看板/临时计划/会话/定时任务）是宿主界面，草案里用 `PAO/工作流/看板/会话` 模拟；计划标签页只在存在两个以上计划时出现（草案固定画了两个）。
