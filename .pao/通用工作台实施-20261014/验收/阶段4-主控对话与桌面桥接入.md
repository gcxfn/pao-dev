### 第 3 项：计划摘要、按版本绑定的执行确认、失败展示真实原因、消息重放不重建

- 创建回包给出计划摘要并要求「先给用户看计划、确认后调 `pao_plan_start`」；**创建工具成功只表示定义落盘**。
- `resolvePlanExecution` 返回待启动的确定位置（工作区＝`<计划目录>/执行/<启动请求ID>`、卡目录、控制清单）；`assertPlanConfirmation` 要求确认事实带 `计划ID + 定义版本 + 启动请求ID` 且来源是宿主确认回调或可信用户交互事件；模型传入的 `{confirmed:true}`、自述同意、普通助手文本都无效。
- 等待确认期间不持文件锁：确认后**重核**版本/撤销/预检，再在锁内受理。
- 工具错误经 `toolResult` 上抛为 `[CODE] message`（真实原因，不吞错）。
- 消息重放：创建/修改/撤销/保存模板/启动均以逻辑请求 ID 幂等——同 ID 同参数回放原结果、不同参数 `PLAN_REQUEST_CONFLICT`；`resolvePlanExecution` 在响应丢失/进程中断后能从控制正本回读原实例。
- 用例：`workflow-plan.test.ts`（24 例，含并发同请求只落一份、版本漂移拒、真实 `startWorkflow` 后重试找回同一实例、关联与控制实例不符报「不完整启动」）+ `workflow-plan-tools.test.ts`（无确认拒启、三方确认拒启、`ui.confirm=false` 拒启、已启动后定义冻结）。

### 第 4 项：步骤/文件讨论对象与意见关联，五种状态分开

- `src/pao/workflow/plan-feedback.ts`：`recordPlanFeedback` / `recordPlanFeedbackDelivery` / `markPlanFeedbackApplied` / `listPlanFeedback`；状态 `已记录 | 待送达 | 已送达 | 投递失败 | 已应用`。
- 意见绑定**提交时正在看的定义版本**：版本漂移即拒（`意见要绑定提交时看到的那一版计划`），改标题不动步骤 ID 所以意见对象不丢。
- 文件意见必须给齐轮次与版本识别依据；「已应用」必须有真实业务处理依据（空白依据拒收），不靠前端状态自报。
- 投递只说真话：没有回执不算送达，失败留原因，同投递请求 ID 重试是回放。
- 用例：`workflow-plan-tools.test.ts` 的「步骤意见绑定提交时的定义版本…」「投递状态只说真话…」「文件意见必须给齐轮次与阅读版本…」；桌面投影侧 `desktop-plans.test.ts` 的「意见按真实状态投影…」。

### 第 5 项：多会话/多项目、同名计划与来源主控归属提示

- 计划按**稳定计划 ID**（`p-YYYYMMDD-xxxxxx`）落 `<项目>/.pao/临时工作流/<计划ID>/`，同名显示名可并存，不用显示名拼路径；`来源会话` 记录在定义里。
- `queryTemporaryPlan(项目根, 计划ID?)`：单份给定义＋启动关联；全部给逐份摘要（含「已启动：实例 …」或「未启动」），坏定义点名进 `问题` 数组。
- 桌面投影 `readDesktopPlans` 把坏定义、坏启动关联、不可读目录都进 `问题`，不静默显示成「还没有计划」。
- **未做**：来源主控被关闭时的界面归属提示（需要 electron 侧接线）。
