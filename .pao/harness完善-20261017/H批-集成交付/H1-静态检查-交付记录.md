## 3. 红项逐条归因

**共同根因：本机 `process.platform === "win32"`，`path.join` 产出反斜杠 `\`，而护栏测试的断言正则写死了正斜杠 `/`。** 不是产品代码缺陷——产品输出内容本身完全正确。

### 3.1 `check-renderer-boundary.test.mjs`（35 条）— 路径分隔符

**4 类**失败标题（35 条是同一根因的 4 种变体）：
- `rejects import ...`（17 条）→ 期望 `/src\/index.ts:1:/`
- `follows aliased workspace re-exports ...`（1 条）→ 期望 `/packages\/shared\/runtime.ts:1: Forbidden/`
- `inline types retain runtime edges ...`（1 条）
- `checks Worker/SharedWorker URL entries ...`（4 条）
- `rejects contract implementation dependency: ...`（6 条）→ 期望 `/src\/index.ts:1: Forbidden renderer runtime import/`
- `rejects host-only extension-ui runtime import: ...`（6 条）

**实测证据**（`scripts/check-renderer-boundary.test.mjs:56:12` 处断言失败的 `Input` 原文）：

```
"apps\\desktop\\src\\index.ts:1: Forbidden renderer runtime dependency 'node:fs'. Use the preload API instead."
```

对照期望正则 `/src\/index.ts:1:/`：产品输出的内容是 `src/index.ts:1: Forbidden renderer runtime dependency 'node:fs'. Use the preload API instead.`——**语义与期望完全一致**，只是分隔符是 `\` 而非 `/`。这是一条**正确抓住了违规**的护栏，只是它的断言在 Windows 上读不到自己的产出。

### 3.2 `check-workspace-typechecks.test.mjs`（1 条）

- 标题：`pnpm discovery catches a new workspace without a typecheck command`
- 失败：`The input did not match the regular expression /modules\/new-workspace\/package.json: missing scripts.typecheck/`
- 根因：该 test 用 `mkdtempSync(path.join(os.tmpdir(), ...))` 造夹具（`scripts/check-workspace-typechecks.test.mjs:9`），本机 `os.tmpdir()` = `C:\Users\ASUS\AppData\Local\Temp`，故产物路径是 `C:\Users\ASUS\AppData\Local\Temp\pi-gui-workspaces-x\modules\new-workspace`——反斜杠。**与 3.1 同根因**。

### 3.3 `typed-lint.test.mjs`（1 条）

- 标题：`a new workspace cannot silently receive only syntax lint`
- 实际输出（原文）：`'packages\\new-feature: add a typed project in eslint.config.mjs; missing no-floating-promises, no-misused-promises, no-unsafe-argument, no-unsafe-assignment, no-unsafe-call, no-unsafe-member-access, no-unsafe-return.'`
- 期望：`/packages\/new-feature: add a typed project/`
- 根因：`packages\new-feature` vs `packages/new-feature`。**同 3.1**。

### 3.4 `test-entrypoints.test.mjs`（1 条）— **这条根因不同，值得单独记**

- 标题：`the public Electron helper loads through Playwright and the marketing script loader`
- 失败原文：`Listing tests: / Total: 0 tests in 0 files / Error: No tests found.`
- 断言位置：`scripts/test-entrypoints.test.mjs:107 assert.equal(result.status, 0, ...)`
- **不是路径分隔符问题**。该 test 在 `:96-105` 用 `spawnSync` 调 Playwright CLI `--list`，传入的是 **绝对路径** spec：`path.join(root, "apps/desktop/tests/core/smoke.spec.ts")`。

**我做的最小复现实验**（只 `--list` 列举，不运行用例、不启动 Electron）：

| 传参形式 | 退出码 | 结果 |
|---|---|---|
| 绝对 cfg + **绝对 spec** | 1 | `Total: 0 tests in 0 files` |
| 绝对 cfg + `core/smoke.spec.ts` | 0 | `Total: 3 tests in 1 file` |
| 绝对 cfg + `core\smoke.spec.ts` | 0 | `Total: 3 tests in 1 file` |
| 相对 cfg + **绝对 spec** | 1 | `Total: 0 tests in 0 files` |

即：**Playwright 的 spec 位置参数传绝对路径时匹配不到任何文件，传相对路径（正反斜杠均可）才正常**，与 `-c` 配置用绝对还是相对无关。这是测试夹具的调法问题，与产品代码无关。

> 参考：在 shell 里直接 `node node_modules/@playwright/test/cli.js test -c apps/desktop/playwright.config.ts apps/desktop/tests/core/smoke.spec.ts --list` 用**相对路径** → 退出码 0，`Total: 3 tests in 1 file`，列出 `core\smoke.spec.ts:15/33/81` 三条。

### 3.5 `contract-resolution.test.mjs`（1 条）— **本机环境导致，非本批引入**

- 标题：`SDK driver implements canonical SessionDriver and cannot omit tree operations`
- 失败原文（`scripts/contract-resolution.test.mjs:40:10`）：
  ```
  AssertionError [ERR_ASSERTION]: Expected values to be strictly equal:
    + undefined
    - 'D:\\AI\\workspace\\pao-dev\\desktop\\packages\\pi-sdk-driver\\src\\contract-proof.ts'
  actual: undefined
  expected: 'D:\\AI\\workspace\\pao-dev\\desktop\\packages\\pi-sdk-driver\\src\\contract-proof.ts'
  ```
- 根因：该 test 在 `:30-33` 重写 `host.getSourceFile` 做内存注入，用 `name === file` 判断命中的是**字面路径**；而 TS 编译器在本机产出的 `diagnostic.file.fileName` 已规范化，与 `file` 不严格相等，故 `diagnostics[0].file?.fileName` 取到 `undefined`。**属夹具跨平台健壮性问题，与产品代码无关。**
- 须同时注意 `:39 assert.equal(diagnostics.length, 1, ...)` **这一条是通过的**——说明类型检查本身正确地产出了恰好 1 条诊断，`SessionDriver` 契约的「不能漏 `getSessionTree` / `navigateSessionTree`」这条真正被守住了；红的只是随后取 `fileName` 的位置比较。
