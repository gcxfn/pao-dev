### 4.1 从零验证一轮：**中断，不计入**（2026-10-17 16:03–16:07）

**跑到哪一步**：起了打包 exe、注入了**空 PAO_HOME**、起了一轮真实对话（假 provider 收到带 50 个工具的请求、模型回了 `stopReason:"stop"`），
在等会话状态转 idle 时**页面被关闭**。

**报错原文**（`现场\从零输出.txt`，3514 B / 16:07:02）：
```
fatal: page.evaluate: Target page, context or browser has been closed
    at waitIdle (…\现场\驱动-从零.mjs:163:31)
```

**归因：外部中断，不是脚本缺陷。** 判据三条，都查了：

1. **驱动没有自己关窗**。`驱动-从零.mjs` 全文只有一处 `app.close()`，在 `:399` 的 `finally` 块里——`finally` 只在 `try` 结束后执行，而当时还卡在 `waitIdle` 里，**不可能被自己关掉**。
2. **时间线对上了**。现场 B 所有目录的**最后写入时刻都是 16:07:01**（`agent\sessions`、`PAO_HOME`、`userdata-zero`），`从零输出.txt` 是 **16:07:02**。一秒之差说明进程是被**从外面掐掉的**（正常收尾会先去跑 `finally` 里的 `app.close()`，再打印结果）。
3. **超时没到**。`waitIdle` 默认 `timeoutMs = 300_000`（`:157`），进入 `waitIdle` 是 **16:03:11**，报错在 **16:07:01** —— 才 230 秒，**离 300 秒超时还差 70 秒**。所以不是「脚本等超时放弃」，是中途被关。

### 4.3 启动关联 `starts` 为空：**这是正确行为，不是坏了**

三件事说清（lead 明确要求写准）：

1. **`starts` 是什么**：落盘位置是 `<项目>/.pao/临时工作流/<计划ID>/启动/<启动请求ID>.md`
   （`PAO/packages/coding-agent/src/pao/workflow/plan.ts:125-127` 的 `planStartRecordPath`）。
   它由「启动受理」这一步写：内核复核状态 → 在计划锁内落「这一版正在启动」的意图 → 才去真正启流。
2. **为什么本轮为空是「正确」而非「坏了」**：启动必须有**宿主确认事实**。内核 `plan-tools.ts:84-86` 要求宿主注入 `requestConfirmation` 回调；
   没注入且没有交互界面时，`plan-tools.ts:860` 直接抛：
   > `[PLAN_CONFIRM_REQUIRED] 没有可用的宿主确认回调，也没有交互界面：启动必须有宿主确认事实。请在宿主注入 requestConfirmation（桌面/CLI 的真实用户确认），无桌面集成时用明确模拟的宿主回调并如实标注——模型自述不算确认。`

   本轮走的是「Node 脚本里直接调 `startControl` 建实例」的取证路径，**没有经过宿主确认**，所以没人请求启动，`启动/` 目录压根没有——**空是对的**。
   在 Node 脚本里伪造一个"宿主确认回调"等于替用户按了确认键，那正是整批在防的假成功，所以**刻意不做**。
3. **谁能在哪一层验它**：桌面层真 Electron 用例（点「启动」→ 宿主确认对话框 → 落 `启动/<请求ID>.md` → 三处内容对得上）。
   **归桌面车道，不归本卡。** 已记入 H 批未验项。

- 现场 B（`D:\AI\workspace\_t24现场B`）**确实在 git 仓库外**——`git rev-parse --show-toplevel` 报 `fatal: not a git repository`，驱动也把这条写进了结果（`gitRootOfWorkspace` / `gitRootOfPaoHome` 均为空）。
- 但**这一轮没走到 `bindMinister`**（4.1 中断），现场 B 里**没有任何控制清单文件**，所以**拿不到「仓库外」的数值**。

**因此不并排写两个数字**——只有一个数，并排就是假的。这里如实记：

| 现场 | 工作区位置 | 控制清单 | 行数 | `test-results` 命中 | 结论 |
|---|---|---|---|---|---|
| `现场-干净` | 仓库内（`pao-dev`） | **509754 B** | **4710** | **23** | 实测 |
| `现场B` | 仓库外 | **不会生成**（不是"没跑到"，见下） | — | — | **已按代码事实定性** |

**根因已查实（2026-10-17 22:55，代码级 + 实测数字对上）——原先记的「待验猜测」现在成立**：

代码出处 `PAO/packages/coding-agent/src/pao/workflow/control.ts`：
- `:432` `const root = await gitOutput(["rev-parse", "--show-toplevel"], dirname(options.cardsDir));`
- `:435` `const cwd = root.text.trim();` ⇒ **`cwd` 是「git 仓库根」，不是项目根/工作区**（现场实测返回 `D:/AI/workspace/pao-dev`）
- `:442` `git add -u -- . :(exclude).pao`，**在仓库根执行** ⇒ 把**全仓**的已跟踪改动都暂存进这一份基线树
- `:448` `git ls-files --others --exclude-standard -z`，**在仓库根执行且没有任何 pathspec** ⇒ 列出**全仓**的未跟踪文件

**实测数字（Lead 亲跑，只读）**：在 `现场-干净\工作区` 所在仓库根执行同一条
`git ls-files --others --exclude-standard -z` → **4575 条未跟踪**，其中含 `test-results` 的 **23 条**；
而那份控制清单（`现场-干净\工作区\.pao\临时工作流\p-20261017-t24a1\执行\start-t24-1\工作流实例-临时-p-20261017-t24a1.md`，
**509754 B / 4710 行**）里 `test-results` 命中 **23 次**、`pao-dev` 命中 **2 次**。
**23 = 23**，且 4575 条未跟踪 ≈ 4710 行减去少量 frontmatter/正文行 ⇒ **这份 509 KB 就是被全仓未跟踪清单撑起来的**。

**旁证（同一概念有两套范围）**：卡级认领基线 `PAO/packages/coding-agent/src/pao/cards/baseline.ts:99-111`
的 `gitStatusEntries(projectRoot)` **做了** `-- .` 与 `:(exclude)…` pathspec、`cwd = projectRoot` ⇒ 它是**按项目根收口**的。
而上面 `control.ts` 的节点基线**没有**。同一个「git 基线」概念、两套范围 —— 与架构原则第 5 条
「同一规则只实现一次」不符。**这是本次查实的实质发现**：工作区若是某个 git 仓库的**子目录**，
节点内容基线会把整个仓库的改动与未跟踪文件都算进去，「worker 改了什么」因此无法归因。

**「仓库外」那半：不用再比了，结论与原先预设相反。** `:433` 在 `git rev-parse --show-toplevel` 失败时写
`node.基线错误 = "非 git 项目或 git 不可用:…"`，随后 `control.ts:818` 与 `status/results.ts:286` 把它**如实报出来**
（`缺 diff 基线：…` / `actualDiff = {可用:false, 原因:"缺 diff 基线：…"}`）。
⇒ 仓库外的后果**不是「控制清单更小」，而是「根本没有 diff 基线」**（产品不假成功，如实报缺）。
所以 §5.4 那条「工作区不要放在 git 仓库里」的建议，真实代价要改写成这个。

**修复方向属将来定案，本报告只报事实**（两种走法：把基线范围收到工作区；或至少与 `baseline.ts` 同口径加 pathspec）。
**未验**：现场 B（仓库外）仍未走到 `bindMinister`，所以「仓库外实测数值」这一栏仍空——但按上面的代码事实，那一栏**本来就不该有数值**。

**谁能验**：真要补实测，按 §4.1b 第4步正本 §6 的五步把驱动跑通即可；**但仓库外那半已不必再跑**。

## §5 可进发行说明的口径

这几条不是"我们做得不错"，而是**用户/维护者会踩的具体事实**，可以直接抄进发行说明。

1. **PAO_HOME 不猜、不默认、不回落开发仓。** 内核 `resolvePaoHome(env)` 没有默认值，缺就抛
   `缺少环境变量 PAO_HOME(使用现场根目录,应含「部门/」与「pao配置/」;开发仓与使用现场是两个仓库)`。
   桌面取值的四级顺序：**用户环境变量 > 设置页 > 便携版 exe 同级含 `部门/`+`工作流/`+`pao配置/` 三标记的目录 > 都不注入**（此时由内核报错）。
   不存在 `homedir()/PAO` 这种默认值。
2. **`PAO_DISABLE_BUILTIN_EXTENSION` 对打包发行物是死开关。** 它的判断只在 `@pi-gui/pi-sdk-driver` 按包名解析的那份副本里，
   而 asar 实际加载的是 `node_modules/@pi-gui/pi-sdk-driver/dist/*.js`。实测设 `"0"`/`"1"`/不设，三次结果**完全一样**。
   要确认扩展装没装，请看**会话级**命令清单（`state.sessionCommandsBySession["<工作区绝对路径>:<sessionId>"]`）里的 `pao` 与 `todo`（`sourceInfo.path:"builtin:pao"`），
   不要看 `state.runtimeByWorkspace[ws.id].extensions`（那是工作区级，不含内置扩展）。
3. **`PI_CODING_AGENT_DIR` 是真正生效的隔离手段**（模型/供应商配置读 `<override>/settings.json`），
   与内核 `getAgentDir()` 不是同一个解析——app-store 的注释原文：the app store passes no custom agentDir, so the default resolution here matches the driver's。
   不指它就会读到宿主机用户态 `~/.pi/agent`（会带进用户自己的扩展与模型清单）。
4. **工作区不要放在 git 仓库里**（这条目前是**建议**不是已验证结论，原因见 §4.4）。
   仓库内的现场产生了 509754 B / 4710 行的控制清单，其中 23 条是开发仓的历史 `test-results` 噪音。
5. **内核 dist 陈旧门会拒绝打包**：改过内核 `src` 后先 `npm run build`（在 `PAO/packages/coding-agent`），否则 `vendor-pao-kernel.mjs` exit 1，陈旧产物进不了包。
6. **不要在 `ELECTRON_RUN_AS_NODE` 存在时启动 `PAO.exe`**：Playwright 会给 exe 加 `--inspect=0 --remote-debugging-port=0`，
   而 exe 变成 Node 进程后直接报 `PAO.exe: bad option: --remote-debugging-port=0` 退出。先用 `Remove-Item Env:ELECTRON_RUN_AS_NODE`。

## §6 教训

按"会让人误判"排序，不是按发生顺序。

### 6.1 假 provider 必须走 SSE 流（第3步踩到）
内核走流式，收尾必须有 `finish_reason`；假 provider 回一次性 JSON 报 `Stream ended without finish_reason`。
判据在 asar 内 `@earendil-works/pi-ai/dist/api/openai-completions.js:479`/`:485-486`（判定）与 `:1267`（`supportsFinishReason: true`）。

### 6.2 让模型落文件时优先 `write`，不要先 `edit`
`edit` 要求 `edits` 数组，假 provider 只给替换串就报 `Validation failed for tool "edit"`——
但**模型侧会以为改成功了**，盘上两处都没写。证据看着像"产品没写盘"，其实是夹具造错了。

### 6.3 别手写内核认的 YAML，用内核自己的发射器
手写配方 YAML 两次都不被 `parseFrontmatter` 认（报缺「名字」「节点」）。正解：
`emitRecipeMarkdown(...)`（`PAO/packages/coding-agent/src/pao/workflow/distill.ts:72-116`）生成 → 再 `parseRecipe(content, filePath)`
（`recipe.ts:218`，**注意第二参是文件路径不是文件内容**）→ `saveRecipe(paoHome, name, content, options)` 四个位置参数。
另外：优先级/档位是英文枚举（`recipe.ts:384` `档位非法`/`:394` `优先级非法`），写中文"高"会被拒。

### 6.4 `SITE` / `EXE` 必须绝对路径（第4步踩到）
`resolve(process.env.SITE)` 给相对路径会把工作拼到 `C:` 上，报错是 `spawn C:\Windows\system32\cmd.exe ENOENT`——看不出真因。

### 6.5 猜 API 签名会让夹具静默走错路（本步踩了 4 次）
`parseRecipe` 第二参是路径不是内容、`saveRecipe` 是四参、`startThread` **返回整份桌面快照**（不是 `{sessionId}`，要前后差集找新会话）、
`getTemporaryPlans` 收对象不是字符串。修法已全部落到 `运行须知-本机core-lane.md` 的**陷阱 8**。

**2026-10-17 22:45 追加第 5 个**：`selectWorkspace` 收**裸字符串**（`api.selectWorkspace(workspaceId)`），
而紧邻的 `selectSession` 收对象（`{workspaceId, sessionId}`）——**同一个 API 面上两种形状，猜必错**。
`驱动-从零.mjs:349` 就栽在这里（产品报 `TypeError: workspaceId must be a string`）。另外 `waitIdle` 要能接受
「进来时就已经 idle」（会话 31 ms 内就收尾时，等 `running` 会白等到超时）。

### 6.6 中断要用时间线证明，不能凭"我觉得"
本次判断"外部中断还是脚本缺陷"，靠的是三条硬判据：驱动唯一的 `app.close()` 在 `finally`（`驱动-从零.mjs:399`）而当时还卡在 `waitIdle` 里；
现场全部目录最后写入 16:07:01、输出文件 16:07:02；`waitIdle` 超时 300 秒而实际只等了 230 秒。
**三条缺一条都不能下"是中断"这个结论。**

### 6.7 夹具提示词里的工具名，必须与内核注册名逐个核对
第二次从零复跑最值钱的一条教训：提示词让模型「用 `pao_dept` 工具」建部，**这个工具名在内核里根本不存在**
（真名 `pao_create_dept`，`PAO/packages/coding-agent/src/pao/dept/index.ts:51`）。
夹具不会报错——它只会「照剧本走完、什么都没建成」，然后看报告的人会以为**产品没做到**。
**规则**：凡在夹具/提示词里点名某个工具，写之前先 grep 内核注册名；报告里凡出现「模型没做 X」，
先确认 X 的工具名写对了。这条与 6.5 同源，但后果更重：6.5 是夹具静默走错路，这条是**结论被写反**。
