## 4. 本步踩到的坑（都已修，按教训价值排序）

### 4.1 内核走 SSE 流，假 provider 回一次性 JSON 必失败
症状：会话 `failed`，assistant 消息 `stopReason:"error"`、`errorMessage:"Stream ended without finish_reason"`、`usage` 全 0。
判据（asar 解包内）：`pi-ai/dist/api/openai-completions.js:352 for await (const chunk of openaiStream)`、
`:206 let hasFinishReason = false`、`:485-486 if ((compat.supportsFinishReason && !hasFinishReason) || output.stopReason === "pending") throw new Error("Stream ended without finish_reason")`、
`:1267 supportsFinishReason: true`。
修法：`text/event-stream; charset=utf-8`，每块 `data: {json}\n\n`，最后一块带 `finish_reason` 与 `usage`，结尾 `data: [DONE]\n\n`。

### 4.2 工具名必须优先 `write`，不能拿 `edit` 冒充新建
原实现 `toolNames.find((n) => n === "write" || n === "edit")` 命中的是 `edit`，回 `{path, content}` →
`Validation failed for tool "edit": - edits: must have required properties edits`，两处都没落盘，
**但模型侧看到的是「成功」继续往下说**。修法：先找 `write`，找不到才退 `edit`。
教训：假 provider 的回执要按真实工具契约造；「看起来成功」≠ 落盘。

### 4.3 别手写内核认的格式，用内核自己的发射器
手写配方 YAML 两次都不被 `parseFrontmatter` 认（报「配方 缺必需字段「名字」」「配方缺「节点」表」）。
正解：`emitRecipeMarkdown({版本, 名字, 自动执行, 参数, 说明, 节点:[{名字,目标,部门,验收,输入,约束,审核,只读,工人数量,允许请求主控裁定,depends_on,人工确认}]})`
（`src/pao/workflow/distill.ts:72-116`），再喂 `parseRecipe(content, filePath)`。

顺带记准三个签名（这次都猜错过）：
- `parseRecipe(content: string, filePath: string): WorkflowRecipe`（`src/pao/workflow/recipe.ts:218`）——**不是**传文件路径；`readRecipe` 不存在。
- `saveRecipe(paoHome, name, content, options)` —— **四个位置参数**。
- 优先级/档位只有英文枚举：`CARD_PRIORITIES = ["high","medium","low"]`、`CARD_TIERS = ["fast","primary"]`；写「高」报 `节点[0]「s1」 优先级非法：高`。

### 4.4 改夹具要连带重跑种子脚本
第一次把优先级从「高」改成 `high` 后仍报同样的错 —— 因为**盘上的种子文件还是旧内容**，只改了驱动。

### 4.5 `SITE` 是 `resolve(process.env.SITE)`，必须给绝对路径
给相对路径 `现场-干净` 时被解析到 `现场\现场-干净`，Playwright 起来时 `cwd` 指过去，
直接 `Error: spawn C:\Windows\system32\cmd.exe ENOENT` —— 这个报错完全看不出真因（现场目录不存在）。

### 4.6 卡号「同号」不是缺陷
执行目录卡 `卡0001/卡0002` 与任务目录 `卡0001-第一章.md` 同号，但两者**共用** `工作区\.pao\卡号.txt`（内容 `2`），
符合内核既定口径（`test/pao/cards-cardfile.test.ts:121-137`「同一项目所有卡目录共用 .pao/卡号.txt 连续发号」）。
而且任务目录那张是假 provider 按旧提示词写的**中文键、无 `card_no`** 的非协议卡，内核根本不认（`status: null`）。

### 4.7 控制清单 509KB 的成因：现场落在 git 仓库里
`bindMinister` 会做 git 基线：`git rev-parse --show-toplevel` → 临时 index → `add -u` → 记未跟踪列表。
本次工作区在 `D:/AI/workspace/pao-dev` 这个 git 仓库内，基线把仓库里 23 条历史 `test-results` 路径收进未跟踪清单，
于是控制清单 4709 行 / 509754 字节。**根因是现场布置，不是产品缺陷**；但说明基线扫的是 **git 仓库根**而非 PAO 项目根，
布置现场应把工作区放在仓库之外。

## 5. 口径（可直接写进 H 批发行说明）

### 5.1 `PAO_HOME` 不猜、不默认
内核 `resolvePaoHome(env = process.env)`：`let home = env.PAO_HOME?.trim(); if (!home) throw new Error("缺少环境变量 PAO_HOME(使用现场根目录,应含「部门/」与「pao配置/」;开发仓与使用现场是两个仓库)");` ——
**无默认值、缺就抛错、绝不回落开发仓**。桌面四级优先级：
① 用户环境变量 → ② 设置页配置 → ③ 便携版 exe 同级含 `部门/`+`工作流/`+`pao配置/` 三标记的目录 → ④ 都不注入（内核报错）。

### 5.2 `PAO_DISABLE_BUILTIN_EXTENSION` 对打包发行物是死开关
它的判断只在 `@pi-gui/pi-sdk-driver` 包内「按包名解析」的 `npm-package-fallback` 副本里。
实测设 `"0"` / `"1"` / 不设，三次结果完全一样（会话级命令表里 `pao`、`todo`一直都在）。
**不要拿它当「装不装 pao」的开关。** 真正的隔离手段是 `PI_CODING_AGENT_DIR`（隔离用户态 `~/.pi/agent`）。

### 5.3 「pao 扩展在不在」要看对地方
`state.runtimeByWorkspace[ws.id].extensions` 是**工作区级**清单，里面本来就没有 pao。
会话级真值在 `state.sessionCommandsBySession["<工作区绝对路径>:<sessionId>"]`，那里 `sourceInfo.path = "builtin:pao"`。

2. **② 的「从零派发」没验**：本轮脚本因实例已存在而跳过起实例与交卡，读到的是上一轮的真结果。要证从零派发，需换新 `planId`/新现场。

4. **部门面板的可视证据没截**：部门投影的真值已证（`departments:["写作","审校"]`），但「在扩展面板里看得见」这一层只用通道核实，没开面板截图取证。
5. **假 provider ≠ 真模型**：本步证的是「发行物里的链路通、文件真落盘、投影真读回」，不证模型输出质量。
