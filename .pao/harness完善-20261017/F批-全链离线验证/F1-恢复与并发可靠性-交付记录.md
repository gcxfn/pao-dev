### 2.9 T19-4 源主控关闭后旧动作失效（3 例，m01061 补活）

补的是 T14「多视图同待办」在内核侧的**另一半**：源主控会话关闭后，旧动作不能再被使用。

判据全部走真实入口 `src/pao/desktop/owners.ts` 的 `registerDesktopOwner` / `desktopOwner` / `desktopOwnerEntry`，**不自造替身**。夹具 `ownerHost()` 只实现 `pi.on`，通过 `fire(event, sessionId, cwd)` 触发真实的 `session_start` / `session_tree` / `session_shutdown`，让 owners 自己的登记与注销逻辑跑起来（`owners.ts:47-51`）。owner 表是模块级 `Map`，故每个用例用互不相同的 sessionId 与项目路径隔离。

| 用例 | 断言 | 结果 |
|---|---|---|
| 错 sessionId／错项目路径 | 正常路径取得到；换成未登记的 sessionId → 抛 `原会话 owner 不可用或已切换` ＋ `请回到对应会话重新查看，不能重放旧动作`；同一 sessionId 配另一个项目路径 → 同样两条都在 | 通过 |
| 源主控关闭 | 登记后 `desktopOwnerEntry` 有值、`desktopOwner().ctx.cwd===project`；触发真实 `session_shutdown` 后 → **条目变 `undefined`**（不是残留）；再取直接抛 `原会话 owner 不可用或已切换`，**不返回别人的 entry** | 通过 |
| 同项目第二个会话（见下） | 记为缺陷现状，注释固定证据 | 通过（断言的是现状） |

**该组第 3 例查出既有缺陷（只报不改）**：`src/pao/desktop/owners.ts:35-51` 的 `registerDesktopOwner` 每次调用只创建**一个**闭包变量 `let id`，`bind` 与 `session_shutdown` 处理器都只认它，等于「一个宿主只跟踪一个会话」：

```ts
let id: string | undefined;
const bind = (_event, ctx) => {
    if (id && owners.get(id)?.pi === pi) owners.delete(id);  // 删「上一次记的」那条
    id = ctx.sessionManager.getSessionId();                  // 再把 id 换成新的
    owners.set(id, {...});
};
```

第二次 `session_start` 确实删掉了旧的那条，但删完就再没人记得它存在过——「清理旧条目」变成了「丢掉旧会话」，而那个会话其实还活着。实测（临时探针，跑完已删）：

```
只登记一号        → 一号=true
再加登记二号      → 一号=false 二号=true
再加登记三号      → 一号=false 二号=false 三号=true   ← 只剩最后一个
两个不同 pi 各登记 → A=true B=true                     ← 不同宿主互不干扰
```

影响面：桌面多窗口／多会话同项目时，非最新会话的读投影会全部失效，用户看到的是「原会话 owner 不可用或已切换」，而会话根本没关。`session_shutdown` 同理只注销最后一个 id。修复方向：`bind` 别用单变量记 id，改为按 `ctx` 拿到的 sessionId 精确增删（或每个 pi 维护 id 集合）。

`src/pao/desktop/` 在 task-19 原写范围内，Lead 也已明令「不改 src/」，故当时**只报不改**；本用例断言的是**当前真实行为**并注明这是缺陷，没有放宽成模糊断言、也没有删掉这条用例掩盖问题。**后续 m01174 授权修复，见 §2.10。**

### 2.10 owners 多会话丢条目缺陷的修复（m01174 授权）

Lead 核实后确认缺陷成立，并补了两条我漏掉的更严重判断：**① `session_tree` 绑的是同一个 `bind`，所以单窗口切分支就会丢掉前一个会话（不止多窗口）；② `session_shutdown` 只删「最后登记的那个 id」，关 B 会把 A 一起删掉。** 另外 `readDesktopWorkerActivity` 按 owner 统计活性，所以这是「活性统计漏人」，不只是读投影报错。

#### 修复前（`git show HEAD:.../owners.ts` 对应行为）

| 测试点 | 修复前 |
|---|---|
| 一号登记 → 二号登记 | 一号被静默删除（`owners` 里只剩最后登记的那个） |
| 关 B 会话 | A 的条目也一起没了（shutdown 只认闭包变量 `id`） |
| `session_tree` 切分支 | 同 pi 其他会话被丢 |
| 三会话同项目活性统计 | 只统计到 1 行 |

#### 修复做法（`src/pao/desktop/owners.ts`，`54 insertions(+), 20 deletions(-)`）

- 新增 `const piSessions = new WeakMap<ExtensionAPI, Set<string>>()`：按 pi 维护「本宿主名下有哪些会话 id」，WeakMap 不持有 pi 强引用；**没有引入模块级可变单例**。
- 抽 `remember(pi, ctx, sessionId, options)`：写 entry 并把 id 记进本 pi 集合。
- 抽 `forget(pi, sessionId)`：先从集合删，再**只在 `owners.get(id)?.pi === pi` 时**删条目——别人的会话一条都不碰。
- `session_start` → `bind`：只 `remember` 当前 ctx 的 id，**不删任何别的 id**。

              { 轮次:2, 卡:[], 原因:"缺结尾" } ]

根因在 `src/pao/desktop/plans.ts:243-248` 的 `stepRecords`：历史轮次只读 `round.判定?.结果`，而 `decideNode`（`src/pao/workflow/control.ts:654`）压进历史的 `判定` 取的是 `target.判定`——change 分支刚在 `:659` 把 `target.判定` 清成 `undefined`，所以被动的那一轮**永远拿不到判定**。后果：界面能说「为什么被打回」（`原因` 在），但说不出「哪一轮被谁判成什么」，要拿得回控制正本自己翻 `历史[].判定`。

处理：`f-results-files.test.ts` 用 `it.fails` 钉住现状（第 3 例），**没有擅自改 `plans.ts`**——这属 R07 之外的语义调整，改法有两种（历史里存「被谁判定」还是「判定结果」，会不会与 `判定` 的既有语义冲突），要 Lead 裁定。

### 跑红归因（4 次跑红，全是夹具／断言写错，未放宽任何断言）

1. **`link.配方()` 被当函数调用** —— `链路` 接口里没有 `配方` 字段（残留写法）。修法是补字段并改 `link.配方`，不是改断言。
2. **`[FLOW_CONTROL] 节点未就绪或部长会话为空`（`control.ts:428`）** —— 夹具漏了生产步骤 `endDecomposition`。`ready()`（`control.ts:192-196`）看的是**前置节点是否 complete**，而上游节点交付后必须由部长宣布本轮拆解结束，下游节点才算就绪。真实工作流就是这么走的，所以补进 `交一稿` 末尾，不是放宽。
3. **`[FLOW_CONTROL] 旧轮次、错误实例或部长会话；拒绝推进当前节点`（`control.ts:416`）** —— 我想直接用 `轮次: 2` 派第 2 轮的卡。但 `identify()` 要求 `identity.轮次 === node.轮次`，轮次是**控制正本自己往前拨的**（只有 `decideNode` 的 change 分支做 `target.轮次++`）。这恰恰说明设计在防「凭空造轮次」，于是改成走真实回边造第 2 轮——用例因此比原计划更强，它证明的是「真实打回路径下旧稿新稿都在」。
4. **摊平事实表的 `for (const line of facts) expect(line).toMatch(/：/)`** —— 两条事实写成「第 1 轮执行过，卡 卡0001」「第 1 轮（卡0001）这份文件在盘上」，没有中文冒号。改摊平函数的格式（补「卡：」「状态：」），断言不变。

另有一次自我更正：我原以为「打回那一轮 `判定` 应为 `change`」是我断言写错，改用探针查证后发现**是真实缺陷**（见上节），于是把该断言从普通 `it` 改成 `it.fails` 并写明根因行号——**没有删掉这条断言**。
