## 一·补、计数口径订正（lead 复跑对不上时查这里）

lead 独立复跑 `f-failure-matrix.test.ts` 得 CJK=1740，我报的是 1946，差 206。已查清原因：

| 正则 | 结果 |
| --- | --- |
| `[\u4e00-\u9fff]`（纯汉字） | **1740** ← lead 用的就是这条 |
| `[\u3400-\u4dbf\u4e00-\u9fff\uf900-\ufaff]`（扩到扩展 A 与兼容区） | 1740 |
| `[\u3000-\u303f\uff00-\uffef\u3400-\u4dbf\u4e00-\u9fff]`（**含中文标点与全角**） | **1946** ← 我原来用的就是这条 |

差别就是 `。`、`、`、`；`、`：`、`（`、`“”` 这类中文标点与全角字符 206 个。**两个数都不是错，是口径不同。**

**订正后的报数规矩（本记录之后一律照此）**：

- 必须报的硬指标只有两个，它们是可复现的：**`bytes`** 与 **`U+FFFD`**。
- 若要报 CJK，必须连同正则一起报，且默认用 `[\u4e00-\u9fff]`（纯汉字）。
- 按此复算：`f-novel-loop.test.ts` **55770 字节 / FFFD 0**；`f-failure-matrix.test.ts` **16908 字节 / FFFD 0**。汉字数分别为 6506（lead 复跑一致）与 1740。

**教训**：「我报的数别人跑不出来」比数字本身高低严重得多。同一批次里同名字段（CJK）必须同口径，否则每一条结论都要被重复怀疑一次。

## 四、小说五步：每步断言了什么

| 步 | 节点 | 断言 |
| --- | --- | --- |
| 1 设定 | s1设定 | 产物真落在 `创作成果/<planId>/s1/1/设定.md`（**普通目录，不是被 git 排除、被忽略的 `.pao/`**）；`git check-ignore -v` 对产物路径返回空；内容来自本轮来源 |
| 2 大纲 | s2大纲 | 等全部前置 `complete()` 才 `ready()`；未满足时被拒且原因如实 |
| 3 首章 | s3首章 | 正文进真实 diff/提交；正文明确模拟，不评价真实质量 |
| 4 审稿 | s4审稿 | **至少一次真实打回**，走真回边 `decideNode({结果:"change", 目标:"s2大纲"})`；产出意见文件；该节点是**写卡**（`只读` 不为真） |
| 5 修订/确认 | s5修订确认 | 旧稿（在 git 历史里）/ 意见 / 新稿都可查；`controlReport(flow).status !== "completed"` 直到 `confirmControl` 成功 |

关键实现事实（写下来供后续复用）：

- **成功交卷的 stage 是 `完成`，不是 `交卷`**（`auto.ts:446-451`：`stage: delivery.交卷 || !delivery.原因 ? "完成" : "停审"`）。字面值 `交卷` 在成功路径上从不出现——我一开始按它断言，是断言错。
- **一次 `drive()` 只按拓扑序推一遍**：部长写完判定后，下游节点要等下一轮才 `ready()`。所以用例体写成 `for (let i = 0; i < 3; i++) props.push(await driver(fixture));`。这不是产品缺陷，是 drive 的既定语义（每轮 `runAutoChain` → 部长批 → 再 `runAutoChain`）。
- 人工门「必被拒」是我臆造的断言：`confirmControl` 本身就是点门动作，条件满足时它**就该成功**。真正被拦的是条件不满足时——改为用错轮次调 `confirmControl(..., 节点.轮次 + 1)` 断言 `旧确认或节点尚未满足确认条件|人工确认`，再用正确轮次确认成功。

## 五、验收判据：改前是占位句，改后是真判据

**改前**（缺陷）：夹具的 `submit()` 写 `acceptance: "按验收"` —— 一句人话。`verifier.ts:77-81` 的 `parseAcceptance` 只认行首 `跑:` / `存在:` / `包含:`，人话句一律归「人工/审查口径（§12 边界）」⇒ **验收环节被整条短路，从没真判过一次**。

**改后**：`submit()` 从配方节点定义的 `验收` 取真值写进卡（`acceptance: def.验收`）。配方侧必须写成引号字符串（`验收: "存在: <路径>"`）；YAML 块映射 `验收:\n  存在: X` 会解析成对象，被 `recipe.ts:185-197` 的 `requireString` 判为缺字段。全仓 130 处先例，如 `test/pao/dispatch-workflow-skills.test.ts:38`、`test/pao/workflow-auto-chain.test.ts:103`。

**实证收益**：接入后用例一首卡的验收步变成 `验收｜全过自动交付（机械条目 1 条全过，已自动落已交付）`，此前是 `无法机械判（验收无可机械核对的条目（1 条人话句），走人工/审查口径（§12 边界））`。占位句确实把验收短路了。

**对既有 4 条断言的影响**：接入真判据后，s1/s2/s3 的卡都能真判通过（产物路径与声明一致）；s4 曾因「重做轮写新轮次目录」被判 `- [存在] 创作成果/第一章/s4/1/审查意见.md → 未过（文件不存在）`，那是**替身违背声明**，不是判据错（见第六节）。除此之外没有断言靠占位句蒙过。

## 六、关键发现：**产品不提供轮次占位符**——替身产物路径必须写声明路径（F 批最容易被踩的一条）

> lead 要求把这条单独成节，理由：**产品不提供轮次占位符是真实约束，下一个写场景测试的人一定会踩。**

### 6.1 事实

`recipe.ts:119` 的 `PLACEHOLDER_PATTERN = /\{([^{}\s]+)\}/g`，`substituteParams`（`:135-137`）**只替换已在配方「参数」里声明且有值的 `{名字}`**，未提供参数时原样保留。全仓**没有 `{轮次}` / `<round>` / `{stepId}` 这类占位符**。

所以配方里写 `创作成果/<planId>/s2/1/大纲.md`，到第 2 轮（重做轮）**还是同一字符串**——路径里的 `1` 是固定的，产品不会替你换成 `2`。

而消费侧是逐字机械核对的：`verifier.ts` 按这个字符串判存在；`baseline.ts` 的 `checkBoundaryWrite` 按这个字符串核对 git 改动是否与声明相符。

### 6.2 我踩的坑（第一版设计，错的）

我最初让替身在重做轮把 `sN/1/` 换成 `sN/2/` 再写文件。后果两条：

1. s4 卡的验收判 `- [存在] 创作成果/第一章/s4/1/审查意见.md → 未过（文件不存在）`，卡停 `in_progress`；
2. s2 卡被自动交付拦截：`越界核查 虚报：虚报 1 项(声明未写):创作成果/第一章/s2/1/大纲.md（改动与声明对不上，结果不可信）`，卡落 `failed`。

### 6.3 判定：**产品没错，错的是替身**

那条虚报判据本身是对的——声明写了 A 文件、git 里改的却是 B 文件，产品当然不该信。假如当时为了让它绿去放宽 `checkBoundaryWrite`，就是把一条真实的护栏拆掉。**这不是妥协题，是替身写错了。**

### 6.4 正确的替身行为（现行实现）

- **重做轮仍写声明路径**：`const actual = relative;`（不再把轮次塞进路径）。
- **但内容必须变**：正文追加 `<!-- 重做轮：<本轮重做理由> -->`。理由很实在——真实的重做就是改稿，内容不变反而失去「新稿」的意义。
- 旧稿因此退到 git 历史里，用 `git log --oneline --all -- <该路径>` 仍可查到——这正好满足第 5 步「旧稿/意见/新稿都可查」。

### 6.5 给下一个写场景测试的人

1. 配方里的产物路径**每轮相同**，不要指望产品按轮次改路径；
2. 若某步真的需要按轮次分目录，只能在**配方参数**里传（`{目录}` 这种已声明的参数），不能靠产品内建占位符；
3. 替身/worker 写文件时，**写的路径必须与卡上 `验收` 声明逐字一致**，否则先被验收判未过、再被越界核查判虚报，两处都会红；
4. 重做轮的区分靠**内容**（改稿），不靠**路径**。

## 七、验收判据真的会拦（否定支，与主线脱钩）

独立 `describe("验收判据真的会拦（否定支）")`，不共享主线的状态机路径，理由是要让这条证据不挂在别处。

单节点链 `只验收节点`，`验收: "存在: 创作成果/第一章/s1/1/设定.md"`，worker 故意只写 `创作成果/第一章/s1/1/别的文件.md`。断言：

1. 卡只有 1 张、`status === "in_progress"` 且 `not.toBe("delivered")`；`frontmatter.acceptance` 等于 `存在: 创作成果/第一章/s1/1/设定.md`（证明卡上是机械判据不是人话句）；
2. 错误产物存在、声明路径不存在（拦的是「声明路径」，不是随便拦）；
3. `report.steps` 的 `stage === "验收"` 步 note 含 `未过` 与 `条未过`；
4. 卡正文 `## 机械验收` 段含 `- [存在] 创作成果/第一章/s1/1/设定.md → 未过（文件不存在）` 与 `- 结论: 未过`；
5. 无 `stage === "完成"` 步、`git log --pretty=%s` 不含「交付」。

⇒ 验收判据**双向都验过**：该过的过（主线 s1–s3 真判 `全过自动交付`）、该拦的拦住（本条）。

## 八、只读审查链与两层拒绝

只读审查节点链独立于小说五步：真实读取指定材料、通过真实协议交审查记录、正确结束。

**lead 的三条断言全部落地**：

- 断言 A（被审查目录快照逐字节不变）：跑完后被审查目录（含 `待审查稿/第一章-旧桥-v1.md`、`待审查稿/只读目录说明.md`）内容与跑前快照逐字节相同。
- 断言 B（审查记录落点在被审查目录**之外**）：审查记录写到真实产出位置，不在被审查目录里。
- 断言 C（**本次是有文件的，不是零文件**）：显式断言 `审查意见.md` 真实存在、内容片段与写入时刻都贴进断言。理由是 §11.2 只说「可零文件」并非唯一合规形态；不写死这条，后来者会把零文件当默认，拿零文件替换真实产物。
- 负向（能力有界）：审稿卡既然写得进审查记录，就有写能力，那它**不该**能写进被审查目录 ⇒ 故意让它往被审查目录写必须被拒，卡状态不得变假成功。lead 原话的精神：证的是「能力有界」，不是「什么都不做」。

**两层拒绝**：白名单层（`只读: true` 卡无 write 工具，`addNodeCards` 直接拒，原文 `只读节点不能派工或写项目；由受限部长读证据并判定`）+ 文件系统层（真 `FileAttributes.ReadOnly`，失败带 `EACCES`/`EPERM`，ACL 用完恢复）。

## 九、第 4 条硬问题：定稿答案

**问**：在所有前置都满足的正确上下文里，`addNodeCards` 对 `只读: true` 节点派工报哪句？

**答**：报 `只读节点不能派工或写项目；由受限部长读证据并判定`（`control.ts:509`）。**夹具前提不全，不是产品缺陷。**

门序是 `identify(flow, identity)`（`control.ts:506`）→ `node.拆解结束 || !inputs.length`（`:507`）→ `def.只读`（`:509`）。`identify()` 自己判 `实例/节点/轮次/部长会话` 四件事，再判 `flow.暂停 || !ready(flow, node)`。所以前置不全时先撞的是身份门或就绪门（原文 `旧轮次、错误实例或部长会话；拒绝推进当前节点` 或 `实例已暂停或前置未完成`），根本走不到只读门。

补齐方式（用例五已按此实现）：`bindMinister("阅读审查","session-只读")` → 从控制正本读回真实 `轮次` → 再 `addNodeCards`。期望文案**一字未改**。

这也给出 F 批的一条正式结论：**报错不指向真因**是这些门序的固有后果——用户看到的是「旧轮次、错误实例或部长会话」，而真因可能是「这节点压根不能派工」。

## 十、用例一归因（原 L509 那个「黑洞」）

**结论：夹具时序，不是产品缺陷，也不是产品缺重复建卡防护。**

1. **`endDecomposition` 的调用者**：全仓唯一产品调用点是 `src/pao/workflow/minister.ts:86`（工具 `pao_breakdown_done` 的 execute）。也就是说**只有部长自己能结束拆解**，桥和自动链都不会替它调。所以「交付后 `拆解结束` 仍为 false」不可能是原子性 bug——这条链没走到那个动作就是夹具没让它走。
2. **探针结论**：`endDecomposition` 每次都成功、正本 `拆解结束` 每次都变 true。原先看到「交付后仍 false」是探针读到了**下一轮**的状态（回边推进后 `decideNode` 的 change 分支会重置 `拆解结束`），不是缺陷。
3. **卡0004/0005 是谁建的**：`bounced` 使 `s2大纲` r1 判定 `change` → `decideNode` 把 s2 及其下游 s3 推进到 r2 → s3 在 r2 重新 `addNodeCards` 建卡（卡0004/0005）。同目标建第二套卡是**产品真实语义**（重做轮本来就该重新拆解建卡），不是「已交付轮次仍允许重复建卡」的漏洞。
4. **s3首章被唤醒两次**：一次是 r1 拆解，一次是 r2 重做轮。两次都是桥在 `eligible` 判定下正常唤醒，不是重入 bug。

## 十一、:621 / :717 两条已绿的真相（别误读成产品修好了）

## 十九、待裁定缺陷 #5：回边重做后部长绑定无法转移（lead 已裁定，本轮不修）

**定性：产品缺陷**，不是夹具问题，也不是设计取舍。三件事连起来，就是「回边这条路，产品要求人做一件它没提供入口的事」——和「中途改要求无公开入口」同类：**链路设计里有的动作，产品没给门。**

- **源码坐标**：`control.ts:625-666` 的 `decideNode` change 分支清了 `卡/拆解结束/判定/基线/零卡理由/重做理由`，**唯独不清 `部长会话`**；`:420-431` 的 `bindMinister` 见「已绑定其他部长」直接拒；`resumeControl` 只清暂停与 reject 判定，**全仓无解绑 API**。
- **栈证据原文**：`control.ts:79 fail ← :429 ← :353 mutate ← withFileLock ← host-bridge.ts:289`。
- **本轮不修的三条理由（lead 定）**：
  1. `workflow/control.ts` 不在 F 批任何卡的写范围，F 批是验证批，不开口子做设计改动；
  2. 「接管」不是一个字段操作，是**授权语义**：谁能接管、旧部长还在跑怎么办、接管要不要留痕、接管失败怎么回滚——这四条不定义清楚，清一个字段就是把洞从「撞门」变成「两个人同时写控制正本」；
  3. 修它会波及 `workflow-control`、`workflow-auto-chain`、`workflow-host-bridge` 三组既有用例的基线。
- **夹具怎么补的**：`takeoverMinister()` 补这一步，并往控制正本 `记录` 留痕。lead 认定「替身补齐 ≠ 作弊」，前提三条：①标明是替身 ②留痕 ③在报告里立成缺陷不藏起来——三条都做到了。
- **H 批两条路（选一）**：
  - **路 A**：`decideNode` 的 change 分支同时清 `部长会话`。简洁，但「谁都自动能接」风险高。
  - **路 B**：`resumeControl` 加显式接管参数（`接管部长: true` 或 `接管会话: <id>`），只有人显式下命令才转移。安全，但要扩 API 与命令面。
  - **lead 倾向 B**：它和 `/pao budget 归还` 那条人工命令是同一个形状——**涉及「谁替谁做主」的动作一律要人显式下令，不搞自动**。最终拍定属 H 批设计决策。
