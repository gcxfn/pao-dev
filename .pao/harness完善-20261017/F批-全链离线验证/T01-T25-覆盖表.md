## 填写口径（先读这一段，否则表会骗人）

- **场景一句话**：抄计划 §11.3「操作」列原文，不改写、不合并。
- **对应层级**：只能填计划 §11.1 的六层之一或组合 —— 定向单元 / 真协议＋离线替身 / 真 Electron / 解包发行 / 机器重启-DPI-读屏 / 真实供应商。**层级决定能宣称什么**：真 Electron 只能证明页面/焦点/侧栏/文件/原主控/终端，不能因为它是「真的」就去顶打包、重启、读屏。
- **证据文件与用例名**：写到 `文件:行号` 与用例名（it 的标题）。交付记录里的自述**不算证据**，只算线索。
- **实际运行命令**：本卡作者**亲自执行过**的完整命令（含工作目录）。没亲手跑过的，这一列留空。
- **真实结果计数**：照抄终端输出的 `Tests N passed` / `N passed (Xs)`。**不许把「别人说通过了」写成计数**，也不许写「全绿」「全量通过」。
- **结论**：只允许三值 —— `通过` / `部分` / `未验`。`部分` 必须在最后一列说明「哪一半没验」；追不到真实命令与计数的，一律降为 `部分` 或 `未验`。
- **未验原因或缺口**：按 §11.1 的层级写真实原因（需要真实供应商 / 需要机器重启 / 需要 125% 系统 DPI / 需要读屏软件 / 需要解包发行版 / 需要人在场），不写「暂未覆盖」这类含糊话。

## 六、与 §11.1 层级的对照：本表显式写下的「不能宣称」

为避免「某项在真 Electron 里跑过」被读成「打包/重启/读屏也过了」，逐层记死边界（原文见计划 `:393-400`）：

| 层级 | 只能证明 | 不能宣称 |
|---|---|---|
| 定向单元 / 边界 | 函数与契约级行为、错误分支 | 真实桌面、真实供应商 |
| 真协议＋离线替身 | 内核派发、受理、恢复在真实协议下的行为 | 真实模型内容质量与费用 |
| 真 Electron（Windows） | 页面、焦点、侧栏、文件、原主控、终端 | 打包、机器重启、读屏自动通过 |
| 本地解包发行 | 发行人环境下小说关键流与重开 | 已发布、正式数据 |
| 机器重启 / 系统 DPI / 真实读屏 | 各自那一项的实际操作证据 | zoom、ARIA、应用重开均不可替代 |
| 真实供应商 | 真实创作质量与费用 | **未授权调用，离线通过不等同此层** |

## 十一、本轮新发现的产品缺陷（只记不改，待裁定）

### 缺陷 #6：被打回那一轮的「判定」在桌面投影里丢失

**症状（探针实录）**
```
s1 records: [ { 轮次:1, 卡:["卡0001"], 原因:"缺结尾" }, { 轮次:2, 卡:[], 原因:"缺结尾" } ]
s2 records: [ { 轮次:1, 卡:["卡0002"], 判定:"change", 原因:"缺结尾" } ]
```
`s1` 第 1 轮本该有 `判定:"change"`，投影里没有。

**根因（源码级）**：`PAO/packages/coding-agent/src/pao/workflow/control.ts:632-665` 的 `decideNode` change 分支先 `target.历史.push({轮次, 卡, 判定: target.判定, 原因: decision.理由})`（`:654`），**紧接着 `:659 target.判定 = undefined`**；而 `PAO/packages/coding-agent/src/pao/desktop/plans.ts:243-248` 的 `stepRecords` 对历史轮只读 `round.判定?.结果`。于是凡被打回过的轮，投影里都没有「本轮回边」这件事。

**影响**：§5.2 要求的「旧稿/新稿/意见同屏」在数据层就丢了「这一轮为什么重做」的字段，界面无法把「打回」与「重开」区分开。

**现状**：已用 `test/pao/f-results-files.test.ts` 里一条 `it.fails` 钉住，未改 `plans.ts`。**待裁定**：历史里应存「被谁判定」（`target.判定` 压栈时机）还是「判定结果」（让 `plans.ts` 改读别的字段）。

### 缺陷 #7：回边重做后，部长绑定无法转移（原编号 #5）

**症状**：走 `decideNode` 的 change 分支（真回边打回）后上游节点重做，但该节点仍绑着原部长会话，新部长进来被拒。
**根因（源码级）**：`control.ts:625-666` change 分支只做 `轮次++` 与清 `卡/拆解结束/判定/基线/零卡理由/重做理由`，**不清 `部长会话`**；`control.ts:420-431` `bindMinister` 见「已绑定其他部长」直接 `fail("已绑定其他部长；须恢复操作明确接管")`；`resumeControl`（`:748-771`）只改 `flow.owner` 与清 reject 判定；**全仓无解绑 API**。生产路径必撞：`host-bridge.ts:289` 每次 `await bindMinister(...)`。栈原文 `control.ts:79 fail ← :429 ← :353 mutate ← withFileLock ← host-bridge.ts:289`。
**现状**：e3 的夹具用 `takeoverMinister()`（模拟接管）补齐，lead 认「替身补齐 ≠ 作弊」，但**产品缺接管入口**这一点必须登记。
**待裁定（lead 倾向路 B）**：路 A = `decideNode` change 分支清 `部长会话`；路 B = `resumeControl` 加显式接管参数（与 `/pao budget 归还` 同形状）。归 H 批。
