- 盘上同一路径已被第 2 轮覆盖、且没有按轮次保留的副本，所以停在第 1 轮时读到的正文就是第 2 轮那份；用例断言它含第 2 轮标记且不含第 1 轮标记，并用 `file-overwritten` 提示承认这一点，**没有**断言「仍能读到旧稿原文」。

改动的产品源码：

- `PAO/packages/coding-agent/src/pao/workflow/plan.ts`：
  - 新增最小版本历史：`PLAN_HISTORY_DIR_NAME = "历史"`、`planHistoryDir`、`planHistoryPath`（`历史/版本-<N>.md`）、`archivePlanVersion`（把被替换掉的那一版原子写入历史）、`PlanHistoryEntry`、`listPlanHistory`（坏存档只记 `问题` 不抛，按版本升序）。理由是不用 git：临时计划落在用户项目的 `.pao/` 里，用户项目未必是 git 仓，内核也不该替他提交。
  - `modifyTemporaryPlan` 与 `undoTemporaryPlan` 在写盘前都先 `archivePlanVersion`，存档与新版在同一把计划锁内 ⇒ 存档成功而新版未写成的中间态里，当前版仍是旧的完整内容。
  - 新增 `PlanRevertInput`/`PlanRevertResult`/`revertTemporaryPlan`：**「撤销最近一次修改」与「撤回整份计划」是两个动作**——revert 只把内容回到上一版、计划照旧可执行，回到的那一版作为**新的定义版本**落盘（版本号继续往前走，不改历史，这样「谁在什么时候撤到哪一版」留得下痕迹）；undo 仍是整份标为已撤销不再启动。revert 同样接归属校验、取消信号与版本漂移拒收（`PLAN_VERSION_CONFLICT`），并在动作本身也存档当前版（否则连着撤两次时第二次找不到上一版）。
  - 新增 `PlanRecoveryResult`/`resolveRecoverablePlan`：当前版读得出用当前版，读不出则退到历史里**通过校验**的最大版本，全读不出抛 `PLAN_CORRUPT` 并保留原件；只认通过校验的版本，不用空步骤或默认值拼一份假定义充数。
  - `TemporaryPlanStep` 新增 `输入?: string[]`（上游成果或资料），新增 `清洗字符串数组`（非数组/非字符串项显式报错，不静默丢），`normalizeSteps` 与 `stepToNode` 接上（`输入` 进卡面，丢了这个字段恢复出来的要求就少了「拿什么干」）。
  - 模板参数化：`PARAM_NAME_PATTERN`、`TEMPLATE_TEXT_FIELDS`、`parameterizeSteps`（只把用户点名的字面量换成 `{参数名}`，不猜哪段该参数化；声明了却没替换到任何文本的参数报错，否则它进了参数表却没对应占位符）、`findTemplatePaths` 覆盖 `输入`、`buildPlanTemplateContent` 的 `参数` 不再恒为空。
  - **修复一个真实缺陷**：`PROJECT_PATH_PATTERN` 原会把项目内相对路径 `创作成果/初稿.md` 从中间的斜杠截出 `/初稿.md` 误报成「本次特有路径」，导致任何带相对成果路径的普通计划都存不成模板；改为要求匹配从路径开头起算（加负向后顾）。
  - `savePlanAsTemplate` 顺序修正：**先参数化、再判未泛化路径**（顺序反了会把即将被参数化掉的路径也报成未泛化）。
- `PAO/packages/coding-agent/src/pao/workflow/plan-tools.ts`：`pao_plan_update` 的 `action` 扩为 `modify|revert|undo` 并加 `target_version`，三个动作互不接受对方的参数（undo 拒 `target_version`，revert 拒 `steps`/`display_name`）；`pao_plan_query` 输出完整详情（身份含来源主控、时刻、运行关联、历史版本、逐步完整字段或 `around_step`＋`step_detail` 按对象读取）；新增 `selectStep`/`renderStepFull`/`renderStepDetail`；steps schema 支持 `inputs`；`pao_plan_save_template` 支持 `params`。

**为什么这个坑能潜伏这么久（值得记住的两点）**

- `desktop/node_modules/electron/install.js` 的 `isInstalled()` **只比对两样**：`dist/version` 文件内容 === package version、`path.txt` 内容 === `electron.exe`。**它不校验二进制本身**，所以任何"文件被动过/环境被改"在安装期都发现不了。
- 这只在 **"通过 DSH 启动的子进程"** 里发生。用户自己在普通终端里跑同一套 E2E 大概率是绿的 ⇒ 报"Windows 上 E2E 跑不起来"时必须先问清**是在什么宿主里跑的**。这是环境事实，不是产品缺陷，但会污染所有在 DSH 会话里做的桌面验证结论（本轮之前所有"未跑真 Electron"的登记，若当时试跑，也会红在这里）。

**传染面登记**：`ELECTRON_RUN_AS_NODE` 影响本机**任何** Electron 程序——`pnpm run package:win:dir` 之后起安装包、`test:e2e:native`、`tests/production`、桌面应用的冒烟启动，全都起不来。今后在 DSH 会话内跑一切 Electron 相关命令，**必须先 `Remove-Item Env:\ELECTRON_RUN_AS_NODE`**。
