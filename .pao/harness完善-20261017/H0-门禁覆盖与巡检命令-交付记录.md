## 二、A：门禁覆盖三条派发路径

### 2.1 `executeDispatch` 的三个调用点（核实过，无第四条路）

| 调用点 | 归属入口 | 接线前 |
|---|---|---|
| `src/pao/worker/index.ts`（`dispatchInBackground` 闭包内） | 单卡 `pao_dispatch_card` + 受理链 `pao_accept_task` | **已接**（G4） |
| `src/pao/fanout/execute.ts`（`runOne` 补位车道） | 扇出 `pao_fanout` | **未接** → 本卡补 |
| `src/pao/workflow/auto.ts`（`runAutoChain` 单卡派发） | 工作流自动链 | **未接** → 本卡补 |

唯一 `runner.run` 在 `src/pao/worker/dispatch-core.ts`；扇出恰恰是最可能大额花钱的入口，接线前它能绕开总预算花穿。
（另有一个同名 `executeDispatch` 在 `src/pao/collab/index.ts`，但那是 `/派` 用户快捷建卡，只建卡不起 runner，**不是派发路径**。）

### 2.2 门禁工厂搬到 `usage/dispatch-gate.ts`——理由是循环依赖（决定性）

四个可搬的搬走：`buildDispatchBudgetGate` / `dispatchBudgetKey` / `BUDGET_REFUSAL_NEXT` / `settleDispatchBudgetQuietly`。
一个留下：`markDispatchBudgetUnknown` 依赖 `locateDispatchCard`，属 worker 域，不搬。

**为什么不能留在 `worker/index.ts`**：`fanout/execute.ts` 与 `workflow/auto.ts` 本来就从 `worker/index.ts` import，
反过来再 import `buildDispatchBudgetGate` 就是**环**。这不是洁癖，是硬约束。

### 2.3 装配次序红线：`预算门禁` 必须排在 `...dispatchOptions` **之后**

原写法是 `预算门禁: ..., ...dispatchOptions`。今天类型上不可达（`dispatchOptions` 的类型放不进 `预算门禁`），
但**类型一放宽，调用方一个同名键就能把门禁静默关掉**——于是安全项变成可选项。已对调并加注释，
`usage-gate-coverage.test.ts` 用源码字符位置钉住次序（`...dispatchOptions,` 的 indexOf 必须小于
`预算门禁: buildDispatchBudgetGate(` 的 indexOf）。

### 2.4 拒绝文案：修掉一个会把人带沟里的缺陷（Lead 点名要单独立住）

自动链被拒的原文案是：

```
卡${cardRef} 派发被拒：${dispatched.原因}（并发上限/依赖/状态原因），自动链停
```

括号里**硬编码了三种原因**。预算不足被拒时，文案会说成「并发上限」——人会去调并发数，越调越远。
改为：

```
卡${cardRef}（节点 ${nodeName}）派发被拒：${dispatched.原因}；自动链停
```

即「哪张卡、为什么（真实原因原文）、下一步（自动链停）」，且不再替真实原因编造分类。
**这不是顺手改**：旧文案对预算拒绝是**主动误导**。

### 2.5 三路径同一判据

判据键统一为 `派发:卡<卡号>:尝试<尝试号>`，由 `dispatchBudgetKey()` 一处生成；三条路径共用，
因此「同一张卡的同一尝试不会被重复授额」在所有入口上都成立，不会出现两套口径。

## 三、B：僵尸预留的人工巡检面

### 3.1 为什么挂在命令面而不是工具面

`/pao budget` 能**改钱账**（把停着的预留额度放回去）。工具面是 agent 自己能调的，把钱账写入口交给 agent
等于让它自己给自己提额度。命令面只有人敲得到；且 `role.ts` 的 `WORKER_SKIPPED_MODULES` 已加
`budget-command`，worker 会话整模块不装载——agent 连这条路都看不见。worker 工具面**一个相关工具都没加**。

### 3.2 两个薄封装（都在 `usage/dispatch-gate.ts`）

- `listReservedReservations(paoHome)`：**纯读、不写盘、不做任何过期判断**。返回每笔 `reserved` 的
  判据键/卡号/尝试号/金额/预留时刻/状态。
- `releaseReservationExplicit(paoHome, {卡号, 尝试号})`：只按 `(卡号, 尝试号)` **精确匹配**判据，
  落盘复用 `budget-ledger.ts` 的 `releaseBudget`（既有加锁 + 原子写 + 既有护栏），**不另写一套落盘**，
  否则两套并发语义迟早冲突。
- 找不到那笔 → 返回「没有这笔预留」并**列出当前停着的判据键供人抄**，不猜他想还哪一笔；
  已结算 → 报「不能归还——取消不抹费用」；结果不明 → 报「须先查清」；写盘失败 → 抛并保留原件。

### 3.3 命令面（`usage/budget-command.ts`）

- `/pao budget` 或 `/pao budget 巡检`：只报不写。空态说「账上没有任何停着的预留」，**不留空白**，
  并提醒「不等于没花过钱——已结算的记录不在此列表」。
- `/pao budget 归还 <卡号>:<尝试号>`：参数缺失/格式不对（含中文冒号、只给卡号）→ 直接拒绝并给正确格式示例。
- 输出能答全「谁、卡几、尝试几、多少钱、什么时候、现在什么状态、下一步做什么」，且**下一步给三条判断路径**
  （进程还在跑 → 什么都别做；确认没派出去 → 显式归还；不确定花没花 → **不要**归还）。
- 裸敲与「巡检」**刻意等价**（router 无参时传空串；已在代码注释里写明是刻意，不是漏分支）。

## 八、口径与边界（写给后来的人）

### 8.1 门禁能保证什么、不能保证什么（H 批与用户都会读这段）

**规范表述（请照这个说，不要简化）：**

> 预留是**事前估算**，真实费用可能超出。门禁保证的是两件事：**不会因为并发而各领一份完整总额**，
> 以及**结果不明时不再授额**。真正硬拦在**轮次边界**，属 `worker/budget.ts` 的 `before_provider_request`。
> 跨任务总额与轮次边界硬拦是两件事，**不要**把前者说成后者。

**禁止出现**「已硬限额」「绝不超支」「不会超支」这类承诺——`usage-gate-coverage.test.ts` 里有
`FORBIDDEN_PROMISES` 常量在扫这几句。已知边界第 21 条里那句「不能承诺『绝不超支』」是否定用法，不是承诺。

### 8.2 「账本对登记表自动比对」是刻意不做，不是欠着的活

三条理由（已写进 `已知边界.md` 第 23 条）：
1. 巡检输出已经答全「谁/卡几/尝试几/多少钱/何时/什么状态/下一步」，人拿 pid 去 `pao_inventory` 对一眼就能比，
   内置一层是**替人做判断**；
2. 进程登记表**纯内存、不持久**（e2a 查出的设计缺口），跨重开读不到别人的 pid，能比的只有同进程的，价值远小于看上去；
3. 比对结果一旦出现「账上有、进程没在」，就会有人想让它自动归还——**红线不靠近处开小口**。

### 8.3 扇出直调链路上预留停在 `reserved` 不自动结算，不是漏接线

结算发生在**进程退出、回执落卡**那一刻，属 worker 侧完成回调；直调 `executeFanout` 时该回调不在链路内。
这是分层事实，**不要看到 `reserved` 就去「修」它**——正确做法是人看 `/pao budget` 再决定。

## 九、过程中的真实教训

1. **`findCardFile(cardsDir, cardNo)` 返回的是卡目录内的文件名，不是完整路径**（`src/pao/cards/cardfile.ts:248`）。
   `readCard(findCardFile(...))` 会去读 `<cwd>/卡0001-xxx.md` 报 ENOENT。正解 `loadCard(cardsDir, parseCardRef(ref))`（同文件 253 行）。
   另：`parseCardRef("卡0001")` 已返回数字，再套 `Number()` 得 `NaN`。
2. **自动链只对 `版本: 2` 的配方生效**（`src/pao/workflow/control.ts:364` 的 `if (recipe.版本 !== 2 || ...) fail(...)`），
   fixture 配方必须写 `版本: 2` 行，否则报「启动 v2 须有版本 2 配方和真实 owner 会话 ID」。
3. **`git diff -U0 | 只看 '-' 行` 会把「删一行、加三行」的替换形态误读成纯删除**。本卡据此曾误以为
