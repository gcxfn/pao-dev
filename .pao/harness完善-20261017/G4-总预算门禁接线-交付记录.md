## 一、结论（先行）

G2 交付的门禁（`src/pao/usage/dispatch-gate.ts`）**已经接到真实派发链上**。从 `registerWorkerTools`
装出来的 `pao_dispatch_card`（以及经同一 `dispatchInBackground` 的受理链）派发时，只要用户在
PAO_HOME 里显式给过总预算，就会在**真正拉起 worker 之前**做「查余额 → 占额度」；没给过总预算时
一个字节的行为都不变（连账本文件都不会被创建）。

四条卡内要求都落到可观察事实上了：真并发只过一个、拒绝不留已派发痕迹、成功按真实用量结算、
重启后只读盘就能判出这条请求的状态。

## 二、接线位置：为什么是「认领之前」而不是「认领成功之后」

**卡里建议的是「认领成功之后、spawn 之前」；我核过代码后改成了「认领之前」，这是本卡唯一偏离卡面的决定，
理由如下（请 Lead 复核）：**

状态机里 `in_progress → unclaimed` 这条迁移**不存在**
（`src/pao/cards/statemachine.ts:17-23` 的 `ALLOWED_TRANSITIONS`：`in_progress: ["delivered","failed","canceled"]`）。
所以如果在认领之后再被门禁拒绝，卡会停在 `in_progress` 而根本没有 worker 在跑——这正是卡里
第 2 条要求要防的「已派发假象」，而且还退不回去。要让「拒绝不留痕迹」成立，拒绝点必须在**卡被写之前**。

卡里另一句「不要在认领前预留（认领失败不能扣额度）」也满足了：预留发生在认领之前，但**认领失败会归还**
（`dispatch-core.ts:939` 的 finally 兜底归还，用例 `门禁放行但认领因依赖未放行而失败 → 预留归还为 released` 覆盖）。
即「先占、失败即还」，额度不会因为一次没派出去的请求被占死。

实际位置（`src/pao/worker/dispatch-core.ts`）：

```
866  const takeoverBlocked = ...（孤儿接管）
870-877  总预算门禁：lock 后重核之后、认领之前
878-883  claimCardForDispatch(...)  ← 门禁拒绝时根本不执行
926-930  门禁放行且认领成功 → gate.commit()（此后不再归还）
939  finally：只在「确定没开跑」时归还
```

选这一点的另一个好处：它已经在**项目写锁之内**、在 workflow 锁后重核之后，所以门禁的判定与
「这一次真的要派」是同一个时点的结论，不会在查完余额到认领之间被别的路径改变前提。

## 三、崩溃会留下什么（如实交代）

| 崩在哪 | 账上状态 | 卡状态 | 说明 |
|---|---|---|---|
| 预留写盘前 | `missing` | 原状 | 什么都没发生 |
| 预留写盘后、commit 前 | `reserved` | 原状（未认领） | 钱占着但没派出去。**目前不会自动归还**，需人工核对后 `releaseDispatchBudget` |
| commit 后、runner.run 抛错（无回执） | `unknown` | `in_progress` | 本卡已补兜底：`worker/index.ts:303 markDispatchBudgetUnknown` 在 catch 里把 reserved 改成 unknown，并进通知面 |
| runner.run 正常返回 | `settled`/`unknown` | 按回执 | 完成回调按 `receipt.usage.cost` 结算；缺 usage 记 unknown |
| 进程整个被杀（commit 后） | `reserved` | `in_progress` | 账停在 reserved＝占着但不知结果。能用 `inspectReservation` 判出，但**不会自动转 unknown**——这是已知局限（见第八节） |

「预留写盘后、认领前崩掉」这一行是唯一会白占额度的窗口，它对应一次真实写盘与一次卡写盘之间的距离。

## 六、用例清单（11 项，按卡内要求归组）

### 要求①「未授权总预算时零行为变化」
1. `没授权记录 → 派发照常成功，且盘上根本不产生总预算账`
   断言：`已派出` + 通知面 `派卡完成` + `runner.runs === 1` + 卡 `in_progress` +
   **`readdirSync(home)` 里没有 `总预算账.json`** + 通知面不含「总预算」。
2. `授权后行为立刻不同`（对照组）：同一场景注入门禁后账上 `settled`、`已结算费用===1.5`、账本文件存在。

### 要求②「真并发争同一份总额，只过一个」
3. `两张卡各要 6、总额 10 → 只过一个，另一个拿到真实拒绝原因且卡未被派发`
   `Promise.all` 同时发两个派发，`delayMs=40` 保证真重叠。断言：通知面同时出现 `派卡完成` 与 `派卡被拒`；
   被拒含 `总预算不足` **和「下一步」**；两卡状态一个是 `in_progress`、一个是 `unclaimed`；
   `runner.runs === 1`；**被拒那条在账上是 `missing`**（没占额度，下次还能派）。

### 要求③「拒绝不假成功」（三件设施都核，不只看文案）
4. `总额不足被拒 → 卡仍 unclaimed、在途表归零、通知面只出现「被拒」不出现「完成」`

## 八、未验项与已知局限（如实）

### 未验项
1. **没在真实模型上跑过**。全部用 FakeRunner，费用来自假回执的 `usage.cost`。
   真实链路「模型回 usage → `nativeUsageTotals` → 回执 `usage.cost` → 这里结算」没有端到端验证。
2. **`并发名额` 没有真正启用**。`checkDispatchBudget` 支持 `并发名额: SharedBudgetConfig`，但本次注入时
   没传——派发侧已有 `runner.reserveDispatchSlot`（部门上限/上游上限）在管并发，再接一层会让两套并发账
   互相解释不清。要不要合并是设计问题，超出本卡（写范围也不允许改 `runtime/`），**留待 Lead 决定**。
3. **没验桌面宿主**。门禁挂在 `resolvePaoHome()` 上，桌面主进程常无 PAO_HOME，此时
   `buildDispatchBudgetGate` 返回 undefined＝不启用。桌面侧是否要通过宿主注入 home 才能真正生效，未验。
4. **没验扇出（`pao_fanout`）与工作流自动链**。它们走同一 `executeDispatch`，但各自的
   `dispatchInBackground` 不一定注入 `预算门禁`（本次只改了 `registerWorkerTools` 里的那一条）。
   也就是说：**目前只有单卡派发/受理链受门禁约束，扇出与自动链尚未接线**。
5. **没验 `pao_accept_task` 链路的门禁实际生效**。受理链复用同一 `dispatchInBackground`，理论上已覆盖，
   但没有专门的用例（`intake-accept.test.ts` 回归通过，未断言门禁行为）。

### 已知局限
1. **「预留后、认领前」崩溃会白占额度**，且**不会自动归还**。需人工 `releaseDispatchBudget` 或
   `grantBudget` 加额度。刻意不做自动清理：自动归还需要判断「那次到底有没有起过进程」，猜错会超支。
2. **进程被杀（commit 后）时账停在 `reserved` 而不是 `unknown`**。`markDispatchBudgetUnknown` 只在
   派发链**抛错**时执行；进程被 `SIGKILL` 就没人执行它了。重启后 `inspectReservation` 能判出 `reserved`，
   但那与「正在跑」看起来一样。**这是这套账目前最大的可用性缺口**：需要一条「拿登记表核对账本」的巡检
   才能把僵尸 reserved 转成 unknown。本卡写范围不含巡检，建议单列。
3. **`commit()` 目前是空操作**（预留写盘已在 `reserveBudget` 完成）。它的意义是**语义锚点**：
   「这之后不再归还」。若将来需要「已提交」与「已预留」在账上可区分，要加状态，属于 G2 范围。
4. **判据是「卡号+尝试号」**。同一卡同一尝试只能有一条预留，这对防重复是对的；但若用户想在同一尝试上
   「加钱重派」，会被 `同判据内容不同（指纹不符）` 或 `已结算过` 拦住，需要换尝试号（即走重开）。
5. **预留额＝每卡 `budget.cost`，没写则预留 0**。预留 0 时门禁只在「总额已被占满」时能拦，
   挡不住「一开始就超支」的场景（因为 0 永远 ≤ 剩余）。这是保守但不精确的口径，G2 已登记。
6. **`$` 金额格式化仍用 `toFixed(2)`**（`dispatch-gate.ts` 的文案）。G2 的
   `formatMeteredCost`（未知/估计三分）用在了用量汇总，**没用在这里的预算文案上**——预算账里的金额都是
   用户显式给的确定数，不存在「未知」口径，所以没改；但如果以后这里要显示「估计花费」，必须换成
   `formatMeteredCost`，不能沿用 `toFixed(2)`。
7. **不能承诺绝不超支**。这套账是「扣额度 + 保守占用」，不是硬隔离；实际花费超过预留额时
   `settleBudget` 会**如实记录超额**（备注形如「实际费用超出预留额：预留 $a → 实际 $b（如实记录，未裁剪）」），
   不会回滚，也不会阻止。
8. **`worker/budget.ts`（轮次边界硬拦）完全没动**。它管的是「单个 worker 会话内的轮次/费用提醒」，
   与跨任务总额是两件事。两者的关系（要不要共享一份账）没有动，属 Lead 已单列的待决项。

## 十、给 Lead 的两个待决

**（A）扇出与工作流自动链要不要也接门禁？**
现在只有单卡派发/受理链受管。`pao_fanout` 一次派 N 张卡，是最可能大额花钱的入口，
但它有自己的一层 `dispatchInBackground`（在 `fanout/` 里），本次写范围不含。
建议单开一张卡把门禁注入点收到「所有派发必经的那一处」，而不是每个入口各接一次。

**（B）僵尸 `reserved` 要不要做巡检？**
见局限 2。可以复用 `inspectReservation` + 登记表写一条「账本对账」巡检，
把「账上 reserved 但登记表无活进程且卡已有回执」的条目转成 unknown 或 released。
需要明确「多久算僵尸」，建议做成显式人工命令而不是自动定时任务（自动改钱账风险高）。
