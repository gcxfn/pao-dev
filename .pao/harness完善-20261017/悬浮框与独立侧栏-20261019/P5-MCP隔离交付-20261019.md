## 验证方法

- 复用 `desktop/apps/desktop/tests/helpers/electron-app.ts` 的 `launchDesktop`、临时 userData、临时 Git workspace、模型扩展和主框架任务创建入口。
- 复用 `desktop/packages/pi-sdk-driver/test/fixtures/mcp-stdio-server.mjs`。该 fixture 连接后向 `initialized.txt` 追加 PID，成功调用 `write_marker` 后向 `called.txt` 追加文本。
- `agentDir/mcp.json`、`agentDir`、`PAO_HOME`、userData 和项目全部位于测试临时目录；MCP 配置为本地 `process.execPath` 启动 fixture，`exposure: "direct"`，没有远端服务、真实供应商或正式用户目录。
- 项目扩展只注册离线脚本 provider 和一个不会执行的 `isolated_extension_tool`。
- 来源问题先请求真实 MCP 工具并传入 `SOURCE_MCP_ONCE`，收到成功结果后回答 `SOURCE_MCP_OK`。
- 辅助问题再请求完全相同的真实 MCP 工具名并传入 `SIDE_MUST_NOT_WRITE`；收到宿主错误后回答 `SIDE_MCP_REJECTED`。
- 测试断言来源模型声明的工具包含 MCP 名和扩展名，来源调用结果不是错误；辅助快照及辅助模型声明严格只有四个读工具，同名调用结果 `isError: true`，扩展名和 MCP 名均不可见。
- 辅助发送前后比较：`initialized.txt` 字节不变、`called.txt` 仍恰好为 `SOURCE_MCP_ONCE\n`、受保护项目文件仍为固定原文、Git `HEAD/status/diff` 不变、隔离 `PAO_HOME/执行记录/control.json` 不变、主 transcript 不变。

fixture 的 `write_marker` 只证明材料 MCP 工具隔离与调用隔离，不新增、也不替代产品写文件证据。产品文件写入拒绝仍由 P5 既有 `project_write_canary` 真例覆盖。
