## 口径三分是怎么落的

三个层次各管一段，边界清晰：

1. **数据从哪来**：`ledger.ts` 的 `UsageLedgerRow.cost` 是供应商真实回的费用（不是我们折算的），`缺用量轮次` 记该会话有多少轮没回 usage。
2. **这一条数字算哪一类**（`basis.ts`）：只要某桶/某合计里有 `缺用量轮次 > 0` 的会话，整桶费用就是 `unknown`，`note` 写明"几个会话未回 usage，累计 $X 只是已知下界"。全部会话都回了 → `knownCost`。有依据但不精确 → `estimated`（接口已留，当前无调用方使用）。
3. **怎么显示**（`formatMeteredCost`）：唯一入口。`unknown` 渲染成 `未知（原因）`，不可能出现 `$0`；`estimated` 带"约"和"估计："前缀；`knownCost` 恰好为 0 时输出 `已知 0（供应商回 0）`，与"不知道"长得不一样。

`sumMeteredCosts` 的保守合并：任一 `unknown` → 合计 `unknown`；否则任一 `estimated` → 合计 `estimated`；否则 `knownCost`。**未知永远不可能被洗成已知**。

## 三条红线各自的用例名

全部在 `test/pao/usage-budget.test.ts`。

### 红线一：没配价格不能显示 $0 / 免费（10 条）

- `未知费用的文案是「未知（原因）」，不含 $0、不含「免费」`
- `未知与已知 0 必须长得不一样（供应商真回 0 才敢说 0）`
- `估计费用必须带「估计」与依据说明，不冒充准确值`
- `四类口径的中文名齐全（Token/已知费用/未知/估计）`
- `token 数不等于费用：token 口径的文案主动否认它是钱`
- `合并时任一未知 → 合计未知（不把未知洗成已知 0）`
- `合并时含估计 → 合计为估计（不当准确值）`
- `账本里缺 usage 的会话，汇总费用是「未知」且渲染文本不出现 $0`
- `空账本的汇总费用是「未知（还没有会话记录）」，不是 $0`
- `未授权总预算时，状态是「未启用」而不是「额度 0」`

### 红线二：并发不能各领一份完整总额（4 条）

- `两个真并发派发请求只有第一个拿到钱，第二个被真实拒绝`
- `两个并发请求各要 6（总额 10）时也只能过一个`
- `同一判据并发重复派发只产生一条预留（复用而非再扣一份）`
- `并发名额已满时拒绝派发（复用既有 reserveSharedRequest，不另写一套）`

真并发怎么保证不是"顺序化后假装"：用 `Promise.all` 同时起两个 `checkDispatchBudget`。**并且做了负向对照实验证明压力是真的**（见下）。

### 红线三：重启能核原请求（5 条）

- `预留落盘后重新读盘（模拟重启）能判出已预留`
- `已结算是重启后的第二种状态，且按实际费用算`
- `费用未知时记「结果不明」，钱继续占着，且拒绝重派（先查不重复授额）`
- `结果不明时不许直接归还（归还可能导致超支）`
- `账里没有这条判据时如实返回 missing（不是假装已预留）`

"重建对象"的落法：`inspectReservation(home, key)` 只按判据重新读盘，全程不依赖任何内存状态——`dispatch-gate.ts` 本身就是无状态模块，所有事实都在盘上。

## 已知局限

1. **不能承诺"绝不超支"**。预留是"事前给一个数"，真实费用可能超过它——`settleBudget` 遇到超额会如实记 `实际费用超出预留额：预留 $X → 实际 $Y（如实记录，未裁剪）`（有用例 `实际费用超出预留额时如实记下超额，不裁剪`），但**超出的部分已经花掉了**。门禁能保证的是"不会因为并发而各领一份完整总额"和"结果不明时不再授额"，不能保证"账户永远不会透支"。要真正硬拦，需要在**轮次边界**按已花费用实时检查（`worker/budget.ts` 的 `before_provider_request` 已经在做这件事，本卡没动它）。
2. **费用迟到无法事前防**。供应商账单可能滞后于会话结束。`settleDispatchBudget` 收到 `实际费用 === undefined` 时把状态记 `unknown`、钱继续占着（保守），但**这笔钱到底花了多少，在查清之前系统确实不知道**。此时余额显示的是"已占用的预留额"，不是"真实已花"。
3. **`unknown` 状态需要人工/后续流程查清**。系统只保证"不重复授额"，不保证自动收敛——没有自动对账器把 `unknown` 推成 `settled`。
4. **"加额度"只能追加、不能缩减**。`grantBudget` 的 `总预算` 是总量；把总量**调小**在技术上可行（追加一个更小的版本），但没有专门的"缩减额度"语义与校验——如果新总量小于已花，`remainingBudget` 会兜底成 0，而不是报错。
5. **压缩/摘要用量的归属是披露而非精确拆分**。`用量账.jsonl` 里若没有独立的"压缩摘要"角色行，我只能披露"摘要用量可能已并入所属会话，也可能完全没落账——本汇总无法把这两者分开"，不能给出精确数字。这是数据源本身的限制，不是实现偷懒。
6. **`releaseBudget` 只释放 `reserved`**。对 `unknown` 直接归还会被拒（`须先查清`），对 `settled` 也会被拒（`取消不抹费用`）。这是刻意的保守设计，但意味着流程上需要一个"查清未知"的环节才能回收这部分额度。
7. **账本没有清理/归档机制**。`总预算账.json` 会持续增长（每条预留一条记录）。当前没有 GC；量级上（派发次数）应该很小，但长期运行需要考虑。
8. **并发名额与钱的检查不是原子的单一事务**。`checkDispatchBudget` 先拿并发名额（`reserveSharedRequest`，它自己的文件锁），再预留钱（`reserveBudget`，另一个文件锁）。中间如果进程崩溃，可能出现"占了名额但没占钱"——这不导致超支（少占不超），但会浪费一个并发名额直到 ESRCH 清理。反向顺序则会"占了钱没占名额"，同样不导致超支。选了当前顺序是因为名额更便宜、清理更容易。
