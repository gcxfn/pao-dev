# E 批离线样例说明

> 本目录是 task-12（E6 离线样例与端到端最小链路）的交付物。
> 覆盖计划 §5.3 / §5.4：各模式可查回、一次受理、部分成功、重复提交、停止、中途改要求。
> 全部离线：不调真实模型供应商，不 spawn 真实子进程，不读写正式 PAO_HOME。

## 一、怎么用

测试文件：`PAO/packages/coding-agent/test/pao/e-batch-sample.test.ts`

```powershell
cd D:\AI\workspace\pao-dev\PAO\packages\coding-agent
pnpm exec vitest --run test/pao/e-batch-sample.test.ts
pnpm exec tsc -p tsconfig.build.json --noEmit
```

测试每次运行都会：

1. 新建一个隔离临时根（`os.tmpdir()/pao-e-batch-<用途>-*`）；
2. 把本目录的 `启动区-PAO_HOME/` 与 `启动区-项目/` 复制进去；
3. 在临时根里跑真实业务代码（`acceptIntake` / `isIntakeOutcomeStale` / `readDeptCatalog` / `validateDeptCatalog`）；
4. 结束时 `rmSync` 整个临时根，**不留任何运行产物在仓库里**。

## 三、部门配方：为什么「工具」与「技能」分两行写

内核 `dept/catalog.ts` 把它们当**两个不同字段**解析，且有一个专门的提示项 `混写技能名`
（把技能名写进「工具」行会被识别为混写并给出提示）。本样例按正确格式写：

```
- 工具:read,write,edit,grep,find,ls     ← 内置工具白名单
- 技能:小说文风校准                      ← pao配置/skills 下的真实目录名
```

验证结果（真实运行）：三个部门 `混写技能名` 均为 `[]`，`validateDeptCatalog()` 返回**零问题**。

> **E1「技能/工具分家」在样例侧的可查证据**：样例使用的三个部门配方（写作／审查／只读审查）
> 均为 `- 工具:` 与 `- 技能:` **两行分写**，`validateDeptCatalog()` 对其返回**零问题**。
> 对应测试用例：`e-batch-sample.test.ts` 第一个用例「三个样例部门齐备，工具与技能分家，档位解析到配方，校验零问题」。
> 具体断言：`工具` 解析为内置白名单（`read/write/edit/grep/find/ls` 等，`内置 === true`）、
> `技能` 解析为 `pao配置/skills/小说文风校准`（`可用 === true`）、`混写技能名 === []`、`validateDeptCatalog() === []`。

## 四、本样例能证明什么

| # | 能证明 | 对应用例 |
|---|---|---|
| 1 | 一次受理返回**真实卡号与卡路径**，且能按卡号在卡目录查回该卡，卡面 goal/constraints 与请求一致 | ① |
| 2 | 批量受理出现「有的受理、有的被拒」时 `partial === true`，被拒那条的**拒绝原因来自真实预检**（点名具体缺失项），且不建卡 | ② |
| 3 | 依赖未放行时报 `deferred`（卡已建、此刻不派），原因**点名前置卡号**，不是泛泛失败 | ② |
| 4 | 请求形状不全时报 `rejected`，原因逐条列出缺什么，且不建卡 | ② |
| 5 | 同一判据重复提交返回 `duplicate`，**回填首次受理的真实卡号与卡路径**，卡文件数不变 | ③ |
| 6 | 重复提交**不重复派发**：派发通道只被调用一次（「不新建卡」与「不重派」分别成立） | ③ |
| 7 | 卡被停（`unclaimed → canceled`）后 `isIntakeOutcomeStale()` 由 `false` 变 `true` | ④ |
| 8 | 卡文件被删后旧结果同样判失效（查不到就不许说成功） | ④ |
| 9 | 中途改目标/追加约束后，卡号不变、能查回新值；同一判据再提交仍返回 duplicate 且不改回旧值 | ⑤ |
| 10 | 尝试号变化（卡进了新一轮）时旧结果判失效 | ⑤ |
| 11 | 部门目录在真实校验下是干净的（三部门齐备、工具与技能分家、档位解析到配方、零问题） | 前置检查 |
| 12 | 全部夹具路径都在临时根下，未指向正式 PAO_HOME；运行后仓库无产物 | 边界自检 |

## 五、本样例不能证明什么（为 F 批留的扩展点）

1. **不覆盖真实模型行为**：全程没有模型参与，产出的是卡与受理结果，不是正文质量。
   F 批若要验证「写作 → 审查打回 → 改稿」的**内容**流转，需要接真实或回放式 provider。
2. **不覆盖真实子进程**：派发用替身钩子（只登记调用，不 spawn）。真实 worker 认领、
   快照基线、回执追加、并发名额这些行为未覆盖。
3. **不覆盖 Electron 界面**：桌面端展示、卡片渲染、侧栏状态均不在本样例范围。
4. **不覆盖工作流实例语义**：样例都是普通卡，`instance`/`node`/`round` 一律 undefined
   （契约规定「能给才给」）。工作流派发的实例/节点/轮次身份需要另建样例。
5. **「中途改要求」在样例里是绕过状态机的测试替身，不是产品用法**（E 批已知缺口，已核对并记录）：
   - **事实**：在本仓 `src/pao/` 全量检索，**不存在** `patchDispatch` 或任何「改进行中卡目标」的公开入口。
     现有卡通道只到 `src/pao/cards/statemachine.ts:188` 的 `changeCardStatus(card, input)`——
     它做的是**状态迁移 + 单写者校验**，管的是 `status`/`owner`/`attempt`/`completed` 这些信封字段，
     **改目标正文（`goal`/`constraints`）不经过任何状态机保护**。
   - **① 样例怎么做的**：测试里用 `readCard` → 直接改 `frontmatter` → `serializeCard` → 写回，
     这是**绕过状态机**的测试替身，只用于构造「卡已被改过」这个前置状态，**不是产品用法，不可照抄**。
   - **② 真实产品里不成立**：owner 改卡必须走状态机/单写者校验通道（同一时刻只允许一个写者、
     且要经过迁移合法性检查）。本样例**不代表那条通道已经存在**，也不代表它已被验证。
   - **③ 列为 E 批已知缺口**：建议在 F 批或后续**单独立项**补正式通道（改目标要留痕、要参与
     版本/尝试号语义、要与 `isIntakeOutcomeStale()` 的失效判定对齐）。
     在那之前，**不得把「改要求已实现」写进任何执行记录**。
   若后续补了正式通道，本样例的 ⑤ 应改为走该通道，替身代码随之删除。
6. **打回重做只验了状态机层面**：样例会通过 `failed → unclaimed` 这类迁移允许重做，
   但没有真实验证「审查打回后写作部门拿到理由再改稿」的完整业务闭环。
7. **只读目录的写入拒绝断言本轮不补**（裁定：留给 F 批，理由如下）：
   计划 §5.3 的字面要求是「**只读部门能对某目录产出审查意见**」，不是「文件系统写保护被拒」。
   本样例已用两条证据验到这条要求的可执行落点：① 只读审查部门的配方只含 `read/grep/find/ls`，
   不含 `write`/`edit`；② 该部门对 `待审查稿/` 目录出了带行号定位的审查意见结构与判定结论。
   而「文件系统 chmod 只读 + 写入被拒」属于**另一件事**（边界防护），且 Windows 上 `chmod` 语义
   与只读属性、清理代价都不小（git 不保留该属性，仓库里放只读目录还会干扰清理）。
   故**本轮不做**，列为 F 批待补项（见第六节第 3 条）。

## 六、给 F 批的扩展建议

> 以下四条已由 lead 裁定**全部采纳进 F 批**（2026-10-17 裁定 3）；
> `启动区-*` 目录作为 F 批起点直接追加、不重构。

1. **接回放式 provider**：录一段真实写作/审查的模型交互，做成回放夹具，即可在完全离线的前提下
   验证内容流转（写作产草稿 → 审查打回 → 写作改稿 → 审查通过）。这是本样例最自然的下一步。
2. **补工作流样例**：用 `workflow` 侧的真实实现搭一个两节点实例（写作节点 → 审查节点，带回边），
   验证 `instance`/`node`/`round` 的回填与 `requiresConfirmation` 门。
3. **F 批待补：只读目录写入拒绝断言**（本轮不做，理由见第五节第 7 条）：
   在临时副本上 `chmod` 只读后验证写操作被真实拒绝且报明确原因。
   本轮不做是因为 §5.3 的字面要求是「只读部门能对某目录产出审查意见」（已由配方工具白名单 + 实际审查产出验证），
   而文件系统写保护属于另一件事（边界防护），且 Windows 上 `chmod` 语义与清理代价都不小。
4. **补同判据并发受理**：同一判据并发提交（占位互斥路径），验证只有一个建成卡、另一个报 `deferred`。
5. **补账本损坏场景**：手写坏 `.pao/intake/受理账.json`，验证如实报错而不是静默重置。
6. **样例骨架可继续生长**：`启动区-*` 目录就是给 F 批的起点，直接在其上追加目录与用例即可，
   不必推翻重构。
