## 一、后台通知为什么会让主控醒来

### 真实调用计数

主控日志约从 12:21:27 持续到 13:08:54，共有：

- 65 次 `bash`；
- 3 次 `pao_start_flow`；

93 个回复不等于 93 次后台唤醒。真实的自定义通知消息只有 6 条：

| UTC 时间 | 日志行 | 现象 |
| --- | ---: | --- |
| 04:28:33.102 | 475 | 第一次自动链异常后的主动唤醒 |
| 04:29:04.657 | 1047 | 与上一回合结束时间非常接近的后续通知 |
| 04:38:06.794 | 16892 | 旧实例处置阶段的进度或停止事件 |
| 04:59:08.370 | 17041 | 实例切换阶段通知 |
| 04:59:08.714 | 22664 | 与上一条仅相隔约 344 毫秒 |
| 05:07:24.840 | 22751 | 加固实例运行期间又启动了一回合 |

`pao-dispatch-notify` 的固定正文仅为“有新的后台结果，请读取本轮注入的通知摘要。”

主控在 05:02:32 的一轮中明确判断：

> 本轮通知为常规进度事件：加固实例 `9b789dae…` 的侦察节点已绑定部长并在本轮拆解中，无停链异常、无 worker 在跑。无需干预，结束本轮等待下一轮通知。

这条回复位于 `pao.txt:22744`，该回合用量为 input 394、output 81、cacheRead 129,280、reasoning 27。缓存读取不是新增生成 token，但该回合确实启动了模型并重新处理了大段上下文。

### 代码链

1. `createDispatchNotifySurface` 的 `notify()` 接收正文后立即压入同一个通知缓冲，并调用 `wake()`：
   - `PAO/packages/coding-agent/src/pao/worker/notify.ts:68-70`
   - `PAO/packages/coding-agent/src/pao/worker/notify.ts:128-155`

2. `wake()` 只合并“同一时刻尚未注入”的通知。它用 `wakePending` 防止一次注入完成前重复唤醒，但正文一旦注入，`inject()` 就把 `wakePending` 重置为 `false`；紧接着到达的新通知仍会再调一次 `wakeUp()`：
   - `PAO/packages/coding-agent/src/pao/worker/notify.ts:114-125`
   - `PAO/packages/coding-agent/src/pao/worker/notify.ts:165-172`

3. `wakeUp()` 最终调用 `sendMessage(..., { triggerTurn: true, deliverAs: "followUp" })`，所以它会启动真实模型回合：
   - `PAO/packages/coding-agent/src/pao/worker/notify.ts:53-65`

4. 主控只有这一个共享通知面。部长宿主通知直接接入 `notifySurface.notify(body)`：
   - `PAO/packages/coding-agent/src/pao/index.ts:355-371`
- 宿主通知工具还把普通宿主通知送入同一面：
   - `PAO/packages/coding-agent/src/pao/host/tools.ts:113-126`
   - `PAO/packages/coding-agent/src/pao/index.ts:485-487`

5. 工作流终态和异常也使用同一面，但其正文会明确标为“自动链完成/停下/失败”：
   - `PAO/packages/coding-agent/src/pao/workflow/tools.ts:432-447`
   - `PAO/packages/coding-agent/src/pao/workflow/tools.ts:486-494`

因此，“常规进度为什么能唤醒”不是日志误判：通知面没有区分信息型进度与需要行动的失败、终态或监督；所有进入它的通知都会尝试主动唤醒。具体到 6 次事件各自由哪个更上层业务函数产生，日志没有为每一轮保存可单独检索的生产者标签，本次没有继续追查；接线行为和至少一条常规进度唤醒用途已经确认。

### 判断

- 6 次主动唤醒分布在约 47 分钟内，总体频率不算持续轮询。
- 一对短间隔连续通知说明 `wakePending` 只解决“未注入前合并”，不能解决“刚注入后紧接新事件”的合并问题。
- 普通进度唤醒没有促成干预；其价值低于结果、失败和到期监督。
- 最小问题不是“通知太多”本身，而是“通知类别没有分层，并且缺少很短的跨回合合并窗口”。

## 四、性能采样漏报 `process.title=pao`

监控的进程探针在读取角色和 PAO 脚本之前，先做 arg0 白名单：

- `PROBE` 读取 `/proc/<pid>/cmdline`；
- 只有 arg0 的 basename 是 `node`、`nodejs` 或 `node.exe` 才继续；
- 其他进程直接 `continue`。

证据：

- `.pao/地图简报与部门协作-20261020/benchmark/real-run-20261022-r3/runtime-scripts/resource-monitor.py:28-57`

PAO 自身会修改进程标题：

- 包配置 `piConfig.name = "pao"`：
  - `PAO/packages/coding-agent/package.json:6-9`
- RPC 入口设置为 `pao-rpc`：
  - `PAO/packages/coding-agent/src/rpc-entry.ts:2-7`
- CLI 入口设置为 `pao`：
  - `PAO/packages/coding-agent/src/cli/setup.ts:1-7`
- `APP_NAME` 从包配置读取：
  - `PAO/packages/coding-agent/src/config.ts:538-540`

Linux 下 Node 的 `process.title` 会改变进程可执行标题，而监控用的 `/proc/<pid>/cmdline` arg0 也随之不再是 `node`。探针因此在进入 PAO 识别、环境变量读取和角色归类之前就把这些进程过滤掉。

`resource-summary.json` 与机制一致：

- 主容器 98 次 `probe_status=collected`；
- 按角色汇总却只有 `unknown / 未标注角色 / 未标注部门`，且只有 2 个匹配样本；
- 没有任何 `kind=pao-runtime` 行。

`collected` 只表示探针命令成功返回，不表示 PAO 被识别。

## 六、最小修复与验收用例

### 1. 通知分类和短时合并

最小修复：

- 给通知增加明确的 `progress | result | failure | supervision` 类别。
- `progress` 只进入缓冲和 toast，不调用 `triggerTurn`；主控下一个真实回合再读取。
- `result`、`failure`、工作流停下/完成和到期监督保留主动唤醒。
- 在主动唤醒路径增加一个很短的合并窗口，至少覆盖相隔数百毫秒的连续事件，并让首个真实回合一次读取全部正文。

验收：

1. 空闲会话只收到普通进度：缓冲可读，模型回合数保持 0。
2. 空闲会话收到失败：产生 1 个主动回合，正文包含失败原因。
3. 500 毫秒内依次收到进度和失败：只产生 1 个主动回合，正文二者都在。
4. 模拟本次时间戳相隔约344毫秒的通知对，另核实其实际投递时刻：不能出现两次独立 `pao-dispatch-notify`。
5. 终态通知仍然可达，且不依赖额外轮询。

### 2. 监督可观测性与跨周期测试

最小修复：

- 为“到期、投递成功、确认、未确认升级”写可检索的审计记录，不能只记录散场和费用缺口。
- 对已投递但长时间未确认的提醒提供一个明确的升级状态；具体升级次数应可配置，不直接恢复高频重复唤醒。
- 保持卡文件仍是业务真相；监督计时若需跨宿主重启保留，优先从活动正本重建，不必先建完整持久化框架。

验收：

1. 用注入时钟让一个工人跨过 15 分钟：部长收到一次 `[监督检查]`，审计同时记录 key、到期时间和投递结果。
2. 让一个部门跨过 30 分钟：主控收到一次合并提醒，审计可查。
3. 发送 `pao_ack_supervision` 后计时从确认时刻重置。
4. 不确认时不会高频重复唤醒；达到升级条件后状态在盘点中可见，而不是静默消失。
5. 重放本次不足 15/30 分钟的短实例切换场景，确认不会伪造“已监督”。

### 3. 替代实例的显式收场与现有实例恢复

主控取舍：不采用“同owner和卡目录只能有一个实例”及额外并行开关。现有产品支持独立并行工作，不能因本次三个替代实例就加入项目级互斥。

最小修复：优先在原实例当前节点恢复；确需替代时，显式暂停旧实例、核对其在途卡与worker、按实例/脉络定向收场，保留会话和旧轮历史，再启动新实例。旧实例缺少明确终局时，状态和通知应提示原实例仍未结束，不能暗示新流程已替它收尾。

验收：原实例可在身份、轮次和在途检查通过后恢复；显式替代只处理被替代实例所属进程；两个不同任务的合法并行实例互不影响；空闲保温会话与正在工作的会话分开显示。

### 4. 性能采样按进程身份而非可变标题识别

最小修复：

- 取消“cmdline arg0 必须是 node”这一前置过滤。
- 用 `/proc/<pid>/exe` 或未改写的内核标识确认 Node，再结合 `PI_CODING_AGENT=true`、PAO 脚本路径和 `PAO_ROLE/PAO_DEPT` 分类。
- `process.title` 只作为展示字段，不作为唯一识别条件。

验收：

1. 启动一个 Node 进程，设置 `process.title="pao"`、`PI_CODING_AGENT=true`，探针把它归为 `pao-runtime`。
2. 设置 `process.title="pao-rpc"`、`PAO_ROLE=部长`、`PAO_DEPT=实施`，角色的部门和类型都正确。
3. 普通题目 Node 进程仍归为 `task-node`，不能误并到 PAO。
4. 一个无关进程即使标题叫 `pao`，也不能只凭标题被归为 PAO。
5. 重放样例后存在非零 `pao-runtime` 行；容器总 CPU/容器内存 数值保持不变。
