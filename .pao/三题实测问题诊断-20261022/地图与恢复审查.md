# 地图与恢复审查

日期：2026-10-22  
范围：`real-run-20261022-r3` 三轮流程反复重建的地图失效、验收拦截、空 owner 硬锁及恢复能力。  
性质：只读审查；未修改产品代码，未启动模型测试或容器。

## 结论

这次连续重建不是单一故障。三次分别停在地图覆盖了流程自身控制文件、坏验收被安全门拦截后卡仍显示进行中、空字符串 owner 被当成真实写者而无法认领。三处原保护都应保留。

最优先修复是空 owner 硬锁。实际卡是 `status: unclaimed`，按协议本应可认领，但 `owner: ""` 让状态机进入“卡已被空身份认领”的分支，主控和部长都无法认领。现有 `resume` 不能解决它，孤儿接管也不能解决它。

恢复能力并非完全没有：实例暂停后有 `resume`；进行中且无回执、无活进程的孤儿卡可显式 `接管`；失败卡可按尝试上限走 `failed → unclaimed → in_progress`。真正缺口是：部长已经结束拆解、但后来发现当前节点需要换一张合格卡时，没有受保护入口把同一实例的当前节点清零重开一轮。模型因此重建了新流程，而没有使用适合当前状态的恢复方式。

| 优先级 | 分类 | 实际问题 | 判断 |
|---|---|---|---|
| P0 | 产品 bug | 空字符串或纯空白 owner 通过校验，并形成不可认领、不可由主控落终态的硬锁 | 必须修 |
| P1 | 配置/模型误用，产品提示不足 | 首轮地图把 `.pao` 内会持续改写的流程控制文件纳入 coverage，派发时正确报 `stale_map` | 保留保护，入口默认值应收紧 |
| P1 | 模型误用，产品缺口 | 第二轮卡内验收使用绝对路径、串联符和内联代码，被静态安检拦截；失败后卡仍停在 `in_progress` | 建卡预检并显式落失败 |
| P1 | 产品功能缺口 | 没有“当前节点在新轮次重开”的主控入口；已有 `resume`、孤儿接管和失败重试都不是这个语义 | 在现有节点控制入口最小扩展 |
| P2 | 模型误用，接口默认路径脆弱 | `pao_inventory(workspace=/app)` 错把项目根推成 `/`，扫描 `/卡` 后误报“无未完卡、无 Git” | 显式拒绝路径不合约，不猜更多父级 |

## 三轮实际停点

### 第一轮：地图覆盖流程自身控制文件

实际停链记录在第一轮控制正本：

`stop-evidence/.../project-pao/benchmark/工作流实例-基准开发流水线.md:320`

> `卡卡0001 派发异常：上游地图覆盖内容在准备与冻结之间已变化，自动链停`

保存地图把 `.pao/benchmark/工作流实例-基准开发流水线.md` 放进了 coverage。流程在派发期间又会改写该文件，因此准备阶段采集的摘要与冻结前重采不一致：

- 覆盖路径采集：`PAO/packages/coding-agent/src/pao/dispatch-brief/workspace.ts:192`
- 文件摘要写入地图：`workspace.ts:203`
- 有效范围按 coverage 和 excludes 重采：`workspace.ts:264`
- 冻结前重采后不一致即拒绝：`PAO/packages/coding-agent/src/pao/dispatch-brief/snapshot.ts:237`

这不是 Git 元数据丢失，也不是 `stale_map` 误报。首轮纳入自动改写文件，随后的变化真实存在，安全门按设计工作。责任分成两层：

- 模型/配置问题：地图保存者把编排区当作交付面。
- 产品完整性问题：`pao_minister_save_node_map` 在 `workflow/minister.ts:443` 直接接收 coverage/excludes，没有在入口明确阻止保存一个包含当前 `.pao` 编排区的地图。错误要到后续派发才以 `stale_map` 出现，诊断成本偏高。

停止快照中的修正、加固配方已经要求 `coverage: ["."]` 和 `excludes: [".pao", ".git"]`，见 `stop-evidence/.../recipes/基准开发流水线-加固.md:18,36`。这一配置方向正确。

### 第二轮：验收被正确拦截，但卡状态没有落失败

实际卡：

`stop-evidence/.../project-pao/benchmark/卡/卡0002-实现交付物appfilter.py（单文.md:10,13,40` 起

卡面：

- `owner: 主控`
- `status: in_progress`
- `attempt: 1`
- worker 已有 `result: success` 回执
- 机械验收有大量“安检拦截”

实际停链记录：

`stop-evidence/.../project-pao/benchmark/工作流实例-基准开发流水线-修正.md:333`

> `卡卡0002（节点 实施）验收结论「未过」，不自动交付，留 owner 处理后推流续跑`

卡上的验收条目包含 `/app/filter.py`、`/usr/local/bin/python3`、`/tmp/...`、`&&` 风格串联、重定向及内联 HTML/Python。静态安全门禁止这些形状是正确的：

- 跑命令安全校验：`PAO/packages/coding-agent/src/pao/cards/verifier.ts:220`
- 存在/包含路径限制在项目根相对路径：`verifier.ts:654`
- 违规条目标记“安检拦截”：`verifier.ts:788`

缺口有两处：

1. 建卡入口尚未复用现有验收解析与静态安检。源码尾注已写明这一接线项：`verifier.ts:1454`。因此坏卡先落盘、结束拆解并派工，最后才在机械验收处被整卡拦下。
2. 机械验收未过后，自动链只返回“留 owner”的停因；`workflow/auto.ts:616` 进入非全过分支，`auto.ts:718` 返回停链，但卡没有从 `in_progress` 落到失败。结果卡面同时表示“worker 已交回执”“机械验收未过”和“仍在进行中”，后续恢复判断失真。

这一轮不能靠 `accepted_deviations` 绕过。`accepted_deviations` 是 owner 对人工可接受未达项的依据通道，不能把安全检查拦截伪装成通过。

### 第三轮：空 owner 形成不可认领硬锁

实际停链时间与记录：

`stop-evidence/.../project-pao/benchmark/工作流实例-基准开发流水线-加固.md:345`

> `2026-10-22T05:07:24.835Z`  
> `卡卡0003 派发异常：卡已被  认领，主控 无权写入，自动链停`

实际卡：

`stop-evidence/.../project-pao/benchmark/卡/卡0003-核验并修正项目根下现有filter.py.md:10,13`

卡面同时出现：

- `owner: ""`
- `attempt: 0`
- `status: unclaimed`

触发链是确定的：

1. `PAO/packages/coding-agent/src/pao/cards/statemachine.ts:89` 把“待认领 → 进行中”视为认领。
2. 同处只用 `owner !== undefined` 判断有无 owner；空字符串不等于 `undefined`，于是进入“已被认领”分支。
3. `statemachine.ts:90` 要求调用者等于空字符串。实际调用者是“主控”，因此在 `statemachine.ts:91` 抛出 `FORBIDDEN_WRITER`。
4. `statemachine.ts:114` 的 `applyOwnerOnClaim` 也只在 `owner === undefined` 时补写 owner，所以空字符串不会被纠正。
5. `PAO/packages/coding-agent/src/pao/cards/cardfile.ts:83` 对 owner 只校验“若存在必须是字符串”；空字符串仍是字符串。
6. `cardfile.ts:376` 会原样写入传入的 owner；`intake/accept.ts:165` 也会透传调用方给出的空字符串。

所以空值写入本身可能是调用方/模型输入错误，但“空字符串可落盘并被当成真实写者”是明确的产品缺陷。两者要分开报告。

该硬锁还跨越了状态边界：普通状态下 `in_progress → unclaimed` 本来就不允许，见 `statemachine.ts:17`。修复不应新增这条常规迁移，因为那会削弱在途卡防双跑保护。

第三轮失败后，主控用 `pao_accept_task` 建了：

`stop-evidence/.../project-pao/卡/卡0004-核验并修正项目根下现有appfilter.md:10,13,14`

卡面为 `owner: 主控`、`status: in_progress`、`attempt: 1`。它位于项目根的 `.pao/卡`，不是原实例的 `.pao/benchmark/卡`。这是一张另立纯卡绕开原工作流的降级交付，不能算恢复原实例。

## 恢复工具核对

实际 main probe 已经暴露了 `pao_control_node`、`pao_dispatch_card`、`pao_change_status`、`pao_spawn_minister` 和 `pao_terminate_card`，见 `stop-evidence/.../agent/organization/probes/main/probe-main.json:4` 起。因此不能说“没有恢复通道”。

| 能力 | 当前是否支持 | 实际入口与限制 | 对本轮是否可用 |
|---|---|---|---|
| 暂停实例恢复 | 是 | `pao_control_node action=resume`，`workflow/tools.ts:545`；要求实例、原 owner、现场核查，且拒绝仍有 `in_progress` 卡，`workflow/control.ts:805` | 第三轮卡是 `unclaimed`，单看状态可通过该检查，但 `resume` 只清暂停/裁定，不修复空 owner，也不重做当前节点 |
| 孤儿在途卡接管 | 是 | `pao_dispatch_card(接管:true)`，`worker/index.ts:198`；仅 `in_progress`、当前尝试无回执、登记表无活进程，`worker/dispatch-core.ts:199` | 第二轮卡已有回执，接管会正确拒绝；第三轮卡不是进行中，接管不适用 |
| 失败卡重试 | 是 | 状态机允许 `failed → unclaimed`，`statemachine.ts:17`；尝试上限仍为 2，`statemachine.ts:25` | 可复用，但必须先有真实失败态；当前第二轮没有落到失败 |
| 部长进程断开、拆解未结束 | 是 | 重推流使用原 `节点.部长会话` 重开同一会话，`workflow/host-bridge.ts:581` | 只覆盖“撤回执/进程重开”，不覆盖“当前节点已结束拆解但需要换卡重做” |
| 当前节点开新轮 | 否 | `host-bridge.ts:568` 对 `拆解结束: true` 且非审核收尾的节点直接返回不推进 | 三轮停住后的共同缺口 |
| 回边重做节点 | 部分支持 | 审核 `change` 已实现旧轮留存、轮次递增、清卡、清基线、写重做理由，`workflow/control.ts:658` | 现有逻辑可复用，但不能要求伪造一次审核拒绝才能恢复 |

因此准确的结论是：

- `resume` 已实现，但不是本轮所需操作。
- 孤儿 `接管` 已实现，第二轮已有回执、第三轮非进行中，故都不适用。
- `failed → unclaimed` 重试已实现，但第二轮缺少失败落态。
- 同实例当前节点受控 `reopen`（重新开启一轮）和“rework”没有对外动作。

## 最小修复建议

### P0：收紧 owner 边界

复用卡公共读写边界，不为中心状态机增加绕过迁移。

1. 在 `cardfile.ts` 的公共 frontmatter 校验与 `createCard` 入参处，将 owner 的纯空白字符串视为非法。写卡时明确拒绝；读取历史坏卡时兼容为“无 owner”，保证现有坏卡可救。
2. 在 `statemachine.ts` 用一个小型纯函数统一判断 `owner === undefined || owner.trim() === ""`，并让 `checkWriterAuthority`、`applyOwnerOnClaim` 共用该判据。
3. 保留真实 owner 的严格单写者比较，不新增 `in_progress → unclaimed` 普通迁移。
4. 对已经存在的空 owner 卡，允许下一次合法认领补写 owner；同时对创建入口直接报错，避免继续产生坏卡。

### P1：地图保存入口守住编排区

继续使用现有 coverage/excludes、摘要重采和 `stale_map`，不放宽失效判定。

1. 在 `pao_minister_save_node_map` 入口规范化 excludes。
2. 如果 coverage 覆盖项目根，除非调用方明确声明保留编排区，否则自动要求排除 `.pao` 与 `.git`。
3. 若调用方确实要覆盖编排区，返回明确说明并要求显式确认；不能静默保存一个由当前流程反复改写的地图。
4. 保持对交付文件变化的 `stale_map` 检查不变。

### P1：建卡前复用验收安全门

1. 在公共建卡入口调用现有 `parseAcceptance` 和 `checkCommandSafety`；存在/包含路径复用同一读路径校验函数。
2. 对“看起来是机械前缀但句式残缺”的行直接报错；绝对路径、串联符、重定向、删除动词、嵌套壳在卡落盘前逐行指出。
3. 不把复杂行为测试伪装成机械项；实测仍由工人执行、部长审核。
4. 自动链发现机械验收硬失败时，显式把卡落为失败状态。语义上推荐增加 `acceptance_failed`；若第一阶段严格不扩失败类型，可先用 `unknown_outcome`，但依据必须写明“机械验收或静态安检未过”，不能继续留假进行中。
5. 修复后复用既有 `failed → unclaimed → in_progress`，尝试上限仍为 2。卡上原来的坏验收重新派发仍会再次失败，因此恢复应能由当前节点开新轮生成合格卡。

### P1：在现有节点控制入口增加受控 reopen

不给主控加“直接改卡”能力，也不更换实例。

1. 在 `pao_control_node` 现有动作中加入 `reopen`，参数至少包含实例、原 owner、节点、当前轮次、理由，并沿用界面确认。
2. 执行前检查：实例/owner/轮次匹配；目标节点没有 `in_progress` 卡；登记表没有该卡活进程；当前尝试没有冲突回执；暂停和裁定状态明确。
3. 复用 `decideNode(change)` 中已有的重置逻辑：把旧轮卡与判定写入历史、轮次加一、清当前卡、`拆解结束=false`、清基线和确认、写重做理由。
4. 保留原实例、原 owner、旧卡与轮次历史。重开后由原节点部长生成新卡/新地图，再走原自动链。
5. 有在途进程、在途卡或回执归属冲突时仍拒绝，保护不放宽。

### P2：盘点路径显式失败

保留现有 `workspace=/app/.pao/benchmark` 用法；仅修复错误默认路径的误导。

1. `worker/inventory.ts:238` 当前把 `/app` 上两级推成 `/`，`inventory.ts:239` 固定扫描 `/卡`。
2. 当 `<workspace>/卡` 不存在时，应返回“路径不合约”的结构化错误，列出检查过的卡目录和可选的显式 `project_root`，不能继续输出“未完卡：无”。
3. 调用方已有正确字段时应传任务工作区 `/app/.pao/benchmark`，或显式传 `project_root=/app`。不应再向更多父级猜路径。

## 验收用例

| 修复 | 最小验收 |
|---|---|
| owner | `owner: ""` 和纯空格在建卡时被拒绝；历史空 owner 卡按无主处理后可认领；真实 owner 仍阻止他人写入；普通 `in_progress → unclaimed` 仍非法 |
| 地图 | 项目根 coverage 默认排除 `.pao/.git`；流程状态、卡、回执连续变化不使地图失效；交付文件真实变化仍返回 `stale_map` |
| 验收预检 | 安全相对路径命令可通过；绝对路径、`&&`、管道、重定向、内联 HTML 在建卡时被拒；坏卡不落正式卡、不结束拆解 |
| 验收失败 | 机械安检未过时卡落入明确失败态，不再假 `in_progress`；可按尝试上限进入下一次合法尝试 |
| 实例恢复 | 无在途卡、无活 worker、无回执冲突时，可让原实例当前节点开新轮；有任一项冲突时仍拒绝；旧轮历史和旧卡保留 |
| 盘点 | `workspace` 下没有 `卡/` 时明确报错；正确任务工作区或显式项目根能找到未完卡与 Git；非 Git 项目仍如实报告不可核验 |

## 关键发现

- 原 `stale_map`、命令静态安检、单写者与在途卡防双跑保护都按设计工作了，不应通过放宽它们解决流程问题。
- 第三轮的空 owner 是 P0：状态仍是 `unclaimed`，却被当成“已有写者”，主控、部长和孤儿接管都没有一条适合它的普通恢复路径。
- 第二轮 worker 已经完成，但机械验收失败后仍显示 `in_progress`，这会误导恢复选择。
- 现有恢复工具足够处理暂停实例、无回执孤儿卡和失败重试；缺的是当前节点受控开新轮，而不是整个恢复体系。
- 模型另建根 `.pao/卡/卡0004` 属于偏离原实例的绕行，不能作为原流程恢复成功。
- inventory 的“无 Git、无未完卡”来自错误推导的项目根和工作区，不是 baseline 或 `.git` 被删除。

## 未核实与限制

- 没有定位到生成 `owner: ""` 的原始部长工具调用参数。现有正常工作流建卡代码 `workflow/control.ts:549` 不主动设置 owner；实际来源仍需在下一轮用部长会话原始工具调用核对。模型自己说“部长多写了空 owner”只能作为假设，不能当事实。
- 没有实际执行 `reopen` 方案；这里只指出可复用的现有位置和必须保留的门禁。
- 没有验证失败类型最终应新增 `acceptance_failed`，还是先用 `unknown_outcome` 过渡；这是主控统一计划的取舍。
- 未重复运行模型、容器、真实宿主集成链或官方测试，因此结论来自停止快照、实际卡/流程文件和当前源码的交叉核对。
