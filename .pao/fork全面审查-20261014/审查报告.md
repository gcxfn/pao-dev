# PAO fork 全面审查报告

> 本报告的修复任务及验收条件已收编至[通用工作台与内核可靠性实施总计划](../../plans/未完成/2026-10-14-通用工作台与内核可靠性实施总计划.md)。调查事实与证据继续维护在本报告；处理状态以总计划为准。

审查日期：2026-10-14。审查对象：当前 `PAO/` 工作区，包含原有未提交修改。本轮没有修改生产源码或项目测试，没有调用真实模型，没有操作正式 PAO_HOME。

## 结论

发现 **16 项可由产品使用路径触发的问题，另有 1 项库接口边界问题**。这表示当前源码存在这些条件性缺陷，不表示正式使用现场已经发生了全部问题。

建议优先处理停止后写入、预算与回执规则冲突、卡片字符串保存和知识入库路径问题，再修指令送达、并发配额及状态反馈。它们会影响“操作到底有没有执行、任务是否真的完成、文件是否保存正确”，应和工作台界面优化一起安排。

严重程度：P1＝优先修复，涉及停止控制或执行结果可靠性；P2＝在具体条件下造成错误、重复操作或状态误导。除特别说明外，下列问题都已有隔离复现；模拟供应商、进程协议和运行器的结果不能代替真实模型集成验证。

## 一、优先修复

### 1. [P1] 点击停止后，尚未发出的共享记忆写入仍会执行

- 位置：[memory/index.ts](../../PAO/packages/coding-agent/src/pao/memory/index.ts)，`buildWriteTool` 第 174 行、`withVendor` 第 126 行。
- 触发：记忆写入工具正在等待供应商启动，用户取消本轮任务。
- 证据：调用正式注册工具后立即触发取消，模拟供应商仍记录 `writes: 1`，工具返回“已写入记忆库”。取消发生在实际 `write` 之前。
- 原因：工具忽略传入的取消信号，等待 `manager.acquire()` 后也未重查取消状态。
- 建议：进入工具、启动等待结束及实际写入前检查取消信号；若供应商支持取消，再继续向下传递。已经完成的外部写入不能靠本地取消回滚，反馈须区分。
- 复现：[memory-cancel-probe.mjs](memory-cancel-probe.mjs)。仅调用模拟供应商，没有真实外发。

### 2. [P1] 父运行器提前杀掉子会话允许的最终回执轮

- 位置：[worker/runner.ts](../../PAO/packages/coding-agent/src/pao/worker/runner.ts) 第 482 行；与 `worker/budget.ts` 第 103–128 行的规则冲突。
- 触发：轮次预算为 1，第一轮使用工具，第二轮需要提交最终回执。
- 证据：子会话的现有离线测试明确允许一次最终提醒/回执轮，并已运行通过；父运行器的隔离进程协议模拟却在第二个 `turn_start` 停止执行，记为 `failed / budget:turns`。
- 影响：任务可能已做完，却没有最终回执，或者被结算为失败。
- 建议：父层与子层共用预算语义，父层兜底也应识别唯一允许的最终回执轮；保留防失控限制。
- 证据及限制：[运行审查记录](runtime-review.md)。尚未用真实 CLI 和模型完成端到端验证。

### 3. [P2] 合法字符串写入卡片后变成数字、真假值或空值

- 位置：[cards/cardfile.ts](../../PAO/packages/coding-agent/src/pao/cards/cardfile.ts) 第 154–157 行，`validateFrontmatter` 第 49 行；下游 `collab/review.ts` 第 107 行。
- 触发：目标写成 `"123"`、`"true"`、`"null"`，或协作父卡使用合法引用 `"1"`。
- 证据：卡片的 YAML（文件顶部的配置格式）输出没有给这些字符串加引号，读回分别得到数字、布尔值和空值。目标 `"null"` 的文件已经落盘，随后读取却报缺少 `goal`。
- 实际工具入口复现：首次协作传 `parent: "1"` 成功；保存后变成数字 `1`，下一次协作申请报 `parent.trim is not a function`。
- 建议：复用项目已有 YAML 包序列化，或统一给字符串正确加引号；同时校验字段实际类型，不能仅检查有无。
- 复现：[卡片字符串复现.mjs](卡片字符串复现.mjs)、[输出](卡片字符串复现输出.txt)；其他标量样本见 [core-review.mjs](core-review.mjs)。

### 4. [P2] 知识入库的新文件名能跨出类型目录，失败前已移动文件

- 位置：[knowledge/ingest.ts](../../PAO/packages/coding-agent/src/pao/knowledge/ingest.ts) 第 62、67、96、134、164 行；工具入口 `knowledge/tools.ts` 的 `pao_ingest_kb`。
- 触发：类型选“做法”，新文件名填 `../跨区.md`。
- 证据：路径检查仅保证在整个知识库内。原候选文件被移动到库根，类型子索引写入不符合预期的链接，最后巡检才抛错。用户看到失败时，原文件已经不在原位置。
- 边界：本次没有突破整个知识库根目录；问题是突破类型目录并留下部分修改。
- 建议：移动前验证普通 `.md` 文件名，拒绝目录分隔符、特殊路径和保留的索引文件名，保证目标直接属于所选类型；失败反馈说明已完成的修改。
- 复现：[knowledge-probe.mjs](knowledge-probe.mjs)，`ingest-path` 场景。

### 5. [P2] 坏卡被静默隐藏，交接页误报没有任务或未决事项

- 位置：[cards/cardfile.ts](../../PAO/packages/coding-agent/src/pao/cards/cardfile.ts) 第 209–223 行；消费者 `cards/handoff.ts` 第 95 行。

### 6. [P2] 模型名称带斜杠时，编辑档位会保存错误名称

### 7. [P2] 给忙碌部长的补充指令被拒收，却报告已注入

- 位置：[host/host.ts](../../PAO/packages/coding-agent/src/pao/host/host.ts) 第 625–626 行；入口 `host/tools.ts` 的部长会话复用及 `first_message`。

- 影响：用户以为意见已送达，部长实际继续按原要求工作。
- 建议：明确即时插话或排队续办，传入已有的 `steer` / `followUp` 模式，等待对应请求的确认后再报告成功。

### 8. [P2] 并发申请协作时，查重和配额一起失效

- 位置：[collab/index.ts](../../PAO/packages/coding-agent/src/pao/collab/index.ts) 第 205–222 行；`collab/review.ts` 第 209、224 行。
- 触发：同项目两个主控会话同时为同一父卡申请同部门协作。
- 证据：父卡协作额度为 1，并发两次调用正式注册工具，均返回“放行”，生成两张子卡。
- 原因：先读卡片并校验，再异步建卡，两次请求可同时看到“尚未建卡”。现有计数器锁只防止卡号重复。
- 建议：将查重、额度检查和创建放进同一临界区，也就是让这几步作为一个整体串行完成，并在锁内重读。
- 复现：[core-review.mjs](core-review.mjs)，`collab-concurrency` 场景。

### 9. [P2] 并发知识巡检会重复创建巡库卡

- 位置：[patrol/drop.ts](../../PAO/packages/coding-agent/src/pao/patrol/drop.ts) 第 41、54 行。
- 触发：同项目两次巡检同时完成，均准备给同部门落巡库卡。
- 证据：两次调用得到不同卡号，且都返回 `exists: false`。正式链路为 `pao_inspect_kb → afterInspect → patrolAfterInspect → createPatrolHook → dropPatrolCard`，没有覆盖跨会话的上层串行保护。
- 建议：按卡目录与部门保护“查找已有卡＋创建”，在锁内重查。本项与第 8 项成因相近，但属于另一个建卡入口。
- 复现：[knowledge-probe.mjs](knowledge-probe.mjs)，`parallel-patrol` 场景。

### 10. [P2] v1 自动推进会超过设定的卡数上限

- 位置：[workflow/auto.ts](../../PAO/packages/coding-agent/src/pao/workflow/auto.ts) 第 213–223 行。
- 触发：同一批有多个可执行节点，剩余额度小于该批节点数。
- 证据：单次上限设为 1，实际运行 2 张卡；默认实例上限 50，已用 49 时又运行 2 张，累计变成 51。
- 原因：只在批次开始检查上限，批内每张卡不再检查。源码注释承认批粒度行为，但它仍会突破防止失控长跑的总量限制。
- 建议：逐卡核对剩余额度，未获额度的节点保留待执行。
- 复现使用真实工作流控制文件及卡片，Worker 由 FakeRunner 替代，无真实模型，见 [工作流复现输出](工作流复现输出.txt)。

### 11. [P2] 没有真正派发的任务也永久消耗自动推进额度

- 位置：[workflow/auto.ts](../../PAO/packages/coding-agent/src/pao/workflow/auto.ts) 第 223 行先计数，第 271 行后检查部门权限；v2 第 167 行也在受理前计数。

### 12. [P2] 记忆供应商并发启动与关闭有竞态

- 位置：[memory/memory-vendor.ts](../../PAO/packages/coding-agent/src/pao/memory/memory-vendor.ts) 第 205、216、223、232 行。
- 触发：两个工具同时首次获取供应商，或会话关闭时供应商还在启动。
- 证据：模拟供应商并发 `acquire` 启动两个实例，关闭只关闭一个；启动过程中 `close`，迟到的启动又把状态改回“已就绪”。
- 影响：可能留下未关闭连接/进程，或关闭后仍保留可用实例。
- 建议：并发调用共用一次启动结果；关闭时让旧启动失效，并关闭迟到实例。供应商自身也应保持关闭幂等。
- 复现：[knowledge-probe.mjs](knowledge-probe.mjs)，`parallel-acquire`、`close-during-start`。实例为模拟供应商，没有启动真实记忆服务。

## 五、建议的修复顺序
