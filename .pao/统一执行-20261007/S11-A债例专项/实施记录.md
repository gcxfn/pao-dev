## 一、逐例根因证据链

### 债例 1-2：主控会话「建立态不上屏」（:508:546 → 修后 :596，:595:634 → 修后 :635 一带）

- 复现（修前，HEAD 3df963c，构建 10-08 23:04，:508 单跑 EXIT=1）：断言败于 :546，按钮 9 次轮询全部「建立主控会话」。**注意 :546 不是首断言——:515 首断「主控会话已建立」是通过的**，主控会话第一次建立成功；失败发生在「新建工作流之后按钮应保持已建立」的复用断言上。
- 失败截图（修前轮）：主控会话真实存在（左侧线程「编辑验证 · 主控」在列），活动标签是新配方草稿标签「新工作流1」，按钮按当前标签无主控的状态显示——**产品行为与状态一致，不是「不上屏」，是「新标签本就没有主控」**。
- 根因：`createNewRecipe`（canvas-page.tsx:486-500）自 S4-1（c202c8e3）起注释明示「新标签不继承旧标签的 controller——同一会话不得绑两个标签」，且主进程 `bindWorkflowController`（app-store.ts:1347）有同会话绑两标签的拒绝守卫、workflow-tabs 单测三条＋workflow-single-view e2e（两标签各自建主控互不串）钉住该契约。而 workflow-canvas.spec 自创建（89800e54，S2+S3 波）从未改过，:544-547/:634 仍是 S4-1 之前的「同标签内新建配方复用已建立的主控」契约——**契约漂移，非产品缺陷**。
- 为什么拖到 S11 才暴露：S4-1 定向门只跑了 workflow-tabs/single-view/bug5 三个 spec，没跑 workflow-canvas；此后每轮 workflow-canvas 的 4 红都被 quit 挂起的 finally 异常掩盖——测试体断言失败后 `finally { app.close() }` 里的挂起异常按 try/finally 语义**顶掉原始断言错误**，全部表现为「30s 关不掉」。S10-B 摘除 quit 挂后真实失败才浮出（B run2、S10-波尾 ⑤、本批修前单跑三度同位，签名一致）。

### 债例 3：保存确认框不弹（:676:705 → 修后 :690 一带）

- 复现（修前单跑 EXIT=1）：守卫「保存并继续」后内核确认框未出现。失败截图铁证：编辑器红色横幅「**请先在项目中建立主控会话，再保存工作流。**」，守卫对话框已关闭。
- 根因：`recipe-canvas-editor.tsx:489` `save()` 无 identity 即拒（`return false`）→ 守卫 `cancelPendingAction`（canvas-page.tsx:612-624）→ 切换动作不执行、确认框永不出。骨架新标签自 S4-1 起无主控 → 保存链必拒。**与债例 1-2 同根**（S4-1 契约漂移），非独立缺陷。

### 债例 4：重开 60s 超时（:727:789 → 修后 :795 一带）

- 复现（修前单跑 EXIT=1，60s 测试超时）：trace 时间轴显示第一阶段全过（建立主控→拖拽→保存→确认→已保存→关闭），二次启动后 sidebar-canvas 点击成功，`canvas-recipe-row` 轮询到超时永不出现。
- 探针实抓第二窗口状态（`证据/s11a-v11-notes.json`）：BODY 文本含「返回工作流中心」「主控会话已建立」、编辑器已加载「编辑验证 · 已保存」与两节点图；COUNTS＝`{"canvasList":0,"recipeRows":0,"workflowTabs":0,"workflowEditor":1}`——**应用处于 S4-2 单工作流嵌入视图**：重启恢复了绑定标签与会话，点 sidebar 工作流入口按契约进入嵌入视图，配方随标签自动读回，工作流库（含配方行）按设计不渲染。测试还在找库行，自然超时。
- 根因：S4-2 入口分流契约（canvas-page.tsx:387-412 workflowEntryNonce 消费）与测试的「全中心→点行」导航期待相悖。**产品行为符合设计，且「恢复即自动读回」对持久化断言是更强证据**。

### T09 签名一：reopen-state:15（30s app-close kill）

- 复现（修前单跑 EXIT=1）：测试体全过，挂死在**第二次** close（spec:158）。Last app output 仅一条 `[test quit] before-quit`，无 will-quit——quit 链停在 before-quit 守卫第一段（requestAll 未决）。
- 根因（读测试体＋守卫实现闭环）：reopen-state 收尾前执行 `forcefullyCrashRenderer()`（验证崩溃恢复），随后 finally quit → `before-quit` → `workflowLeaveGuard.requestAll` → `request()` 见 `contents.isCrashed()` 走**原生兜底 `dialog.showMessageBox`**（main.ts:322-334「继续等待/放弃并离开」，设计上不超时自动批准）→ 测试环境无人应答 → quit 永久停摆 → 30s kill。B 包 harness 代答只覆盖**页内**对话框，覆盖不了**原生**框。
- 顺带：该轮的 `Worker teardown timeout of 120000ms` 是 kill 的下游副产品——harness win32 超时杀只杀主进程，子进程树残留持有输出管道，Playwright worker 收尾等管道到超时（S10-B 已登记的 harness win32 树杀缺口）。杀不再发生，teardown 挂即消失（见修后 3/3）。

### T09 签名二：settings-appearance:134（60s Playwright 测试超时）

- 单跑实证（扩时 120s 后）：**1 passed (1.8m)**——不是挂死，是「8 预设×2 明暗＝16 轮 UI 往返」的矩阵测试实测 108s，超出默认 60s 预算（配置注释自认 CI 机器还要慢 2-3 倍）。T09 记录的 3/3「60s 超时」全是预算问题。

## 二、共查结论（任务书假设逐条）

1. 「主控会话生命周期事件不达渲染层＝症状 1 与 3 共同根因」——**证伪**：主控会话建立成功且上屏（截图左栏线程在列、:515 首断言过）；症状 1-3 共同根因是 S4-1 新标签不继承主控，保存链缺身份。
2. 「teardown 挂＝worker/扩展宿主句柄不放」——**部分证伪**：T09 本尊挂＝守卫原生兜底框等人（非句柄）；teardown 挂＝SIGKILL 留子树持管道（下游副产品）。另在探针中观察到一类「will-quit 已到、进程 30s 不退」的挂（见第四节排除清单），未在真实 spec 流中复现。
3. 4 债例＋T09 **不同源**：前四例全是「测试侧契约漂移」（S4-1×3＋S4-2×1），T09 是「测试制造极端状态＋测试预算」——与波审 P2「:727 与关闭挂起 3 例应拆两族」的判断一致并进一步细化。
