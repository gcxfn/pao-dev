## 二、冻结语义（拒旧条件＋代际重置时序）

1. **拒旧条件同义**：内核 isStaleEvent（view-envelope.ts:37-39）＝`event !== current`；桌面 canvasEventStale（canvas-model.ts:303-309）＝两侧均有值且不等。在有值域上完全同义；缺省分支桌面放宽为「未知不拒」（spec canvas.spec.ts:449-453 逐值钉死）。差异仅在缺省值：内核签名要求 string，若强传 undefined 且对侧有值会判「旧」（拒）；桌面判「不拒」。这是 renderer 不可引 node:crypto（view-envelope.js 引 Node 模块进不了浏览器包）下的必然本地位，两侧实施记录均已注明边界（D2 记录§二末行）。登记为 P3-6：事件通道落地时须保证内核事件负载必带 generation，否则「缺省不拒」会把旧内核事件全放行。
2. **代际重置时序一致**：内核换代际的唯一时机＝作用域身份变化（sessionGenerationOf 输入变化）；消费方接管基准的唯一时机＝commit（canvas-page.tsx:367-368 `baselineRef.current = arrival`），drop/dedupe 不动基准。切作用域（重挂组件→ref 重建为空基准；或同挂载下发新请求→新代际随最新请求 commit 接管），与契约「消费方切换后以新查询的代际为基准」逐句对齐。卸载 cleanup bump（canvas-page.tsx:395-398）额外覆盖 effect 因依赖变化重跑的场景，防旧 api 实例响应回落——语义正确。
3. **注意双代际空间**（P3-7）：canvas 信封作用域＝`{paoHome}`（canvas.ts:101 注释、:385），**不随会话/工作流切换而变**；快照信封作用域＝`{项目根, 会话}`（read-model.ts:216-218）。canvas-page.tsx:352-355 注释「切会话/工作流重置 generation」措辞易误读为 canvas 信封代际会随会话变——实际 canvas 的会话/工作流切换靠组件重挂＋requestId 承接，代际只在切 PAO home 时变。与 K4 契约表「作用域＝PAO_HOME」一致，非漂移，但注释值得在后续包顺手修正。

## 三、D2 关键解读裁定（第 3 项审核面）

**裁定：解读成立。** D2「拉路径有意不做代际≠基准即拒」是对契约的正确分层，非漏洞。依据四点：

1. **契约文本自身分层**。正本 §S6 第 4 条（计划 L265）：「切会话/工作流重置 generation，拒旧事件」；K4 冻结契约（view-envelope.ts:16-21 注释＋实施记录契约表）：「**消费方切换后以新查询的代际为基准**，**事件代际**≠当前代际＝旧作用域事件拒收」。拒旧谓词的主语自始就是「事件」，查询路径的规则是「以新查询的代际为基准」——基准条款的含义即「采纳并重置」。D2 拉路径只做 requestId 竞速＋指纹去重，事件路径才挂 canvasEventStale（通道未建、语义已钉），与契约分层逐字对应。
2. **反证成立**：若拉路径做「≠基准即拒」，切换作用域后首个携带新代际的查询会被旧基准拒收，而基准更新只发生在 commit 上——拒收即永不更新，死锁。D2 记录所述「拒了新数据永远拒收」在机制上精确成立。
3. **requestId 竞速在拉模式下充分，「requestId 与代际都不足以区分」的窗口不存在**。一个 requestId 恰好对应一次 `api.getCanvas()` 调用，Electron invoke 一对一应答、无复用 id 的重试层——同一 requestId 不可能产生两个响应，故不存在「同 id 双响应竞速」。能携带旧代际的响应只能产自旧作用域时期发出的查询；而消费方每次切作用域（重挂或发新请求）都会使旧请求的 id 落后（spec canvas.spec.ts:456-484 两态钉死）。旧代际响应能 commit 的唯一情形＝它就是最新请求的应答——即消费者最近一次主动查询所询问的真相，且 generation+revision 恰好完整标识「哪个作用域＋什么内容」，不存在错标。指纹去重亦不吞更新：dedupe 要求 gen 与 rev 双等（canvas-model.ts:326-332），rev 是内容纯函数，同 rev⇒同内容；基准为空（旧 dist）时从不去重（canvas.spec.ts:516-530）。
4. **残余窗口良性且有界**：内核作用域在「请求已发出、响应未回、此后无更新请求」的间隙翻转时，旧代际数据会 commit 并接管基准，直到下一次刷新才被新代际覆盖。这是拉模式的标准语义（所见即所查，数据恰是查询时刻的权威投影），窗口由下一次刷新闭合；在此窗口叠加代际拒旧只会更糟——保留更旧的数据且阻塞基准重置。

附注（非裁定变更）：onStarted 补拉把 `applyCanvasResult` 的返回计划（drop/dedupe/commit）弃用，后续定位新实例/开标签副作用无条件执行（canvas-page.tsx:585-618）。当前语义下这是向导预期行为（无论哪个响应获胜都要开新实例标签），不构成漏洞；但未来若 arrival 语义扩展（如信封缺失改判 drop），此处会误触发——登记 P3-8。
