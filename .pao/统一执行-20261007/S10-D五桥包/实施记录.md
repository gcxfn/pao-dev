## 四件修法与结论

### ① 卡号函数单源化（桌面）——同口径，合一处导出

- 取证：两处为同一「卡NNNN」命名规则的两个方向，不是同函数互抄——
  `formatCardNumber`（原 kanban-command.ts:40，数字→引用，平行内核 counter.ts formatCardNumber）
  与 `cardRefNumber`（原 kanban-board.tsx:1259，引用→数字，平行内核 counter.ts parseCardRef /
  cardfile.ts cardNumberFromFileName）。两者互为逆运算、口径一致（格式化产物可被解析原样读回），
  按任务书「同则合一处导出」收敛。
- 修法：`cardRefNumber` 移入 `kanban-command.ts` 与 `formatCardNumber` 同文件导出（kanban-board.tsx
  本就 import 该模块，零新文件、零新增依赖）；调用点全改（唯一调用点 findNodeCard 改走 import）；
  kanban-command.spec.ts 新增 1 条单测钉互逆性与不认格式返回 undefined。
- 与内核口径差异（如实报，不属两处之间差异）：桌面解析只认「卡NNNN」整引用（不认内核 parseCardRef
  的「卡#17」/「17」变体），不认时返回 undefined 走缺卡显式处理而非抛错——看板引用只来自内核产物，
  窄口径是有意的防御面，维持原行为不改。
- 另发现（登记不修，归主控裁）：`electron/platform/pao/canvas-query.ts` 卡面整形里还有一处内联
  四位补零（cardRef: `卡${...padStart(4,"0")}`），是命名规则的第三份拷贝；在 electron 主进程层，
  与 renderer 层 kanban-command 不便互引，超出本包「两处」点名范围，未动。

### ② 目录整形防御面口径统一（桌面）——坏条目显式错误行

  改为显式入错误行：`{ name: "未知", available: false, error: { code: "形状损坏", detail: ... } }`，
  复用契约既有的条目级错误面（CanvasRecipeEntry 不可用变体），对齐 wizard `normalizeCatalog`
  「坏行显式上报」与 S2 验收「坏文件明确报错」口径。
- 正常输入面零变化：好行、坏档（可用:false＋错误键）行走原路径；既有测试（好/坏混合、非列表抛错）
  全部原样通过。新增 1 条单测钉坏条目显式行。
- 已知边界：内核 canvas 投影（desktop/canvas.ts:59）保证配方行必带名字，坏行只可能是传输损伤；
  多条坏行会重名「未知」（渲染 key 相同），属防御路径罕见态，接受不处理。

### ③ flow-control-query 断言纪律（桌面）——逐字段收窄，不新增报错面

  终读仍由 normalizeFlowControl fail-fast。未加任何新抛错点（加严会在坏形态时提前改写报错面，
  违背「不新增报错面」）。既有测试 :144-148（工作流非列表显式失败）原样通过，无需新增测试
  （无行为变化）。
