## 一、结论

**竞态确实存在（四处叠加的发送竞速窗口），需要补丁；但后果与 A6 原文「前一条被顶掉/丢失」不同**：

1. **不会发生双跑或消息静默丢失**——内核最底层的 `Agent.prompt()` 有 `activeRun` 单飞闸（`PAO/packages/agent/src/agent.ts:373-378`，`runWithLifecycle` 内 `:507-510` 检查与 `:517` 置位之间无 await，原子），第二条必被抛错拒绝；桌面回执链把错误上浮、草稿恢复（`app-store-composer.ts:601-602`、`use-session-composer.ts:170-184`），第二条文本不丢。
2. **真实后果有二**：
   - **常态窗口**（第二条晚到一点，第一条已置 `_isAgentRunActive`）：第二条被内核干净拒绝（`agent-session.ts:1967-1971`"Agent is already processing. Specify streamingBehavior..."）→ 桌面弹出错误横幅＋会话被误标 `failed`（`session-supervisor.ts:1123`）——**该发出去的消息变成报错＋草稿回退**，而不是按用户预期排队。
   - **重叠窗口**（第二条在第一条的内核前置期到达）：两条并发进入 `_runAgentPrompt`（`agent-session.ts:1776`，无互斥），输家在 `agent.prompt` 抛错后其 `finally`（`:1797-1804`）**提前发出 `agent_settled` 并把 `_isAgentRunActive` 清零（`:1053`），而赢家的 run 还在跑**——早落定、状态来回翻转（idle↔running，`session-supervisor.ts:2792-2800` vs `:2653/:2706`）、`agent_settled` 双发、`runningRunId` 被输家覆盖后清掉（`:1009`→`:1112`→`:2648` 补随机值），早落定窗内新发的消息全部报错直至赢家真正落定。
3. 窗口在四层都开着（渲染层无闸、主进程无闸、driver 入口只查内核流式位、内核 isStreaming 检查在输入事件 await 之后）。触发不需要病态条件：**快速连发两条消息**（Enter 后几十 ms 内再 Enter）即进入窗口；冷会话（transcript 未加载）、慢盘写快照、OAuth 鉴权刷新（秒级）会显著拉宽窗口。

判定：**存在，需要补丁**；补丁目标是「第二条自动排队重放＋前置卡死兜底」，不是防双跑（双跑内核低层已防住）。

### 2.2 复现路径（操作序列 → 代码路径）

前提：会话 idle（新会话或上一轮已落定）、模型已选。

序列 A（常态窗口，最容易复现）：
1. 用户输入消息 1，回车。渲染层以无 `deliverAs` 的 send 发出（`use-session-composer.ts:162-164`，status 陈旧为 idle）。
2. 消息 1 走 `session.prompt()`，进入内核前置 await（如鉴权/扩展钩子），`_isAgentRunActive` 尚为 false。
3. 用户在「running」广播回到渲染层之前（冷会话/慢盘/鉴权刷新时窗口达数百 ms～秒级）输入消息 2，回车——status 仍 idle，消息 2 同样无 `deliverAs` 直发。
4. 消息 2 到 driver 入口（:976）时若消息 1 已置位流式标志 → 内核 `:1967-1971` 抛错 → driver `:1123` 把会话标 `failed`＋`runFailed` 事件 → 渲染层错误横幅＋消息 2 回退草稿。**用户预期是排队，实际是报错**。

序列 B（重叠窗口，状态污染）：
1. 同上 1-3，但消息 2 的内核 `isStreaming` 检查（:1967）发生在消息 1 置位（:1784）之前。
2. 两条并发进 `_runAgentPrompt`（:1776）：消息 1 先占 `activeRun`；消息 2 在 `agent.prompt`（agent.ts:374）抛错，其 finally（agent-session.ts:1797-1804）提前 `_emitAgentSettled`——`_isAgentRunActive=false`＋`agent_settled` 事件**在消息 1 的 run 进行中发出**。
3. driver 侧：早落定映射 status=idle/runEnded（:2792-2800）；消息 1 的后续流式事件又把 status 拉回 running（:2653/:2706）→ UI 摆动；消息 1 真正落定时第二个 `agent_settled`（双发——PAO 挂 settle 的扩展面会见到两次，具体影响需修复包内核实）；`runningRunId` 被消息 2 覆盖（:1009）再清空（:1112），消息 1 的 `agent_start` 只能补随机值（:2648）。
4. 早落定窗内（isStreaming=false 但 activeRun 仍被占）任何新发送都会在内核低层再抛错＋再早落定，直到消息 1 结束。

## 三、最小补丁清单（不实施；供主控派包）

### 首选：desktop 仓 driver 单飞闸（建议道次：desktop，S4-3 修复包）

1. **入口同步闸＋忙时转排队**（核心落点 `session-supervisor.ts`）：
   - 在 `sendUserMessage`（:959）入口、任何 await 之前给 record 置同步「发送在途」闩（JS 单线程＋IPC 按序派发，同步前置段对后续并发提交可见，闸即闭合；`promptStarting` 不够——它在两个 await 之后才置位）。
   - `sendReadyMessage` 的忙判定（:976）从「仅 `session.isStreaming`」扩为含在途闩（或直接用 `isRecordBusy`:3802）。忙且无 `deliverAs` 时**不再抛错**，转既有排队道：追加 `record.queuedMessages`（followUp）＋持久化＋提示，语义与 running 期排队（:1043-1080）一致；重放沿用既有 `startQueuedMessageWhenIdle`（:1247-1319，`whenIdle`:1480-1483 在 `agent_settled` 触发）——「排队重放」零新机制，内核 followUp 语义已核实（2.3）。
   - 直发分支在 `session.prompt` 前补一次落定窗复检（对齐排队分支 :1049-1053 的现成写法）。
2. **超时兜底**：前置卡死（`promptStarting` 置位后既无 `agent_start` 也无拒绝，如鉴权挂死）60s 计时到 → 上抛可重试错误（复用 `runFailed` 事件面）并保留队列，不伪造运行态（对齐取消道「no timeout that fakes a stop」的既有哲学，:1332-1334 注释）。
3. **渲染层（可选加固）**：`submitComposerDraft` 把「接收」态（`sendAcceptedPendingRun`，五态表 `thread-control-state.ts:57-60` 已有该态）视同 running 补 `deliverAs`；发送按钮在接收态禁用或转排队文案。渲染层因陈旧不可能成为主闸，只做一致性。
4. 事件名全部现成：driver 侧 `sessionUpdated`/`runFailed`/`queuedMessageStarted`/`runEnded`；内核侧不新增事件。

### 伴随（可选，另一道次）：内核早落定窄修（建议道次：PAO 仓，小包）

`agent-session.ts` `_runAgentPrompt`（:1776-1784）入口在置位前补 `if (this._isAgentRunActive) throw new Error("Agent is already processing. Specify streamingBehavior ('steer' or 'followUp') to queue the message.")`——**在 try 块之前抛**，避免输家 finally 提前 `agent_settled`。这把重叠窗后果从「状态污染」降为「干净报错」，且惠及 CLI/RPC 等其他宿主。若做此项，桌面闸（首选项）仍是主修——内核窄修只兜其他宿主与未来新入口。

### 不建议：内核扩展级参照闸（pi-maestro-flow 抄改件 `submit-gate`）

参照件模式（input 拦截 handled＋agent_settled 释放＋60s 兜底＋source==="extension" 放行，见 `plans/附件/2026-10-07-pi-maestro-flow抄改代码摘录.md:255-280`）在当前内核 API 上可落（2.3 已核实），但 **desktop driver 自带排队/自启机制（record.queuedMessages＋startQueuedMessageWhenIdle）会与扩展级闸的重放双轨**，有双投递风险（driver 自启经 `session.prompt` 直发，input 事件 source 是 interactive 而非 extension，扩展闸无法识别放行）。对 A6（桌面侧问题）收益为负，登记为否决方向；仅当将来要给无自有队列的宿主（纯 CLI/RPC）补闸时再评估。
