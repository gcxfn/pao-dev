# A8 外围模块必要性与简洁性审核

审核完成日期：2026-10-29  
范围：任务书 §6.8 指定的 PAO 外围模块  
性质：只读静态审核；未修改源码，未启动真实模型、Docker、Harbor 或 Electron，未进入正式 PAO_HOME。本文是本次唯一写入文件。

## 1. 结论

1. **没有发现 P0。** knowledge、memory、usage、routing、healthcheck、patrol、todo、context、notify、friction、桌面读模型等均有真实装配点或外部入口，不能因为名字像外围模块就删除。
2. **A8-01，P1：工作流部长仍会被暴露实际不会放行的工具。** 工作流部长在 index.ts 的 tool_call 白名单之外注册了 knowledge、memory、healthcheck、status 等工具；基准又保留部长原有 active tools 再加入必需工具。工具定义默认激活，所以模型会看到必然被拒的调用，增加试错轮次和基准波动。
3. **A8-02，P1：巡库链只完成了“发现并落卡”，没有完成 worker 可执行、结果可消费的闭环。** 主控或部长可调用 pao_inspect_kb 自动落巡库卡，但 worker 角色跳过整个 knowledge 模块；卡面却又要求复跑 pao_inspect_kb。judgment、retire、demote、repair 也只有测试调用，没有生产调用者。
4. **A8-03，P1：自动交接是用户可见的无效开关。** 记忆供应商配置和 /pao 设置页仍提供“自动交接”，文案承诺压缩时写记忆；resident 没有 session_compact 写入处理，测试还明确断言不会写供应商。这个控制项会让用户误以为记忆已同步。
5. **A8-04，P2：状态视图存在“同一出口”承诺与实际不一致。** 首跑清单提示重看详情走 /pao status，但 status 不渲染待处理段；/pao pending 才是包含人工门、缺输入、失败待处置的出口。pano 又重复 status 的大部分只读聚合，适合收拢为一个投影加不同视图。
6. **A8-05，P2：存在已证实的测试专用导出和未接入产品路径。** worker/usage.ts 的 budgetGate 没有生产调用；knowledge 的 repairIndex、retireEntry、demoteToPending 及 judgment 消费没有生产调用。它们不是垃圾文件，分别是旧公开 API、故障修复能力或巡库链缺口的证据，应先决定接入或兼容退役。
7. **不可删的部分已经确定。** src/experimental 相对上游合入点没有改动，且发行 files 排除它；src/extensions 是上游内置 MCP、codemode、tool-search、llama 加 PAO 接线，不能按“PAO 外围”删除。desktop 读模型、迁移 CLI、通知、摩擦草稿、todo、用量账均有真实消费者或明确用户需求。

## 3. 问题清单

### A8-01 P1：注册面、active 工具面和 tool_call 授权面不一致

**证据**

- role.ts:39 的部长跳过清单只有 fanout、collab、host、resident；所以 knowledge、memory、healthcheck、status、todo 等仍注册。
- src/pao/index.ts:309-334 对 workflowMinister 只允许 13 个工具，其他工具在调用时返回 block。
- 基准 activate-tools.mjs:51-53 对部长采用 getActiveTools() 加必需工具，而不是改成工作流白名单本身。
- core/extensions/types.ts:603-607 明确 direct/model-only 工具注册后默认 active；getActiveTools 正是声明给模型的集合。
- knowledge/tools.ts:249-271 无条件注册 pao_restricted_query；根入口未传 restricted 授权时，它每次只能返回“未授权”。

**根因类别**

装配边界把“模块已注册”“工具声明给模型”“某次调用允许执行”混成了三层。静态注册一层没有真正按角色收窄。

**关联历史**

未找到直接对应停链的历史证据；这是静态可确认的模型负担和误调风险。r35 的 activate-tools.mjs 已把该风险做成可观测面，但本轮未真实运行，不能声称已造成某轮失败。

**修复方向：结构改**

- 在 I3 建立一份小型 loadout 表，列出主控、普通部长、工作流部长、worker 的模块、active tools、命令和允许调用集合。不要新增通用插件框架。
- workflowMinister 在第一个 provider 请求前直接 setActiveTools 为静态白名单；不要继续用 tool_call 规则拦已经展示给模型的工具。
- pao_restricted_query 只在有卡号、轮次和知识库绑定时注册或激活。
- pao_health_check 对工作流部长和基准默认隐藏；主控若需要，用显式诊断命令或用户明确要求时启用。
- 普通部长保留现有知识、记忆、状态等业务能力，不把工作流白名单外推到所有部长。

### A8-02 P1：巡库卡生成后没有闭合的 worker 与终审消费链

**证据**

- patrol 真实接线：src/pao/index.ts:451-457 给 knowledge 注入 patrolAfterInspect；knowledge/tools.ts:365-394 在巡检后调用回调。
- patrol/hook.ts:84-108 把注册表中的库映射为部门并调用 createPatrolHook；draft.ts:53-65 在 ⚠️ 达到阈值时生成卡，卡面验收要求复跑 pao_inspect_kb。
- role.ts:47-50、76 明确 worker 跳过 knowledge；loadout-role.test.ts:118 对 worker 记录的注册工具只有 read、todo_write、pao_save_dispatch_recon。
- knowledge/judgment.ts:42-85 没有生产调用者；repairIndex、retireEntry、demoteToPending 也只由测试调用。代码图入边分别返回 0（repairIndex、retireEntry、demoteToPending）。
- shell 护栏只拦 bash 与 powershell（patrol/wire.ts:41-51），不会拦 write/edit；若巡库 worker 被要求直接改文件，现有“只准写 ⚠️ 与初判”的约束没有同一层的机械执行器。

**根因类别**

能力按模块分别实现，但没有定义一个“巡库结果”可被谁接收、谁能执行、如何终审的闭环契约。卡面文案先于执行能力落地。

**关联历史**

未在本轮找到“巡库卡已落但没有 worker 能执行”的真实运行记录。该问题由当前静态可达性直接证明，历史影响仍标为未确认。

**修复方向：结构改，须在删除任何代码前决定**

推荐先做两件事：

1. 主控或部长执行“机械发现并生成报告”，不要在 worker 无工具时自动落卡。
2. 增加一个窄的巡库执行入口：worker 只能读取指定知识库、只写受控初判段或结构化 judgment 结果，不能改条目正文；终审由部长通过现有知识工具完成。

若暂时不做窄入口，应把 patrolAfterInspect 从自动落卡降为报告提示，避免产生无法完成的卡。repair/retire/demote 先保留，它们是完成该链的现成原语，不能按“只有测试调用”删除。

### A8-03 P1：自动交接设置可见但确定无效

**证据**

- memory/memory-vendor.ts:106-114 定义自动交接字段，:147-159 接受并返回该值。
- panel/index.ts:301-310 在设置页展示“自动交接”，文案称压缩时把交接摘要写进记忆供应商。
- 当前 memory/resident.ts 只有 before_agent_start 的常驻索引、自动召回和 context 纠正处理；没有 session_compact 写入桥。
- memory-resident.test.ts:597-607 明确验证自动交接开启后写入次数为 0；:631-648 还验证不外发、不启动供应商。

**根因类别**

旧行为被安全策略停用后，配置读取和 UI 控制仍保留，界面与真实行为脱节。代码没有静默执行错误动作，但向用户表达了错误能力。

**关联历史**

原计划曾实现压缩摘要交接，后来以“任务状态不能写入共享用户事实库”收紧。本轮证据来自当前代码和现行测试，不对旧轮是否损害结果作推断。

**修复方向：局部改**

推荐在 P2 删除或隐藏“自动交接”设置入口。配置字段可继续读取并忽略，以兼容旧文件；若字段为 true，面板应明确提示“历史字段，当前不生效”。若将来恢复，只能交接用户明确授权的长期事实，不能自动写任务摘要。

### A8-04 P2：status、firstrun、pano 三个只读出口边界不清

**证据**

- status/firstrun.ts:113-125 把 pending 四行拼进首跑清单，并提示“重看详情：/状态（同一出口）”。
- status/index.ts:32-69 只渲染任务、部门、用量、后台/值守，不包含 collectPending 或 renderPendingSection。
- preflight/index.ts:360-361 实际注册的是 /pao pending，而不是 /pao status。
- panorama/index.ts:111-175 再次聚合队列、工作流、部门、后台、用量；与 status 的主体高度重叠。

**根因类别**

同一批只读事实被三个命令各自组合，命令的文字承诺没有以共享投影契约测试。

**关联历史**

没有把该文案差异关联到某次真实停链；它会增加用户找错出口和漏看待决项的风险。

**修复方向：局部改，后续合并渲染**

- 立即把 firstrun 的提示改为 /pao pending，或让 /pao status 真正包含 pending 段。
- 保留 status 作为短总览，pano 作为详细/钻取视图；两者共用同一聚合函数，不各自维护 section 读取逻辑。
- panel 只负责命令与设置入口，继续复用这些子命令，不复制数据读取代码。

### A8-05 P2：存在真实测试专用导出，但当前不能直接删

**证据**

- codebase-memory trace_path 对 budgetGate 的入边为 0；rg 只在 worker/usage.ts 定义和 usage-rollup.test.ts 调用。
- worker/index.ts:94 从 pao 公开 barrel 转出该文件；src/pao/index.ts:90 再转出 worker/index.ts，所以删函数会影响已发布 pao 入口。
- knowledge 的 repairIndex、retireEntry、demoteToPending 入边为 0；只在 knowledge-repair.test.ts、knowledge-retire.test.ts、knowledge-patrol-chain.test.ts 调用。
- 这些能力对应“引用修复、退役、打回待验证”，是巡库终审实际需要的动作，不能因为有测试无生产调用就判为无用。

**根因类别**

基础能力先落地，产品接线或公开兼容策略没有同步完成。

**关联历史**

属于实现先后顺序问题，没有历史停链证据。

**修复方向**

- budgetGate：先标记 deprecated/internal，补一个周期或消费者审计；若确认没有仓外调用，再在大版本中删除。不要现在直接删公开导出。
- knowledge maintenance：结合 A8-02 决定接入哪个终审工具；接入后保留实现，不保留无入口的重复 wrapper。
- 删除门槛：生产入口、桌面桥、公开包消费者、测试夹具四处均为零，且写明兼容替代。

### A8-06 P2：PAO_HOME 解析被放在 routing/config

**证据**

- routing/config.ts:155-162 定义 resolvePaoHome，与档位配置同文件。
- src/pao/index.ts:39、memory/index.ts:22、healthcheck/index.ts:16、cards/tools.ts:8、desktop/index.ts:9 等不同域都从 routing/config 导入它。
- package ./pao 和 ./pao/desktop 又把它作为公开面转发。

**根因类别**

共享路径基础设施没有独立归属，导致模型路由模块承担了全项目的环境解析职责。

**关联历史**

纯结构耦合，没有停链证据。

**修复方向**

把 PAO_HOME 路径解析迁到 shared 配置模块，由 routing、memory、knowledge、desktop 共同引用。保留原导出别名以避免破坏公开导入。该调整应随 I3 或 I6 的窄批次进行，不单独启动全库改名。

### A8-07 P2：总预算能力与 v2 需求文本存在批准来源冲突

**证据**

- v2-REQUIREMENTS.md:29 明确不要“预算/审批机器”。
- v2-REQUIREMENTS.md:110 要求用量显示与四项指标，重点是观测成本。
- 后续执行计划 2026-10-17-Harness完善与工作台迭代执行计划.md:313-322 又明确批准“显式总预算”的预留、结算、未知占用与并发锁。
- usage/dispatch-gate.ts:225-271 在无显式总预算时返回 undefined，不增加派发门禁；有总计时才启用。当前代码没有凭空设默认额度。

**根因类别**

需求正本没有同步记录后续局部批准，形成表面冲突。当前实现是条件启用的安全机制，不等同于 v2 当初否决的重型预算平台。

**关联历史**

暂无该门禁造成停链的证据；缺少总预算时路径为零行为。

**修复方向**

保留当前显式总预算实现，在 P2 修订需求正本或决策记录，写清“反对默认预算和审批平台；允许用户显式授权的持久总预算”。如果不保留该能力，再单独删除 ledger、gate、命令和兼容读取，不能在文档冲突未解决时直接删。

## 4. 大刀阔斧的目标设计建议

### 4.1 用一个角色装载矩阵收口，不增加插件框架

新增一个很薄的 loadout 定义，输入角色和运行形态，输出：

- 要注册的模块；
- 首次请求前应声明给模型的 active tools；
- 可执行的命令；
- 仅接受程序调用的隐藏工具；
- workflowMinister 的动态拒绝条件。

真实存在的重复是模块清单、白名单和基准激活器各写一份，适合合并。矩阵只表达静态角色和上下文差异，不引入动态插件发现、优先级总线或通用依赖注入。

验收应直接读取真实 AgentSession 的 getActiveTools/getAllTools，并核对最终 provider payload。至少固定四组：主控、普通部长、工作流部长、worker。

### 4.2 巡库链要么闭环，要么保持报告模式

推荐目标链：

~~~mermaid
flowchart LR
  inspect[机械巡检] --> report[结构化巡库报告]
  report -->|超过阈值且执行入口可用| card[巡库卡]
  card --> worker[受限巡库 worker]
  worker --> judgment[结构化初判]
  judgment --> owner[部长终审]
  owner --> update[更新 / 退役 / 打回]
  inspect -->|无执行入口| notice[只提醒，不落卡]
~~~

程序必须判断“执行入口是否可用”，不能只看阈值。worker 的写权限由工具准入控制，不能只写进卡面约束。shell 护栏保留，同时文件写工具要另设巡库白名单或禁止直接写。

### 4.3 只读视图用一个投影层，三个入口只做不同呈现

建议统一数据投影：

- 任务与卡计数；
- 待处理项；
- 挂起工作流与实例异常；
- 部门积压；
- 后台与在途 worker；
- 用量下界与未知项。

status 输出短摘要；pano 输出完整分区与钻取；firstrun 输出启动时需行动的子集；桌面 read-model 输出结构化 JSON。四者复用同一投影函数，不再各自从目录拼一次。

### 4.4 保留清单与删除顺序

必须保留：

- knowledge 的查库、入库、巡检与维护原语；
- memory 的常驻索引、手动写入/召回、供应商生命周期；
- usage 的原生用量归一、页脚、跨会话账和显式预算；
- routing、healthcheck、patrol shell 护栏、todo、context、notify、friction；
- desktop 读模型和 migration；
- 上游 experimental；
- extensions 中的 MCP、codemode、tool-search、llama 及 10-25 的 MCP 关闭重试补丁。

先删或降级：

1. panel 的自动交接可操作入口；
2. 工作流部长的无效 active tools 与无授权 pao_restricted_query；
3. 巡库无执行入口时的自动落卡；
4. status/firstrun 的错误“同一出口”文案。

满足兼容审计后再删：

1. budgetGate；
2. 无生产入口且已被新巡库链替代的 wrapper；
3. 统一投影完成后重复的 section 组装代码。

### 4.5 迁移步骤

1. P2 确认无人值守与巡库策略。
2. I3 先落 loadout 快照和真实 active tools 测试。
3. I1/I3 接通巡库结果契约或明确报告模式。
4. 主控整合点修改 src/pao/index.ts，删除工具可见性错位；不改公开工具名。
5. I6 统一 status/pano/firstrun 文案与投影，删除无效设置说明。
6. 最后按公开 API 消费者清单移除测试专用导出；冻结历史与实验源码不动。

风险：

- 过度集中 loadout 会让模块自行注册能力变得难追踪。控制方式是矩阵只列最终事实，模块内部仍负责自身业务。
- 删除自动交接字段可能破坏旧配置读取。保留读取兼容，只移除可操作 UI。
- 巡库工具开放过多会形成越权写。应只开只读和结构化初判，不开 cards、delivery、workflow 管理。
- status 与 pano 合并可能牺牲终端快速查看。保留短/详两视图，不保留两份取数实现。
