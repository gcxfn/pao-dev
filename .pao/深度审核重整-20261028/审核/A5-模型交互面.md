# A5 模型交互面：工具、提示词与回执协议

审核员 A5，只读。日期 2026-10-28。状态：完成。术语：**工具声明**＝每轮随请求发给模型的工具名、说明和参数模式，模型据此决定调什么；**回执**＝工人做完卡后交给部长/主控的结果；**钩子拦截**＝工具已声明给模型，但调用时被程序的 `tool_call` 钩子拒绝。
记号：SRC/ ＝ `PAO/packages/coding-agent/src/pao/`；R37/ ＝ `.pao/地图简报与部门协作-20261020/benchmark/real-run-20261028-prepared-r37/jobs/pao-audit-first-20261028-r37-task-1/html-js-filter__QhDcwrN/agent/`；统计脚本 `临时文件夹/深度审核重整-20261028/sess-stats.ps1`，输出 `sess-stats.json`（138 个会话：r3—r37 共 25 个运行目录里能找到的主控 26、部长 78、工人 34）。

## 1 结论（按影响排序）

1. **部长在“看得见却不能用”的工具上空转，是模型层最大的浪费**。工作流部长的工具声明里有 bash、edit、write、todo_write、tool_search、pao_dispatch_brief、pao_worktree_*、知识库 4 个工具等 27 个，真正放行的只有 read 加 9 个部长工具（SRC/index.ts:314-334）。78 个部长会话里：bash 274 次调用 274 次被拒，tool_search 113/113，pao_dispatch_brief 54/54，pao_query_kb 46/46，todo_write 34/34，pao_worktree_list 22/22，全是同一句“工作流部长只读规划；请通过 pao_minister_submit_cards 交工人执行”。r30—r37 的 24 个部长会话仍有 72 次 bash 被拒。这些工具不该声明，不是该让模型反复撞墙。
2. **部长的 read 失败率 62%**（3343 次调用，2071 次报错：EISDIR 168、ENOENT 约 1900）。原因（推断，证据见 §3 A5-02）：grep/find/ls 被放行却没激活，模型只能用 read 当 ls 去探目录和猜路径；README、requirements.txt、index.html 这类根本不存在的文件被反复探测，还去读容器里不存在的 `/tmp/harbor-pao-source/...` 内核源码。
3. **主控会话从首轮约 5.0k token 涨到约 124k（23 条助手消息）**，不是工具声明大，而是轮询：26 个主控会话里 pao_inventory 327 次、pao_query_flow 306 次，而启动指令明确写了“不 sleep、不轮询”。每次查询返回整份流程快照，被原样留在上下文里。主控对流程的“理解”完全靠这些快照，程序本可以在唤醒时直接注入一句话状态。
4. **回执仍是“最后一条助手消息里的 JSON 文本”**：工人只有 7 个原生工具，没有任何 pao 工具，回执只能写成文本（SRC/worker/dispatch-core.ts:122-125 要求；SRC/worker/runner.ts:1023-1050 解析，失败再走围栏/裸 JSON 恢复，SRC/worker/receipt.ts:273-600 约 330 行扫描代码）。其中 `changes`（改了哪些文件）、`artifact_path`、`usage`、`exitCode`、`command` 都是程序能自己得到的事实，却要模型抄写；r37 工人 a9818683 的最终回执 9591 字符里 changes 与 artifact_path 是纯重复事实。一个带类型的回执工具 `pao_submit_receipt` 其实早已存在（SRC/cards/tools.ts:570），但工人进程不装、不用。
5. **主控的验收手续约 8 步、十余个须模型抄写的标识字段**：decision_pack → accepted_deviations 每项填 attempt/verification_index/condition/basis＋总 basis → change_status（operator 必须等于卡面 owner）→ deliver_card → 核实 → query_flow → control_node rule（instance/node/round/result/reason/references）→ push_flow。r30—r37 的主控 231 次调用中 42 次报错；其中 18 次是“须用户在界面显式确认”（无出口，A2-1），其余是抄错标识、理由超长或缺 `file:line`、顺序不对。这些字段几乎全部是程序已知事实。
6. **预检装配与真实运行装配不一致**：r37 的工人预检探针看到 read/bash/edit/write/todo_write/pao_save_dispatch_recon，真实运行只有 7 个原生工具、`required_registered` 为空（R37/organization/tool-activation.jsonl 工人行；R37/organization/probes/worker/ 对比）。预检通过不代表真实装配正确，侦察卡要求调用的 `pao_save_dispatch_recon`（dispatch-core.ts:118）工人实际没有（推断：该工具仅在工人经派发 kit 装载时才有，需 A3 的装配图确认）。
7. **建议**：角色工具集按“最小可完成本角色工作”重定：主控 9→2、部长 10(有效)→3-4 加 4 个只读原生、工人 7 原生＋1 个带类型的回执工具；回执里程序事实全部由程序采集；主控验收手续合并为一个带类型的 `pao_owner_decide`，无人值守时模板化部分由程序执行。

## 3 问题清单

严重度：P0＝会让无人值守整链停住或给出错误结论；P1＝高风险或已在历史运行出现；P2＝维护与简洁性。

### A5-01 P0 审核判定从未成功提交：规则只在报错时才告诉模型，且一条报错混了三个条件
- 证据：r24、r29、r34 三轮的审核部长共调用 `pao_submit_decision` 23 次，23 次全部被拒（sess-stats.json；r24 7/7、r29 5/5、r34 11/11）。拒因 17 次是同一句“判定须含理由（最多 400 词，中文逐字计；最多 1600 字符）与 file:line 引用”，其余是顺序（须拆解结束且全部卡机械交付后，3 次）和回边（打回目标没有声明回边，2 次）。
- 代码：SRC/workflow/control.ts:1024-1032 一个 `if` 把结果值、理由为空、理由 >1600 字符、词数 >400（汉字逐字计，另按词计，:1028）、引用为空、任一引用不匹配 `^.+:\d+` 合成一个报错，模型无法知道是哪一条。r34 审核部长的 6 次重试里理由从 3,601 字符降到 473 字符，引用里仍混着 `selftest/audit_probe.evidence.log`（无 `:行号`），所以始终失败；参数模式（SRC/workflow/minister.ts:644-653）把 `reason`、`references` 只声明成 `Type.String()`/`Type.Array(Type.String())`，没有长度或格式约束，规则也不在工具说明里（minister.ts:643）。
- 根因类别：协议（规则不可见）＋手续太多。关联运行：r24、r29、r34（A1 把这三轮的停点归为审核/状态一致性，未单列“判定被拒”）。
- 修复方向：结构改。把判定拆成 `result`、`axis`、`findings[{path, line, note}]`（line 为整数，缺了不让提交）、`summary`（≤300 字，工具说明里写明）；超长由程序截断并回显，不拒绝；顺序前置条件在审核节点启动时由程序保证，不靠报错提示。

### A5-02 P0 工作流部长约 12% 的调用打在“被钩子拒绝”的工具上（必败），read 又有 62% 失败，合计 66% 的部长调用报错
- 证据：78 个部长会话，bash 274/274、tool_search 113/113、pao_dispatch_brief 54/54、pao_query_kb 46/46、todo_write 34/34、pao_worktree_list 22/22、pao_inspect_kb 5/5 全部被拒（拒因同一句），合计约 548 次；read 3,343 次中 2,071 次报错（EISDIR 168、ENOENT 约 1,900）。r30—r37 仍然如此（bash 72 次、tool_search 24 次、dispatch_brief 13 次、query_kb 10 次被拒；read 报错 约 130 次 ENOENT/EISDIR）。
- 代码：SRC/index.ts:309-335 先“跳过”8 个模块，再注册部长工具，再用白名单钩子拒绝其余；但 read/bash/edit/write/todo_write/tool_search 等是原生与全局模块的工具，不受“跳过”控制，仍进入声明。白名单放行 grep/find/ls（:317-320），而 R37/organization/tool-activation.jsonl 部长行的 `active` 里没有 grep/find/ls，所以模型只有 read 可探路。部长系统提示的 tools 段（R37 部长会话首条 system）只列 read/bash/edit/write/todo_write/pao_worktree_create/list/cleanup/tool_search，让模型把 bash 当主要探索手段。
- read 的失败来源：系统提示 `docs` 段（1,274 字符，所有角色都有）写着“Pi 文档位于 /tmp/harbor-pao-source/packages/coding-agent/README.md …”，容器里并没有这个目录，模型每个会话去读一遍（ENOENT 89 次出现在该路径）；再加上模型去猜 `/app/README.md`、`requirements.txt`、`index.html`、`/usr/local/lib/python3.12/site-packages/bleach|html5lib|lxml_html_clean/...`（侦察/规划在探测第三方库是否存在）。
- 根因类别：协议（声明与放行不一致）。关联运行：r3—r37 每轮都有。
- 影响：直接成本是模型回合与 token；间接影响是模型在被拒后会换路子（用 pao_minister_submit_cards 之外的方式“绕”），也使 `tool_search` 之类“找更多工具”的行为必然失败。
- 修复方向：结构改。声明集合＝放行集合（§4.1）；原生探索工具改为 read/grep/find/ls 同时激活；去掉 `docs` 段（对 PAO 角色无用，且指向不存在的路径）。

### A5-03 P0 工人回执是文本里的 JSON，格式出错就停链（承接 A1-04）
- 证据：A1 记录 r9、r25、r28、r32、r36 五轮因回执缺字段、散文包裹 JSON 或双围栏而停。代码：提示 SRC/worker/dispatch-core.ts:122-125；严格解析并在失败时进入恢复 SRC/worker/runner.ts:1021-1050；围栏/裸 JSON 扫描 SRC/worker/receipt.ts:273-600（约 330 行，含 `scanMarkdownFences`、候选唯一性规则）；必填字段校验 :91-148（`summary` 超 3 行判 problem，:134）。一个 `usage`/`evidence_path`/`exitCode` 必填的 `validateReceipt`（:115）其实是对程序合成的回执做的，模型文本只需 result、artifact_path、summary、任务态、verification、changes。
- r37 样本：工人 a9818683 的最终文本回执（9.6k 字符的会话首条用户消息之后）把 `changes`（含 `.pao/benchmark/黑板.md`）和 `artifact_path` 都写了一遍；这些由程序用 git 状态加事件流里的 write/edit 调用可得。summary 被要求“不超过 3 行”，模型写成含 `\n` 的 3 行，擦边通过。
- 同时存在带类型的通道却没用：`pao_submit_receipt`（SRC/cards/tools.ts:570，只追加、硬校验产物路径存在/摘要≤3 行/尝试号一致）与 `AppendReceiptInput`（SRC/cards/receipts.ts:12-27，已有 任务态、verification、changes 字段）。工人进程不装卡工具（role.ts:70-91 工人跳过 18 个模块）。
- 修复方向：结构改，见 §4.2。

### A5-04 P1 主控验收是 8 步手续，模型要抄十余个标识
- 证据与代码：见 §2.3 与启动提示 `benchmark_organization`（R37 主控会话首条 system，844 字符；源码版 benchmark-sdk-host/activate-tools.mjs:62-66，与 r37 冻结件不同，A2 已指出）；change_status 的 `accepted_deviations` 必须恰好覆盖全部自报 fail/not_run 项，每项含 attempt/verification_index/condition/basis（SRC/cards/tools.ts:584 的描述）；r30—r37 主控 42 次报错里有 `accepted_deviations 的 attempt 必须等于当前尝试 2；收到 1，旧尝试参数不能重放到新尝试`、`canceled → unclaimed 非法迁移`、`没有匹配的主控裁定请求`（26 次，全期）。
- 根因：把“程序已知的事实”设计成了模型的校验题；模型填错只是被拒绝，不会被纠正。
- 修复方向：结构改（§4.1，`pao_owner_decide`）。

### A5-05 P1 主控靠轮询工具把自己的上下文撑到 124k
- 证据：26 个主控会话 pao_inventory 327 次、pao_query_flow 306 次、pao_push_flow 109 次（push 用于“没有可推进的就返回”）；r37 主控会话 23 条助手消息、输入从 5,025 涨到 123,930。启动提示明确要求不轮询（SRC 对应 activate-tools.mjs 与 `pao-dispatch-lifecycle`）。主控被后台通知唤醒后，通知文本（"有新的后台结果，请读取本轮注入的通知摘要"）并未带摘要内容——r37 主控会话里该通知后的第一反应是“No actual notification content injected? … Let me query the flow and inventory”（assistant thinking 原文），然后一次调 query_flow＋inventory。
- 根因：唤醒消息没有信息量，迫使模型自己查询；查询返回的是完整快照，并留在上下文里。

## 4 目标设计

### 4.1 各角色最小工具集（前后数字）

原则：声明集合＝放行集合；程序已知的事实不让模型填；一个意图一个工具；工具按“角色×节点类型”装载，其余不注册（不是注册后拦截）。

| 角色 | 现在（声明/实际可用） | 建议 | 变化说明 |
|---|---|---|---|
| 主控（基准/无人值守） | 9 / 9（含 inventory、query_flow、push_flow 轮询类，control_node 6 个 action） | **2**：`pao_flow_status`（只读，仅在被唤醒信息不够时用）、`pao_owner_decide`（带类型的验收裁决） | start_flow 由宿主在受理时直接调内部函数（主控不再启流）；ack_supervision 改为程序记账；push_flow/deliver_card/change_status/control_node 的组合由 `pao_owner_decide` 内部按固定顺序执行；inventory 删除（轮询类）。有人值守时另加 `pao_control_node` 的 pause/resume/reopen 三个人工动作，不进无人值守集合 |
| 工作流部长（只读节点：侦察/规划/审核前期） | 27 / 10 | **5**：read、grep、find、ls、`pao_node_submit`（联合类型：`map` 或 `decision`） | save_node_map＋breakdown_done 合一（map 提交成功即结束拆解）；submit_decision 并入同一入口；request_ruling 在无人值守下删除（改由 `pao_node_submit` 的 `needs_owner` 字段申请，程序按冻结的运行方式处理，A2 的停点表给出出口） |
| 工作流部长（实施节点） | 27 / 10 | **5**：read、grep、find、ls、`pao_node_submit`（`cards[]` 或 `rework[]` 或 `review` 工人结论） | submit_cards 提交成功即结束拆解（breakdown_done 删除，需要零卡时提交空数组加理由）；review_worker/rework_cards 合进同一联合类型 |
| 工人 | 7 / 7 | **8**：read、grep、find、ls、bash、write、edit＋`pao_report`（带类型的回执，见 §4.2） | 只加一个工具；侦察卡的结构化结果（现 `pao_save_dispatch_recon`）合进 `pao_report.recon` 字段 |
| 审核部长 | 同实施节点 | **5**：同只读节点集 | 判定由 `pao_node_submit{kind:"decision"}` 提交，见 A5-01 |

总量：注册给模型的 pao 工具由现在主控 9＋部长 24（声明）＋工人 0，降到主控 2＋部长 1＋工人 1。58 个 pao_* 工具里，上述角色用不到的（计划 6、知识 4、记忆 3、worktree 6、协作 fanout/collab 等）只在“终端/桌面主控”场景装载，不进基准和工作流部长。预计首轮输入：部长 9.5k→约 4k token（去掉 17 个无效声明、docs 段、tools 段中的失效项），主控 5.0k→约 3k，工人持平（约 7k，主要是卡简报）。**这些数字是估算，不是测量**；可在离线彩排（§5）里以脚本化模型记录每轮请求体字符数直接对比。

### 4.2 回执：带类型的工具参数＋程序采集事实

现状：工人最后一条消息是 JSON 文本；程序解析不到就走恢复，再不行判 `unknown_outcome`（runner.ts:1021-1050）。

新协议 `pao_report`（工人唯一回执入口，模型调用后会话自动结束，没有调用则程序判“无回执”，并在同一会话里追加一条提醒一次）：

```
pao_report({
  state: "completed" | "completed_with_deviations" | "blocked" | "checkpoint" | "failed",
  failure_type?: "transient" | "missing_input" | "insufficient_capability" | "unknown_outcome",
  summary: string,               // 参数模式 maxLength 600；超长由程序截断，不拒绝
  verification: [{ condition: string, result: "pass"|"fail"|"not_run", evidence: string }],
  recon?: { facts[], unknowns[], scope[], acceptance[], risks[], evidence[], integration? }   // 侦察卡
})
```

由程序采集（不再让模型写，也不再校验模型写的值）：
- `changes` 与 `artifact_path`：从工作树 git 状态（相对认领基线）加事件流里 write/edit 的目标路径得到；`.pao/` 内的流程控制文件按白名单剔除，不混进“本次成果”。
- `usage`、`exitCode`、`command`、`pid`、`duration_ms`、`evidence_path`：本来就是程序写（receipt.ts:40-70），保持。
- 命令与退出码清单：来自事件流里的 bash 工具调用；`verification[].evidence` 允许模型引用其中的编号，不必复述输出。
- “自报 not_run 必转 owner 裁决”：保留作为数据，是否转人工由冻结的运行方式决定（A2-3）。

要改的地方（逐项）：
1. 新增工具：`SRC/worker/` 下注册 `pao_report`；`role.ts:70-91` 的工人跳过清单中放行该模块；工人进程的 `tool-activation` 加入。
2. 提示：`worker/dispatch-core.ts:122-125` 四行 JSON 说明改为一句“完成后调用 pao_report”；参数说明承载格式要求。
3. 解析：`worker/runner.ts:1021-1050` 改为读取 `pao_report` 的工具调用结果；`worker/receipt.ts:273-600` 的围栏扫描与恢复（约 330 行）、`receipt_format_recovery` 字段整体删除；`validateReceipt`（:115-148）只保留对程序采集字段的断言。
4. 卡层：`cards/receipts.ts:12-27 AppendReceiptInput` 已有 任务态、verification、changes，直接作为 `pao_report` 的内部落点；`cards/tools.ts:570 pao_submit_receipt` 并入或删除（避免两个回执工具）；`cards/cardfile.ts:535`、`migration/migrate.ts:92`（BULLET_KEEP）保持卡面中文键不变（兼容契约，任务书原则 7）。
5. 机械验收：`cards/verifier.ts` 现比对“模型自报 changes”与 git 真值；改为以程序采集为唯一来源，比对逻辑可整段删除，“自报与实际不一致”变成不可能状态。
6. 迁移与回退：保留读旧回执（含历史卡）的解析路径一个版本；新旧开关由冻结的配方字段 `回执协议: tool|text` 控制；测试见 §5。
7. 风险：模型不调 `pao_report`（以文本结束）；缓解：会话结束钩子检测到未调用，追加一次“请调用 pao_report 提交回执”并给 1 轮，仍无则判 unknown_outcome（与现状一致，但不再需要格式恢复）。

### 4.3 主控验收：`pao_owner_decide`

```
pao_owner_decide({
  decision: "accept" | "rework" | "abort",
  items?: [{ index: number, verdict: "accept" | "reject", basis: string }],   // 对自报 fail/not_run 逐项
  summary: string                                                          // 总 basis
})
```
instance、node、round、attempt、condition、operator、card_no 全部由程序从当前待办填入；`items` 若未覆盖全部偏差，程序在返回里列出缺的 index 再让模型补，而不是拒绝。内部固定顺序执行 change_status → deliver_card → push_flow，中间任何一步失败整体回滚并返回一句话原因。无人值守下 `accept` 直接生效，不再出现“须用户在界面显式确认”（A2-1）。

### 4.4 提示词按需装载

- 系统提示由三层拼接：身份（≤300 字，固定）、当前节点职责（≤500 字，来自冻结配方的该节点段）、当前动作（≤300 字，由状态机在进入该状态时注入，例如“拆解中：先看地图，再 pao_node_submit”“收到工人结果：先看 verification 的 fail/not_run”）。
- 删除：pi 的 `docs` 段（1,274 字符，所有角色）、主控的 `pao_temporary_plan`、空 `pao-resident-memory`、`pao-dispatch-lifecycle` 与 `benchmark_organization` 的重复句。
- 部长系统提示的“tools”段由实际放行集合生成，不再列已被拦截的工具。
- 唤醒消息带内容（A5-05）：“实施节点卡0001 已回执：自报 3 项 not_run；请 pao_owner_decide”。

### 4.5 迁移步骤与风险

1. 先做 A5-02 的声明＝放行对齐和 docs 段删除（半天，纯减法，最容易验证）。
2. 做 A5-01 判定入口重写（依赖 A2 的状态机）。
3. 做 `pao_report`（§4.2）与 `pao_owner_decide`（§4.3），旧工具保留一个版本、默认关闭。
4. 提示分层。
风险：兼容契约——公开工具名属于契约（任务书原则 7）。`pao_owner_decide`、`pao_node_submit`、`pao_report` 是新增；旧名（push_flow、deliver_card、change_status 等）在终端/桌面的有人值守场景保持可用，只在无人值守装载集合里隐藏，所以不破坏现有用户；P2 请用户确认。

## 5 离线验证方式
