## 5. 大刀阔斧的目标设计建议

### 5.1 源码、配置、运行记录三地分离

推荐布局如下；具体名字由 P2 的目标架构最终决定，核心是保持一个事实一个家：

| 内容 | 建议位置 | 说明 |
|---|---|---|
| 基准控制器、观察器、准备/评分入口、测试 | 开发根 bench/src/、bench/tests/ | 可提交、可引用、可独立测试 |
| 部门配方、题目清单与版本锁 | bench/configs/、bench/fixtures/ | 小文件才入库；大依赖走摘要缓存 |
| 一轮真实运行 | .pao/<任务>/runs/<run-id>/，忽略 Git | 只放不可变输入摘要、事件账本、结果、自动报告 |
| 历史报告与冻结快照 | .pao/archive/ 或现有任务目录内 | 只读；只由索引链接，不再追加 |
| 决策原因 | .agents/notes/implemented/ 或 rejected/ | 只写为什么，不复写运行经过 |

benchmark-organized-entry.mjs、benchmark-child-entry.mjs、benchmark-host-factories.mjs 等若仍承担独立适配职责，迁入 bench/；若统一产品宿主已覆盖，则按 A3 结论删除。benchmark-worktree-host.mjs 是生成副本，不迁为手写源码。

### 5.2 迁移步骤

1. 以 P0 基线为底，先把现役基准和适配器复制到新 bench/ 骨架；原目录保持只读，避免边迁边改。
2. 把现有测试改成导入新源码，添加“仓内 .pao/ 不得出现可执行基准源码”的边界检查。
3. 用一个已结束的 r37 运行目录做回放，验证新入口只读取旧证据、不改历史；输出与旧入口一致后才切换 README 和调用方。
4. 把旧源码目录标记冻结；确有重复价值的探针迁入测试，其余留在历史快照。真实运行目录只保留终端收据、任务摘要、控制状态等小证据，超大依赖副本改摘要引用。
5. 最后再精简执行总册和规则文件；迁移事实稳定前不改写历史正文。

风险与保护：迁移期间存在两份源码，必须明确哪一份可写；在新入口离线回放通过前，旧入口仍是唯一运行入口；任何清理都先做路径、跟踪状态和引用检查。

### 5.3 流程自动化边界

| 现在人工或模型完成 | 新做法 | 保留的人工判断 |
|---|---|---|
| 手工冻结 HEAD、diff、未跟踪文件和 38—42 个 SHA | 一条命令生成 manifest；工作区不干净就拒跑或明确进入开发验证模式 | 是否允许带补丁运行 |
| 手工汇总测试命令、退出码、耗时 | 每个命令包装器直接写事件账本；报告自动生成 | 失败是否阻断、是否接受已知失败 |
| 总册、治理计划、治理记录各写一遍 | 运行目录一份 report.md；总册只留阶段状态、最终结论和链接 | 契约变化、跨模块取舍、用户授权 |
| 每轮启动脚本复制改参数 | bench run 接受一份配置和 run-id，自动选网、准备、观察、收尾 | 真实模型运行授权 |
| 成功后人工拼摘要 | 根据账本生成事实摘要，模型只补为什么和剩余风险 | 质量结论、是否继续下一阶段 |

这不是再建一套任务状态机：状态仍归现有工作流、卡和运行账本；这里只增加围绕一次 benchmark 运行的可重复命令和自动报告。
