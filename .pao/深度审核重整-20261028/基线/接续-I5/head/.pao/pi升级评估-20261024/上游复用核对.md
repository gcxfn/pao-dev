# PAO 生命周期修复与 pi v1.4.0 上游复用核对

日期：2026-10-25
性质：只读源码核对；未运行测试、模型或实际升级

## 结论

升级时应先采用 pi v1.4.0 的统一启动路径，再在这条官方路径外接回 PAO 的关闭门和排空语义。不能因为函数名称相近，就删除当前本地修复。

本次核对没有发现 v1.4.0 已提供 PAO 当前需要的完整生命周期：

- v1.4.0 已提供 `_startRun()`、`_prepareRun()`，以及用户消息和 custom message 共用的启动、启动期 abort 处理。
- v1.4.0 仍没有“停止受理新轮次”的关闭门，也没有把已受理活动、settled 回调和 deferred actions 一起纳入空闲判断。
- v1.4.0 的 runtime `dispose()` 先发 `session_shutdown`，后由 session 的同步 `dispose()` 调 `agent.abort()`；这不满足主动销毁时先停止受理、再 abort 活动、等待收敛、最后 shutdown 的顺序。
- v1.4.0 的 print mode 没有后台结果等待；正常结束时直接进入 `dispose()`。
- v1.4.0 的 `prompt()` 仍先 `await _tryExecuteExtensionCommand()`，再决定是否开始普通轮次。PAO 当前同步预查真实扩展命令，是为了避免 `/new`、`/resume`、`/fork` 等替换当前会话的命令等待自己。

当前修复不应被理解为五个彼此独立的新框架。最小必要边界可以收敛为一个会话级关闭门，加一套确定的收敛顺序：

1. 关闭门先停止受理新轮次。
2. 正常 print 等待已经受理的后台结果和 follow-up 轮次完成。
3. 主动销毁时，关闭门之后 abort 仍在运行的活动，等待活动、settled 回调和 deferred actions 收敛。
4. 收敛后才发 `session_shutdown`、释放后台端口并使旧上下文失效。

## 上游可直接复用的部分

### 统一启动和 custom message

v1.4.0 的 `packages/coding-agent/src/core/agent-session.ts`：

- `_startRun()` 约在 1873 行。它在第一次 `await _prepareRun()` 前同步设置 `_isAgentRunActive = true`。
- `_prepareRun()` 约在 1926 行，统一处理 compaction、`before_agent_start`、系统提示、用户消息和 custom message。
- `prompt()` 约在 2092 行，最终调用 `_startRun({ messageType: "user", prompt, images })`。
- `sendCustomMessage()` 约在 2357 行；需要触发轮次时调用 `_startRun({ messageType: "custom", message })`。
- 约 1103 至 1106 行处理“启动期间收到 abort”：等 `agent_start` 出现后立即调用 `agent.abort()`。

这部分应由上游提供。升级后不要再保留一套名称不同、行为相近的 PAO 启动实现；PAO 只在其外增加受理计数和关闭检查。

### print 截断响应退出码

v1.4.0 的 `packages/coding-agent/src/modes/print-mode.ts` 约 154 至 157 行，把 `stopReason === "length"` 作为非零退出。当前 PAO HEAD 没有这项行为，可直接采用。

### `agent_settled` 的 abort 状态

v1.4.0 的 `_emitAgentSettled()` 在 `agent-session.ts` 约 1078 至 1099 行发出 `agent_settled` 时携带 `aborted`。PAO 现有事件处理、RPC 事件类型和测试需要适配这个字段。

## 必须保留的 PAO 缺口

### 1. 关闭门与已受理活动计数

当前修复在 `agent-session.ts` 约 1046 至 1076 行维护关闭等待、`_acceptedActivityCount`、`_isSettled()` 和 `_throwIfClosing()`；约 2504 至 2519 行提供 `beginClose()` 与 `close()`。

v1.4.0 的 `isIdle` 约在 1484 至 1485 行，只检查 agent run 和 compaction；源码中没有 PAO 的 accepted activity 计数、closing 标志或 close 等待接口。

这不是重复实现，必须保留。升级后应让关闭门覆盖用户 prompt、会触发轮次的 custom message、后台通知触发的 follow-up，以及扩展命令执行期间的边界。

### 2. settled 回调与 deferred actions 的完整排空

v1.4.0 的 `_emitAgentSettled()` 会在 `agent_settled` 回调和 deferred action 完成前把 `_isAgentRunActive` 设为 false；`isIdle` 可能因此过早返回 true。

当前修复在 `agent-session.ts` 约 1089 至 1101 行增加 `_isDrainingSettledActions`，并在约 1061 至 1069 行把 settled 回调、deferred actions 和 accepted activity 一起纳入 `_isSettled()`。必须保留，否则正常 print 可能在合法后台结果尚未处理完时就关闭。

### 3. 真实扩展命令的同步预查

当前修复在 `agent-session.ts` 约 1964 至 1995 行先同步调用 `_extensionRunner.getCommand(commandName)`：

- 找到真实扩展命令时执行命令，不计入旧 session 的 accepted activity。
- 未知 slash 命令、`/skill:` 和普通输入，在第一次 await 前计入 accepted activity。

v1.4.0 的 `prompt()` 在约 2101 至 2108 行先 await `_tryExecuteExtensionCommand()`，而该函数到约 2186 行才查询命令。

保留当前同步预查的理由不是优化，而是语义：`/new`、`/resume`、`/fork` 可能在命令处理中替换当前 session。若把命令自身算作旧 session 的活动，旧 session 会等待一个只有替换完成才结束的操作，形成自等死锁。

### 4. 单飞入口检查

PAO HEAD 已有的 `_runAgentPrompt()` 在进入活动区前同步检查 `_isAgentRunActive`。v1.4.0 的 `_startRun()` 一开始就设置 active，但静态源码中没有同等的“进入前再次拒绝”检查。

因此升级时要保留同步单飞检查，并放在官方 `_startRun()` 设置 busy 之前。两个并发调用若都先通过较早的 `isStreaming` 检查，上游目前没有第二道同步拒绝。这个结论来自源码静态比较，尚未通过 faux provider 运行复现。

### 5. runtime 主动销毁顺序和幂等

v1.4.0 的 `packages/coding-agent/src/core/agent-session-runtime.ts`：

- `teardownCurrent()` 约在 167 至 178 行，顺序是 `abort → session_shutdown → invalidate → dispose`。
- `dispose()` 约在 404 至 411 行，顺序是 `session_shutdown → invalidate → session.dispose()`；session 的同步 `dispose()` 随后才调用 agent abort。
- 没有 `beginClose/close`，也没有 `_disposePromise` 幂等。

当前修复约 169 至 183 行、409 至 424 行的顺序是：

`beginClose → abort → close → session_shutdown → 释放后台端口 → invalidate → session.dispose`

并保留 `_disposePromise`。必须保留。它同时解决三个问题：

- 主动销毁时先拒绝新轮次。
- 活动模型收到 abort，并等到轮次、通知和 settled 回调收敛。
- `session_shutdown` 在旧上下文仍可能接活之前发出，避免销毁后的晚到事件落入旧上下文。

### 6. 正常 print 的合法后台结果等待

v1.4.0 的 `print-mode.ts` 没有 background-work 等待，约 166 至 170 行 finally 直接 `disposeRuntime()`。

当前修复在约 124 至 157 行通过 background-work 端口的 `snapshot()` 和 `waitForChange()` 等待 running/unread 归零，并在通知可能启动 follow-up 时再次确认 session idle；约 178 至 179 行先执行正常 `session.close()`，之后 finally 才 dispose。

必须区分两类事件：

- **关闭前已受理事件**：正常 print 必须等待并让合法后台结果进入 follow-up，不能先 shutdown 把结果丢掉。
- **销毁后晚到事件**：关闭门拒绝新轮次，主动销毁再 abort 当前活动并完成收敛。

因此“先 shutdown 再 abort”不是可接受的简化；同时，正常 print 也不能把关闭门当作“立即丢弃通知”的开关。

### 7. 后台工作、通知和 PAO 业务面

`packages/coding-agent/src/core/background-work.ts` 是 PAO 增量，v1.4.0 没有对应文件。它按 `SessionManager` 对象身份提供 running/unread 快照、变化等待、关闭错误和端口释放。

相关 PAO 增量还包括：

- `packages/coding-agent/src/pao/runtime/background.ts`
- `packages/coding-agent/src/pao/worker/notify.ts`

`sendDispatchNotifyWakeup()` 使用 `pi.sendMessage(..., { triggerTurn: true, deliverAs: "followUp" })`；通知正文由下一轮 `before_agent_start` 注入。这些实现承载 worker、workflow、fanout、host 和通知面状态，不能由 v1.4.0 替代。

## 升级适配点

以下工作只列为后续实施项，本次没有修改。

| 位置 | 适配要求 | 原因 |
|---|---|---|
| `before_agent_start` | 从旧的 `(prompt, images, options)` 调用适配为 `BeforeAgentStartTrigger`；同时覆盖 `messageType: "user"` 和 `"custom"` | custom message 也要进入同一启动路径，并能在启动期 abort |
| `_startRun()` | 采用上游统一实现；PAO accepted activity 的生命周期包住它，但不复制它 | 避免两套启动逻辑分叉 |
| `prompt()` | 在任何 await 前做 closing 检查；同步预查真实扩展命令；未知 slash、skill、普通输入在第一个 await 前登记已受理活动 | 防止关闭窗口漏接输入和替换命令自等 |
| `sendCustomMessage()` | 在触发轮次分支接 closing 检查与活动登记，然后调用上游 `_startRun({ messageType: "custom" })` | 通知 follow-up 也属于真实会话活动 |
| 单飞检查 | 在官方 `_startRun()` 同步置 busy 前完成最终拒绝 | 上游目前缺少进入前第二道检查 |
| `agent_settled` | 消费上游新增的 `aborted` 字段，并保持 PAO settled/deferred 排空 | 上游空闲快照不覆盖 PAO 的延迟动作 |
| `waitForIdle` 与 `close` | 明确两个语义：`waitForIdle` 等待 agent 主轮次；`close` 等待所有已受理活动完整收敛 | 后台通知和 settled 回调可能发生在 agent run 结束之后 |
| runtime teardown | 主动替换和 quit 都采用 `beginClose → abort → close → shutdown → 释放端口 → invalidate → dispose`；dispose 保持幂等 | 保留取消语义并防止晚到事件 |
| print mode | 正常完成先等待 background-work 和可能的 follow-up，再 close；仅异常/信号销毁路径主动 abort | 区分合法排空与主动取消 |

升级不宜直接整体 cherry-pick v1.4.0 的三个文件。应先引入官方启动主路径，再逐项重接 PAO 缺口，并使用无模型 faux provider 做定向验证。

## 正常 print 与主动销毁的顺序

### 正常 print

1. 输入和已受理后台通知继续运行。
2. 等 background-work 快照没有 running/unread。
3. 等待可能由通知启动的 follow-up 轮次结束。
4. 调用 session `close()`，确认 accepted activity、agent run、settled 回调和 deferred actions 都已收敛。
5. 再进入 runtime dispose 和输出收尾。

### 主动销毁或信号

1. `beginClose()`，立即拒绝新轮次。
2. `abort()`，终止仍在运行的模型请求、工具和后台轮次。
3. `close()`，等待取消后的持久化和回调收敛。
4. 发出 `session_shutdown`。
5. 释放 background-work 端口，使旧上下文失效，再销毁 session。

这两条顺序共同满足“正常结果不丢”和“主动销毁不留活上下文”两个要求。

## 若改用 `vastsa/PI-Desktop` 作为宿主

截至本报告日期，没有核对 `vastsa/PI-Desktop` 的实际插件 API，因此下面不是兼容性结论，而是 PAO 现有闭环要求宿主或适配层提供的接口。必须逐项用真实源码和最小探针确认。

### 扩展与事件

- 按 session 创建相互隔离的 `ExtensionAPI` 和扩展闭包；旧 session 替换后，旧 `pi/ctx` 必须失效并给出可识别的 stale 错误。
- `on(...)` 至少支持 PAO 使用的输入、会话、agent、provider、tool 和 UI 生命周期事件。
- `before_agent_start` 必须同时接收用户输入和 custom message trigger，允许修改 system prompt sections，并返回附加消息。
- `agent_settled` 必须携带 `aborted`，且宿主不能把事件发出误当成所有异步后续已收敛。
- `before_provider_request`、请求 headers、响应和流事件必须存在，用于预算硬拦、路由和诊断。

### 注册与消息

- `registerTool`
- `registerCommand`
- `registerFlag`
- `registerProvider` / `unregisterProvider`
- `registerVirtualModel` / `unregisterVirtualModel`
- MCP 工具、资源和连接注册
- `sendMessage`、`sendUserMessage`、`appendEntry`
- 工具渲染、消息渲染、状态 UI、快捷入口和确认交互

### 会话控制

- `waitForIdle`
- `newSession`、`fork`、`switchSession`、`reload`
- 替换后的 `withSession(ctx)` 回调
- 能访问 canonical context、session id、cwd、session file 和持久化 transcript
- 多会话或多标签页之间不能共享命令闭包和旧 session 上下文

### 生命周期与后台工作

- 提供 running/unread 快照和变化通知，或提供可让 PAO 实现同等语义的 session 绑定接口。
- 正常结束路径允许等待已受理的后台结果和通知触发的 follow-up。
- 主动销毁路径允许先封闭受理，再 abort、收敛、shutdown。
- 若宿主不直接提供 PAO 的 `background-work` 端口，适配层必须完整保留对象身份绑定、端口释放和关闭错误语义。

### 进程、文件与运行环境

- 管理 worker、fanout、自动链等子进程树。
- 提供跨进程文件锁。
- 可读写独立 `PAO_HOME`、项目 `.pao` 和工作区文件。
- 能保留 worker 身份、取消、通知和 receipt 语义。

### 宿主模式相关能力

若仍保留 CLI、JSON、RPC，还需要：

- print 的最终结果与退出码语义，包括截断响应非零退出。
- JSON 事件流和 stdout backpressure。
- RPC 的 background-work 事件、session 替换和 `waitForIdle` 契约。

若 `PI-Desktop` 只承担桌面宿主，这一组可标为模式相关能力；但不能把桌面可运行当作 PAO 全闭环已满足。

## 尚不确定与后续验证

- 本次没有升级到 v1.4.0，也没有运行测试。上述替代关系来自共同 base、PAO HEAD、当前工作树和 v1.4.0 的静态源码比较。
- 上游缺少 `_startRun()` 前单飞检查是源码可确认的缺口；具体并发时序仍需 faux provider 定向验证。
- `vastsa/PI-Desktop` 的实际 ExtensionAPI、session 隔离、custom trigger、后台生命周期和 provider 钩子尚未核对。
- 后续最小验证应明确使用 faux provider，不访问网络、不产生付费模型调用，覆盖：
  - 启动期 abort。
  - custom message 与用户消息共用启动路径。
  - `/new`、`/resume`、`/fork` 替换时不自等。
  - 未知 slash、skill 路由与 close 并发。
  - 关闭前已受理后台结果能触发 follow-up。
  - 关闭后晚到通知被拒绝。
  - 运行中的 faux provider 在 dispose 时确实收到 abort，且 shutdown 只发生一次。
