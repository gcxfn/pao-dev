### 本轮最有价值的发现：`版本: 3` 会把用户误导去走 v2 入口（可复现缺陷描述）

**缺陷位置**：`src/pao/workflow/driver.ts:164`（改前）。

**改前代码**：

```ts
export function parseManifest(content: string): WorkflowManifest {
	const { frontmatter } = parseFrontmatter<Record<string, unknown>>(content);
	if (frontmatter.版本 !== undefined) throw new Error("带版本控制的实例须经 v2 控制入口读取，不得降为旧映射");
```

**缺陷机制**：这一行把**所有**带版本号的实例一律报成"须经 v2 入口"。但盘上实例可能有两种情况：

1. `版本: 2` —— 真的是控制正本，确实该走 v2 入口，原报错正确；
2. `版本: 3`（或任何未知新版）—— 这个内核根本不认识该格式，**走 v2 入口同样会失败**，正确处置是"停止、保留原件、升级内核"。

改前两种都报同一句话，用户看到"须经 v2 控制入口读取"会去调 `pao_query_flow`，然后撞上 `readControl:89` 的第二句话"旧实例或未知版本只可历史展示"——两句话互相矛盾，用户既不知道**是哪个文件**出的问题，也不知道**到底该做什么**。

**为什么这是缺陷而不是风格问题**：§8.3 要求未知新版"保留原件并阻止不可靠写"。原报错既不点名文件（无法定位原件），也不指明"这是未知新版、不要试图用现有入口读"，只给了唯一一条走不通的出路。用户按字面执行的直接后果是反复重试 v2 入口。

**改后**（`src/pao/workflow/driver.ts:162-180`）：

```ts
export function parseManifest(content: string, filePath?: string): WorkflowManifest {
	const { frontmatter } = parseFrontmatter<Record<string, unknown>>(content);
	// 格式版本与编辑版本分开：这里的「版本」是格式版本（1=旧清单 / 2=控制正本），不是编辑修订号。
	// 未知格式版本（如 3）一律拒绝降级读取：补默认值当 v1 会把新版现场误画成旧清单，属假成功。
	if (frontmatter.版本 !== undefined) {
		const where = filePath ? `（文件：${filePath}）` : "";
		if (frontmatter.版本 === 2) {
			throw new Error(
				`带版本控制的实例须经 v2 控制入口读取，不得降为旧映射${where}；` +
					"实例状态未变、原件保留，请用 v2 入口（pao_query_flow / 控制正本）读取，不要手工改版本号",
			);
		}
		throw new Error(
			`实例格式版本「${String(frontmatter.版本)}」不认识，只认 1（旧清单）与 2（控制正本）${where}；` +
				"原件保留不动，按新版处理须升级内核；不得当旧清单续跑，也不得手工改版本号掩盖",
		);
	}
```

**改后文案对比**：

| 场景 | 改前 | 改后 |
|---|---|---|
| `版本: 2` | `带版本控制的实例须经 v2 控制入口读取，不得降为旧映射` | 原句 + `（文件：<路径>）；实例状态未变、原件保留，请用 v2 入口（pao_query_flow / 控制正本）读取，不要手工改版本号` |
| `版本: 3` | 同上（误导） | `实例格式版本「3」不认识，只认 1（旧清单）与 2（控制正本）（文件：<路径>）；原件保留不动，按新版处理须升级内核；不得当旧清单续跑，也不得手工改版本号掩盖` |

**向后兼容证据**：既有断言用的是 `toThrow(<子串>)` / `toContain`，改后主句原样保留在前缀，104 例既有 spec 全过。

| 损坏对象：保留原件 + 不拖累正常对象 | ④ 同目录一好一坏 → 好的进挂起清单，坏的只进异常行并带原件路径 | 断言好流在、坏流不在挂起、异常行 `路径 === badPath`、原因含 `格式版本「9」不认识`、原件逐字节不变 |
| | ⑤ 缺「状态」字段 → 报错点名字段+声明不得自动续跑，原件保留 | 断言含 `实例清单损坏`、`「状态」`、`保留原件`；字节不变 |
| 桌面读面同口径 | ⑥ `readDesktopFlows` 一好一坏 → 好实例照常返回，坏实例只记问题带路径 | 断言 `工作流.length === 1`、`问题` 里有该路径、两面原件字节不变 |
| 格式版本与编辑版本不混用 | ⑦ 配方格式版本写 3 → 直接拒 | 断言 `配方版本仅支持 1 或 2` |
| | ⑧ 格式版本（1/2）与计划定义版本各自编号 | 断言控制正本有 `版本: 2`、无 `定义版本:` |

用例 ⑥ 一处设计说明：`readDesktopFlows` 的失败链是先 `loadFrozenRecipe` 再 `readControl`，未知版本实例在**找配方**一步就已经失败（报「冻结配方丢失或归属失配」），走不到版本判断。因此该用例断言"有可诊断原因、不是 `[object Object]`、路径指回坏实例本身"，而**不锁死具体文案**——锁死具体文案会把未来更早加入的守卫变成假红。这是断言口径的选择，不是放宽：保留原件与好对象照常展示这两条硬线在该用例中仍按字节断言。
