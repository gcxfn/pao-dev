### 2.2 关键设计：为什么「一个事实一个家」

- **预算/部门/档位/技能**：内核 `TemporaryPlanStep`（`PAO/packages/coding-agent/src/pao/workflow/plan.ts:61-84`）本来就持有这些字段，而内核 `desktop/plans.ts` 的 `DesktopPlanStep` 没投影。字段补在**桌面契约**而不是 `pi-sdk-driver` 契约，符合该包 `AGENTS.md`「不要把桌面展示关切拉进 driver 契约」。**没有改内核**。
- **预算不填 0**：`normalizeBudget` 对 `turns`/`toolCalls`/`cost`/`collabQuota` 逐个判 `Number.isFinite`，未配置即 `undefined`；整对象非对象时返回 `undefined`（＝「未配置」），不造 `{}` 假装已配置。符合 §7.4 第①类「未配/未知不填 0」与 §8.3「不能补默认值假成功」。
- **等待原因给机器可读来源，不给抠中文**：内核 `controlView` 的 `挂起` 是一句散文（`等待前置节点` 里不含步骤号），桌面拿不到依赖来源。新增 `wait: { kind, blockedBy }`，`kind` 取自稳定枚举（`deps|minister|audit|confirm|budget|paused|failed|read-error|none|unknown`），`blockedBy` 由 `dependsOn` 与各步完成度实算，界面才能写出「等待第 2、3 步」。原文案仍保留在 `hold` 供排查。
- **坏卡/缺映射单独报**：`readProblems: [{ stepId?, code, message }]` 与计划级 `readProblems` 并存，正常节点继续可读（§7.1「坏卡/缺映射单独报，正常节点继续可读」）。**旧内核合法**：新增键（`全部卡`、`读取问题列表` 等）缺失不报错——这正是回归中踩到的坑：`全部卡` 最初用硬要求列表解析，直接让两个旧 spec 报 `步骤全部卡引用列表字段缺失。`，改为可缺省后转绿。教训：**给投影加字段时，缺字段必须默认可选，否则等于让旧数据非法**。

### 2.3 成果正文读取的四道闸

renderer 只报「哪个成果」（四元身份 + 相对路径 + 轮次 + 版本依据），正文由宿主读。逐闸：

1. **身份闸**：`startRequestId + stepId + artifactPath + round` 必须命中内核已投影的产物行，且 `versionBasis` 逐字一致。不命中 → `not-found-in-plan`；轮次/依据对不上 → `version-mismatch`。**这是 §6.4 第 3 条「不能贴旧标签读新文件」的落点。**
2. **范围闸**：拒绝绝对路径、`..` 段、空段；对「项目根」与「候选路径」**双侧 realpath** 后再判越界（历史教训：单侧 realpath 的 symlink 能骗过检查）；命中符号链接直接 `symlink` 拒绝，不跟随。
3. **目标闸**：必须是常规文件（非常规 → `unsupported`），读权限失败 → `permission-denied`。
4. **体积闸**：`ARTIFACT_CONTENT_LIMIT_BYTES = 256 KiB`，超限**读前 256 KiB 并置 `truncated: true`**（明确标注截断，不是静默截断也不是全拒）；扩展名不在文本白名单 → `unsupported`。

返回体在成功时带 `relativePath`/`versionBasis`/`round`/`card`/`content`/`byteLength`/`truncated`/`modifiedAt`，失败时带稳定 `code` + 中文 `message`。

## 六、遗留项与风险

### 6.1 已知待决（不属本批）：`canvas-query.ts` 空状态兜成 `no_card`

lead 裁定 **本批不动**，条文如下，供立项时直接引用。

- **现状**：`desktop/apps/desktop/electron/platform/pao/canvas-query.ts:325`
  ```ts
  status: asText(record["状态"]).trim() || "no_card", // S10 投影单域英文；空值兜底同域
  ```
  节点状态读到空值／非字符串时，兜底成 `no_card`。
- **与 §8.3 的张力点在哪**：§8.3 要求「正常对象继续展示，**不能补默认值假成功**」。这里确实是在补默认值。
  但 §8.3 真正要防的是把**读不出来**译成**成功/已完成**；而 `no_card` 在内核状态值域里是**合法状态**（该节点本轮没有卡），
  不是「成功」也不是「已完成」——所以它**不构成假成功**，而是「把未知译成了一个合法但可能不等于事实的状态」。
  这正是它危险的地方：**用户看到 `no_card` 会以为「真的没卡」，而不是「这里读坏了」**。
- **为什么不能顺手改**：`no_card` 被画布与看板两条既有判据消费（节点是否已派卡、能否推进、画布节点的空态与可操作性都由它区分）。
  改成显式失败会让所有「读不到状态」的实例从「可展示」变成「不可展示」，波及面远超投影层。
- **立项时该怎么改（建议）**：不要简单改成抛错，而是引入一个**区别于 `no_card` 的显式未知态**（如 `unknown` / `读取异常`，内核已有 `读取异常` 先例），
  让画布与看板各自决定怎么展示「未知」，并对两条判据各补一组「空状态」用例。属**契约级改动**，须单独立项、单独验证，不能混在投影批次里做。

### 6.2 其它遗留

- **成果正文读取只覆盖临时计划路径**：画布/看板的成果读取仍走既有 `readWorkspaceFile`。是否收敛到同一闸（复用 `readArtifactContent` 的判定）属下一批。

## 附：本轮环境陷阱（四条，都已实测踩到）

**正本已写入 `.pao/harness完善-20261017/运行须知-本机core-lane.md`**（lead 授权，2026-10-17），此处只留索引：

1. **`ELECTRON_RUN_AS_NODE=1`** → 全部 Electron core 用例在启动阶段集体失败（`electron.exe: bad option: --remote-debugging-port=0`），极易误读成「自己改坏了代码」。跑前 `Remove-Item env:ELECTRON_RUN_AS_NODE`，且必须与 playwright 同进程。
2. **PowerShell 管道回写源码写坏 UTF-8** → `Get-Content -Raw | Set-Content` 把中文注释写成 `U+FFFD`，build 随后解析失败。源码一律用 `edit`/`write`。
3. **build 失败时旧 `out/` 让 Playwright 对旧产物「假通过」** → build 必须在 playwright 之前且确认成功。
4. **改了 view/资源不 rebuild 就重跑，跑的是旧 renderer bundle** → 与第 3 条同根因的两副面孔；D1 本轮因此把「composer 为空」误判成实现缺陷。

## 附二：改了主进程公共行为，必须扫一遍所有既有调用方

本轮最实在的一条教训，自记于下：我为「重载前先让渲染层交出草稿」在 `main.ts` 加了 `did-start-navigation` 拦截，
**自己的新用例全绿**，但 D4 用的公共辅助 `tests/helpers/electron-app.ts:2318 reloadDesktopRenderer()` 裸调 `window.reload()`，
第一发必然以 `ERR_ABORTED` 结束（拦截生效的正常表现），于是 D4 的用例红了。
结论：**改了公共行为就必须扫一遍所有既有调用方**，这比单条断言通过更重要；反向验证只证明「断言能抓住目标缺陷」，
不证明「没有打断别的东西」。修法是让拦下重载的 `reloadDesktopRenderer()`（位于公共入口 `tests/helpers/electron-app.ts:2318`）遇到 `ERR_ABORTED` 重试一发并注明原因，而不是去改 D4 的 spec。
