## 四、攻击面 4：阶段组合攻击（killTree 长预算 × 桌面接管/关窗）

### 4.1 树杀进行中，桌面点「显式接管」——**不成立，fail-closed 三层兜住**

- 层 1：树杀进行中该会话的运行时锁仍被持有（runtime/index.ts:97 的 release 在 session_shutdown 内、位于 stopAll **之后**；killTree 是 async execFile，宿主事件循环活着，proper-lockfile update 2s 心跳持续），他端接管走 `lockfile.check(stale 10s)` → 「同会话已有控制方」活锁拒绝（session-lock.ts:45-46）。
- 层 2：手敲 `/pao runtime takeover <token>` 打自己活锁同样在 acquire 内被活锁检查拒绝（实测四段之②，本轮复核代码路径一致）。
- 层 3：即使构造出「宿主事件循环饥饿 >10s 心跳断→锁判 stale→他端凭 token 接管成功」的病态窗口（需要 >10s 同步阻塞，killTree 链路无此形态），接管方的新派发也会被**项目写锁**拦住——旧宿主「先停后放锁」，confirmStopped 前项目锁不放（worker/lock.ts:83-93），双写不可能；旧宿主醒后 assertOwned 察觉 token 轮换、后续请求被拒（session-lock.ts:80-83），其 release 检查 token 不匹配、不会误删新持有者的锁（:65-77）。
- **判定：无互斥假设被组合违反。接管 UI 只出现在残留锁错误行（持有者已死），与活宿主树杀在锁语义上不相交。**

### 4.2 树杀进行中，用户关窗——**按设计收敛，残留项目锁为唯一后果（P4-A）**

- 静态构造：main.ts:1414-1434 before-quit 中 `disposeSessions()`（→ session_shutdown → stopAll → killTree）与 5 秒 `QUIT_FLUSH_TIMEOUT_MS`（main.ts:318）竞速；超时后 `app.quit()` 第三次进入 before-quit，`quitFlush==="done"` 不再 preventDefault，进程退出、未完的 stopAll 弃置。
- 后果分解：① 树本身——worker 带 `PAO_MANAGED_PARENT`，宿主进程死→IPC disconnect→自树杀（退出矩阵情形 c 实测 693ms 全灭），**不会留活树**；② 项目写锁——finally 放锁没跑成→锁目录残留→无自动清（R05「由人决定」）→后续派发「锁被占用」，preflight 判「可排队…须人工处理」（preflight/index.ts:172-179），恢复手段＝人工删锁或 24h stale。

- **判定：非缺陷；登记 P4-A 提示 S5「租约与权限」阶段须给项目写锁残留一个与运行时锁 takeover 对等的显式恢复决策（现状只有人工删/24h），否则 S5 验收「租约」会在此撞墙。**
