## 一、对抗路径结果

### 1. 吞噬面攻击（dead-pipe.ts）——发现 P2-1、P3-1

- 错误码口径与内核逐字一致：desktop `DEAD_PIPE_ERROR_CODES={EIO,EPIPE,ENOTCONN}`（dead-pipe.ts:9）＝内核 interactive-mode.ts:290 `DEAD_TERMINAL_ERROR_CODES`，且 desktop 单测第 1 测钉住该一致性。
- 流级腿正确只在拥有管道的边界吸收：`process.stdout/stderr` 各挂一个 error 处理器，非断管 rethrow 成 uncaughtException（单测覆盖同步＋微任务＋rethrow＋dispose 六面）。
- **P2-1（设计面）**：`uncaughtException` 腿是**全局吸收**，不分错误来源。`isDeadPipeError` 为真的错误无论来自 stdout/stderr、子进程 stdio、IPC socket 还是 fs 流，只要没挂自己的 error 处理器，都会在顶层被吞（仅尽力 console.error 一行）。内核的对应做法是流级吸收＋uncaughtException 一律 crash（interactive-mode.ts:4341-4360），desktop 的全局腿实际**超出**内核口径；模块注释「只在拥有该管道的边界吸收」对流级腿成立、对本腿不成立。影响：非控制台管道的同类错误（如子进程管道 ENOTCONN）失去崩溃信号且无持久化日志。缓解：W-bug7 实录路径（Electron 内部 console 转发）确实只能在此层吸收；正常控制台存活的场景下吸收处有 console 行可查。建议：吸收处增带来源信息的持久化记录（或按 error.stack 收紧到 stdout/stderr 写路径），并把「全局腿是有意放宽」写进 `.agents/notes` 决策。
- **P3-1**：ECONNRESET 不在口径（与内核一致，属有意对齐）。若未来以 socket 形态接入控制台/管道（部分 pty 场景断连表现为 ECONNRESET），该类错误会走 showErrorBox 而非吸收。现状可接受，登记备查。
- 接线点覆盖：仅 main.ts 一处、stdout/stderr 两条流，无误吸收别的子进程管道的流级接线；desktop 其余子进程错误处理（checkpoint-store.ts:1100 等）为本包改动前既有。

### 2. 锁文件竞态攻击（session-lock-owner.ts）——未破

- TOCTOU：读到 owner 与 UI 渲染之间锁被换/释放，只影响展示的 pid/宿主面/时间（陈旧信息）；接管动作由内核在文件锁下重新校验 token，陈旧 token 被拒（真实复验第四段），无越权面。
- 损坏/半写：JSON.parse 失败或字段不完整（isOwnerRecord 不满足）一律按「未找到」→ 原始报错原样呈现，不崩、不误接管；内核侧 owner json 为 writeFileAtomic 原子写，半写概率本就极低。单测第 6/7 测覆盖。
- 时区/时钟：formatAcquiredAt 用本地时区渲染 ISO，「持有自」语义不含时长计算，无漂移敏感逻辑。异常 ISO 原样回显（React 文本转义，无注入）。
- 扫描方式：按 token 全目录扫描（报错文本不含 sessionId，无法直接算 sha256 文件名），首个 token 匹配即返回；token 为内核 randomUUID，碰撞不现实。

### 3. 接管链路攻击——未破，P3-3

- 双击/连点：每次 click 弹一次模态 confirm，确认两次则提交两条接管命令；第一条成功换发 token，第二条带旧 token 被内核拒绝，产生一条新的富化报错行（含新 token 和新按钮）。无锁损坏、无死锁、无锁出；属视觉噪音（P3-3，可在提交后禁用按钮消除）。
- takeover 期间原 owner 释放：内核 acquire 看不到 previous → 全新获取成功，语义合理（锁语义未改，禁改红线未触碰）。
- 错误 token 被拒：**本轮独立真实复验通过**（见第三节），锁文件 token 未变。
- Esc/关窗打断 confirm：返回 false → 不提交任何命令；内核接管为文件锁内原子操作，不存在半接管态。代码层确认无残留路径。
- 复核实施证据：归档脚本五段与日志一致；第四段错误 token 拒绝、第五段一键接管成功的程序化断言（锁文件 token 轮换）成立。注意：归档图「4-一键接管成功.png」观感与拒绝态无异（成功仅靠锁文件断言，「本会话控制权有效」info 提示可见性未断言，实施记录已如实登记为未验证项 2）——归 P3-4。

### 4. renderer 边界攻击——未破

- 富化单点：`handleSessionEvent` 入口对 hostUiRequest 富化一次（app-store.ts:3603-3607），经 applyHostUiRequest→addExtensionNotice 进时间线/应用内通知；事件重放由 `message.includes("原控制方：")` 幂等护栏兜底（单测第 4 测）。两个事件入口（直调 869 行、排队 3147 行）都过同一富化。
