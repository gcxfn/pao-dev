## A1（P2）重试假成功：孤儿不可达时二跳空选报成功

**路径与条件**：第一次 stopWindowsTree 部分成功且**深层成员 taskkill 瞬时失败**（`& taskkill … | Out-Null` 对原生命令失败不 throw，`$ErrorActionPreference='Stop'` 管不到 native 命令退出码）→ 杀循环继续向根推进、根被杀 → 存活检查 throw「Tree member still alive」→ 重试：`Win32_Process` 只枚举**活**进程，BFS 从根 pid 沿 ppid 走，**中游已死则深层孤儿不可达** → `$selected` 为空/不含孤儿 → 收尾存活检查只查 `$selected` → PS exit 0 → killTree 返回成功「taskkill /PID … /T /F」，孤儿泄漏且假报树已灭。

**证据**（全部实测，见探针输出）：
1. `killTree(不存在的 pid)` win32 分支**返回成功**（无 alive 预检，POSIX 分支才有）——「空选即成功」语义实证；
2. 本机现场普查：**27 个活进程 ppid 已死**（explorer/wps/clash-verge 等）——「中游死、深层活」是现实常见形态，非构造幻影；
3. kill.ts 自身注释承认「MSYS shell descendants may outlive their root」——后代活得比父久是本工具明确要处理的目标场景。

**公平性说明**：PS 被 60s 超时杀死的形态（实施记录 §三.2 的主推理）确实收敛——杀序最深层优先，残余必在近根侧，二跳可达可续杀；该形态**无假绿**。假绿需要的是「深层 taskkill 失败但循环继续杀到根」或「PID 复用 throw 时序」——前者恰是重试要吸收的另一个注册环境族（S1 调查 §五.2 taskkill 瞬时拒绝访问）。即：**对同一环境族，修前报错（响、能被上层兜底 SIGKILL），修后可能假报成功（静默漏树）**——与本文件自家注释「宁报错不假报树已灭」相悖。本机 node 链演练出现「父死孙随亡」传染（机制未查明，疑为环境 job 行为），使纯 node 树难以呈现该形态，但这不保护 breakaway/MSYS/dev server 树。

**影响**：泄漏进程＋假绿回执；host/runner 侧 `registry.markExited`＋摘登记照常执行，登记表失去「未确认死亡」线索。

**建议（最小改法）**：stopWindowsTree 失败路径在 throw 前 `Write-Output` 存活成员 pid，killTree 把它们作为二跳的附加根（或二跳收尾检查覆盖首跳存活名单）；约 5 行 PS＋3 行 TS。若不做，至少把「二跳成功但首跳失败」标记为「树灭未经完整确认」上报。

## A2（P2）重试放大：最坏时延与波及面

**核过的事实链**：
- verifier 条目最坏＝命令 120s（`命令超时毫秒` 缺省 120000）＋killTree 2×60s＋间隔 0 ≈ **240s/条**，条目顺序执行、无总预算（`workflow/auto.ts` 只透传单条超时）；N 条挂死验收 → N×240s。
- worker cancel/terminate：`#stopEntry` 顺序 await killTree（≤~120s）→ awaitClose 10s → StopProof → 写锁才放。锁持有顺延 ≤~130s；**无双重释放**（`entry.停止` promise 去重、失败时重置后顺序重试，无并发双杀）；`index.ts:285` 多目标顺序 terminate，时长线性叠加。
- host 散场/拉起失败路径、`app.ts`、`parent-lifecycle.ts` 均直接 await 或 fire-and-forget，无上层超时竞态。
- **仓内不存在「上层先超时、下层还在杀」竞态**：pao 侧所有调用方都 await killTree，无人先超时。唯一未验证处：pi 工具层（MCP 调用）若有外层超时，terminate 工具调用可能先超时而杀链仍在跑（仓内不可见，未测）。
- **波及面超出本包授权**：`src/core/tools/bash.ts:137` 同用 killTree（中止路径 `Promise.race(waitForChildProcess, stopFailed)`）——abort 一条 bash 命令最坏从 ~15-30s 变成 **~120s 才返回**。bash.ts 是 src/core 共享面，实施记录只作为「范围外观察」登记了它的判定顺序问题，未提及时延放大。

**建议**：二跳预算减半（如 30s×2）或总和封顶；或至少在实施记录/后续包里显式登记 bash.ts 的时延放大，交 S1-2 余量裁决。

## A3（P3）取消时 stopError 无处可查

对调后 `signal?.aborted → reject(signal.reason)` 先行，stopError 是闭包私有变量：**不落日志、不挂 cause、无处可查**。兜底 `child.kill("SIGKILL")` 只杀直接子，孙进程泄漏时排障者无从知道「树杀曾失败、失败原因是什么」。tracked 子进程本身被 SIGKILL，不属「未知状态」，故不升 P2。建议：`console.debug` 一行或 reject 前挂 `cause`（保持 `name:"AbortError"` 的包装 Error 需谨慎，测试钉了 name）。

## A4（P3）降级「说明」截断截掉了真正的原因

降级说明取 `String(error.message).slice(0, 160)`。实测 execFile 错误报文结构：`Command failed: <powershell 全路径> -NoProfile -NonInteractive -Command <整段脚本回显>…<真实原因（如 'Tree member still alive: N'）在 1000+ 字符之后>`。160 字符只覆盖 powershell 路径＋脚本头两行——**降级说明对最常见失败（PS 超时/存活检查 throw）排障价值≈0**。建议取 stderr 尾部或匹配 `^` 抛错行。
