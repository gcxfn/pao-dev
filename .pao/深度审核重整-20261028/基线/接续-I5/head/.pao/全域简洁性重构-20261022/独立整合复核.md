# 全域简洁性重构独立整合复核

复核日期：2026-10-22

## 结论

本轮定向复核未发现尚未解决的高、中严重新增正确性、复杂度、安全或资源问题。

桌面公开类型的迁移问题已经识别，主控也已否决本轮 API 迁移。按要求回退后，当前源码已核对：`PaoCardOpsCard` 恢复为 `path/card_no/frontmatter` 的最小形状，`PaoCardStatusChangeInput.to` 恢复为 `string`；其他桌面桥同样保留原有公开最小投影，只在统一加载边界做必要断言。因此它属于已修正项，不构成剩余问题。

## 已解决复核项

### 桌面公开契约曾收窄，最终已回退

精确 patch 的中间版本中可以看到，卡操作公开类型曾改成内核原生 `ParsedCard` 和 `StatusChangeInput` 的别名。这会使使用轻量卡对象的现有调用者或测试替身承担额外的完整原生结构要求；其中 `to` 也改变了原有的字符串契约。该问题属于真实存在的编译期契约收窄，已由主控识别并否决。

当前源码已经恢复：

- `desktop/packages/pi-sdk-driver/src/pao-card-ops.ts` 中，`PaoCardOpsCard` 仅要求 `path`、`card_no` 和带 `status` 的 `frontmatter`；`PaoCardStatusChangeInput.to` 为 `string`。
- `PaoCardOpsModule` 恢复原来的最小函数签名，状态值是否存在、是否允许迁移继续由内核状态机运行时校验。
- 统一加载入口调用公开子路径 `@earendil-works/pi-coding-agent/pao`，原子加载 `readCard` 与 `changeCardStatus`，缺失时明确报错。
- 只有 `module as unknown as PaoCardOpsModule` 这一处加载边界转换。断言不暴露给调用者，也不再改变公开类型。

真实生产调用者 `desktop/apps/desktop/electron/platform/pao/kanban-ops.ts` 读取完整原生卡后，以 `{ 操作者: "用户", to: "canceled", ... }` 调用内核；测试替身则使用最小卡，两者都能满足当前公开契约。`public-contract.compat.mts` 提供最小公开形状的编译探针。最终桌面类型检查与探针运行结果以桌面实施报告为准；主控此前的内核生产类型检查不能替代桌面类型检查，本复核也未自行运行编译。

复核了同批其他桌面桥：

- `pao-canvas.ts`、`pao-flow-control.ts`、`pao-workflow.ts` 的公开返回结构和函数签名仍是原最小投影，真实内核函数只在加载点转换。
- `pao-dept.ts`、`pao-plans.ts` 同样保留原公开投影，加载点做一次转换。

没有找到生产调用者需要本轮扩大 API 的真实支持用法，因此以当前源码判断，已符合“恢复原有公开最小类型/函数签名，仅保留加载入口收口和必要边界断言”的要求。此项已经识别，主控已要求修正，最终源码核对通过。

## 逐区核对

### panel 快照值、坏字段与错误文案

未发现问题。

- 保温配置通过 `inspectConfig` 一次 `readJsonRaw` 同时取得校验状态和解析后的对象，原先“先校验、再为值快照重读”的中间态已消失，也没有增加模块级结果缓存。
- `required` 和字段校验器仍是原入口规则。文件缺失、读取期间出现 `ENOENT`、顶层不是 JSON 对象、目标字段类型错误，分别落到 `missing` 或 `invalid`；权限或路径不可读落到 `unreadable`。
- `toast` 仍按“未显式 `false` 即开”取值；并发上限按有限正数取整；字段坏时界面显示“异常”，不会拿缺省值冒充有效配置。
- 记忆配置只通过原有 `loadMemoryVendorConfig(path)` 读取一次。返回值同时用于快照和校验结果；缺文件由该 loader 返回空值，解析或字段问题由原异常转成状态。
- 错误原因经过 `safeConfigReason` 归一，展示固定类别；错误信息中可能出现的 JSON 原文片段、供应商“参数”等配置内容不会进入面板提示。

调用链与测试覆盖了缺文件、坏 JSON、坏字段、写回失败以及保留原配置键等路径。这里只引用测试存在与真实读取链，没有在本次复核中重跑测试。

### status 共享扫描深度、错误与 v1/v2

未发现问题。

- `scanWorkflowInstanceFiles` 统一发现挂起、待处理信号和结果页使用的实例文件。每个项目的 `.pao` 顶层再加深度 4 的子目录都会参与扫描，覆盖临时计划里较深目录的现行布局。
- `.pao` 不存在时按真实空态跳过；根目录不可读、候选目录不可读，以及单个实例读取或解析失败，都会生成带路径和原因的异常行。
- `collectInstanceDirectories` 不吞掉父层目录：子目录枚举失败时返回空，但父层此前已经把该子目录加入候选；后续扫描会尝试读取它，并在非 `ENOENT` 时上报异常。当前调用链未确认存在“不可达被当成空”的漏报。
- `readWorkflowInstance` 是 v1/v2 分流的唯一入口。v2 从实例的 `卡目录` 与冻结配方读取控制正本并计算状态；v1 继续使用原 `parseManifest` 的严格必要字段校验。
- 结果页不再自行按浅字段猜版本：v2 使用共享控制数据，v1 明确说明四样（要求、实际 diff、验收、遗留）不可结构化读取，不冒充成功。
- `/状态` 的部门区改为从 `dept/panels.ts` 直接导入，避开对 `pao/index.ts` 总入口的依赖。没有发现形成新的运行时循环加载或改变数据来源。

### desktop 公开 module、owner 共享与 card 操作

未发现问题。

- 所有迁移后的桥都通过 `pao-desktop-module.ts` 加载 `@earendil-works/pi-coding-agent/pao/desktop`；PAO 的 `package.json` 明确公开该子路径，`desktop/index.ts` 导出所需函数。
- 内置 `pao` 扩展由 `extensions/index.ts` 引用 `src/pao/index.ts`，主控角色在该目录调用 `registerDesktopOwner`。公开导出和内置扩展最终解析到同一 `dist/pao/desktop/index.js`，Node ESM 原生模块缓存复用同一模块实例和 owner 表。
- `pao-desktop-module.ts` 不再维护第二层 Promise 缓存，也没有通过拼接内部 `dist` 路径创建第二条加载通道。
- 身份测试逐项比较公开入口与桥返回的函数，确认是同一函数。相关 owner、路径安全、内核状态机责任仍由原入口承担。
- 卡操作的真实调用者只执行“用户取消”，路径会先经过工作区越界与文件名卡号校验；实际状态迁移、单写者检查和读改写仍留在内核，没有在桌面桥复制规则。

### 模型合并顺序

未发现问题。

`mergeEnabledModelPatterns` 现在只在 `desktop/packages/session-driver/src/runtime-types.ts` 维护，并由包入口导出。`runtime-supervisor.ts` 与 `app-store.ts` 都调用这一个实现。函数先复制已有模式，再按提供方顺序追加未见项，同时去重既有项和追加项，保留了此前的顺序与追加语义。

### workbench 局部滚动

未发现问题。

共享函数 `scrollIntoContainer(element, containerSelector)` 只操作最近的指定滚动容器，元素已完整可见时直接返回。文件编辑器以 `.file-editor__body` 为容器，文件树以 `.file-workbench__tree` 为容器，样式中两者均为 `overflow: auto`。现有 Electron 测试构造了长文件第 350 行和嵌套文件第 79 行，验证目标只在自己的容器内滚动。
