# 独立审查：并发与整合测试有效性

## 结论

截至 2026-10-21 01:15（Asia/Shanghai），本审查快照中的四个测试文件没有发现以下制造绿灯的方式：

- 把原并发场景改成两次串行调用后仍宣称同一场景通过；
- 删除关键拒绝条件而只留下弱计数；
- 放宽到无需证明真实取消或版本变化；
- 用协议不符的模拟对象替换产品正式入口。

主代理此前抓到的“同父预算两张卡被改成两次串行调用”已在当前源码恢复。当前 `worker-dispatch-guards.test.ts:415-443` 是一次 `executeFanout`，同时提交卡号 `["2","3"]`，并发上限为 `2`；第一张落回执，第二张因“预算耗尽”未拉起。该点已恢复，不再是本次新问题。

四个文件的静态有效性与当前执行证据分开看：

- `card-process-stop.test.ts` 的全部树杀协议仍通过 mock 触发；“真实”部分只是被停止的 Node 子进程真实存在。
- `worker-dispatch-guards.test.ts` 有真实本地 Node worker 子进程用例，但预算争用与“启动边界后停止未知”本身使用 `MockRunner`。后者只证明调度状态机保留锁和名额，不能当作真实 worker 启动后树杀失败的端到端证据。
- `delivery-commit.test.ts` 的取消用例有真实 Git hook、父进程和孙进程，并在 Windows 上实际执行；受控交付用例有真实 Git worktree、commit、tree 和 ref。

因此，本报告是当前作者修改过程中的阶段审查，不是最终封板结论。

## 逐项审查

### 1. 同父预算并发与串行边界

**原触发：** 两张同父卡进入一次扇出，父预算只够一轮；第二张必须在第一张真实回执落卡后拒绝。

**当前触发：**

- `worker-dispatch-guards.test.ts:415-443` 一次 `executeFanout` 同时提交两张卡，不拆成两次调用。
- `worker-dispatch-guards.test.ts:425-440` 除了总数，还分别检查：
  - 第一张 `attempt=1`、回执存在、`usage.turns=1`；
  - 第二张终态为“未拉起”、原因包含“预算耗尽”、没有 attempt；
  - 两张卡按卡号查找结果，不再依赖结果数组顺序。

**生产对应：**

- `dispatch-core.ts:1057-1070` 同一预算池进入共享队列。
- `dispatch-core.ts:1323-1354` 队列覆盖“重读余额→认领→启动→回执落卡”，之后才释放。

**实际影响：** 这证明工程上的并发启动和预算串行边界，不是性能基准。没有把 `runner.runs` 数量单独当作全部成功证据。

### 2. 回执落卡失败后的拒派

**原触发：** 第一个 worker 返回的产物随后消失，回执无法落卡；同父卡第二张不得把缺账当作零消耗继续执行。

**当前触发：**

- `worker-dispatch-guards.test.ts:492-549` 对单卡入口和扇出入口都执行该场景。
- `MockRunner` 只制造 worker 回执；“返回后、落卡前产物消失”是明确标注的替身条件，产品工具接线、产物校验、回执写卡和错误分类都没有被替换。
- `worker-dispatch-guards.test.ts:537-544` 按卡号检查第一张“失败 / 未落卡 / `unknown_outcome`”，第二张“未拉起”，原因必须包含“已用量未知”或“持久占位”。

**修改判断：** 原来按数组位置写的两条内联断言被拆开，不是删除。当前还避免结果顺序变化导致误判。允许“已用量未知”或“持久占位”两种原因，分别对应内存中的缺账和落盘的占用记录，二者都直接表达不能安全派发；没有省略拒绝原因。

同一轮末次修改给文件里已存在的两个真实本地子进程用例补了显式 30 秒超时，见 `worker-dispatch-guards.test.ts:628、662`，防止本机启动和清理较慢时用默认超时误判。预算并发和停止状态机的相关断言未改变。

### 3. 取消后先停后放

#### 3.1 调度状态机

`worker-dispatch-guards.test.ts` 的两个新场景分别覆盖失败前后：

- `740-764`：执行锁取得后、runner 启动前复核失败时，执行锁和共享名额都释放。
- `766-788`：runner 进入启动边界后取回执失败，且停止不能确认时，执行锁和共享名额都保留。

生产在 `dispatch-core.ts:1366-1412` 先判断停止证明，再决定释放；只有 `stopProven` 会放名额。`dispatch-core.ts:1413-1425` 对受管工作树也保留执行根守卫。这与测试的 `isExecutionLocked(root)===true` 和 `runner.slots===1` 对应。

这里的 `StartThenUnknownRunner` 覆盖了 `run()` 和 `confirmStopped()`，`run()` 直接抛错，没有拉起真实 worker。因此它**证明的是调度器在“可能已启动、停止未知”状态下的保守处理**，不是实际进程树杀失败后仍占锁的端到端证明。

#### 3.2 runCardProcess 的停止错误协议

`card-process-stop.test.ts` 启动真实 Node 子进程，但 `killTree` 在文件级被 mock：

- `card-process-stop.test.ts:18-22` 明确说明了这个替身边界。
- `65-100` 同时检查取消仍归类为 `AbortError`、停止未确认仍可识别、`cause` 和原始 `abortReason` 保留。
- `91-100` 额外覆盖字符串和冻结对象作为取消原因，避免修改 `AbortSignal.reason` 或错误地假定它一定是 `Error`。
- `102-108` 保留无取消时真实超时错误不被吞掉的检查。
- `111-179` 保留 `verifyCard` 的“无法判”、长错误尾部、沙箱保留和取消传播。

生产在 `process.ts:14-24` 定义专用错误，`58-93` 先保留取消语义，再挂停止失败原因。当前 `process.ts:58-61` 在 `execFile` 因输出超过采集上限中止后，也沿同一 `killTree` 停止链确认后代退出，而不是只凭直接子进程退出就声称整棵树已停。新增断言与这个协议一致。树杀自身是否可靠仍由单独的 kill-tree 测试负责，本文件的通过不能替代它。

#### 3.3 真实 Git hook 取消

`delivery-commit.test.ts:322-383` 仅 Windows 执行，使用：

- 真实 Git 仓库和真实 `pre-commit` hook；
- hook 父进程与孙 Node 进程；
- 正式 `pao_deliver_card` 工具入口；
- 真实提交数、产物文件及无关进程检查。

原实现先创建 `expect(operation).rejects...`，再取消。当前 `341-356` 先附加 `operation.then(...)` 的拒绝处理器，保存 `outcome`，随后 abort，最后仍断言 `AbortError`。这是为消费 rejection、避免后续 finally 或清理时出现未处理拒绝竞态，没有移走 AbortError 断言。

`357-360` 还新增检查：hook 的两个 PID 都已退出，无关 Node 进程仍活着，commit 数不变，产物仍在。当前 `cancel-delivery.log` 于 01:08:08 记录该用例 1 个通过、19 个跳过，持续 14.02 秒；对应 `timing-delivery-cancel.json` 记录 hook 就绪约 3.28 秒、停止约 13.83 秒、收尾约 13.94 秒。这是较早一次当前测试文件的单用例证据，不等于作者最终复跑。
