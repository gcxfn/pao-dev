## 已确认并复核通过

### 1. 无关目录的提交不会使地图失效

`sameDispatchMapCoverage()` 已不再比较仓库的 HEAD 或 treeId。它比较声明的覆盖路径、覆盖依据，以及每份已纳入文件在 HEAD、索引、工作区和当前内容上的摘要。仓库的头和树只留作采集证据，不参与地图有效期判断。因此，覆盖范围外的提交可以复用现有地图。

这不是只读注释得出的结论：`dispatch-brief-artifacts.test.ts` 有“覆盖外 commit 不作废地图”的测试。最新模块测试轮次中的失败都发生在非 Git 身份用例，没有推翻这一比较逻辑。

### 2. linked worktree 的共同 Git 目录边界已修

旧要求“执行根必须位于 projectRoot 目录下”已被替换。预检、正文装配和快照复核现在都能消费宿主 `WorktreeBinding.kind` 和 `commonGitDir`；managed 工作树必须有 Git 身份，普通 primary 在无地图时允许没有 Git 身份。实际检查共同 Git 目录的同一性，不再依赖目录嵌套。

源码位置：

- `dispatch-brief/workspace.ts:268`：只比较声明覆盖范围内的内容。
- `dispatch-brief/precheck.ts:132`：无 Git 身份仅在 managed 时拒绝。
- `dispatch-brief/brief.ts:330`：执行身份检查区分 managed 与可无地图的 primary。

### 3. 持久摘要中的伪造仓库路径不能绕过实时 Git 核验

`cards/execution-context.ts` 的实时核验会读取执行根的真实 Git 顶层、共同 Git 目录及分支，再与持久绑定比较。`execution-context.test.ts` 有真实 Git 用例：篡改持久记录中的 `repositoryRoot` 并重新计算自洽摘要后，实时解析仍拒绝。

这证明宿主 Git 事实不是一张只靠摘要自洽即可信任的文本凭证。该项已通过。

## 已确认的真实问题

### P1：语法正确但不存在的受控引用可以被写进卡

`appendCardInputReference()` 只调用 `parseDispatchUri()` 做 URI 规范化，随后直接检查 owner、attempt、status 并写入 `inputs`。它不加载目标简报、地图或契约产物。因而，一个格式正确、摘要格式也正确，但产物不存在的 URI 会被保存成卡输入；真正加载失败要等到后续 prepare。

这是真实可达的写入行为，不是假设。现有测试“非法 URI 不写卡”位于 `dispatch-brief-artifacts.test.ts` 附近，目前未覆盖“语法合法但指向不存在产物”的情况。建议在写卡原语中按 scheme 调用现有产物加载器核验身份和摘要，拒绝不存在的目标；不需要另造兼容层。若作者认为写卡只应校验语法，则至少要保证保存工具返回的引用来自刚保存的真实产物，并且普通 `append` 入口不会被当作受控事实的背书。

这个问题与派发最终入口的接线进度无关；它是已经存在的 API 边界漏洞。

### P2：4.1.3 的生产链目前未达到“侦察结果自动被下游消费”

已核实存在的消费能力：

- `prepareDispatchBrief()` 会解析卡已有 `inputs` 与 `upstreamRefs` 中的 `pao-brief://`，加载已保存正文。
- 冻结快照的 `briefMarkdown` 会被 `buildWorkerPrompt()` 直接放进本次提示词。
- `dispatch-core` 已实现依赖卡的 execution-context 路由：对 `depends_on` 找到上游当前 attempt 的 `briefRef`，不复制正文、不做模型语义改写。

但生产侧仍未闭环：

- `saveDispatchReconResult()` 的注释明确写着“是否允许在角色装载面注册由主控接线决定”，当前源码中没有找到它在真实 worker 装载面注册或暴露窄工具的调用点。worker 角色仍整块跳过 `cards`，`pao_dispatch_brief` 也没有在 `pao/index.ts` 中被注册。
- 当前唯一的自动路由实现从依赖卡的 execution-context 取 `briefRef`。侦察 worker 的最终结果摘要本身不会自动变成这个 `briefRef`；需要先由可达的保存原语写出受控简报，再把精确引用挂到真实依赖／交接链上。
- 当前集成测试刚新增一条“侦察结果自动进入下游”的测试，但它引用未定义的 `setupReconFixture()`，定向运行得到 `ReferenceError`。这条测试尚未证明真实链路。

因此，当前能证明的是“如果卡上已经有正确的 `pao-brief` URI，准备和提示注入模块能消费它”；尚未证明“侦察 worker 能从自己的真实运行入口保存摘要，程序会沿依赖把精确引用自动送进下游简报，全程无需主控读全文转述”。这不是要求自动语义总结；侦察已保存的受控摘要只需被可靠路由。

建议作者把链路收成一条真实入口：侦察 worker 获得最小写摘要能力（或由现有 worker 回执机制生成同一受控产物）→ 保存结果返回精确 URI → 卡依赖／工作流自动建立引用 → 下游 prepare/freeze/prompt 直接包含该摘要正文。测试必须走这条入口，不能只在测试里直接构造新 schema。

### P3：规划与审核角色尚未证明得到不同必要结论

`brief.ts` 现在按 `purpose` 为上游结论的小标题选择“规划所需结论／审核所需结论／实现所需结论”，但没有看到规划、审核、实施各自需要的额外字段、装配或路由规则。实现模板仍需携带目标、范围、验收、证据和已知事实；审核还应有实际变更摘要、风险、未知和证据入口，规划还应有调查结论、接口选择、依赖和任务切片所需信息。

所以目前只能确认“同一正文模板使用了不同标题”，不能确认角色按卡目的获得不同的必要结论，也不能确认规划／审核不会被塞入整段主对话。应继续核最终实现和真实入口；若最终仍只是标签差异，应作为 4.1.3 的语义装配缺口，而不是“未自动总结”缺陷。

### P4：普通非 Git 旧卡的兼容仍需真实入口验收

当前设计已经明确允许 primary 没有地图、没有 Git 身份继续运行，并把 managed 的 Git 要求单独保留。但审查时的实现仍在修改，且以下风险必须用真实旧卡验证：

- `dispatch-core` 的 primary 只有 `commonGitDir` 为空时才免读 Git 身份。
- brief capture 和映射装配仍然可能对执行根调用 Git 相关检查；若错误地套到无地图旧卡，整体派发会被拒。
- 兼容要求只限普通旧卡与 primary；不要求 managed 工作树支持非 Git。

这项当前状态是“作者已按边界修，真实链路未验”，不重复记成已完成或未完成。至少要用真实临时非 Git 项目、无地图旧卡，经实际 dispatch 入口观察它成功执行；同时保留 managed 缺 Git 时拒绝。

## 给实施者的首轮收口清单

1. 统一新增的 `worktreeKind` 契约，消除当前类型检查红灯；不要用 `as any` 或兼容层掩盖。
2. 用真实非 Git 临时项目的旧卡走实际 dispatcher，确认 primary 无地图仍执行；managed 缺 Git 必须拒绝。
3. 把侦察 worker 保存受控摘要接到角色真实装载面；用依赖或工作流自动产生精确 URI，验证下游冻结正文直接含侦察结论，主控不传 markdown／facts。
4. 让规划／审核按卡目的获得各自必要结论，至少分别验证规划所需的调查／接口／依赖信息与审核所需的变更／风险／证据入口。

6. 作者收口后重跑当前三份定向测试和类型检查，再通知进行入口级复核。
