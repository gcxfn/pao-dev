## §1 编排状态机（文字版）

**卡（Task）主状态**（`packages/shared/src/types/core.ts:61`）：
`backlog → todo → in_progress → in_review → done`，旁路 `blocked`/`cancelled`。

迁移全部收敛在纯函数模块 `packages/shared/src/task-status-flow.ts`，每个迁移追加 history 条目（label+时间戳，:38-45），首次 done 落 `completedAt`、离开 done 清空（:31）：

| 迁移 | 函数（task-status-flow.ts） | 触发者/锚点 |
|---|---|---|
| backlog/todo → in_progress | `syncTaskStatusFromWorkspaceBound`(:59) | 任务绑定工作区即启动（`apps/server/src/routes/task-route-support.ts:786`） |
| 任意(非 done/cancelled) → in_review | `syncTaskStatusFromReviewReady`(:70) | PR 创建成功（`task-git-routes.ts:825`）、worker 回报成功（`task-chat-dispatch/result-utils.ts:442`）、MCP 工具（`integrations/mcp/wemux-mcp-workspace-session-tools.ts:493`） |
| 任意 → done | `syncTaskStatusFromWorkMerged`(:81) | **仅** PR merged（`task-git-routes.ts:960`、`cluster-routes.ts:631`）——人工合入是唯一 done 门 |
| 执行完 → ok?in_review:todo | `markTaskExecutionFinished`(:91) | 会话回合结束（`integrations/opencode/task-chat-stream.ts:309`、`result-utils.ts:443`）；失败回退 todo |
| → in_progress(重试) | `retryTask`（`task-orchestrator.ts:271`） | 人/Agent 点重试，`POST /api/tasks/:id/retry`（`task-routes.ts:1013`），retryCount+1 |
| 人工拖卡 | `POST /api/tasks/:id/move`（`task-routes.ts:1031`） | 前端乐观更新（`apps/web/src/routes/kanban.tsx:388+`） |

**执行 run 子状态**（`TaskExecutionRun.status`，`task-domain.ts:245`）：planned→draft→queued→assigned→preparing→executing→syncing_back→completed/failed/cancelled/timed_out/lost。分布式 worker 回执契约 `DistributedTaskStatus`（`core.ts:44-55`）。

**派发子状态机**（谁触发迁移）：任务创建（人／主聊天 Agent 经 MCP `task.create`，`integrations/mcp/wemux-mcp-task-tools.ts:312`）→ 指派决策（`task-assignment-policy.ts:57-80`：有负责人+指派有变化+非 backlog+startMode=now 四条件同时成立才派发 `task.assigned` 事件）→ 排队执行（`task-execution-service.ts:298-315` 建 TaskRun＋入 task-chat 队列）→ worker 执行 → 回执写 result → in_review 等人工。

**可视化六步链**（非自由 DAG）：`OrchestrationStep` 固定 understand→worktree→select_agent→dispatch→verify→handoff（`task-orchestrator.ts:17-24`），步骤 pending/running/done 由当前 status **推导**（:163-187），不单独持久化进度。

## §2 逐问题答案

### Q1 任务状态机全貌
见 §1。补充两点：
- `Task` 本体 = TaskDraftState＋TaskAssignmentState＋TaskExecutionBinding＋TaskRuntimeState＋协作视图的组合（`packages/shared/src/types/task-domain.ts:254-405`），14 字段协议可对照它的分组方式（草稿态/指派态/执行绑定态/运行态四段正交）。
- 会话（WorkspaceSession）有平行的 `needsHumanConfirm`＋`agentRunningStatus`＋`runtimeStatus`（idle/queued/running/waiting/completed/error/lost/cancelled，`core.ts:65`）；`executor-ws-message-handler.ts:376`：runtimeStatus = needsHumanConfirm ? 'waiting' : 'running'。

### Q2 人工确认门
- **门标志**：`needsHumanConfirm`（Task: `task-domain.ts:290`；Session: `:546`）。置 true 的时点＝「交付物已就绪待人裁决」：PR 创建（`task-git-routes.ts:827,835`）、PR 刷新仍 open（:969,975）、分布式回执 syncing_back（`cluster-routes.ts:499,517,640,646`）、MCP 侧（`wemux-mcp-workspace-session-tools.ts:509,514`）。
- **diff 呈现**：专门的 git 差异端点族 `GET /api/tasks/:id/git/working-tree-diff | file-diff | commit-diff | diff | status`（`task-git-routes.ts:308,356,402,445,476`）；PR 评审中心用 `ProjectPullRequestReviewSummary`，**逐文件带 patch/additions/deletions**（`packages/shared/src/pull-request-review.ts:10-54`）。即：确认门前先看 diff，diff 是独立只读端点＋react-query 缓存键（`apps/web/src/lib/workspace-query-keys.ts:26,39`）。
- **确认/打回回传**：
  - 「知道了」：`POST /api/tasks/:id/acknowledge-confirmation`（`task-interaction-routes.ts:341-371`）——**只清标志，不含裁决语义**。
  - 「通过」：人工建 PR/合入 → PR merged 事件回读后 `syncTaskStatusFromWorkMerged`→done＋清标志（`task-git-routes.ts:958-964`）。
  - 「打回」：`POST /api/tasks/:id/retry`→in_progress（`task-routes.ts:1013-1020`），或在任务评论 @agent 带修改意见（`/api/tasks/:id/send`，`task-interaction-routes.ts:373+`）。
- **前端交互**：kanban 里**点开任务即自动 acknowledge**（乐观置 false，API 失败回滚 true，`kanban.tsx:337-354`）；详情面板顶部琥珀色横幅「需要人工确认 · 工作区名」（`task-detail-panel-sections.tsx:395-401`）。
- **超时**：**没有**。标志一直挂着直到 acknowledged/merged；无超时升级、无自动过期（全库 grep 无 confirm 相关 timeout/expire）。未确认：snooze 基建（inbox）未接到确认门上。

### Q3 主聊天编排的路由决策
- **主聊天 ≠ 决策器，是「带 MCP 工具的 Agent」**：`requestMainChatExecutorReply`（`project-main-chat.ts:769`）解析执行节点→自定义 Agent 身份→模型 profile→拼 system prompt（`main-agent-prompt.ts:27-61`）。路由规则写在**提示词**里：涉仓库工作必须 task.create＋委派 Workspace Session；**用户没指定执行者就先 agent.list 列候选问用户，禁止自己接单**（:40-41）；"一个 Task 只由一个负责 Agent 执行"。
- **Agent 挑选**：没有自动挑选算法——`pickAgent` 是返回默认值的桩（`task-orchestrator.ts:15`）；真正选择＝人指派＋`resolveTaskAssignmentDispatch` 决策表（dispatch/self/unassigned/backlog/parked/unchanged 六种结果各配给 Agent 的引导文案，`task-assignment-policy.ts:21-80`）。
- **群聊自动路由（scheduling brain）**：小模型结构化意图分类（DeepSeek，JSON-only 输出，10s 超时，temperature 0；`services/scheduling-brain/intent-classifier.ts:35-63` 提示词、:218-269 入口）→ intent ∈ task_request/agent_request/question/chat/none → run_agent（目标必须在群内可见，否则弃用模型结果回落规则，:189-196）/direct_reply/none。**规则兜底**在 `packages/shared/src/scheduling-brain.ts:77`（关键词分类）。决策与副作用分离：`dispatch-brain.ts:37-77` 只把决策翻译成 implicitAgentIds/直答文案。
- **无主事件监督**：`event-supervisor.ts:56-71` 纯函数判定「孤儿事件」（任务无 assigneeId/assigneeAgentId/assigneeAgentGroupId 即无主；有主一律不碰），无主才发 `brain.event.review` 给群负责人 Agent——失败/无主聚合的思路原型。
- **失败重路由**：retryTask＋`task-chat-runtime-recovery.ts`（恢复卡死的运行态）＋inbox 执行摘要 `InboxExecutionSummary`（failed/dispatch_fault 留痕，`inbox.ts:112-122`）。

### Q4 任务看板数据形状与前端状态管理
- 数据形状：服务端持有全量 `AppState`（tasks/workspaces/sessions/projects/config），每次变更 `withState` 回**全量快照**＋`publishState` 广播。PAO 不抄存储，可抄其**投影**：看板只用 `Task[]`＋assignees 选项＋PR 展示映射（`kanban-page.tsx:51-54`）。
- 前端：TanStack Router 路由级持有状态（`routes/kanban.tsx`），AppProvider context＋`useSyncExternalStore` 页面级 store（`lib/page-tabs-store.ts:276`）；git diff 这类重查询用 react-query（独立缓存键族）。拖卡＝乐观更新＋回滚（`kanban.tsx:388+`）。
- 组件形态：`components/kanban/` 一页三视图（kanban/list/files）：`kanban-page.tsx`（纯组合、状态上游注入）＋`kanban-column/card`（列配置 6 列=TaskStatus 去 cancelled，`constants.ts:33-40`）＋`task-detail-panel*`（右侧抽屉：身份卡/确认横幅/评论/时间线/orchestration 步骤/validationChecks）＋`create-task-modal`＋`task-proposal-card`＋`task-timeline`（模型层 `task-timeline-model.ts` 与视图分离）。
- 快捷建卡：zod schema＋幂等键＋originType=`agent_quick_create`＋originId 溯源（`task-quick-create-service.ts:29-40,58-64`）。

### Q5 Electron 桌面端与 web 控制台的关系
- **壳复用，零 UI 重写**：`apps/desktop/src/main.mjs`（828 行）生产态加载自定义协议 `wemux-app://local/chat`（web 静态产物由 server 的 `web-shell.ts` SSR/静态服务），开发态加载 Vite `http://127.0.0.1:15173/chat`（main.mjs:709,735-741）；`will-navigate` 白名单 origin，外链一律 `shell.openExternal`（:713-719）。
- 壳只做四件事：①窗口状态持久化/托盘；②**本地 worker 探活**——TCP probe `127.0.0.1:48121`，托盘每 15s 刷新「本地 Worker 在线/离线」（main.mjs:468-484,500-514），不负责拉起；③深链 `wemux://`（preload 桥 `__WEMUX_DESKTOP__`＝invoke/onDeepLink/onUpdate 三件套，`preload.cjs`，41 行）；④electron-updater 手动下载更新＋meeting-runtime 本地转写进程管理。
- 协议：与 web 完全同源（HTTP/WS 打控制面），desktop 无私有 API。dev.mjs 负责开发期拉起 Postgres/object-storage/server/web 再启 Electron（`dev.mjs:103-133`）。
- 对照 PAO：PAO 桌面壳是主进程直读 JSONL，比 wemux 更自主——可抄它的窗口/托盘/深链/更新/origin 白名单骨架，抄不了（也不需要）"加载远端 web UI"。

### Q6 工作区/群聊会话与任务的关系建模
- 层级：Project → Workspace（绑定执行节点＋worktree/branch，`task-domain.ts:407-432`）→ WorkspaceSession（`:501-563`）。会话字段极丰富：`sessionKind: primary|subagent`、`sessionRole: general|tester|doc-writer|reviewer|researcher`、`sessionOrigin: manual|delegate|fork`、`parentSessionId/rootSessionId/forkMode(local|worktree)/forkedFromMessageId`、`delegatedPrompt`、`agentInvocationMode: mention|delegate`——**多 agent 协作靠会话角色＋fork＋委派，不靠群聊本身**。
- 任务↔会话：`TaskWorkspaceBinding`（taskId+workspaceId，active/detached/archived，`:475-482`）；每次执行落 `TaskRun`（:234-252）；结果 `TaskExecutionResult.delivery`＝branch 或 PR（:196-201）。会话可以是"无任务的裸会话"：`buildWorkspaceSessionRuntimeTask` 造临时 Task 形适配器给旧 API，**永不持久化**（`workspace-session-runtime-task.ts:14`头部注释）。
- 群聊：独立于任务的 Conversation，成员＝用户＋Agent（`workspace-group-chat-routes.ts:35-40` schema），群内多 session，@mention 分发（`chat-mentions.ts`）＋调度大脑隐式分发；mention 通知双通道（任务评论/群聊，`task-domain.ts:345-378`）。
- 对照 PAO：PAO 的"主控拆卡派 worker"≈ wemux 的"主聊天 Agent 委派 WorkspaceSession"；wemux 的 sessionRole（tester/reviewer）值得 PAO 卡协议参考。

### Q7 工作流/DAG/模板机制
- **没有 DAG/画布**。全库无 workflow 引擎；唯一 "workflow" 是 GitHub Actions 运行状态的只读观测（`pull-request-review.ts:99-174`）。
- 最接近的三样：①固定六步 `OrchestrationStep`（状态推导显示，非执行引擎）；②`ProjectEnvironmentTemplate`（wemux-yml 环境模板，`task-domain.ts:165-171`）；③`CustomAgentTemplatePackage`/TransferPackage——自定义 Agent 的导入导出模板（`custom-agent.ts:206-245`）；④automations（cron 触发，`automation-service.ts`）。
- 结论：PAO P4 画布在 wemux 无可直接照抄物；可借的是「步骤显示从状态推导」与「Agent 模板包」两个点子。

## §3 PAO 可抄清单

| # | 抄什么 | 抄到 PAO 哪里 | 抄法 |
|---|---|---|---|
| 1 | **纯函数状态迁移模块**（task-status-flow.ts：迁移集中、history 追加、completedAt 单向落） | PAO 卡状态机（控制入口五态的迁移层） | **翻译后抄**：函数形状照搬，枚举换成 PAO 五态；写成无 IO 纯函数+JSONL 侧写 |
| 2 | **needsHumanConfirm＋agentRunningStatus 双标志**（卡上"待人"标志与会话"运行中"标志分离） | PAO 审查门：卡上 `reviewPending`，worker 会话上 `agentRunningStatus(idle/thinking/executing/waiting/complete/error)` | **直接抄**（字段名+语义）；六值枚举照搬 |
| 3 | **确认门三动作**：acknowledge（仅消音）/merge→done/retry→打回 | PAO 审查回执：验收通过=合入语义、打回=retry 语义、忽略=acknowledge 语义 | **翻译后抄**：PAO 加显式 reject 载荷（wemux 没有）；超时 PAO 需自设计（wemux 无超时，见 §2 Q2） |
| 4 | **task-assignment-policy 决策表**（六种派发结果+给 Agent 的引导文案+自指派去重） | PAO 部长派卡规则（"一卡一负责 worker"） | **直接抄**逻辑，翻译成 PAO 卡协议 |
| 5 | **调度大脑三件套**：小模型 JSON-only 意图分类+10s 超时+规则兜底+目标可见性校验 | PAO 主控路由（自然语言→选 worker） | **翻译后抄**：DeepSeek→本地模型/规则；intent 枚举与「决策/副作用分离」结构照搬 |
| 6 | **孤儿事件监督**（isWorkspaceEventOrphan 纯函数：无主才升级给负责人） | PAO 待处理列表的"失败卡/待裁定聚合"判定 | **直接抄**判定式，触发器改本地事件 |

| 8 | **看板交互**：6 列配置、乐观拖卡+回滚、右侧详情抽屉、快捷建卡（zod+幂等键+origin 溯源）、时间线模型/视图分离 | PAO 看板（文件聚合只读→交互层一致） | **交互照搬，数据层 PAO 自有**；quick-create 的 originType/originId 字段加进 PAO 卡协议 |
| 9 | **diff 端点族分离**（working-tree/file/commit 三粒度独立只读接口+独立缓存键） | PAO 审查门 diff 回执（主进程直读 git/文件 diff） | **翻译后抄**：接口分形照搬，实现换本地 git |
| 10 | **Electron 薄壳骨架**：窗口状态持久化、托盘+执行节点 TCP 探活、深链协议+preload 三件套（invoke/deepLink/update）、origin 白名单、单实例锁、手动更新 | PAO 桌面壳（只读聚合看板） | **直接抄**骨架代码（Apache-2.0 带头声明）；worker 探活对 PAO=worker 进程探活 |
| 11 | **WorkspaceSession 角色/fork 建模**（primary/subagent、tester/reviewer 角色、fork 溯源、delegatedPrompt） | PAO 会话内详情的 worker 会话建模 | **翻译后抄**：按 PAO 卡协议裁剪字段 |

## §4 明确不值得抄

- **双存储架构**：app-state-store（JSON 快照）与 postgres/*-store 并存的过渡期兼容层，复杂度高且 PAO 无此需求。
- **集群/网格**：cluster sync、easytier 组网、preview tunnel、executor mesh 路由——PAO 单机不需要。
- **commercial-gate/hosted-model-gate**（`services/gate/`，882 行）：商业授权门，与编排无关，别被 "gate" 目录名误导。
- **pickAgent 桩**：名为挑选实为默认值，无真实匹配逻辑可抄。
- **acknowledge 即消音的交互**：点开任务自动清 confirm 标志（kanban.tsx:337）对 PAO 是反模式——PAO 审查门要显式验收/打回，勿抄自动 acknowledge。
- **marketing/SSR/SEO/meeting-runtime**：与编排无关。
- **scheduling brain 的 DeepSeek 硬编码**：外部 API 依赖，PAO 应走本地模型或纯规则。
- **固定六步 orchestration 的具体步骤名**：绑定 wemux 的 worktree 工作流，PAO 生命周期不同，只抄"状态→步骤映射"机制。
