## 1. 结论

I2-1 已提供无需桌面 catalog、checkpoint、Git 或 runtime 适配器的默认本地工厂。CLI、基准和受信任子进程可直接使用：

```ts
createLocalPaoWorktreeHost({
  stateRoot: string,
  projectRoot?: string,
}): PaoLocalWorktreeHost
```

工厂不读取环境变量。`stateRoot` 由调用方决定：桌面主进程应传 `userDataDir`；子进程通过可信 `childEnvironment` 取得与父进程完全相同的 `PAO_WORKTREE_STATE_ROOT`。当前主控的 CLI 默认策略是优先使用 `PAO_WORKTREE_STATE_ROOT`，否则使用 `(PAO_HOME/agentDir)/worktree-host`。`projectRoot` 只用于限制一个宿主可服务的项目范围。

这个路径是“工作树宿主状态根”，不是新的 `PAO_HOME`。例如桌面传入 `userDataDir` 后，共享状态文件就是 `userDataDir/pao-worktree-host.json`。CLI 父进程和子进程只要拿到同一个字符串，就会读取同一份创建记录和 Git 工作树真值，不会各维护互不认识的 catalog。

工厂构造阶段只解析路径并组装对象；目录、状态文件和 Git 裸仓都在首次动作时惰性创建。导入工厂没有进程监听、命令行解析或磁盘写出。

## 3. 复用来源与实现

- 内容边界和内容树捕获复用 `cards/baseline.ts` 的 `captureContentTree`，覆盖 tracked 改动、相关 untracked 和项目统一排除规则。
- 跨进程状态互斥复用 `shared/lock.ts` 的 `withFileLock`；状态写入复用 `shared/atomic.ts` 的 `writeFileAtomic`。
- 占用、清理守卫和运行产物识别复用 `worker/lock.ts` 的现有实现。
- 工作树公开契约复用 `worktrees/types.ts`；`createSingleRootWorktreeHost` 继续如实报告 `primary-only`。
- 宿主状态机以桌面的 `pao-worktree-host.ts`、`pao-worktree-host-state.ts`、`worktree-manager.ts` 和 `app-worktree-roots.ts` 为迁移来源，桌面只保留公开兼容类型和真实存储适配差异。
- 源内容树到独立裸仓的搬运使用一次 `git pack-objects --stdout --revs` 管道到 `git unpack-objects -q`。没有逐 tree/blob 启动两个 Git 进程，也没有新增 npm 依赖。
- `pack-objects` 和 `unpack-objects` 都会收集 `error`、退出码、信号和 stderr。管道读写错误会关闭写端并终止两端；取消和超时向调用方传播，不静默吞错。
- 搬运完成后分别执行 `rev-list --objects`，比较源仓和目标裸仓的完整可达对象集合，并验证根 OID 仍是 tree。路径枚举使用 NUL 分隔，支持中文和特殊路径。
- 新建工作树的 checkout 索引位于 `stateRoot/tmp/worktree-index-*`，属于一次性中间目录，使用后在 `finally` 中删除；测试夹具不使用系统临时目录。

状态根中的主要数据：

| 路径 | 用途 |
|---|---|
| `pao-worktree-host.json` | 创建、清理和幂等记录 |
| `worktrees/` | 默认工厂创建的真实 Git 工作树 |
| `worktree-baselines.git/` | 独立、可恢复的裸基线仓 |
| `pao-worktree-host-requests/` | 跨进程 request 锁 |
| `tmp/worktree-index-*` | checkout 到新工作树时的一次性索引目录 |

## 4. 七项验收对应

### 4.1 构造工厂不写磁盘

测试先创建真实 Git 仓，再构造默认工厂，随后断言 `stateRoot` 仍返回 `ENOENT`。只有调用宿主动作后才产生状态。同一测试还验证非 Git 目录创建失败后没有留下状态根。

### 4.2 dirty tracked、untracked、多目录和二进制基线

输入包含：

- 已提交后被修改的 `tracked.txt`；
- 新产生的 `src/未跟踪说明.txt`；
- 已提交的中文路径文件；
- 两层中文目录；
- 5 字节二进制文件和 4096 字节批量二进制文件。

创建后可恢复工作树读到相同的 dirty/untracked 内容。独立裸仓中的根 tree 可读取，`git show` 证明二进制逐字节一致，`ls-tree -z` 的路径与 `includedPaths` 一致，源仓与独立裸仓的可达对象集合也一致。

### 4.3 第二工厂解析同一 managed 工作树

第二个默认工厂使用相同 `stateRoot` 和 `projectRoot`，按第一个工厂返回的 `worktreeId` 调用 `resolveForDispatch`。返回的 `worktreeId`、`executionRoot`、`branchName`、`baseline` 和 `inputVersion` 与创建结果一致；旧 `inputVersion` 被明确拒绝。

I2-1 的第二实例解析是同进程内的不同宿主实例。真实 Node 子进程覆盖并发创建和状态合并。桌面父进程用桌面适配器创建、默认子进程工厂解析属于 I2-2，尚未运行，不能计入本项通过。

### 4.4 相同 request 重放幂等

第一个工厂创建 request 后，第二个工厂重放相同 request，返回完全相同的绑定。持久状态中该请求只有一条记录，没有重复创建第二棵工作树。

### 4.5 不同 request 并发不覆盖状态

两个真实 Node 子进程同时使用同一 `stateRoot` 创建不同 request。两端生成了不同的 `worktreeId` 和 `executionRoot`；最终状态文件同时保留两条记录，且两条都是 `completed`。这里依靠 request 锁、全局状态锁、原子替换和写后重新解码，未删除或绕过既有锁。

### 4.6 损坏和显式失败不退化为成功

- 非 Git 目录的 `capability` 明确返回 `ok: false`，`create` 明确抛错。
- 人为写入损坏 JSON 后，新工厂解析 managed 工作树明确失败，没有返回旧绑定或空记录。
- 单根适配器明确报告 `create=false`、`cleanup=false`、`baseline=primary-only`；尝试派发 managed 工作树明确失败。

### 4.7 用户工作树边界与停止保护

测试由用户手工执行 `git worktree add` 建立 `user/manual` 工作树，再用其路径作为 managed ID 请求默认宿主接管。宿主以“不在应用目录根内”拒绝；用户文件内容、分支和工作树均保持原样。

共享宿主保留了迁移后的占用检查、执行根守卫和清理时保留现场逻辑；I2-1 只验证“不接管用户工作树”。完整的清理竞态、停止未确认保留和运行中拒绝属于 I2-3，本报告不把它们算作已验收。
