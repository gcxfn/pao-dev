# PAO 实施后全面审阅与 harness 优化建议

审阅开始：2026-10-16；结论日期：2026-10-17。审阅对象为当前未提交工作区：内核 HEAD `a2380612e`，桌面 HEAD `2cf4c807`，含两者之上的全部既有修改。没有修改生产源码、项目测试、正式 PAO_HOME 或调用真实供应商。

## 1. 结论

PAO 已具备相当一部分 harness 能力。harness 在这里指围绕模型的运行底座：安排上下文与工具，控制执行，核对结果，支持人工干预与恢复。

这次实现改善了共享内核、停止与回执预算、记忆取消、卡片读写、并发协作和桌面文件查看等路径。**但目前还不宜将“完整计划已验收”和“可信的自动工作闭环”画等号。** 新临时计划层存在归属、取消和启动一致性的实际缺陷；意见状态、撤销、模板复用及文件版本链也没有完全兑现计划。

建议先做一轮小范围可靠性修复，再补不依赖真实供应商的完整运行链测试。下一阶段重点是：用户给出的意图、程序实际做过的动作、界面显示的结果能够逐一对上。

本轮有 **106 项已有定向测试通过**；新增隔离脚本复现了 10 个场景，包含 1 项需明确产品语义的重复启动观察。测试通过与反例并不矛盾：已有测试覆盖常规行为，反例针对未覆盖边界。具体范围见第 6 节。

## 2. 需要优先修复的问题

P1 表示可能越过用户停止/会话归属或破坏启动一致性；P2 表示在明确条件下造成错误、丢失输入、误导反馈或功能断链。以下按影响排序，而非按发现时间排序。

### 1. [P1] 临时计划动作没有执行项目与来源主控的归属校验

- 位置：[plan-tools.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan-tools.ts) 第 190–196、337–345、413–440、540–550 行；[App.tsx](../../desktop/apps/desktop/src/app/App.tsx) 第 1241 行。
- 真实触发：同项目有两个主控会话，B 拿到 A 的计划 ID 后调用修改工具；或者模型传入不同的 `project_root`。
- 隔离结果：来源为 `owner-A` 的计划被 `owner-B` 正式注册工具改到版本 2；工具注册时绑定项目 A，显式参数仍可把创建落到项目 B。
- 原因：宿主解析的项目和来源会话主要被当作默认值/记录字段，没有成为修改、启动、意见等动作的校验条件。桌面“交给主控”也只是把文字放入当前选中会话的输入框，没有先定位计划来源主控。
- 影响：多个任务之间容易串线。这里报告的是受管操作的正确性缺陷，不宣称它构成操作系统级安全隔离漏洞。
- 建议：项目以宿主身份为准，显式路径须匹配；所有计划变更检查来源 owner，启动回调后重核身份。桌面操作定位原主控，原主控不可用时解释原因，不静默使用当前另一个会话。
- 验收：B 不能修改/启动 A 的计划；其他项目参数被拒且无文件变化；原主控操作正常。确需转交时另走明确交接，不靠换参数接管。

### 2. [P1] 用户在确认等待期间取消，计划仍会启动

- 位置：[plan-tools.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan-tools.ts) 第 490、510–550 行。
- 隔离结果：启动工具等待模拟宿主确认时取消信号已触发；随后确认回调返回，真实控制文件仍形成，工具报告已受理。
- 原因：启动工具接收 `_signal` 却忽略它，也未将信号传入启动受理阶段。已有工作流入口支持的取消保护，在新包装层丢失了。
- 边界：本次确认和后台受理面为模拟，没有发出真实模型请求；实际计划、控制及关联文件由正式工具创建。
- 建议：进入工具、确认返回后、拿锁后、实际受理前检查取消；将信号传入同步受理。已受理后台任务沿既有显式停止语义处理，不能把“取消尚未受理”和“停止已运行”混为一谈。
- 验收：确认等待中取消后，控制文件、启动关联和新执行请求均为零；受理后停止走真实终止结果。

### 3. [P1] 启动、编辑与冻结没有共用计划级临界区

- 位置：[plan-tools.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan-tools.ts) 第 533–558 行；[plan.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan.ts) 第 477–484、556–558、728–791 行。
- 隔离结果：控制正本形成后、启动关联落盘前，另一个操作仍成功编辑同一计划；最终定义为版本 2，已经启动的关联仍为版本 1。
- 复现方式：用模拟后台受理面固定这个时间窗口，调用真实修改入口；两份结果均真实落盘。不是声称已在正式现场捕获竞争。
- 原因：编辑只看启动关联文件判断冻结；启动不拿编辑使用的计划锁，且关联在启动核心返回之后才写。控制文件存在但关联尚未形成时，定义仍被认为可编辑。
- 建议：确认等待不持锁；确认回来后，在计划锁内重核版本、归属、取消及启动意图，并先持久化“这一版正在启动”的必要关联。后续按已有控制正本结算；启动中断可恢复，不能退回可编辑状态。不需要新增通用事务框架。
- 验收：并发启动/编辑只能有一个先受理；启动中断后定义仍受保护；重试找回原实例，不能错配定义版本。
- 另外观察：同一计划分别使用两个启动请求 ID，能形成两个不同实例。两次模拟确认均返回同意，因此本项不单独判为无授权重复启动。产品应明确“计划只运行一次”还是“允许显式再运行”，避免普通重试换 ID 后意外再跑；现有界面仅取最后一个启动记录也应与该选择一致。

## 3. 其他已确认缺陷和功能缺口

### 4. [P2] “已送达／已应用”仍可以由模型自述直接写入

- 位置：[plan-tools.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan-tools.ts) 第 621–728 行；[plan-feedback.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan-feedback.ts) 第 235–265、284–307 行。
- 隔离结果：没有调用任何部长投递，也没有修改任何成果文件，仅传 `delivered: true` 和非空结果文字，再传一段非空 `evidence`，意见就变为“已应用”。
- 当前检查只保证文字不空；并未关联宿主已经确认的投递请求、具体实例或真实业务变更。登记过投递 ID 的意见，结算时甚至可以不提供 ID。
- 建议：模型可以提出“投递/应用”意图和说明；送达状态由宿主真实请求回执结算，应用状态关联可核对的卡、修订或差异。无法机械确认的文字只能标为“主控说明”，不要冒充已经核实的事实。
- 验收：没有真实请求、请求 ID 不匹配、无有效业务依据时不能变为已送达/已应用；有效回执重放不重复结算。

### 5. [P2] 插入或重排步骤后，旧意见会指向另一个任务

- 位置：[plan-tools.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan-tools.ts) 第 207–211、432 行。
- 隔离结果：原 s2 为“正文初稿”，已有针对 s2 的意见；在首位插入“新增准备”后，s2 变为“人物设定”，意见仍指向 s2。
- 原因：工具按列表位置沿用旧 ID，修改协议不让调用者携带旧步骤 ID；稳定身份只对原位改标题有效。
- 建议：修改工具接受稳定步骤 ID；新增步骤分配新 ID，重排只改顺序，删除要检查依赖和意见。依赖序号需按提交的实际 ID 映射，不能直接假定第 N 项就是 sN。
- 验收：插入、删除、重排后旧意见仍指向原任务；删除对象保留可解释记录，不转挂其他步骤。

### 6. [P2] 没有实现可恢复的“撤销最近修改”

- 位置：[plan.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan.ts) 第 388–390、517–552 行；[workflow-cards-model.ts](../../desktop/apps/desktop/src/features/workflow-cards/workflow-cards-model.ts) 第 343–345 行。
- 隔离结果：修改后执行 `action=undo`，得到的是整份计划被标为已撤销，字段仍为新值；计划目录只有当前 `计划.md`，请求记录没有保存上一版步骤内容。
- 桌面“撤销最近一次修改”没有调用这个取消动作，而是让主控用 modify 改回上一版；程序没有提供可靠旧版本，离开原对话后无法保证还原。
- 建议：把“撤回整份计划”和“撤销最近修改”拆清。复用最小版本快照或可逆字段差异，撤销带目标版本与当前版本检查；无需做通用版本管理产品。
- 验收：修改→关闭会话/重开→撤销，真实字段恢复且计划仍可启动；新版本冲突时拒绝覆盖。

### 7. [P2] 模板参数化和桌面复用链尚未闭合

- 位置：[plan.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan.ts) 第 904–911 行；[workflow-cards-view.tsx](../../desktop/apps/desktop/src/features/workflow-cards/workflow-cards-view.tsx) 第 399–407 行。
- 隔离结果：按工具建议把路径改成 `{项目}/正文.md` 后保存模板，报 `RECIPE_PARAM_PLACEHOLDER`：参数“项目”未声明。模板构造器固定输出 `参数: []`，没有对应声明入口。
- 桌面现状：模板库在新工作台中只是静态名称列表，没有选择、参数填写或启动操作；App 的工作流入口直接打开卡片页，旧画布内向导不再是这条产品路径的入口。CLI/模型工具仍可能使用已有模板，不应据此说整个内核模板能力消失。
- 建议：定义/保存动作支持明确参数声明，复用已有配方解析和向导校验；在卡片工作台提供模板查看与“用于本次任务”，不恢复画布。保存模板也需有可恢复的请求结果，避免返回丢失后重试只报同名冲突。
- 验收：保存参数化模板→另一个项目选择→填写输入→真实启动新实例，不能带入旧会话、旧卡号或旧成果路径。

### 8. [P2] 查询工具无法完整恢复任务要求

- 位置：[plan-tools.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan-tools.ts) 第 452–473 行；[plan.ts](../../PAO/packages/coding-agent/src/pao/workflow/plan.ts) 第 372–384 行。
- 隔离结果：磁盘保存了特定任务要求，`pao_plan_query` 工具返回中却没有该要求。它只交回摘要、标题、部门和部分依赖，`details` 也为空。
- 影响：主控压缩上下文或重开后，不能仅靠查询恢复要求、验收、约束、预算与技能。正常 read 工具仍可能读取原文件，所以这不是数据丢失，而是恢复接口不完整。
- 建议：保留简短列表，但指定计划/步骤查询返回完整定义和必要运行身份；提供有界分页/按步骤读取，不要求模型猜文件路径或把整个历史一股脑常驻注入。
- 验收：用空历史的新会话仅通过查询找回原要求，不能遗漏验收或偷偷改变约束。

### 9. [P2] 文件意见没有绑定用户实际阅读的版本，整体意见还生成空步骤 ID

- 位置：[workflow-cards-model.ts](../../desktop/apps/desktop/src/features/workflow-cards/workflow-cards-model.ts) 第 280–283、365–375 行；[workflow-cards-view.tsx](../../desktop/apps/desktop/src/features/workflow-cards/workflow-cards-view.tsx) 第 934–945 行；[desktop/plans.ts](../../PAO/packages/coding-agent/src/pao/desktop/plans.ts) 第 177–197 行。
- 已复现的纯函数结果：整体意见被转成“目标类型=步骤，步骤ID=”；文件意见只传路径，要求模型自己推断真实轮次与版本。
- 源码事实：讨论对象没有实例、步骤、轮次或文件版本；产物按路径去重，同路径的历史轮次会被后来的条目覆盖。正文只按当前磁盘路径读取。
- 影响：用户读着旧稿提意见时，主控可能绑定新稿；同路径旧稿不能通过这条预览入口准确选择。Git 历史存在，不等于 UI 已经把历史版本接上。
- 建议：文件条目和意见携带宿主核实的“实例＋步骤＋轮次＋版本身份”，预览与提交使用同一身份；整体意见应有流程目标，或明确不写步骤意见。历史文件需要实际快照/提交版本读取，不能只显示历史标签。
- 验收：阅读旧稿时产生新稿，旧意见仍绑定旧版本；同名同路径不同轮次可区分；整体意见可被真实记录，不要求模型补猜步骤。

### 10. [P2] 界面刷新、草稿和“已修改”反馈与计划承诺不一致

- 位置：[workflow-cards-view.tsx](../../desktop/apps/desktop/src/features/workflow-cards/workflow-cards-view.tsx) 第 173–185、236–278、550–570、895–902 行。
- 源码可触发：刷新会重新生成 `selectedStep` 对象，依赖它的 effect 把尚未提交的字段重置成盘上值；切项目直接清空意见输入，没有按对象保留。普通步骤选择也会改变讨论对象，与“查看不自动改变发言对象”的原约定不同。
- 另一个直接问题：点“交给主控”只是把文字放到输入框，尚未发送或落盘，就设置 `pendingChange` 并显示“已修改第 N 步的…”。同页另一处“还需发送”的提示不能消除这条冲突反馈。
- 建议：草稿按项目/计划/步骤保留，只在收到对应版本保存结果后替换；用稳定 ID 与版本决定何时同步初始值，不能跟随每次投影对象重置。提交前标“待提交”，真实修改成功后才显示已修改及撤销。
- 验收：编辑中经过 30 秒刷新、切步骤再返回、切项目再返回均不丢；消息未发送不显示已修改。此项本轮依据当前源码调用关系确认，未重新启动 Electron 操作复现。

### 11. [P2] 当前主控输入框可能被覆盖，操作可能交给错误会话

- 位置：[workflow-cards-view.tsx](../../desktop/apps/desktop/src/features/workflow-cards/workflow-cards-view.tsx) 第 288–302 行；[App.tsx](../../desktop/apps/desktop/src/app/App.tsx) 第 1236–1241 行。
- 触发：主控输入框已有未发送内容，点击保存模板、修改要求或提交意见。
- 源码事实：动作回调直接 `setComposerDraft(text)`，没有保留或合并原草稿，也没有按选中计划的 `sourceSessionId` 切回原主控。展示来源会话并不等于实际发送到了该会话。
- 建议：先定位原主控；把本次意图作为有对象关联的草稿交给该会话，原草稿非空时保留并让用户选择合并/暂存。尽量避免反复生成内部工具说明让用户再手动转发。
- 验收：两主控切换、原输入框非空、来源主控关闭三种场景均不丢输入、不投错对象。归属校验仍在内核执行，不能只靠 UI 切换。

### 12. [P2] 同路径文件更新后，预览缺少新版本识别与刷新入口

- 位置：[workflow-cards-view.tsx](../../desktop/apps/desktop/src/features/workflow-cards/workflow-cards-view.tsx) 第 1537–1557 行。
- 触发：用户保持右栏打开，后台更新同一成果路径。
- 源码事实：正文请求 effect 只依赖 api、项目和路径；同路径内容变化不会重读，也没有新版本提示。用户切走再回来时会读取当前稿，仍没有明确版本身份。
- 建议：宿主投影提供版本依据；检测变化后提示“有新版本”，用户显式切换后读取。保留正在读的正文与位置，不能靠每次轮询强制重载来修复。
- 验收：更新后有提示，旧稿不被抢换；切换新稿后正文与意见目标版本一致。本轮未做真实 Electron 重演，结论依据状态依赖与读取路径。

## 4. 验收与记录的缺口

这些项目是“尚未证明完成”，不等同于已确认产品存在相同缺陷。

1. **全链路未被端到端验证。** [阶段 7 脚本](../../临时文件夹/阶段7-发行与性能-20261015/verify-novel-loop.mjs)直接调用 driver/control，手工绑定部长、形成卡和回执、执行判定/确认。它证明了状态转换、真实文件及 Git 交付，可以保留；没有证明主控工具→宿主确认→部长请求→Worker→回执这一整条实际运行通道。
2. **真实界面控制成功路径不足。** 当前 `workflow-cards.spec.ts` 的确认/暂停夹具没有活的 owner，主要验证拒绝和正本不变。脚本直接 `confirmControl` 成功，不能替代 UI→IPC→owner 的成功集成。可以使用本地离线模型/部门替身补齐，无需为此调用付费供应商。
3. **机器重启、真实读屏与系统缩放未验。** 报告已有披露，但总计划所有阶段标为通过，开头仍写“新任务尚未实施”。计划状态、完成标准和实际结论需要对齐；浏览器/Electron zoom 不等于系统 DPI，ARIA 检查不等于实际读屏。
4. **发行物验收范围较窄。** 当前 `packaged-smoke.spec.ts` 验证应用启动与创建线程，尚不足以证明新临时计划工具、确认、文件版本与恢复在内嵌内核里都可用。应补一个打包版关键工作流用例。
5. **“真实数据”表述需分层。** 由 API 写出的文件是真实文件；脚本生成正文、回执和决策仍属于模拟任务输入/执行者。阶段 7 报告“数据不是模拟”容易把文件真实性和执行者真实性混在一起，建议按这两个维度分别记录。
6. **旧 UI 覆盖已归档，不能只对比测试总数。** 旧工作流多份 core spec 被移入 archive，新页面的四个用例未覆盖此前全部能力。应按动作与故障场景对照保留覆盖，尤其模板再运行、成功人工确认、源主控归属、草稿和版本恢复。

建议总计划保持“主要实现完成、补充验收和缺陷修复中”，逐项注明未验事实；本轮没有直接替用户改写计划状态。

## 5. 后续如何让 PAO 成为更完善的 harness

### 5.1 第一批：把动作结果交给程序核实

**优先做第 1–5 项，再补第 6–12 项的工作闭环。** 不建议这一轮新增编排类型或插件框架。

| 工作包 | 复用基础与做法 | 验收结果 |
|---|---|---|
| 统一计划变更入口 | 在现有 workflow 边界内复用小函数核对 actor、项目、版本、请求和取消；确认返回后重核，短临界区内预留启动 | 跨会话误改为零、取消前未受理不会产生新执行、并发不出现冻结版本漂移 |
| 真实投递与应用回执 | 使用 host 已修复的请求确认，将请求 ID/实例与意见关联；模型说明和程序核实状态分开 | 无真实回执不出现已送达，无真实变更依据不出现已核实应用 |
| 稳定对象与版本 | 稳定步骤 ID；最小定义历史；成果版本身份；恢复查询返回完整要求 | 重排不换意见对象、重开能撤销、旧稿意见不绑新稿、模型能找回任务约束 |
| 完整模板复用 | 复用配方参数及现有向导校验，做成卡片化的“用于本次任务”入口 | 保存→换项目→填参数→启动新实例一次走通；不夹带旧运行数据 |
| 无损输入与事实反馈 | 复用会话草稿机制，按对象存草稿；UI只根据受理/保存结果显示成功 | 刷新不丢、切任务不串、提交前不显示已应用/已修改 |

### 5.2 第二批：建立小而完整的运行验证集

已有测试数量不少，下一步收益更大的是补**真实调用链**，而非继续堆只测数据形状的用例。

- 使用已有 pi 会话与 RPC 接口，加可控的离线供应商/部门替身，让它真正发工具调用、接拒绝/超时/取消并提交回执。保留明确模拟标记，避免真实花费。
- 固定五类日常任务：有文件交付的写作、代码修改、只读审查、多部门协作、用户中途更改要求。第一轮可以先选写作和审查，不必一次铺开全部。
- 每类包含正常完成、权限/版本拒绝、工具失败、取消、应用崩溃后恢复；验证重试是否重复执行、恢复是否遗漏约束、最终状态是否与文件一致。
- 每次记录源码及构建身份、逻辑请求、实例/步骤/轮次、实际请求与结果、用量和人工动作。沿用原生日志和账本，通过已有 ID 关联，不新建全量重复事件平台。
- 核心通过标准：重复副作用为零、越权受理为零、未核实成功状态为零；没有足够证据的结果明确未知。
- 真实供应商的小样本创作质量、模型工具选择和费用验证，待用户另行授权后补；它与离线工程验收分别报告。

### 5.3 第三批：补任务级的可观察、恢复和成本解释

| 方向 | 建议 | 暂不做 |
|---|---|---|
| 上下文恢复 | 查询提供当前目标、约束、已确认结论、缺失输入及必要文件版本；用已有 context/压缩接口按需补入 | 不把全部历史和记忆每轮重复注入，不另建第二个记忆系统 |
| 待处理事项 | 从控制正本重建待确认、失败、未投递意见及恢复原因；对必须送达的操作保留请求关联 | 不依赖仅存内存的提醒来判断任务完成，也不急于上消息中间件 |
| 成本与预算 | 先复用原生用量统计提供实例汇总，区分已知、未知及估计；用户显式给总预算时再实现跨部门/Worker的剩余额度预留 | 不把每卡预算误当整条工作流总预算，不用缺省0伪造费用完整 |
| 工具错误与重试 | 给工具结果保留稳定状态/错误码与“是否已经产生副作用”；只对明确可重试失败自动重试 | 不依据一段自然语言错误或模型猜测重放写操作 |
| 数据格式与恢复检查 | 计划/启动/意见读取完整校验字段与格式版本；损坏时保留原件，提示可恢复步骤 | 不把编辑版本号当文件格式版本，不静默补默认值继续执行 |
| 模块维护 | 对真实重复的身份、取消和版本规则小范围收口；保持 pi模型循环与PAO业务边界 | 不为 harness 名称再做整体重写、通用规则引擎或插件市场 |

这些方向可以分批交付。前两批优先解决现有正确性与验证缺口；第三批再依据日常任务数据决定顺序，避免为了“更像平台”增加用户暂时用不到的机制。
