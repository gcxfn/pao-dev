# r11 生命周期修复实施报告

## 结论

已修复源码中可确认的 print 收尾竞态，并把修复收敛为一个会话级关闭门加正确的最终收敛顺序：

1. 封闭新的模型轮次和会进入底层队列的输入。
2. 等待关闭门之前已受理的活动、`agent_settled` 回调及其延迟动作完成。
3. 发送一次 `session_shutdown`。
4. 释放后台端口、使扩展上下文失效并销毁会话。

正常 print 会处理关闭前已经合法的后台结果和后续轮次；销毁后晚到的输入会被拒绝，不能再借旧扩展上下文启动模型。没有修改 PAO 的 background、worker 通知或业务模块。

这次修复能确认并消除源码里的生命周期窗口缺陷。它不能证明 r11 当时保存的 `pao-dispatch-notify` 一定走过这条窗口，也不能补出当时缺失的 caller、精确交错和关闭原因。r11 的确切因果仍未证实。

## 关闭前与销毁后

两类事件在实现和测试中明确分开：

- **关闭门之前已受理**：普通输入、未知 slash、现有 skill、input、认证、压缩、before-start、图片处理、模型轮次和 settled 后续动作计入活动，`close()` 等它们正常结束。真实扩展命令可以替换当前会话，因此不记旧会话活动。通知正文可在当前已受理轮次内作为上下文注入，不靠丢弃通知结束。
- **关闭门之后到达**：新的 prompt、会开始/排队轮次的 custom message、steer、followUp 和 nextTurn 被同步拒绝。旧后台任务晚到的通知不会产生第三个模型轮次。

不能简单地“先 shutdown、后 dispose”来避免错误。那会把关闭门前已经受理的合法结果丢掉，并把正常收尾误报成工作流失败。

## 返修后的关闭语义

主控复核发现两处阻断项，已返修：

- 正常 print 仍先完成 `waitForBackground()`，再显式 `session.close()`，让关闭门前已受理的后台结果和 follow-up 正常完成。
- 所有主动 `AgentSessionRuntime.dispose()` 调用（包括 SIGTERM、SIGHUP、交互 shutdown 和 RPC 会话替换）恢复到现有取消语义：`beginClose()` → `abort()` → `close()` → `session_shutdown("quit")` → 释放后台端口 → invalidate → 销毁会话。正常 print 调用 dispose 时，前面的显式 close 已让会话空闲，所以再次 abort 不会丢合法结果。
- `dispose()` 仍由 `_disposePromise` 串行复用，并发调用和后续重复调用只执行一次 shutdown。
- slash 输入在第一次 `await` 前同步查扩展命令。真实扩展命令保留原路径，避免 `ctx.newSession()` 等旧会话自身；未知 slash、现有 `/skill:` 和普通输入先登记活动，再进入异步处理。

这里只修正常关闭和主动取消共用的一条会话生命周期边界，没有建立新权限、终止机制或通用框架。
