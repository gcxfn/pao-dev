# r11 停链调查

## 结论

这次是**流程停链，不是控制器或操作系统 `pause`**。

已确认的因果是：

1. 主控最后一段有效模型轮次在 `2026-10-24T11:39:31.612Z` 正常结束。
2. `11:39:32.154Z` 注入了一条 `pao-dispatch-notify` 通知。
3. 此后主控原生会话只有这条通知，没有新的 assistant 输出，也没有 `agent_end` 或 `agent_settled`。
4. 同一时间前后开始出现 `turn_end could not resolve the persisted assistant entry ID` 和旧扩展上下文失效错误。
5. 主会话关闭时，工作流桥接层执行 `pauseControl(..., "主会话关闭，须显式人工恢复")`，并把实例状态落为 `挂起`。

因此，“主会话关闭”这一结论成立，但**触发哪一种会话关闭的具体动作尚未确认**。源码能把它细分为 `quit`、`new`、`resume`、`fork` 或 `reload`，现有运行证据没有保存关闭原因。

容器仍在运行，不等于任务仍在运行。截至 `2026-10-24T12:11Z`：

- Docker 状态是 `running`，`Paused=false`。
- 外层任务原题时限是 `28800` 秒，调查时远未到期。
- `docker top` 只有 `sleep`、任务父 shell、`benchmark-organized-entry.mjs` 的 Node 进程和 `tee`。
- 没有部长 `--mode rpc` 子进程，也没有 worker 子进程。
- 原生会话没有 11:39:32 之后的新 assistant 记录。
- 因此没有证据表明仍有真实模型调用或活工人在推进任务。

本轮继续只读定位源码后，可以把根因缩到 **print 收尾与异步通知的生命周期竞态**：

- 最后模型轮次正常 `stop` 后，`11:39:32.154Z` 的派单通知已写入旧会话。
- `waitForBackground()` 在“没有后台工作”的路径直接返回，没有冻结通知入口，也没有建立“此后不得再受理新轮次”的关闭门。
- 随后 print 进入 `finally`，最终 `dispose()` 先发 `session_shutdown(reason="quit")`，直接释放后台端口并使旧扩展上下文失效；它没有先 `abort()` 并等待已经受理的轮次。
- 工作流桥接在该 `session_shutdown` 中落成“主会话关闭，须显式人工恢复”。

这能证明以上源码竞态客观存在，也能解释现有事件外形；但运行记录没有保存这次通知的具体 caller、通知时是否已执行 `_runAgentPrompt`、关闭时是否存在 deferred action，以及 `session_shutdown` 的准确触发调用点。故 r11 的实际交错仍是**高可信推断，不是已经逐事件确认的事实**。

`stale` 文案不能证明发生过 `new/resume/fork/reload`。`AgentSession.dispose()` 在任何最终销毁路径都会 invalidate 旧扩展 runner，并复用同一条通用 stale 文案。现有证据只能确认旧上下文在会话文件最后一次写入后失效。

## 根因判断

已确认部分：

- 工作流暂停由 `session_shutdown` 触发。
- 主控业务进程和部长、worker 已经停止。
- 最后模型轮次在 11:39:31 正常结束。
- 派单通知后的模型轮次没有建立，旧扩展上下文随后持续报错。
- 外层 Node 和日志管道仍在，不能等同于任务仍在运行。

推断部分：

- 11:39:32 的派单通知进入了一个正在退出或已替换的主会话边界。
- 旧扩展回调仍持有已失效的 session context，因此在关闭和通知竞争期间反复报错。
- 旧上下文回调或仍在重连的网络句柄可能让 Node 事件循环没有自然清空，导致外层 trial 继续等待。

尚未确认：

- 触发关闭的具体是正常收场、reload、new、resume 还是 fork。
- 哪一段扩展回调在会话处置后仍在运行。
- TCP 连接由具体哪个残留对象维持。
- 11:39:32 通知的具体 caller，以及旧会话是否已经为该通知启动或延迟了一轮。
- 最终 `dispose()` 与通知的确切先后次序。

现有证据不支持把测试暂停归因于 worker 失败、任务时限、Docker `pause` 或模型主动结束。

## 源码竞态：为什么流程会自行收尾

这一节描述的是源码允许发生的交错。它是通过真实函数、真实后台计数和真实通知面定位出的**可复现实例**，不是把 r11 未保存的调用顺序补写成事实。

### 1. 最终空闲检查与销毁之间存在开放窗口

- `PAO/packages/coding-agent/src/modes/print-mode.ts:124-157`
  - `waitForBackground()` 读取一次 `snapshot()`。
  - 若 `running === 0 && unread === 0` 且 session idle，它只额外调用一次 `waitForIdle()`。
  - 此时 `waitForIdle()` 在 `agent-session.ts:2410-2415` 因 `isIdle === true` 立即返回。
  - 返回前没有再次读取后台信号版本，也没有将 session 标记为 closing。
- `print-mode.ts:178-208`
  - 随后打印最终输出。
  - 进入 `finally` 后才由 `disposeRuntime()` 设置局部 `stopping/disposed`。

局部 `stopping` 只停止 print 自己的循环，不能阻止通知面在这段窗口内受理新通知。

### 2. 通知会同步触发唤醒，也可能进入 settled 延迟队列

- `PAO/packages/coding-agent/src/pao/worker/notify.ts:136-164`
  - `notify()` 先把通知放入 buffer，发出 `added`，随后对非 `progress` 通知调用 `wake()`。
- `notify.ts:65-73`
  - 唤醒消息使用 `triggerTurn:true, deliverAs:"followUp"`。
- `PAO/packages/coding-agent/src/pao/index.ts:363-364`
  - 主控共享通知面的 wakeUp 是 `sendDispatchNotifyWakeup(pi)`。
- `PAO/packages/coding-agent/src/core/agent-session.ts:2256-2282`
  - session 空闲时，`sendCustomMessage()` 会直接调用 `_runAgentPrompt()`。
  - 若正处于 `_isEmittingAgentSettled`，则把动作压入 `_deferredSettledActions`，稍后执行。
- `agent-session.ts:1776-1794`
  - `_runAgentPrompt()` 在第一次 `await` 前同步设置 `_isAgentRunActive=true`。

所以“isIdle 曾经为真”不能保证通知到达后仍没有新轮次。反过来，报文已保存也不证明它一定启动了模型：可能是 `agent_settled` 延迟动作，也可能在真正调用模型前被销毁。

### 3. 最终 dispose 没有先收敛已受理轮次

- `PAO/packages/coding-agent/src/core/agent-session-runtime.ts:168-180`
  - 会话替换路径 `teardownCurrent()` 的顺序是：`await session.abort()`，再发 `session_shutdown`，再释放端口并 invalidate。
- `agent-session-runtime.ts:406-414`
  - 最终 `dispose()` 的顺序是：先发 `session_shutdown(reason="quit")`，释放后台端口，再 invalidate 和 `session.dispose()`。
  - 没有先 abort，也没有 `await session.waitForIdle()`。
- `PAO/packages/coding-agent/src/core/agent-session.ts:1364-1384`
  - `session.dispose()` 会 abort agent，随即 invalidate runner 并断开事件监听。

`agent.abort()` 是同步发出中止信号。它不能阻止通知在 `session_shutdown` 前被受理，也不能替代“等待已开始轮次收敛”。

### 4. 后台计数清零与通知之间存在顺序差

- `PAO/packages/coding-agent/src/core/background-work.ts:9-60`
  - 后台工作条件为 `running > 0 || unread > 0`。
- `PAO/packages/coding-agent/src/pao/runtime/background.ts:79-92`
  - snapshot 合并 worker、workflow、fanout、host 的在途数和通知未读数。
  - `waitForChange()` 有版本号保护“读快照后、开始等待前”的变化。
- `PAO/packages/coding-agent/src/pao/workflow/tools.ts:459-475, 525-528`
  - `settleChain()` 先 `notify()`。
  - 后台链的 `finally` 随后才删除 `chainInFlight`、触发背景变化并完成受理 Promise。
- `PAO/packages/coding-agent/src/pao/worker/index.ts:1095-1102`
  - worker 派发链同样是先完成通知，随后才删除 `inFlight` 并通知背景变化。

版本号只能守住一次“等待尚未开始”的遗漏。最终收尾路径没有使用同一版本号建立关闭门，因此仍可在“三处计数均为零”的交错中受理通知。

### 5. 并发交错

可用以下真实事件序列复现：

| 序号 | 事件 | 结果 |
|---|---|---|
| 1 | 最后 assistant 正常停止，workflow/worker 的 `finally` 即将清零计数 | print 进行空闲检查 |
| 2 | `waitForBackground()` 读到 `running=0, unread=0` | 第二次 `waitForIdle()` 立即返回 |
| 3 | 后台链执行 `notify()`，通知面先 buffer 再 wake | 唤醒消息可能开始或延迟一轮 |
| 4 | print 打印最终文本并进入 `finally` | 尚无关闭门阻止事件 |
| 5 | `runtimeHost.dispose()` 发 `session_shutdown(reason="quit")` | 工作流被置为挂起 |
| 6 | release port、invalidate、session dispose | 已受理轮次或 deferred action 接触旧 runner，可能继续报 stale 或 `turn_end` 条目缺失 |

运行侧已确认步骤 1 的最后 assistant `stop`、步骤 3 的通知落盘，以及步骤 5 的结果。步骤 2、4、6 的具体先后来自源码能力与上述时间外形，尚未被运行日志逐点记录。

## 最小修复研究（尚未改代码）

主方案是一个真实的会话关闭门，再加最终等待。关闭门解决并发生命周期，不是为未来扩展预留的抽象。

> 2026-10-24 后续状态：主控已授权实施，最小修复实际落在 `agent-session.ts`、`agent-session-runtime.ts` 和 `print-mode.ts`。五项独立机制已收敛为“一个会话/runtime 关闭门 + 正确收敛顺序”，没有修改 background、worker 通知、intake、host、workflow、minister 或 `pao/index`。实际改动、验证命令和残留局限见同目录 `r11生命周期修复-20261024\实施报告.md`。本节以下保留为调查当时的建议和推理，不再表示代码尚未修改。

### 建议修改点

1. **在 `AgentSession` 增加 closing 状态**
   - 位置：`PAO/packages/coding-agent/src/core/agent-session.ts`
   - 在收尾开始时原子地设置 closing。
   - `prompt()`、`sendUserMessage()` 和 `sendCustomMessage(triggerTurn:true)` 在 closing 后拒绝创建新轮次。
   - `_emitAgentSettled()` 不再把新动作放入 `_deferredSettledActions`；关闭时清空未执行动作，并让已等待方得到明确结束结果。
   - 已受理轮次仍可正常收敛，避免把正常关闭误当成工作流失败。
   - `sendUserMessage()` 当前只是转调 `prompt()`；关闭检查集中放进 `prompt()` 即可覆盖，不另维护两份状态判断。

2. **让最终 dispose 与替换路径拥有同一收敛顺序**
   - 位置：`PAO/packages/coding-agent/src/core/agent-session-runtime.ts:406-414`
   - 顺序改为：先关闭新轮次入口；停止通知面继续唤醒旧 session；`await session.abort()` 或等待已受理轮次；再发 `session_shutdown`；最后释放端口、invalidate 和 dispose。
   - 这是把已有 `teardownCurrent()` 的生命周期规则复用到最终退出，不新增另一套停止协议。

3. **print 只在拿到稳定关闭门后进入 finally**
   - 位置：`PAO/packages/coding-agent/src/modes/print-mode.ts:124-208`
   - `waitForBackground()` 返回前，以 `BackgroundWorkSignal.currentVersion` 封闭最后一次快照：若版本已变化，继续等待和处理。
   - 版本稳定后，在同一同步边界设置 closing，再打印与销毁。
   - `disposeRuntime()` 中的局部 `stopping/disposed` 不足以承担这个职责，因为它只影响 print 自己的循环。

4. **通知面与后台 host 使用同一个关闭时代**
   - 位置：`PAO/packages/coding-agent/src/pao/index.ts`、`runtime/background.ts`、`worker/notify.ts`
   - 正常收尾开始时先让通知面停止接受新通知和主动唤醒。旧异步任务晚到的通知应丢弃或保留给下一会话，不能唤醒已关闭的旧 session。
   - `background.shutdown()` 当前只解绑 signal，不主动关闭共享通知面；需要由上层收尾边界统一调用。

5. **保留一个事件级诊断字段**
   - 为 `session_shutdown` 诊断记录 `reason`，并为被拒绝的 closing wake 记录通知类别与 session 标识。
   - 只增加能回答“为何没有启动”和“谁在关闭后尝试唤醒”的字段，不把模型正文或凭证写进日志。

不能只修其中一处：只加版本复检仍可能在末次检查后收到通知；只先 abort 仍可能在 abort 与 invalidate 之间受理新事件；只关闭 notifySurface 不能撤回已调用的 `sendMessage` 或 deferred action。

## 对“为什么测试暂停、是不是 harness 问题”的直接回答

- **不是系统或 Docker pause。** 容器是 running、paused=false；外层 trial 只是尚未结束。
- **不是普通工作流业务失败。** 工作流因主会话关闭事件而挂起。
- **是流程进入收尾，但收尾边界有并发缺陷。** print 无后台工作时会自行销毁运行时；最终销毁路径又未先封闭新轮次。
- **暂时不能把 harness 判为根因。** 外层 harness 的等待是结果；当前证据指向 coding-agent 的 print 收尾、通知唤醒和 session 生命周期竞态。
- **也不能把 11:39:32 的通知称为已确认的模型重启。** 运行证据只保存了通知，没有保存它是否在销毁前真正启动轮次。
