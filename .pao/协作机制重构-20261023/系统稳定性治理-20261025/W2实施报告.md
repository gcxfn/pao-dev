# W2 宿主装配核查与关闭失败处置实施报告

## 结论

截至 2026-10-25，W2 生产源码可以冻结供 W6 构建。本轮确认并修复了“关闭失败后会话仍存活，但观察、通知、查询状态或资源身份已经提前销毁”的装配缺口。修复统一复用现有 `session_shutdown` 与 `onConfirmedShutdown`，没有新增能力框架、权限边界或终止机制，也没有重置 WorkerRunner、WorkflowHostBridge 的永久停止语义。

内核生产类型检查 `tsc --noEmit -p tsconfig.build.json`、包含测试源码的根 `tsc --noEmit`、拥有文件 Biome、以及内存与真实 Runner 定向测试均通过。桌面代际原测试通过。MCP 强化故障测试由 Locke 独立完成，报告只合并其结果，不保留本轮曾新建的重复夹具。

## 实际生产改动

### 关闭失败后保留会话装配

- `src/pao/host/tools.ts`：`unsubscribeToolEnd()` 与 `host.stopTracking()` 一起延后到确认关闭。
- `src/pao/index.ts`、`src/pao/worker/index.ts`、`src/pao/runtime/background.ts`：后台观察、通知来源、静默监督和会话装配的查询/监听清理延后到确认关闭；旧式无参关闭事件保留立即清理 fallback。
- `src/pao/desktop/owners.ts`：owner 身份延后到确认关闭后遗忘，旧式 fallback 保留。
- `src/pao/todo/index.ts`、`src/pao/context/index.ts`、`src/pao/worker/usage-display.ts`、`src/pao/fanout/index.ts`、`src/pao/workflow/tools.ts`、`src/pao/memory/resident.ts`、`src/pao/memory/compaction-state.ts`：可查询现场与用量结账状态延后到确认关闭。失败期间新增用量可在重试成功时一次性进入结账，避免提前落账和重复结账。
- `src/pao/context/precompaction.ts`：已有 adapter 保留显式守卫；解绑仅在该会话确认关闭后执行。这里只修复真实装配边界，没有修改停写策略。

### MCP 与记忆资源关闭

- `src/extensions/mcp/runtime.ts`：连接建立前就保留 `client/transport` 身份；`getClient()` 优先等待正在进行中的装配；启动、禁用或重配清理失败时保留资源，只有两层清理均成功后才清除身份。关闭标记用于阻止资源关闭过程被误判为自然断连。相关强化测试由 Locke 的 `test/mcp-shutdown-failures.test.ts` 提供，新测试 3/3，旧套件 24 过 1 跳。
- `src/pao/memory/mnemosyne.ts`：启动前保留 `client/transport`；`start()` 和 `close()` 的分层清理失败均传播，全部成功后才除身份。`running` 在 close 开始时立即关闭，旧 client 不能继续执行记忆业务；失败资源保留给同一会话重试。
- `src/pao/memory/memory-vendor.ts`：关闭轮串行化，在途启动与清理错误聚合；清理失败时保持 `shutdownRequested`，阻止同轮 `acquire()` 取用正在关闭的资源。关闭重试成功后才允许下一会话重新获取，并发 `acquire()` 不会拿到正在关闭的 vendor。
- `src/pao/memory/index.ts`：等待 manager 关闭，错误向上传播并留下结构化警告，不再静默吞掉。

## 确认正确、未改业务规则

- 人工门与独立审核必要能力 guard 已存在，同一 host 注入正确；未把猜测改成缺陷，也未删除公开默认 host 或可选降级。
- WorkerRunner 的 `stopAll` stopSignal 与 WorkflowHostBridge 的 `closing` 都是永久全停语义。失败后仍可重试停止和查询现场，但不会自动恢复旧任务或重置取消信号。
- Desktop extension bridge 的当前 active generation 在会话关闭事件到达时立即撤销能力，这是现有契约；异步清理失败只意味着底层资源尚可重试关闭，不能宣称资源已全部关停。
- `precompaction.stopAndDrain()` 的五秒等待是既有政策。超时会记录“取消等待超时，费用未知”后放行确认关闭，因此**无法证明超时后的后台摘要生成已经排空**；不能把该函数称为全部后台写入已停止。本轮没有扩大成永久等待或新终止策略。

- Runner 新例使用真实 `ExtensionRunner`、`SessionManager`、事件分发和 todo/owner/context/usage 接线；用量通过 `runner.emit({ type: "agent_end", ... })` 的真实原生事件入口刷新，模型、用量消息与业务中断仍是模拟数据，不是实际两次模型请求。

- 双会话测试证明真实内核实例、通知、取消和模型配置映射隔离；没有证明两个真实模型请求并发时的供应商行为。
