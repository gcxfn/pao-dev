## 生产行为

### verifier 身份与观察范围

- `watch_run.py` 使用 `bench_controller.compose_project(trial, "verifier") + "__trial"`，与真实 Harbor 项目名一致。
- 真实试次只从 `jobs/<job>/<trial>/config.json` 读取；`jobs/<job>/config.json` 只作为 JobConfig，不冒充试次。
- 当前阶段必须出现的身份保存为 `planned_identities`；本轮已创建并需要持续观察的身份保存为 `observed_identities`。
- 正式阶段不会丢掉预检遗留容器。预检 env 仍 Running 时，即使正式 env、verifier 和控制器都已退出，也不签停写。
- 评分容器 `pao-score-<runsha>` 始终按本轮固定名称纳入发现；即使 `current-score/result.json` 已完成，只要容器仍活跃也不终局。
- 真实验证器缺失、容器身份不明或 Docker 查询失败时，`scope_complete` 不能成立，不写全停回执。
- 所有本轮实际写入者已停止后，非零控制器退出可收终局并记录 `controller_crash`，保留已有官方奖励和原异常，不改写业务控制状态。

### 奖励收证

- 有效有限数值保留，包括真实 `0.0`。
- 缺失、坏格式、布尔值、字符串、`NaN`、`Infinity` 分别保留原始状态；序列化使用 `allow_nan=False`。
- JSON 根为数组、布尔或 `null` 时记 malformed，并继续读取其他评分文件，不因一份坏结果丢全部收证。
- 官方奖励只从 `jobs/*task-*/<trial>/result.json` 的 `verifier_result.rewards.reward` 读取。
- 缺有效正式奖励不填 0。终局回执分别记录 `official_rewards=[]`、`official_reward_status`、`reward_rows` 和 `reward_errors`。

### 首错与清理错误

- `runner_common.command_evidence()` 是命令输出 JSON 安全的唯一转换点：文本原样保留，`bytes` 转成带 `encoding=base64` 和 `data` 的结构。`bench_controller.command()` 不再保留重复的 bytes 转换。
- `bench_controller.command()` 把命令原始 `stdout`、`stderr`、`returncode` 和阶段写入 `command-evidence.jsonl`；超时和进程启动异常也记录 `returncode=null`、阶段和已取得的输出，并原样重抛同一异常实例。
- `observe_runtime()` 的实际 `docker ps/cp/exec/inspect` 边界全部复用 `command()`，不再绕过证据记录。二进制 tar 保持 bytes 写入 `supervision-last-control.tar`；证据文件把 bytes 用 base64 和编码标记保存，避免损坏或无记录。
- 控制器测试的 Docker 假程序不再只生成 Windows `.cmd`：Windows 生成转发到当前 Python 的 `.cmd`，其他系统生成带当前 Python shebang 的可执行文件。超时用例读取假程序实际 PID，并确认该次子进程在断言结束前退出。
- `classify_result()` 直接复用 `runner_common.finite_number()`；字符串、布尔、NaN、Infinity 仍视为缺失有效评分，真实 `0.0` 仍为完成。
- 执行失败后的停机核查仍有单独 `runtime_stop_check` 证据；执行失败和停机查询失败同时发生时使用 `BaseExceptionGroup` 保留两项原异常。
- Harbor 业务错误与 Docker 清理查询错误可以同时进入 `BaseExceptionGroup`。
- `run_sequence()` 保留首个业务错误阶段，业务、取消、超时和清理错误可同时存在；观察错误与任务收尾错误并存时先写入 `stop_unconfirmed`，外层通用异常路径不再覆盖首错。
- `score_current()` 的业务错误和评分容器清理错误可同时保留，且只在成功分支写一次评分结果。
- `watch_run.query()` 同样复用 `runner_common.command_evidence()`；非零退出、`TimeoutExpired` 和 `OSError` 的 `watch-error.json` 保存阶段、argv、返回码和原始输出。POSIX 下即使使用 `text=True`，超时异常仍可能携带 `bytes`；该路径现在可写入 JSON，且保留同一异常对象及其原始 `output`/`stderr`。

### 启动、共享契约与用量

- `launch_run.py` 的 Docker 子进程显式接收传入环境，凭证只经环境传入，不写 argv 或回执。
- 控制器启动同时保留 `D:/AI/workspace → /mnt/d/AI/workspace` 与配置 `local_root → container_root` 两条职责不同的挂载。
- 启动回执分别记录控制器 tag、实际 image ID、解释器容器路径、宿主来源摘要和字节数。image ID 查询使用 `docker inspect --format "{{.Image}}"`。

## W1 只读审计结论

在 2026-10-25 当前工作树上核对后，未发现需要重新列为 K2/K3 未修的代码证据：

- K2：`PAO/packages/coding-agent/src/pao/shared/atomic.ts:13-42` 只使用同目录临时文件加 `renameSync`；占用类错误重试三次，失败后只清理临时文件并重抛，未退回普通覆盖。`test/pao/shared-state-failures.test.ts:58-124` 已用真实文件、并发读线程和注入的 `EPERM`/`EACCES`/`EIO` 验证旧正本保持完整；替换与清理同时失败时 `AggregateError.errors` 保留两错。断电安全仍未验证且不应由该测试外推。
- K3：`PAO/packages/coding-agent/src/pao/shared/lock.ts:72-88` 在业务异常时释放锁，释放也失败则用 `AggregateError` 保留两错；业务成功而释放失败时，释放异常传到调用者。`test/pao/shared-state-failures.test.ts:126-151` 已覆盖业务失败/成功与释放失败/成功的四种组合，并核对每次恰好释放一次。
- K1 主路径：`PAO/packages/coding-agent/src/pao/intake/accept.ts:339-530` 将每个请求收敛为一个 `IntakeOutcome`；形状错误、坏账、占位写失败、建卡读取失败、转正失败、撤回失败和派发失败均有真实原因与已知身份。`test/pao/intake-accept.test.ts:165-277` 覆盖坏账、占位失败、转正失败、撤回失败和卡读取失败，并证明批次继续及 pending 防重复；`:444-500,503-612,615-779` 覆盖部分受理、重试和重复派发保护。

剩余的真实维护缺口在错误细节保真：

1. `accept.ts:99-119` 的派发账补写失败只保留 `String(error)`，`IntakeLedgerError.details`、原始 `cause` 和锁定/写入错误分类会丢失。触发条件是卡已建、派发通道已调用，随后 `updateIntakeEntry` 遇到锁超时或账写失败。现有 `intake-tool.test.ts:426-484` 只断言警告文字和未知派发状态，没有断言结构化错误原件。最小方案是复用 `IntakeOutcome.problems` 已有契约，在 `reason`/问题项中保留 `error.name`、`code` 和 `message`；如确实需要机器读取，只追加一个可选错误详情字段，不建新错误框架。验收应直接调用 `acceptIntake`，分别注入 `LOCK_TIMEOUT`、`WRITE_FAILED` 和账文件写入后的锁释放失败，核对卡身份、实际派发布尔值及原始错误分类仍在同一条 outcome。
2. `accept.ts:474-486` 的转正失败和 `:520-530` 的兜底只读取 `(error as Error).message`/`String(error)`。若 `writeFileAtomic` 同时发生替换失败与临时文件清理失败，`AggregateError.errors` 中第二个异常只可能进入 `message`，调用者无法稳定读取两项原件。触发条件是建卡成功后受理账转正时出现替换与清理双故障。现有 `intake-accept.test.ts:230-255` 只抛普通 `Error("模拟转正失败")`，没有注入 `AggregateError`。最小方案是在原 outcome 的 `reason` 中保留聚合错误名称与两个子错误的可区分文本，或采用上一条同一个可选结构化错误字段。验收应以真实隔离账文件注入双故障，确认卡与 pending 保留、不同步派发，并可从 outcome 定位两个原错误。

上述两项属于错误可查性增强，当前代码没有伪造成功：建卡身份会保留，受影响的条目会 rejected/带警告。W1 本轮按要求只读，没有修改源码或新增测试；因此该段只列审计结论，不声称修复已通过。
