# 工作包 L：关闭失败修复报告

记录时间：2026-10-25。状态：本轮源码与定向故障验证已完成；最终生产构建、真实 Electron 退出、整合审核与提交由主控接管。

## 结论

关闭失败现在会沿内核、共享 SDK 和 desktop 返回，而不会被改写成 `idle`、`closed` 或成功 `sessionClosed`。已经确认停止的会话仍按原成功契约完成清理；未确认的会话保留运行时、会话、执行控制权与租约，并保留下一次关闭入口。

修复集中在单次 `session_shutdown` 事件内的共享结果和既有状态上：全部关闭处理器先获得执行机会，任意失败就聚合抛错；只有该事件全部成功后才执行已登记的确认清理。没有新增持久 `StopProof`、跨事件状态机、参与者注册或通用生命周期总线。

## 实际行为与接口契约

### PAO 内核

- `ExtensionRunner.emit()` 保持普通事件的隔离语义；对 `session_shutdown` 汇总每个失败处理器后抛出 `AggregateError`。关闭事件的 `onConfirmedShutdown(cleanup)`（`PAO/packages/coding-agent/src/core/extensions/runner.ts:1089`）只登记本事件的清理；`PAO/packages/coding-agent/src/core/extensions/types.ts:801` 定义了可选回调。
- 部长 `MinisterHost.stopAll()` 遍历全部登记会话，先记录成功对象，再汇总失败。失败句柄继续留在登记表，仍可重试（`PAO/packages/coding-agent/src/pao/host/host.ts:1620`）。返回成功对象数组的既有契约保持不变。
- worker 关闭同时尝试 worker 和部长停止；任一失败时上抛聚合错误。`host.stopTracking()` 与退出钩子释放登记到最后确认清理（`PAO/packages/coding-agent/src/pao/worker/index.ts:1161`）。
- owner 锁和后台端口同样延迟到确认清理（`PAO/packages/coding-agent/src/pao/runtime/index.ts:97`、`PAO/packages/coding-agent/src/pao/index.ts:399`）。部长没有登记时，不会因为缺少“必需参与者”而无法关闭。
- `AgentSessionRuntime.dispose()` 失败会清除拒绝中的缓存 Promise，关闭窗口仍保持；下一次可以重新执行并成功，成功后继续幂等（`PAO/packages/coding-agent/src/core/agent-session-runtime.ts:409`）。
- `reload()` 先进入关闭状态；旧 shutdown 失败时保持关闭。新 runtime 装配完成后、`session_start` 钩子之前恢复接收工作，因此启动钩子合法排队的消息不会被误拒绝（`PAO/packages/coding-agent/src/core/agent-session.ts:3734`、`:3761`）。
- `processInvocation` 三处公共装配属于主控改动，本轮没有修改；本轮只保持与其兼容。

### 共享 SDK 与 desktop

- `SessionSupervisor.closeSession()` 在开始关闭时拒绝新工作；成功后才清理 UI 请求、写 `idle/closed`、持久化、发送 `sessionClosed` 和释放租约。失败记录保持 `stopping`、runtime、session 与原租约，并保留 `closeError` 供重试（`desktop/packages/pi-sdk-driver/src/session-supervisor.ts:1965`、`:2211`）。并发关闭复用 `closePromise`。
- `disposeAll()` 尝试全部会话；部分失败不阻止其他会话清理，最终抛出聚合错误（`desktop/packages/pi-sdk-driver/src/session-supervisor.ts:2028`）。`PiSdkDriver.disposeAll()` 对其他 SDK 资源也采取先尝试、后汇总（`desktop/packages/pi-sdk-driver/src/pi-sdk-driver.ts:171`）。
- `QuitSessionStopCoordinator` 只缓存尚未结束的真实停止；成功、失败或超时后，真实操作一旦结束就清除引用，下一次退出会检查当前会话。后台停止未结束时，重试仍复用同一操作（`desktop/apps/desktop/electron/lifecycle/quit-session-stop.ts:6`）。
- `before-quit` 分开使用 15 秒受管停止预算和 5 秒持久化预算。停止或持久化失败、超时都会复位退出尝试；只有两者成功后，才销毁 extension views、停止应用服务、排定 relaunch 并调用 `app.quit()`（`desktop/apps/desktop/electron/main.ts:1493`）。`window-all-closed` 不再提前停服务（`:1476`）。
- 工作流退出检查失败或未获批准时，会复位 `quitLeaveApproved`，下一次退出重新检查当前场景，不能复用旧批准。

## 追加：工作树原始字节与规范化过滤器核查

主控串行恢复期间追加的窄审查确认了两个方向相反的真实缺口，并已在 desktop 工作树宿主收敛修复。没有运行测试，避免与四部门恢复检查并发。

### 确认结论

- `recoverPending()` 原先在 `pao-worktree-host.ts:487` 以临时索引执行 `git add -A` 后与 raw snapshot tree 比较。`git add` 会应用 `core.autocrlf` 和 `.gitattributes` clean 过滤器，所以工作目录原始 CRLF 与基线原始 CRLF 虽然相同，仍可能因保存的索引对象是 LF 而误拒绝。
- 同一恢复路径还缺少 raw capture，因此工作目录被改成 CRLF、而 `git add` 把 CRLF 规范化为与基线相同的 LF 时，会被错误接受为“已完整落地”。旧检查既会误拒绝合法基线，也会漏过原始字节偏差。
- `createNow()` 在 `:539` 的 raw capture 已用 `checkpoint-store.ts:581` 的 `hash-object --stdin-paths --no-filters` 验证精确原始字节，随后 `:545` 又执行同一规范化 `git add` 检查，属于重复且方向错误的校验。源文件是 CRLF、仓库启用 `core.autocrlf=true` 的合法场景会在这里失败。
- 这两条路径都受影响，且 `inspectCheckoutTree` 当时只有这两个调用者。只关闭 `core.autocrlf` 还不够，`.gitattributes` 的 text/eol 规则和其他 clean filter 仍会改变对象；应直接使用已有 raw capture。

### 改动与接口契约

- 修改 `desktop/apps/desktop/electron/platform/worktrees/pao-worktree-host.ts`：
  - 恢复路径 `:487` 改用现有 `options.checkpoints.capture()`，再以 `requireUnchangedCapture()` 做完整覆盖检查及 raw tree 精确比较。失败仍以“内容尚未完整落地、保留现场待盘点”上抛。
  - 创建路径 `:546` 保留唯一一次 raw capture 比较，删除之后重复的规范化比较。
  - 删除仅剩这两个调用者的 `inspectCheckoutTree()`；同时保留 `inspectLinkedWorktree()`、来源仓库目录检查、应用工作树登记检查、分支与 Git 身份检查、`requireBaselineRecoverable()` 快照对象和文件清单校验、创建后来源未变化检查。
