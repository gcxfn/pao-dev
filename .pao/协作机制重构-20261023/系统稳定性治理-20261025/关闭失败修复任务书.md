# 工作包 L：关闭失败修复任务书

记录时间：2026-10-25

## 目标

让真实的 worker、部长或 runtime 停止失败沿 PAO 内核、SDK 和 desktop 边界可见。失败时不能把会话伪装成 `idle` 或 `closed`，不能发送成功 `sessionClosed`，不能提前释放租约；失败会话必须保留可重试的停止入口。所有成功路径和正常退出体验保持不变。

本工作包不处理 `processInvocation` 公共装配，不增加通用关闭框架、持久化 `StopProof` 或新的审批流程。

## 当前基线与风险

- PAO 的 `WorkerRunner.stopAll()` 已会拒绝，但 `session_shutdown` 使用 `Promise.allSettled` 后丢弃拒绝。
- `MinisterHost.stopAll()` 已保留停止失败的句柄，但只发通知，返回数组里看不出部分失败。
- 通用 `ExtensionRunner.emit()` 为兼容普通扩展事件会捕获并隔离每个处理器异常。不能把普通事件统一改成抛错。
- `AgentSessionRuntime.dispose()` 会缓存 Promise；当前实现若某次 dispose 拒绝，后续重试只会拿到同一个拒绝。
- desktop 的 `closeSession()` 先设置 `closed=true`、`idle`，再吞掉 abort/dispose 异常，随后仍发送 `sessionClosed`。
- desktop 退出路径把停止失败降级成日志，并在 5 秒期限后无条件退出。

## 实施边界

### PAO

1. `MinisterHost.stopAll()`
   - 逐个尝试全部会话，不让单会话失败阻断其余会话。
   - 成功散场记录仍作为返回数组元素，保持成功对象契约。
   - 任一失败时汇总成 `AggregateError`；失败句柄继续留在登记表，可再次调用 `stopAll()`。
   - 错误中保留 pid、部门、原因等定位信息，不用裸字符串取代已有记录。

2. `session_shutdown`
   - 所有 `session_shutdown` 处理器仍都获得执行机会。
   - 该事件处理器抛错时汇总到 `AggregateError` 并向 runtime 传播。
   - 普通 `emit()` 事件继续逐个隔离异常并上报 `onError`。
   - 关闭事件携带本次事件内的共享停止状态。worker 在开始受管停止时登记停止条件，只有 worker 与部长均确认停止后才标记成功。
   - owner 锁、部长活动跟踪、退出钩子等释放动作登记到“全部处理器结束且停止已确认”后才执行的清理队列；失败时全部保留，后续关闭可重试。
   - `runtime/index.ts` 的 `session_shutdown -> state.release()` 必须受该状态门控；`state.acquire()` 内正常换会话的释放不变。
   - 只有 worker 与部长都停止成功，才调用 `host.stopTracking()` 并释放 `disposeExitHooks`。
   - 通知面关闭和静默提醒器停止是本地释放，可在停止尝试前执行；失败时保留可重试的受管子进程入口。

3. `AgentSessionRuntime`
   - `dispose()` 首次失败后清除缓存的拒绝 Promise，使后续关闭可重试。
   - 关闭窗口在开始时就保持关闭，失败重试时仍拒绝新任务。
   - 成功后的 dispose Promise 保持缓存，重复成功关闭幂等。

4. `pao/index.ts` 关闭装配
   - `stopObservingActivity()` 是活动观察订阅的本地清理，可提前执行。
   - `workflowBridge.shutdown()` 实际承担部长会话全停，失败须继续向关闭事件汇总。
   - `releaseBackgroundHost()` 只释放后台等待端口，不拥有执行进程、控制锁或 session lease，可提前执行。
   - `installPaoWorktreeHost()` 只安装扩展对象上的宿主适配器，没有对应关闭释放动作，不新增清理。
   - 保留主控刚完成的 `processInvocation` 三处修改，不在本工作包改动该公共装配。

### desktop

1. `SessionSupervisor.closeSession()`
   - 不在停止确认前写 `closed=true`、`idle`、清运行 ID 或取消待处理 UI 请求。
   - abort 失败、runtime dispose 失败或 PAO shutdown 汇总失败都保留为失败。
   - 失败时不持久化“已关闭”快照、不发送 `sessionClosed`、不释放租约。
   - 记录保留错误和“正在关闭/关闭失败”状态，拒绝新 prompt 和重复启动 runtime，同时允许再次调用关闭。
   - 一个会话失败不阻止 `disposeAll()` 清理其他会话；最终汇总失败。
   - 成功时继续执行现有 abort、unsubscribe、dispose、租约释放、快照持久化和 `sessionClosed`。

2. 应用退出
   - 正常停止成功时保持现有退出体验。
   - `app.relaunch()`、`stopAppServices()` 等不可逆或破坏重试条件的动作只能在 session stop 和必要持久化成功后执行。失败时保留 relaunch 意图，不提前排定重启或停光服务。
   - 现有 5 秒只作为草稿和持久化 deadline，不能短于 worker 的 2 秒树杀加 10 秒退出确认。受管停止另设与现有预算相容的明确期限。
   - 停止失败或超时时不得继续 `app.quit()` 伪称成功，也不得释放租约。保留应用与失败记录，给出明确“未确认停止，可重试关闭”的错误信息；不新增批准对话框或自动续跑。
   - 后台停止 Promise 尚未结束时，再次关闭必须复用同一关闭操作，不能并发启动第二轮 dispose。

### 测试

- worker `stopAll()` 拒绝且部长也失败时，两者都被调用，`session_shutdown` 抛出汇总错误，控制资源未被提前释放。
- 普通扩展事件处理器抛错仍隔离，不改变通用 emit 契约。
- runtime 首次 dispose 拒绝后，第二次 dispose 能重新执行并成功；关闭窗口持续拒绝新任务。
- desktop 停止失败不发 `sessionClosed`，记录不进入 `closed/idle`，租约不释放，后续 prompt 被拒绝，重复关闭可成功。
- `disposeAll()` 中一个会话失败时，其他会话仍被清理，最终抛出汇总错误。

## 退出政策取舍

停止失败或超时时保留应用并报告未确认停止，会让用户需要再次关闭；收益是避免把“父进程断开后异步自树杀”当作已经优雅停写。正常关闭成功时不会多出确认步骤。该取舍同时取消现有 5 秒后的无条件退出，避免回执、证据或账本仍在写入时被截断。
