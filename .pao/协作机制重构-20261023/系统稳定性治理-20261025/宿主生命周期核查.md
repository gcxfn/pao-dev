## 重点发现

### 1. 底层停止失败被关闭层吞掉，桌面仍可能宣布成功关闭并退出

**等级：高；确认失败传播与成功事件，进程是否存活或写入是否截断为推断。**

**触发条件**

- 手工关闭桌面会话、退出应用，或 `new`、`resume`、`fork`、`reload` 替换当前会话时，任一 worker 或部长子进程的树杀失败、退出确认超时，或运行时 `dispose()` 失败。
- 退出时 `disposeSessions()` 超过 5 秒，或者某个 runtime 的 `abort()`、`dispose()` 抛错。

**路径与行号**

- `WorkerRunner.stopAll()` 会汇总失败并抛出 `PaoWorkerError("停止失败")`，而且失败时不会签发放锁凭据：`PAO/packages/coding-agent/src/pao/worker/runner.ts:1312-1336`。其停止链会先树杀，再最多等待 10 秒确认子进程退出；未收到退出确认同样抛错：`runner.ts:248-267,586-597`。
- `MinisterHost.stopAll()` 对每个部长会话单独捕获失败、保留句柄并通知，但最终只返回成功散场记录，没有把失败聚合到返回结果：`PAO/packages/coding-agent/src/pao/host/host.ts:1622-1637`。
- PAO 扩展的 `session_shutdown` 处理器用 `Promise.allSettled([runner.stopAll(), host.stopAll(...)])` 等待两者，却完全不检查 settled 结果，随后继续 `stopTracking()` 并返回成功：`PAO/packages/coding-agent/src/pao/worker/index.ts:1161-1168`。`ExtensionRunner.emit()` 也会捕获处理器异常并只上报错误，不把异常返回给关闭调用者：`PAO/packages/coding-agent/src/core/extensions/runner.ts:1089-1118`。
- desktop 的 `closeSession()` 先把记录设为 `closed=true`、状态设为 `idle`，再吞掉 `abort()` 异常：`desktop/packages/pi-sdk-driver/src/session-supervisor.ts:1950-1969`；`disposeRecordRuntimeSafely()` 又只打印 `dispose()` 失败：`session-supervisor.ts:2179-2193`。之后它仍持久化快照并发送成功 `sessionClosed`：`session-supervisor.ts:1975-1981`。
- 退出路径把 `disposeSessions()` 的异常降级为日志，并与持久化一起最多等 5 秒；到点后无条件 `app.quit()`：`desktop/apps/desktop/electron/main.ts:321-323,1539-1562`。测试也明确固定了“失败后仍标记全部 closed”的当前语义：`desktop/packages/pi-sdk-driver/test/dispose-all.test.mts:136-158`。

**影响**

- 已确认：内核已有明确的停止失败结果，但该结果不会越过共享扩展边界成为关闭失败；桌面会清除活动状态、写快照、发成功关闭事件并继续退出。调用者无法区分“已停”与“只改了内存状态”。
- 推断：树杀失败时，部长句柄按设计仍保留，但扩展紧接着 `stopTracking()`，桌面记录也已摘除，后续难以通过原会话重试；真实 worker 树可能继续运行。
- 推断：5 秒退出期限会切断正常停止、交接页、回执、证据和用量账的写入；这些写入目前没有“完成证明”和“因超时被截断”的独立结果。
- 父控制通道断开后的自树杀可以兜底异常退出：`PAO/packages/coding-agent/src/pao/worker/parent-lifecycle.ts:7-35`，Windows 真实强杀测试也验证了子进程与孙进程停止写入：`PAO/packages/coding-agent/test/pao/parent-lifecycle.test.ts:53-98`。这条兜底不等于优雅停写证明，而且对成功退出路径而言，其异步树杀也未必在宿主退出前完成。

**最小公共边界修法**

- 在 `paoExtension` 的装配层提供一个关闭协调器，返回结构化结果，例如 `{ stopped, failed: { workers, ministers, other } }`；先收集全部结果，再决定关闭状态。
- `WorkerRunner.stopAll()`、`MinisterHost.stopAll()` 和 workflow/通知面都接入同一结果类型。部长停止失败必须出现在返回结果中，不能只发通知。
- `session_shutdown` 不吞 `stopAll` 失败。`ExtensionRunner.emit()` 的通用异常隔离可以保留，但关闭事件需要单独的失败返回通道，不能只依赖错误监听器。
- desktop 分开“逻辑关闭”和“进程已确认停止”：停止失败时保留记录、租约与错误，不发送成功 `sessionClosed`；退出超时要返回明确的“强制退出，优雅停写未完成”证明。

**已有验证与缺口**

- 已有测试证明关闭窗口期间仍持有控制权、关闭后拒绝迟到请求：`PAO/packages/coding-agent/test/pao/runtime-shutdown-window.test.ts:106-170`。
- 已有测试证明 `WorkerRunner.stopAll()` 树杀失败会抛错并保留执行锁：`PAO/packages/coding-agent/test/pao/worker-dispatch-managed-real.test.ts:409-425`。
- 已有测试证明一个 runtime 停止失败时仍继续关闭其他会话，但它把失败会话也标为 `closed`：`desktop/packages/pi-sdk-driver/test/dispose-all.test.mts:136-158`。
- 未见组合测试覆盖：`runner.stopAll()` 拒绝后桌面事件、记录、租约是否仍显示关闭；`MinisterHost.stopAll()` 部分失败时退出结果；退出期限到点后进程树、交接、回执和账本是否完整。本阶段未运行这些测试。

### 2. `processInvocation` 仍是 worker 与部长分别注入，公共扩展装配无法保证真实执行入口一致

**等级：中；接口缺口与默认路径正确均确认，只有嵌入方自行覆盖入口后才可能触发，未观察到现网错误。**

**触发条件**

- 宿主、SDK、测试夹具或未来发行入口需要把 worker 与部长都绑定到同一个受控 CLI、构建产物或启动器，并通过 `PaoExtensionOptions` 装配 PAO。
- 当前公共装配口没有统一 `processInvocation`，调用者只能分别构造 `WorkerRunner` 和 `MinisterHost`；如果只注入其中一个，另一类子进程仍走 `defaultInvocation()`。

**路径与行号**

- worker 和部长各自定义了同签名的 `processInvocation`：`PAO/packages/coding-agent/src/pao/worker/runner.ts:157-167` 与 `PAO/packages/coding-agent/src/pao/host/host.ts:74-82`。
- 公共 `PaoExtensionOptions` 只接受完整 `runner`、`host` 和 `worktreeHost`，没有 `processInvocation`：`PAO/packages/coding-agent/src/pao/index.ts:105-122`。
- 默认装配分别新建 `WorkerRunner` 和 `MinisterHost`，两者都没有收到统一 invocation：`index.ts:155-166`。
- 两个类实际使用各自的入口：worker 在 `runner.ts:702-704`，部长在 `host.ts:889-891`；默认实现都指向 `defaultInvocation()`：`runner.ts:207-229`。
- desktop 的 driver options 允许传 `paoExtensionOptions`，app store 当前只补 `worktreeHost`：`desktop/apps/desktop/electron/application/app-store.ts:214-222,350-365`；runtime supervisor 原样传给 `paoExtension`：`desktop/packages/pi-sdk-driver/src/runtime-supervisor.ts:531-545`。npm 回落入口也原样传递：`desktop/packages/pi-sdk-driver/src/npm-package-fallback.ts:108-120`。

**影响**

- 当前默认路径没有发现不一致：worker 与部长都调用 `defaultInvocation()`，并且 Electron 缺内嵌构建时都会失败关闭，不会静默回落到 PATH 上的全局 `pao`。
- 公共装配契约没有保证一致性。嵌入方若按类分别注入，worker 与部长可能运行不同版本的 CLI 或不同启动包装器；两边的启动身份、模块装载、关闭协议因此可能不同。
- 这是“真实执行绑定”的组合缺口，不应表述成已在生产观察到双入口故障。

**最小公共边界修法**

- 在 `PaoExtensionOptions` 增加可选 `processInvocation`，构造默认 `WorkerRunner` 和 `MinisterHost` 时同时传入。
- desktop、SDK 和 npm 回落入口从同一个 runtime 装配对象向下传递该函数；保留现有显式 `runner`、`host` 注入，供测试和高级覆盖使用。
- 不新增第二套启动协议；复用两个子进程已有的同签名调用。

**已有验证与缺口**

- 已有测试覆盖 `defaultInvocation()` 的当前脚本、SDK 内嵌和 Electron 缺构建三条路径：`PAO/packages/coding-agent/test/pao/worker-sdk-entry.test.ts:8-55`。
- 未发现测试断言公共 `paoExtension` 同时把同一个 `processInvocation` 交给 worker 和部长，也未发现 desktop/SDK 入口的该组合测试。本阶段未运行相关测试。

### 3. 重启恢复验证了会话和 worktree 绑定，没有覆盖“旧停止失败后重启”的组合

**等级：中；未覆盖组合，当前持久化与会话恢复规则本身已确认。**

**触发条件**

- 应用在发现停止失败或 5 秒退出期限到点后仍退出，随后从同一会话文件重启；旧 worker 或部长进程在退出期间没有死亡。
- 重启后的宿主重新声明会话租约、重新拉起子进程，而旧进程仍可能继续写同一任务现场。

**路径与行号**

- 桌面运行时以 `record.closed` 判断是否中断旧运行：`desktop/packages/pi-sdk-driver/src/session-supervisor.ts:450-460`。`closeSession()` 在停止确认前已把它设为 true：`session-supervisor.ts:1956-1958`。
- 恢复子会话时，只延续上一尝试状态为 `success` 或 `failed`、执行根一致、`worktreeId` 与绑定摘要一致的会话；运行中或未知状态会新开会话：`PAO/packages/coding-agent/src/pao/worker/session-bridge.ts:37-79`。
- 部长身份在 RPC 握手中从真实 `get_state.sessionId` 回填：`PAO/packages/coding-agent/src/pao/host/host.ts:997-1010,1251-1267`。
- desktop 有 worktree 重启恢复测试，例如持久化基线在宿主重启后可重新解析：`desktop/apps/desktop/tests/unit/pao-worktree-host.spec.ts:243-261`。这些测试覆盖数据恢复，没有覆盖旧受管进程仍存活时的互斥。

**影响**

- 会话延续本身不会把“运行中”的旧尝试误当成功或失败，这一边界是正确的。
- 如果发现 1 的退出失败组合发生，旧进程和新宿主可能同时操作同一任务现场。当前父通道兜底在“父进程真正消失”时能停止树，但退出期限到点后的极短重叠、树杀本身失败或进程无法访问，没有验证。
- 不能仅凭 `record.closed=true` 证明旧执行已停止；它只是桌面内存状态。

**最小公共边界修法**

- 复用现有执行锁、登记表或会话租约，在重新打开会话前检查旧执行是否已确认停止；把 `StopProof` 或等价的进程停止证明持久化到同一现场。
- 停止证明缺失时，重启应保留恢复阻塞和错误，不应仅依据 `closed` 标记启动第二个执行者。
- 这是发现 1 的恢复侧边界；实现时应并入关闭协调器，不单独增加一套状态机。

**已有验证与缺口**

- 已确认的验证包括 worktree 数据跨宿主重启恢复、子会话只在已结算且绑定一致时延续。
- 未见真实组合测试覆盖：树杀失败或退出超时后立即重启、旧进程仍存活、新会话尝试获取租约并恢复任务。本阶段未运行测试。

## 真实接口契约

| 边界 | 当前契约 | 当前实现状态 |
|---|---|---|
| 启动身份 | `PaoExtensionOptions` 每次扩展加载新建独立 runner/host；主会话 `session_start` 把真实会话 ID 写入部长默认脉络；worker/部长子进程强制注入角色环境变量 | 已确认正确 |
| 真实执行绑定 | worker 与部长各接受同签名 `processInvocation(args)`；默认都由 `defaultInvocation()` 选择当前安装包的内嵌构建 | 默认正确；公共装配口未统一 |
| 子会话结果 | 部长 RPC 只有成功响应才算受理，最终以 `agent_settled` 和最后 assistant 状态结算；迟到结果投递在关闭前后重复检查 | 已确认正确 |
| 取消与超时 | `WorkerRunner` 先树杀再等待 10 秒退出确认；失败不签发停止凭据。部长任务与注入各有超时，超时不当成功 | 底层返回真实；关闭层丢失失败 |
| 主控唤醒 | 通知面消费式缓冲，关闭时清缓冲、保留项、监听器并拒绝后续通知；结果投递关闭后不重新唤醒 | 已确认正确 |

| 重启恢复 | worker 只延续上一尝试已结算且执行绑定一致的会话；桌面从已持久化 session 与 worktree 数据重开 | 数据恢复正确；旧进程未确认死亡时未覆盖 |

## 已确认正确的生命周期行为

- 每次 `paoExtension` 加载创建独立 runner/host，没有模块级单例串会话：`PAO/packages/coding-agent/src/pao/index.ts:134-166`。
- `new`、`resume`、`fork` 先关闭旧 runtime，`reload` 先发 `session_shutdown` 再替换扩展：`PAO/packages/coding-agent/src/core/agent-session-runtime.ts:169-183` 与 `PAO/packages/coding-agent/src/core/agent-session.ts:3734-3771`。

- 关闭期间仍持有控制权，关闭后迟到工具与模型请求被拒绝：`PAO/packages/coding-agent/test/pao/runtime-shutdown-window.test.ts:106-170`。

## 未覆盖组合与建议分组

| 组合 | 当前结论 | 建议由集中治理计划归组 |
|---|---|---|
| `runner.stopAll` 拒绝 + 部长部分停止失败 + 桌面手工关闭 | 确认成功误报 | 关闭协调器与统一 `StopProof` |
| 退出 5 秒期限到点 + 交接/回执/账本仍写入 | 推断可能截断 | 关闭协调器与强制退出结果 |
| 同一 `processInvocation` 同时装配 worker 与部长 | 确认接口缺口 | 宿主公共装配 |
| 停止未确认 + 立即重启 + 旧进程存活 | 未覆盖组合 | 关闭证明与重启恢复门 |
| CLI、desktop、npm 回落三个入口共享同一装配对象 | 入口传参链已核，统一 invocation 未覆盖 | 宿主公共装配 |

本阶段不继续扩大全库搜索。发现 2 当前没有生产错误证据，应按“共享契约补齐”实施；发现 1 和发现 3 应共用同一个关闭结果与恢复门，避免拆成两套补丁。
