## 必须处理的问题

### F01［P1］实际重试仍复用预留判据，覆盖已发生费用

位置：`memory/extraction-scheduler.ts:442`、`memory/extract-model.ts:420`、`evolution/candidates.ts:379`。

提炼把首个来源 ID 当作 attemptKey，同批解析失败后的实际重试仍使用原键。候选把已入库候选数量当作 attemptKey，`no_change`、解析失败等不增加候选行的结果也会复用原键。底层预算账按键复用并覆盖结算金额，调用方却再次发出真实模型请求。

运行 R1：同批两次解析失败，每次夹具报告 0.02，实际写了两条请求用量；预算账只保留一条 settled、费用 0.02，预期累计 0.04。运行 R2：两次返回 `no_change` 的生成请求同样只结算 0.02。

修法：每次实际模型调用使用独立 request/attempt 身份作为预算判据；来源批次、问题和候选序位保留为归属信息。复用已有 requestId，不改变预算账对同一笔请求的幂等语义。回归需覆盖成功、失败、取消和无改动后的下一次实际调用。

### F02［P1］嵌入预算只包住整项作业，缺逐批结算且空作业也占额

位置：`memory/runtime-embedding.ts:127`、`memory/embeddings.ts` 的批次循环。

预算在调用 `embedMemories` 前按 jobId 预留一次；该函数随后可能发多个请求，调用后没有结算或释放。相同 job 的后续嵌入也复用原判据。没有待发送内容时同样先预留。

运行 R4：两条记忆、batchSize=1，实际发送两次，只有一条 0.05 预留，完成后仍为 `reserved`。运行 R5：零待嵌入记忆、零请求，仍留下一条 0.05 `reserved`。

修法：确定真正待发送的批次后，在每次嵌入请求边界预留；成功或失败后按实际费用结算，缺费用则转 unknown；未发送不占额。保留同一作业的项目与来源归属。

### F03［P1］默认零 usage 被当成已知零费用，未知占额被清掉

位置：`memory/extract-model.ts:490`、`memory/extract-model.ts:502`。

同一响应在记账侧因 totalTokens=0 标为“用量未返回”，结算侧却直接使用 `message.usage.cost.total`。模型适配器的默认 usage 包含零 cost，该值被当成实际零费用。

运行 R9：返回默认零 usage，记录注明“用量未返回”，预算预留却成为 `settled`、已结算费用 0，预期为 `unknown` 并继续占额。

修法：记账与预算使用相同的“费用是否实际已知”判断。缺失用量的默认零对象不能证明免费；有真实用量且价格明确为零的情况仍可正常结算为零。

### F04［P1］日累计检查在预留锁之外，正常并行作业可超限

位置：`memory/budget.ts:175`、`memory/budget.ts:185`。

读取当日累计、判断额度和实际预留不是同一个原子操作。两个后台作业会分别看到旧累计，再通过已有账本锁各自预留。项目支持 CLI/桌面及多个后台请求，该并行入口属于正常使用范围。

运行 R6：每日上限 0.06，总预算充足，两个作业并行申请各 0.05，两个均获批，合计预留 0.10。

修法：把相应用途的当日累计检查和预留放进既有预算账的同一个临界区，保持总预算、未知占额和幂等规则；不新增平行预算账。

### F05［P1］候选生成仍没有项目外发许可检查

位置：`evolution/candidates.ts:384`、`evolution/candidates.ts:459`。

`proposeCandidate` 检查预算后直接调用模型，未调用项目外发许可。提示中包含开发样例的输入和失败描述；总预算授权不能替代项目资料的外发授权。

运行 R3：隔离 home 配好预算而未配置外发许可，模型入口仍被调用一次，返回 `no_change`。

修法：在预留和外发之前，复用已有 `checkOutbound`，按可信执行/来源项目确认本次提示涉及的资料范围。项目身份随业务编排传递，不能由模型自报。

### F06［P2］多批嵌入与异常请求仍从费用聚合中漏失

位置：`memory/embeddings.ts` 的 `batchRequest`/`embedUsageNote`、`memory/usage-query.ts:139`、`memory/extract-model.ts:461`。

所有嵌入批次沿用同一 requestId，聚合按 jobId+requestId 去重，实际多次请求被折成一次。提炼请求抛异常时只写 failure custom entry，聚合仅遍历 usage entry，因此异常请求的未知费用不可见。

运行 R4：原始账本有两条嵌入 usage，聚合只返回一条，unknownCount=1。运行 R10：异常请求的预算状态已为 unknown，费用聚合却返回零条、unknownCount=0。

修法：嵌入每个实际请求具有独立 ID，单次请求的结果与失败沿用该 ID；请求异常也写入可被统一聚合识别的未知请求记录。继续复用现有账本，避免同一费用双计。

### F07［P2］共享 ID 只连接了注入和估算，仍未连接实际前台用量

位置：`memory/context-usage.ts:314`、`pao/desktop/memory.ts:2119`、`pao/desktop/memory.ts:2129`。

前台实际模型用量保存在 assistant 消息中。桌面读取上下文用量时只寻找 `type=usage` 且 note 含快照 requestId 的记录，当前普通请求没有这样的关联写入。两个扩展共享 UUID 不能单独补齐实际用量关联。

运行 R8：真实 SDK、真实 SessionManager、遵守 onPayload 请求钩子的离线供应商；请求钩子触发一次、快照一条、assistant 实际用量为 10 token；桌面结果的 `actual` 仍缺失，独立 usage entry 数为 0。

修法：在请求结束时把 requestId 与实际 assistant 条目关联，桌面按该引用读取真实 usage；保留原费用正本。验收从真实 SDK 请求读到页面 DTO，不只手工构造两个扩展事件。

### F08［P2］unlimited 候选请求结算不存在的预留，完成后抛异常

位置：`evolution/candidates.ts:384` 及后续 `settleMemoryJobBudget` 分支。

预算门在 unlimited 模式不建立预留，候选生成仍无条件结算。运行 R7：模型请求一次并返回 `no_change`，随后抛出 `BudgetLedgerError`，原因是没有对应预留。

这是实施记录已披露的未修缺陷。修法与提炼已采用的方式一致：仅对实际存在的预留结算；unlimited 仍记录请求和用量。该问题应保持明确的未完成归属。

## 已确认有效的部分

- 生产提炼调度已传入执行路径推导的项目身份、scopeKey 和预算参数。
- 现有用例确认：提炼未获外发许可时零请求且不预留；缺后台预算配置时零请求；正常授权可以请求；请求异常保留 unknown 预算并写 failure 记录。
- 嵌入开关缺省或 false 时零请求，true 时可继续执行。
- 顺序执行两个不同预算判据时，新增日累计检查可以拒绝第二笔超限预留。
- 注入记录与上下文快照已共享 requestId，跨轮会换发；缺费用字段的聚合展示会标未知。

这些行为保留。O01 尚需解决的是剩余边界和实际归因，不需要替换账本或增加通用请求框架。
