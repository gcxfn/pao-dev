## J01（F01，高）：organize handler 接进维护队列

**缺口**：`tools.ts:892-947` `buildMaintenanceHandlers` 只注册 embed/archive；`maintenance.ts` 未注册分支记 failed。`organize.ts` 的 collect/group/stale 全是纯函数无生产调用。`enqueue` 零生产调用。

**修复**：注册 `organize` handler + 一个生产触发点 enqueue。

- **handler 链**（`organize:{projectId}` scopeKey，`job.sourceScope` 解 scope——不取 `ctx` 当前会话）：
  `collectChangedMemories(store, scope, job.cursor)` → `groupForOrganize` → 组内 `findLexicalDuplicates` + 语义候选（`readMemoryVectors`+`cosine`）`mergeOrganizeCandidates` → **`staleOrganizeMembers` 提交前复核**（核 current_revision/usage_state/merged_into；如审核文档所记它不查 source_exclusions，需补或沿用现有复核规则）→ `service.mergeMemories`。
- **service 依赖**：`MaintenanceSchedulerDeps` 无 MemoryService——在 deps 增注入（或 handler 内 `openMemoryService` 并管释放；推荐 deps 注入，同 registerBuiltinMemory 装配处可拿到）。
- **事务边界**：node:sqlite 不嵌套 BEGIN IMMEDIATE——每组 merge 独立 `store.transaction`，不包外层事务（extract-commit「候选级事务」先例）。
- **正式决定保护**：organize 契约「只整理关联与当前状态，不让整理改成新定案」；双 confirmed 冲突拒并沿用 mergeMemories 既有规则。
- **触发点**：handler 注册后需谁 `enqueue("organize","organize:{projectId}",sourceScope)`——自然挂点是提炼 job 收尾（extraction-scheduler finishJob/completeJob 后）或 settled；按既有 embed 作业的挂点惯例接入，不做新调度框架。
- **验收**：真实事件→空闲整理→来源/修订复核→提交；模型等待期纠正/停用/删除后旧候选不提交；正式决定不被改成新定案。

## J02（F02，中）：增量游标改 (updated_at,id) 复合游标

**缺口**：`organize.ts:85` `updated_at > cursor` 过滤但 `:118` 存 `row.id`、`:120` 返回 ID 当 nextCursor——ID/时间语义错位，增量失效；`ORDER BY updated_at,id` 同时间戳一批会被 `>cursor` 整批跳过。

**修复**：`(updated_at,id)` 复合游标同序过滤。

- cursor 序列化二元值（如 `updated_at|id` 或 JSON）；过滤 `(updated_at > ?) OR (updated_at = ? AND id > ?)` 配合 `ORDER BY updated_at, id`。
- 消费方 `advanceCursor`（extraction-jobs.ts:199）TEXT 原样存，兼容。
- **验收**：首批、无变化、新增、旧记录修订、>200 条同时间记录，仅返回未处理部分、同时间超批次不漏。

## J03（F05，高）：rebuild/备份/恢复开放产品入口

**缺口**：`rebuildMemoryIndex`/`createMemoryBackup`/`restoreMemoryBackup` 生产调用全零；`/pao memory` 六子命令无管理类；`maintenanceHandle.enqueue` 无调用。

**修复**：沿 `/pao memory` 现有 `registerMemoryCommand`/`addPaoSubcommand` 扩管理子命令（桌面经 `pao/index.ts:629` 同一命令转发复用）。

- **rebuild**：`/pao memory rebuild [--project <id>] [--kind <kind>]` → `rebuildMemoryIndex(store,{projectId?,kind?,dropExistingFts:true})`，输出 dropped/rebuilt 计数。
- **backup**：`/pao memory backup <dir>` → 经 `maintenanceHandle.enqueue("archive","archive:{backupDir}",{kind:"archive",backupDir})` 登记（`parseArchiveJobScope` 约定），archive handler 走 `createMemoryBackup`。
- **restore**：`/pao memory restore <dir>` → `restoreMemoryBackup({backupDir,targetHome,liveHome})`；目标库独立打开（backup.ts:412 自 `new DatabaseSync`），不在 openMemoryStore 引用内。
- **F15 边界**：`serialize/deserialize` 在 Electron 缺失归 O07——本项只要求入口可达，CLI（node:sqlite）下可用；桌面触发 backup/restore 若撞 F15 属 O07 范围，不在本任务验收。
- **验收**：从实际 CLI 入口触发 rebuild/backup/restore 并观测队列/结果，不靠测试直调业务函数。

## J04（F06，高）：rebuild 清除范围与筛选一致

**缺口**：`rebuild-index.ts:112-117` `DELETE FROM memory_fts` 整表清再插回筛选行——`{projectId:'A'}` 会清掉 B 的索引。

**修复**：清除范围 = 读取范围。

- 有筛选时 `DELETE FROM memory_fts WHERE memory_id IN (筛选出的 id)`；无筛选+`dropExisting` 才全清。
- `store.transaction` 内原子；范围内排除项不复活。
- `rebuildSourceFts` 无范围参数是全量重建，本项不动（除非任务书要求加范围，审核文档未要求）。
- **验收**：A/B 与多 kind 同存，重建 A 指定类型后 B 索引与查询不变；范围内排除项不复活。
