## 已核实的运行事实（不要重复怀疑）

- 备份/恢复唯一源文件：`PAO/packages/coding-agent/src/pao/memory/backup.ts`。
- Electron 37.10.3 / Node 22.21.1 的 `DatabaseSync` 实测方法只有：`open, close, prepare, exec, function, location, aggregate, createSession, applyChangeset, enableLoadExtension, loadExtension`。**没有 `serialize` / `deserialize` / `backup`**。
- 双端（Node 24 + Electron 37）都验证可用的一致性快照方式：**`VACUUM INTO '<路径>'`**（经 `db.exec` 调用）。Node 24 的 `serialize/deserialize` 不能用来替 Electron 兜底——必须选双端共有的路径。
- 恢复现状（backup.ts:374-459）：恢复把段文件复制到 `targetHome/memory/archives/`，但**没有更新恢复库 `archive_segments` 的 `original_path`/`compressed_path`**，仍指向旧 home 绝对路径 → `readSourceEvents` 走 `segment.compressedPath/originalPath`（archive.ts:340/344）读到旧现场 → D1 实测 `source_missing`。受管成果（`artifacts.ts` 的 `location.kind==="managed"`，`location.dir` 绝对路径）完全不在备份范围 → 旧 home 丢失后 `resolveArtifactVersion` 失败。
- 恢复现状：重放 exclusion 后仅 `purgeDerivedIndexes` 清 FTS/向量，**`memories`/`memory_revisions`/归档正文保留** → D2 实测 `getMemory(includeHistory=true)` 仍返回已删结论。

## 三个缺陷与修法

### F15（API 兼容性）→ 用 VACUUM INTO 做快照与恢复落地

**备份** `createMemoryBackup`：把 `store.db.serialize()` 换成 `store.db.exec("VACUUM INTO '<snapshotPath>'")`。
- `VACUUM INTO` 输出的是一份**非 WAL 的一致性主库文件**，正好满足恢复端「干净镜像」需求（现状注释里说 serialize 输出带 WAL journal 头需中转——VACUUM INTO 直接消掉这个中转）。
- 目标文件不能已存在（SQLite 要求），落点前确保 `backupDir/memory.snapshot` 不存在；路径含单引号要 `''` 转义。
- 快照与文件清单使用同一数据时刻；当前验收与修复要求见 [修复任务书 R1](o07-修复任务书.md#r1清单与快照一致p1i4)。

**恢复** `restoreMemoryBackup`：现状用 `deserialize → serialize → 写盘` 的三段中转（backup.ts:402-411）。VACUUM INTO 的快照本身就是干净主库文件，**直接 `copyFileSync(snapshotPath → targetPaths.database)`** 即可，不再走内存库中转。然后用 `new DatabaseSync(targetPaths.database)` 打开、置 `journal_mode=WAL`/`foreign_keys=ON` 沿用现状。

> 验证点：本任务全部改动须用 **Node 当前版本**跑通定向测试即可；不另起 Electron。但实现只能用 `exec`/`prepare`/`VACUUM INTO` 这些双端共有 API——**禁止再出现 `serialize`/`deserialize`/`db.backup`/内存库 `deserialize`**。

### F07（恢复重定位 + 受管成果纳入备份）

**来源重定位**：恢复段文件复制到 `targetHome/memory/archives/<sessionId>/<file>` 后，**在恢复库事务内 UPDATE `archive_segments` 的 `original_path`/`compressed_path` 指向新落点**（按 manifest 里每段的 `backupPath` 与新根拼出实际路径；区分 compressed 与否，对应写 `compressed_path` 或 `original_path`，另一列置 NULL）。这样 `readSourceEvents`（读 `segment.compressedPath ?? originalPath`）在新 home 读到恢复副本，不回旧绝对路径。
- manifest 的 `backupPath` 形如 `segments/<sessionId>/<segId>.jsonl[.gz]`；恢复落点现状是 `join(targetPaths.archives, relative("segments", entry.backupPath))`——沿用同一落点计算，写库时用绝对路径（与 `openSegmentForSession` 写绝对路径一致）。

**受管成果纳入备份**：现状备份只复制 archive_segments，不含 `memory/artifacts/` 下受管成果副本。
- 备份时遍历 `artifact_versions`，对 `location.kind==="managed"` 的版本复制 `location.dir` 下文件到备份目录（如 `artifacts/<artifactId>/<versionId>/<file>`），manifest 增加成果段登记。
- 恢复时把受管文件复制到 `targetHome` 对应 `artifacts/<artifactId>/<versionId>/`，并把恢复库 `artifact_versions.location_json` 里 `dir` 重写到新落点（kind==="git" 的版本不动——Git 对象由仓自身保留，F07 明确「用户 Git 仓只保留版本引用，不复制整个仓库」）。

### F08（恢复重放删除要清正文，不只清索引）

现状 `purgeDerivedIndexes` 只删 `memory_fts`/`memory_vectors`，`memories`/`memory_revisions`/归档正文保留。修法方向：**恢复时应用最新排除后，按删除语义把被排除来源关联的「不再被任何有效记忆引用」的记忆正本、修订、来源行、派生内容清掉**，让按 ID/原文/索引都不返回已删正文。

关键约束（来自 sources.ts 的 `sourceGlobalExclusionSql` / `isSourceGloballyExcluded` 既有语义，**复用同一套，不自造判定**）：
- `source_exclusions.memory_id IS NULL` → 全局排除；
- `memory_id` 非空 → 仅「该被删记忆」的引用标记；来源仍被其他有效记忆引用则不算整体排除。
- 「彻底删除」= 排除不再被引用的正本/修订/来源行 + 清 task_continuations 正文（参照 `applyDatabasePlan` deletion.ts:1580 的 UPDATE 同款把 content_available 置 0）+ 清归档段里对应条目 + 清 FTS/向量/usage/links。

最小落地：重放 exclusion 后，对每个「整体被排除且不再被有效记忆引用」的来源，复用与 `applyDatabasePlan` 相同的一组 DELETE（memory_fts/memory_vectors/memory_usage/memory_source_links/revision_links/memory_revisions/memories + source_fts + sources + task_continuations 清空 + artifact_refs ref_kind='memory' 解除）。**不引入新的删除框架，但也不要把 deletion.ts 整套搬过来**——恢复场景是「按已确定的排除清单清理」，不是「重新预览构建删除计划」。归档段正文重写（redactSegmentLines）若实现成本高，至少保证：被整体排除来源对应的段条目在 `readSourceEvents` 按排除判定时不可达，且 `getMemory`/原文/索引三处都不再返回已删正文。把确实清不掉的残留如实计入结果的 limitation/计数，不伪装已删。

> 验收口径（D2）：备份 → 真实 deleteMemory → 带 liveHome 恢复后，`getMemory(includeHistory=true)` **不得返回已删结论正文**；按 ID、来源窗口、归档文件、重建索引均不得返回被删正文；未删来源仍可读。
