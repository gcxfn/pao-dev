## 1. 待修问题

### O05-1 / P1：封存发布期间仍向旧段追加，新事件可能丢失

位置：[capture.ts:419](../../PAO/packages/coding-agent/src/pao/memory/capture.ts#L419)、[archive.ts:141](../../PAO/packages/coding-agent/src/pao/memory/archive.ts#L141)、[archive.ts:259](../../PAO/packages/coding-agent/src/pao/memory/archive.ts#L259)。对应 F10，证据 B4。

settled 回调启动封存后立即返回；段在压缩发布完成前仍为 `unsealed`。后续采集经 `findOpenSegment` 选回该段。若新事件在压缩已经读完原文、发布尚未结束时追加，发布后删除原文件会一起删除新事件，而压缩副本没有该事件。

独立场景固定这一异步 I/O 边界：两次采集得到同一 segmentId，第二条来源成功登记，封存结束后回读却返回 `source_missing`，原因是段中没有对应事件。下一轮输入、工具操作继续采集均为现有用法；settled 时没有 writer 不能保证整个后台发布期间没有新 writer。

修复：封存开始、进入异步 I/O 前，先把该段移出可追加集合，让新采集开新段；保留原段的失败回读能力。沿现有段状态与采集入口处理，无需新建归档作业框架。验收须覆盖发布未完成时的新采集，不仅检查等待封存结束后的下一轮。

### O05-2 / P1：模型召回工具丢弃 sourceHits，未提炼讨论仍不可发现

位置：[tools.ts:485](../../PAO/packages/coding-agent/src/pao/memory/tools.ts#L485)。对应 Q3/Q4，证据 B1。

`searchMemory(mode=history)` 已返回来源命中，但 `pao_memory_recall` 仅检查、转换和渲染 `result.hits`。没有结构化记忆时，工具直接回复“历史查询无命中”；即使同时命中结构化记忆，来源命中也不会被输出。

独立场景中，服务返回一条真实采集的 SQLite 讨论来源，实际注册的模型工具回复无命中，未提供 sourceId。`pao_memory_read` 虽能按已知 ID 展开，模型仍无法从历史查询获得这个 ID。

修复：在 history 工具输出中独立展示来源摘要及 sourceId，并指向 `pao_memory_read`；空结果判断同时考虑两类命中。来源保持追溯语义，不转换成已确认决定，也不参与 current 自动注入。

### O05-3 / P2：来源查询未遵守项目与任务范围

位置：[source-fts.ts:171](../../PAO/packages/coding-agent/src/pao/memory/source-fts.ts#L171)、[scope.ts:100](../../PAO/packages/coding-agent/src/pao/memory/scope.ts#L100)。对应 Q3，证据 B2/B7。

来源查询只使用 `(s.project_id = ? OR s.project_id IS NULL)`，没有任务条件。绑定 task-a 的来源会出现在 task-b 查询中；采集时未绑定项目的普通会话来源，则能被任意项目查询命中。

`historyScopeFilter` 实际要求项目准确匹配；任务为 NULL 或当前任务，查询未带任务时仅取无任务记录。原验收记录所称“与 history 宽口径一致”不符合当前源码。来源未绑定表示归属未知，不能自动成为所有项目共享的知识。

修复：在候选截取前落实项目、任务条件。普通会话采集和查阅使用宿主已有的可信项目或会话归属，使未绑定讨论仍能在其可证明的范围内发现；不能简单把未绑定记录全部丢弃，也不能以 NULL 无条件跨项目放行。

### O05-4 / P2：刷新元信息与截断提示未完整计费，实际渲染仍超预算

位置：[session.ts:356](../../PAO/packages/coding-agent/src/pao/memory/session.ts#L356)、[session.ts:365](../../PAO/packages/coding-agent/src/pao/memory/session.ts#L365)、[session.ts:701](../../PAO/packages/coding-agent/src/pao/memory/session.ts#L701)。对应 Q6，证据 B5/B6。

刷新路径为超限 builtin 条目保留全部来源元信息，却只累计提示正文成本。初始可注入的决定增加二十条来源后，经真实修订刷新与可见消息过滤，实际输出 **2398 码点，超过 2000 上限**。正文置空并不能免除元信息的渲染成本。

可截断供应商条目另有同类漏计：预算累计 `keep`，但实际正文追加了截断提示。正常三条候选在默认 2000 预算下实际渲染 **2132 码点**。

修复：初选和刷新均按最终文本累计完整成本，包含来源行、提示、消息头和换行。整项装不下时省略该项；仍需保留的依据放在既有结构化状态中，不能把超长元信息重新渲染进请求。可截断条目先预留提示空间，再决定正文长度。刷新同时沿用本轮有效预算。

### O05-5 / P2：先截取再排除，有效原文会被隐藏

位置：[source-fts.ts:188](../../PAO/packages/coding-agent/src/pao/memory/source-fts.ts#L188)、[source-fts.ts:204](../../PAO/packages/coding-agent/src/pao/memory/source-fts.ts#L204)、[source-fts.ts:218](../../PAO/packages/coding-agent/src/pao/memory/source-fts.ts#L218)。对应 Q3，证据 B3。

MATCH 与 LIKE 都先做 SQL LIMIT，然后在内存中过滤来源排除记录。被过滤来源已占满候选位置，后续有效原文没有补入。

持久排除状态场景中，十一条被当前查询判定为排除的来源排在有效来源之前。`limit=1` 的来源候选为空；扩大到 20 后能找到同一有效来源。短词 LIKE 路已复现，MATCH 路使用相同的截取顺序。

修复：把实际可见性与排除条件下推到候选 LIMIT 前，复用既有排除身份；不通过盲目扩大候选上限掩盖问题。与 O05-6 一并明确共享保留来源的可见性。

### O05-6 / P2：删除一条共享记忆会隐藏仍应保留的来源原文

位置：[source-fts.ts:218](../../PAO/packages/coding-agent/src/pao/memory/source-fts.ts#L218)、[sources.ts:221](../../PAO/packages/coding-agent/src/pao/memory/sources.ts#L221)、[deletion.ts:1561](../../PAO/packages/coding-agent/src/pao/memory/deletion.ts#L1561)。对应 Q3 的删除一致性，证据 B8。

真实 SessionManager 文件中，一条原文被两条记忆引用。调用删除 API 并选择 `sharedSourcePolicy=retain` 后，删除结果为 `complete`，来源动作为 `retain`，另一条记忆仍引用它，按 sourceId 展开也正常。

删除会为被删记忆写入带 memoryId 的来源排除记录。新来源查询调用不区分记忆归属的 `isSourceExcluded`，把该来源整体隐藏；查询原文特有的 SQLite 词时返回无命中。这使保留原文只能依靠预先知道的 ID 读取，不能通过历史查询重新发现。

修复：查询时区分被删记忆的排除记录与来源整体不可用；仍有有效引用、明确保留的来源继续可发现。真正的来源排除在查询与展开中保持一致。保留共享来源是既有删除契约，不应通过拒绝全部共享原文读取来消除差异。
