## 修改清单（8 项）

### 1. `pao/memory/budget.ts` — 预算判据粒度 + 日累计 + 嵌入开关

- `checkMemoryJobBudget` 的输入新增可选 `attemptKey?: string`。`idempotencyKey` 构成改为：
  - 传了 attemptKey → `memory-job:{jobId}:{jobKind}:{attemptKey}`（单次请求/尝试一条预留）；
  - 没传 → 保持现有 `memory-job:{jobId}:{jobKind}`（向后兼容）。
  指纹保持 sha256(jobId+scopeKey+kind) 前 16 位，不把 attemptKey 并入（指纹回答「同一判据的内容是否同一任务」，attemptKey 回答「第几次尝试」）。
- `settleMemoryJobBudget` 与 `releaseMemoryJobBudget` 同样接受可选 `attemptKey` 并按同一规则拼判据。
- 新增导出 `checkMemoryEmbeddingAllowed(input: {paoHome, jobId, scopeKey, 金额?, 现在, config?})`：读同一份 `记忆后台预算.json`，`unlimited` 直通；`允许嵌入 !== true` → `{ok:false, kind:"未授权", reason}`；其后调用 `checkMemoryJobBudget`（jobKind="embed"）。
- 日累计（维护 F04 附属缺口）：在 `checkMemoryJobBudget` 的额度判断里，当 `config.每日上限` 有值时，读 `readBudgetLedger(budgetLedgerPath(paoHome))` 的 `reservations`，按 UTC 当日（`预留时间`/`结算时间` 以 `input.现在` 的日期为界）聚合「卡号以 `memory:` 开头」的记录：settled 取 `已结算费用`，reserved/unknown 取 `预留额`；`当日已发生 + 本次金额 > 每日上限` → 返回 `{ok:false, kind:"额度不足", reason}`。本逻辑只约束 memory:* 预留（后台额度），不影响 dispatch 判据。

### 2. `pao/memory/extract-model.ts` — 提炼请求接许可 + 预算 + 失败记账

`RequestExtractionDeps` 新增可选字段：

```ts
/** 本批实际来源的项目名（外发许可判定用；缺省不发请求）。 */
outboundProjects?: string[];
/** 外发许可配置（测试注入；缺省 loadOutboundConfig(paoHome)）。 */
outbound?: OutboundConfig;
/** 本次请求所属 job 的预算 scopeKey（extraction-jobs 的 scopeKey 同值）。 */
budgetScopeKey?: string;
/** 本批请求在 job 内的次序（批级预算判据；缺省 "0"）。 */
budgetAttemptKey?: string;
```

`requestExtraction` 内（档位解析之前）新增两段门：

- 外发：`checkOutbound(input/deps 给出的项目名列表, outbound)`；不通过 → 返回 `{ok:true, requestId, candidates:[], rejected:[], failure:{stage:"request", message:"禁外发：项目 … 未获有效许可"}}`（不发请求，不占预算——先查许可再预留，避免无意义占额）。
- 预算：`checkMemoryJobBudget({paoHome: deps.paoHome, jobId: input.jobId, jobKind: "extract", scopeKey: deps.budgetScopeKey ?? input.jobId, attemptKey: deps.budgetAttemptKey, 现在: new Date().toISOString()})`；不通过 → 同样 `failure:{stage:"request", message:"预算门拒绝:…"}` 返回，不发请求。deps.paoHome 缺失且未注入 tierConfig 时维持原 invalid_input 行为（预算门放在档位文件解析之前，不引入额外读盘前提）。

结算/释放接线：

- streamSimple `catch` 分支（:407-413 现址）：先 `settleMemoryJobBudget(…, undefined, …)`（未知费用占额保留），并补 `deps.ledger.appendCustomEntry("pao-memory-extraction-failure", {requestId, jobId, sourceSessionId, error})`（F09：异常请求也要有失败回执），再返回。
- `appendUsage` 之后的三条返回路径（error/aborted、parse 失败、成功）：统一 `settleMemoryJobBudget(…, message.usage.cost?.total ?? undefined, …)`——cost 缺省 → unknown 占额，不释放。
- `if (input.entries.length === 0)` 与档位/tierConfig 缺失、模型找不到三条 invalid_input 返回发生在预留之前或之后？顺序定为：**先校验输入形状（entries 非空、档位可解析、模型存在），再过许可，再预留**——未发出的请求不产生预留。模型找不到走 `releaseMemoryJobBudget`（若已预留）。
- `budgetScopeKey`/`budgetAttemptKey` 未传时跳过预算门与结算（测试兼容：现有测试不传 → 行为不变）。

### 6. `pao/memory/usage.ts` + `pao/memory/context-usage.ts` — 前台请求共享 requestId

现状：usage.ts `context_with_system` 记 pending、`before_provider_request` 自造 requestId；context-usage.ts 在 `context_with_system` 另造一个。两文件是同一 `registerBuiltinMemory` 装配下的独立闭包，无法共享局部变量。

最小修法（不加 runner 字段、不新增事件）：

- 新建 `pao/memory/request-identity.ts`：模块级 `Map<SessionManager, string>`（或 WeakMap），暴露 `requestIdFor(sessionManager): string` 与 `rotateRequestId(sessionManager): string`。
- `usage.ts` 的 `before_provider_request`（:137）与 `context-usage.ts` 的 `context_with_system`（:313）都改为调用 `requestIdFor(ctx.sessionManager)`：首个调用方生成并暂存；`turn_end`/`agent_settled`/`turn_start` 时 `rotateRequestId` 作废。两扩展各自仍持有 pending，但 requestId 同源 → 快照与 inject 记录同 ID。
- 注意事件序：`context_with_system` 先于 `before_provider_request`（同一 emitContext 调用内顺序触发），turn 内第二次请求（工具回合续跑）需要新 ID——`before_provider_request` 消费后不 rotate（同 turn 内多次 provider 请求沿用同一 ID，符合「同请求」粒度的合理近似；`turn_start` 必 rotate）。文档注释写清「ID 粒度 = 一次会话轮次内的前台请求」。
- `desktop/memory.ts:2128` 的旁列查找逻辑不动——ID 同源后自然命中。

### 7. `pao/evolution/candidates.ts` — 候选预算判据按尝试分键

- :374 `budgetJobId` 保持 `evo-${problemId}`；**改为把第几次生成传成 attemptKey**：`attemptKey = `cand-${existingCount.n}``（existingCount 是 :362 已查的候选行数；同一序位重试=同判据，不同候选=不同预留）。所有 `checkMemoryJobBudget/settleMemoryJobBudget/releaseMemoryJobBudget` 调用点（约 11 处）统一补 `attemptKey` 实参。
- 结果：每次实际模型请求一条独立预留/结算，第二次不再复用第一次的 settled 记录、不再覆盖已结算费用（E09 修复）。
- `input.budget?.jobId` 外部注入路径保留；外部调用方传了 jobId 时 attemptKey 同样按 `cand-${existingCount.n}` 派生。
