## J01（P1，B4）：封存发布期间新事件不再追加旧段

**缺口**：`capture.ts:417-428` offSettled 调 `sealSegment`（异步）；段在压缩读完、发布完成前仍 `unsealed`，期间 `openSegmentForSession`/`findOpenSegment` 选回该段追加，发布后原文件删除连带新事件丢失 → `source_missing`。

**修复**：封存在进入异步 I/O 前，先把该段移出「可追加」集合。最小改动：在 `sealSegment` 开头（`archive.ts:232` 拿到 segment 后、调 `archiveWorkerEvidence` 前）把行状态从 `unsealed` 改为中间态（如 `sealing`），使 `findOpenSegment`（只查 `unsealed`）不再选回；发布成功置 `sealed`、失败回 `failed`（保留重试）。

- `findOpenSegment` WHERE 保持 `status='unsealed'` 即可自然排除 `sealing` 段。
- `sealSegment` 需处理入参已是 `sealing`/`sealed` 的幂等；`status` 无 CHECK 约束则直接新增 `sealing` 值，有约束则用既有状态位替代（先核 `archive_segments` 建表 SQL）。
- 崩溃遗留：`sealing` 段重启后应可重试或回读，纳入 rebuild/getSegment 既有口径，不新建框架。
- **验收**：`o05-deep-review.test.ts` B4（固定压缩读完-发布未完边界，新采集须开新段且回读 ok）。

## J02（P1，B1）：history 召回工具输出 sourceHits

**缺口**：`tools.ts` `pao_memory_recall` 只渲染 `result.hits`，`mode=history` 时 service 已返回 `sourceHits` 但工具丢弃 → 模型拿不到 sourceId 无法用 `pao_memory_read` 展开。

**修复**：`searchMemory` 工具执行器在 history 结果中独立展示来源摘要区——列出 `sourceId`/`sessionId`/`entryId`/`eventType`/`capturedAt`/snippet，并标注「来源命中，按 sourceId 用 pao_memory_read 分页回读；为追溯信息非已确认决定」。空结果判定同时考虑 `hits` 与 `sourceHits`（sourceHits 非空不算无命中）。来源命中不参与 current 注入、不渲染成已确认决定。

- **验收**：B1——service 有 sourceHits 时工具输出含 sourceId 字符串。

## J03（P2，B2/B7）：来源查询落实项目+任务范围

**缺口**：`source-fts.ts:171` 仅 `(s.project_id = ? OR s.project_id IS NULL)`，无 taskId 条件；未绑定来源被任意项目命中。

**修复**：候选截取前落实 scope 条件，对齐 `historyScopeFilter` 语义：

- projectId：`scope.projectId` 有值时按 `s.project_id = ?` 准确匹配；**不再无条件放行 NULL**。未绑定（NULL）来源只在「能证明其归属」的范围命中——按采集会话归属：用 `session_id` 关联到该会话的项目/任务归属判定，而非简单放行或丢弃。
- taskId：`scope.taskId` 有值时 `s.task_id = ? OR s.task_id IS NULL`；scope.taskId 无值（未指定任务查询）时仅取 `s.task_id IS NULL` 的记录——与 current 记忆的 taskId 语义一致。
- 与 J04 排除下推合并到同一 WHERE。
- **验收**：B2（task-a 来源不出现在 task-b）、B7（NULL project_id 来源不被另一项目命中，但能被其可证明归属的范围发现）。

## J04（P2，B3）：排除条件下推到候选 LIMIT 前

**缺口**：`source-fts.ts` MATCH/LIKE 都先 `LIMIT laneLimit` 再内存 `isSourceExcluded`，被排除来源占满候选位挤出有效原文。

**修复**：把可见性排除下推到 SQL——候选查询 JOIN/WHERE 中直接排除 `source_exclusions` 命中的来源（复用 J05 的排除判定语义），再 LIMIT。不通过调大 `sourceLaneLimit` 掩盖。

- **验收**：B3——11 条已排除来源在前、limit=1 仍能返回有效来源。

## J05（P2，B8）：区分「记忆被删的引用排除」与「来源整体不可用」

**缺口**：`sharedSourcePolicy=retain` 删除一条共享记忆后，`isSourceExcluded` 不区分 memoryId，把仍被另一记忆引用的来源整体隐藏。

**修复**：`source_exclusions.memory_id` 已存在。查询/展开路径区分两类记录：

- `memory_id IS NULL` 的排除 → 来源整体不可用，隐藏（既有全局排除语义）。
- `memory_id` 非空的排除 → 仅该记忆被删的引用标记；若该来源仍被**其他有效（未删）记忆**引用或经 retain 保留 → 历史查询/展开仍可见。仅当来源不再被任何有效引用时才视为整体排除。
- 判定「仍被有效引用」复用 `memory_sources`/来源链接表现存关系，不新建表。
- J04 的 SQL 下推用同一判定（来源整体排除才进 WHERE 剔除）。
- **验收**：B8——retain 删除后来源仍可 `pao_memory_read` 展开且 history 查询可发现。

## J06（P2，B5/B6）：刷新与截断提示计入完整渲染预算

**缺口**：
- B5：`budgetAutomaticRecallHits`/`filterVisibleMessages` 刷新路径为超限 builtin 条目保留全部来源元信息，只累计提示正文成本 → 实测 2398>2000。
- B6：`selectForContext` 可截断条目累计 `keep` 但正文追加截断提示 → 2132>2000。

**修复**：初选与刷新统一按**最终渲染文本**累计完整成本（含来源行、meta 行、截断/回读提示、消息头、行间换行）：

- 截断条目：先预留截断提示所需码点，再决定可保留正文长度；装不下则整项省略（`因正文预算省略`）。
- 刷新路径：超限条目不把超长元信息重新渲染进请求；整条含 meta 渲染仍超预算时整项省略，所需保留依据留在既有结构化 `state.visibleHits`/`details`，不进入模型可见文本。刷新沿用本轮有效预算（`budgetAutomaticRecallHits` 接收并执行 budgetLimit）。
- **验收**：B5、B6——实际渲染文本 ≤ 2000。
