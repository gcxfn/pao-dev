## 总原则

- 批内去重不能再短路实质差异分派——同一批里后到的确认/条件变化必须进入与跨批一致的出口（duplicate / corrected / flagged / semantic_conflict）。
- 写入工具的来源是 `toolcall:<id>`（助手），不能顶替 `user_statement`/`confirmed`——依据身份决定 evidenceKind/confirmation，助手推断保持 tentative。
- 条件变化触发重议前，先核对候选的实据身份；模型推断/tentative 变化不修订已确认决定的重议状态。

## 修改清单（3 项）

### 1. `pao/memory/extract-commit.ts` — 批内去重进入语义分派（I01）

`batchSeen` 目前存「首个该 batchKey 的 candidateIndex」，命中即返回 `duplicate_in_batch`。改为存「该 batchKey 最近一次**成功落库**的目标」，批内第二条起与库内当前状态做同一分派。

具体做法：

- `batchSeen` 的类型改为 `Map<string, { memoryId: string; currentRevision: number; candidateIndex: number }>`——记录该结论在本批已提交的 memoryId、修订号与首个候选 index。
- 每次成功提交（submitted/corrected/flagged/duplicate）时更新 `batchSeen` 为本次写入的 `(memoryId, currentRevision, candidateIndex)`——第一条的 candidateIndex 保留作 `duplicateOf` 展示，但 memoryId/revision 随每次写入前进（链式：I1 第一条 tentative submitted rev1、第二条 confirmed 对 rev1 升级到 rev2、第三条 confirmed 同条件对 rev2 无差异 duplicate）。duplicate 补链不改写当前修订内容，currentRevision 不变仍记同一 memoryId。
- 第二条候选命中 `batchSeen` 后：取库内该 memoryId 的当前修订内容（`currentRevisionContent(db, memoryId, currentRevision)`，batchSeen 存的 revision 即当前），按 `semanticDelta` 分派——与第 5 关 `sameConclusion` 分支共用同一套「无差异→duplicate 补链、仅 tentative→confirmed→升级、conditions→flag、其余→semantic_conflict」逻辑；只有无差异时才返回 `duplicate_in_batch`。
- `flagForReDiscussion` 的分支也进入此分派——第二条带来新条件 → 对批内刚提交的 memoryId 标重议（I2 的期望），不是返回 duplicate_in_batch。
- 「先 confirmed、后 tentative 同结论」的既有行为保持：tentative 候选落到已 confirmed 的 memoryId 时 delta.confirmationChanged=true，走 semantic_conflict 或 duplicate——按现有第 5 关口径执行，不为批内单独开口。

实现建议：把第 5 关的 `sameConclusion` 分派抽成一个共用闭包/函数（`dispatchSameConclusion(candidate, candidateIndex, target, batchKey)`），第 4 关来源命中、第 5 关同范围命中、第 3 关批内命中三处调用同一实现——同一规则只实现一次。

### 2. `pao/memory/tools.ts` — 写入/纠正按依据身份定确认（I02）

`buildBuiltinWriteTool` 的两条分支（新建、correct_id）现固定写 `evidenceKind="user_statement"`、`confirmation="confirmed"`。改为：

- 工具调用来源 `captureToolCallSource` 的 eventType 是 `toolcall:<id>`，不是用户条目——不能作为 user_statement 的实据。
- 新建分支：`evidenceKind` 改为 `"model_inference"`，`confirmation` 改为 `"tentative"`。理由：write 工具由助手调用，其内容除非关联到真实用户/执行来源，否则是助手陈述或推断。工具调用来源仍如实登记为来源（操作留痕），但不顶替用户确认。
- correct_id 分支：同样 `model_inference`/`tentative`——助手调用工具纠正一条记忆，不等于用户已确认新内容；修订来源保留 toolcall 操作 + 旧修订来源（service 并集已有），但确认状态不升级。
- 描述同步改：`写入的内容以助手工具调用为来源,登记为 model_inference/tentative;需要用户明确确认的表述应由用户在对话中给出,或经 /pao memory correct 的用户确认通道修订。`
- 这是行为变化，不是类型变化——工具的参数形状不变（content/tags/correct_id/expected_revision），落库字段变。注意 `createMemory` 的 service 校验允许 model_inference/tentative 组合，不改服务端契约。

### 3. `pao/memory/extract-commit.ts` — 重议只对用户实据触发（I03）

`flagForReDiscussion` 的触发条件（`sameConclusion` 分支）在 `conditionsChanged` 外再核对候选身份：

- 候选 `evidenceKind === "model_inference"` 或 `confirmation === "tentative"` → 不触发重议，按「其余实质差异」走 `semantic_conflict`——推断不能替用户改条件，如实跳过留给下一轮重评估。
- 候选 `evidenceKind === "user_statement"`（经第 2 项与引文校验后确为真用户）且 conditions 不同 → 保持 flagForReDiscussion（这是真实的用户重议）。
- `execution` 证据的条件变化属于执行环境变化，按 user_statement 同口径处理——可触发重议。
- 触发条件注释同步写清「重议必须有用户/执行实据，推断不触发」。

## 不改的部分

- `correctMemory`/`flagForReDiscussion`/`setMemoryUsage` 的来源并集口径不动。
- `tools.ts` 的 forget/recall/resolveArtifact 三路不动；captureToolCallSource 的来源登记机制不动。
- `extraction-scheduler.ts` 的 finishJob 对 skipped/semantic_conflict 的归并不动——duplicate_in_batch 不再承载实质差异（I01 修复后批内冲突已走正确出口），remaining duplicate_in_batch 仍是真重复，保持推进游标。
- `runBuiltinMemoryCommand`（session.ts 的 CLI 纠正）不动——它是用户 UI 确认通道，confirmation/evidenceKind 由用户身份正当给出。
