## 确认问题

### F01　S7 规整没有生产编排，来源提交保护也未形成运行链（高）

- **位置与证据：** `K/memory/tools.ts:588` 明确说明 organize 编排尚未实现；`:600` 的 handler 仅 embed/archive。`organize.ts:72/146/296` 的收集、分组、提交前快照检查仅有定义和导出，没有生产调用。`tools.ts:729` 把这份 handler 表交给调度器。`maintenance.ts:195` 的未注册分支把作业记 failed。
- **受支持触发：** 正常任务积累重复经验、条件变化或矛盾记录，期望空闲维护整理；即使通过公开队列登记 organize，也只会失败。不存在实际模型归纳、合并服务调用、输入修订与来源排除的事务内复核链。
- **需求与影响：** S7-01/04/05，以及详细路径“经验整理与维护”第 2—5 步未兑现；Hindsight 的提交前来源复核没有在整理链落实。原 S7 报告将辅助函数写成“增量规整完成”，超出实现。
- **最小修法：** 在现有队列注册 organize handler，接变化登记、按范围选组、必要时模型请求、现有 merge/commit 业务入口及短事务内来源/修订复核；无变化零请求。直接复用现有提交规则，不新增维护框架。
- **验证：** 从真实共享会话结束事件产生变化并进入空闲处理；观察实际 handler、提交结果和 checkpoint。模型等待期间纠正、停用、删除后旧候选不得提交；正式决定不由整理改成新定案。

### F02　公开规整辅助函数的增量游标不成立（中）

- **位置：** `K/memory/organize.ts:85` 按 `updated_at > cursor` 过滤，`:118` 保存 `row.id`，`:120` 把 ID 返回为 nextCursor。
- **触发与证据：** 公开 `collectChangedMemories` 首次返回 memoryId，调用方把返回值继续传入。内存 SQLite 探针首次返回 `a`，再次查询无结果；实际 `mem-…` ID 与 ISO 日期比较同样不是时间游标。
- **影响/需求：** S7-04 的增量整理可能漏掉后续修订。此缺陷当前影响公开函数；不能误写成已经在线上自动整理中发生。
- **最小修法：** 使用 `(updated_at,id)` 作为排序游标并以同一二元顺序过滤，避免批次上限 200 时同一时间的一批被跳过。
- **验证：** 首批、无变化、新增、旧记录修订、超过 200 条同时间记录，均仅返回尚未处理部分。

### F03　重启空闲维护与 home 级前台优先未接通（高）

- **位置：** `K/memory/tools.ts:721` 只有首次 `before_agent_start` 才装维护调度器；`maintenance.ts:109/114` 只订阅所属会话 agent_start/agent_settled；`:162` 扫描全 home pending，`:170` 循环仅检查 accepting。`extraction-scheduler.ts:298` 只消费本会话的 pendingSessions。
- **触发：** 有未完成作业时重启应用但不发用户请求，没有专用维护会话主动装配和唤醒；同 home 的另一会话/宿主开始前台任务，原会话后台也收不到那个 agent_start。同一 drain 被前台中断后，还可继续领取后面的 target。
- **影响/需求：** S7-02 规定“不靠打开记忆页恢复”和普通任务优先；当前会话局部 AbortController 不能证明 home 级调度正确。死持有者任务可以被 recover 为 pending，但不等于宿主会自动执行它。
- **最小修法：** 由既有宿主生命周期建立可关闭的维护会话，并把同 home 前台忙闲信号接到现有调度器；忙时不领取后续任务，空闲再唤醒。保留数据库唯一队列和游标。
- **验证：** 真正启动 CLI/桌面，同 home 遗留作业、无用户会话重启、A 后台/B 前台、至少两个 pending 作业；确保普通任务运行期间无新后台模型请求。

### F04　维护预算门只有定义，实际付费路径不调用（高）

- **位置：** `K/memory/budget.ts:106/166/186` 定义检查、结算、释放，生产引用仅导出；`extraction-scheduler.ts:427` 直接 requestExtraction，`:318` 及 `tools.ts:601` 直接嵌入。未找到调用预算门的生产入口。
- **触发：** 已配置提炼模型或允许云嵌入，但没有后台费用授权，或已达后台限额，正常会话结束仍可进入这些调用。
- **需求/影响：** S7-07 “无后台授权不开展额外付费作业”未落实。外发许可只回答可否发送资料，不替代费用授权。
- **附属实现问题：** `budget.ts:121` 之后只比较“本次预留金额是否超过每日上限”，没有按日累计后台支出；即使只接现有函数，每次 0.05、上限 0.50 的多次请求也无法由这个比较实现每日总限额。
- **最小修法：** 在实际网络请求前复用已有总预算预留，按真实请求而非永久 job 身份结算；在同一预算正本核对当天已用后台份额。未授权/不足时保留等待原因，只有未受理请求才释放。
- **验证：** 用本地脚本 provider 计数，不配置后台额度时请求数为零；多次调用累计达日限额后停止；失败、取消、未知费用仍占相应份额。

### F05　索引重建、备份恢复缺少产品操作入口（高）

- **位置：** `K/memory/index.ts:163` 导出 rebuildMemoryIndex；源码搜索无生产调用。`backup.ts:141/374` 定义备份/恢复；备份仅在 `tools.ts:626` archive handler 被引用，但没有生产 enqueue/archive 调用；恢复没有产品调用，且 memory 桶文件没有导出 backup 接口。`maintenanceHandle.enqueue` 在当前装配中没有生产使用者。

- **验证：** 从实际 CLI/桌面入口触发并观测队列/结果；不靠测试直接调用业务内部函数。

### F06　按项目或类型重建会删除范围外的全文索引（高）

### F07　恢复没有重定位来源，受管成果也未纳入备份（高）

- **位置：** `K/memory/backup.ts:158` 读取 archive_segments 后序列化整库；`:419` 复制段到 targetHome，但未更新恢复库的 `original_path/compressed_path`。`archive.ts:306` 依数据库原绝对路径读取，`:330` 的 `_home` 不参与重定位。备份清单和复制循环仅处理归档段，不含 artifacts 受管内容；`artifacts.ts:614` 按 location.dir 绝对路径读副本。
- **受支持触发：** 按 S7-09 恢复到新目录，原 home 移走/不可用；恢复后的来源读取仍找旧 home。原 home 尚在时也可能读取旧现场而非恢复快照。受管成果文件随旧 home 丢失后无法恢复。

- **最小修法：** 恢复段时在恢复库事务更新实际落点；对受管成果复制所引用版本并重定位；用户 Git 仓继续只保留版本引用，不复制整个仓库。只备份本功能实际管理的内容。
- **验证：** 备份后让旧 home 完全不可访问，再通过新 home 的公开来源/成果读取拿到确切字节；来源与版本均不得回到旧绝对路径。

### F08　恢复重放删除记录仅清索引，没有履行彻底删除（高）

- **位置：** `K/memory/backup.ts:339` 的 purgeDerivedIndexes 仅删 FTS/向量；`:430` 后重放 exclusion，`:441` 清派生索引，保留恢复出的 memories/revisions 和归档正文。源码注释明确允许按 ID 查看正本。
- **触发：** 备份后用户彻底删除内容，恢复旧备份时传入仍存在的 liveHome，以最新删除记录约束恢复。
- **需求/影响：** S7-09 详细路径要求应用 exclusion 后清对应原文/索引再开放读取；当前仅阻止检索，不等于把用户已删除正文从恢复目录清除。旧备份缺少后续删除记录的限制声明是正确的，但不能用它解释已传 liveHome 时的缺失。
- **最小修法：** 在恢复目录复用既有删除计划/正文清理规则，应用最新排除记录后完成正本、归档和相关派生内容清理，再交付读取。无需新增删除框架。
- **验证：** 备份→真实彻底删除→带 liveHome 恢复，按 ID、来源窗口、归档文件、重建索引均不得返回被删正文；未删来源仍可读。

### F09　费用聚合漏掉嵌入及请求异常，并漏标无价格项（高）

- **位置：** `K/memory/usage-query.ts:103/132` 仅消费 type=usage；`embeddings.ts:199/250` 的嵌入成功/失败都是 custom entry，usage/cost 标 unknown，没有 appendUsage；`extract-model.ts:407` 异常直接返回，只有收到 message 后 `:417` 才 appendUsage。`usage-query.ts:174` 仅用 totalTokens>0 判 known，桌面 `K/desktop/memory.ts:1996` 重复相同判定。
- **触发与证据：** 正常云嵌入、模型请求抛异常、供应商只返回 token 不返回价格。内存探针输入 13 token、无 cost，合计得到 unknownCount=0。现有“cost 未返回”测试只断言 cost 缺失，没有断言未知数量。

- **验证：** 各一笔已知、仅 token、异常、取消、嵌入分批及迟到结果，核对请求数、token、已知金额、未知数；同请求在多个成果关联下总计一次。

### F10　请求身份分裂，注入、上下文估算和实际费用不能联查（高）

- **位置：** `K/memory/usage.ts:137` 在 before_provider_request 自建 randomUUID；`context-usage.ts:313` 在 context_with_system 另建 randomUUID，`:332` 保存它。两模块没有传递共享 requestId。`K/desktop/memory.ts:2128` 却用快照 UUID 在 usage.note 中查找实际用量。

### F11　成果登记和使用归因未接入正常执行（高）

### F12　Git 查重没有维护新登记的成果及任务引用（中）

- **验证：** 两任务同 Git 版本，检查返回 ID、详情版本、两个 task 引用及删除保留；原查重测试仅核对 versionId 不足。

### F13　失败回执被成果页面显示为“已验证”（中）

- **位置：** `D/src/features/memory/artifacts-model.ts:41/46` 的 artifactVerificationLabel 仅按 receiptRef 是否存在返回“已验证”；`K/desktop/memory.ts:681` 的版本 DTO 只有 receiptRef，没有结果状态。`artifact-detail.tsx:475` 后来源和回执只列 ID/字符串。

- **需求/影响：** S6-05/09/11 禁止失败标成功验证；用户无法从标签分辨成功、失败和仅留回执。LobeHub 的来源与用量关联未完整呈现。
- **最小修法：** DTO 从实际回执读取验证状态；未解析时显示“有回执/结果待核”，不宣称成功。沿已有来源、会话、文件和用量导航补窄链接与共享费用说明。
- **验证：** 成功、失败、取消、不可读回执和无回执五类；切两个版本时状态、正文、来源一起更新，且能定位生成和验证记录。

### F14　无卡任务完成全部 todo 后仍可恢复旧下一步（中）

- **最小修法：** 以当前任务实际完成的 todo 结果更新接续完成/无下一步状态，保留真实来源；不创建卡或新执行授权。
- **验证：** 同一无卡任务“有待办保存→全完成→压缩/重开→继续”，不得返回旧待办；其他任务接续不变。

### F15　支持的 Electron 宿主没有备份所调用的 SQLite API（高）

- **位置：** `K/memory/backup.ts:165` 调用 db.serialize；`:405` 调用内存库 deserialize。类型强转只绕过类型约束，不会提供运行时方法。
- **受支持触发与证据：** 主控提供的实际 Electron API 探针确认 Electron 37.10.3 / Node 22.21.1 中 db.serialize、db.deserialize 均为 undefined；证据为本审核目录下 `evidence/electron-sqlite-api.log`。因此在桌面内调用备份、或从有效快照恢复，分别会在上述调用处抛 TypeError。当前开发机 Node 24.18.0 的方法存在不能替代支持宿主验证。
- **需求与影响：** S7-09 数据库一致性备份/恢复在支持的桌面运行时不可执行；不是一般待验风险。F07/F08 是运行时 API 修正后仍需处理的独立语义缺陷。
- **最小修法：** 采用支持宿主实际具备的 node:sqlite 备份能力或 SQLite 一致性快照入口，恢复沿受支持的文件/连接方式打开；按现有异步操作契约等待完成，不为此升级全局工具链或增加兼容框架。
- **验证：** 沿产品入口在同一目标 Electron 版本完成备份/恢复，实际回读来源和成果；保持旧 home 不可访问、最新排除生效。复用主控 API 探针，本轮不重复运行。

应保留：项目目标/卡/实例各有正本；worktree 与项目知识分离；进入项目和预览版本不执行；Git 指定 commit 对象读取、缺失不拿当前文件代替；受管成果字节比较；短事务领取与死进程恢复；后台账本与用户会话不双写费用；本地查询不为显示统计额外请求模型。

有价值的结构调整集中在现有边界，不做全库重构：

1. **把后台状态归属收回持久队列。** `maintenance.ts` 的 pendingScopes 与数据库 pending 行重叠，现有 enqueue 的数据正本已是数据库；接线时可让宿主仅发唤醒信号。提炼收尾直跑嵌入与 embed handler 的两套路径应收为一条，避免取消、预算和记账分叉。保留不同 jobKind 的实际语义。
2. **费用只在内核聚合一次。** `usage-query.ts` 和 `desktop/memory.ts:1983` 重复用途汇总与未知判定，已共同出现 F09。由内核一次返回用途分组和请求明细，DTO 只映射，页面只展示。
3. **成果登记事务缩短。** `artifacts.ts:414` 的事务中包含多次同步 Git 子进程和受管磁盘读写，单次 Git 超时可长期占写事务。先准备确切版本/内容，再在短事务核对身份、提交关联；不引入后台快照框架。
4. **备份取消无用途摘要。** `backup.ts:92/210` 为每段额外读取生成 sha256，恢复从不读取校验字段；既不替代昂贵操作，也不改变下一步。删除这项重复读盘和 manifest 字段，保留实际需要的身份、路径和大小。预算指纹使用既有预算 API 契约，另行判断其正本要求，不在本轮随意替换。
5. **上下文查询先选最近文件再截断。** `desktop/memory.ts:2109` 在目录顺序扫描到 limit 后才全局按时间排序，较新会话可被跳过；应按现有会话目录/索引选择候选后排序取最近，不增加数据库正本。用两个目录、旧会话超过 limit、新会话一条的夹具验证。
