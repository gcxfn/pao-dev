## 修改清单（5 项）

### 1. `pao/memory/search.ts` — 词法路：当前修订与来源排除在 perLane 截取前生效（Q1）

现 `lexicalCandidates` 在 `perLane` 截断后由 `searchMemories` 回表卡 `current_revision` 与 `filterExcludedMemories`——limit 小时当前修订被旧修订挤出。

- FTS 与 LIKE 两路的 SQL 在 `filter.where` 上追加当前修订条件：
  - `mode === "current"` 时拼 `f.revision = m.current_revision`（JOIN 已有 `m`）。
  - `historyRevisions === "superseded"` 已由 `historyScopeFilter` 拼 `f.revision < m.current_revision`，保持；`"all"` 不加修订条件。
- 来源排除下推：`mode === "current"` 时在 lane SQL 内排除「任一引用来源已排除」的记忆，SQL 形：
  `NOT EXISTS (SELECT 1 FROM memory_source_links l JOIN source_exclusions e ON (e.source_id = l.source_id OR (e.session_id IS NOT NULL AND e.session_id = (SELECT s.session_id FROM sources s WHERE s.source_id = l.source_id) AND e.entry_id = (SELECT s.entry_id FROM sources s WHERE s.source_id = l.source_id))) WHERE l.memory_id = f.memory_id AND l.revision = f.revision)`。
  注意 `source_exclusions` 的 `memory_id` 列是后加的（旧库无此列）：先按 `filterExcludedMemories` 现有 PRAGMA 探测口径取 `hasMemoryId`，有列时追加 `(e.memory_id IS NULL OR e.memory_id = l.memory_id)`。**此子查询只用于 lane 过滤，不替换最终回表核对**（最终核对仍调 `filterExcludedMemories`，双保险，候选量小）。
- 保留 `searchMemories` 末尾的回表复核（`mem.current_revision !== cand.revision`、`excluded.has`）不动——它防 lane 与合并之间的竞态，不是多余。
- 文件头契约注释更新：补「词法候选在 perLane 截取前已卡当前修订与来源排除」。

### 2. `pao/memory/search.ts` + `scope.ts` — 准确记忆 ID 定点召回（Q2）

现 `extractExactIds` 提取的 `mem-…` 只进 `exactIds` 排序置顶，候选本身仍靠词法/语义命中——正文不含自身 ID 时查不到。

- `searchMemories` 在合并前对 `extractExactIds(input.query)` 的每个 ID 做一次定点读：`SELECT id, current_revision, scope_json, usage_state, merged_into FROM memories WHERE id = ?`，命中且：
  - `mode === "current"`：`usage_state` 匹配调用（缺省 active）、`merged_into IS NULL`、scope 过滤通过 → 候选追加 `{memoryId, revision: current_revision}`。
  - `mode === "history"`：同范围（`historyScopeFilter` 口径）→ 追加当前修订；`historyRevisions === "all"` 时不额外取旧修订（旧修订若含查询词走正常 lane）。
- scope 核对复用现有 `currentScopeFilter`/`historyScopeFilter` 的 where 条件拼到定点 SELECT 上（同一套范围表达，不新写过滤逻辑）。
- 定点候选走 `mergeSearchCandidates` 的 `exactIds` 通道（已存在，relevance=1 置顶）；其余命中照旧。来源排除由最终回表核对兜住（准确 ID 命中被排除条目时如实返回空，不绕过排除）。
- `extractExactIds` 正则不放开——只认 `mem-` 前缀的既有格式，不把工具名混进定点读取。

### 3. `pao/memory/scope.ts` + `session.ts` + 渲染 — branch「来源 vs 适用」语义（Q5）

现 `MemoryScope.branch` 只是记录产生时的分支，scope 过滤不消费——审核确认「不是所有带 branch 的记忆都应被过滤」（项目通用决定跨 worktree 共享）。方案采用**最小语义区分**，不新增字段：

- 在 `scope.ts` 补注释级契约与一处判定函数：
  - `scope.branch` 的语义定案为「产生来源的分支」（来源身份，参与展示），**不**默认做过滤条件——worktree 共享 projectId 的项目决定继续互相可见（I06/`memory-scope.test.ts` 既有断言保持）。
  - 新增导出 `isBranchScoped(content: MemoryRevisionContent): boolean`：当 `conditions` 明示分支限制（匹配 `/分支|branch|worktree/` 且含具体分支名模式）时返回 true——这条只是给「明确受限条目」一个可识别的判定入口，**不**在 SQL 层做自然语言解析。
- `searchMemories` 在最终回表核对后对 `mode === "current"` 的命中追加一条程序性过滤：调用方 `scope.branch !== undefined` 且命中条目 `isBranchScoped(content)` 且命中 scope.branch 与当前 scope.branch 不同 → 从 hits 剔除。无明确受限标记的条目照常共享（不串的判据=显式标记，不靠猜测）。
- 注入渲染（`session.ts renderBuiltinHitBody` 与 `session.ts` meta 行）把命中 `scope.branch`/`executionRoot` 带进 `来源`/`状态` 标注：有 branch 时 `状态:` 行追加 `来源分支:{branch}`，让模型能看到来源语境而非隐形字段。
- `types.ts` 的 `MemoryScope.branch` 注释更新为「产生来源的分支/执行根标识；适用范围由 conditions 显式声明，范围过滤见 scope.ts」。
- **不做**：不新增 `appliesToBranch` 结构化字段、不在 FTS/向量 lane 做分支 SQL（受限条目占比小，最终核对处过滤代价可忽略）、不自动推断「这条记忆只适用某分支」。

### 4. `pao/memory/embeddings.ts` + `search.ts` — 向量读取按范围下推（Q7）

现 `readMemoryVectors` 只按 `model+dimension` 读全库，内存里再过 scope——同 home 其他项目与旧修订也解码。

- `readMemoryVectors` 签名扩展为 `readMemoryVectors(db, model, dimension, filter?: ScopeFilter)`：传了 filter 时 SQL 改为
  `SELECT v.memory_id, v.revision, v.model, v.dimension, v.vector FROM memory_vectors v JOIN memories m ON m.id = v.memory_id WHERE v.model = ? AND v.dimension = ? AND ${filter.where}`。
  filter.where 里 `m.` 前缀照旧可用（`currentScopeFilter`/`historyScopeFilter` 条件全在 `m` 与参数上）；`f.revision` 形式不出现（向量路修订条件改用 `v.revision`——给 `historyScopeFilter` 的 `superseded` 分支做适配：`historyScopeFilter` 返回的 where 含 `f.revision < m.current_revision`，调用方需将其替换为 `v.revision < m.current_revision` 再传入，或让 `historyScopeFilter` 接受一个修订列名参数——**选择给 `historyScopeFilter` 加可选 `revisionColumn` 参数**，`"f.revision"`/`"v.revision"` 二选一，保持同一处范围表达不复制）。
- `semanticCandidates` 调用处改为传入当前 filter（mode=current 时另加 `v.revision = m.current_revision`，与词法路同口径；`currentScopeFilter` 的 where 可直接拼接该条件进 filter 参数——**推荐新增小工具**：在 `scope.ts` 导出 `withCurrentRevision(where, column)` 或直接在 `semanticCandidates` 里拼 `filter.where + " AND v.revision = m.current_revision"`，后者更简单，采用之）。
- `memory_vectors` JOIN `memories` 后行数已限范围；`inScope` Map 核对保留（防 JOIN 后到读取之间的竞态）但最终 `scored` 的 `inScope.get` 仍要查——把现有 `scopeRows` 查询保留即可，不删。
- 测试夹具路径注意：`putVector` 直写 `memory_vectors` 不经过 `memories`——JOIN 后旧 fixture 行必须仍命中：现有测试夹具都配套 `add()`（先插 memories 行），无孤儿向量；若复核发现孤儿向量夹具，改夹具而非放宽 JOIN。

### 5. `test/pao/memory-search.test.ts` + `memory-scope.test.ts` — 定向断言

沿用现有夹具风格新增用例（具体断言以实现后行为为准，先写失败再修）：

- **Q1 回归**：同 ID rev-1/rev-2 词同时命中、`limit=1` 返回 rev-2（复刻审核 `current-revision-before-limit` 场景为正式用例）；来源被排除的条目占满 perLane 时范围外有效条目仍返回。

## 关键事实（已核实，直接采用）

- `lexicalCandidates`（search.ts:130）FTS/LIKE SQL 均 JOIN `memories m`，`filter.where` 以 `m.` 前缀拼条件，追加 `f.revision`/`v.revision` 类条件无语法障碍。
- `searchMemories`（search.ts:455-494）的最终回表核对已覆盖 `current_revision` 与来源排除——lane 下推后它是兜底双保险，保留。
- `historyScopeFilter`（scope.ts:107）`superseded` 分支已拼 `f.revision < m.current_revision`，但只被词法路使用；向量路当前用 `matchesHistoryRevisionSelection` 内存核对——本次下推后两处口径须一致。
- `filterExcludedMemories`（scope.ts:125-159）已含 `hasMemoryId` PRAGMA 探测与两种排除形式（source_id / session_id+entry_id），lane SQL 按同一语义写。
- `source_exclusions` 表结构（store.ts:198-206）：`exclusion_id/source_id/session_id/entry_id/reason/memory_id`；`memory_id` 列为可空，旧库可能无此列（PRAGMA 探测先例已存在）。
- `MemoryScope.branch` 当前唯一消费者是 `project-identity.ts` 的 scope 解析与 I06 夹具——无任何过滤消费，本次新增的是「显式受限条目」的判定，不是给所有 branch 记录加过滤。
- 测试夹具 `add()`/`putVector` 配套使用，向量行均有对应 memories 行；孤儿向量不在现有夹具中。
- `renderBuiltinHitBody`（session.ts:71）已有 `referenceOnly`/`needsReDiscussion` 标注先例，分支标注同型追加。
