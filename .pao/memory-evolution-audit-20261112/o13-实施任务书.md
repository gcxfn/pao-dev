## E14：新任务初始绑定（P1）

### 绑哪些资源、在哪绑（侦察修正后的口径）

宿主「任务」有两类，分开处理：

1. **交互会话（CLI/桌面主会话）**：审核口径「新任务真实加载新版本」的直接验收对象。装配时把**全部已登记且 `effective_version` 非空**的资源绑进本任务——成本是多挂几个 versionDir 进 priority 通道。如实标注现状：主会话装载面本就不含 `pao配置/skills`（受控技能只经 worker 派发装载），给主会话绑定后 prioritySkillPaths 生效的前提是主会话本来就装同名技能；绑了但主会话没装 → 绑定存在但无行为差异，**不算伪造使用**（绑定语义是「本任务若用该资源就固定用这个版本」）。
2. **worker 派发任务（受控技能的真实使用现场）**：`dispatch-core.ts:734-753` 把配方/工作流声明的技能解析成 `<paoHome>/pao配置/skills/<name>` 绝对路径 → `runner.ts:282` `--skill <path>` spawn 独立 pao CLI 子进程；该子进程 main.ts:802 createRuntime 同样走绑定解析。**派发装配处（dispatch-core 解出技能清单后、spawn 前）才是真正的「实际使用」绑定挂点**：技能路径 basename → `skill:<name>` resourceId，`bindTaskResources(taskId=worker标识, resourceIds)` 落绑定 → worker 进程 createRuntime 读到绑挂 versionDir 进 prioritySkillPaths 压过 `--skill` 传来的原路径（priority 排在 additional 前；两条路径都挂时同名由绑定版生效）。
   - **taskId 口径**（侦察发现、审核未点名）：worker 的 `会话标识` 有值时 taskId=它（子进程 sessionId=它，绑定键天然一致）；`--no-session` worker（会话标识 undefined，dispatch-core.ts:1566 失败路径会置空）没有 sessionId——派发层须生成稳定 taskId（`执行标识` randomUUID 现成，或 `卡号-尝试号`）作为绑定键，并在 spawn 参数里把它同时传给 worker（经 `--session-id` 或环境变量，让 worker 进程内装配解析用同一键）。选最小：有会话标识用它，没有用 `执行标识`（同一尝试的生命周期内稳定，重试新尝试自然换键）。
   - **worker 进程内**：createRuntime 的 `resolveTaskBoundPathsForSession(sessionManager.getSessionId())` 读到的 sessionId 就是绑定键——前提是派发层用同一值落绑定且传给 `--session-id`。无会话 worker（`--no-session`）没有 session 目录也没有 sessionId——绑定的任务解析按传入键走，worker 侧需确认 main.ts 在无会话模式下 sessionManager.getSessionId() 的行为（若无会话返回生成 id 则绑定键必须用「派发层写入的、经 `--session-id` 传入的值」，`--no-session` 与 `--session-id` 互斥时 worker 侧绑定解析按跳过处理并在任务书报告如实记「无会话 worker 不参与绑定换版」——该形态本身短命，权重低）。

### 落点（两宿主 + 派发，共用内核函数）

- `evolution/host-mount.ts` 增 `ensureTaskBindings(store, {taskId, paoHome, resourceIds?})`：resourceIds 缺省时读 `evolution_resources WHERE effective_version IS NOT NULL` 全量（主会话口径）；显式传时按清单（派发口径）→ `bindTaskResources` 批量落绑定 → 返回 `resolveTaskBoundResourcePaths` 同形结果。库未建/清单为空 → 空清单不建绑定。
- CLI 主会话：`main.ts` `resolveTaskBoundPathsForSession`（:573）先 ensure（全量口径）再解析——mode 从 `readonly` 换 `readwrite`。
- 桌面主会话：`pao/desktop/host-mount.ts` `resolveDesktopTaskBoundPaths` 同样先 ensure——store mode 从 `readonly` 换 `readwrite`。session-supervisor 调用处签名不变。
- 派发：`dispatch-core.ts` 组 `runOptions.skills` 完成后（:736/:753 两处汇合点之后），对已解析技能路径集合 basename→`skill:<name>` 调 `ensureTaskBindings(store, {taskId, resourceIds})`——dispatch-core 有 paoHome，store 在其进程内开闭（readwrite）。worker 进程的 createRuntime 解析照走既有路径（只读，不 ensure——派发层已写）。
- **失败口径**：bindTaskResources 同事务整批，任一资源无 effective 即全拒——派发侧按已登记清单传，残余失败（竞态删除）记 dispatch 警告不拒派（技能装载不阻塞业务）；主会话侧 ensure 失败如实上抛（绑定读不出来时静默降级会让会话拿错版本无留痕，现 resolveTaskBoundPathsForSession 已按此口径 throw）。

## E15：激活基线分离（P1）+ publish 后自动激活接回

### 分清两个基线（activation.ts e 段）

现 e 段拿「资源根当前指纹」比「候选 base_version」。正确语义是「**验证期没人改过验证所依据的版本正文**」，不是「资源根等于旧版」。侦察复核的细化口径——引入「根基线」概念，比「版本目录在不在」更稳：

- **根基线（rootBaseline）= 资源根最后被同步到的版本**：首轮 = 登记快照 baseVersion；激活成功后若不回写资源根（审核明确「不要逐文件覆盖正式资源根」），根基线**不随 effective 前进**——它留在最初快照值。显式来源：首个 `activation='effective'` 凭据的 `from_version`（首轮激活时记的 baseVersion 快照），或资源行上的显式字段（若加列成本低）。判定：根指纹 vs rootBaseline——不一致 = 资源根被人工改过 → conflict（保留 :315/:337 用例的防人工改语义，断言口径从「比 base_version」改为「比 rootBaseline」）。
- **验证基线 = candidate.base_version**：若它已是已发布版本（存在完整 `versions/<dirSafe>/<baseVersion>/` 目录）——验证依据是版本目录正文，核对**该目录**指纹 === baseVersion（versionId 即清单哈希），不要求资源根等于它。第二轮（base_version=v1、effective=v1、根仍 v0）走这里：版本目录核对过、根基线核对过（根==v0==rootBaseline）→ 不冲突，合法激活。
- 两个核对都过才进事务：「验证对象没被换」由版本目录指纹守住；「用户现场被人工改」由根基线指纹守住——人工改资源根后照样 conflict，不丢原防线。
- 实现：e 段拆两支——`versions/<dirSafe>/<baseVersion>/` 完整 → 比版本目录；否则比根（兼容首轮）。另加根基线核对：rootBaseline 从该资源首个 effective 凭据 from_version 解析（无 effective 凭据=未激活过 → 根基线=当前 effective_version 即 baseVersion 快照，与首轮行为等价）。fingerprintResourceRoot 复用现成共享实现。

### publish → activate 接回

- `evolveOneProblem`（tools.ts:1427 段）发布成功后追加：`activateCandidate(store, {candidateId, paoHome, expectedEffectiveVersion: resource.effectiveVersion ?? problem.base_version, reason})`——expected 取发布前读到的资源指向，竞态冲突由 activation 事务内重读收口。
- 结果分支：`ok+versionId` → 记 `pao-evolution-activated` 诊断；`status:"conflict"` → 记 `pao-evolution-verdict`（verdict="activate_conflict", reason 透传），问题不推进终态（留待人工/下轮）；契约失败 → skip 诊断。激活失败不留半套：activation 事务天然原子，published 版本仍在盘上可由恢复流程报待激活。
- 是否自动激活沿既有开关：`auto_evolution_enabled=0` 的资源 activation 前置 d 已拒，编排层不用再加判断。

## S9-05：安全点换版的绑定/加载/重载同步（P1）

现 `switchSessionResourceAtSafePoint` 先写绑定再视忙闲 reload——busy 时 DB 新版+runtime 旧版分叉且无人消费 deferred 完成态。修法（保持现有模块切分，最小改）：

- **绑定写入与实际加载同事务语义化**：`switchSessionResourceAtSafePoint` 增加「换版后不显示已生效直到 reload 真完成」口径——把「绑定已写但 reload 未完成」作为显式中间态返回 `{status:"deferred", pendingTo: newVersionId}`；driver 内部把 pending 换版记在 record 上，`runPendingReload` 完成后才向外发换版完成事件（若走 emit）。**不引入第二套绑定状态**——绑定行 + switch_history 照常写（它是意图记录），「生效展示」以 reload 完成为准。
- busy→deferred 路径补消费方：`runPendingReload` 现只处理 reloadPending；换版挂的 pending 与 reloadPending 用同一标志即可（换版后的 updateAdditionalPaths 是同步的，reload 一发生新路径即生效），关键是**失败时不能把绑定已换当成功报出**——`runReload` 失败已走 closeError 路径，如实上抛不改语义。
- CLI 侧对应物：CLI 没有会话 supervisor；`switchTaskResourceAtSafePoint` 若要在 CLI 暴露（如 /pao evolution switch 命令），在命令层直接调 binding 函数+提示「下次会话生效」，不伪装热生效。本轮无 CLI 命令需求则不新增——桌面 supervisor 是唯一已接换版的宿主，先把它修对。
- 生产调用者：desktop 详情页/通知区的「换版」动作入口（Electron 测过函数级，未接 UI 触发）——本轮在 driver 层把语义修对，UI 触发接线若 desktop bridge 已有对应写桥则挂上；没有则在任务书报告里如实留「driver 就绪、UI 触发未接」。

## S9-06/07/08/09：使用观察与退步回退接入（P1）

### recordUsed 挂点（侦察修正）

「使用技能」的真实信号不是单个工具调用——技能是 SKILL.md 注入上下文，**装载即采用**；成败挂在任务/回执终态上，不是某个 tool_result 的 isError。两路接入：

1. **worker 派发（受控技能的真实使用现场）**：派发装配已 `ensureTaskBindings`+`--skill` 挂载；worker 终态回执（卡完成/失败，O08 已接的 `executeSubmitReceipt`/`executeDelivery`/派发回执通道）按「本任务绑定清单 ∩ 已登记受控技能」逐条 `recordUsed`：outcome=success（回执 delivered）/failure（失败终态），receiptRef=回执引用（`receipt:<id>` 或卡路径定位）。派发进程内有 paoHome+store——挂点在回执登记旁，不开新通道。
2. **交互会话**：`registerBuiltinMemory` 挂 `agent_settled`（capture.ts:487 同款事件先例）——读本会话 active 绑定清单（`listTaskBindings(taskId=sessionId)`），对每条绑定记 `recordUsed`（versionId 缺省取绑定值），receiptRef=`session:<sessionId>:settled:<turn>`，outcome 从本轮回执/终态映射（无明确成败信号时只记 used 不带 outcome 前缀——used 行存在即「该版本被真实装载采用」，成败分列留给 worker 回执路）。幂等：同一 (sessionId, resourceId, versionId) 同 versionId 同 settled 轮次只记一条——按 toolCallId/轮次拼 receiptRef 天然去重，或先查同 receipt_ref 已有行跳过。
- 失败口径：recordUsed 返回 invalid_input（无绑定/停用）→ 不写不噪音（预期内）；其他错误如实 console.warn。
- 注意 `tool_result` 事件（types.ts:1231 带 toolName/isError/toolCallId）**不用于** used 判定——技能使用与工具调用不一一对应，拿工具结果当技能采用会错记；工具级 used 语义不成立就不记，宁缺不伪造。

### judgeRegression/handleRegression 挂点

- 触发源两路（侦察确认现成件）：
  1. `pao_evolution_declare` 登记的问题若带 resourceId 且指当前 effective 版本：窄工具**补传** resourceId——宿主从本会话已绑定清单（`listTaskBindings(taskId=sessionId)`）按技能/资源名匹配填充 + baseVersion=绑定 versionId，不让模型自报；登记后 `judgeRegression`（problemId 结构化判据：该 problem 候选发布过当前坏版 → original_problem）→ true 即 `handleRegression`（内含 rollback+affectedTasks+cancelPending）。调用点：登记受理成功后同步判定（declare 工具 execute 内或紧接的编排步），不等后台 drain——退步是即时安全问题。
  2. worker 回执 outcome=failure 且该任务绑定版本有 problemId 关联线索时同样可判 normal_breakage（坏版有 used 行+任务 active 绑定在坏版）——本轮在派发回执登记处补一次 judgeRegression 调用（problemId 无明确线索时不传，靠 used 行+绑定判 normal_breakage）。
- affectedTasks 消费（S9-09）：`handleRegression` 返回里 taskId=sessionId 的——①**本进程内**（CLI 当前会话/桌面 supervisor 持有的 record）：桌面 driver 对 record 调 `switchSessionResourceAtSafePoint` 换到 targetVersion；CLI 侧会话内换版无热通道（装配期一次性读绑定）——CLI 当前会话把绑定换掉（switchTaskResourceAtSafePoint 落库）+ 提示「下次会话生效」，不伪装热生效；②**跨进程**（别的窗口/已关会话的 taskId）：绑定先切（安全点换版落库不受影响——它只写绑定表），下次装配自然读新版；正在运行的跨进程任务本批触达不到——如实记 notification 不伪造已停。
- restoreVersion 的 affectedTasks 同病（desktop/memory.ts:3266-3301 返回后无人消费）——同一消费函数复用：算出 affectedTasks 后走上面①②同款分发。
- 通知递送（侦察确认现成通道，不新建框架）：CLI 走 `notifySurface.notify`（worker/notify.ts，category "ruling" 会主动唤醒主会话注入 pao-dispatch-notify 段）；桌面走 `record.undeliveredLoadNotices`/`hostUiRequest` 或已有回退通知区（memory.ts:2910 lastRollback 已读）；+ ledger `pao-evolution-regression` 诊断留痕。
