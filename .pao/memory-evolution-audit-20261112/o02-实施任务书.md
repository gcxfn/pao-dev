目标：**同内容同条件的重复仍复用补链，但确认状态、证据类别、理由或条件的实质变化走明确修订或重议，不再被去重吞掉；confirmed 必须有与证据类别同身份的实据；CLI 与写入工具的明确纠正进 `correctMemory` 同一入口并保留条件/理由/真实来源；无依据的关系不再建立**。不新增费用正本、不改 sources 表结构、不动停用恢复语义。

工作根：`D:\AI\workspace\pao-dev`；业务代码在 `PAO/packages/coding-agent/src/pao/`（下称 `pao/`）。改前先读 `PAO/AGENTS.md`（内核规则）与本文件引用的每个源文件。工程命名 ASCII 英文；注释/文档中文；成员包内禁止 pnpm/npm install；不跑全量测试。

## 总原则

- **同一规则只实现一次**：确认的语义差异集中在提交侧（extract-commit）按既有 service 原语表达，不新建第二个修订接口；页面/CLI/工具三路纠正最终都落 `service.correctMemory`。
- **来源是修订的依据，不是展示的附件**：任何「升级确认状态/改条件/改结论」的修订必须同时带来能回读到该次依据的来源；只有本次候选的来源可以承担这个身份，不能拿旧来源顶替。
- **没有依据不升级**：用户没有明确确认的不转正；模型不能凭工具调用或助手文本冒充用户陈述；条件/理由保持未写不缺省造。
- **普通推断不自动重议**：候选仅推断或 tentative 变化不触发 flagForReDiscussion；触发条件保持「同 kind + 结论归一相同 + conditions 不同」这一既有门槛，本任务只修它丢失旧来源的问题。

## 修改清单（6 项）

### 1. `pao/memory/extract-commit.ts` — 批内/来源级去重先核对实质差异（F04）

`findSourceLevelDuplicate` 现在只比「kind + 归一结论 + active」，命中即补链返回。改为：

- `findSourceLevelDuplicate` 返回值从 `string | undefined` 改为 `{ memoryId: string; currentRevision: number; content: MemoryRevisionContent } | undefined`（取当前修订内容随 ID 一起回）。
- 命中后由调用方在补链前做差异判断，抽出公共判断（供第 4 步同结论分支复用）：

```ts
/** 候选与既有当前修订相比是否有实质差异：任何一项不同即不能按纯重复处理。 */
function semanticDelta(candidate: ValidatedCandidate, content: MemoryRevisionContent): {
  confirmationChanged: boolean;
  evidenceKindChanged: boolean;
  rationaleChanged: boolean;
  conditionsChanged: boolean;
} {
  return {
    confirmationChanged: content.confirmation !== candidate.confirmation,
    evidenceKindChanged: content.evidenceKind !== candidate.evidenceKind,
    rationaleChanged: (content.rationale ?? "") !== (candidate.rationale ?? ""),
    conditionsChanged: (content.conditions ?? "") !== (candidate.conditions ?? ""),
  };
}
```

- 来源级命中（第 4 关）的处理：
  - 全部四项无变化 → 保持现状：补链、返回 duplicate（同来源重复结果不新建，不变）。
  - **仅 confirmation 从 tentative → confirmed 且 evidenceKind/conditions/rationale 未变** → 走新出口「确认升级」：调用 `service.correctMemory`（service 注入面扩展，见下），replacement 取候选字段（conclusion/conditions/rationale/evidenceKind/confirmation），`sourceIds: candidate.sourceIds`，`expectedRevision: row.current_revision`，`source` 取该候选首个来源 ref（sourceIds 与 sourceRefs 同批，缺 ref 退回 `{sessionId:""}`）。成功 → outcome `{status:"submitted", candidateIndex, memoryId, revision}` 语义新加一档 `"corrected"`？——见下「outcome 契约」；失败 → `status:"rejected"`。
  - conditions 或 rationale 变化 → 不再按 duplicate 短路：继续走第 5 关的 sameConclusion/flag 分支；具体出口在第 5 关统一处理（见第 2 项）。
  - confirmation 反向（confirmed → tentative/rejected）或 evidenceKind 变化 → 同样转第 5 关统一处理（不能静默降级或换类别）。

- service 注入面从 `Pick<MemoryService,"createMemory"|"flagForReDiscussion">` 扩为 `Pick<MemoryService,"createMemory"|"flagForReDiscussion"|"correctMemory">`——三个方法的调用点都在同一处，不新增第二套接口。

### 2. `pao/memory/extract-commit.ts` — 同结论分支按差异分派（F04 主体）

第 5 关 `sameConclusion !== undefined` 内现为「条件不同 → flag，条件相同 → 补链」。改为按 `semanticDelta` 分派：

- 无差异 → 保持补链 + duplicate（不变）。
- `conditionsChanged === true` → 保持 flagForReDiscussion 重议路径（第 3 项修其来源口径）；其他差异若同时存在也一并交给重议（条件变化优先——它是业务上明确的重议信号）。
- `conditionsChanged === false` 且仅 confirmation tentative→confirmed（evidenceKind/rationale 未变）→ 与来源级一致的「确认升级」correctMemory 路径。
- 其余组合（含 confirmed→任何、evidenceKind 变化、rationale 变化、confirmed→confirmed 但 rationale 变）→ 不做静默处理：outcome 记 `status:"skipped"`，reason 新增 `"semantic_conflict"`，detail 里写明哪一项不一致。理由：模型重述同结论但改了理由/降了状态，没有足够依据替用户决定是纠正还是新决定；如实跳过并把候选留给下一轮重评估，比写错关系安全。`semantic_conflict` 与既有 `stale_request_snapshot` 一样不推进游标、不重放（finishJob 对 skipped 的归并保持；见第 6 项确认）。

### 3. `pao/memory/service.ts` — correctMemory/flagForReDiscussion 保留旧来源（F11/F09 数据面）

- `correctMemory`：当 `input.sourceIds === undefined` 且 `sourceIdsFromEvent` 为空时，新修订来源 = `sourceIdsForRevision(db, id, row.current_revision)`（现状已如此）。**追加一段**：显式给了 `input.sourceIds` 时，新修订来源 = `[...new Set([...input.sourceIds, ...sourceIdsForRevision(db, id, row.current_revision)])]`——纠正带来新来源但旧依据不丢（旧结论的原文出处仍随当前版可查；F11 要求「保留旧来源」）。`sourceIdsFromEvent` 登记出来的操作来源同样并入（事件来源 + 旧来源 + 显式来源三者并集）。注意 setMemoryUsage 已是这个口径（previousSourceIds ∪ operationSourceIds），correctMemory 对齐它。
- `flagForReDiscussion`：同样把显式 `input.sourceIds` 与「上一修订来源」并集，而不是替换（现状是替换——F11 的出处）。触发重议的来源是本次候选的，旧决定的原始依据不能随标记修订消失。
- 两个函数的「来源随修订走」注释同步改写：来源是修订的证据链，追加不替换；需要单独标「本次触发来源」的由 revision_links 的 relation（supersedes/flagged_rediscussion）区分，不靠换来源表达。
- `sourceIdsFromEvent` 的 eventType 参数保持 `"user"`（页面/CLI 用户操作）；service 层不区分调用端，调用端在 source.entryId 缺席时仍得完整并集。

### 4. `pao/memory/extract-model.ts` — confirmed 的证据身份闭合（F08）

`validateCandidate` 第 3 段改为按 evidenceKind 分别核对实际来源身份：

```ts
// confirmed 必须有与 evidenceKind 同身份类别的实据：
// - user_statement：至少一条来源 eventType === "user"，且该来源在 candidate.sourceIds 内；
// - execution：至少一条来源 eventType === "toolResult"；
// - model_inference：前面已拒，不重复。
// 引用闭合：quotedSpan 的 sourceId 必须包含在 candidate.sourceIds 内（引用了未声明来源 = 虚构依据）。
const spanSourceIds = new Set(candidate.quotedSpans.map((span) => span.sourceId));
const unclosed = [...spanSourceIds].filter((id) => !candidate.sourceIds.includes(id));
if (unclosed.length > 0) reasons.push(`quotedSpan 引用了未列入 sourceIds 的来源:${unclosed.join("、")}`);

if (candidate.confirmation === "confirmed") {
  if (candidate.evidenceKind === "model_inference") {
    reasons.push("confirmed 候选不允许 evidenceKind=model_inference（推断不能自证为定案）");
  } else {
    const byId = new Map(entries.map((entry) => [entry.sourceId, entry.eventType]));
    const required = candidate.evidenceKind === "user_statement" ? "user" : "toolResult";
    const hasEvidence = candidate.sourceIds.some((id) => byId.get(id) === required);
    if (!hasEvidence) {
      reasons.push(
        `confirmed/${candidate.evidenceKind} 候选的来源中没有 eventType=${required} 的实据条目（${required === "user" ? "缺用户明确选择" : "缺执行回执"}）`,
      );
    }
  }
}
```

- 顺手把「user 或 toolResult 都算确认来源」的旧判断删掉——它就是 F08 里「工具回执冒充用户决定」的入口。
- rationale 不缺省补造保持；理由未知时 content.rationale 仍为 undefined（现状已对，不回归）。
- 提示词同步收紧一行：`confirmed 的 user_statement 至少引用一条 user 条目；execution 至少引用一条 toolResult 条目；quotedSpan 的 sourceId 必须全部出现在本条 sourceIds 里。`（EXTRACTION_PROMPT 尾部追加，不改现有长文。）

### 5. `pao/memory/session.ts` + `pao/memory/tools.ts` — 明确纠正进同一入口（F03/F09）
