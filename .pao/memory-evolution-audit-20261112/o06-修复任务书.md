## 根因（已核实，供定位）

- **D1 整理只能跑一次**：`maintenance.ts:159 enqueue` 调 `createJob`（extraction-jobs.ts:131），后者 `getJobRowByScopeKey` 命中既有 done 行直接返回（L134）；`claimJob` 在 `status==='done'` 返回 undefined（L168）。done job 复用后永不可再领。且 `runJob` done 分支只 `completeJob`（L238），`advanceCursor` 只在未完成分支（L241）——**完成批次的 cursor 没落库**。
- **D4 晚到作业不唤醒**：`enqueue` 只 `pendingScopes.add`（L167）不触发 `drainQueue`；提炼在 settled 启动的异步收尾里登记 organize，同轮 settled 的 drain 已扫完空队列，之后无新 settled 则永久 pending。
- **D2/D3 自动合并改判**：`findLexicalDuplicates`（organize.ts:272）只按归一化结论相同配对；`runOrganizeMaintenance` 复核未核对条件等价与确认状态；`mergeMemories` 只拒「双 confirmed 且结论不同」，其余复制 keep 内容——keep 方向按 `sortByExpiry`（过期状态+memoryId），不保证 confirmed/条件优先生存。
- **D5/D6 引号空格参数**：session.ts L1403/1431/1453 用 `\S+` 单片段正则，`"a b"` 带空格被截断或判用法错误；rebuild 截断后仍提示「重建完成 0 行」伪装成功。

## 修复项

### R1（D2+D3，P1）：自动整理不改判正式决定

在 `runOrganizeMaintenance` 的候选→合并链路上加等价与确认保护（`organize.ts`）：

- **条件等价核对**：词法/语义候选配对后，比对两条记忆的 `conditions`。条件**不等价**（归一化后不同，含一方有条件一方无）→ 不自动合并，保留为候选不提交。互斥条件（「仅限单机」「仅限多机」）必须都留下。
- **确认状态保护**：一条 confirmed 一条 tentative → 不自动合并（confirmed 决定不得并入/降级成 tentative）。只有确认状态兼容（同 confirmed 且条件等价、或同 tentative 且条件等价）才允许 merge。
- **keep 方向**：允许合并时 keep 必须选 confirmed 侧/权威侧；不因 `sortByExpiry` 的 memoryId 序让 confirmed 被 tentative 吃掉。
- **不扩大契约**：不动 `mergeMemories` 手动合并公开契约；服务层「双 confirmed 结论不同拒并」规则不变。保护逻辑放 organize 调用侧/复核，不改服务签名。

验收：D2 互斥条件两决定都保留不合并；D3 confirmed 不并入 tentative、正本仍 confirmed。

### R2（D1，P1）：done 维护作业可被后续变化重新激活 + 完成批次存 cursor

- **重新激活**：`enqueue` 遇到同 scopeKey 的 done（或 failed）job 时，按既有状态机恢复为 pending 可领取（重置 owner/attempt 语义按提取作业既有约定），而非幂等返回 done。**只改维护类 job（embed/organize/archive）生命周期；extract job 的来源幂等契约不动**——可在 createJob 加 jobKind 分支或维护侧专用复活入口，不能让 extract 的 done 也被复活。
- **完成批次存 cursor**：`runJob` done 分支（L238）也要 `advanceCursor` 保存 handler 返回的 cursor（若 handler 提供了 cursor），再 completeJob。organize handler 需返回本批 nextCursor 供持久化。

验收：D1 第一次整理完成后，新增相同结论+重新登记+settled，handler 再执行一次、attempt_count 增加、两个重复正本被合并；完成批次 cursor 落库非 NULL。

### R3（D4，P2）：空闲时登记的维护作业唤醒既有 drain

- `enqueue` 成功登记后：若当前**空闲**（`foregroundBusySize==0` 且 `accepting` 且非 drain 进行中会自我接续），唤醒一次 `drainQueue`。drain 进行中登记的作业在当轮 targets 并集外时，本轮结束后须再续一轮消费（drain 循环结束前复查 pendingScopes/库内 pending，或 enqueue 标记触发 drain 尾部再扫）。
- **保留契约**：复用现有 `foregroundBusySize` 前台忙、`accepting` 取消、串行锁；前台忙时不抢、不新增轮询服务/维护平台。唤醒是「触发既有 drain」，不是新调度循环。

验收：D4 settled 结束后异步登记 organize，无需另一次用户回合，job 被消费到 done、handler 调用数>0。

### R4（D5+D6，P2）：管理命令引号/空格参数解析

`session.ts` rebuild/backup/restore 三处：

- 统一参数解析：支持 `"带空格值"` 与不带引号单值。抽一个小函数 `parseCommandArgs`（或逐命令正则支持 `"..."` 与 `\S+` 两态），rebuild 的 `--project`/`--kind`、backup 的目录、restore 的 `<备份目录> <目标目录>` 都用同一规则。
- **不伪装成功**：解析失败/参数缺失 → `ctx.ui.notify` 明确报错（用法提示），不进入业务调用；rebuild 不得把截断的项目 ID 当合法范围报「重建完成」。
- restore 同规则修复（本轮审核未跑恢复业务，但解析缺口一致，一并修）。

验收：D5 带引号空格项目路径 rebuild 正确解析项目 ID、目标记忆索引重建；D6 带引号空格目录 backup 正常登记 archive 作业、库内有对应行。
