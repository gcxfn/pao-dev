## 1. O04-I01 / P1：适用分支仍被错误地绑定到来源分支

位置：[scope.ts:178](../../PAO/packages/coding-agent/src/pao/memory/scope.ts#L178)、[search.ts:554](../../PAO/packages/coding-agent/src/pao/memory/search.ts#L554)。

`isBranchScoped` 只返回条件中是否出现分支名，未返回具体适用分支。搜索随后比较调用方分支与 `hitScope.branch`。但后者已明确定义为来源分支，不等于 conditions 中声明的适用分支。

A1 在 feature-a 记录“仅适用 feature-b 分支”的决定，分别从两条分支按准确 ID 查询。实际 **feature-a 命中、feature-b 返回空**，与明确条件完全相反。这是已有 ASCII 分支名及 conditions 的正常输入，不涉及复杂语言解析。

修法：从既有明确条件格式取出适用分支，与调用方分支比较；`scope.branch` 继续保存来源身份。无分支限制的项目通用决定继续跨 worktree 共享。明确的适用条件不能依赖来源分支存在或与其相同才生效。

## 2. O04-I02 / P1：候选先截取、再过滤，仍会丢掉有效结果

位置：[search.ts:341](../../PAO/packages/coding-agent/src/pao/memory/search.ts#L341)、[search.ts:371](../../PAO/packages/coding-agent/src/pao/memory/search.ts#L371)、[search.ts:522](../../PAO/packages/coding-agent/src/pao/memory/search.ts#L522)。

合并先按用户 limit 截取，分支适用过滤随后才执行；语义路也先按 perLane 截取，来源排除只在合并结果上执行。词法路新增的来源排除 SQL 没有覆盖语义路。

| 场景 | 数据与查询 | 实际结果 |
|---|---|---|
| A2：分支受限候选挤掉共享结果 | 一个高分候选仅适用 feature-a，一个较低分候选为项目共享；从 feature-b 查询 | limit=1 返回空，limit=3 返回共享结果 |
| A3：已排除语义候选挤满 lane | 21 条高分候选的来源均已排除，一条较低分候选有效；只走固定向量语义路 | limit=1 返回空，limit=30 返回有效结果 |

两例都不是有效结果不存在，而是它在截取时被不应返回的候选占位。A3 的窄查询 perLane=20，有效结果根本没有进入合并；只扩大合并 limit 也无法补救。

修法：在各路 perLane 截取及最终 limit 之前统一核对候选资格。语义路的来源排除沿用既有排除规则；分支适用核对同样应在截取前完成，词法路需要时补取到足量有效候选。保留最终回表核对，不能仅扩大固定倍数掩盖漏召回。

## 3. O04-I03 / P2：准确 ID 不支持仅历史修订范围

位置：[search.ts:505](../../PAO/packages/coding-agent/src/pao/memory/search.ts#L505)、[search.ts:517](../../PAO/packages/coding-agent/src/pao/memory/search.ts#L517)。

定点读取在 history 模式固定使用 `historyScopeFilter(..., "all")`，候选固定为 `current_revision`。当调用方指定 `historyRevisions="superseded"` 时，后续核对又剔除这个当前修订，因此准确 ID 召回返回空。

A4 创建记忆并纠正为 revision=2，再以该准确 ID 查询 history/superseded、limit=1。revision=1 实际存在，结果却为空。该组合属于公开 `SearchMemoryInput` 的历史检索契约。

修法：定点读取也遵循请求的历史修订范围；superseded 应生成满足 `revision < current_revision` 的修订候选，再进入既有合并与排序流程。
