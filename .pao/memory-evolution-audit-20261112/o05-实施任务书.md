## 修改清单（4 项）

### 1. `store.ts` + 新建 `source-fts.ts` + `search.ts` — 来源原文词法索引（Q3）

**表**：在 `SCHEMA_SQL` 追加（readwrite 打开即建；`CREATE VIRTUAL TABLE IF NOT EXISTS` 幂等，旧库无迁移问题）：

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS source_fts USING fts5(
    source_id UNINDEXED,
    session_id UNINDEXED,
    entry_id UNINDEXED,
    event_type UNINDEXED,
    project_id UNINDEXED,
    task_id UNINDEXED,
    content,
    tokenize = 'trigram'
);
```

只索引「可保存文本」：`sanitizeContent` 之后的 `event.content`——字符串直取；数组取各 text 块 text 拼接；对象取 `.content` 递归提取文本。附件引用块、图片块不产文本。**实现一个 `extractIndexableText(content): string` 放在 `source-fts.ts`**，与 capture 同口径但独立（capture 已脱敏，这里只取文本不写库）。

**写入**：`captureCommittedEntry`（capture.ts:274-321）在 `registerSource` 成功后，同一事务内调 `upsertSourceFts(db, sourceId, {sessionId, entryId, eventType, projectId, taskId, content: extractIndexableText(content)})`。`upsertSourceFts`/`dropSourceFts` 仿 `upsertMemoryFts` 写进 `source-fts.ts`（先 DELETE 再 INSERT；调用方事务内）。**三个旁路写入方**（knowledge archiveSource、project-operation-source）**不接入**——它们不是会话讨论原文，需求只覆盖「未提炼讨论」；如复核要求覆盖再补。

**查询**：`searchMemories` 在 `mode === "history"` 时追加 source lane。新建 `sourceCandidates(db, scope, query, limit)`：
- FTS5 `source_fts MATCH ?`（同 `lexicalCandidates` 的 MATCH→LIKE 降级骨架），trigram 短词自动落 LIKE。
- 范围过滤：`s.project_id = ?`（sources JOIN 取）或 `source_fts.project_id = ?`——以 sources 行 project_id 为准（source_fts 的 project_id 是冗余便于过滤）。**taskId 不预过滤**（同 current 记忆的 taskId 语义：NULL 或匹配）。
- 排除：对命中 sourceId 调 `isSourceExcluded({sourceId})` 与 `isSourceExcluded({sessionId, entryId})` 任一命中即剔除（与 extract-commit/task-continuation 同口径）；同时剔除「任一引用该来源的记忆被删」场景——删除时 memory_id 有值或全局排除（`e.memory_id IS NULL`）都会写 source_exclusions，两种查法已覆盖。
- 截断：去重后按 rank 取前 `sourceLaneLimit`（建议 `Math.max(10, 2*limit)`，独立于 perLane——source 命中不参与 RRF）。

**返回**：`SearchMemoriesResult` 增加 `sourceHits?: SourceSearchHit[]`；`SourceSearchHit` 新类型进 types.ts：`{sourceId, sessionId, entryId, eventType, projectId?, taskId?, segmentId?, capturedAt, snippet}`，`snippet` 为命中行文本截 ≤200 码点（不整段回读，展开交 Q4 工具/桌面）。service.searchMemory 透传 `sourceHits`；`SearchMemoryResult` 同步加字段。

**mode 语义**：sourceHits 只 history 返回；current 不返（「未提炼原文」是历史追溯语义；current 只查当前有效修订——与 S3-06「history 模式包含归档段」一致）。

**删除/重建挂点**：
- `applyDatabasePlan`（deletion.ts:1617-1622）删 `sourceRowsToDelete` 时同事务 `DELETE FROM source_fts WHERE source_id = ?`；`rewriteSegmentFile`/`redactSegmentLines` 整行移除 entryId 时（deletion.ts:445-554）**同步 `DELETE FROM source_fts WHERE entry_id = ?`**——entryId 级清理比 sourceId 级更稳（覆盖同 entryId 多 eventType 来源）。两处在 `applyDatabasePlan`/`advanceFileObjects` 的事务边界内调。
- `rebuild-index.ts` 加 `rebuildSourceFts`：从 `sources` JOIN `archive_segments` 逐段回读（复用 `readSegmentLines`）提取各 sourceId 的 indexable text 重建；`dropExisting` 同口径。归档段解压读取只在重建时做，正常查询不预解压（S3-06）。
- 备份/恢复无需特殊处理：`serialize()`/`deserialize()` 整库快照自动覆盖新表。

**验证**：新采集未提炼事件 history 命中 sourceId；停用/删除来源后不再命中；封存段回读仍命中；重建后命中一致。

### 2. `tools.ts` — 新增 `pao_memory_read` 只读详情/来源展开工具（Q4）

新工具 `pao_memory_read`（只读，不写记忆正本）：

- **参数**（`readParams`）：`memory_id`（可选）、`source_id`（可选）、`entry_id`（可选锚点）、`offset`（可选，可负）、`limit`（可选，1-200）。三种用法互斥须校验：
  - 只 `memory_id`：`getMemory` 取当前修订详情（含 sourceSummaries、sourceIds）。
  - 只 `source_id`：`readMemorySource` 展开该来源，`entry_id` 缺省用来源行自身，`offset/limit` 分页。
  - `memory_id` + `source_id`：先 `getMemory` 核对 `source_id` 属于该记忆当前修订的 `sourceIds`（含 `sourceSummaries[].sourceId` 并集），不一致返回 `invalid_input`；一致再 `readMemorySource`——与桌面 `readDesktopMemorySource` 同口径。
- **返回**：沿用 `{content:[{type:"text",text}], details}`。文本逐事件渲染为可读行（`[时间][eventType] 文本`），details 带 `events/hasMore/nextOffset/startLine/endLine/segmentId`——模型拿到 `hasMore:true` 知道要再翻页。
- **expand 记账**：`source_id` 展开成功后调 `service.recordMemoryUsage({action:"expand", memoryId, revision, sessionId, usageRef:sourceId, requestId:requestIdFor(ctx.sessionManager)})`；`memoryId/revision` 仅在 `memory_id` 入参给定时记（来源展开不带记忆归属时不写 usage——与桌面口径一致：桌面也只在同传 memoryId+revision 时记）。requestId 复用 `request-identity.ts` 的 `requestIdFor`，不新建。
- **排除/缺失**：`readMemorySource` 已返回 `source_missing`；工具如实透传错误文本，不伪造内容。`isError:true`。
- **权限**：`pi.registerTool` 在 tools.ts:791-794 加一行；`MEMORY_FRESHNESS_GUARDED_TOOLS` **不加**——只读工具不阻断。`builtin` 供应商路注册；非 builtin 供应商路与 worker 角色不装（同现四工具口径）。
- **桌面**：无需新增 IPC/preload——工具经同一 inline `paoExtension` 自动获得；模型侧工具与桌面页面调用面互不干扰。

**验证**：实际会话工具调用展开准确修订与来源；缺失/排除来源返回 `source_missing`；`hasMore/nextOffset` 连续翻页；`memory_id+source_id` 不一致返回 `invalid_input`；expand 记账落 `memory_usage`。

### 3. `session.ts` + `resident.ts` — 完整渲染预算（Q6）

**预算对象**：把「整条实际渲染成本」纳入，不是只按 `hit.内容`：
- 单条渲染成本 = `renderMemoryHit(hit, i, sessionId)` 全长（含 `内容` + meta 行 + `N. ` 前缀 + 换行缩进）。`formatMemoryHitMeta` 与 `renderMemoryHit` 已有，直接复用做预算计算。
- 消息级固定开销 = `[pao 自动召回] 当前可见 N 条…` 头 + `AUTO_RECALL_RESULTS_BOUNDARY` + 行间 `\n`。

**实现**：
- `session.ts` 新增 `renderedHitChars(hit, index, sessionId)` = `Array.from(renderMemoryHit(hit, index, sessionId)).length`；`AUTO_RECALL_MESSAGE_OVERHEAD` 常量 = `Array.from(`[pao 自动召回] 当前可见 ${n} 条…${BOUNDARY}`)` 模板长（n 用最大值估算，或先算 n 再拼——选「先按候选数估算上限，装完后按实际 n 重算一次」的简化：预算核对用 `remaining` 时以「`hit` 完整渲染长 + 固定消息头（按 hits.length 上界）」计，避免逐条重排）。
- `selectForContext`/`budgetAutomaticRecallHits` 的 `bodyChars` 累计改为累计**渲染成本**（`renderedHitChars`），预算常量仍是 `AUTO_RECALL_BODY_LIMIT=2000`/`AUTO_RECALL_HIT_LIMIT=800` 但语义改为「渲染后码点」；`__paoWholeOnly` 条目按整条渲染长判 `keep < renderedChars` 时整项省略（逻辑不变，只是口径换成渲染长）。
- `resident.ts:280-302`：候选数与注入数分开——`searchMemory` 的 `limit` 从固定 `AUTO_RECALL_TOP` 改为 `AUTO_RECALL_CANDIDATE_LIMIT`（建议 8，召回候选多于注入上限，让 selectForContext 有挑选余地）；`selectForContext` 的返回 hits 数仍受预算约束自然 ≤ 渲染预算可容纳条数（不再硬卡 3 条——预算够时可注入更多条，这是「按上下文余量」的直接兑现）。
- **上下文余量信号**：`before_agent_start` 里 `ctx.sessionManager.buildSessionProjection()` 已在用（resident.ts:292）；新增「按 `estimateProjectedContextTokens(projection, branch)` + `model.contextWindow`（缺省 128000）算 `availableChars ≈ (contextWindow - projectedTokens) * 4`」估算，`AUTO_RECALL_BODY_LIMIT` 的实际生效值取 `min(2000, availableChars * 0.05)`（注入正文最多吃余量 5%，防记忆挤占任务上下文；比例是资源约束常量，写进注释）。`contextWindow` 从 `ctx.modelRegistry`/`ctx` 取——按实际能拿到的字段写，拿不到退回固定 2000。
- `budgetAutomaticRecallHits`（刷新路）同口径改渲染成本。

**保留**：`__paoWholeOnly` 整项省略、修正截断注记、`因正文预算省略` 计数、可见修订去重——这些已有效，只是预算口径从「正文码点」换成「渲染码点」。

**验证**：含长条件+多来源摘要的条目，渲染后总码点超 2000 时整项省略（不截断条件）；候选 8 条预算够时注入 >3 条；接近上下文上限时注入条数减少；`formatMemoryHitMeta`/`renderMemoryHit` 不变。

### 4. `archive.ts` + `capture.ts` + `tools.ts`/`maintenance.ts` — 事件段封存接入（F10）

**触发点**：`capture.ts` 的 `agent_settled` 处理器（offSettled，capture.ts:395-402）尾部——本会话本轮采集刚同步完成、且无该段 writer 正在追加（capture 的写入是同步 `appendFileSync`，settled 时本进程内不会有第二个 capture 写者；knowledge/页面操作旁路不走 capture 钩子，封存后它们再追加会自动开新段，语义兼容）。

**实现**：
- `captureCommittedEntries`/`captureCommittedEntry` 不直接 seal；在 `registerCapture` 的 `offSettled` 尾部，对本会话 `findOpenSegment(db, sessionId)` 得到的 unsealed 段调 `sealSegment(store.db, paoHome, segmentId)`。失败不阻塞 settled（seal 是后台优化，原段保留可读）——`console.error` 记录，不向上抛。
- **不在 turn_end seal**：同一 agent 回合内用户可能继续发消息，seal 后下一条目只是开新段，安全但收益仅截断读放大；settled 是更准确的「本轮采集结束」边界。session_shutdown 不额外 seal——close() 已卸钩子，且 shutdown 时封存无收益（下次会话重开是不同 sessionId 新段）。
- **多会话安全**：`sealSegment` 幂等且只动本 sessionId 的 unsealed 段；`openSegmentForSession` 幂等找回——其他会话/进程的 unsealed 段不受影响。不需要跨进程锁（每会话段独立，`acquireSessionControl` 只在删除正文时用，封存量级不需要）。
- **读放大收尾**：`countLines` 全读只在追加时发生，settled 后段被 seal 不再追加——长会话的累计读放大随段封存自然截断（每段独立计数）。
- **maintenance handler 不接**：复用 `'archive'` jobKind 会引入表重建迁移（CHECK 枚举）与 scopeKey 语义混杂（`archive:{backupDir}` vs `archive:seal:{sessionId}`）；settled 同步 seal 更简单且满足「无该段 writer 的既有空闲/会话安全边界」。如复核要求「崩溃/异常退出后遗留 unsealed 段」兜底，再评估是否加维护作业——本任务书按 settled 单点接入，报告中写明该取舍。

**验证**：实际会话采集→agent_settled→`archive_segments.status='sealed'`（或 `uncompressed`）；原文仍可读；故意压缩失败（如段文件被删）行标 `failed` 且原段保留可读；重开会话新事件开新段。
